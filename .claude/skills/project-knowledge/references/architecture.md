# Architecture

## Tech Stack

| Layer | Technology | Why |
|-------|-----------|-----|
| **Backend** | Java 21 + Spring Boot 3.5.x + Spring MVC on virtual threads | Synchronous-code clarity (stack traces stay shallow and module-local; no `.flatMap`/`switchIfEmpty`/`onErrorResume` chains) combined with virtual-thread concurrency (`spring.threads.virtual.enabled=true`) — Tomcat dispatches each HTTP request on a fresh VT. Spring Framework 6.x, Spring Security 6.x unchanged. See `patterns.md` → `## Virtual Threads` for the runtime model and observed pinning surface. |
| **Database** | MongoDB 8.0 | Document model fits the flexible subscriber custom fields and funnel step structures; native support by JobRunr for job storage |
| **Cache** | Redis 7.4 | Brute-force counters (per-email + per-IP for login, change-password, password-reset) and analytics cache (1-min TTL). Sessions are stored in MongoDB via `spring-session-data-mongodb`, not in Redis. |
| **Job Scheduling** | JobRunr (`jobrunr-spring-boot-3-starter`) | Distributed background jobs with MongoDB storage; supports multi-instance deployments via atomic distributed locking; built-in dashboard. Must use `jobrunr-spring-boot-3-starter` — not compatible with Spring Boot 4.x. |
| **Frontend** | Nuxt 4.4.x (Vue 3 + TypeScript) | SSR-capable Vue framework; good DX for admin-style SPAs; TypeScript strict mode enabled. Nuxt 3 EOL July 2026 — Nuxt 4 used from project start. |
| **Frontend i18n** | `@nuxtjs/i18n@^9` + Vue I18n 11 | Two locales: `uk` (default, no prefix) and `en` (`/en/...`). Cookie `i18n_lang` for persistence; `useLocaleHead({ seo: true })` drives `<html lang>` and hreflang alternates. `langDir: 'locales'` resolved relative to Nuxt 4's `restructureDir: 'i18n'` — locale JSONs live at `frontend/i18n/locales/{uk,en}.json`. |
| **Frontend E2E** | `@playwright/test@^1.59` | Single E2E spec for golden-path locale switching. `webServer: pnpm dev` auto-spawn; `reuseExistingServer: !CI`; chromium-only. |
| **Containerization** | Docker + Docker Compose | Single-command local dev environment; production deployment on VPS |

## Data Model

Full collection schemas are in `docs/db-schema.md`. Key collections:

- `users` — email, hashed password, name, status (`pending|active|blocked|deleted`), `isSuperAdmin` flag, embedded email-verification and password-reset token hashes (SHA-256; raw token only in email URL)
- `sessions` — managed by `spring-session-data-mongodb`; holds `SecurityContext`, `principal` field (used to terminate sessions by user), `maxInactiveInterval`, TTL index on `expireAt` (auto-created by Spring Session at startup; physical expiry is database-level so it survives reactive-cleanup issue #226)
- `projects` — owned by one user, has name/description/timezone, supports soft-delete
- `bots` — one connected per project on MVP. Stores AES-256-GCM-encrypted token (`encryptedTokenCiphertext` + `encryptedTokenIv`), 3-char `tokenSuffix` for the UI mask (`{telegramBotId}:•••...{tokenSuffix}`), SHA-256-hashed `webhookSecretHash` (plaintext only exists in memory during Connect — `WebhookSecretVerifier` hashes the incoming `X-Telegram-Bot-Api-Secret-Token` header and constant-time-compares via `MessageDigest.isEqual`), Telegram identity (including nullable `ownerChatId: Long` — populated by Epic 04b via atomic `findAndModify` with `ownerChatId=null` predicate on the first private `/start` against a CONNECTED bot; first-private-`/start`-wins, accepted race threat with attackers documented in 04b user-spec R2), and `status` (CONNECTED / DISCONNECTED). Disconnect is soft — encrypted fields are nulled, document retained for audit; reconnect creates a NEW document. Three indexes: non-unique `(projectId, status)` for lookups, partial unique `(telegramBotId)` filtered `status=CONNECTED` (platform-wide identity), partial unique `(projectId)` filtered `status=CONNECTED` (per-project single-bot rule). Pre-checks + index = defense-in-depth (see `patterns.md` → Bot Connection)
- `raw_updates` — durable inbox for inbound Telegram updates (Epic 04b). Stores `projectId`, `updateId`, `payload` (raw Telegram JSON as BSON via `org.bson.Document`), `processingStatus` (`PENDING|DONE|FAILED` enum persisted as uppercase via `enum.name()`), `processingError` (scrubbed + truncated to 1024 chars; populated only when status=FAILED), `createdAt`. Two indexes: compound unique `(projectId, updateId)` for idempotency (Telegram retry on delayed 200 OK), TTL `createdAt expireAfter=90d` with partial filter `processingStatus IN ['PENDING', 'DONE']` — **uppercase** enum literals match `name()`-persistence; FAILED rows are NOT auto-deleted to preserve audit visibility until the JobRunr dashboard is enabled in Epic 10.
- `subscribers` — scoped to a project; Telegram identity fields, `tags` array, `customFields` document (key = `CustomFieldDefinition.name`, per-type validated/normalized by `CustomFieldValueValidator` — DATE stored as `Instant`, never `OffsetDateTime`, which has no Mongo codec), status (`active|unsubscribed|blocked|deleted`) + lifecycle timestamps (`subscribedAt`/`unsubscribedAt`/`blockedAt`/`deletedAt`/`lastSeenAt`). Indexes (Epic 09): unique `(projectId, telegramUserId)`; text index `language="none"` on firstName/lastName/username (weights 3/3/5 — **whole-word** match, no stemming/prefix, see `patterns.md`); secondaries `(projectId,lastSeenAt:-1)`, `(projectId,subscribedAt:-1)`, `(projectId,status)`, `(projectId,tags)`
- `funnels` — embeds an ordered `FunnelStep` array (per-type fields flat, no `_class` discriminator — Decision 12; `order` rewritten from array index by the server). **Phase 6 (`15-message-composer`)** replaced the three flat message step types with one `MESSAGE` composer step holding an ordered `List<ContentBlock> blocks` (immutable `ContentBlock`/`MediaItem` records + `BlockType` enum `TEXT|IMAGE|VIDEO|AUDIO|FILE|ALBUM`, flat no `_class` — Decision 1); the old flat msg fields (`text`/`parseMode`/`imageUrl`/`caption`) are gone. Phase 2 graph fields per step: stable `id` (server-minted), `next` (default target), `List<Button>` (immutable `Button` record `type|label|targetStepId|url`; Phase 2 `MENU`-only, Phase 6 reused by the `MESSAGE` composer's last non-album block), optional `timeoutValue/timeoutUnit/timeoutTargetStepId`. Phase 3 adds `eventName` per step (only `EMIT_EVENT`; carried through `copyOf`); the funnel-level `keywords: List<String>` it added was **moved per-trigger in Phase 8** (see trigger model below). Phase 5 adds three per-step fields (only `SUBSCRIBE_TO_FUNNEL`; carried through `copyOf`): `targetFunnelId`, optional `targetEntryStepId` (cross-funnel entry; null → target start), `endParentAfter` (boolean) — cross-funnel reference is the pair `(targetFunnelId, targetEntryStepId)` since step ids are unique only within a funnel. **`16-persistent-keyboard`** adds two reply-keyboard step types `SET_KEYBOARD`/`CLEAR_KEYBOARD` with five nullable per-step fields (carried through `copyOf`, `keyboardRows` defensively deep-copied like `blocks`/`buttons`): `keyboardText` + `keyboardParseMode` (mandatory rendered text, both types), and SET-only `keyboardRows: List<KeyboardRow>` (immutable `KeyboardRow(List<KeyboardButton>)` / `KeyboardButton(String)` records, flat no `_class`, 1..10 rows × 1..4 buttons), `isPersistent`, `oneTimeKeyboard`; `resize_keyboard` is hardcoded `true` at send and never stored. No migration (nullable adds). `status` (`draft|active|paused`, lowercase persisted via `.name()`), `allowReEnter`. **Phase 8 (`17-funnel-multi-entry`)** replaced the flat trigger trio (`triggerType`/`triggerValue`/`keywords`) with `List<Trigger> triggers` — each `Trigger = {triggerType, triggerValue, keywords, entryStepId}` (flat embedded POJO, no `_class`; `triggerType ∈ {on_start, keyword, tag_added, custom_field_set, event}`; `keywords` moved per-trigger here; `entryStepId` is non-null only for `event` triggers = mid-graph entry, null for all others) — plus a denormalized nullable scalar `onStartTriggerValue` synced from the `on_start` element on every save (`""`/blank → null). A funnel can now hold N triggers (multi-entry). Index change (Phase 8): the Phase-3 partial-unique `(projectId, triggerType, triggerValue)` was dropped and replaced by partial-unique `(projectId, onStartTriggerValue)` filtered `status=active AND onStartTriggerValue exists` — a multikey unique index over `triggers.*` can't express on_start uniqueness (partial filters are document-level, so they'd wrongly bind shared `event` values), so the single on_start value is denormalized to a scalar; old index dropped before `MongoTemplate` auto-creation by the `FunnelTriggerIndexReconciliation` BeanPostProcessor (see `patterns.md` → Funnel Engine Phase 8). `(projectId)` for hard-delete cascade. No migration — `funnels`/`funnel_executions` manually wiped on deploy (no prod data)

## Data Flow

### Incoming Telegram Message

Telegram posts an update to `POST /webhooks/telegram/{projectId}`. `WebhookPayloadSizeFilter` (a servlet `Filter`) enforces a 1 MB cap scoped to the webhook path (rejects chunked + missing Content-Length too) without raising Tomcat's global `maxPostSize`. The controller looks up bot by `(projectId, status=CONNECTED)`, then project (existence + soft-delete) — both lookups collapse to a uniform 404 (anti-enumeration); then verifies the secret via `WebhookSecretVerifier`. On success it persists to `raw_updates` and enqueues a JobRunr job with a deterministic UUID (`UUID.nameUUIDFromBytes(rawUpdateId)`) directly on the current virtual thread — blocking work on a VT is cheap, so no offload boundary is needed. A `DuplicateKeyException` from the save triggers a self-heal re-enqueue (deterministic UUID makes it idempotent — recovers from a prior mid-flight enqueue failure). Returns 200 OK to Telegram in under 100ms (P99). `ProcessTelegramUpdateJob` (JobRunr worker) parses `/start [payload]` / `/stop`, atomically populates `Bot.ownerChatId` on the first private `/start`, calls `SubscriberServiceImpl` (Epic 09: rate-limited auto-register / reactivate on `/start`, mark-unsubscribed on `/stop`) + `FunnelTriggerServiceImpl.fire(projectId, chatId, "on_start", payload)` (Epic 06 — matches an active funnel on the exact `(triggerType, triggerValue=payload)` and starts a snapshot execution; `/stop` → `cancelActiveFor`; fully `try/catch(Throwable)` so a funnel error never fails the webhook update). Phase 2 adds a typed `callback_query` dispatch branch (before the message fallback): resolve CONNECTED bot → `FunnelTriggerServiceImpl.advanceOnCallback(projectId, chatId, callbackData, callbackQueryId)` (error-isolated), event `telegram_callback_query` emitted before the flip. Phase 3 (`12-funnels-triggers`) adds keyword dispatch in the plain-text branch (after subscriber upsert): if the subscriber has an in-flight `waiting_for_reply` execution → keyword is suppressed (menu precedence wins); else `FunnelEventService.dispatchForSubscriber(..., keyword, text, 0)` contains-matches the text against active keyword funnels and starts every match (fan-out). The keyword dispatch is wrapped so any fault is swallowed (greppable WARN `KEYWORD_DISPATCH_ERROR`) and the worker still returns 200 (error-isolation). Writes events via `EventService.logEvent` BEFORE flipping `processingStatus=DONE`. Re-entry guard short-circuits on DONE (handles JobRunr retry overlap). On exception: scrubs + truncates `processingError`, writes FAILED atomically, rethrows for JobRunr's default retry (10 attempts, exponential backoff).

### Funnel Step Execution

`FunnelExecutionEngine` runs a JobRunr `@Recurring` sweep (default 30s, `FUNNEL_SCHEDULER_INTERVAL`) that picks up `funnel_executions` whose `nextRunAt` is due. Each step is guarded by an atomic `findAndModify` claim (`stepRunStatus pending→in_progress`) so a JobRunr retry, an instance restart, or a second replica never re-sends — at-most-once per step (exactly-once is unreachable; a mid-tick crash leaves the row `in_progress`/stuck, the deliberate at-most-once-over-liveness trade-off). The side-effect-then-claim-conditional-advance ordering is the commit point. `StepExecutor` dispatches per `StepType`: Message (Phase 6 composer — sends N messages, one per `ContentBlock`, all under one claim, via `TelegramSender.sendText`/`sendPhoto`/`sendVideo`/`sendAudio`/`sendDocument`/`sendMediaGroup`; `VariableTemplateRenderer` substitutes `{user.*}`/`{custom.<key>}` and escapes per `parse_mode` — author markup untouched; album element type per item — Decision 5; inline keyboard + park-on-reply attach to the last non-album block), Delay (parks via `nextRunAt`→`waiting`, never `Thread.sleep`), Add/Remove Tag and Set Custom Field (routed through `SubscriberServiceImpl`/`SubscriberCustomFieldsService` — the sole writers, so audit events fire; an unknown custom-field key is silently skipped). Consecutive non-Delay steps run within one tick. Set Custom Field on a DATE field accepts the `@now` sentinel, resolved to the execution-time instant (`Clock`-driven). A pre-send status gate cancels the run if the subscriber is no longer `active`; after the last step the run is `completed`. **Phase 3** adds the `EMIT_EVENT` step (synchronously calls `FunnelEventService` for the current subscriber at `enrollDepth+1`, returns `CONTINUE` so the parent funnel proceeds) and makes Add Tag / Set Custom Field *active triggers*: `SubscriberServiceImpl.addTag` / `recordCustomFieldsSet` fire `tag_added` / `custom_field_set` via the dispatcher AFTER their idempotency guard + audit write (a no-op write does not fire), with origin depth threaded explicitly (0 from manual/API callers, `execution.enrollDepth+1` from funnel-step callers — never a ThreadLocal). **Phase 2** moved navigation to a graph (resolve step by `currentStepId`, advance along `next`/button targets; per-tick step budget `FUNNEL_MAX_STEPS_PER_TICK` replaces the old `size+1` loop guard, trip → `failed` + marker `FUNNEL_STEP_BUDGET_EXCEEDED`). Phase 6 folded `MENU` into the composer: the `MESSAGE` step's last non-album block, when it carries `buttons`, sends an inline keyboard and *parks on reply* (`waiting_for_reply`, `nextRunAt`=timeout deadline or `null`) — callback wire-contract `{executionId}:{buttonIndex}` unchanged. A removed/unknown `stepType` in a legacy document reads as `StepType.UNKNOWN` (`StepTypeReadConverter` + `FunnelMongoConfig`) and terminal-fails only that execution instead of crashing the sweep tick (Phase 6 tolerant-read fail-safe). **Phase 5** adds the `SUBSCRIBE_TO_FUNNEL` step: a fire-and-forget cross-funnel enroll via `FunnelEventService.enrollSpecificFunnel` (depth-cap → rate-limit → fail-closed `projectId` target resolve → re-enter → `insertExecutionAt(targetEntryStepId)`) that inherits the parent's `telegramBotId`, then returns `Outcome.COMPLETE` (`endParentAfter=true` → parent `completed` immediately) or `CONTINUE` (parallel). A non-`active`/deleted/foreign target at runtime is a silent skip + greppable WARN (parent continues). Two wakeup paths: a button press enters via the separate `resumeOnCallback` (subscriberId-scoped claim-CAS, anti-IDOR — NOT the sweep), while an optional timeout is picked up by the existing sweep (`nextRunAt`=deadline; menus without a timeout have `nextRunAt=null` so the sweep predicate never matches them). **`16-persistent-keyboard`** adds two fire-and-forget reply-keyboard steps: `SET_KEYBOARD` renders `keyboardText` and sends a Telegram `ReplyKeyboardMarkup` (`{keyboard:[[{text}]], is_persistent, resize_keyboard:true, one_time_keyboard}`), `CLEAR_KEYBOARD` sends `ReplyKeyboardRemove` (`{remove_keyboard:true}`) — both through the existing 6-arg `TelegramSender.sendText` (the markup is an ad-hoc `Map` serialized verbatim, no typed wire DTO), both return `CONTINUE` so the keyboard survives execution completion and the engine never parks. A button tap routes back as plain text through the existing Phase-3 keyword dispatch — no new engine path, no keyboard stack / auto-restore (return-to-menu is an authoring pattern: a `SET_KEYBOARD` at the end of branches). **Phase 8 (`17-funnel-multi-entry`)** adds **redirect-or-start** on a fired `event`: `FunnelEventService` (the single dispatcher) re-scans the matched funnel's `triggers[]` for the matched element's `entryStepId`, then — if the subscriber already has an in-flight execution of THAT funnel (`status ∈ {running, waiting, waiting_for_reply}`, found via a trusted probe) — calls the new `FunnelExecutionEngine.redirectExecution` (a `claimForRedirect` CAS scoped by `subscriberId`+`funnelId`, anti-IDOR, accepting the three in-flight statuses; sets `currentStepId=entryStepId` resolved against the execution's own `stepsSnapshot`, unparks, drives now) — one execution per funnel per subscriber, mutating the existing row (no second execution); else it starts fresh at `entryStepId` via `insertExecutionAt`, honouring `allowReEnter`. CAS-loss (a sweep owns the row) → best-effort no-op + greppable WARN, no retry; broken cursor (entryStepId absent from snapshot) → terminal-fail only that execution. See `patterns.md` → Funnel Engine and `docs/roadmap/funnels.md`.

### Broadcast Delivery

On trigger (immediate or scheduled), one `broadcast_message` record is created per subscriber in the audience segment. JobRunr workers consume the queue and call TelegramSender at approximately 25 messages per second (below Telegram's 30/sec ceiling). Each message status is updated to `sent`, `failed`, `blocked`, or `unsubscribed`. When all records are processed the broadcast status is set to `completed` and aggregate stats are written.

### External API Event (Phase 3)

An external system calls `POST /api/integrations/v1/events` with an `X-API-Key` header and body `{event_name, telegram_user_id?, subscriber_id?}`. The `@Order(1)` STATELESS security chain (`securityMatcher("/api/integrations/**")`, CSRF off) runs `ApiKeyAuthFilter`: SHA-256-lookup of the presented key → pins the project (project comes from the key, never the path/body — anti-IDOR), stamps `lastUsedAt`; any key problem (missing/malformed/unknown) → one uniform bodyless 401 (anti-enumeration). `EventsController` then validates the DTO (`event_name` slug `^[A-Za-z0-9_-]{1,64}$`; ≥1 identifier required else 400; `subscriber_id` wins when both present), applies a fail-open global Redis rate-limit (`bf:rate:events` → 429 over the cap), resolves the subscriber project-scoped (`subscriber_id` else `telegram_user_id`), and dispatches via `FunnelEventService` at depth 0 (external root). Response matrix: 202 (start) / 202 (no-op — subscriber exists, no listener) / 404 (unknown subscriber) / 400 (bad body) / 401 (key) / 429 (rate-limit); never 5xx (an engine fault is swallowed → 202); never auto-creates a subscriber. The `EMIT_EVENT` funnel step shares the same `event` namespace/dispatcher — see Funnel Step Execution above.
