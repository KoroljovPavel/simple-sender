# Patterns

## Git Workflow

### Branch Structure

- `main` — production-ready code. Direct commits forbidden; all changes via Pull Requests.
- Feature branches: `feature/epic-name-short-description` (e.g., `feature/02-auth-registration`)
- Bug fix branches: `fix/short-description`
- All branches cut from `main`, merged back to `main` via PR.

### Commit Convention

Conventional Commits: `type(scope): short description`. Allowed types: `feat`, `fix`, `chore`, `refactor`, `test`, `docs`.

### Pull Request Rules

- PR requires at least one approval before merge
- All CI checks must pass (build, tests, lint)
- Squash merge to keep `main` history clean
- Delete branch after merge

### Security Gates

- **Pre-commit:** gitleaks scan — blocks commits containing secrets or tokens. Installed via `bash scripts/install-hooks.sh` (idempotent). Soft-failure: exits 0 with warning when gitleaks not installed (does not block commits).
- **Pre-push:** full test suite must pass (planned — not yet implemented)

## Testing Requirements

- Unit tests for all business logic (funnel engine, broadcast delivery logic, segment evaluation)
- Integration tests for API endpoints: `@SpringBootTest(webEnvironment = RANDOM_PORT)` + `MockMvc` (via `@AutoConfigureMockMvc`). Servlet-stack canonical client on the MVC + virtual-threads runtime; runs in-process against the dispatcher servlet, no real socket. Use `TestRestTemplate` + RANDOM_PORT only for the AC2 P99 latency probe where a real wire path matters.
- No mocking of the database in integration tests — use real embedded MongoDB. **Exception:** skeleton/security-only tests that never query MongoDB may use `@MockitoBean` for connection factories (see Decision 6 in Epic 01 tech-spec). This exception is scoped to Epic 01 only.
- Test coverage target: 80%+ on business logic modules

### Spring Boot Test Specifics

- Use `@MockitoBean` (not deprecated `@MockBean`) — required from Spring Boot 3.4.0+. Import: `org.springframework.test.context.bean.override.mockito.MockitoBean`
- Spring Boot 3.5.x requires two mocks to prevent auto-config from connecting to live databases: `com.mongodb.client.MongoClient` (synchronous driver) and `org.springframework.data.redis.connection.RedisConnectionFactory` (synchronous Lettuce). The pre-flip reactive driver / reactive connection-factory types are gone from the classpath after the migration to Spring MVC on virtual threads — any old test still declaring them will fail to compile.

## Virtual Threads

### Why VT and what this gives us

The backend runs on Spring MVC + Tomcat with `spring.threads.virtual.enabled=true` (set in `application.properties`). Every incoming HTTP request is dispatched on a fresh virtual thread; outbound `RestClient` calls (`TelegramApiClient`, `TelegramSender`), the synchronous Mongo driver (`mongodb-driver-sync`), the Lettuce sync API used by the brute-force counters in `AuthService`, and the JobRunr `VirtualThreadPerTask` worker pool all execute under the same VT model. The benefit framed by user-spec is developer-ergonomics (no `.flatMap`/`switchIfEmpty`/`onErrorResume` chains; stack traces stay shallow and module-local) and future-flexibility, not a per-instance throughput gate — horizontal scaling is handled at the deployment layer (see [architecture.md](architecture.md) for the production posture). User-spec lines 28–32 spell out the deliberate trade-off vs waiting for Spring Boot 4 + JDK 24.

### Observed pinning sites

A post-flip probe ran the backend with `JAVA_TOOL_OPTIONS="-Djdk.tracePinnedThreads=full" ./gradlew bootRun` and drove three workload shapes: a 30-second idle startup window, a 40× concurrent `POST /api/auth/register` storm (50 successful BCrypt cost-12 encodes across two passes), a 20× concurrent `POST /api/auth/login` storm against unknown users (20 BCrypt dummy-hash matches plus 20 Lettuce brute-force `INCR`/`EXPIRE`/`DEL` roundtrips per VT), and a 20× concurrent `POST /webhooks/telegram/{projectId}` storm against a non-existent project (40 Mongo sync read pairs total). The captured JVM stdout/stderr — including the `Picked up JAVA_TOOL_OPTIONS: -Djdk.tracePinnedThreads=full` confirmation banner — is kept under `work/migrate-to-virtual-threads/logs/working/task-11/boot.log` (gitignored).

Total `Thread held by virtual thread` banners observed across all four workloads: **0**.

The empty-trace result for BCrypt diverges from the expectation written into the task brief, which assumed cost-12 encodes would surface as pinning entries. The divergence reflects how the JDK 21 trace flag actually works, not a gap in the probe:

- `-Djdk.tracePinnedThreads=full` fires only when a virtual thread invokes `LockSupport.park` (or an equivalent native blocking call) **while** it holds a `synchronized` monitor that the carrier cannot release. Long CPU bursts on a virtual thread — including BCrypt cost-12 hashing — do not park; the carrier is consumed for the duration of the burst, but no pinning banner is emitted.
- BCryptPasswordEncoder's hash routine has no `LockSupport.park` under `synchronized` in the path that handles user passwords. The encode/match call sites used by `AuthService.register` and `AuthService.handleUserNotFound` are CPU-only, so the trace flag has nothing to report regardless of concurrency level.
- The active Lettuce 6.5.5.RELEASE and `mongodb-driver-sync` 5.4.0 builds use `j.u.c.locks.ReentrantLock` for internal coordination instead of `synchronized` blocks that park — meaning their sync APIs are in the trace flag's blind spot by design, not by accident.

This deviation is recorded in `work/migrate-to-virtual-threads/decisions.md` so a future maintainer who expects the historical BCrypt-pins-on-VT folklore can reconcile it against the probe evidence.

### What we deliberately don't do

- No `Semaphore`-based back-pressure around BCrypt or any other CPU-bound code (Decision D4 under "Технические решения" in `work/migrate-to-virtual-threads/user-spec.md`). The previous `Schedulers.boundedElastic` cap was loose enough that removing it is not a meaningful regression; if a register-storm ever causes measurable CPU starvation in production a `Semaphore` (VT-safe) can be added point-locally at that time.
- No migration of Lettuce sync calls to the async API for "VT optimization" reasons (Risk R2). The sync API on a VT is the documented happy path; rewriting to async would trade ergonomics for no observable benefit.
- No preemptive code changes to "harden against pinning" before the trace flag actually observes a site (user-spec line 86). The probe above is the system of record; sites not listed in this section have not been observed.
- No zero-pinning gate. User-spec AC7 is satisfied by observing, naming, and bounding the pinning surface — not by driving it to zero.

### How to re-observe

Re-run the probe on demand from `backend/` (matches the project-knowledge convention for gradle commands):

```
JAVA_TOOL_OPTIONS="-Djdk.tracePinnedThreads=full" ./gradlew bootRun
```

Drive the workloads against the running instance:

```
# Prime XSRF cookie
curl -s -c /tmp/vt-probe-jar.txt http://localhost:8080/health > /dev/null
XSRF=$(awk '$6=="XSRF-TOKEN"{print $7}' /tmp/vt-probe-jar.txt)

# Register-storm (BCrypt encode)
for i in $(seq 1 20); do curl -s -b /tmp/vt-probe-jar.txt -H "X-XSRF-TOKEN: $XSRF" \
  -H 'Content-Type: application/json' -X POST \
  -d "{\"email\":\"vt-probe-$(date +%s)-$i@example.com\",\"password\":\"Password123!\"}" \
  http://localhost:8080/api/auth/register & done; wait

# Login-storm (BCrypt dummy-hash + Lettuce brute-force INCR)
for i in $(seq 1 20); do curl -s -b /tmp/vt-probe-jar.txt -H "X-XSRF-TOKEN: $XSRF" \
  -H 'Content-Type: application/json' -X POST \
  -d "{\"email\":\"unknown-$i@example.com\",\"password\":\"WrongPw1!\",\"rememberMe\":false}" \
  http://localhost:8080/api/auth/login & done; wait

# Webhook-storm (Mongo sync read paths)
for i in $(seq 1 20); do curl -s -H 'Content-Type: application/json' \
  -H "X-Telegram-Bot-Api-Secret-Token: stormSecret$i" -X POST \
  -d "{\"update_id\": $((RANDOM*1000+i)), \"message\":{\"message_id\":$i,\"chat\":{\"id\":12345},\"text\":\"vt-$i\"}}" \
  "http://localhost:8080/webhooks/telegram/000000000000000000000001" & done; wait
```

## Spring Security MVC

- `SecurityConfig` requires BOTH `@Configuration` AND `@EnableWebSecurity` — `@EnableWebSecurity` does NOT include `@Configuration` in Spring Security 6.
- `SecurityFilterChain` uses `HttpSecurity` (Servlet-stack DSL on Spring MVC + virtual threads).
- Rule ordering is first-match: always put specific `requestMatchers(...).permitAll()` BEFORE `anyRequest().authenticated()` — swapping causes all requests to require auth.
- CSRF: for session-based SPAs (this project: Nuxt frontend + `spring-session-data-mongodb`) use `CookieCsrfTokenRepository.withHttpOnlyFalse()` plus a plain `CsrfTokenRequestAttributeHandler` so the SPA can read the `XSRF-TOKEN` cookie and echo the raw token back as the `X-XSRF-TOKEN` header on mutating methods, combined with a `SameSite` cookie policy as defense in depth. We deliberately do NOT use `XorCsrfTokenRequestAttributeHandler` (Spring Security 6.x's default): it BREACH-masks only the form attribute and would break the cookie/header round-trip since `CookieCsrfTokenRepository` writes the cookie raw. BREACH protection is unnecessary here — tokens travel only via cookie, never rendered into a compressible JSON body. A custom `OncePerRequestFilter` (`CsrfCookieMaterializer`) sits after `CsrfFilter` and reads `CsrfToken.getToken()` so the cookie is materialised on every request, including safe-verb GETs — `CsrfFilter` itself stores a `Supplier` in request attributes but never calls `.get()` on its own. CSRF disable (`.csrf(csrf -> csrf.disable())`) is reserved for truly stateless endpoints with no cookie auth — webhooks (e.g. `/webhooks/telegram/{projectId}` authenticated by a secret token) and public APIs authenticated by API key.
- Current security baseline: `/health` and `/api/auth/**` are permitAll; `/api/**` is explicitly authenticated (placed before the catch-all so any future `/api/...` route fails closed); all other paths require an authenticated session via the catch-all.

See also: the `## Virtual Threads` section above for the runtime model (`spring.threads.virtual.enabled=true`, Tomcat + VT, observed pinning surface).

## Code Patterns

### Auth & Sessions

- **Security event logging.** Append to the `events` collection via `EventService.logEvent(...)`. The `eventType` field is an open enum: each epic that introduces new audit events extends it. Do not log raw secrets (passwords, tokens, session IDs) in metadata.
- **Fire-and-forget side effects.** `EmailService` swallows every SMTP / MIME-build exception inside a `try { javaMailSender.send(msg); } catch (Exception e) { log.error(...); }` block — failure never propagates to the caller, the surrounding flows (register, resend-verification, forgot-password, reset-password) return 200 regardless. Callers also wrap each `emailService.send*(...)` call in a defence-in-depth `try { … } catch (RuntimeException ex) { log.warn("... userId={}: {}", id, ex.getMessage()); }` so a future synchronous bubble-up still cannot break the user-facing response. Under virtual threads the previous `boundedElastic` justification (free the Netty event loop) no longer applies — blocking SMTP work on a VT is cheap, so the synchronous swallow-and-log is the canonical shape. Reuse this pattern for any non-critical side effect that must not fail the user-facing request.
- **Terminate sessions for a user.** Sessions are stored as documents in `sessions` (managed by `spring-session-data-mongodb`). To invalidate sessions for a given user, query by the document's `principal` field via `MongoTemplate` (`Query.query(Criteria.where("principal").is(userId))` + `mongoTemplate.remove(q, "sessions")`) and delete matching docs. Used by `reset-password` (all sessions), `change-password` (all except current), and `terminate-all-sessions`. The `principal` field path is a collection-schema fact — Spring Session writes the principal name there — and is unchanged across the servlet / reactive split — keep using `principal` rather than re-deriving.
- **Brute-force throttle keys (Redis).** Login uses two counters per failed attempt: `brute:fail:{email}` (threshold 5) and `brute:fail:ip:{ip}` (threshold 20), each `INCR` + `EXPIRE 900` on first set, `DEL` on success. Fail-open if Redis is unreachable — this is DoS mitigation, not an auth gate. Reuse this dual-key shape for any other endpoint that needs brute-force protection (e.g. forgot-password if abuse appears).
- **Timing-attack prevention on user lookup.** When an email is not found in login, run `BCryptPasswordEncoder.matches(input, DUMMY_HASH)` before returning 401 so missing-user latency matches wrong-password latency. Same shape applies whenever an endpoint must hide whether a record exists.
- **Session fixation.** On successful login, mint a fresh JSESSIONID on the authenticated `HttpSession` before storing `SecurityContext`. The current shape is `httpRequest.getSession(true); httpRequest.changeSessionId();` — `changeSessionId()` requires an existing session, so materialise one first if anonymous. Spring Security's `SessionFixationProtectionStrategy` is invoked only when the form-login filter is engaged; this project uses a manual login handler (`AuthService.openSession`), so the rotation must be done explicitly. `changeSessionId()` is chosen over `invalidate() + getSession(true)` because no current writer puts state into an anonymous session before login (verified across `SecurityConfig` + filter chain + controllers); if a future filter starts writing session-scoped attrs pre-auth, switch to the explicit `invalidate() + getSession(true)` shape to drop them (mirrors `SessionFixationProtectionStrategy migrateSessionAttributes=false`).
- **Per-request session cookie `Max-Age` (remember-me).** `RememberMeCookieSerializer` (subclass of Spring Session's `DefaultCookieSerializer`) overrides `writeCookieValue` to set `cookieMaxAge` to `rememberMeDays * 86400` when the request attribute `SessionAttributes.REMEMBER_ME_ATTR` is `Boolean.TRUE`. `AuthService.openSession` writes the attribute on the `HttpServletRequest` synchronously before `securityContextRepository.saveContext(...)` flushes the `SecurityContext`, so the serializer sees it during the `Set-Cookie` write. Registered as `@Bean CookieSerializer` in `SecurityConfig`, shadowing Spring Session's `@ConditionalOnMissingBean` default. Absent or `Boolean.FALSE` leaves the default `Max-Age=-1` (session-scoped cookie); logout still emits `Max-Age=0` regardless of the per-request flag. Cookie attributes (`name`, `httpOnly`, `secure`, `sameSite`, `path`, `domain`) are read live from `serverProperties.getServlet().getSession().getCookie()` via `PropertyMapper.alwaysApplyingWhenNonNull()` — no duplicated literals in Java; env vars `SESSION_COOKIE_*` flip behaviour on restart. The manual `PropertyMapper` overlay does NOT auto-forward future Spring Boot `Cookie` POJO fields — extend it when upgrading.
- **JobRunr recurring jobs.** Cleanup/maintenance jobs are registered as recurring jobs with explicit cron (e.g. `HardDeleteJob` daily at 03:00). Use `BackgroundJob`/`@Recurring` + idempotent semantics; jobs run on every replica but JobRunr's distributed lock prevents double-execution.

### Frontend i18n

- **All visible UI strings via `t('key')`.** Locale dictionaries live at `frontend/i18n/locales/{uk,en}.json`, namespaced by feature (`auth.*`, `dashboard.*`, `profile.*`, `layout.*`, `validation.*`, `errors.*`, `common.*`, `brand.*`). Brand wordmark is also keyed (`brand.name`) — same value `"Bot Funnel"` in both locales — so the parity gate doesn't mistake a literal for missing translation. Keys are camelCase; nested objects.
- **Build-time parity gate.** `frontend/scripts/check-locales.mjs` runs as `prebuild` (npm convention — fires before `nuxt build`). Compares key sets between `uk.json` and `en.json`; exits 1 on missing/corrupted file or divergent keys. Uses `Object.create(null)` accumulator + filters `__proto__`/`constructor`/`prototype` keys against prototype-pollution payloads in JSON. Add a key in one locale but forget the other → CI build fails before deploy.
- **Locale-aware navigation.** Replace `<NuxtLink>` with `<NuxtLinkLocale>`; wrap every `navigateTo()` target in `useLocalePath()` (string form: `localePath('/dashboard')`; object form: `{ path: localePath('/auth/login'), query }`). Default-locale (uk) `localePath` is identity, so existing UA-literal asserts in tests pass without modification.
- **Auth middleware via route name.** `frontend/middleware/auth.global.ts` resolves the route base name with `useRouteBaseName()` and matches against an explicit `PUBLIC_ROUTE_NAMES` whitelist. Fail-closed semantics: `getBaseName(to) === undefined` (catch-all/unknown route) → unauth user redirects to login. Path-prefix matching (`startsWith('/auth/')`) was rejected because it broke under `prefix_except_default` for `/en/auth/...`.
- **`useApiError()` composable factory** (`frontend/composables/useApiError.ts`). Call once at the top of `<script setup>` (correct lifecycle for `useI18n()`). Returns a handler `(error, contextKey) => string`. Handler extracts status via `error?.statusCode ?? error?.status ?? error?.response?.status`, normalizes through `Number()` + `Number.isFinite`, and walks `errors.{ctx}.{status}` → `errors.{ctx}.generic` → `errors.generic` with `te()` confirmation before each `t()` (Vue I18n in production silently returns the lookup key on missing entries — `te()`-gating prevents that key string from leaking into the UI). Use 2-level `errors.{action}.*` for auth contexts (`login`, `register`, …) and 3-level `errors.profile.{action}.*` for profile contexts.
- **Reactive Zod schemas.** Wrap every `toTypedSchema(z.object({...}))` chain in a single `computed()` and pass the `ComputedRef` AS-IS to `useForm({ validationSchema: schemaComputed })` — never `.value`, never `unref()`. vee-validate v4 reads the ref reactively, so live locale switch re-runs validation in the new language. Unwrapping converts the subscription to a one-time snapshot and freezes UA messages in the form.
- **Server-side prefix stripping.** Nitro middleware at `frontend/server/middleware/strip-invalid-locale.ts` 302s any unsupported 2-letter prefix (including `/uk/...`, since `prefix_except_default` forbids the default-locale prefix). Path normalization order: backslash reject (400) → strip prefix → collapse leading slashes → decode percent-encoding. For auth-zone redirects (`/auth*`), the 302 itself carries `X-Robots-Tag: noindex, nofollow` + `Referrer-Policy: no-referrer` so `?token=` doesn't leak via Referer to the next request. Pure decision logic lives in `server/utils/locale-strip.ts` (no h3 deps, unit-testable).
- **`NON_DEFAULT_LOCALES` is single-source.** Defined in `frontend/shared/i18n-locales.ts`, consumed by both `nuxt.config.ts` (generates `routeRules` for `/{code}/auth/**`) and `strip-invalid-locale` allow-list. Adding a third locale only requires updating that constant.
- **VITEST conditional on `detectBrowserLanguage`.** Disabled under Vitest in `nuxt.config.ts` — happy-dom defaults `navigator.language` to `en-US`, which would otherwise flip the test locale to `en` and break every UA-literal assertion in existing page specs. Production behavior unchanged.
- **Nuxt DevTools off.** `devtools: { enabled: false }` in `nuxt.config.ts` because `@vue/devtools-api` ships only as CJS and is not pre-bundled by Vite — browser throws `ReferenceError: exports is not defined` at hydration, silently breaking client-side handlers (LangSwitcher.setLocale, form submits). DevTools is dev-only ergonomics; disabling avoids fighting the bundling.
- **AC18 page-spec exception (i18n feature).** Existing UA-literal-asserting page specs may receive exactly ONE additional `mockNuxtImport('useLocalePath', () => () => (path: string) => path)` identity-passthrough mock (preserves uk-default behavior). UA literal asserts must stay verbatim. Any other test mutation is out-of-scope and a violation. Currently authorized: `tests/middleware/auth.global.spec.ts`, `tests/pages/auth/{login,register,forgot-password,reset-password,verify-email}.spec.ts`, `tests/pages/{dashboard,profile}.spec.ts`.

### Project Workspace / Access Control

- **`/api/v1/...` is the versioned namespace for project-scoped modules.** All multi-tenant resources mount under `/api/v1/projects/{projectId}/...`. Legacy `/api/auth/**` and `/api/profile/**` stay unversioned. The `SecurityConfig` `requestMatchers("/api/**").authenticated()` rule covers both — no new SecurityConfig edits per epic.
- **`ProjectService.requireOwned(ownerId, projectId, includeSoftDeleted): Project` is the single ownership entry point** for every project-scoped handler in the platform. Synchronous return on the MVC + virtual-threads runtime — no Mono unwrapping needed. Future modules (bots, subscribers, funnels, broadcasts, api_keys) MUST call this first in their service before any other work — including read-only endpoints. The guard returns the loaded `Project` so callers don't re-fetch. Skipping it = cross-tenant data leak (Risk R1 in `work/completed/05-projects/user-spec.md`).
- **Anti-enumeration 404 (uniform).** `requireOwned` throws `AppException.notFound("Project not found")` for all three cases: foreign-owned, soft-deleted (when `includeSoftDeleted=false`), and malformed `ObjectId`. Bad-hex handling is a synchronous `try { repo.findById(projectId); } catch (IllegalArgumentException e) { throw AppException.notFound(MESSAGE_NOT_FOUND); }` — same 404 as every other case. Never 403 — a 403 response leaks "exists, but not yours". Same shape applies to every future project-scoped resource.
- **422 + business code for rule violations; 400 for bean-validation; 409 for unique conflict.** `AppException.unprocessableEntity(code, message)` (2-arg, intentional asymmetry — 422 ALWAYS carries a code) for quota-style rejections (e.g. `project_limit_reached`). `AppException.conflict(code, message)` for unique-constraint collisions (e.g. `project_name_taken`). `MethodArgumentNotValidException` from `@Valid` on MVC controllers flows through `GlobalErrorHandler` as 400 with `code: null` (the body's `message` field carries a comma-joined `"<field>: <defaultMessage>"` summary). Frontend `useApiError` resolves `errors.{ctx}.{status}` when code is absent, `errors.{ctx}.codes.{code}` when present.
- **Service-level uniqueness pre-check (no partial unique index) — default.** Spring Data MongoDB `@CompoundIndex` does NOT support `partialFilterExpression` directly on the annotation, but DOES support `partialFilter = "{ ... }"` JSON. The default convention is service-only pre-check (e.g. `findByOwnerIdAndNameAndDeletedAtIsNull`). Race window ~10–60ms is bounded by business caps (e.g. 5 active projects per user), not by check latency — automated clients can't flood. Fallback: `IndexOps.ensureIndex` with `partialFilterExpression` when collisions appear in prod.
- **Defense-in-depth uniqueness (service pre-check + partial unique index) — when race semantics matter.** Adopted for `bots` collection (`telegramBotId` platform-wide; `projectId` per-project), both filtered `status=CONNECTED`. The pre-check keeps the happy-path 409 message clean and short-circuits before any external API call; the index closes the residual race window definitively. `DuplicateKeyException` is caught and mapped to the same 409 as the pre-check, plus a compensating rollback (see "Compensating action on persist failure" below) when the conflict surfaces after an external side effect. Use this variant when: (a) two unrelated tenants could race for the same identity, (b) recovery from a missed conflict requires manual operator intervention.
- **JobRunr cascade ordering for audit-surviving events.** Hard-delete jobs (e.g. `ProjectHardDeleteJob`, cron `0 3 * * *`) must emit the `*_hard_deleted` event AFTER deleting prior events for the same ids AND BEFORE deleting the resource document. Reversing either order either swallows the audit trail in the same cascade run, or leaves the event pointing at a partially-deleted resource. Every hard-delete cron should also write a structured INFO log per run (`deletedCount`, `eventsRemovedCount`, `runDurationMs`) so zero-deletion days remain visible in operations.
- **Mass-assignment defense via DTO whitelist.** Every `*Request` record carries `@JsonIgnoreProperties(ignoreUnknown = true)`. `ownerId`/owner-bound fields are NEVER read from the request body — only from `SecurityContextHolder.getContext().getAuthentication()` (Servlet-stack helper) via `currentUserId()`. Integration tests seed a hostile body (`{ownerId: "<other-user>"}`) and assert the DB row still has the authenticated user as owner + response body does NOT echo `ownerId`.

### Frontend State & API Conventions

- **Pinia setup-store + opaque-ID localStorage (scope-locked).** Only opaque resource identifiers (ObjectId hex) may be persisted to `localStorage`. No tokens, no PII, no list data, no cached server responses. Currently a single key — `bot-funnel.currentProjectId`. Any future epic adding `localStorage.setItem` requires a fresh security review and an amendment to this rule. Verified via `grep -rn "localStorage.setItem" frontend/` — exactly one writer in `stores/projects.ts`.
- **SSR-snapshot stomp recovery for localStorage-backed refs.** A Pinia setup-store ref initialized as `ref(readPersisted())` runs both on SSR (where `localStorage` is unavailable → null) and on client. Pinia's hydration then replays the SSR null onto the client store, clobbering the client-side localStorage read. The recovery pattern: re-read `localStorage` inside the first action that actually runs client-side (e.g. `fetchAll → runAutoSelect` in `stores/projects.ts`) when the ref is still null. Explicit-clear flows must also call the matching `localStorage.removeItem` so the re-read doesn't re-introduce stale state.
- **Path-scoped 404 interceptor for stale-resource recovery.** `composables/useApi.ts` `onResponseError` matches `^/api/v1/projects/[^/]+$` exactly (single-resource hit, no sub-paths). When the path matches AND the extracted id equals `currentProjectId`, the interceptor clears in-memory + localStorage state via `projectsStore.handleStaleCurrent()` and sets `projectsStore.pendingBannerKey = 'errors.projects.unavailable'`. The `handleStaleCurrent` call is fire-and-forget with `.catch(...)` logging — the original request's reject still propagates to the caller. Sub-path 404s (`/api/v1/projects/{id}/bots` etc.) pass through to module-specific handlers.
- **Cross-cutting banner surface (`pendingBannerKey`).** When a cross-cutting layer (404 interceptor, page guards) needs to render a one-shot informational banner that survives a route change, it writes an i18n key into `projectsStore.pendingBannerKey`. The host page (currently `/projects`) renders a persistent dismissable banner against this key — explicitly NOT auto-dismissed like the transient restore toasts. Same pattern reusable for future epics that need to surface "the resource you came here for is gone" notices.
- **Project-scoped page redirect on missing resource.** Pages routed by `[projectId]` (e.g. `pages/projects/[projectId]/settings.vue`) MUST do an explicit GET on mount + redirect to `/projects` (with `pendingBannerKey` set when not already present) when the project is absent from the active list or the GET returns 404. Same-tab back-after-delete, cross-tab staleness, and foreign/malformed ids all collapse to the same "go back to the list with an explanation" UX. Don't render passive in-page banners — they get missed.

### Bot Connection / External APIs

- **Synchronous `RestClient` for outbound HTTP (D1).** Single `RestClient` per upstream wrapped in a `@Component` (first instance: `TelegramApiClient`). Base URL injected via `@Value("${app.<upstream>.base-url:...}")` so tests can override with `@DynamicPropertySource` pointing at `MockWebServer`. Constructed with a JDK `java.net.http.HttpClient` connect-timeout (`CONNECT_TIMEOUT = 5s`, public static for reuse by sibling clients) wrapped in `JdkClientHttpRequestFactory` with `setReadTimeout(DEFAULT_RESPONSE_TIMEOUT = 10s)`; `DefaultUriBuilderFactory(baseUrl)` with `EncodingMode.NONE`. Methods return synchronous values (`TelegramUser`, `Boolean`) — no `Mono` wrapping. Retry policy (D2): hand-rolled `for` loop with `MAX_RETRIES = 3`, `INITIAL_BACKOFF = 200ms`, `MAX_BACKOFF = 2s`, geometric `Thread.sleep(min(initial << attempt, max))` between attempts. Under virtual threads `Thread.sleep` is cheap (carrier-thread parking) — no need for a Reactor scheduler. Transient classification: walks the cause-chain (`CAUSE_CHAIN_MAX_HOPS = 16`) and matches `HttpServerErrorException`, `RestClientResponseException` with 5xx, `IOException`, `TimeoutException`. 4xx is mapped synchronously inside `.onStatus(HttpStatusCode::is4xxClientError, ...)` to an `AppException` and rethrown — never retried.
- **Per-method boundary token-shape guard.** When the SDK method takes a secret in the URL or body (e.g. Telegram bot token), every public method on the client calls a `requireValidTokenShape` guard at the top. Catches programming mistakes (malformed value bypassing controller-layer regex) before they reach the wire.
- **Log scrubber for upstream descriptions.** When a WARN/ERROR line echoes an external API's `description`/`error_message` field, run it through a token-regex scrubber (in `bot/`: `\d{1,20}:[A-Za-z0-9_-]{30,50}` → `[REDACTED_TOKEN]`) before logging. Upstream can quote the caller's secret back; the scrubber is the last-mile defense. The scrubber utility itself is `public static` so callers in the same module (e.g. `BotService` rollback paths) reuse it without duplication.
- **Compensating action on persist failure after a remote side effect.** When the happy-path sequence is `external-call A → external-call B → local persist`, and persist failure leaves the upstream in a state our system doesn't know about, the orchestrator issues a best-effort compensating call (`deleteWebhook` after `setWebhook` + Mongo persist fail). Compensation is a synchronous nested `try { compensate(); } catch (Exception compErr) { log.warn(...); }` inside the outer persist catch, runs inside the same request, never rethrows, logs on failure (token-scrub the message). The original error still propagates as 500 to the caller. Symmetric to soft-delete cleanup patterns where the Telegram side may also be down on the way out (Disconnect path WARN+proceed).
- **At-rest encryption: AES-256-GCM via `common/crypto/TokenEncryptor`.** JDK `javax.crypto` (no new dependency). 12-byte SecureRandom IV per encryption, 128-bit GCM auth tag, 32-byte key from env. Fail-fast in the constructor on missing/short/non-hex key — application context refuses to start. The component lives in `common/crypto/` (not in the consuming module) so any future at-rest secret reuses the same primitive. Returns `EncryptedValue(iv, ciphertext)` — Base64 encoding/decoding is the consumer's responsibility (keeps the helper schema-agnostic).
- **SHA-256 hash, not encryption, for secrets that need pre-image verification only.** Telegram webhook secret (`webhookSecretHash`) is stored as a hex SHA-256 hash, not AES-encrypted. The verifier (06b) hashes the incoming `X-Telegram-Bot-Api-Secret-Token` header and compares — no decryption needed. A Mongo backup leak then reveals only hashes; an attacker cannot forge updates without the plaintext. Apply this whenever the only operation on a stored secret is "does this candidate match?".
- **Brute-force counter shape variant: INCR-every-attempt.** Default auth variant (login) INCRs on failure only and DELs on success. Bot Connect uses an INCR-every-attempt variant per user (`brute:bot-connect:{userId}`, threshold 10, 900s TTL, EXPIRE only when INCR returns 1, DEL on success). Required because an attacker could chain `Connect-success → Disconnect → Connect-success` to bypass an INCR-on-failure-only limiter. No per-IP key for authenticated endpoints — abuse vector is per-account, not per-IP. Fail-open on Redis errors WITH a WARN log per failure (closes the observability gap left by the auth-module fail-open). Counter primitives are still duplicated across modules; consolidating into a shared `common/RateLimit` helper is deferred until a third consumer appears.
- **External API integration tests via `MockWebServer` (okhttp3).** `testImplementation` dependency only. Pattern: class-level `MockWebServer` started in `@BeforeAll`, `app.<upstream>.base-url` overridden via `@DynamicPropertySource`, scripted responses `.enqueue(...)`'d per test. Compatible with `MockMvc` for inbound assertions and synchronous `RestClient` for the outbound path exercised by the test target. Chosen over WireMock for minimal Spring footprint — no separate config beans, no extra context cost.
- **Race-condition integration tests.** For uniqueness defended by a partial unique index, prove the race by issuing `ConcurrencyTestUtils.parallelInvoke(2, () -> POST connect)` (D10 — `Executors.newVirtualThreadPerTaskExecutor()` + a `CountDownLatch` barrier so N tasks fire simultaneously after all of them have parked) and asserting status pair `{200, 409}` plus one persisted row plus the compensating-call count (`setWebhook`-count is `[1, 2]` because the loser may legitimately short-circuit at the pre-check; `deleteWebhook`-count is `setWebhook-count - 1`). Hard counts on the lenient side; strong invariants (status pair, persisted row count) on the strict side.
- **Frontend secret-handling in stores.** Stores that accept a secret as an action argument (e.g. `botStore.connect(projectId, token)`) MUST: (a) pass the secret only inside the request body of `useApi()` — never on a `ref`, never in the URL, never in error state. (b) Unconditionally redact `err.options.body` in the catch block before rethrowing, covering both ofetch's realistic JSON-string body shape AND a defensive object-shape fallback. (c) Preserve `response.status` so downstream `useApiError`/404 interceptor still resolves. Pinia setup-store action arguments are not opt-out-able from devtools traces; production builds disable Vue devtools, but the redaction-on-throw is the operative defense.
- **Frontend Settings folder split + sub-nav.** When a single Settings page accumulates a second concern (e.g. "Bot"), convert `pages/projects/[id]/settings.vue` → `settings/index.vue` + `settings/<subpage>.vue` and add a shared `components/SettingsSubnav.vue` rendered at the top of each child. Active state is computed from `useRoute().path` stripped of locale prefix (sourced from `frontend/shared/i18n-locales.ts → NON_DEFAULT_LOCALES`) and surfaced via `aria-current="page"` + Tailwind class — NOT via Vue Router's `exact-active-class` prop (it isn't reliably swappable under `@nuxt/test-utils` `mountSuspended`, blocking regression tests). Existing sidebar links to `/projects/{id}/settings` keep working via folder-route auto-resolution to `index.vue`.

### Outbound Telegram Send (`TelegramSender`)

These rules govern the outbound `sendMessage` path. They sit alongside the Connect-path policy above (which lives on `TelegramApiClient`); the two beans intentionally diverge — same external API, different UX-vs-reliability tradeoffs.

- **Send path is a distinct `@Component` from the connect path.** `TelegramSender` and `TelegramApiClient` each construct their own `WebClient`, retry policy, and audit semantics. Mixing them in one class would force a per-method switch on retry budget and obscure which policy applies where. The shared bits (`scrubTokens`, `requireValidTokenShape`, `isTransient`, `CONNECT_TIMEOUT = 5s`, `DEFAULT_RESPONSE_TIMEOUT = 10s`) are `public static` on `TelegramApiClient` — promoted as needed; the sender reuses them directly rather than redeclaring. The `MONO_TIMEOUT` constant stays private because the sender owns its own outer ceiling (30s, see below).
- **Send retry ladder: `Retry.backoff(3, 1s).maxBackoff(4s)` (1s/2s/4s, 3 retries after first attempt = 4 total).** Distinct from connect-path 200ms/400ms/2s. Send tolerates longer pauses because Telegram needs time to recover from 5xx; connect must stay fast because the user is waiting in a form. 4xx is never retried; `isTransient` filters to 5xx + `IOException` + `TimeoutException` (walked through a bounded cause-chain — reused from connect-path).
- **429 retry loop wraps the 5xx retry loop (outer/inner ordering).** Reactor `.retryWhen` stacks such that the second-applied operator wraps the first: chain `.retryWhen(transientRetry)` first, then `.retryWhen(rateLimitRetry)`. Wrong order would let `retry_after` waits exhaust the 5xx counter and mis-classify recoverable 429s as transient failures. Verified by an interleaving test against scripted `[5xx, 429(retry_after=1), 5xx, 200]` → success at `attempts==4`.
- **Clamp `retry_after` before sleeping.** `Math.max(0, Math.min(retryAfter, 30)) + jitter(0..200ms)`. Reactor treats a negative `Duration` as immediate, so missing/negative `retry_after` from Telegram becomes a spin loop without the `Math.max(0, ...)`. The `Math.min(..., 30)` bounds a single delay; the overall timeout below is the only cap on the loop iteration count.
- **`.timeout(Duration.ofSeconds(30))` is the single effective ceiling on the chain.** Theoretical retry budget (4 attempts × up to 10s read + 1s+2s+4s backoff ≈ 47s plus an indefinite 429 loop) exceeds 30s by design — the outer cap is what actually fires. Frontend default `ofetch` timeout is ~35s, so the sender fails before the frontend gives up and the user gets a coherent error rather than a hung request.
- **Sender owns the audit trail for every outbound send.** `telegram_message_sent` on success and `telegram_send_failed` on terminal failure are emitted by `TelegramSender` itself via `EventService.logEvent(ownerId, ...)`. Each caller may layer its own domain event on top (e.g. `BotService.sendTestMessage` writes `bot_test_message_sent` only on success; on failure it does NOT write `bot_test_message_failed` — the sender already wrote `telegram_send_failed`). Caller-only audit was rejected because any caller bug would silently lose the trail. `ownerId` is nullable for system-context callers (Epic 06/07 workers); `EventService.logEvent` already accepts `null userId` — no sentinel needed.
- **`attempts` counter lives at the outermost lambda closure.** Allocate `AtomicInteger attempts = new AtomicInteger(0)` BEFORE `Mono.defer`/`Mono.fromSupplier` that builds the per-attempt request, and increment via `.doOnSubscribe`. A counter declared inside the per-attempt supplier resets on every 429 resubscription, breaking the AC14 "total HTTP attempts" semantics. The single counter survives both retry loops.
- **Per-call decrypt; `requireValidTokenShape` runs BEFORE URI construction.** Decrypt the token inside the chain closure (no field, no cache, no scheduler hop — closure capture is the existing `BotService` convention). Then validate shape immediately; only then build the WebClient URI. Order is non-negotiable: a tampered-Mongo token must never be concatenated into the `/bot{token}/sendMessage` template. Plaintext lifetime is at most the 30s overall timeout. Cache (Caffeine with short TTL) was rejected as premature — revisit when Epic 07 broadcast load profiles show measurable cost.
- **Decrypt-error mapping: catch only `Base64.getDecoder().decode` `IllegalArgumentException`.** Map that single failure mode to `BotTokenInvalidException → 422 invalid_bot_token`. Do NOT catch `IllegalStateException` from `TokenEncryptor.decrypt` — that one wraps both `AEADBadTagException` (corrupted/tampered ciphertext) and a misconfigured `TokenEncryptor` bean, and the two are indistinguishable at the call site. Both deliberately propagate as 500 via `GlobalErrorHandler` (same trade-off as the existing `BotService.disconnect` precedent). Differentiating corrupted-ciphertext vs misconfig-bean is deferred (operator concern, not user-fixable).
- **Internal sentinel exception for retry signaling.** `TelegramRateLimitException(retryAfterSeconds)` is package-private, extends `RuntimeException` (NOT `AppException`), and never reaches `GlobalErrorHandler`. The 429 outer `retryWhen` filter does an `instanceof` check on it. Typed alternative to a sentinel-string `RuntimeException(...)` — keeps the retry filter readable and prevents the sentinel from leaking past the loop. External outcomes for the send path are exactly two `AppException` subtypes (`BotTokenInvalidException → 422 invalid_bot_token`, `TelegramSendException → 400 telegram_send_failed`); both are caught and mapped by the same `GlobalErrorHandler` path as every other module.
- **Scrubber sites for send-path logging.** Wrap every Telegram-`description` or transport-error string in `TelegramApiClient.scrubTokens(...)` before passing to `log.warn`/`log.error`. The required call sites are: 4xx error path in `map4xx` (WARN), `ok=false` mapper (WARN), 5xx retry observer (WARN), 429-wait announcement (WARN), terminal failure log inside `doOnError` (ERROR), overall-timeout error log (ERROR), transport-error path (WARN/ERROR — URI-bearing). `ListAppender<ILoggingEvent>` tests are split per log site with explicit level filtering — a single combined assertion masks which site leaked. The `BotTokenLeakTest` `toString`-invariant on the `Bot` entity remains in force (no `@ToString`, no Lombok generation that would expose the encrypted fields).
- **WebClient construction mirrors `TelegramApiClient` shape.** `HttpClient.create().responseTimeout(...).option(ChannelOption.CONNECT_TIMEOUT_MILLIS, ...)` → `ReactorClientHttpConnector` → `DefaultUriBuilderFactory(baseUrl)` with `EncodingMode.NONE` → `WebClient.Builder` injected. Reuses the `app.telegram.base-url` property (no per-bean override). Construction shape is mirrored, not factored out — two beans is below the abstraction threshold; revisit if a third upstream lands.
- **Schema-add convention for nullable wrapper fields.** Add the Java field with a getter/setter on the entity; do NOT write a Mongo migration script. Spring Data MongoDB reads missing fields as `null` for wrapper types (`Long`, `String`, etc.) — proven by `Bot.disconnectedAt` precedent and pinned by `BotRepositoryTest.findById_legacyDocumentWithoutOwnerChatId_readsAsNull`. No `@Indexed` unless a query path actually filters on the new field. Do NOT add a `toString` accessor on entities that hold encrypted secrets (token-leak invariant).

### Webhook Ingestion (Inbound Telegram)

These rules govern the inbound `POST /webhooks/telegram/{projectId}` path. They sit alongside the outbound `TelegramSender` rules above; the two beans operate on opposite sides of the Telegram API boundary and have independent retry/audit policies.

- **Two-resource anti-enumeration 404 for soft-delete cascade gaps.** When a webhook handler depends on resource A (bot) but resource B (project) lacks delete cascade to A, do TWO sequential indexed reads: bot lookup first, then project existence + `deletedAt == null`. Both empty/malformed cases collapse to uniform 404, no body. Avoids touching the upstream module to add a cascade (out-of-scope blast radius). Cost: +1 indexed `_id` read (~5ms). Mirrors `requireOwned` anti-enumeration, but for cases where the access guard cannot be invoked because the request is unauthenticated.
- **Status-distinguishing response codes acceptable for security-sensitive endpoints when ratified by user-spec.** Webhook returns 401 (bad secret) distinct from 404 (missing project). The 401-vs-404 distinguisher is acceptable because the attacker still needs the secret to reach 401, and a uniform-401 policy was rejected as scope creep against ratified ACs. Apply this carve-out narrowly — default convention remains uniform 404.
- **Explicit-status no-body responses bypass `GlobalErrorHandler`.** Webhook controller returns `ResponseEntity<Void>` with explicit 200/401/404/413/400 statuses. `GlobalErrorHandler.handleAppException` always writes a JSON body — adding a no-body exception variant is more code than a direct `ResponseEntity.status(...).build()`. An outer `try { … } catch (Throwable t) { return ResponseEntity.status(500).build(); }` enforces this even on enqueue failure (otherwise the thrown exception propagates to `GlobalErrorHandler` and leaks a body). The pattern applies whenever a handler must produce status-only responses for security or contract reasons.
- **Path-scoped servlet `Filter` for per-endpoint payload caps.** When ONE endpoint needs a larger or smaller payload limit than Tomcat's `maxPostSize`, register a custom servlet `Filter` (extending `OncePerRequestFilter` or implementing `jakarta.servlet.Filter`) matched to that path (single segment like `/webhooks/telegram/{projectId}`, NOT `/**`). Order high enough to run before the security filter chain. Reject on (a) `Transfer-Encoding: chunked` header — bypasses Content-Length checks; (b) missing/unparseable `Content-Length`; (c) `Content-Length > limit`. Bumping the global Tomcat cap instead expands attack surface to every other path. Use Spring's `PathPattern` (not hand-rolled regex) for normalization parity with `SecurityConfig` matchers — percent-decoding, dot-segment handling. `getHeaders(name)` over `getHeader(name)` for headers that can repeat (`Transfer-Encoding`).
- **Scoped CSRF disable: AND with `CsrfFilter.DEFAULT_CSRF_MATCHER`, not bare negation.** When disabling CSRF for a specific path (e.g. webhooks authenticated by their own secret), the matcher must be `new AndRequestMatcher(CsrfFilter.DEFAULT_CSRF_MATCHER, new NegatedRequestMatcher(new AntPathRequestMatcher("/webhooks/telegram/{projectId}")))`. Bare `NegatedRequestMatcher(path)` would extend CSRF enforcement to ALL HTTP verbs (GET/HEAD/OPTIONS) on non-excluded paths, breaking every read-only endpoint. The AND preserves the default verb-restriction (POST/PUT/DELETE/PATCH only) while adding the path negation. Cross-check at implementation time via Context7 — Spring Security 6.5.x matcher API has tonalities.
- **Idempotency = unique compound index + `DuplicateKeyException` + deterministic JobRunr UUID self-heal.** Insert raw update with class-level `@CompoundIndex` unique on `(projectId, updateId)`. On `DuplicateKeyException`: increment `rejected{reason=duplicate}` counter AND still re-enqueue with `UUID.nameUUIDFromBytes(rawUpdateId.getBytes(UTF_8))`. JobRunr `enqueue(UUID, lambda)` is idempotent — duplicate ID is a no-op. Together this self-heals the silent-message-loss scenario: save succeeds → enqueue fails → Telegram retries → DuplicateKey path → re-enqueue with same UUID → job exists, 200 returned. Without this, a PENDING raw_update orphans forever. The "still re-enqueue on DuplicateKey" branch is explicit, not a side effect.
- **JobRunr worker re-entry guard via terminal-status short-circuit.** Worker's FIRST action is "if `processingStatus == DONE` return immediately — no event write, no stub call, no counter tick". Handles JobRunr retry overlap (prior attempt succeeded but JobRunr didn't observe success in time before scheduling a retry). Without the guard, the worker double-fires audit events and double-calls downstream stubs. FAILED rows ARE re-processed (treat as new attempt).
- **Event-write before status-flip in worker (audit-survives-crash invariant).** Order all worker actions: `eventService.logEvent(...)` BEFORE `rawUpdateRepository.save(processingStatus=DONE)`. A worker crash mid-flight must NEVER leave a DONE row without an audit event. Generalisation of the JobRunr hard-delete cascade ordering rule, applied to ingestion workers. Both calls are synchronous on the MVC + virtual-threads stack — blocking-safe inside JobRunr worker threads.
- **Atomic `findAndModify` for first-writer-wins state transitions.** Populating `Bot.ownerChatId` uses `mongoTemplate.findAndModify(Query.query(Criteria.where("_id").is(botId).and("status").is(CONNECTED).and("ownerChatId").is(null)), Update.update("ownerChatId", chatId), Bot.class)` (synchronous Mongo driver). A `null` return = predicate-fail no-op (already populated by another worker, or status changed). Use this whenever two workers can race to write to the same field and only the first should win; avoids the read-then-write race window. Subsequent calls return `null` — treat as benign no-op, never as failure.
- **Worker exception rethrow with scrubbed + truncated error AND clean message.** On exception: catch, atomically write `processingStatus=FAILED` + `processingError=scrubTokens(ex.getMessage()).substring(0, min(len, 1024))` via `findAndModify`, increment `worker_outcome{outcome=failure}`, then rethrow a NEW `RuntimeException(classSimpleName + ": " + scrubbedTruncatedMessage)` with NO cause chain (stack copied via `setStackTrace`). Bare `throw ex` leaks the raw exception message to JobRunr's `jobrunr_jobs` failure row AND the ERROR log path — bypasses the scrubber. The new exception preserves stack-trace fidelity for debugging while the cause-chain replacement closes the token-leak path.
- **Static `BackgroundJob.enqueue` vs injected `JobScheduler`.** Use injected `JobScheduler` bean when the controller boots inside a multi-Spring-context test environment — the static `BackgroundJob` indirection picks up whichever `StorageProvider` was registered last, which can silently target the wrong context. Production behaviour is identical. For one-shot enqueues from worker/job code, static is fine.
- **`@JsonIgnoreProperties(ignoreUnknown=true)` on every Telegram update record.** Mass-assignment defense — Telegram adds new fields without warning, unknown-property errors would 4xx legitimate updates. Apply uniformly to `TelegramUpdate` + every nested record (`Message`, `Chat`, `User`). Non-message update kinds (`callback_query`, `my_chat_member`, etc.) are modelled as opaque `JsonNode` slots; the worker resolves `updateKind` by scanning slots for the first non-null field name. Unmodelled kinds → `updateKind="unknown"`. Don't model nested schemas for non-message types until the consuming epic (05/06) needs them.
- **Token-scrubber on every webhook + worker log site.** Wrap every WARN/ERROR string-formatted with payload-derived input through `TelegramApiClient.scrubTokens(...)`. Enumerated sites: controller DuplicateKey WARN, controller enqueue-failure ERROR, filter 413 WARN (header values too), worker INFO/WARN/ERROR sites. Test via per-site `ListAppender<ILoggingEvent>` filtered by `Logger.getName()` AND `Level` — split per call site, never a combined assertion (a single combined assertion masks which site leaked). The `BotTokenLeakTest` invariant on the `Bot` entity (no `@ToString`, no Lombok generation that exposes encrypted fields) remains in force.
- **Explicit `@Bean SimpleMeterRegistry` when actuator NOT on classpath.** Without `spring-boot-starter-actuator`, Spring Boot does NOT autoconfigure a `MeterRegistry` — the `MetricsAutoConfiguration` ships in `spring-boot-actuator-autoconfigure`. Register the bean ourselves in `common/metrics/MeterRegistryConfig` with `@ConditionalOnMissingBean MeterRegistry meterRegistry() { return new SimpleMeterRegistry(); }`. The `@ConditionalOnMissingBean` future-proofs against an actuator upgrade autoconfigured registry. Adding `micrometer-core` also activates JobRunr's `JobRunrMetricsAutoConfiguration`, which carries class-literal references to actuator classes Spring resolves during autoconfig sort — exclude by name (string-based) on `@SpringBootApplication`. The exclusion is the minimal-surface fix; pulling `spring-boot-actuator-autoconfigure` for the class symbol alone re-introduces the broad autoconfig surface we want to avoid.
- **Counter ownership = where the rejection happens, not where the contract describes it.** When a request is rejected by a `WebFilter` BEFORE the controller, the counter MUST live in the filter. A counter in the controller would sit at 0 forever in production. Test: assert from outside via `meterRegistry.find(name).tag(reason, ...).counter()`. Grep guard: `grep "payload_too_large" backend/src/main/java/.../Controller.java` must return zero matches (filter is sole owner).

### Subscribers CRM (Epic 09)

Patterns for `subscriber/` (CRM, tags, custom fields, CSV export). Decision numbers reference `work/completed/09-subscribers/tech-spec.md` → Decisions.

- **Signed download token (`common/crypto/SignedDownloadToken`).** CSV export links are HMAC-SHA256 over `{exportId, expiresAt}` keyed by `SUBSCRIBER_EXPORT_TOKEN_KEY` — verification is stateless (no per-link row). Constructor fail-fast on missing/short/non-hex key, mirroring `TokenEncryptor`. The key is SEPARATE from `BOT_TOKEN_ENCRYPTION_KEY` — never share. Rotation invalidates every outstanding link; the UI exposes a "Refresh link" action (re-signs against the current key) rather than failing silently (Decision 15). Download non-200 paths still emit audit events (Decision 16).
- **Single in-flight export via partial-unique index, not a Redis lock.** `subscriber_exports` has partial-unique `(projectId)` filtered `status IN [PENDING,RUNNING]`; a second export attempt hits `DuplicateKeyException` → 409 `export_in_flight` (Decision 2). Same index-as-lock philosophy as the bot uniqueness rules — prefer a Mongo constraint over a distributed lock when the invariant is "one row in state X".
- **CSV streaming to GridFS.** `ExportSubscribersJob` streams `MongoTemplate.stream(...)` through a `PipedOutputStream`/`PipedInputStream` pair into GridFS — bounded heap at 50k+ rows, no full materialization (Decision 7). UTF-8 BOM is written first so Excel renders Cyrillic. `ExportCleanupJob` purges the blob + flips status to PURGED after `SUBSCRIBER_EXPORT_RETENTION_DAYS`.
- **Keyset cursor pagination (opaque base64 of `{sortVal, lastId}`).** List endpoints page by `(sortField, _id)` tie-break, never `skip/limit` (Decision 5). Text search is applied as a FILTER, not a relevance ranker, so the deterministic `sortField desc, _id desc` order stays intact and the cursor never skips/duplicates rows. Frontend mirror: a Pinia store appends pages into one array on "Load more" (Decision 12, `stores/subscribers.ts`).
- **Mongo text search is whole-word (`language="none"`).** The subscribers text index does exact-token match, no stemming, no prefix/substring (Decision 6) — "pvl" does NOT find "pvlkr". Known UX gap; the indexed-prefix replacement (B+, lowercase fields + anchored regex) is scoped in `workflow/improvements.md`, not yet built.
- **`CustomFieldValueValidator` is the single normalizer for BOTH a definition's `defaultValue` and a subscriber's value.** Per-type validate + coerce: trimmed String / parsed Double / Boolean / **`Instant`** for DATE. DATE parses the ISO-8601 input as `OffsetDateTime` then reduces to `.toInstant()` — the Mongo driver has NO codec for `OffsetDateTime` (would 500 on write), but does for `Instant`. The `<input type="date">` ↔ ISO bridge lives in `frontend/utils/customFieldDate.ts` (date-only `YYYY-MM-DD` ⇄ `…T00:00:00Z`). The 20-field cap is enforced by an atomic conditional `$push` (Decision 3).
- **`SubscriberEvent` collection is the SOLE writer for CRM lifecycle events** (`subscriber_registered|reactivated|unsubscribed|blocked|deleted|tag_*|custom_field_set`), distinct from the security `events` collection (Decision 10), TTL 365d. Funnels/Broadcasts (Epic 06/07) read this history; do not fork a second CRM-event writer.
- **Rate limits reuse the `BotService` INCR-every-attempt fail-open Redis shape** (Decision 9) for three buckets: new-`/start` registration (per project), signed-URL download, and manual personal-message (per subscriber). Existing subscribers are exempt from the registration limit (only NEW `/start` counts). Env-tunable (`SUBSCRIBER_*_RATE_LIMIT_*`, see `deployment.md`). Still per-module copies — consolidate into `common/RateLimit` once a fourth consumer appears.
- **Tag-delete cascade is synchronous** (`$pull` from all subscribers in-request, Decision 17) — no JobRunr job; the affected-count comes from the loaded row. Custom-field delete cascades the same way. `ProjectHardDeleteJob` was extended IN PLACE (not a separate job) to cascade `subscriber_events → GridFS → subscriber_exports → subscribers → tags` (Decision 8).
- **Frontend CRM conventions.** Validation messages live in the flat `validation.*` i18n namespace and are passed into Zod (`.regex(re, t('validation.X'))`) inside the `computed()` schema so a locale switch re-validates. Per-field "dirty" tracking (a `baseline` snapshot vs the edit buffer) gates each custom-field Save button + an "unsaved" marker. `layouts/default.vue` hydrates the projects store and syncs the current project from `route.params.projectId` so deep-link refresh of a project-scoped page keeps the sidebar/selector populated. `@vue/devtools-api` is aliased to a no-op stub in `nuxt.config` (`stubs/vue-devtools-api.mjs`) to silence a dev-only vee-validate/Pinia `setupDevtoolsPlugin` rejection (multi-version resolution; devtools already disabled project-wide).

### Funnel Engine (Epic 06 — Phase 1)

Patterns for `funnel/` (linear engine). Decision numbers reference `work/completed/10-funnels/tech-spec.md` → Decisions. Phase map: `docs/roadmap/funnels.md`.

- **At-most-once per step via a single atomic claim, never exactly-once.** `FunnelExecutionEngine` claims each step with one `findAndModify` CAS (`stepRunStatus pending→in_progress`) BEFORE the side effect, and the in-tick writes (`persistProgress`/`scheduleDelay`/`complete`/`terminate`) are themselves claim-conditional CAS on `stepRunStatus=in_progress` (Decision F2 / Task 15) so a concurrent terminal cancel deterministically wins and a cancelled/deleted execution never resurrects. A mid-tick crash leaves the row stuck `in_progress` (never re-sent) — the deliberate at-most-once-over-liveness trade-off. Proven by two-replica race + crash ITs, not mocks.
- **Snapshot steps + pinned bot at start.** `FunnelTriggerServiceImpl.fire()` deep-copies the funnel's steps onto the execution (`FunnelStep.copyOf`) and pins `telegramBotId` — funnel edits never touch in-flight runs (Decision 3), and a bot reconnect yields a predictable `failed` rather than silently re-routing.
- **`fire()` is isolated from the webhook worker.** Wrapped in `try/catch(Throwable)` with idempotent swallow+log — a funnel error must never mark the `raw_update` FAILED or trigger a webhook retry storm (Decision 6). It runs AFTER the subscriber upsert (which sets `status=active`), so the first send doesn't self-cancel on the status gate.
- **Re-enter guard is the unique partial index, not a query-time check.** `(funnelId, subscriberId)` filtered `running|waiting`: `allow_re_enter=false` swallows the `DuplicateKeyException` (ignore), `=true` does atomic cancel-then-insert. Single mechanism — no race-prone pre-check (Decision 9).
- **Reuse the sole writers for subscriber mutations.** Add/Remove Tag → `SubscriberServiceImpl.addTag/removeTag`; Set Custom Field → `SubscriberCustomFieldsService` (validate→applyAll→`recordCustomFieldsSet`, Decision F1/Task 15) so the funnel-driven path emits the same `subscriber_*` audit events as the HTTP path. Never fork a second writer (see CRM sole-writer rule above). An unknown custom-field key is silently skipped (definition resolved at runtime); an unknown tag slug still attaches to the subscriber but `TagService.incrementCounter` (no upsert) leaves it uncounted — an orphan tag, which is why the editor restricts to existing tags.
- **`@now` dynamic-date sentinel.** A Set Custom Field step on a DATE field may store the literal `@now` instead of a fixed date; `StepExecutor` resolves it to the execution-time instant via the injected `Clock` (`StepExecutor.CURRENT_DATE_TOKEN`, mirrored on the frontend as `CURRENT_DATE_TOKEN` in `types/funnel.ts`). No other templating is applied to custom-field values — only message text/caption go through `VariableTemplateRenderer`.
- **Client step validation is a UX mirror, not the contract.** `FunnelStepForm.vue` re-implements `FunnelService.validateSteps` byte-for-byte (Phase 6 composer: 1–10 blocks, per-type required fields, http(s)/file_id media source, album 2–10 + the type-mixing predicate, buttons only on the last non-album block, over-length warned-not-blocked; plus delay ≥1, tag slug regex, custom-field key non-empty) — but the funnel **save** endpoint does NOT type-check a custom-field value against its definition type; only the engine's `CustomFieldValueValidator` does, at execution. So the per-type value widget (text/number/date/checkbox + `@now`) and its validation guide the author but a bad value surfaces as a runtime `custom_field_type_mismatch` (execution `failed`), not a 422 on save.
- **`SearchableSelect.vue` is the shared combobox** for the custom-field-key and tag pickers (`components/funnels/`). Presentational (options/i18n strings passed in, `testPrefix` for data-test ids); `FunnelStepForm` owns the lazy fetch (`/custom-fields`, `/tags`) and resolves the selected field's type from the definitions to drive the value widget. Both pickers are strict selects over existing project entities.
- **Activate errors map by business code, inline — not a global toast.** The six activate/validation codes (`funnel_step_limit_reached`, `funnel_trigger_conflict`, `custom_field_type_mismatch`, …) are surfaced as `errors.funnels.<code>` next to the control via a small `resolveFunnelError` helper (`err.data.code ?? err.response._data.code`, falls back to `useApiError`), since the shared status-based `useApiError` can't distinguish them.
- **Sweep is JobRunr `@Recurring`, interval ≥ poll-interval.** Distributed lock (not Spring `@Scheduled`) for multi-replica safety; `app.funnel.scheduler-interval` is an ISO-8601 Duration (`PT30S`) and must be ≥ `org.jobrunr.background-job-server.poll-interval` (pinned 15s, Decision 2). Delay accuracy is ±~the sweep cadence. Time is `Clock`-injected (`ClockConfig`) so engine ITs are deterministic (0 `Instant.now()`, 0 `Thread.sleep`).

### Funnel Engine (Epic 06 — Phase 2: Interactive / MENU)

Phase 2 (`work/completed/11-funnels-interactive/`) adds inline keyboards + branching as one composite `MENU` step and moves the engine from a linear index to a graph. Decision numbers below reference that tech-spec. Phase 1 patterns above still hold (claim-CAS at-most-once, snapshot, sole-writers, `@now`, sweep — all unchanged).

- **Graph model, not index navigation.** Every step has a stable server-minted `id`; the cursor is `currentStepId` (not `currentStepIndex`). Non-`MENU` steps have one `next` target (default = next in list); `MENU` has a target per button (+ optional timeout target). Targets are stable `id`s, so editor reorder is safe without remapping and a future canvas is a pure visualization layer with no data migration (Decision 2). `currentStepIndex` is retained only as a drain fallback for in-flight Phase-1 runs (`graphMode` probe in `FunnelExecutionEngine`).
- **`MENU` is one composite step (message + keyboard + wait + branch), not Wait+Branch.** Its executor outcome is *park-on-reply*: send the message with `reply_markup`, set `status=waiting_for_reply`, leave the cursor on the `MENU`, set `nextRunAt`=timeout deadline or `null` (Decision 1).
- **Two-path wakeup; `waiting_for_reply` stays IN the sweep/claim `$in`.** Callback wakeup is a separate engine entry point `resumeOnCallback` (NOT via sweep). Timeout reuses the existing sweep: a menu with a timeout has `nextRunAt`=deadline and is picked up naturally; a menu without a timeout has `nextRunAt=null`, which the sweep predicate `nextRunAt <= now` never matches — so no separate "exclude from sweep" branch is needed (Decision 3). `waiting_for_reply` (lowercase) must appear in all 8 literal `$in`/partialFilter sites + the static drift assertion in `FunnelExecution` — `FunnelStatusEnumTest` + `FunnelIndexesIT` fail loudly if a site is missed.
- **Anti-IDOR is two independent layers on the callback path.** `callback_data = "{executionId}:{buttonIndex}"` is attacker-controllable (ObjectId is not a secret), so `FunnelTriggerServiceImpl.advanceOnCallback` verifies `exec.subscriberId/projectId` match the resolved subscriber, AND `resumeOnCallback`'s claim-CAS is scoped by `subscriberId` (Decision 6). `callback_data` is strictly parsed BEFORE any DB lookup (exactly one `:`, 24-hex executionId, bounded index). `answerCallbackQuery` is best-effort and fires on EVERY path including every no-op (stale/foreign/malformed) so the subscriber's spinner always clears (Decision 8).
- **Loop guard is a per-tick step budget, not `size+1`.** Graph edges aren't monotonic (loops), so the old growing-index guard is replaced by `app.funnel.max-steps-per-tick` (default 100 > the 50-step funnel cap). A loop with no `MENU`/Delay between steps trips it → `terminate(failed)` with greppable marker `FUNNEL_STEP_BUDGET_EXCEEDED` (Decision 4).
- **`FunnelStep.copyOf` now needs an explicit deep copy of the buttons list.** Phase-1 snapshot isolation relied on all fields being immutable scalars; the mutable `List<Button>` breaks that, so `copyOf` does `new ArrayList<>(buttons)` (`Button` is an immutable record, so element-shallow is enough) — Decision 5.
- **`id` migration is an idempotent `ApplicationRunner` (`FunnelStepIdBackfill`, patterned on `SuperAdminSeeder`).** Backfills `id` onto both funnel definitions AND in-flight `funnel_executions.stepsSnapshot`, and seeds `currentStepId` from `currentStepIndex` for in-flight runs — logs-but-never-throws, safe on restart (Decision 7).
- **URL buttons are `http(s)`-only via strict `URI` parse** (scheme `equalsIgnoreCase`, non-empty host — not `startsWith`); rejects `javascript:`/`data:`/`tg://`/whitespace. `timeoutUnit` reuses the `delayUnit` convention (`MIN`/`HOUR`/`DAY`) and is validated like `requireDelay` (the tech-spec Data Models text saying `minutes/hours/days` is stale). Analytics hook is minimal: `funnel_button_clicked` event (ids/codes only, no PII) + `lastButtonClicked` on the execution.
- **`SearchableSelect.vue` gained a `showValue` prop (default true).** The tag/custom-field pickers show the option value as a grey suffix (a meaningful slug/key); the `MENU` target picker passes `:show-value="false"` so the author sees only the step number + name, never the raw Mongo `id`/`__END__` sentinel. Note `withDefaults` is required — an absent declared Boolean prop coerces to `false`.

### Funnel Engine (Epic 06 — Phase 3: Triggers / Event Bus + Public API)

Phase 3 (`work/completed/12-funnels-triggers/`) adds five entry triggers, an internal event bus, and the first public-API rails. Decision numbers reference that tech-spec. Phases 1-2 patterns above still hold.

- **Subscriber-scoped fan-out via index relax, not `List<Trigger>` (Decision 1).** "One event → N funnels" is N separate funnels sharing a trigger value — achieved by relaxing the `funnels` partial-unique index filter from `{status:active}` to `{status:active, triggerType:on_start}` (so only `on_start` stays 1:1). Each firing still creates exactly one `FunnelExecution` per subscriber, reusing the unchanged execution-creation path. Multi-entry (`List<Trigger>` on one funnel) is deliberately deferred to Epic 8.
- **`FunnelEventService` is the single subscriber-keyed dispatcher (Decision 2).** `dispatchForSubscriber(projectId, subscriberId, triggerType, matchKey, originDepth)` resolves the subscriber via the service boundary, LIST-queries active matching funnels, and loops `insertExecution` per match (fan-out). All four trigger sources call it: keyword (webhook), tag/field (subscriber writers), `EMIT_EVENT` (StepExecutor), api-event (EventsController). It is distinct from the chatId-keyed `FunnelTriggerServiceImpl.fire` (`on_start`, single-result) — overloading `fire` would have broken its single-result contract. Named `FunnelEventService` to avoid the `events`/`subscriber_events` audit collections (Decision 4) — neither is a bus.
- **`FunnelExecutionFactory` is the extracted sole owner of execution creation.** `insertExecution(..., enrollDepth)` + `cancelExistingForPair` were moved out of `FunnelTriggerServiceImpl` into a package-private `@Component` injected by BOTH the dispatcher and the trigger service. This breaks the would-be `FunnelEventService → FunnelTriggerServiceImpl → StepExecutor → FunnelEventService` bean cycle structurally (no `@Lazy` on this edge). The separate `SubscriberServiceImpl ↔ FunnelEventService` edge (tag/field firing) IS broken with `@Lazy` on the dispatcher constructor param — a clean 2-node break, not the prohibited StepExecutor workaround.
- **Three independent loop backstops; "auto-enroll" = depth>0 (Decision 6).** (a) per-subscriber auto-enroll rate-limit (`bf:rate:auto-enroll:{subscriberId}`, 20/min, Redis fail-open, counts only depth>0 enrolls); (b) Redis-independent `enrollDepth` cap of 10 carried on the execution (cuts runaway even when Redis is down and the fail-open limiter would pass); (c) Redis-independent per-dispatch fan-out ceiling (`app.funnel.max-fanout-per-event`, default 50, bounds request width — closes the fail-open hole at the public ingress). An enroll is *auto* iff it originated inside a running execution (depth>0); manual-UI tag-add, `/start`, keyword, and external api-event are human/external roots (depth 0) and are exempt from the volume limit. Origin depth propagates as an **explicit method parameter**, never a ThreadLocal (the funnel sweep runs on arbitrary JobRunr/VT pool threads — a ThreadLocal would leak or be absent across the pool boundary). The re-enter partial-unique guard still catches a direct same-funnel dupe.
- **Error-isolation on every new trigger path (Decision 12).** Each dispatch path is `try/catch(Throwable)` + greppable PII-free WARN: a keyword fault in `ProcessTelegramUpdateJob` is swallowed so the worker returns 200 and the JobRunr job doesn't fail; an engine fault inside `POST /events` is swallowed → 202. Mirrors the existing `FunnelTriggerServiceImpl.fire` convention.
- **Keyword is a list field with contains-match in code (Decision 3).** `Funnel.keywords` (lowercase-normalized on save, deduped, size/length-capped); matched case-insensitive, contains, any-of-many via a code-side scan of active keyword funnels — the exact-match `triggerValue` index can't express it. Menu precedence: a `waiting_for_reply` execution suppresses keyword (read-only `exists()` probe, never the destructive update).
- **Tag/field fire in the sole writers, after idempotency + audit (Decision 5).** `tag_added` in `SubscriberServiceImpl.addTag`, `custom_field_set` in `recordCustomFieldsSet` — fired AFTER the idempotency guard and `writeSubscriberEvent`, so a no-op write does not fire. These are the verified single choke points (manual controller + StepExecutor); do not hook the controllers or `applyAll` (would miss the funnel-step path or double-fire).
- **API key: hash-only, ≥256-bit, on-demand (Decision 8).** `ApiKeyService` mints a 32-byte `SecureRandom` plaintext, stores `Sha256Hex.hex(plaintext)` + a short `keyPrefix`, returns plaintext once; lookup is by hash (no plaintext compare — a 256-bit random key makes unsalted SHA-256 safe). Generated only via the settings endpoint (no generate-on-create, no backfill); regenerate overwrites (invalidates the old key). No rotation/expiry (Epic 08). Reuses `common/crypto/Sha256Hex`.
- **Dedicated `@Order(1)` key chain on `/api/integrations/**` (Decision 7).** A higher-priority STATELESS `SecurityFilterChain` (CSRF off, `ApiKeyAuthFilter` instantiated inside the chain — NOT a global `@Component`) precedes the demoted `@Order(2)` session chain, else the session chain's `/api/**` matcher would shadow the public endpoint. Project resolves from the key (no `{projectId}` in path); any key problem → one uniform bodyless 401 (anti-enumeration). Mutual isolation is proven both directions (key ✗ cabinet, session ✗ `/integrations`). Namespace `integrations` (not `public`/`external`) is deliberate — precise, doesn't imply "no auth".
- **Index relax via a `BeanPostProcessor`, not an `ApplicationRunner` (Decision 9 + deviation).** The tech-spec prescribed a `FunnelStepIdBackfill`-style `ApplicationRunner`, but `auto-index-creation=true` creates indexes during `MongoTemplate` instantiation — *before* any runner — and since the old/new trigger indexes share a name but differ in partial filter, auto-creation throws `IndexKeySpecsConflict` (error 86) and the context fails to start, so the runner never runs. `FunnelTriggerIndexReconciliation` is therefore a `BeanPostProcessor` on the `MongoDatabaseFactory` bean (created before `MongoTemplate`): it drops the old `projectId_triggerType_triggerValue_unique_active` index in `postProcessAfterInitialization` so the conflict is cleared before auto-creation recreates the new shape. Idempotent (decision driven by the actual `partialFilterExpression`, not the index name), log-but-never-throw, greppable APPLIED/NO-OP markers. **Lesson: an index whose shape change is a partial-filter edit under one name cannot be migrated by a post-context runner with `auto-index-creation=true` — the drop must happen before `MongoTemplate` initializes.**
- **Reuse the Redis fail-open INCR/EXPIRE idiom for both new rate-limits (Decision 10).** Per-subscriber auto-enroll (`bf:rate:auto-enroll:{subscriberId}`) and the global `/events` limit (`bf:rate:events`, ~300/min). Distinct key prefixes; fail-open paired with the Redis-independent fan-out ceiling so a Redis outage cannot leave the public ingress unbounded. Still per-module counter copies — the `common/RateLimit` consolidation remains deferred.
- **Trigger form is a portable component (Decision 11).** `FunnelTriggerSettings.vue` is a self-contained trigger-type selector + per-type value editor (keyword chip list / tag+field `SearchableSelect` / event slug / on_start payload) bound via `defineModel` only — it migrates unchanged as a node form when the canvas editor arrives; only the list-page wrapper is throwaway.
- **Gate trigger auto-save on per-type readiness (Phase-3 live finding).** The funnel-editor page debounce-persists trigger edits, but switching to a non-`on_start` type leaves the required value empty → an immediate 422. `[funnelId].vue` gates `scheduleTriggerPersist` on a per-type `triggerReady()` check (on_start → value-regex incl. empty; keyword → ≥1 keyword; tag/field → non-empty `triggerValue`; event → event-name slug) so switching the type alone never fires a PATCH; `activate()` still flushes + persists so a genuine activate of an incomplete funnel surfaces the inline 422. The gate mirrors but does not replace server validation. Applies to any auto-saving form whose required fields depend on a just-changed type selector.

### Funnel Engine (Epic 06 — Phase 4: Author tooling)

Phase 4 (`work/completed/13-funnels-tooling/`) adds four author-tooling endpoints on `FunnelController` + the editor message-preview panel. No schema change, no migration — almost entirely wiring of existing primitives. Phases 1-3 patterns above still hold.

- **"Test for me" = direct enroll bypassing trigger matching.** `POST /{funnelId}/test-run` resolves the author's own subscriber (CONNECTED bot → `Bot.ownerChatId` → `SubscriberService.findByChat` → ACTIVE filter) and calls `FunnelExecutionFactory.insertExecution(depth=0)` — NOT `FunnelTriggerServiceImpl.fire` / `FunnelEventService` (those re-match triggers, which is exactly what a test must skip). Re-click = restart: `cancelExistingForPair` BEFORE insert (avoids the re-enter `DuplicateKeyException`). Pre-validated through `validateSteps` (raised `private`→package-private, no logic change) so an empty/invalid funnel returns the same 422 codes as activate. Unresolved owner (null `ownerChatId` / missing / non-ACTIVE subscriber) → one uniform `funnel_owner_not_linked` 422, never 500. 2xx means enroll registered, NOT delivery — a Telegram-send failure surfaces later as `execution.failed`. Draft funnels are test-runnable (the factory never checks `funnel.status`).
- **"Stop all" reuses one claim-CAS bulk-cancel helper.** The bulk-cancel body was extracted into `FunnelService.cancelInFlightExecutions(projectId, funnelId)` — scoped by BOTH `projectId` AND `funnelId` (tenant isolation; `delete()` was funnelId-only and was hardened to call this same helper) — setting `status=cancelled` AND `stepRunStatus=done` together. Setting `stepRunStatus=done` is mandatory: a cancel that flips only `status` loses the claim-CAS race to a mid-tick `persistProgress`. The returned count is `UpdateResult.getModifiedCount()` (best-effort — a run starting/finishing concurrently may miss the count; correctness is guaranteed by the CAS, not the count). Bulk op via `MongoTemplate` (the repo intentionally has no query methods).
- **Preview renders on the backend, displays as text on the frontend.** `POST /{funnelId}/steps/{stepId}/preview` runs the SAME `VariableTemplateRenderer` the engine uses, so `parse_mode` escaping is byte-identical (no frontend re-implementation → no markup/XSS drift, OWASP A03). Content is **on-the-fly** from the request body (Phase 6: `{stepType, blocks}` → `{renderedBlocks[]}`; was `{stepType, text, parseMode}`), not the saved step, so the panel is reactive to unsaved edits. `render` requires a non-null `Subscriber`; when the owner isn't linked the endpoint passes a **stub subscriber** (sample values, `sampleData=true`) to avoid NPE. The frontend `FunnelMessagePreview.vue` (Phase 6) renders an ordered stack of blocks; every rendered string is output EXCLUSIVELY via `{{ }}` — never `v-html`/`innerHTML` (the Telegram-escaped string is not browser-safe); media is bound via `:src`/`:href` (binding, not a sink; FILE `:href` and any media `:src` only for an `http(s)` scheme — opaque `file_id`/non-http falls back to a type icon, anti-SSRF/anti-XSS Decision 6). The author-subscriber resolution is a private helper shared with test-run (`resolveOwnerSubscriber` — test-run fails 422, preview falls back to the stub).
- **Duplicate forces draft + resets trigger to dodge the partial-unique index.** `POST /{funnelId}/duplicate` deep-copies the graph via `FunnelStep.copyOf` (ids/edges verbatim — step ids aren't globally unique, no remint), copies `keywords`/`allowReEnter`/`description`, but forces `status=draft` + `triggerType=on_start` + `triggerValue=""`. A draft never enters the `(projectId, triggerType, triggerValue)` partial-unique index, so copying an active funnel's trigger can't collide. Name `"<name> (копія)"` is truncated to the 128-char `@Size` cap (suffix never causes a 400).

### Funnel Engine (Epic 06 — Phase 5: Composition / SUBSCRIBE_TO_FUNNEL)

Phase 5 (`work/completed/14-funnels-composition/`) adds one fire-and-forget step type `SUBSCRIBE_TO_FUNNEL` that enrolls the same subscriber into ANOTHER funnel of the project. Jump / cross-funnel return / return-to-menu are configuration patterns over this single step — no new state machine, no new `ExecutionStatus`, no migration. Decision numbers reference that tech-spec. Phases 1-4 patterns above still hold.

- **Enroll via a new non-matching `FunnelEventService.enrollSpecificFunnel(...)`, not the factory directly (Decision 2).** The target is explicit (no trigger matching), but the method still applies BOTH Phase-3 per-subscriber backstops in dispatcher order — depth-cap (`enrollDepth` > `max-enroll-depth`) → auto-enroll rate-limit (`bf:rate:auto-enroll:{subscriberId}`) → resolve → re-enter → factory — before creating the child. A direct-factory call would inherit only the re-enter guard, missing the rate-limit. The enroll rides the existing `StepExecutor → FunnelEventService` edge, so no new bean-cycle risk (do NOT inject the engine/factory/`FunnelService` into `StepExecutor`).
- **`Outcome.COMPLETE` ends the parent from any cursor position.** The engine previously reached `completed` only at end-of-graph; `endParentAfter=true` must complete the parent right after enroll regardless of position, so `StepExecutor` returns a new `Outcome.COMPLETE` that `FunnelExecutionEngine.drive` maps to the existing claim-conditional `complete(exec, now)`. `endParentAfter=false` returns `CONTINUE` (parent advances, both funnels run in parallel). `CANCEL` was rejected — it yields `cancelled`, the wrong status.
- **`FunnelExecutionFactory.insertExecutionAt(..., startStepId)` overload starts the child at an arbitrary step.** Legacy `insertExecution` hard-starts at step 0; the SUBSCRIBE child must start at `targetEntryStepId`. The overload sets `currentStepId = startStepId` (fallback to step 0 when null/unresolved); `insertExecution` now delegates with `null`. The child inherits the parent's pinned `telegramBotId` (one CONNECTED bot per project — no new lookup, Decision 9).
- **Fail-closed by `projectId` at BOTH save and runtime — the main IDOR guard.** `FunnelRepository.findById` is NOT project-scoped, so every target resolution does an explicit `target.getProjectId().equals(projectId)` after load: `FunnelService.resolveSubscribeTarget` at save/activate, `FunnelEventService.enrollSpecificFunnel` at runtime. Missing / malformed-ObjectId / foreign-project all collapse to one rejection (no cross-tenant existence oracle). The entry field is `targetEntryStepId` (NOT `targetStepId`) to avoid the `Button.targetStepId` collision and stay out of the generic edge-pass (Decision 5).
- **Loud at save/activate, silent at runtime (Decisions 6-7).** Save validates existence + same-project + entry-step-exists only — `active` is deliberately NOT checked at save (allows referencing a still-`draft` target while building two linked funnels). Activation of the parent blocks if any SUBSCRIBE target is non-`active` (`funnel_subscribe_target_inactive`, 422). At runtime a `draft`/`paused`/deleted/foreign target → silent skip + greppable WARN (one id per reason, ids-only logs — anti log-injection), parent continues (snapshot isolation); a deleted entry step → fallback to start + WARN. Mirrors the deleted-custom-field precedent.
- **Cycles are a feature, bounded only by the two per-subscriber backstops.** `A→B→A` (return-to-menu) is allowed and NOT statically detected. The per-tick step budget does not bound a cross-execution cycle (the child is a separate `funnel_executions` row swept independently), so the only bounds are `enrollDepth` (depth-cap) + auto-enroll rate-limit — both already applied by `enrollSpecificFunnel`. Self-target `A→A` needs no special branch: it falls out of the re-enter guard (no-op without `allowReEnter`, restart-at-entry with it).
- **At-most-once: enroll is the side-effect before the claim-conditional advance/complete** (same ordering as `EMIT_EVENT`). A crash-replay of the step re-enrolls, but the re-enter partial-unique guard makes the duplicate a no-op (logged at WARN, `LOG_ENROLL_REENTER_IGNORED`).
- **Frontend: one form block over reused primitives.** `FunnelStepForm.vue` adds the `SUBSCRIBE_TO_FUNNEL` block — target picker (`SearchableSelect`, lazy `useFunnelsStore().fetch`), entry-step picker (lazy `fetchOne(targetFunnelId).steps` + a "from the start" sentinel → `targetEntryStepId=null`), an `endParentAfter` checkbox, an inline not-`active` hint, and a return-pattern hint (recommend `endParentAfter=true`; otherwise returning into a still-alive parent with `allowReEnter=false` becomes a no-op — Risk 2). The preview panel shows the `non_message` placeholder automatically (SUBSCRIBE is not in `isMessageStep`).

### Funnel Engine (Epic 06 — Phase 6: Message Composer)

Phase 6 (`work/completed/15-message-composer/`) replaces the three flat message step types (`SEND_MESSAGE`/`SEND_IMAGE`/`MENU`) with ONE `MESSAGE` composer step holding an ordered `List<ContentBlock>`. Decision numbers reference that tech-spec. Phases 1-5 patterns above still hold (claim-CAS at-most-once, snapshot, graph nav, sweep — unchanged).

- **One composer step = N Telegram messages, one per block.** `StepExecutor.message` iterates `blocks` under a SINGLE claim and sends one message per `ContentBlock` (TEXT→`sendText`, IMAGE/VIDEO/AUDIO/FILE→`send{Photo,Video,Audio,Document}`, ALBUM→`sendMediaGroup`). Per-node at-most-once is preserved (Decision 3): a crash mid-blocks leaves the node `in_progress`, the already-sent blocks are NOT resent (lost-forward, same as the old flat senders) — there is deliberately no per-block cursor.
- **Buttons + timeout stay step-level, attached to the LAST non-album block (Decision 2).** `buttons`/`timeout*` were NOT moved onto `ContentBlock`, so the callback wire-contract `{executionId}:{buttonIndex}`, strict parse, and IDOR/owner checks in `advanceOnCallback` are unchanged — only the keyboard's SOURCE moved from the `MENU` step to the composer's last non-album block. The old `advanceOnCallback` guard "cursor must point at a MENU step" became the POSITIVE `stepType == MESSAGE` (fail-closed) — replacing, not deleting it, else parked-MESSAGE callbacks would silently reject.
- **Album type-mixing predicate (Decision 5).** Each album `MediaItem` carries a `BlockType type` (∈ IMAGE/VIDEO/AUDIO/FILE); valid groups = photo/video mix, all-audio, or all-document; AUDIO/FILE never mix with another kind; `caption` only on the first item. Enforced inline on save (`FunnelService.validateAlbum`, `funnel_step_invalid` 422) AND mirrored in `FunnelStepForm.vue`. `TelegramSender.sendMediaGroup` derives each wire `media[].type` from the item kind via a closed-enum→four-literal map (never raw input), with its own array-response mapper (`mapBodyToSentAlbum`) + token-scrub parity.
- **Media is URL/file_id only — never dereferenced (Decision 6).** `requireMediaSource` accepts exactly an `http(s)` URI (rejects `file://`/`data:`/`javascript:`/empty-host) or an opaque `file_id`; the backend passes it verbatim to Telegram. No SSRF surface; the album correction added no dereference path.
- **Tolerant-read fail-safe for removed step types.** A legacy document with a removed `stepType` (`MENU`/`SEND_MESSAGE`/`SEND_IMAGE`) reads as the sentinel `StepType.UNKNOWN` via `StepTypeReadConverter` (`@ReadingConverter`, registered by `FunnelMongoConfig#mongoCustomConversions`) instead of throwing inside the sweep's `find(...)` (which is OUTSIDE the per-execution try/catch). `StepExecutor` terminal-fails an `UNKNOWN` step (`unknown_step_type`) — only that one execution, the tick survives. `UNKNOWN` is read-path only and can never be authored (gated by `validateSteps`, 422 — NOT the Jackson boundary, since `"UNKNOWN"` is a valid enum constant). Both exhaustive switches handle it without a `default`.
- **Engine ITs live under `@Tag("slow")`** (`FunnelExecutionEngineIT` — Testcontainers Mongo) and are EXCLUDED from the default `./gradlew test` lane. The load-bearing invariants (per-node at-most-once across two ticks, snapshot-isolation, tolerant-read) only run with `./gradlew test -PrunSlow=true` — pre-deploy QA MUST run the slow lane (no CI config exists yet). Seed helpers are split by navigation mode: index-seeded runs use an id-less helper, graph-mode runs set `currentStepId` — a non-null first-step `id` flips `graphMode` on and a null cursor then reads as "End" (silent no-op), which previously masked the crash-semantics IT.

### Funnel Engine (Epic 06 — Phase 7: Persistent Keyboard)

Phase 7 (`work/completed/16-persistent-keyboard/`) adds two fire-and-forget reply-keyboard step types `SET_KEYBOARD` (set a persistent bottom `ReplyKeyboardMarkup`) / `CLEAR_KEYBOARD` (`ReplyKeyboardRemove`). No new branching mechanism, no new `ExecutionStatus`, no migration (nullable adds). Decision numbers reference that tech-spec. Phases 1-6 patterns above still hold.

- **Standalone step types, NOT a `MESSAGE`-composer extension (Decision 1).** `MESSAGE.buttons` is coupled to the inline keyboard + `waiting_for_reply` park — the opposite semantics of a fire-and-forget reply keyboard, which returns `CONTINUE` and never parks. Both steps carry their own mandatory text (`keyboardText`+`keyboardParseMode`, ≤4096, same `VariableTemplateRenderer`) because Telegram attaches `reply_markup` only to a message.
- **Wire markup is an ad-hoc `Map` built in `StepExecutor`, `resize_keyboard` hardcoded `true` (Decision 5).** There is no typed `InlineKeyboardMarkup`/`ReplyKeyboardMarkup` record to extend — the inline keyboard was already an ad-hoc Map and `TelegramSender.sendText`'s 6th arg serializes any `Object replyMarkup` verbatim via Jackson. Buttons use the object form `{"text": …}` (not bare strings) for forward-compat with future per-button fields (`request_contact`, `web_app`). Wire shapes verified against the live Bot API via Context7. `KeyboardRow`/`KeyboardButton` are stored as records-in-list-in-record (the `ContentBlock.items` round-trip pattern), NOT `List<List<String>>`.
- **Validation reuses `funnel_step_invalid`; the duplicate-button-text check is new (Decision 6).** All rejections throw `invalidStep(...)` → 422 `funnel_step_invalid` (varying message, already keyed in both locales — zero error-mapping work). Caps: 1..10 rows × 1..4 buttons, button text non-blank ≤64 (= the keyword cap, so a label can always be an exact keyword). Duplicate trimmed button texts within one keyboard are blocked via `HashSet` — NO precedent in `validateButtons` (inline keyboards allow dup labels). `CLEAR_KEYBOARD` strict-rejects SET-only fields (`keyboardRows`/`isPersistent`/`oneTimeKeyboard`) being present rather than silently ignoring them. Every rule is mirrored byte-for-byte in `FunnelStepForm.vue` (the 422 is a backstop).
- **"Button → funnel" is a text convention + a non-blocking client-side hint, no backend match (Decision 8).** A tap arrives as ordinary `message.text` and routes through the existing Phase-3 keyword dispatch unchanged (contains-match, fan-out, re-enter guard, menu-precedence suppression all apply). The editor warns (amber, non-blocking — `subscribeInactiveHint` precedent) next to any button whose lowercased text matches no keyword of an `active && triggerType==='keyword'` funnel, computed live from `useFunnelsStore` (mirror of `containsAnyKeyword`). No new endpoint; the hint is advisory and never blocks save.
- **Preview branches on the SAVED step type, `kind="keyboard"`, labels clamped not rendered (Decision 7).** `previewStep` renders the request's `keyboardText` via the engine renderer and returns it as a single TEXT `RenderedBlock`; button labels are echoed VERBATIM (no variable rendering — labels are the keyword link, variables would break matching) but CLAMPED to the validation caps so preview never reflects an unbounded payload. The frontend `FunnelMessagePreview.vue` renders text + a bottom-keyboard mock; `{{ }}` only, never `v-html` (the Telegram-escaped string is not browser-safe, OWASP A03).
- **Engine slow-lane ITs gained their first wire-body assertions (Decision 9).** `FunnelExecutionEngineIT` (`@Tag("slow")`) previously asserted only counts/statuses; the keyboard ITs assert the exact `/sendMessage` `reply_markup` body via the `TelegramSenderIT` JsonNode idiom + the `FunnelTestRunSendIT` `takeRequest`/`readUtf8` drain, and that the run ends `completed` (never `waiting_for_reply`). Run them with `-PrunSlow=true`.
- **Form: keyboard behaviour is ONE 3-way radio, not two checkboxes (post-delivery UX change).** Telegram's `is_persistent` + `one_time_keyboard` are independent booleans whose `true+true` combo is contradictory (clients favour `is_persistent`). `FunnelStepForm.vue` collapses them into a single mutually-exclusive `keyboardMode` radio (Persistent / Normal / One-time) that maps to the two booleans on submit and derives the mode from them on edit-load — **persistent wins** on a contradictory stored `true+true` seed. The wire contract is unchanged (still emits both booleans); the mapping lives entirely in the form. (This supersedes the original user-spec "two checkboxes" AC.)
- **Preview-panel "edited step wins" priority MUST gate on `editOpen`, not just `editIndex` (regression fix).** `[funnelId].vue` sets `editIndex` on open but never resets it on close, and `editStep` derives from `editIndex` alone — so `previewIndex`'s `if (editOpen.value && editStep.value)` guard is load-bearing: drop the `editOpen` term and the preview stays pinned to the last-edited step forever, making row clicks a no-op.

### Funnel Engine (Epic 08 — Phase 8: Multi-entry)

Phase 8 (`work/completed/17-funnel-multi-entry/`) replaces the one-trigger-per-funnel model with `List<Trigger>` (multi-entry): besides the `on_start` main entry, a funnel can carry N `event` triggers, each bound to an `entryStepId` inside its own graph. A fired event redirects the subscriber's in-flight execution onto that branch, or starts a fresh one. Decision numbers reference that tech-spec. Phases 1-7 patterns above still hold (claim-CAS, snapshot, graph nav, sweep, dispatcher — unchanged); this builds the listen-side on the existing `EMIT_EVENT`/API-event fire-side. No canvas — the editor stays a vertical list (canvas is the next feature, `18-funnel-canvas`).

- **`List<Trigger>` + a denormalized `onStartTriggerValue` scalar — NOT a multikey unique index (Decision 6, the load-bearing schema call).** on_start cross-funnel uniqueness can't be expressed by a unique partial index over `triggers.*`: `partialFilterExpression` is document-level, so a funnel holding both an `on_start` and `event` triggers would bind ALL its trigger keys (including `event`) to the unique index — wrongly colliding `event` values that Phase 3 deliberately shares across funnels. So the single on_start value is denormalized to a nullable scalar `Funnel.onStartTriggerValue` (synced from the on_start element on every save path; `""`/blank → null), with partial-unique `(projectId, onStartTriggerValue)` filtered `status=active AND onStartTriggerValue exists`. `checkTriggerConflict`/`saveHandlingTriggerConflict` (pre-check + `DuplicateKeyException`→422) stay as defense-in-depth. The conflict lookup passes `""`→ actual value but **never null** (null would match all event-only funnels).
- **Index reshape via the existing `FunnelTriggerIndexReconciliation` BeanPostProcessor (Decision 7, same lesson as Phase 3).** The old `projectId_triggerType_triggerValue_unique_active` index is dropped in `postProcessAfterInitialization` (before `MongoTemplate` auto-creates the new `onStartTriggerValue` shape) so an `IndexKeySpecsConflict` (error 86) can't crash boot. `INDEX_NAME` still points at the OLD (dropped) index; idempotency keys off old-index presence-by-name, log-but-never-throw, greppable APPLIED/NO-OP markers. Never an `ApplicationRunner` (runs after auto-creation).
- **Redirect-or-start is one collaborator + a new engine method (Decisions 2, 3, 11).** `FunnelEventService` (the single Phase-3 dispatcher) owns the decision: a trusted in-flight probe (a fresh `findOne` scoped by projectId+funnelId+subscriberId, modelled on `ProcessTelegramUpdateJob.hasWaitingForReplyExecution` — that method lives there, NOT in the event service) → in-flight (`running|waiting|waiting_for_reply`) calls `FunnelExecutionEngine.redirectExecution`, else `FunnelExecutionFactory.insertExecutionAt(entryStepId)` honouring `allowReEnter`. `redirectExecution` is the only new execution-mutation point — no forked writer. It extends the `resumeOnCallback`/`claimForCallback` mechanic: a `claimForRedirect` CAS (`findAndModify`) scoped by BOTH `subscriberId` AND `funnelId` (anti-IDOR — the `executionId` comes ONLY from the trusted probe, never request/event input; the CAS re-verifies the pair so a mismatched-subscriber redirect is a guaranteed no-op), accepting the three in-flight statuses + `stepRunStatus=pending`, atomically sets `currentStepId=entryStepId` + `status=running`/`stepRunStatus=in_progress`, then runs `preStepGates`+`drive` now. **One execution per funnel per subscriber** — redirect mutates the existing row (no second `funnel_executions` doc), so `enrollDepth` is unchanged and the loop backstops still bound any `EMIT_EVENT`→trigger self-loop (no new row + per-tick budget + human-press menu-park; no artificial redirect counter).
- **The `@Lazy` bean-cycle break is REAL here (Decision 11, contrast Phase 3).** Injecting `FunnelExecutionEngine` into `FunnelEventService` closes `FunnelEventService → FunnelExecutionEngine → StepExecutor → FunnelEventService`. Phase 3 avoided its cycle structurally via `FunnelExecutionFactory` (no engine edge); Phase 8's redirect genuinely needs the engine, so the edge is broken with `@Lazy` on the injected engine — the context must start without `BeanCurrentlyInCreationException` (asserted by the full-context ITs).
- **Multikey element-match needs `$elemMatch`, and a re-scan recovers which element matched (Decision 12).** The event/tag/field fan-out query uses an explicit `@Query` with `$elemMatch` — flat derived predicates (`{'triggers.triggerType':?, 'triggers.triggerValue':?}`) evaluate independently across array elements and cross-element false-positive match. A multikey match still returns the funnel, not the element, so the dispatcher re-scans `triggers[]` to find the matched element and read its `entryStepId` (extends the Phase-3 keyword re-scan idiom). **`fire`'s on_start lookup uses the array `$elemMatch` query, NOT `findByProjectIdAndOnStartTriggerValueAndStatus`** — the denormalized scalar is null for a bare `/start` (Variant A) and that repo method forbids a null arg, so a bare-start funnel would never resolve; the array query preserves exact old semantics for both bare `""` and deep-link payloads.
- **Broken cursor after redirect fails only that execution (Decision 5).** The redirect resolves `entryStepId` against the execution's `stepsSnapshot` (snapshot isolation, no funnel versioning); if absent → terminal-fail just that execution (the Phase-6 tolerant-read precedent), the sweep + other executions continue.
- **Bound the trigger array + keep keyword caps (Decision 14, DoS A04).** The flat-trio model was implicitly bounded; the array reopens array-bloat / N×keyword-scan DoS. `@Size` ceiling on the trigger array (DTO) + a service-level 422 check, plus the preserved per-trigger keyword count/length caps (`MAX_KEYWORDS=50`, `MAX_KEYWORD_LENGTH=64`); the public `/events` path stays behind the existing rate-limit + fan-out ceiling.
- **Frontend Triggers panel clones `FunnelStepsList`, reuses `FunnelTriggerSettings` (Decision 13).** `FunnelTriggersPanel.vue` is a vertical add/delete/select list mounting the portable `FunnelTriggerSettings.vue` (Phase-3 node form, `lockType` added so the panel owns the type) per trigger + a per-trigger entry-step `SearchableSelect` built from PROP-sourced steps. The `__START__` sentinel maps to the **first step's id, not null** (event mid-entry requires a non-null `entryStepId` per the backend 422). Client duplicate-event-name guard is advisory; the 422 is the authority. The editor page (`[funnelId].vue`) holds triggers as an array with a per-element autosave gate: it **cancels the pending PATCH timer before re-checking the gate** (a later edit that makes the array incomplete must not let an armed PATCH fire), and uses an `applyingResponse` re-entrancy flag to suppress one watch cycle on the server echo (else `persist→applyResponse→watch→persist` PATCH-storms, since the echoed array always has a fresh identity).
- **i18n "no empty values" must assert the leaf value, not just key presence.** `check-locales.mjs`/`toHaveProperty` treat `""` as present, so the user-spec "без порожніх ключів" AC needs an explicit `value.trim().length > 0` assertion per required key in both locales (`required-keys.spec.ts`).
