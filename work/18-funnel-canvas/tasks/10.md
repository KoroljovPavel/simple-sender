## Description

Полнофичевый аудит качества тестов для фичи 18-funnel-canvas. Это задача Audit Wave — кода не пишем, только читаем все тесты, созданные/расширенные в фиче, и пишем отчёт.

Фича разбита на три слоя поверх готового графового бэкенда, и тестовая пирамида распределена осознанно (см. tech-spec «Testing Strategy»):
- **Unit-слой (Vitest)** несёт логику маппинга canvas (model↔graph): новый `frontend/composables/useFunnelCanvas.ts` со спекой `frontend/tests/composables/useFunnelCanvas.spec.ts`.
- **Component-слой (Vitest + `mountSuspended` + `mockNuxtImport('useFunnelsStore')`)** несёт визуальные инварианты canvas: `frontend/tests/components/funnels/FunnelCanvas.spec.ts`, плюс расширения `funnel-editor.spec.ts` и `required-keys.spec.ts`.
- **Integration-слой (backend)** несёт персистентность и семантику движка: round-trip в `FunnelControllerIT` / `FunnelService*` и семантику исполнения в `FunnelExecutionEngineIT`.
- **E2E намеренно отсутствует** — Vue Flow drag/zoom/connect хрупок под Playwright; живой drag/zoom покрыт ручной проверкой пользователя, golden-path Playwright (locale switch) остаётся.

Цель аудита: убедиться, что покрытие соответствует «Testing Strategy», ассерты проверяют конкретные значения полей на правильном объекте модели (а не counts/наличие ключей), пирамида сбалансирована (каждый инвариант лежит на правильном уровне, без дублирования и без дыр), и отсутствие E2E обосновано. Результат — письменный отчёт.

## Details

<!-- Аудит — read-only. Никакого кода/тестов не пишем; единственный артефакт — отчёт под logs/working/task-10/. -->

**Files:** `work/18-funnel-canvas/logs/working/task-10/test-audit.md` — единственный записываемый файл (отчёт-аудит). Кода и тестов не трогаем.

**Чек-лист покрытия (из tech-spec «Testing Strategy» — что должно быть покрыто):**

Unit-слой (`useFunnelCanvas.spec.ts`):
- model → nodes/edges: steps + опциональный start node + event-trigger nodes + notes дают правильный набор узлов; каждое ребро пишет правильное поле с правильным id (`next` / `Button.targetStepId` нужной кнопки / `timeoutTargetStepId` / entry)
- edge → model field, включая «no edge» → `null` (НЕ `""`) и неизменность соседних edge-полей
- dagre auto-layout при отсутствии координат; stored-координаты используются как есть; **mixed** (часть с координатами, часть null) лейаутит только непозиционированные
- **cycle** (return-to-menu) маппится и сериализуется без бесконечной рекурсии
- delete node → все входящие рёбра (`next`/button/timeout/`trigger.entryStepId`) авто-чистятся; **count** разрывов точный, выжившие рёбра не изменены
- **broken-edge detection**: ребро на отсутствующий/удалённый таргет И `on_start` trigger c `entryStepId == null` помечены как broken
- notes изолированы от `steps[]` (заметка не попадает в steps в PATCH payload)
- add node/edge → корректный PATCH payload (saved-node-only edge constraint)
- cross-funnel SUBSCRIBE → exit badge, не ребро

Component-слой (`FunnelCanvas.spec.ts` и расширения):
- broken-edge **highlight** рендерится для висящего ребра / start node без entry-ребра
- start-node **lifecycle**: нет для event-only воронки; есть при `on_start`; удаление узла убирает `on_start` entry; удаление только ребра оставляет подсвеченный broken edge; повторное добавление `on_start` из палитры заблокировано пока он есть
- side panel монтирует `FunnelStepForm` c `hideTargetPickers` → target `SearchableSelect`s отсутствуют; emitted step сохраняет существующие поля
- note text c `<img src=x onerror=...>` рендерится **escaped** (нет `v-html`, скрипт не исполняется)

Integration-слой (backend):
- **round-trip** `canvasPosition` (step + trigger) и `notes[]` через PATCH↔read; forward mapper + reverse mapper + **`FunnelStep.copyOf` асертится ОТДЕЛЬНО** (свой silent-drop seam); новый note получает server-minted id; app стартует на воронках без координат
- `FunnelExecutionEngineIT` (⚠️ `@Tag("slow")` на уровне класса — запускать ТОЛЬКО через `-PrunSlow=true`, иначе IT молча скипается; аудит обязан подтвердить, что эти ITs реально ВЫПОЛНИЛИСЬ, а не были пропущены тегом): `next == null` = конец гилки (нет fall-through к соседу по массиву); `on_start` c `entryStepId` входит в целевой шаг независимо от `order`; `applyTriggers` принимает `entryStepId` на `on_start` **только** если он резолвится в шаг этой воронки И **отклоняет** на non-event триггере (негативный кейс); существующий `funnel_broken_edge` 422 всё ещё срабатывает на activate c висящим ребром (regression); **step-budget loop backstop** всё ещё завершает циклическую воронку (Phase 2–3 regression при переписанном `advanceToNext`)

**Качество ассертов (главный фокус):** ассерт обязан проверять конкретное значение поля на правильном объекте модели И соседнее поле, которое НЕ должно меняться. Помечать как находку любой тест, который:
- проверяет только `.length` / количество узлов или рёбер
- проверяет только наличие ключа / `toHaveProperty` без значения
- проверяет только факт вызова мока без аргументов
- проверяет «no edge» как отсутствие ключа, а не как явный `null` (упустит баг `null` vs `""`)

**Баланс пирамиды:** mapping-логика обязана жить на unit-уровне (не дублироваться в component-тестах кроме рендер-инварианта); персистентность и семантика движка — только в ITs; визуальные инварианты (highlight, lifecycle, escape) — только в component. Помечать смещение уровня и дублирование одного инварианта.

**Dependencies:** задачи 1–7 завершены (их тесты — предмет аудита). Если canvas-специфичных файлов (`useFunnelCanvas.spec.ts`, `FunnelCanvas.spec.ts`) нет на диске — это критическая находка покрытия (задача реализации не написала тесты), а не сбой аудита.

**Edge cases:**
- Тестовый файл существует, но кейс из чек-листа в нём отсутствует → пробел покрытия.
- Кейс есть, но ассерт слабый (count/key) → находка качества, не покрытия.
- Один инвариант покрыт и в unit, и в component → возможное дублирование пирамиды (оценить, оправдано ли).
- `copyOf` round-trip не выделен в отдельный ассерт → находка (tech-spec требует отдельный seam).

**Implementation hints:** опираться на tech-spec «Testing Strategy» как на единственный источник чек-листа. Severity находок: critical (пропущен кейс из стратегии / ассерт не валит mis-wired handle), major (слабый ассерт, дублирование уровня), minor (стиль/именование). Отчёт — markdown, структура по четырём осям (покрытие / качество ассертов / баланс пирамиды / обоснование E2E) + список находок + вердикт.
