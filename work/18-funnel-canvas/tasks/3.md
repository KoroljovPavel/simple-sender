# Task 3: Backend execution semantics — null next = end, on_start explicit entry

## Required Skills

Перед выполнением задачи загрузи:
- `/skill:code-writing` — [skills/code-writing/SKILL.md](../../../.claude/skills/code-writing/SKILL.md)

## Description

Make the **drawn graph the single source of truth** for funnel execution. Today three behaviours still let
the steps-array ORDER secretly drive the flow; the canvas (Decision 3) replaces invisible order-edges with
explicit drawn `next` edges, so the engine must stop falling back to array order. Three coupled changes:

1. **`next == null` = end of branch** (Decision 4). `FunnelExecutionEngine.advanceToNext` currently treats a
   null `next` as "fall through to `array[here+1]`". After this task a step with no drawn `next` edge
   **terminates its branch** — the cursor goes to `null` (the existing "End" marker the drive loop already
   completes on). No fall-through to the neighbouring array element.

2. **`on_start` explicit entry via reused `Trigger.entryStepId`** (Decision 5). In `FunnelService.applyTriggers`
   the `on_start` case stops calling `requireNoEntryStep` and instead routes the supplied `entryStepId`
   through the **same funnel-scoped check as `event`** (`requireEventEntryStep`'s `stepIds.contains` rule), so
   an `on_start` entry is accepted **only when it resolves to a step of THIS funnel** — but, unlike `event`, a
   **null `entryStepId` is allowed** (it is a broken-edge state surfaced like every other broken edge, not a
   hard 422 here). All other non-event types keep rejecting any `entryStepId` (negative case must still 422).

3. **Start at the entry step, not step 0** (Decision 5 + APPROVED user-spec deviation). `FunnelTriggerServiceImpl.fire()`
   reads the matched funnel's `on_start` trigger `entryStepId` and starts the execution at it via the existing
   `FunnelExecutionFactory.insertExecutionAt(..., entryStepId)` primitive instead of `insertExecution(..., 0)`.
   **`FunnelService.testRun`** is aligned to the same entry step (APPROVED deviation: user-spec scoped the
   change to `fire()` only; without it a test-run from `array[0]` would execute the wrong/empty branch after
   change #1).

Constraints: `FunnelExecutionFactory.resolveStartCursor` is **untouched** (its step-0 fallback is
defence-in-depth, Phase-5 seam preserved); **no new field** is added (reuse `Trigger.entryStepId`); the
per-tick **step-budget loop backstop** must still terminate cyclic funnels after the `advanceToNext` rewrite.
Result: array order no longer affects execution; the engine ITs are green.

## What to do

1. **`FunnelExecutionEngine.advanceToNext`** — when `step.getNext() != null`, keep current behaviour
   (cursor → `next`, index synced). When `step.getNext() == null`, set the cursor to the **end marker**
   (`currentStepId = null`, `currentStepIndex` parked at the end of the snapshot) — **remove the
   `array[here+1]` fall-through** entirely. Update the method comment so it no longer claims "default-next =
   the step after this one in the list". Leave `advancePastDelay` working (it delegates to `advanceToNext`;
   its legacy null-cursor index+1 path for non-graph linear runs stays as-is).

2. **`FunnelService.applyTriggers` (`TRIGGER_ON_START` case)** — replace `requireNoEntryStep(dto.entryStepId())`.
   `requireEventEntryStep` **cannot** be called directly here: it throws 422 on a null id (verified L771-773),
   but the on_start case MUST accept null (an absent on_start edge is a broken-edge state surfaced elsewhere,
   not a hard error). Therefore a **dedicated null-tolerant helper/branch is REQUIRED** (not optional). Add a
   private helper — e.g. `requireOnStartEntryStep(entryStepId, stepIds)` — that: (a) when `entryStepId == null`
   → returns `null` (accepted; broken/absent edge), (b) when `entryStepId != null` → validates it through the
   funnel-scoped `stepIds.contains` check (reusing `requireEventEntryStep`'s `stepIds.contains` logic /
   `CODE_INVALID_ENTRY_STEP`) and throws `CODE_INVALID_ENTRY_STEP` (422) on a non-resolving id, otherwise
   returns the id. Store the (possibly null) result on the trigger via `trigger.setEntryStepId(...)`. The other
   non-event cases (`keyword`, `tag_added`, `custom_field_set`) keep calling `requireNoEntryStep` unchanged
   (they still 422 on any `entryStepId`). This is an A04 input-validation path — the helper/branch is mandatory,
   not a convenience.

3. **`FunnelTriggerServiceImpl.fire()`** — after matching the active on_start funnel, read the matched
   funnel's `on_start` trigger from `funnel.getTriggers()` and extract its `entryStepId`; replace both
   `executionFactory.insertExecution(projectId, funnel, ..., 0)` callsites (the re-enter-restart branch and the
   re-enter-disabled branch) with `executionFactory.insertExecutionAt(projectId, funnel, ..., 0, entryStepId)`.
   **The injected factory field in `FunnelTriggerServiceImpl` is named `executionFactory`** (NOT
   `funnelExecutionFactory` — that name belongs to `FunnelService`); use `executionFactory.` here. Update the
   stale comment that says "on_start enrolls always START at step 0 (entryStepId is null for on_start)".

4. **`FunnelService.testRun`** — read the funnel's `on_start` trigger `entryStepId` and replace
   `funnelExecutionFactory.insertExecution(projectId, funnel, ..., 0)` with
   `funnelExecutionFactory.insertExecutionAt(projectId, funnel, ..., 0, entryStepId)` so the author's test-run
   enters the same step as a live `/start`. **In `FunnelService` the injected factory field is named
   `funnelExecutionFactory`** (the longer name; distinct from `FunnelTriggerServiceImpl.executionFactory`); use
   `funnelExecutionFactory.` here.

5. Confirm `FunnelExecutionFactory.resolveStartCursor` and `insertExecutionAt` are reused **unchanged** (a
   null/dangling `entryStepId` already degrades to step 0 there — defence-in-depth).

## Acceptance Criteria

- [ ] `advanceToNext`: `next == null` ends the branch (cursor → null → completes); **no fall-through** to the
      next array element.
- [ ] `on_start` enrolment via `fire()` enters the step targeted by the start node's edge
      (`Trigger.entryStepId`), independent of array `order`.
- [ ] `FunnelService.testRun` enters the same on_start `entryStepId` (not `array[0]`).
- [ ] `applyTriggers` accepts an on_start `entryStepId` **only when it resolves to a step of this funnel**
      (funnel-scoped `stepIds.contains`); a null on_start `entryStepId` is accepted (broken-edge state); other
      non-event types still reject any `entryStepId` (negative case asserted).
- [ ] `resolveStartCursor` and `insertExecutionAt` are reused unchanged; **no new field** added.
- [ ] The step-budget loop backstop still terminates a cyclic funnel after the rewrite.
- [ ] `cd backend && ./gradlew test --tests '*FunnelExecutionEngineIT*'` is green; no regressions in other
      backend tests.

**Edge cases:**
- on_start trigger with a **null** `entryStepId` (start node present, edge deleted, or a legacy bare on_start):
  `applyTriggers` accepts it; `fire()`/`testRun` pass `null` to `insertExecutionAt` → `resolveStartCursor`
  degrades to step 0 (defence-in-depth) — no crash, no broken cursor.
- on_start `entryStepId` pointing at a **deleted** step: rejected at save (`applyTriggers` 422 on a non-null
  dangling id), and `funnel_broken_edge` still 422s on activate for the generic edge case (regression).
- **Cyclic** funnel (`a --next--> b --next--> a`): every edge is an explicit `next`, so the rewrite does not
  change the loop — the per-tick `maxStepsPerTick` budget in `drive` still trips and terminates `failed`.
- Empty snapshot / last step with null `next`: cursor → null → `endOfGraph` true → `complete`.
- Legacy linear (no step ids) runs: `advancePastDelay`'s null-cursor index+1 fallback path is untouched.

**Implementation hints (NOT pseudocode):**
- The drive loop's End semantics already exist — `advanceToNext` only needs to produce the SAME end-state the
  current `else` branch produces (`currentStepId = null`), just unconditionally when `next == null` instead of
  after a failed `array[here+1]` lookup.
- `fire()` matches the funnel but not a specific `Trigger` object; you must scan `funnel.getTriggers()` for
  the on_start element to read its `entryStepId` (mirror `syncOnStartTriggerValue`'s scan over triggers by
  `TRIGGER_ON_START`).
- Keep `CODE_INVALID_ENTRY_STEP` as the single error code so the frontend localizes one message.
- Do NOT touch `resolveStartCursor` / `insertExecutionAt` — passing a resolvable id is enough.
