## Description

Full-feature security audit фичи 18-funnel-canvas. Это аудит-таска — код не пишется, на выходе только отчёт.

Прочитать все исходники, созданные/изменённые в этой фиче (по `tech-spec.md` "Files to modify" из задач 1–7 и по записям в `decisions.md`), и проанализировать их против OWASP Top 10 по всем компонентам — бэкенд (DTO/валидация, mapping в `FunnelService`, execution-семантика `applyTriggers`/`fire`/`testRun`) и фронтенд (рендер заметок, canvas-компоненты, page-wiring).

Три фокус-зоны, заданные tech-spec, должны быть оценены явно:

1. **Stored XSS / note text rendering (A03 Injection):** текст заметки (`Funnel.notes[].text`) должен рендериться экранированным через `{{ }}` и НИКОГДА через `v-html`. Это совпадает со строгим no-`v-html` guard в `FunnelMessagePreview`/`FunnelStepForm` (Decision 7). Проверить, что ни в одном новом/изменённом фронтенд-компоненте текст заметки (или любой пользовательский ввод) не уходит в `v-html`/`innerHTML`/`domProps.innerHTML`.

2. **PATCH payload validation (DoS + injection guards):** на `UpdateFunnelRequest`/`NoteDto`/`CanvasPositionDto` должны быть: cap массива `notes[]` (`@Size(max=MAX_NOTES)`) с **service-side re-check** (зеркалит `MAX_TRIGGERS` DoS guard); `@Size(max=NOTE_TEXT_MAX)` на тексте заметки; finite-coordinate валидация (отклонять `NaN`/`Infinity` в `x`/`y`); note `id` **server-minted** (`ObjectId().toHexString()`, никогда не доверяется из тела запроса — зеркалит step-id minting в `toSteps`). Проверить, что эти границы реально присутствуют и в DTO-аннотациях, и в сервисном пере-чеке.

3. **Relaxed `entryStepId` validation path (A04 Insecure Design / input-validation regression — Decision 5):** ослабление в `applyTriggers` (`on_start` больше не зовёт `requireNoEntryStep`) НЕ должно расширять input-trust surface. `on_start` `entryStepId` обязан проходить funnel-scoped проверку (`requireEventEntryStep` → `stepIds.contains(id)`), то есть резолвиться в шаг ИМЕННО ЭТОЙ воронки — никакие dangling/cross-funnel/произвольные id не принимаются. `entryStepId == null` — это broken-edge state (422 на activate), а не дыра. Шаг-0 fallback в `resolveStartCursor` — defence-in-depth, не первичный guard; убедиться что первичный guard на месте.

**Edge cases для аудита:**
- Note text с `<img src=x onerror=...>` / `<script>` → должен рендериться экранированным (см. tech-spec Threats / AVP).
- PATCH с `notes[]` сверх cap → service re-check должен резать (не только bean-validation; DoS).
- PATCH с `x: NaN` / `x: Infinity` в `canvasPosition` → finite-validation должна отклонять.
- PATCH с note `id`, выдуманным клиентом → должен игнорироваться/переминтиться сервером, не доверяться.
- `on_start` trigger с `entryStepId` от другой воронки / несуществующим / произвольным → funnel-scoped `stepIds.contains` должен отклонять; `entryStepId == null` → broken edge (422 на activate), не приём произвольного.
- Не-`on_start` типы триггеров с `entryStepId` → по-прежнему должны отклоняться (relaxation касается только `on_start`).

**Implementation hints:**
- Источник истины по фокус-зонам — Decision 5 и Decision 7 в `tech-spec.md`, плюс "Bounds rationale (security)" в Data Models и Threats-таблица.
- Сверять с существующими безопасными паттернами проекта (`MAX_TRIGGERS` guard, no-`v-html` в `FunnelMessagePreview`/`FunnelStepForm`, step-id minting в `toSteps`) — новый код должен их зеркалить, а не изобретать.
- Для каждой фокус-зоны давать вердикт PASS/FAIL с файлом:строкой, а не общими формулировками.
