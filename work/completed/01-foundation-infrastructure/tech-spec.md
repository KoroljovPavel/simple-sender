# Tech Spec: 01 — Foundation Infrastructure

## Solution

Greenfield monorepo skeleton for Bot Funnel Service. No existing code — everything is created from scratch. The output is a runnable developer environment: Spring Boot 3.5.x reactive backend with one `/health` endpoint, Nuxt 4 frontend with a Hello World page, MongoDB + Redis via Docker Compose, and a developer onboarding guide.

The core technical challenge is Spring Security configuration for WebFlux: without an explicit `SecurityWebFilterChain` bean, Spring Boot auto-configuration blocks all endpoints with 401. We configure it upfront in Epic 01 to establish the security baseline for all subsequent epics.

Integration tests cannot rely on live MongoDB/Redis connections — developers run `./gradlew build` before starting `docker compose`. We solve this with `@MockBean` on the reactive connection factories, allowing `@SpringBootTest` to start without real DB connections.

## Architecture

### What we're building/modifying

- **`backend/`** — Gradle project: Spring Boot 3.5.x + WebFlux + Security; packages `com.botfunnel` (main), `com.botfunnel.security` (SecurityConfig), `com.botfunnel.common` (placeholder); `GET /health` endpoint returning `{"status":"ok"}`; three integration tests
- **`frontend/`** — Nuxt 4 project: Vue 3 + TypeScript + pnpm; `app.vue` Hello World page; `nuxt.config.ts` with `compatibilityDate` and TypeScript strict mode
- **`infra/`** — `docker-compose.yml` with MongoDB 8.0 + Redis 7.4; named volumes; no app containers
- **`docs/`** — `local-setup.md`: step-by-step developer onboarding guide
- **Root** — `.gitignore` (extended with Java/Gradle/Node/Nuxt artifacts), `.env.example` (2 vars), `.nvmrc` (Node 24)
- **`scripts/`** — `install-hooks.sh` that copies the gitleaks pre-commit hook to `.git/hooks/`

### How it works

Developer setup flow (from `git clone` to working backend):
1. `bash scripts/install-hooks.sh` → copies hook to `.git/hooks/pre-commit`
2. `cp .env.example .env` → defaults work without changes
3. `docker compose -f infra/docker-compose.yml up -d` → MongoDB :27017, Redis :6379
4. `cd backend && ./gradlew bootRun` → Netty starts on :8080
5. `GET http://localhost:8080/health` → `{"status":"ok"}`
6. `cd frontend && pnpm install && pnpm dev` → Nuxt dev server on :3000

Request flow for `/health`:
- HTTP GET arrives → Netty (embedded in Spring WebFlux)
- Reactive Security filter chain: `/health` matches `permitAll()` in `SecurityWebFilterChain` → passes through
- `HealthController` returns `Mono<Map<String, String>>` with `{"status":"ok"}`
- HTTP 200, `Content-Type: application/json`
- Any other path → `anyExchange().authenticated()` → HTTP 401

Integration test flow:
- `@SpringBootTest(webEnvironment = RANDOM_PORT)` starts full Spring context
- `@MockBean` for `MongoClient (com.mongodb.reactivestreams.client.MongoClient)` + `ReactiveRedisConnectionFactory` → no real DB connections
- `WebTestClient.get().uri("/health")` → assert HTTP 200 + `$.status == "ok"`
- Second test: same request without auth header → assert HTTP 200 (verifies SecurityConfig)

### Shared resources

None — no repositories or services use DB connections in Epic 01. MongoDB and Redis drivers are on the classpath but no beans depend on active connections at startup.

## Decisions

### Decision 1: Spring Boot 3.5.x over Spring Boot 4.0.x
**Decision:** Use Spring Boot 3.5.x (Spring Framework 6.x, Spring Security 6.x)
**Rationale:** Boot 3.5.x is the stable LTS line with comprehensive ecosystem support. `jobrunr-spring-boot-3-starter` (needed in later epics) is explicitly compatible. Boot 4.x introduced Spring Framework 7 breaking changes requiring vetting of every future dependency — unnecessary risk at project start.
**Alternatives considered:** Spring Boot 4.0.6 (original user-spec) — rejected due to JobRunr compatibility risk and immaturity of the 4.x ecosystem.
**References:** AC-3; approved by user during tech-spec planning.

### Decision 2: Nuxt 4 over Nuxt 3
**Decision:** Use Nuxt 4 (4.4.x stable). `compatibilityDate` field in `nuxt.config.ts` is strongly recommended (generated by `nuxi init` by default) — controls Nitro preset behavior.
**Rationale:** Nuxt 3 reaches EOL July 31, 2026 — starting a new project on it creates a short-term migration obligation. Nuxt 4 is stable since July 2025.
**Alternatives considered:** Nuxt 3 (original user-spec) — rejected due to EOL during the active development period.
**References:** AC-9; approved by user during tech-spec planning.

### Decision 3: Include spring-boot-devtools [TECHNICAL]
**Decision:** Add `spring-boot-devtools` as `developmentOnly` dependency in `build.gradle`
**Rationale:** Spring Boot 3.5.x fully supports devtools. Enables hot restart in IntelliJ without full JVM restart. `developmentOnly` configuration ensures it is stripped from production JARs automatically — the final JAR/Docker image is not affected.
**Alternatives considered:** Excluded (original user-spec, due to Boot 4 classloader incompatibility) — reason does not apply to Boot 3.
**References:** [TECHNICAL] — developer ergonomics improvement; approved by user during tech-spec planning.

### Decision 4: Static /health response, no Spring Boot Actuator
**Decision:** `HealthController` returns hardcoded `{"status":"ok"}` as a plain `@RestController`
**Rationale:** Actuator with real connectivity checks requires DB layer to be running. `spring-boot-starter-actuator` is not on the classpath in Epic 01. Full Actuator health indicators are added when monitoring is set up (deferred epic).
**References:** AC-5; user-spec "Технічні рішення" section.

### Decision 5: SecurityWebFilterChain with @EnableWebFluxSecurity
**Decision:** `SecurityConfig` uses `@Configuration` + `@EnableWebFluxSecurity`, defines one `SecurityWebFilterChain` bean via `ServerHttpSecurity`. CSRF is explicitly disabled (stateless REST API). `/health` gets `permitAll()`, then `anyExchange().authenticated()` for all other paths.
**Rationale:** Without an explicit `SecurityWebFilterChain` bean, Spring Boot auto-configures one that blocks all requests with 401. Spring Security 6 WebFlux enables CSRF protection by default — for a stateless REST API this must be disabled explicitly, otherwise all non-GET requests return 403. Rule ordering is first-match: `pathMatchers("/health").permitAll()` must appear before `anyExchange().authenticated()` — swapping them causes all requests including `/health` to require auth.
Note: `@EnableWebFluxSecurity` does not include `@Configuration` in Spring Security 6 — both annotations are required.
**References:** AC-6, AC-8; user-spec "Технічні рішення" section.

### Decision 6: @MockBean for DB auto-config in integration tests
**Decision:** Integration tests use `@MockBean` for `MongoClient (com.mongodb.reactivestreams.client.MongoClient)` and `ReactiveRedisConnectionFactory`
**Rationale:** Developers must be able to run `./gradlew build` without `docker compose` running. `@MockBean` is the simplest solution — the skeleton test does not actually use DB, so mocking the connection factory is sufficient and avoids heavyweight embedded-DB dependencies.
**Note — patterns.md conflict:** `patterns.md` states "No mocking of the database in integration tests — use real embedded MongoDB." This decision intentionally deviates from that rule. Rationale: the patterns.md rule targets business logic tests that exercise MongoDB queries. The Epic 01 tests exercise HTTP routing and Spring Security filters only — MongoDB is never queried. Using embedded MongoDB would add a heavyweight dependency for a test that never touches the DB. The deviation is scoped to this skeleton epic; all future epics with real repository usage must follow patterns.md.
**Alternatives considered:** Embedded MongoDB (`de.flapdoodle.embed.mongo`) — adds a heavyweight dependency for a test that doesn't exercise MongoDB; overkill for Epic 01.
**References:** AC-15; user-spec "Тестування" section.

### Decision 7: Gitleaks hook via scripts/install-hooks.sh
**Decision:** Pre-commit hook is distributed via `scripts/install-hooks.sh` (tracked in git). Running the script writes the hook to `.git/hooks/pre-commit` and sets it executable.
**Rationale:** `.git/hooks/` is not tracked by git. An install script is the standard approach for hook distribution without Husky or pre-commit frameworks (intentionally not added in Epic 01 to keep dependencies minimal).
**References:** AC-14; user-spec "Ризики" section.

### Decision 8: Gradle Groovy DSL + Java 21 toolchain + Foojay resolver
**Decision:** `build.gradle` (Groovy DSL), Java 21 toolchain via `java.toolchain.languageVersion = JavaLanguageVersion.of(21)`, Foojay resolver plugin in `settings.gradle` for JDK auto-provisioning, Gradle 8.x wrapper
**Rationale:** Groovy DSL is the Spring Initializr default and most documented format. Toolchain pinning is stronger than `sourceCompatibility` — Gradle provisions the exact JDK via Foojay if not installed locally.
**References:** AC-3; user-spec "Технічні рішення" section.

### Decision 9: MongoDB 8.0 + Redis 7.4 with named volumes and localhost binding
**Decision:** `mongo:8.0` and `redis:7.4` official images; named volumes `mongodb_data` and `redis_data`; ports bound to `127.0.0.1` (e.g. `127.0.0.1:27017:27017`)
**Rationale:** Latest stable major releases. Named volumes ensure data persists across `docker compose down` / `up` cycles. Binding to `127.0.0.1` instead of the default `0.0.0.0` prevents unauthenticated MongoDB/Redis from being accessible to other machines on the local network — important since no auth is configured for local dev convenience.
**References:** AC-10.

### Decision 10: Only security and common packages in Epic 01
**Decision:** Create only `com.botfunnel.security` (SecurityConfig) and `com.botfunnel.common` (package-info.java) alongside the root `com.botfunnel` package
**Rationale:** Other modules (auth, project, bot, etc.) are created in their respective epics with final names. Creating stubs now leads to renaming churn.
**References:** AC-6, AC-7; user-spec "Технічні рішення" section.

## Agent Verification Plan

**Source:** user-spec "Як перевірити" section.

### Verification approach

Agent runs all checks locally without deployment. Backend is started after `./gradlew build` passes.

1. `cd backend && ./gradlew build` → `BUILD SUCCESSFUL`, all three integration tests pass
2. Start backend: `./gradlew bootRun` (background), wait for Netty startup log
3. `curl -s http://localhost:8080/health` → body `{"status":"ok"}`, HTTP 200
4. `curl -s -o /dev/null -w "%{http_code}" http://localhost:8080/health` → `200` (no auth token — confirms Security config)
5. `ls backend/ frontend/ infra/ docs/` → all four directories exist
6. `grep -E "MONGODB_URI|REDIS_URL" .env.example` → both vars present
7. `docker compose -f infra/docker-compose.yml up -d` → both services start
8. `nc -z localhost 27017 && nc -z localhost 6379` → both ports accessible

### Tools required
bash, curl, docker — all standard. No MCP tools required (frontend verification is by user, not agent).

## Risks

| Risk | Mitigation |
|------|-----------|
| MongoDB/Redis auto-config breaks `./gradlew build` | `@MockBean` on `MongoClient (com.mongodb.reactivestreams.client.MongoClient)` + `ReactiveRedisConnectionFactory` — Spring context starts without real connections |
| Gitleaks not installed by developer | Hook exits 0 with a warning (soft failure) — chosen to not block `git commit` for new devs who haven't installed it yet. Accepted risk: no CI-side compensating scan in Epic 01 (deferred). `docs/local-setup.md` provides install instructions. |
| Port conflicts (27017, 6379, 8080, 3000) | `docs/local-setup.md` documents how to remap each: `docker-compose.yml` for 27017/6379, `application.properties` for 8080, `nuxt.config.ts` for 3000 |
| Windows developer: bash scripts and Docker Compose behavior | `docs/local-setup.md` includes WSL2 recommendation and explicit Windows warning |
| Nuxt 4.4.x `ssr: false` bug | SSR stays enabled (default) in `nuxt.config.ts` — bug only affects SPA mode |
| Gradle wrapper not present at start | Task 2 runs `gradle wrapper` inside `backend/` — prerequisite: Gradle 8.x installed locally once |
