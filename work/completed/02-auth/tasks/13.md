# Task 13: Security Audit

## Required Skills

Before starting, load:
- `/skill:security-auditor` — [SKILL.md](~/.claude/skills/security-auditor/SKILL.md)

## Description

OWASP Top 10 security audit across all auth components. This is the most important audit for this feature — auth code is the highest-risk code in any application.

Focus areas: token entropy and hash storage, session fixation prevention, brute-force bypass scenarios, dummy BCrypt timing attack prevention, CSRF configuration, email enumeration prevention, mass assignment in profile PATCH, Bean Validation completeness, HTML encoding in email templates, CORS allowCredentials setup, HttpOnly/Secure/SameSite cookie flags, sensitive data in logs.

## What to do

1. **Review token security** (OWASP A02: Cryptographic Failures):
   - Verify `TokenService.generateRawToken()` uses `SecureRandom` (not `Random` or `Math.random()`)
   - Verify tokens are 32 bytes (256 bits) of entropy — sufficient against brute-force
   - Verify SHA-256 hash stored in DB, raw token never persisted
   - Verify `DUMMY_HASH` in AuthService is a valid bcrypt hash (not empty, not plaintext)

2. **Review session security** (OWASP A07: Identification and Authentication Failures):
   - Verify session fixation prevention: old session invalidated, new session created before `SecurityContext` stored
   - Verify SESSION cookie is HttpOnly (configured in SecurityConfig)
   - Verify SameSite=Strict in prod, SameSite=Lax in dev
   - Verify `maxInactiveInterval` set correctly for rememberMe vs non-rememberMe

3. **Review brute-force protection** (OWASP A07):
   - Verify both per-email AND per-IP keys checked before any user lookup
   - Verify INCR + EXPIRE atomicity: EXPIRE only on first INCR (count == 1), not on every failed attempt
   - Verify counters reset on successful login (DEL both keys)
   - Test bypass: IP counter bypass — what if attacker uses different IPs? (Per-email counter still applies — verify threshold 5)
   - Test bypass: email counter bypass — what if attacker uses different emails per IP? (Per-IP counter threshold 20 — verify)

4. **Review email enumeration prevention**:
   - `forgotPassword`: always 200, same response time — verify no timing difference in code path
   - `resendVerification`: `SET NX EX 60` executed BEFORE user lookup — verify order in code
   - Login with missing user: dummy BCrypt executed — verify it actually runs (not short-circuited)

5. **Review CSRF** (OWASP A01: Broken Access Control):
   - Verify CSRF was NOT disabled after the `csrf.disable()` removal in Task 2
   - Verify `CookieCsrfTokenRepository` configured correctly for SPA use
   - Verify SameSite cookie policy supplements CSRF token (defense in depth)

6. **Review mass assignment** (OWASP A01):
   - `PATCH /api/profile`: verify `UpdateProfileRequest` only has `name` field — `isSuperAdmin` cannot be set via PATCH
   - Verify `@JsonIgnoreProperties(ignoreUnknown=true)` is on `UpdateProfileRequest`

7. **Review injection and XSS**:
   - Email templates: verify user name is HTML-escaped before embedding
   - Error messages: verify user-supplied data (email, name) is not reflected raw in error responses in a way that could enable XSS on frontend

8. **Review sensitive data exposure**:
   - Verify no passwords, tokens, or session IDs in log statements across all packages
   - Verify `ErrorResponse` does not expose stack traces or internal details

9. **Review CORS** (OWASP A05: Security Misconfiguration):
   - Verify `allowedOrigins` is NOT `*` when `allowCredentials=true`
   - Verify origin is the exact app URL, not a regex/prefix that could be exploited

10. **Write security findings** to `work/02-auth/logs/working/task-13/security-auditor-1.json` as JSON array of `{severity, category, file, issue, recommendation}`.

## Details

**OWASP mapping for this feature:**
- A01 (Access Control): mass assignment, CSRF, unauthenticated endpoint access
- A02 (Crypto): token entropy, BCrypt cost, hash storage
- A03 (Injection): HTML injection in emails via user name
- A05 (Misconfiguration): CORS, cookie flags, CSRF disabled
- A07 (Auth failures): session fixation, brute-force, timing attacks, enumeration

**Critical checks (highest risk):**
1. `DUMMY_HASH` must be a valid bcrypt string starting with `$2a$12$` — if it's empty or wrong format, `BCryptPasswordEncoder.matches()` throws instead of returning false, which means the timing protection fails AND returns 500
2. Session fixation: if the code calls `session.invalidate()` but then stores `SecurityContext` in the OLD session attributes (before invalidation takes effect), fixation is not prevented — verify the code flow carefully
3. `SET NX EX 60` on resend: if user lookup happens before the `SET NX`, an attacker can time the difference between "email exists" (slower) and "email not found" (faster) responses
