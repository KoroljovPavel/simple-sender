## Description

Test quality and coverage audit across all auth feature components written in Tasks 1–11. The goal is to verify that the test suite actually catches real bugs — not just that tests exist or that status codes are checked.

This is an Audit Wave task — the auditor IS the review. No reviewers. Output: findings report at the JSON path and a summary written to decisions.md.

These all mock MongoDB and Redis via `@MockitoBean`. None of the auth integration tests from the tech-spec Testing Strategy have been written yet by the time this audit runs. The auditor must evaluate WHAT was actually written by Tasks 1–11 against WHAT was required by the tech-spec.

## What to do

1. **Discover all test files** written by Tasks 1–11:
   - List `backend/src/test/java/com/botfunnel/` recursively
   - For each test file: read it fully; note what it tests, what container setup it uses, what assertions it makes

2. **Audit Testcontainers setup** (Decision 6):
   - Does `AbstractIntegrationTest` base class exist?
   - Does it use `@SpringBootTest(RANDOM_PORT)` + `@Testcontainers` + singleton container pattern?
   - Are all three containers present: `MongoDBContainer` (via `org.testcontainers:mongodb`), Redis (via `org.testcontainers:redisstack` or `GenericContainer("redis:7-alpine")`), and `MailpitContainer` (via `ch.martinelli.oss:testcontainers-mailpit:1.3.1`)?
   - Does `application-test.properties` override `spring.data.mongodb.uri`, `spring.data.redis.url`, `spring.mail.host/port`?
   - Are containers started with `@Container` + `static` field (singleton pattern = containers shared across all tests, not restarted per test class)?

3. **Audit integration test assertion depth**:
   - For each flow: does the test assert ONLY HTTP status, or also DB/Redis state?
   - Required: after registration → query MongoDB `users` collection, assert `status=pending`, `emailVerificationTokenHash` is non-null
   - Required: after login → query MongoDB `events` collection, assert `login_success` event present with matching userId
   - Required: after failed login × 5 → query Redis, assert `brute:fail:{email}` counter = 5
   - Required: after successful login (post-failure) → query Redis, assert key DELETED (not just count = 0)
   - Required: after reset-password → query MongoDB `sessions` collection by principal, assert 0 records

4. **Audit Mailpit token extraction**:
   - Do tests that cover email verification and password reset actually fetch the email from Mailpit API?
   - Expected pattern: after POST /api/auth/register, call `GET http://mailpit:8025/api/v1/messages`, parse response, extract raw token from email body link, then use that token in verify-email request
   - Flag any test that uses a hardcoded/mocked token instead of the real one from Mailpit

5. **Audit brute-force counter reset test**:
   - Is there a test that: performs N-1 failed logins → performs 1 successful login → then queries Redis to verify both `brute:fail:{email}` and `brute:fail:ip:{ip}` keys are gone?
   - A test that only checks the 200 response on success is insufficient — the Redis DEL must be verified in the DB layer

6. **Audit event collection assertions**:
   - After `POST /api/auth/login` (success): assert `EventRepository.findByUserIdAndEventType(userId, "login_success")` returns a record
   - After `POST /api/auth/login` (failure): assert `login_failed` event with null userId saved
   - After `POST /api/profile/change-password`: assert `password_changed` event saved
   - After `DELETE /api/profile`: assert `account_deleted` event saved
   - Flag any flow that has no corresponding event assertion

7. **Audit session TTL verification**:
   - Does the rememberMe=true test actually query the MongoDB `sessions` collection and assert `maxInactiveInterval >= 2592000` (30 days in seconds)?
   - Does the rememberMe=false test assert `maxInactiveInterval <= 86400` (24h)?
   - A test that only checks the 200 response without querying the sessions collection is insufficient

8. **Audit dummy BCrypt timing test**:
   - Is there a test that confirms login with a non-existent email does NOT return 500 (this is the minimum)?
   - Is there a timing test that measures response time for non-existent-email login vs wrong-password login and confirms they are comparable (within ~2x)?
   - Note: timing assertions are inherently flaky — flag if the test uses `Thread.sleep` or hardcoded time bounds instead of a reasonable tolerance

9. **Audit change-password session invalidation test**:
   - Does the test for `POST /api/profile/change-password` (success path) verify:
     a. Current session (`SESSION` cookie used in request) remains valid — subsequent request with same cookie returns 200
     b. A second session (created by a separate login before the password change) is now invalid — request with that cookie returns 401
   - A test that only checks the 200 response or only checks the new password works is insufficient

10. **Write findings** to `work/02-auth/logs/working/task-14/test-reviewer-1.json` as a JSON array of `{severity, area, file, issue, recommendation}` objects.
    - Severity: `critical` (test missing entirely for required flow), `high` (test exists but assertion is HTTP-status-only), `medium` (test exists, assertions partially correct but miss DB/Redis state), `low` (minor quality issue)

11. **Write summary** to `work/02-auth/decisions.md`.

## Details

**What the tech-spec requires (Testing Strategy section) — use as the checklist:**

Required integration test flows (all must use Testcontainers, not mocks):
- Registration: 201 + user in DB with status `pending` + email in Mailpit + event NOT present
- Email verification: valid token → 200 + `status=active` + token hash cleared in DB
- Login: 200 + SESSION cookie + `login_success` event in `events` collection
- Login brute-force: 5 wrong → Redis counter = 5; 6th → 429; success after → Redis keys DEL'd
- Login rememberMe: MongoDB `sessions.maxInactiveInterval` ≥ 2592000 (rememberMe=true) / ≤ 86400 (false)
- Login non-existent email: 401 (not 500); timing comparable to wrong-password login
- Forgot/reset password: Mailpit token extraction → valid token → 200 + old password rejected + sessions collection → 0 records
- Change-password: current session still valid + other session invalidated + `password_changed` event logged
- Terminate-all-sessions: query `sessions` collection → 0 records for user
- Delete account: `status=deleted` + `deletedAt` set in DB + `account_deleted` event + current session invalidated
- Super Admin seed: idempotency (run twice → 1 record)
- Hard-delete job: `deletedAt > 30d` → deleted; `deletedAt < 30d` → kept

**Assertion quality scale:**
- Insufficient: `expectStatus().isOk()` only
- Partial: status check + one DB field
- Complete: status check + all relevant DB/Redis fields + event record

**Testcontainers singleton pattern (correct):**
```java
@Container
static MongoDBContainer mongo = new MongoDBContainer("mongo:8.0").withReuse(true);
```
The `static` keyword is critical — without it, containers restart per test class (slow and unreliable).
Note: `.withReuse(true)` requires `testcontainers.reuse.enable=true` in `~/.testcontainers.properties` and does not work in CI without additional setup. Prefer a static singleton base class pattern instead.

**Mailpit token extraction (expected pattern):**
To extract the verification token from email: construct a WebClient pointing to `http://localhost:{mailpitContainer.getMappedPort(8025)}`. Call `GET /api/v1/messages` to list emails, then `GET /api/v1/message/{id}/body.txt` or parse the HTML body to extract the token URL.
Any test that injects a token via direct DB write instead of extracting from Mailpit is missing the actual email delivery assertion.
