## Description

Final acceptance gate for Epic 02 — Authentication & Accounts. This task runs the full test suite, verifies every acceptance criterion from user-spec and tech-spec, and confirms the feature is production-ready.

Scope covers: backend test suite with 80%+ coverage, all auth REST endpoints, session behavior (TTL, fixation prevention), brute-force protection (per-email and per-IP keys), email flows via Mailpit Testcontainer, Super Admin seed idempotency, JobRunr hard-delete job, and frontend pages rendering with auth middleware redirects.

No reviewers — this IS the final QA gate. Output: report at `work/02-auth/logs/working/task-15/pre-deploy-qa-1.json`.

## What to do

1. **Run the full test suite** — `./gradlew test` from `backend/`. Confirm all tests pass and JaCoCo reports 80%+ line coverage for `auth`, `user`, `profile`, `email`, `events` packages. If any test fails, record the failure in the report (do not fix — escalate to decisions.md).

   Pre-flight checks before running:
   - Create output directory if needed: `mkdir -p work/02-auth/logs/working/task-15/`
   - Verify JaCoCo plugin is configured in `backend/build.gradle` (added in Task 1). If missing, it's a blocker — Task 1 must be re-run or fixed before QA can verify coverage.

2. **Verify auth endpoints against acceptance criteria:**
   - `POST /api/auth/register` (valid) → 201, user `pending` in MongoDB, email in Mailpit
   - `POST /api/auth/register` (invalid password < 8 chars, no digit) → 400 with validation errors
   - `POST /api/auth/register` (existing email) → 409 + message "Користувач з таким email вже існує"
   - `POST /api/auth/register` (soft-deleted email within 30d) → 409 + support contact message
   - `GET /api/auth/verify-email?token=VALID` → 200 `{redirect: "/login"}`, user status `active`, token hash cleared
   - `GET /api/auth/verify-email?token=INVALID` → 400 (not 500)
   - `GET /api/auth/verify-email?token=EXPIRED` → 400 `{code: "TOKEN_EXPIRED"}`
   - `POST /api/auth/resend-verification` within 60s → 429
   - `POST /api/auth/login` (active user) → 200 + SESSION cookie
   - `POST /api/auth/login` (pending user) → 200 + SESSION cookie + warning field
   - `POST /api/auth/login` (blocked user) → 403 + message containing SUPPORT_EMAIL value
   - `POST /api/auth/login` (non-existent email) → 401 (not 500, check timing is comparable)
   - `POST /api/auth/logout` → current session invalidated; other sessions on other devices unaffected
   - `POST /api/auth/forgot-password` (any email, including non-existent) → always 200
   - `POST /api/auth/reset-password` (valid token) → 200, old password rejected, ALL sessions invalidated (query `sessions` → 0 records for user)
   - `POST /api/auth/reset-password` (expired token) → 400
   - `POST /api/auth/reset-password` (already-used token) → 400
   - `POST /api/auth/reset-password` (invalid token) → 400 (not 500)
   - `GET /api/auth/me` → returns current user DTO when authenticated; 401 when not authenticated

3. **Verify session behavior:**
   - `rememberMe: true` → query MongoDB `sessions` collection, assert `maxInactiveInterval` ≥ 2592000 seconds (30 days)
   - `rememberMe: false` (or absent) → assert `maxInactiveInterval` ≤ 86400 seconds (24h)
   - Session fixation prevention: session ID after login differs from any pre-auth session ID

4. **Verify brute-force protection (both Redis keys):**
   - 5 failed logins from the same email → 6th attempt returns 429; Redis key `brute:fail:{email}` = 5
   - 20 failed logins from the same IP (different emails) → next attempt returns 429; Redis key `brute:fail:ip:{ip}` = 20
   - Successful login after failed attempts → both Redis counters deleted (DEL confirmed)
   - INCR + EXPIRE atomicity: Review `AuthService` source code — verify `EXPIRE` is called only when INCR returns 1 (first failure), not on every failed attempt. This cannot be verified via test output — read the code.

5. **Verify email flows via Mailpit Testcontainer:**
   - Registration email delivered to Mailpit; token URL extractable from body
   - Password reset email delivered to Mailpit; token URL extractable from body
   - Resend-verification email delivered on second call (after 60s cooldown reset in test)
   - No email sent for `POST /api/auth/forgot-password` with unknown email (Mailpit count = 0 for that test)

6. **Verify session fixation prevention:**
   - Obtain session ID before login (or note there is no pre-auth session), login, confirm new session ID in response cookie differs

7. **Verify Super Admin seed idempotency:**
   - Run `SuperAdminSeeder` logic twice (integration test or manual trigger)
   - Query MongoDB: exactly 1 document with `isSuperAdmin=true` and the configured email

8. **Verify JobRunr hard-delete job:**
   - Integration test: create user with `deletedAt = now - 31d`, create another with `deletedAt = now - 29d`
   - Trigger job manually
   - Assert: first user hard-deleted from MongoDB; second user still present
   - Assert: deleted user IDs appear in logs

9. **Verify profile endpoints:**
   - `GET /api/profile` → 200 with name, email, status
   - `PATCH /api/profile` with `{name: "New Name"}` → 200, name updated in MongoDB
   - `PATCH /api/profile` with `{isSuperAdmin: true}` → field ignored (whitelist DTO), isSuperAdmin unchanged
   - `POST /api/profile/change-password` (wrong current password) → 400
   - `POST /api/profile/change-password` (correct current password) → 200; new password works for login; other sessions invalidated; current session still valid
   - `POST /api/profile/terminate-all-sessions` → all user sessions removed from MongoDB `sessions` collection
   - `DELETE /api/profile` → user status `deleted`, `deletedAt` set, current session invalidated; `account_deleted` event logged

10. **Verify auth events in `events` collection** — confirm each of the following event types is present after corresponding flow:
    - `login_success` (after successful login)
    - `login_failed` (after failed login attempt)
    - `password_changed` (after change-password or reset-password)
    - `email_verified` (after verify-email)
    - `account_deleted` (after delete account)

11. **Verify frontend — 7 pages render (manual or Playwright):**
    - `/auth/login` renders without console errors
    - `/auth/register` renders without console errors
    - `/auth/forgot-password` renders without console errors
    - `/auth/reset-password` renders without console errors
    - `/auth/verify-email` renders without console errors
    - `/dashboard` renders when authenticated
    - `/profile` renders when authenticated

12. **Verify auth middleware redirects:**
    - Unauthenticated user navigates to `/dashboard` → redirected to `/auth/login`
    - Unauthenticated user navigates to `/profile` → redirected to `/auth/login`
    - Authenticated user navigates to `/auth/login` → redirected to `/dashboard`

## Details

**Test suite structure to verify coverage:**
- `AbstractIntegrationTest` base: MongoDB 8.0, Redis 7.4, Mailpit 1.3.1 via Testcontainers (Singleton pattern)
- `application-test.properties` overrides: `spring.data.mongodb.uri`, `spring.data.redis.url`, `spring.mail.host/port`
- Coverage target packages: `com.botfunnel.auth`, `com.botfunnel.user`, `com.botfunnel.profile`, `com.botfunnel.email`, `com.botfunnel.events`

**Brute-force test edge cases to confirm present:**
- Test uses different test users per brute-force test (counters may bleed between tests if same email used)
- Per-IP test: `WebTestClient` must send `X-Forwarded-For` or the test must control IP via mock — confirm the integration test covers the per-IP path, not just per-email
- Counter reset: after a failed attempt sequence, a correct login must DEL both keys (verify via `ReactiveRedisTemplate.hasKey()` returns false)

**Session TTL verification:**
- After login with `rememberMe: true`, query MongoDB `sessions` collection: `db.sessions.findOne({principal: userId})` → check `maxInactiveInterval` field value (in seconds)
- Spring Session stores `maxInactiveInterval` as a `Duration` serialized to the document — verify the integration test asserts on the actual stored value, not just HTTP response

**Sessions collection field path:**
- Task 6 established the verified field path for `ReactiveMongoTemplate` terminate-all-sessions queries — confirm the field path used in tests matches what spring-session-data-mongodb actually stores (log or query the sessions collection in the test if uncertain)

**Super Admin seed:**
- `SUPER_ADMIN_EMAIL` and `SUPER_ADMIN_PASSWORD` must be set in test environment (either `application-test.properties` or environment vars passed to `SpringBootTest`)
- Idempotency test: run `SuperAdminSeeder` bean twice — assert `userRepository.countByIsSuperAdminTrue()` == 1

**JobRunr job trigger:**
- In integration test, inject `JobScheduler` (JobRunr) and call the job directly, or use JobRunr's `BackgroundJobServer` to trigger the recurring job by name
- Assert on MongoDB state after trigger, not on log output alone

**Frontend check:**
- If Playwright tests are not available, manual verification via browser is acceptable for frontend items
- Key middleware check: navigate directly to `http://localhost:3000/dashboard` without auth → must land on `/auth/login`

**Known risks from tech-spec:**
- `spring.data.mongodb.auto-index-creation=false` may prevent spring-session from auto-creating the `expireAt` TTL index on `sessions` — verify session expiry works in at least one integration test
- Dummy BCrypt on missing user: login with non-existent email must return 401 (not 500). If `DUMMY_HASH` is malformed (not a valid bcrypt string starting with `$2a$12$`), `BCryptPasswordEncoder.matches()` throws → test catches this as 500 failure
