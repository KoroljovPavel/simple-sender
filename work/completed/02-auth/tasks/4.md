# Task 4: Login + brute-force + session management

## Required Skills

Before starting, load:
- `/skill:code-writing` — [SKILL.md](~/.claude/skills/code-writing/SKILL.md)

## Description

Implement the login endpoint with dual brute-force protection (per-email + per-IP), session fixation prevention, SecurityContext injection, rememberMe TTL, and event logging. Also create the `Event` domain and `EventService` used by all subsequent auth flows.

This is the most security-critical task in the feature. The `POST /api/auth/login` implementation must follow the exact sequence described in the tech-spec to avoid timing attacks, session fixation, and brute-force bypass.

Key complexity: Spring WebFlux does not auto-wire `UsernamePasswordAuthenticationFilter`. The login handler must manually: (1) check brute-force counters in Redis, (2) verify credentials with BCrypt, (3) invalidate the pre-auth session, (4) create a new session, (5) store `SecurityContext` in the new session via `WebSessionServerSecurityContextRepository`.

## What to do

1. **Create `Event` @Document** at `backend/src/main/java/com/botfunnel/events/Event.java`:
   - Fields: `String id`, `String userId` (nullable), `String eventType`, `String ipAddress`, `String userAgent` (nullable), `Map<String,Object> metadata` (nullable), `Instant createdAt`
   - `@Indexed` on `{userId: 1, createdAt: -1}`

2. **Create `EventRepository`** at `backend/src/main/java/com/botfunnel/events/EventRepository.java`: extends `ReactiveMongoRepository<Event, String>`.

3. **Create `EventService`** at `backend/src/main/java/com/botfunnel/events/EventService.java`:
   - `logEvent(String userId, String eventType, String ip, String userAgent, Map<String,Object> metadata)` → save event, fire-and-forget (errors logged only)

4. **Create auth DTOs**: `LoginRequest` (`String email`, `String password`, `boolean rememberMe`), `AuthResponse` (`String id`, `String email`, `String name`, `String status`, `String warning`), `MeResponse` (same fields).

5. **Create `TokenService`** (skeleton) at `backend/src/main/java/com/botfunnel/auth/TokenService.java`:
   - `generateRawToken()` → 32 random bytes from `SecureRandom`, base64url-encoded (no padding)
   - `hashToken(String rawToken)` → SHA-256 hex of rawToken
   - Full use in Task 5; only skeleton needed here for compilation

6. **Create `AuthService`** at `backend/src/main/java/com/botfunnel/auth/AuthService.java`:
   - Inject: `UserRepository`, `ReactiveRedisTemplate<String, String>`, `BCryptPasswordEncoder`, `WebSessionServerSecurityContextRepository`, `EventService`, `@Value` session TTLs
   - Declare `DUMMY_HASH` constant: a pre-computed bcrypt hash (cost 12) of a known throwaway password. Used when user not found to consume ~250ms and prevent timing-based email enumeration.
   - `login(LoginRequest request, ServerWebExchange exchange)` → implement the full login sequence per tech-spec:
     1. Check `brute:fail:{email}` key in Redis (GET); if count ≥ 5 → throw `AppException.tooManyRequests(...)`
     2. Check `brute:fail:ip:{ip}` key (GET); if count ≥ 20 → throw `AppException.tooManyRequests(...)`
     3. Find user by email. **If not found**: run `BCryptPasswordEncoder.matches(request.password, DUMMY_HASH)`, then throw `AppException.unauthorized(...)`
     4. BCrypt-verify password against stored hash. On mismatch: INCR both Redis keys, set EXPIRE 900 on first increment (use Lua or INCR then EXISTS to detect first), return 401
     5. Check user status: `blocked` → throw `AppException.forbidden(...)` with SUPPORT_EMAIL; `deleted` → throw `AppException.unauthorized(...)`; `pending` → allow, add warning to response
     6. Session fixation: `exchange.getSession().flatMap(WebSession::invalidate)` then re-fetch `exchange.getSession()` to get new session
     7. Create `UsernamePasswordAuthenticationToken` with user as principal, store in `SecurityContextImpl`, call `securityContextRepository.save(exchange, context)`
     8. Set `session.setMaxInactiveInterval(Duration.ofDays(30))` if `rememberMe`, else `Duration.ofHours(24)`
     9. DEL both Redis brute-force keys on success
     10. Log `login_success` event via `EventService`
     11. Return `AuthResponse`
   - `me(ServerWebExchange exchange)` → extract `SecurityContext` from session, return `MeResponse` for current user

7. **Create `AuthController`** (skeleton) at `backend/src/main/java/com/botfunnel/auth/AuthController.java`:
   - `POST /api/auth/login` → call `authService.login()`; set `SESSION` cookie in response if needed
   - `GET /api/auth/me` → call `authService.me()`
   - Other endpoints (register, verify, logout, forgot, reset) added in Tasks 5 and 6

8. **Extract IP from request**: check `X-Forwarded-For` header first (for reverse-proxy setups), fallback to `exchange.getRequest().getRemoteAddress().getAddress().getHostAddress()`.

**Dependencies:**
- Task 1 (Testcontainers deps), Task 2 (SecurityConfig, UserRepository, AppException, ErrorResponse)
- Note: Task 3 (EmailService) is NOT a dependency for event logging. Events are written to MongoDB via EventService, which is created within this task itself.

**Edge cases:**
- INCR + EXPIRE atomicity: Redis INCR increments (creating key if absent with value 1). Only set EXPIRE when the result of INCR is 1 (first failure). Otherwise TTL would reset on each failed attempt, allowing infinite failures within the window.
- `DUMMY_HASH` constant: pre-compute with `new BCryptPasswordEncoder(12).encode("dummy-password-that-nobody-uses-xK7f")` and store as a `private static final String`. Do NOT call `encode()` at runtime on every request.
- Session fixation: `exchange.getSession()` after `invalidate()` returns a new session with a new ID; this is automatic in Spring WebFlux session management.
- `WebSessionServerSecurityContextRepository.save()` stores the `SecurityContext` in the session's attributes under the key `SPRING_SECURITY_CONTEXT`.

**Security note — X-Forwarded-For trust:**
X-Forwarded-For header is read for per-IP brute-force tracking. In production, ensure the backend is behind a trusted reverse proxy (nginx/traefik) that sets this header. Without a proxy, clients can forge this header and bypass per-IP limits.

**Implementation hints:**
- `ReactiveRedisTemplate<String, String>` is the correct type for INCR/DEL operations on string keys
- For INCR: `redisTemplate.opsForValue().increment(key)` returns `Mono<Long>` with the new value
- For EXPIRE after first INCR: check if `result == 1` then set TTL; chain with `flatMap`
- Use `@MockitoBean` (not deprecated `@MockBean`) in unit tests
- Integration tests extend `AbstractIntegrationTest` (created in later task) — for now, create a minimal base class stub or write tests without it; refactor when `AbstractIntegrationTest` is available
- **Principal name contract**: When constructing `UsernamePasswordAuthenticationToken`, the principal is a `UserDetails` instance whose `getUsername()` must return the user's `id` (MongoDB ObjectId string), NOT the email. Spring Session stores this value in the `sessions` collection's `principal` field. Tasks 6 and 7 query sessions by this value, so using anything other than `id` will break those lookups.
