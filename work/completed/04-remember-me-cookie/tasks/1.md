# Task 1: Implement remember-me cookie persistence

## Required Skills

Перед виконанням задачі завантаж:
- `/skill:code-writing` — [skills/code-writing/SKILL.md](../../../.claude/skills/code-writing/SKILL.md)

## Description

Виправляємо баг: чекбокс «Запам'ятати мене» на `/auth/login` зараз не робить
сесію persistent. Сервер уже піднімає TTL `WebSession` до 30 днів у Mongo,
але cookie `SESSION`, що повертається у відповіді, не має `Max-Age` — це
session cookie, який видаляється при закритті браузера.

Корінь проблеми: Boot реєструє `CookieWebSessionIdResolver` як одиночний
бін з фіксованим `Max-Age` для всіх запитів. Поставити `Max-Age` per-request
через `addCookieInitializer` неможливо (ініціалізатор отримує лише builder,
не exchange), а мутувати поле `cookieMaxAge` в момент логіну небезпечно
під WebFlux concurrency.

Рішення (Decisions 1-7 у tech-spec):

1. Створюємо `RememberMeWebSessionIdResolver`, який наслідує
   `CookieWebSessionIdResolver` і override-ить тільки `setSessionId(...)`.
   У override-і будуємо `ResponseCookie` з нуля, читаючи cookie-флаги з
   `ServerProperties.getReactive().getSession().getCookie()` (single source
   of truth — `name`, `path`, `domain`, `httpOnly`, `secure`, `sameSite`,
   `partitioned`), а `Max-Age` визначаємо за per-request атрибутом
   exchange `REMEMBER_ME_ATTR`.
2. `AuthService.openSession` додатково публікує `Boolean rememberMe` у
   `exchange.getAttributes()` під ключем
   `RememberMeWebSessionIdResolver.REMEMBER_ME_ATTR`. Решта логіки
   (`setMaxIdleTime` на сесії, save SecurityContext) — без змін.
3. `SecurityConfig` реєструє `@Bean WebSessionIdResolver` нашого типу.
   Boot's `WebSessionIdResolverAutoConfiguration` має
   `@ConditionalOnMissingBean`, тож наш бін заміщає дефолт.
4. `expireSession` (logout, `Max-Age=0`) і `resolveSessionIds` (читання
   cookie з запиту) успадковуються від батька без змін.
5. Cookie `Max-Age` у режимі `rememberMe=true` — `Duration.ofDays(app.session.ttl-remember-me-days)`.
   Резолвер читає той самий ключ конфігу, що й `AuthService` для серверного
   TTL, — отже, sync між cookie і Mongo гарантований.
6. Якщо атрибут відсутній або `Boolean.FALSE` — пишемо session-only cookie
   (без `Max-Age`). Сюди потрапляють: register-auto-login, lazy-session,
   будь-які не-login flow.

Результат: `POST /api/auth/login` з `rememberMe=true` повертає `Set-Cookie`
з `Max-Age=2592000` і `Expires=<+30d>`; з `rememberMe=false` —
session-only cookie без `Max-Age` / `Expires`. Sliding expiration не
вмикаємо (Decision 5). Pre-fix cookies продовжують авторизувати юзера до
природного закінчення серверного TTL.

## Details

### Files

**`backend/src/main/java/com/botfunnel/security/RememberMeWebSessionIdResolver.java` (new)**
- `extends CookieWebSessionIdResolver`
- `public static final String REMEMBER_ME_ATTR = "com.botfunnel.auth.rememberMe"`
- Конструктор приймає `ServerProperties` і `long rememberMeDays`
- Override лише `setSessionId(ServerWebExchange, String)` — будує
  `ResponseCookie` з нуля. **Pattern reference:** дзеркали Boot's
  `WebSessionIdResolverAutoConfiguration#cookieWebSessionIdResolver` —
  скопіювати кожен `server.reactive.session.cookie.*` атрибут із
  `serverProperties.getReactive().getSession().getCookie()` у
  `ResponseCookie.from(...)` builder тим самим способом, що auto-config
  робить це для `CookieWebSessionIdResolver.addCookieInitializer(...)`.
  Якщо Boot 3.5.x мапить `partitioned` — змапити теж (Risk 4 у tech-spec).
  Єдина девіація від auto-config: branch на `REMEMBER_ME_ATTR` —
  `Boolean.TRUE` → виклик `.maxAge(Duration.ofDays(rememberMeDays))`;
  інакше → НЕ викликати `.maxAge(...)` взагалі. Фінальний крок —
  той самий, що у parent `setSessionId`: записати cookie у
  `exchange.getResponse().getCookies()`.
- **Gotchas:**
  - НЕ передавати `null` у `.maxAge(...)` — `ResponseCookieBuilder` робить
    `Assert.notNull(maxAge)` і кидає `IllegalArgumentException`. Гілка
    "session cookie" реалізується через відсутність виклику `.maxAge()`,
    а не через `null`-аргумент.
  - НЕ мутувати поля біна (зокрема не дзвонити `super.setCookieMaxAge(...)`
    у override) — резолвер є singleton, concurrent логіни перетруть один
    одному стан.
- НЕ override `resolveSessionIds`, `expireSession` — успадковуються

- Жодних нових package-ів. `org.springframework.boot.autoconfigure.web.ServerProperties`,
  `org.springframework.web.server.session.{CookieWebSessionIdResolver, WebSessionIdResolver}`,
  `org.springframework.http.ResponseCookie` — уже в classpath через
  `spring-boot-starter-webflux` + `spring-boot-autoconfigure`.
- Депенденс лише на існуючий конфіг: `app.session.ttl-remember-me-days`,
  `server.reactive.session.cookie.*` (вже в `application.properties`).

### Edge cases

- **Атрибут відсутній** (lazy-session, fallback flow) → session-only cookie.
  Не throw, не log warning. Decision 2.
- **Атрибут `Boolean.FALSE`** → session-only cookie. Те саме, що відсутній.
- **Re-login зі зміною прапорця** (FALSE → TRUE або навпаки) → новий
  cookie перезаписує старий. Resolver не тримає state між викликами
  (Scenario D).
- **Logout після `rememberMe=true` сесії** → `expireSession` пише
  `Max-Age=0`, незалежно від атрибута (інхерит, Scenario H).
- **Pre-fix backward compat** → старий cookie без `Max-Age` далі резолвиться
  парентським `resolveSessionIds`. Не торкаємось read-path.
- **Зміна `server.reactive.session.cookie.name=ALT` через env** → cookie
  пишеться під ім'ям `ALT`. Жодних правок коду (Scenario F, AC-8).
- **`server.reactive.session.cookie.secure=true`** через env → cookie має
  `Secure`. Знов — без правок коду (Scenario F).

### Implementation hints

- `ServerProperties.getReactive().getSession().getCookie()` повертає
  `org.springframework.boot.web.server.Cookie` (НЕ `jakarta.servlet.http.Cookie`).
  Має getter-и: `getName()`, `getDomain()`, `getPath()`, `getHttpOnly()`
  (Boolean wrapper), `getSecure()`, `getSameSite()` (enum
  `Cookie.SameSite` з методом `attributeValue()`), `getMaxAge()`
  (Duration — IGNORE цей у нас, ми ставимо власний). У Boot 3.5 може
  бути також `getPartitioned()` — перевірити і змапити.
- `ResponseCookie.ResponseCookieBuilder.maxAge(Duration)`:
  - **rememberMe = `Boolean.TRUE`** → виклик `.maxAge(Duration.ofDays(rememberMeDays))`.
  - **rememberMe = `Boolean.FALSE` або атрибут відсутній** → НЕ викликати
    `.maxAge(...)` взагалі. Builder за замовчуванням ставить
    `Duration.ofSeconds(-1)`, що рендериться як session-cookie (без
    `Max-Age` / `Expires` у заголовку).
  - **НЕ передавати `null`** у `.maxAge(null)` — `ResponseCookieBuilder`
    робить `Assert.notNull(maxAge)` і кидає `IllegalArgumentException`.
    Гілка "session cookie" реалізується саме через відсутність виклику
    `.maxAge()`, а не через `null`-аргумент.
- При мутуванні `exchange.getResponse().getCookies()` краще
  використовувати `set(name, cookie)` замість `add(name, cookie)`, щоб
  не дублювати `Set-Cookie` заголовки якщо щось інше вже додало (хоча
  parent `setSessionId` робить `set`).
- `MockServerWebExchange.from(MockServerHttpRequest)` — стандартний
  fixture для unit-тестів резолвера. Response — це
  `MockServerHttpResponse`, у якого `getCookies()` повертає реальну
  multi-value мапу, з якої можна читати `getFirst(name)` і робити
  assertion на `ResponseCookie`.
- Для тесту на `AuthService.register` — НЕ треба піднімати весь flow
  Mongo + Redis. Mock-и достатньо. Реальний save — у вже існуючих IT-ах.
- Якщо в Boot 3.5.x Cookie не має `partitioned`, нічого додавати не
  треба. Tech-spec Risk 4 фіксує: при наступному bump Boot — code review
  довкола auto-config змін має це підхопити.
