## Description

Полный код-аудит фичи `04-remember-me-cookie` после Wave 1. Это Audit Wave — новый код не пишется. Аудитор читает все исходные файлы, созданные/модифицированные в Task 1 (`RememberMeWebSessionIdResolver`, `SecurityConfig`, `AuthService`), и оценивает их холистически — не как изолированные диффы, а как единое решение, которое должно следовать архитектурным решениям из tech-spec и существующим паттернам проекта.

Фокус аудита — кросс-компонентные качества, которые нельзя оценить по одному файлу:
- Race-freedom при per-request обработке (Decision 1): cookie строится с нуля в override, ни одно поле bean'а не мутируется в `setSessionId`. Под WebFlux concurrency несколько запросов одновременно вызывают `setSessionId` на одном и том же resolver-singleton — никаких разделяемых mutable полей.
- Никакого дубликата cookie-атрибутов (Decision 3): значения `name`, `httpOnly`, `secure`, `sameSite`, `path`, `domain` читаются исключительно из `serverProperties.getReactive().getSession().getCookie()`. В коде фикса не должно быть hard-coded `"SESSION"`, `true/false` для httpOnly/secure, литералов `SameSite.LAX` и т.п.
- Корректные Spring WebFlux паттерны: `ServerWebExchange.getAttributes()` использован идиоматично; нет блокирующих вызовов; нет `ThreadLocal`; constant `REMEMBER_ME_ATTR` является `public static final` в resolver-классе и импортируется из `AuthService` (Decision 2 — производитель импортирует контракт потребителя, без третьего файла).
- Naming consistency: новый класс лежит в пакете `com.botfunnel.security`, имя `RememberMeWebSessionIdResolver` следует существующим конвенциям (см. соседние классы в `auth/` и `security/`); modifiers/visibility согласованы с проектным стилем.
- Wiring корректность: `@Bean WebSessionIdResolver` в `SecurityConfig` действительно заменяет дефолтный bean от `WebSessionIdResolverAutoConfiguration` (`@ConditionalOnMissingBean`); `ServerProperties` инжектится правильно; конструктор resolver'а принимает зависимости явно.
- AuthService изменения минимальны и не ломают другие auth-flow: `register(...)` по-прежнему вызывает `openSession(saved, false, exchange)` (Decision 6); запись атрибута выполнена после установки `WebSession.maxIdleTime` и до flush'а сессии фреймворком; нет invalid'ации `WebSession.invalidate()` (комментарий на `AuthService.java:598-602` сохранён).
- Ordering атрибута относительно реактивной цепочки (Decision 2 — атрибут как per-request канал между handler'ом и framework callback'ом): `AuthService.openSession` пишет `exchange.getAttributes().put(REMEMBER_ME_ATTR, ...)` ДО того, как подписывается реактивная цепочка, сохраняющая `SecurityContext`. Атрибут должен быть видим в `WebSessionIdResolver.setSessionId` callback'е в момент session-flush'а. Аудитор обязан подтвердить, что put не спрятан внутри `flatMap`/`doOnSuccess`, который срабатывает уже после записи cookie (race с самим собой по сути ломает решение, даже если код "компилируется").

Результат — отчёт аудита по `code-reviewing` методологии (11 measurement dimensions). В Audit Wave аудитор сам ЯВЛЯЕТСЯ ревьюером — никаких дополнительных reviewers нет.

## Details

**Files to audit (deliverables of Task 1, current state on disk):**
- `backend/src/main/java/com/botfunnel/security/RememberMeWebSessionIdResolver.java` — new resolver subclassing `CookieWebSessionIdResolver`. Must override only `setSessionId(ServerWebExchange, String)`. Must read `Boolean rememberMe` from exchange attribute `REMEMBER_ME_ATTR = "com.botfunnel.auth.rememberMe"`. Must build `ResponseCookie` from scratch using `serverProperties.getReactive().getSession().getCookie()` for all non-Max-Age attributes. Must NOT mutate any bean field in the override.
- `backend/src/main/java/com/botfunnel/security/SecurityConfig.java` — must register `@Bean WebSessionIdResolver` returning a `RememberMeWebSessionIdResolver` instance. `ServerProperties` must be injected (constructor or method param) and passed to the resolver. Bean must NOT be conditionally created — replaces Boot's auto-config unconditionally.
- `backend/src/main/java/com/botfunnel/auth/AuthService.java` — `openSession` (around line 590-606 pre-fix) must additionally write `Boolean rememberMe` to `exchange.getAttributes()` under `RememberMeWebSessionIdResolver.REMEMBER_ME_ATTR`. Existing `WebSession.maxIdleTime` set still required. Method signature unchanged. `register(...)` (around line 167) call to `openSession(saved, false, exchange)` MUST be unchanged.

**Cross-component invariants to verify:**
- Constant `REMEMBER_ME_ATTR` defined in resolver class (single owner), imported by `AuthService`. Not duplicated.
- TTL config keys `app.session.ttl-default-hours` and `app.session.ttl-remember-me-days` are read both by `AuthService` (for `WebSession.maxIdleTime`) and by resolver (for cookie `Max-Age`) — same source, no drift (Decision 4).
- No new `app.session.cookie-max-age-*` property introduced in `application.properties`.

**Dependencies:** Task 1 must be `done` before this task runs (depends_on: [1]). Auditor reads on-disk code, so Task 1 changes must be committed/staged in the working tree.

**Edge cases the auditor must consider in the code under review:**
- Concurrent requests: two simultaneous `setSessionId` calls on the same resolver instance — race-free?
- Missing exchange attribute (lazy session, WebSocket upgrade, anonymous flows): does resolver fall back to session-only cookie without throwing?
- `Boolean.FALSE` vs absent attribute: both must produce session-only cookie (Decision 2 fallback).
- Re-login flip (`true` → `false` or vice versa): each call independently produces correct cookie.

**Implementation hints (for the auditor — what to look for, NOT what to write):**
- Look at the resolver constructor: should accept dependencies (likely `ServerProperties` plus `@Value` for TTL days). Should NOT rely on field injection if the rest of the codebase uses constructor injection.
- Look for any `String SESSION_COOKIE_NAME = "SESSION"` constant in the new code — that's a smell of duplicated config (Decision 3 violation).
- Look for `synchronized`, `volatile`, `AtomicReference` in resolver — if present, the implementation may be working around the race instead of avoiding it. Decision 1 mandates "build cookie from scratch", which should make these unnecessary.
- Look for any `@Value("${app.session.ttl-remember-me-days}")` in the resolver — that's correct (Decision 4). Compare with `AuthService` to confirm same key name.
