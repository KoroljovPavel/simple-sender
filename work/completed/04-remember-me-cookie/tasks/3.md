# Task 3: Security Audit

Перед выполнением задачи загрузи:

## Description

Full-feature security audit for the remember-me-cookie fix delivered in Task 1.
This is an Audit-Wave task: nothing new is implemented, no production code is
written. The auditor reads every source file produced or modified in this
feature and confirms that no security regression was introduced.

The fix touches the most security-sensitive surface of the app: the `SESSION`
cookie itself, the resolver that writes it, and the auth service that drives
the cookie's `Max-Age`. A flaw here downgrades the entire session-auth model
(downgraded `Secure`/`SameSite`, leaked session id, auth bypass via missing
attribute). The audit's job is to prove none of those failure modes are
present.

The audit explicitly considers two OWASP Top-10 categories:

- **A02 — Cryptographic Failures.** Cookie protections (`Secure`, `HttpOnly`,
  `SameSite`) and how they are sourced.
- **A07 — Identification & Authentication Failures.** Session-cookie
  lifetime, fallback behavior when the per-request `rememberMe` attribute is
  absent, session-id leakage, regression of the existing CSRF/XSRF flow.

The auditor produces a single audit report at the path defined below. There
are no follow-up reviewers — the auditor IS the review for this task.

## What to do

1. Re-read the user-spec and tech-spec for this feature so the audit maps
   findings to the documented decisions and risks (Decision 3, Risk 1, Risk 2,
   Risk 3, AC-1, AC-2, AC-4, AC-6).
2. Read every source file produced or modified by Task 1 and the configuration
   that drives cookie attributes — full list under "Context Files" → "Code
   files".
3. Run the audit pass over the resolver, the security config, and the auth
   service against the checklist below. For each item produce a verdict
   (`pass` / `fail` / `n/a`) plus evidence (file path + line range or a
   one-line quote).
4. Audit checklist (must be addressed in the report):
   - **No hard-coded cookie security flags.** `name`, `httpOnly`, `secure`,
     `sameSite`, `path`, `domain` MUST be read from
     `serverProperties.getReactive().getSession().getCookie()` inside
     `RememberMeWebSessionIdResolver`. No constants, no string literals for
     these attributes. Confirms tech-spec Decision 3 and user-spec AC-1.
   - **Configurable cookie attributes still flow through.** Changing
     `SESSION_COOKIE_SECURE`, `SESSION_COOKIE_SAME_SITE`, or
     `server.reactive.session.cookie.name` via env still changes the
     resulting `Set-Cookie` header without code changes (Risk 1, AC-8). Verify
     by code-reading the resolver and `application.properties`.
   - **No session-id leakage in logs.** The resolver MUST NOT log the session
     id, cookie value, or any `SecurityContext` content. `AuthService.openSession`
     MUST NOT log the session id either. Grep the audited files for
     `log.`, `System.out`, `System.err` and confirm.
   - **No regression in CSRF/XSRF flow.** `SecurityConfig` continues to
     register `CookieServerCsrfTokenRepository.withHttpOnlyFalse()` plus the
     `ServerCsrfTokenRequestAttributeHandler`. The new
     `WebSessionIdResolver` bean does not interfere with the CSRF cookie
     materialization filter. Confirm CSRF rules remain configured for
     non-safe methods on session-cookie-authenticated endpoints.
   - **No auth bypass via missing attribute.** When the
     `REMEMBER_ME_ATTR` exchange attribute is absent (lazy session, WebSocket
     upgrade, any non-login flow that triggers `setSessionId`), the resolver
     MUST emit a session-only cookie (no `Max-Age`) — NOT skip writing the
     cookie, NOT throw, NOT default to authenticated-30-days. Verify the
     fallback in code and confirm the unit test covers the `attribute-absent`
     branch.
   - **Per-request concurrency safety.** No bean-level mutable state is
     touched in `setSessionId`. The resolver builds the `ResponseCookie`
     from scratch per call; no field write reachable from a request
     handler. Confirms Decision 1 (Risk: per-request mutation under WebFlux
     concurrency).
   - **TTL synchronization.** Cookie `Max-Age` and `WebSession.maxIdleTime`
     are derived from the same `app.session.ttl-*` keys. No drift surface
     was introduced (Decision 4, AC-3).
   - **Logout still clears the cookie.** `expireSession` is inherited from
     `CookieWebSessionIdResolver` unchanged; logout emits `Max-Age=0`
     regardless of the per-request flag (AC-5).
   - **OWASP A02 — Cryptographic Failures.** Cookie `Secure`, `HttpOnly`,
     `SameSite` come from runtime config; in production these resolve to
     `Secure=true`, `HttpOnly=true`, `SameSite=Lax|Strict`. The fix code
     does not weaken any of these. The cookie value (session id) is opaque
     (managed by `spring-session-data-mongodb`); the resolver does not
     mutate it.
   - **OWASP A07 — Identification & Auth Failures.** Per-request
     `rememberMe` cannot be forged from outside the request — the attribute
     is set server-side in `AuthService.openSession` and cleared with the
     exchange. A client cannot inject the attribute through a header,
     query string, or cookie. Logout/terminate-all flows are unchanged
     (Decision 5).
   - **Pre-fix backward compatibility.** `resolveSessionIds` is inherited
     unchanged → pre-fix session cookies (no `Max-Age`) continue to be read
     and to authorize the user (AC-4).
   - **Register-flow regression.** `AuthService.register` calls
     `openSession(saved, false, exchange)` (line ~167); after the fix this
     path produces a session-only cookie. Confirm the boolean is `false`
     and not silently flipped (AC-6, Decision 6).
5. Write the audit report to the path under "Verification Steps → Automated".
   Use the report template required by the `security-auditor` skill: per-item
   verdicts, evidence (file:line), risk severity, an executive verdict
   (`approve` / `approve-with-findings` / `block`), and an explicit
   sign-off on OWASP A02 and A07.
6. Stop. No code changes, no follow-up reviewers, no commits.

## Details

**Files (audit targets, with current state and what to verify):**

- `backend/src/main/java/com/botfunnel/security/RememberMeWebSessionIdResolver.java`
  (new in Task 1) — subclasses `CookieWebSessionIdResolver`, overrides
  `setSessionId(ServerWebExchange, String)`. Audit must verify:
  - cookie attributes `name`, `httpOnly`, `secure`, `sameSite`, `path`,
    `domain` are read from
    `serverProperties.getReactive().getSession().getCookie()`, not from
    string literals or local constants;
  - the fallback when the `REMEMBER_ME_ATTR` exchange attribute is absent
    or `Boolean.FALSE` is a session-only cookie (no `Max-Age`), not a
    skipped write or an exception;
  - no `log.*`, `System.out`, `System.err` calls reference the session id
    or cookie value;
  - no bean-level field is mutated inside `setSessionId`; the
    `ResponseCookie` is built from scratch each call.

- `backend/src/main/java/com/botfunnel/security/SecurityConfig.java`
  (modified by Task 1) — current state already configures CSRF via
  `CookieServerCsrfTokenRepository.withHttpOnlyFalse()` +
  `ServerCsrfTokenRequestAttributeHandler` (lines 44–53), CORS
  (`Access-Control-Allow-Credentials: true`, allowed origin from `app.url`),
  authorization rules (`/health` and `/api/auth/**` permitAll, `/api/**`
  authenticated, catch-all authenticated), and a CSRF cookie-materialization
  WebFilter (lines 69–79). Audit must verify the new `@Bean
  WebSessionIdResolver` does not displace, reorder, or weaken any of those.

- `backend/src/main/java/com/botfunnel/auth/AuthService.java`
  (modified by Task 1) — `openSession` is at lines 590–606. Today it sets
  `WebSession.maxIdleTime` and saves `SecurityContext` only. After Task 1
  it must additionally write the `rememberMe` boolean into
  `exchange.getAttributes()` under `REMEMBER_ME_ATTR`. Audit must verify
  the write happens BEFORE `securityContextRepository.save(...)` flushes
  the session, otherwise the resolver runs with the attribute absent.
  The register-auto-login call site (around line 167) must remain
  `openSession(saved, false, exchange)` — boolean must be `false`.

- `backend/src/main/resources/application.properties` — current state
  declares `server.reactive.session.cookie.http-only=true`,
  `server.reactive.session.cookie.secure=${SESSION_COOKIE_SECURE:false}`,
  `server.reactive.session.cookie.same-site=${SESSION_COOKIE_SAME_SITE:lax}`,
  `app.session.ttl-default-hours=${SESSION_TTL_DEFAULT_HOURS:24}`,
  `app.session.ttl-remember-me-days=${SESSION_TTL_REMEMBER_ME_DAYS:30}`.
  Audit must confirm the resolver code path actually reads these and
  that no Java constant duplicates any of these values.

**Dependencies:** Task 1 (must be `done` before this task starts).

**Edge cases the audit MUST cover:**
- Attribute absent (non-login flow that triggers `setSessionId`) → expect
  session-only cookie, NOT a thrown exception, NOT a skipped cookie write,
  NOT `Max-Age=30d` by default.
- Attribute set to `Boolean.FALSE` → behaves identically to "absent".
- Concurrent logins for two different users on the same instance → no
  cross-request bleed via shared bean state.
- Logout flow → `expireSession` inherited; cookie cleared with `Max-Age=0`
  regardless of attribute state.
- Pre-fix cookie (no `Max-Age`) hitting a post-fix backend → still resolved
  via inherited `resolveSessionIds`; user remains authenticated.
- Future Spring Boot upgrade introducing a new `Cookie` field (e.g.
  `partitioned`) — note explicitly that the manual mapping does not forward
  it; this is a documented `[TECHNICAL]` note in tech-spec, not a block.

**Implementation hints (for the auditor):**
- Use `grep`-style searches across the audited files for `httpOnly`,
  `secure`, `sameSite`, `Max-Age`, `SESSION` — any literal match in Java
  code (outside imports) is a candidate finding.
- Use `grep` for `log.`, `System.out`, `System.err` in
  `RememberMeWebSessionIdResolver.java` and the modified region of
  `AuthService.java` to confirm no session-id logging.
- Cross-reference each cookie attribute against
  `serverProperties.getReactive().getSession().getCookie()` accessor
  chain to confirm single-source-of-truth.
- The audit is read-only: the auditor does NOT run the backend, does NOT
  run tests. Static analysis only.
