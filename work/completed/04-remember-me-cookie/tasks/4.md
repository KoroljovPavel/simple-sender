## Description

Полный аудит качества тестов фичи `04-remember-me-cookie`. Это задача ревью, не написания кода. Auditor — последняя линия защиты test-strategy перед Final Wave (Pre-deploy QA).

Tech-spec явно решил (Decision 7) обмежити тестове покриття resolver unit-тестом (`RememberMeWebSessionIdResolverTest`) плюс розширення `AuthServiceTest`/`AuthServiceRegistrationTest` — без нового `@SpringBootTest` IT, який би перевіряв `Set-Cookie` напряму. Це усвідомлене обмеження через `bindToApplicationContext` у `AbstractIntegrationTest`. Аудит **не повинен** позначати відсутність такого IT як gap — тільки перевірити, що unit-рівень дійсно покриває всі гілки рішення.

**Важлива структурна нота про AuthService-side тести:** проєкт має ДВА test-файли для `AuthService` — `AuthServiceTest` (login flow) і `AuthServiceRegistrationTest` (register flow). Розширення login-кейсів очікується у `AuthServiceTest`, а register-auto-login регресія може бути додана у будь-якому з двох (логічніше у `AuthServiceRegistrationTest`, бо там вже стоять всі register-моки). Аудитор **не повинен** маркувати register-кейс як missing, якщо він знайдений у `AuthServiceRegistrationTest` замість `AuthServiceTest`.

Що треба переконатись:
1. `RememberMeWebSessionIdResolverTest` покриває всі три гілки атрибута: `Boolean.TRUE`, `Boolean.FALSE`, відсутність атрибута (Scenarios A/B/C). Жодна гілка не пропущена і не дубльована.
2. Параметризований кейс на cookie security flags (Scenario F) дійсно змінює асерт — кожна ітерація таблиці перевіряє інший атрибут (`name`/`http-only`/`secure`/`same-site`/`path`/`domain`), а не "усі дефолти однакові у кожному рядку" (vacuous pass).
3. Re-login flip (Scenario D) дійсно демонструє відсутність per-request state у resolver (два послідовні виклики на свіжих exchange, незалежні асерти).
4. Параметризація TTL (Scenario E) — TTL читається з конфігу, а не з константи; кейси `{30, 7, 60}` дають різні `Max-Age`.
5. Inherited-behavior smokes (Scenarios G — `resolveSessionIds` з cookie без `Max-Age`; H — `expireSession` пише `Max-Age=0` незалежно від `rememberMe`).
6. У `AuthServiceTest` (login flow) додано/розширено два кейси: login + `rememberMe=true`, login + `rememberMe=false`. Обидва **верифікують запис у `exchange.getAttributes()`** (ключ `REMEMBER_ME_ATTR`, значення `Boolean.TRUE`/`Boolean.FALSE`).
7. Register-auto-login регресія: новий кейс у `AuthServiceTest` АБО у `AuthServiceRegistrationTest`, який викликає `register(...)` і верифікує запис `(REMEMBER_ME_ATTR, Boolean.FALSE)` у `exchange.getAttributes()`. Локує AC-6 проти регресії на `Boolean.TRUE`. **Не позначати як missing, якщо знайдено у `AuthServiceRegistrationTest`.**
8. **Mock extension в `AuthServiceTest`:** хелпер `mockExchangeWithSessions` зараз стабує тільки `exchange.getRequest()` і `exchange.getSession()`. Після Task 1 у `AuthService.openSession` додається запис в `exchange.getAttributes()` — це означає, що мок повинен бути розширений: або `when(exchange.getAttributes()).thenReturn(...)` з реальним `Map`/`mock(Map.class)`, або через `Mockito.RETURNS_DEEP_STUBS`. Перевірити, що цей мок дійсно правильно розширений і `verify(...).put(REMEMBER_ME_ATTR, ...)` працює проти живого spy/мок-Map, а не falls through на silent NPE.
9. Жоден доданий тест не дублює існуюче IT-покриття (`AuthControllerIT`, `ProfileControllerIT` — session lifecycle через Mongo `sessions`).
10. Загальна якість: тести детермінантні, без `Thread.sleep`/таймаутів, не залежать від реального HTTP-стенда; назви методів читаються як специфікація поведінки.

Підсумок аудиту — markdown-репорт із severity-rated findings (`blocker` / `major` / `minor` / `nit`) і явним вердиктом `pass` / `fail`. Якщо знайдено `blocker` — фіча не може йти у Final Wave без виправлення.

Register-auto-login регресія може бути додана сюди (логічніше — тут вже стоять усі register-моки, `securityContextRepository.save` лояльно стабований у `setUp()` ≈line 88). Очікуваний кейс:

**Edge cases в аудиті:**
- Якщо у `RememberMeWebSessionIdResolverTest` Scenario F (cookie security flags pass-through) написаний як один `@Test` з усіма прапорами одразу замість `@ParameterizedTest` з таблицею — це finding `major` (vacuous risk: непомітно, який саме прапор tested).
- Якщо TTL у Scenario A асертиться константою `2592000L` замість `Duration.ofDays(30).toSeconds()` чи `app.session.ttl-remember-me-days * 86400` — finding `minor` (drift risk: зміна конфігу ламатиме тест замість його провалити).
- Якщо Scenario C (відсутність атрибута) перевіряє тільки `Max-Age == null` без перевірки що cookie з value `sessionId` все одно записаний — finding `minor` (incomplete assertion).
- Якщо register-кейс (у `AuthServiceTest` АБО `AuthServiceRegistrationTest`) асертить тільки виклик `openSession`, але не перевіряє запис в `exchange.getAttributes()` — finding `blocker` (AC-6 не локований). **Перш ніж писати "missing register case" — перевірити обидва файли.**
- Якщо `mockExchangeWithSessions` хелпер у `AuthServiceTest` не розширений для `getAttributes()` після Task 1 — finding `major` (silent false-confidence: `verify(attrs).put(...)` no-op'ить через NPE/silent stub miss, тест "зеленіє" без реальної перевірки контракту).

**Implementation hints:**
- Аудит — це не "запустити lint". Це уважне читання обох тест-файлів і звірка з Description list 1-8.
- Test-master skill `references/test-quality-review.md` має чек-лист — пройти по ньому методично.
- Vacuous-pass detection: для кожної параметризованої таблиці питати "якби я видалив рядок X — який інший рядок впав би?". Якщо жоден — це vacuous.
- Не пропонувати додавати IT на `Set-Cookie` — Decision 7 явно це відхиляє з технічних причин (`bindToApplicationContext`). Замість цього перевіряти, що unit-рівень чесно покриває всі гілки.
- Якщо знайдено `blocker` — задача завершується вердиктом `fail`, репорт зберігається, у `decisions.md` записується `Test Audit: fail — blocker(s) found, see report`. Виправлення робиться окремою таскою або ре-роботою Task 1, не цим аудитом.
- Severity rubric:
  - `blocker` — gap у coverage critical AC (AC-1/2/6/7) або тест дає false confidence (vacuous pass).
  - `major` — слабкий тест, який не зловить регресію в обозримому майбутньому.
  - `minor` — стиль тесту, який утруднює maintenance (magic numbers, неговорящі імена).
  - `nit` — косметика (форматування, порядок асертів).
