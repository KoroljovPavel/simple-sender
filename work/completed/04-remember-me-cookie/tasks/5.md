## Description

Final-Wave acceptance testing для фічі `04-remember-me-cookie`. Запускаємо повний backend test suite, після чого вручну прогоняємо кожен AC-1..AC-8 з user-spec на локально піднятому стеку (Docker Compose з `infra/` + `./gradlew :backend:bootRun` на `:8080`). Цей таск не пише код — лише валідує те, що зробив Wave 1 (Task 1) і пропустили audit-таски (Tasks 2/3/4). Включає manual browser smoke (DevTools → Cookies, перезапуск браузера) із розділу user-spec "Пользователь проверяет" — без нього таск не закривається. Звіт пишеться у `decisions.md` з посиланням на pre-deploy-qa лог; виявлені проблеми блокують merge і повертають фічу в Task 1.

## What to do

1. Підняти локальний стек: `docker compose up -d` з `infra/`, потім `./gradlew :backend:bootRun` (бекенд на `:8080`). Підготувати тестового юзера — або через `POST /api/auth/register`, або seed-скрипт; зафіксувати email/пароль для подальших curl-запитів.
2. Запустити повний backend test suite: `./gradlew :backend:test`. Вимога — усі тести зелені, включаючи новий `RememberMeWebSessionIdResolverTest` і розширені кейси в `AuthServiceTest` (з Task 1). Якщо хоч один тест падає — таск стопає, фікс іде на доопрацювання.
3. Прогнати AC-1..AC-8 з user-spec проти живого `:8080` — конкретні команди й очікування зведено в розділі "Verification Steps → Smoke" нижче. Кожен AC підтверджується або смоук-командою, або existing-test-проходом, або обома.
4. Зробити manual browser smoke з user-spec "Пользователь проверяет": локально запустити Nuxt dev-сервер, залогінитися з галочкою "Запам'ятати мене", перевірити в DevTools → Application → Cookies, що cookie `SESSION` має `Expires` ~+30 днів. Закрити браузер, відкрити знову — потрапити на `/dashboard` без релогіну. Повторити сценарій без галочки (cookie має `Expires=Session`, після закриття браузера — редірект на `/auth/login`). Перевірити logout — cookie `SESSION` зникає зі списку.
5. Якщо будь-який AC не пройшов — задокументувати в `decisions.md` секції цього таска і повернути фічу на додатковий цикл (новий do-task для Task 1). Якщо всі 8 AC + manual browser smoke зелені — записати summary в `decisions.md`, зазначити версію коду (commit hash) і дату прогону.

## Verification Steps

### Automated

- `./gradlew :backend:test` → все зелено (повний backend suite, включаючи нові/extended тести з Task 1).
- `./gradlew :backend:build` → збірка проходить, `Started ... in N s` у логах bootRun.

### Smoke

Локальний стек: `docker compose up -d` (з `infra/`) + `./gradlew :backend:bootRun`. Бекенд на `http://localhost:8080`. Заздалегідь створений тестовий юзер (через `POST /api/auth/register` або seed).

**AC-1 — login з rememberMe=true:**
```bash
curl -i -s -X POST http://localhost:8080/api/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"email":"test@example.com","password":"...","rememberMe":true}' \
  | grep -i '^set-cookie:'
# Очікувано: Set-Cookie: SESSION=...; Path=/; Max-Age=2592000; Expires=...; HttpOnly; SameSite=Lax
```

**AC-2 — login з rememberMe=false:**
```bash
curl -i -s -X POST http://localhost:8080/api/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"email":"test@example.com","password":"...","rememberMe":false}' \
  | grep -i '^set-cookie:'
# Очікувано: Set-Cookie: SESSION=...; Path=/; HttpOnly; SameSite=Lax  (без Max-Age, без Expires)
```

**AC-3 — синхронність server TTL і cookie:** покривається existing-тестом (`AuthServiceTest` перевіряє `WebSession.maxIdleTime`) + новим `RememberMeWebSessionIdResolverTest` Scenario E (parameterized over `app.session.ttl-remember-me-days`). Окремих smoke-команд не потрібно — підтверджується проходом `./gradlew :backend:test`.

**AC-4 — pre-fix backward compat:** валідну сесію симулюємо через AC-2 крок (логін без rememberMe → cookie без Max-Age), потім використовуємо цей cookie у запиті до захищеного ресурсу:
```bash
# 1) Залогінитися хоч раз і запам'ятати SESSION-кукі (з кроку AC-2 вище).
# 2) Відправити /api/auth/me з тим cookie, без атрибутів Max-Age/Expires (клієнт надсилає лише name=value):
curl -i -s http://localhost:8080/api/auth/me \
  -H 'Cookie: SESSION=<value-з-кроку-AC-2>'
# Очікувано: 200 OK, тіло — об'єкт юзера. Сесія не інвалідується деплоєм.
```
Примітка: ендпоінт мапиться через `AuthController @RequestMapping("/api/auth")` + `@GetMapping("/me")` → повний шлях `/api/auth/me`. Шляху `/api/me` у проекті не існує.

**AC-5 — logout очищує cookie:** logout — це state-changing POST, а CSRF включений у `SecurityConfig` через `CookieServerCsrfTokenRepository.withHttpOnlyFalse()` + `ServerCsrfTokenRequestAttributeHandler` (raw token, без BREACH-маскування). Cookie `XSRF-TOKEN` матеріалізується кожним запитом через `csrfCookieMaterializer` фільтр. Без `X-XSRF-TOKEN` хедера POST поверне 403, тож рецепт двокроковий: спершу GET (будь-який, наприклад той самий `/api/auth/me`) із `-c cookies.txt` мінтить `XSRF-TOKEN`, потім POST `/logout` з тим же cookie jar (`-b cookies.txt`) і `X-XSRF-TOKEN` хедером:
```bash
# 1) Mint XSRF-TOKEN cookie (зберегти SESSION + XSRF разом):
curl -i -s -c cookies.txt -b cookies.txt http://localhost:8080/api/auth/me > /dev/null
XSRF=$(awk '$6=="XSRF-TOKEN" {print $7}' cookies.txt)

# 2) POST /logout із cookie jar + X-XSRF-TOKEN:
curl -i -s -X POST http://localhost:8080/api/auth/logout \
  -b cookies.txt \
  -H "X-XSRF-TOKEN: $XSRF" \
  | grep -i '^set-cookie:'
# Очікувано: Set-Cookie: SESSION=; ... Max-Age=0; ...
# (Заразом може бути Set-Cookie: XSRF-TOKEN=...; це нормально, нас цікавить SESSION з Max-Age=0.)
```
Якщо у локальному стеку CSRF свідомо вимкнено (нестандартна конфігурація — за замовчуванням він УВІМКНЕНО), достатньо одношагового `curl -i -s -X POST http://localhost:8080/api/auth/logout -H 'Cookie: SESSION=<active-session-cookie>'`.

**AC-6 — register auto-login без галочки:**
```bash
curl -i -s -X POST http://localhost:8080/api/auth/register \
  -H 'Content-Type: application/json' \
  -d '{"email":"qa-fresh@example.com","password":"StrongP@ssw0rd!"}' \
  | grep -i '^set-cookie:'
# Очікувано: Set-Cookie: SESSION=...; Path=/; HttpOnly; SameSite=Lax  (без Max-Age)
```

**AC-7 — re-login зі зміною прапорця:** виконати AC-2 (false), потім AC-1 (true) тим же email. Підтвердити, що друге `Set-Cookie` має `Max-Age=2592000`. Cookie перезаписується без додаткових дій.

**AC-8 — зміна cookie name через env var:** зупинити бекенд, виставити змінну середовища і перезапустити:
```bash
SERVER_REACTIVE_SESSION_COOKIE_NAME=ALT ./gradlew :backend:bootRun
# Потім повторити AC-1 smoke. Очікувано: Set-Cookie: ALT=...; ... Max-Age=2592000; ...
# Код фіксу при цьому не змінювався — підтверджує, що cookie name читається з конфігу.
```
Після перевірки повернути конфіг до дефолту (`SESSION`).

### User

Локально, перед merge — manual browser smoke з user-spec "Пользователь проверяет":

1. Запустити стек: `docker compose up -d` (з `infra/`) + `./gradlew :backend:bootRun` + `pnpm dev` у `frontend/`.
2. Відкрити `http://localhost:3000/auth/login` у звичайному (не incognito) браузері. Поставити галочку "Запам'ятати мене", залогінитися. У DevTools → Application → Cookies → `localhost` має бути cookie `SESSION` з `Expires` ~+30 днів. Закрити браузер повністю, відкрити знову, перейти на `http://localhost:3000/dashboard` — потрапляє на дашборд без релогіну.
3. Зробити logout, повторити крок 2 без галочки. Cookie `SESSION` має `Expires=Session`. Закрити браузер, відкрити знову → редірект на `/auth/login`.
4. Знову залогінитися, натиснути "Logout". У DevTools cookie `SESSION` зникає зі списку Cookies для `localhost`.
5. Запитати в користувача підтвердження: "Усі три браузерні сценарії (persist з галочкою, session-only без галочки, logout очищує cookie) пройшли коректно?". Без явного OK таск не закривається.

- `backend/src/main/java/com/botfunnel/auth/AuthService.java` — переконатися, що `openSession` пише `rememberMe` в `exchange.getAttributes()` під ключем `RememberMeWebSessionIdResolver.REMEMBER_ME_ATTR`. Сигнатура методу не змінилася.

- `backend/src/test/java/com/botfunnel/auth/AuthServiceTest.java` — extended кейси: login з rememberMe=true → put(REMEMBER_ME_ATTR, TRUE), login з false → FALSE, register → FALSE.

**Dependencies:**
- Залежить від Tasks 2, 3, 4 (всі три аудити мають бути зеленими — без невирішених findings).
- Не пишемо нового коду — лише виконуємо checks.

**Edge cases для перевірки під час QA:**
- Incognito-режим браузера: per user-spec "Ограничения" — браузер ігнорує `Max-Age` у privacy mode. Це known limitation, не баг. Не блокуємо.
- Concurrent login на тому ж юзері з різних вкладок: cookie має перезаписатись з останнім значенням `rememberMe` (AC-7 покриває).
- Pre-fix cookie з закінченим серверним TTL: має повернути 401, юзер релогіниться → отримує новий cookie з правильним `Max-Age`. Це не AC-4 violation, це нормальний flow.
- `Secure`-прапор у локальному dev: дефолтно `false`, бо HTTP. У проді через env var → `true` + HTTPS. Локально перевіряємо лише наявність/відсутність `Max-Age`/`Expires`, не `Secure`.

**Implementation hints:**
- Для AC-4 seed-сесії: можна не патчити Mongo напряму — достатньо зробити логін (AC-2 крок), забрати cookie, потім використати його у запиті на `/api/auth/me`. WebFlux парсер cookies не вимагає `Max-Age` у HTTP-запиті — клієнт надсилає лише `name=value`. Це симулює pre-fix scenario.
- Для AC-8: `application.properties` ключ — `server.reactive.session.cookie.name`. Spring Boot маппить його з env var як `SERVER_REACTIVE_SESSION_COOKIE_NAME`. Інші cookie attrs (secure, samesite) аналогічно через `SERVER_REACTIVE_SESSION_COOKIE_SECURE`, `SERVER_REACTIVE_SESSION_COOKIE_SAMESITE`.
- Якщо `./gradlew :backend:test` падає лише в IT через відсутній Mongo/Redis у тесті — перевірити, що `docker compose up -d` підняв `mongo` і `redis` контейнери та порти 27017/6379 не зайняті іншим процесом.
- Логи pre-deploy-qa складати у `work/04-remember-me-cookie/logs/working/task-5/` (формат на розсуд скіла); посилання — у `decisions.md`.
- Не виконувати real-deploy. Усе локально. Якщо QA зелений — фіча готова до feature-execution → done → merge → CI/CD.
