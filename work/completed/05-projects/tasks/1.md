# Task 1: Backend foundation — AppException factories + Project domain + DTOs + ValidTimezone

## Required Skills

## Description

Lay down the persistence + validation primitives that Wave 2 (`ProjectService`, `ProjectController`, `ProjectHardDeleteJob`) will consume. This task is purely additive on the backend: a brand-new `com.botfunnel.project` package (entity + repository + DTOs + custom validator) plus three factory methods on the existing `common/AppException.java`. No services, no controllers, no business logic — Wave 2 owns those.

Three pieces of intentional design need to be respected verbatim:

1. **`AppException.unprocessableEntity(code, message)` is 2-arg** — the canonical 422 shape going forward (Decision 7). Every 422 in this feature carries a business-rule code (`project_limit_reached` and future codes); a 1-arg variant would let callers emit codeless 422s, breaking i18n key resolution on the frontend (AC-14b). `notFound(message)` stays 1-arg to match the existing `badRequest`/`unauthorized`/`forbidden`/`tooManyRequests` factory shape.
2. **`AppException.conflict(String code, String message)` is added as a NEW 2-arg factory alongside the existing 1-arg `conflict(String message)`** — required by AC-5 and AC-12b (user-spec) which mandate 409 with `code: "project_name_taken"`. The existing `conflict(message)` hardcodes `code = null`; without a 2-arg variant Task 3's `ProjectService` cannot emit a coded 409 without bypassing the factory layer. The 1-arg `conflict(message)` stays untouched (no callers migrate in this task).
3. **`@ValidTimezone` uses `ZoneId.getAvailableZoneIds().contains(tz)` — NOT `ZoneId.of(tz)`** (Decision 3). Pure `ZoneId.of` accepts `"GMT+5"`, `"+02:00"`, `"UT"` — they parse but are not IANA names; future broadcast scheduling depends on DST-aware IANA zones, so offset-only IDs would silently break "send daily at 09:00 local time" semantics.

The `app.projects.max-per-user=${PROJECTS_MAX_PER_USER:5}` config row is added in this task; the actual `@Value("${app.projects.max-per-user:5}")` injection into `ProjectService` happens in Task 3 (no `@ConfigurationProperties` class — matches the codebase pattern).

   - `unprocessableEntity(String code, String message)` returning `new AppException(HttpStatus.UNPROCESSABLE_ENTITY, code, message)` — 2-arg by design (Decision 7).
   - `conflict(String code, String message)` returning `new AppException(HttpStatus.CONFLICT, code, message)` — 2-arg overload added alongside the existing 1-arg `conflict(message)` (which stays untouched). Required by AC-5 and AC-12b (`code: "project_name_taken"`).

2. Create the `com.botfunnel.project` package layout:
   - `Project.java` — `@Document(collection = "projects")` with `@CompoundIndexes` (the container annotation is required — two bare `@CompoundIndex` annotations would be a compile error; see Implementation hints) holding `{ownerId:1, deletedAt:1}` and `{ownerId:1, name:1, deletedAt:1}` (both NON-unique — service-layer enforces uniqueness per Decision 4); `@Indexed` on `ownerId`. Standard getters/setters (match `User.java` style — explicit, no Lombok). Add a short production-index note comment that mirrors the *style* (placement + brevity) of `User.java:10-11` / `Event.java:10-11`, but reflects the current actual config: `application.properties` has `spring.data.mongodb.auto-index-creation=true`, so dev auto-creates indexes; production index management is out of scope. Do not copy any "indexes not auto-created" wording verbatim from the older entities if it conflicts with current config (see Implementation hints for the rationale and acceptable wording).
   - `ProjectRepository.java` — `extends ReactiveMongoRepository<Project, String>` with derived finders exactly as listed in tech-spec Architecture section: `findByIdAndOwnerId`, `findByOwnerIdAndDeletedAtIsNullOrderByCreatedAtDesc`, `findByOwnerIdOrderByCreatedAtDesc`, `countByOwnerIdAndDeletedAtIsNull`, `findByOwnerIdAndNameAndDeletedAtIsNull`, `findByOwnerIdAndNameAndIdNotAndDeletedAtIsNull`, `findByDeletedAtBefore`. Reactive return types — `Mono<Project>`, `Flux<Project>`, `Mono<Long>` — mirroring `UserRepository.java`.

3. Create the three DTOs under `com.botfunnel.project.dto`:
   - `ProjectResponse` — Java record with fields `(String id, String name, String description, String timezone, Instant createdAt, Instant updatedAt, Instant deletedAt)`. NO `ownerId` field (response-shape lock for Risk R2 mass-assignment defense — IT will assert `$.ownerId` does not exist).
   - `CreateProjectRequest` — Java record annotated with `@JsonIgnoreProperties(ignoreUnknown = true)`. Fields: `name` (`@NotBlank @Size(min=3, max=50)`), `description` (`@Size(max=200)`, null/blank allowed), `timezone` (`@NotBlank @ValidTimezone`).
   - `UpdateProjectRequest` — Java record annotated with `@JsonIgnoreProperties(ignoreUnknown = true)`. Patch semantics: `name` (`@Size(min=3, max=50)`, optional — null = no change), `description` (`@Size(max=200)`, null = no change, blank = clear to null in service per AC-22b), `timezone` (`@ValidTimezone`, optional — null/blank = no change). NO `@NotBlank` on optional fields.

4. Create `@ValidTimezone` annotation + validator under `com.botfunnel.project.validation`:
   - `ValidTimezone.java` — annotation pinned at `@Target({ElementType.FIELD, ElementType.PARAMETER})` and `@Constraint(validatedBy = ValidTimezoneValidator.class)`, default `message = "must be a valid IANA timezone identifier"`. Mirror the shape of `auth/validation/ValidPassword.java`.
   - `ValidTimezoneValidator.java` — implements `ConstraintValidator<ValidTimezone, String>`. Returns `true` when `tz == null || tz.isBlank()` (delegate to `@NotBlank` per `ValidPasswordValidator.java` precedent — avoids stacking two error messages on the same missing value); otherwise returns `ZoneId.getAvailableZoneIds().contains(tz)`. NEVER falls back to `ZoneId.of(tz)` (Decision 3).

5. Write the unit test `ValidTimezoneValidatorTest.java` BEFORE running the real validator (TDD anchor below).

6. Add config + env scaffolding:

   - `.env.example` — append `PROJECTS_MAX_PER_USER=5` with a one-line comment matching the file's existing comment style.

**Edge cases:**
- Null/blank `timezone` returns `true` from `ValidTimezoneValidator`; ensures `@NotBlank` owns the message on `CreateProjectRequest.timezone` (matches `ValidPasswordValidator` precedent).
- `UpdateProjectRequest.timezone` is optional → no `@NotBlank` → null/blank is allowed by validation; the service in Task 3 will treat blank as "no change" (AC-22c). This task only enforces the bean-validation contract; service-layer normalization is Task 3's concern.

**Implementation hints:**
- `AppException` overloads: Java resolves `conflict(String)` vs `conflict(String, String)` by arity — the two factories coexist cleanly. The new 2-arg form must NOT replace or remove the 1-arg `conflict(String message)`; both must remain (the 1-arg version may still be reached by other code paths in the codebase).
- `Project.java` `@CompoundIndexes` container is REQUIRED whenever a class declares two or more `@CompoundIndex` annotations. Two bare `@CompoundIndex` annotations on the same class produce a Java compile error ("duplicate annotation of non-repeatable type"; Spring Data's `@CompoundIndex` is NOT marked `@Repeatable`). Use `@CompoundIndexes({ @CompoundIndex(name = "owner_deleted", def = "{...}"), @CompoundIndex(name = "owner_name_deleted", def = "{...}") })` from `org.springframework.data.mongodb.core.index`. **First use of `@CompoundIndexes` in this codebase** — `events/Event.java:13` and `user/User.java` use only a single `@CompoundIndex` each, so there is no in-repo precedent to copy from; both imports (`CompoundIndex` + `CompoundIndexes`) must be added.
- Production-index note comment on `Project.java`: mirror the *style* (1-2 line `//` comment near the class declaration) of `User.java:10-11` and `Event.java:10-11`, but the FACTUAL content of those comments may not match current `application.properties` — the project's `application.properties` currently has `spring.data.mongodb.auto-index-creation=true` (not false). Do not propagate a "indexes are not auto-created" claim here. Acceptable wording: "// Indexes auto-created via spring.data.mongodb.auto-index-creation=true (dev). Production index management is out of scope (see decisions / user-spec Constraints)." If you are tempted to copy the existing comment verbatim, prefer this style mirror instead, and note the rationale briefly in the implementation report (decisions.md).
- Java records work cleanly with Bean Validation: annotations on the record header parameters apply on construction. Spring Boot 3.5.x supports this without extra config.
- `@JsonIgnoreProperties(ignoreUnknown = true)` on a Java record goes ABOVE the `public record ...` declaration (class-level annotation; Jackson respects it during deserialization).
- `ZoneId.getAvailableZoneIds()` returns `Set<String>` — `.contains(tz)` is O(1) typical. Don't cache it; the JDK's set is already a singleton.
- `ValidTimezoneValidator` must NOT throw on a null arg — `@ValidTimezone` may be applied to a nullable patch field (`UpdateProjectRequest.timezone`).
- For tests use plain JUnit 5 (`org.junit.jupiter.api.Test`) and direct instantiation of the validator (`new ValidTimezoneValidatorTest().isValid("...", null)`) — see `ValidPasswordValidator` test precedent if it exists, otherwise the validator is pure logic and a `ConstraintValidatorContext` mock is unnecessary (pass `null`).
