# Task 10: Playwright golden-path E2E spec

## Required Skills

Перед виконанням задачі завантаж:
- `/skill:code-writing` — [skills/code-writing/SKILL.md](../../../.claude/skills/code-writing/SKILL.md)

## Description

Створити єдиний Playwright golden-path E2E-спек `frontend/e2e/projects.spec.ts`, який наскрізно покриває весь UX-флоу проектів від реєстрації до restore. Це останній шар тестової піраміди для фічі 05-projects (бекенд IT/unit + фронтенд vitest вже зібрані у Wave 1-3); E2E-спек ловить інтеграційні регреси, які unit-рівень принципово не бачить (реальні redirect chains, hydration timing, Pinia↔localStorage↔topbar synchronization, реальні CSRF cookies).

Спек має закривати tech-spec AC-T1..T10 на end-to-end-рівні через **єдиний** сценарій, без per-locale варіантів (locale switching уже покритий `e2e/i18n.spec.ts`). Уся інфраструктура реюзається з існуючого `playwright.config.ts` (chromium-only, `webServer: pnpm dev`, `reuseExistingServer: !CI`, `baseURL: http://localhost:3000`) — нових залежностей чи конфігів не вводимо.

Спек є частиною AC-28 (`pnpm test:e2e` зелений) і виконується в Pre-deploy QA Wave перед деплоєм.

## What to do

1. Створити `frontend/e2e/projects.spec.ts` з єдиним `test(...)` блоком, що покриває golden-path.
2. Згенерувати унікальний email на старті тесту (наприклад, `e2e-projects-${Date.now()}@test.local`) — щоб при `reuseExistingServer` проганяти спек локально багато разів без ручного очищення Mongo.
3. Зареєструвати свіжого юзера через `/auth/register` UI-флоу (form fill + submit) і дочекатися auto-login redirect на `/dashboard`.
4. На `/dashboard` перевірити inline empty-state CTA "Create your first project" (AC-18) і клікнути по ній.
5. На `/projects/new` заповнити форму першого проекту (name, опціонально description; timezone defaults to browser TZ — не чіпаємо), submit, дочекатися redirect на `/dashboard` з welcome content і селектором у topbar з назвою першого проекту (AC-19).
6. Через селектор у topbar відкрити dropdown і клацнути "+ Create new project" → знов `/projects/new` → створити другий проект з іншим іменем.
7. Відкрити dropdown селектора, перевірити що обидва проекти видимі, переключитися на перший (AC-21 — оновлення in-memory store + localStorage write).
8. Через селектор перейти на "Project settings" поточного проекту → форма перейменування → ввести нову назву → submit → перевірити що селектор у topbar показує нову назву **без перезавантаження сторінки** (AC-22a; критичний реактивний шлях).
9. Settings → Danger zone → "Delete project" → відкрити модал → перевірити, що кнопка Delete задизейблена при порожньому/частковому інпуті, ввести точну назву проекту → перевірити що Delete стає enabled → confirm → DELETE → дочекатися redirect зі сторінки settings; перевірити що проект зник із селектора (AC-22d).
10. Перейти на `/projects` → перевірити, що секція "Recently deleted" видима з removed-проектом (AC-23) → клацнути Restore → перевірити, що проект знов у Active секції і знов з'являється у селекторі topbar.

## TDD Anchor

E2E-спек сам по собі не має класичного TDD-циклу (тести = код). Натомість перед написанням спеку погратися з UI вручну (через `pnpm dev` + браузер), щоб упевнитися, що всі data-test/role-селектори, на які буде розраховувати спек, реально відрендерені у відповідних станах. Орієнтовний пакет селекторів, на які спирається спек:

- `frontend/e2e/projects.spec.ts::golden path` — registration → empty-state → create #1 → selector populated → create #2 → switch → settings rename → live selector update → soft-delete via type-name modal → /projects "Recently deleted" → restore → active again.

Селектори: тримати їх стабільними через `data-test="..."` атрибути там, де вже є (див. `pages/auth/register.vue` — `data-test="email-error"`, `data-test="submit-error"`); `getByRole(...)` з locale-stable accessible name використовувати лише за необхідності (бо UI у uk-default локалі — UA-літерали в селекторах привнесуть локаль-залежність).

## Details

**Files:**
- `frontend/e2e/projects.spec.ts` — створити. Стиль наслідувати `e2e/i18n.spec.ts` (named import з `@playwright/test`, `test(...)` + `expect(...)` API, без custom fixtures на цей етап). Уся логіка в одному `test('golden path', async ({ page }) => { ... })`; **без** допоміжних helper-файлів — інакше це окрема дискусія про test-utils-shape, не наша.

**Dependencies:**
- Завдання залежить від 7 (`/projects` index page — active + recently deleted з restore), 8 (project settings page — rename, description, timezone, danger-zone delete), 9 (layout integration + ProjectSelector у топбарі). До запуску спеку весь UI має бути зашитий і vitest-зелений.
- Жодних нових npm dev-deps — `@playwright/test` уже у `frontend/package.json` (див. AC-T3).

**Edge cases:**
- **`reuseExistingServer: !CI`.** Локально Playwright використовує живий `pnpm dev`; CI запускає свій. Спек має бути deterministic в обох контекстах.
- **Унікальний email per run.** Не використовувати фіксований seed-email, бо при локальному `reuseExistingServer` друга прогонка зловить 409 на реєстрації. Згенерувати `e2e-projects-${Date.now()}@test.local` на початку тесту.
- **Hydration timing.** Як у `i18n.spec.ts`, після перших navigation чекати `page.waitForLoadState('networkidle')` перед взаємодією з елементами, які залежать від client-side hydration (dropdown селектора, Pinia store init).
- **Default-locale (uk).** UI рендериться українською. Селектори, що залежать від тексту, мають бути на uk-літералах **або** на data-test/role атрибутах (краще друге — менш fragile при локалі-змінах у наступних епіках). Існуючий `i18n.spec.ts` явно `test.use({ locale: 'uk-UA' })` — наш спек **не** використовує `test.use(...)`, бо default-locale uk без опційного override (Nuxt i18n `prefix_except_default` робить uk identity).
- **Soft-delete redirect.** Після confirm в Danger zone модалі юзер редиректиться зі сторінки settings (бо проект тепер soft-deleted і `requireOwned(includeSoftDeleted=false)` → 404 для PATCH/GET). Перевірити куди — на `/dashboard` або на `/projects` (залежить від реалізації Wave 3).
- **Type-the-name модал — case-sensitive trim-compare.** Спек має ввести точний `project.name` як string, інакше Delete лишиться disabled. Переконатися, що `page.fill(...)` не додає trailing whitespace.
- **localStorage cross-tab.** Спек запускається в одному browser context — cross-tab independence (AC-21 nuance) тут не перевіряємо; це окрема (свідомо опущена) E2E-варіація.

**Implementation hints:**
- Тримати спек **читабельним** — кожен крок golden-path має читатися як comment-section: `// Step 1: register fresh user`, `// Step 2: empty-state`, тощо. Це знадобиться при майбутньому debugging-у падінь у CI.
- Селектори — пріоритет `data-test=...` (вже застосовано у `pages/auth/register.vue`), потім `getByRole({ name })` з UA-літералом, потім `page.locator('text=...')` як fallback.
- Тест-пароль інлайнити фейковий (`Test1234!` тип), не зчитувати з env — інакше CI впаде на missing var.
- **Не** додавати `test.beforeAll/afterAll` із cleanup-ом DB — для MVP залишок у локальному Mongo прийнятний (юзер email унікальний per-run); централізований cleanup — окрема дискусія, не наша.
- **Не** мокати API через `page.route(...)` — спек має ходити в реальний бекенд (це і є цінність E2E-шару).
- При timing-flakiness замість `page.waitForTimeout(...)` (анти-патерн) використовувати `expect.poll(...)` (як у `i18n.spec.ts`) або `await expect(locator).toBeVisible()` із дефолтним 5s timeout-ом.
- Якщо реалізація Wave 3 додасть optimistic UI updates (наприклад rename миттєво відображається до 200 OK) — спек уже це покриває через "live update без `page.reload()`" перевірку, додаткових assertions не треба.

**Selector coordination contract (data-test атрибути):**

Спек цього таску спирається на стабільні `data-test` хуки замість text-based селекторів. Сетап атрибутів — **відповідальність Wave 3 тасків (6, 7, 8, 9)**, не Task 10. Task 10 лише консумує контракт; якщо при написанні спеку виявиться, що якогось хука бракує — це fix у відповідному Wave 3 таску, не правка тут.

  - `data-test="project-selector-current"` — елемент, що показує назву поточного проекту (для assertion-ів live-update після rename).
  - `data-test="project-selector-toggle"` — клікабельний trigger, що відкриває dropdown.
  - `data-test="project-selector-option"` — `[data-test="project-selector-option"][data-project-id="..."]` для пунктів списку проектів (AC-21).
  - `data-test="project-selector-create-cta"` — "+ Create new project" пункт у dropdown.
  - `data-test="project-selector-settings-cta"` — "Project settings" link у dropdown (для поточного проекту).

Під час написання спеку: спочатку запустити `cd frontend && pnpm dev`, відкрити кожен релевантний стан у браузері і перевірити DOM на наявність хуків. Якщо хук відсутній — припинити, відкрити fix-задачу для відповідного Wave 3 таску, дочекатися фіксу, тоді продовжити. **Не** додавати `data-test` атрибути у Wave 3 файлах в межах цього таску — це порушить ownership boundary і zero-touch контракт AC-T7.
