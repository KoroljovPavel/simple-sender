# Task 11: Code Audit

## Description

Holistic, full-feature code quality audit of everything that landed in feature `05-projects` (Tasks 1–10). Per-task reviewers (code-reviewer / security-auditor / test-reviewer) only see one slice; this audit looks across the whole PR for cross-component issues that no single per-task reviewer can catch:

- duplicate resource initialization (e.g. two places building the same `WebClient`, `MongoTemplate` query helper, Pinia store, validator, etc.);
- shared-resource compliance with the Architecture decisions in tech-spec — most importantly the **single ownership entry point**: every project-scoped backend handler must go through `ProjectService.requireOwned(ownerId, projectId, includeSoftDeleted)`. There must be no second ownership check, no inline `findById + ownerId.equals` bypass, no controller-level filtering that duplicates the guard;
- architectural consistency: DTOs use the `@JsonIgnoreProperties(ignoreUnknown=true)` whitelist pattern (Task 1); the `currentUserId()` pattern is reused exactly as in `ProfileController`/`AuthService` (no fresh re-implementations); 404 anti-enumeration uniformity across `requireOwned` paths; `EventService` audit emission lives in the service layer (not in controllers, not in the job — except where Task 4 explicitly emits `project_hard_deleted` BEFORE deletion per AC-17b);
- **AC-T7 zero-touch contract:** no edits in this feature to `frontend/middleware/auth.global.ts`, `backend/src/main/java/com/botfunnel/security/SecurityConfig.java`, `backend/src/main/java/com/botfunnel/jobs/JobRunrMongoConfig.java`. Also verify the broader zero-touch list from tech-spec architecture (`EventService.java`, `AbstractIntegrationTest`) was not edited;
- **AC-T11:** all Mongo queries in `com.botfunnel.project.*` and `com.botfunnel.jobs.ProjectHardDeleteJob` use `ReactiveMongoRepository` derived finders or `Query.query(Criteria.where(field).is/in(typedValue))` with typed values. No string concatenation into `Criteria`, no `Criteria.where(...).is(rawJson)`. This is the NoSQL-injection guidance freeze for downstream epics;
- **AC-T12:** `frontend/stores/projects.ts` is the only frontend source file calling `localStorage.setItem` (Decision 10 scope-lock);
- **AC-T6:** `pages/dashboard.vue` does NOT call `localStorage` directly;
- **AC-T9:** no backend code references `@CompoundIndex(unique = true, partialFilter = ...)` (unsupported in Spring Data MongoDB; uniqueness lives in service layer per Decision 4).

The output is a written audit report — not code changes. The auditor IS the reviewer, so the `reviewers` list for this task is empty by design.

- `cd frontend && node scripts/check-locales.mjs` → exit 0 (locale parity unbroken after all waves — AC-T5).

## Details

**Files:** This task does not modify code. It produces:
- `work/05-projects/logs/working/task-11/code-audit-1.json` — structured audit findings.
- New entry in `work/05-projects/decisions.md` for Task 11.

**Dependencies:** Task 10 (everything from Waves 1–4 must be on disk). Audit Wave runs in parallel with Tasks 12 (Security Audit) and 13 (Test Audit) — they look at orthogonal dimensions and do not block each other.

**Edge cases for the audit itself:**
- A file listed in tech-spec `Files to create` but not actually created → record as a finding (`high` severity — spec drift).
- A file edited that is not in any task's `Files to modify` list → record (`medium` — unplanned change).
- AC-T7 zero-touch file edited even if functionally harmless → record (`critical` — explicit AC violation).
- A duplicate ownership check found alongside `requireOwned` → record (`high` — defeats the architectural single-entry-point guarantee).
- `localStorage.setItem` in a second frontend file → record (`high` — AC-T12 violation, breaks Decision 10 scope-lock).

**Implementation hints:**
- Lean on the `code-reviewing` skill's review dimensions; this audit is the cross-component application of those dimensions, not per-file.
- For each finding, prefer `severity = info` over silence — the report exists so future audits and downstream epics see what was checked, not just what failed.
- The JSON is consumed by `feature-execution` and the final QA wave — keep keys stable: `{summary: {verdict, totals_by_severity, scope_files_count}, findings: [{id, severity, area, file, lines, issue, recommendation}]}`.
- If a finding crosses domains (e.g. a security issue surfaces during the code audit), record it AND flag it for Task 12 (Security Audit) via a cross-reference note in the finding.
- "Pass-with-recommendations" is the expected normal outcome; `block` is reserved for AC violations or duplicate-ownership-check class issues.
