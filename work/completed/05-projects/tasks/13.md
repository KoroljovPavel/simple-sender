## Description

Финальный аудит качества тестового набора фичи `05-projects` перед Pre-deploy QA. Цель — убедиться, что весь тестовый код, написанный в волнах 1–4 (Tasks 1–10), действительно покрывает 31 acceptance-criterion из user-spec и 12 технических AC-T1..AC-T12 из tech-spec, что ассерты содержательные (не «200 OK ради 200 OK»), а пирамида тестов сбалансирована согласно методологии проекта (`patterns.md`, секция Testing Requirements: тяжёлые IT для бэкенда поверх `AbstractIntegrationTest`, фокусированные vitest юниты для компонентов/сторов, ровно один Playwright golden-path).

Auditor для этой задачи и есть ревьюер — поэтому секция `reviewers` пустая. Результат — отчёт-маркдаун с findings (severity-классификация: blocker / major / minor / nit), который параллельно идёт с Task 11 (Code Audit) и Task 12 (Security Audit), а его выводы должны быть устранены до старта Task 14 (Pre-deploy QA). Если найдены blocker-пробелы (отсутствующее покрытие AC, фиктивные ассерты), фича не должна уходить в Final Wave — auditor возвращает работу в соответствующую волну.

## Verification Steps

### Automated

Audit задача — самопроверка через check-list ниже; ничего отдельно «запускать» не нужно. Опционально, для конфидентности:

- `./gradlew test --tests "com.botfunnel.project.*"` → проходит без skipped/ignored
- `./gradlew test --tests "com.botfunnel.jobs.Project*"` → проходит без skipped/ignored (покрывает `ProjectHardDeleteJobTest` + `ProjectHardDeleteJobIT`, которые лежат в пакете `com.botfunnel.jobs`, а не `com.botfunnel.project`)
- `pnpm --dir frontend test -- --reporter=verbose tests/stores tests/components tests/pages tests/composables tests/i18n` → нет `.skip` и `.only`
- `pnpm --dir frontend test:e2e -- e2e/projects.spec.ts --list` → ровно один спек выводится

Эти команды — для подтверждения, что тестовый набор хотя бы запускается; авторитетным запуском всё равно остаётся Task 14 (Pre-deploy QA).

**Dependencies:**

**Edge cases & gotchas (call them out in findings if encountered):**
- Soft-deleted-but-foreign IDs and malformed IDs MUST return 404 uniformly across GET / PATCH / DELETE / RESTORE. Missing any verb-parity row (`PATCH /{malformed-id}` etc.) is a blocker — anti-enumeration is a security property, not a nice-to-have.
- `ProjectHardDeleteJobTest` and `ProjectHardDeleteJobIT` live under `backend/src/test/java/com/botfunnel/jobs/` (mirroring the production-code location `backend/src/main/java/com/botfunnel/jobs/`), NOT under `com.botfunnel.project.*`. Auditor must read both files from the `jobs/` package; `ValidTimezoneValidatorTest` lives under `backend/src/test/java/com/botfunnel/project/validation/` (mirroring `auth/validation/ValidPasswordValidatorTest.java`).
- `JobRunr` recurring-job assertion has "no precedent" in current test code (per tech-spec line 350). If the autowire path failed and the test fell back to inspecting `InMemoryStorageProvider` directly — that's acceptable; if it's silently absent — blocker.
- `frontend/tests/i18n/required-keys.spec.ts` is a NEW test file added specifically because `check-locales.mjs` would pass even if all four AC-25 keys were omitted from BOTH locales. Verify the spec actually iterates over both locales and asserts both, not just one.
- The `localStorage` SSR-safety branch (`frontend/tests/stores/projects.spec.ts` with `import.meta.client = false`) addresses Risk R6. If this branch is missing, mark blocker — Nuxt 4 SSR will throw `ReferenceError` in production.
- Beware false positives in the pyramid check: `ProjectControllerSliceTest` is intentionally MINIMAL (only happy-path response shape, per tech-spec line 297). Don't flag its leanness as missing coverage — it's a deliberate decision.

**Implementation hints:**
- Build the AC → test mapping as a literal markdown table inside the inline audit report. This makes findings reviewable at a glance.
- For each finding, include a one-line "fix anchor": file path + suggested test name. This lets the orchestrator dispatch the fix back to the right wave/task without re-reading the spec.
- When in doubt about whether something is `weak` vs `direct` coverage: ask "if this test passed but the production code regressed AC-X, would the test still pass?" If yes → weak.
