## Description

Финальная приёмка фичи `05-projects` перед деплоем. Запускаем полный test suite (backend `./gradlew test`, frontend `pnpm test`, E2E `pnpm test:e2e`, build `pnpm build`), затем проходим Agent Verification Plan из user-spec — шаги 2-11 (curl-проверки лимитов/конфликтов/auth/404, инспекция MongoDB, JobRunr recurring registration через интеграционный тест, PK alignment grep). После этого верифицируем все критерии приёмки: user-spec AC-1..31 (backend, frontend, quality gates, UI limit, documentation alignment) и tech-spec AC-T1..T12 (контрактные ограничения). Финал — проводим вручную чек-лист "Локально перед merge" из user-spec (cross-restart localStorage persistence, soft-delete + 404 cleanup, i18n smoke на /en).

Это QA-задача без code changes — никаких ревью (reviewers: []), никаких TDD anchor. Цель: обнаружить дефекты ДО merge/deploy и зафиксировать состояние "feature ready". Если найдены regressions/баги — описать в decisions.md и вернуть соответствующие задачи в work-loop.

## Verification Steps

### Automated

- `cd backend && ./gradlew test` → BUILD SUCCESSFUL, 0 failures
- `cd frontend && pnpm test` → vitest all green
- `cd frontend && pnpm test:e2e` → Playwright golden-path `e2e/projects.spec.ts` passes
- `cd frontend && pnpm build` → Nuxt build success, locale parity gate (`scripts/check-locales.mjs`) exit 0
- `cd frontend && node scripts/check-locales.mjs` → exit 0

### Smoke

AVP-агент шаги 2-11 (выполняются на локально поднятом стеке):

- **Шаг 2 (CREATE limit):** `curl -i -X POST localhost:8080/api/v1/projects -H 'Cookie: SESSION=<5-projects-user>' -H 'Content-Type: application/json' -d '{"name":"6th","timezone":"Europe/Kyiv"}'` → **422** + body `{"message":"...","code":"project_limit_reached"}`.
- **Шаг 3 (RESTORE limit):** `curl -i -X POST localhost:8080/api/v1/projects/{soft-deleted-id}/restore -H 'Cookie: SESSION=<5-active-1-deleted-user>'` → **422** + `code: "project_limit_reached"`.
- **Шаг 4 (foreign id):** `curl -i localhost:8080/api/v1/projects/{foreign-objectid} -H 'Cookie: SESSION=<other-user>'` → **404** (НЕ 403).
- **Шаг 5 (malformed id):** `curl -i localhost:8080/api/v1/projects/zzz-not-an-objectid -H 'Cookie: SESSION=...'` → **404** uniform.
- **Шаг 6 (no session):** `curl -i localhost:8080/api/v1/projects` (без cookie) → **401**.
- **Шаг 7 (duplicate name):** создать проект → второй `POST` с тем же `name` → **409** + `code: "project_name_taken"`.
- **Шаг 8 (invalid timezone):** `POST` с `"timezone":"GMT+5"` → **400**, message содержит `timezone`, `code: null`.
- **Шаг 9 (Mongo inspection):** `mongosh ... --eval 'db.projects.findOne({name:"AVP-test"})'` → проверить `ownerId` (ObjectId), `name`, `timezone`, `createdAt`, `deletedAt: null` на активном; после soft-delete — `deletedAt` ISO instant.
- **Шаг 10 (JobRunr recurring):** интеграционный тест из Task 4 (`ProjectHardDeleteJobIT`) ассертит `JobScheduler.getRecurringJobs()` содержит `id="hard-delete-projects"`, `cron="0 3 * * *"` — проверка через `./gradlew test --tests 'com.botfunnel.jobs.ProjectHardDeleteJobIT'`.
- **Шаг 11 (PK alignment grep):** `grep -n "full-page onboarding" .claude/skills/project-knowledge/references/ux-guidelines.md` → 0 результатов.

Дополнительные проверки tech-spec AC-T:

- **AC-T7 (zero-touch):** `git diff main -- frontend/middleware/auth.global.ts backend/src/main/java/com/botfunnel/security/SecurityConfig.java backend/src/main/java/com/botfunnel/jobs/JobRunrMongoConfig.java` → пусто.
- **AC-T8 (gitleaks):** `gitleaks detect --source . --verbose --no-banner` → pass (репо использует raw git hook через `scripts/install-hooks.sh`, `pre-commit` framework не настроен).
- **AC-T9 (no partial unique index):** `grep -rn "@CompoundIndex" backend/src/main/java/com/botfunnel/project/` → 0 результатов с `unique = true, partialFilter`.
- **AC-T11 (NoSQL safety):** `grep -rn "Criteria.where" backend/src/main/java/com/botfunnel/project/` — все вхождения должны использовать typed values, никаких string-concat в Criteria.
- **AC-T12 (single localStorage):** `grep -rn "localStorage.setItem" frontend/` (исключая `node_modules`, `tests`) → ровно один source-file match в `frontend/stores/projects.ts`.

### User

- Запустить стек (Docker Compose + backend + frontend dev). Зарегистрировать юзера, создать 2 проекта A и B, выбрать B в селекторе.
- В Chrome DevTools → Application → Local Storage убедиться, что `bot-funnel.currentProjectId === <B-id>`.
- Закрыть браузер. Открыть снова → залогиниться → селектор должен показать **B** (не A — то есть localStorage сработал, не fallback на новейший).
- Soft-удалить B из settings → открыть новую вкладку → селектор должен показать **A** (B исчез из активных + 404-interceptor очистил localStorage).
- **i18n smoke:** переключить локаль на `/en` → визуально пройти golden path → проверить, что все новые тексты (selector, settings, danger zone, "Recently deleted", toast про unavailable project) переведены и нет видимых ключей вида `projects.delete.confirm`.
- **JobRunr dashboard (опциональный post-deploy smoke, не AVP-обязанность):** после деплоя открыть `/jobrunr-dashboard` → Recurring → убедиться, что `hard-delete-projects` (cron `0 3 * * *`) присутствует рядом с существующим `hard-delete-users`. На pre-deploy шаге достаточно integration-test ассерта (Шаг 10).

## Details

**Files:** read-only (QA не меняет код). Если найдены defects — открыть тикет / описать в `decisions.md`, не патчить здесь.

**Dependencies:**
- Tasks 11 (Code Audit), 12 (Security Audit), 13 (Test Audit) должны быть `done` — их audit reports в `decisions.md` дают контекст известных compromises.
- Локальный стек: Docker Compose (Mongo + Redis + Mailpit — 3 сервиса из `infra/docker-compose.yml`), backend `./gradlew bootRun` на :8080, frontend `pnpm dev` на :3000.
- Тестовые фикстуры: 2 разных юзера (для AVP шага 4 — foreign id), один юзер с 5 активными проектами (для AVP шага 2), один юзер с 5 активными + 1 soft-deleted (для AVP шага 3). Создавать через REST API в начале QA-сессии.

**Edge cases (must-not-skip):**
- AVP шаг 4 (foreign id) — критическая anti-enumeration проверка. Если возвращается 403, а не 404 — **blocking defect**.
- AVP шаг 9 (Mongo inspection) — обязательно проверить, что `deletedAt` действительно `null` на активном и ISO instant на soft-deleted (не пустая строка / not-set).
- "Локально перед merge" cross-restart — реальная закрытие/открытие браузера (не только refresh), потому что storage event listener свідомо отсутствует (per AC-21).
- i18n smoke — пройти minimum 1 проект create/rename/soft-delete/restore цикл на `/en`, не просто открыть страницы.
- AC-T7 (zero-touch) — даже одна строка изменения в forbidden файлах = blocking defect.

**Implementation hints:**
- Использовать MongoDB MCP для шага 9 если доступен; иначе `mongosh` с `--eval`.
- Все curl-команды с `-i` для inspection полного response (status + headers + body).
- Для AVP шагов 2-3 нужны seed-юзеры с N проектами; самый быстрый путь — создать через 5 последовательных POST в начале сессии под одним session cookie.
- При обнаружении любого failed AC — НЕ продолжать тихо. Записать в `decisions.md` под секцией "Task 14 — defects found" с воспроизведением, ожидаемым vs фактическим, и предлагаемым исправлением (или возврат task X в work-loop).
- Если все AC pass — финальный отчёт в `decisions.md`: "Task 14 QA: ALL PASS, ready to merge", дата, оценка времени, ссылка на test reports.
