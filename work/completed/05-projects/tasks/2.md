# Task 2: Frontend foundation — types + Pinia projects store + i18n keys (uk + en)

## Required Skills

Before starting, load:
- `/skill:code-writing` — [skills/code-writing/SKILL.md](../../../.claude/skills/code-writing/SKILL.md)

## Description

Lay down the frontend foundation primitives that every later Wave 2/3 task in feature 05-projects will consume: a shared `Project` TypeScript type, a Pinia `projects` store that owns `projects[]` + `currentProjectId` (mirrored to `localStorage` under SSR-safe `import.meta.client` gates), and the full i18n key tree for `projects.*`, `errors.projects.*`, `layout.projectSelector*`, `layout.sidebar.settings`, `validation.projectName*`, `validation.timezone*` namespaces — with parity between `uk.json` and `en.json` enforced atomically (locale parity gate, AC-25, AC-T5).

The store implements user-spec Сценарій 2 auto-select rule (AC-20: prefer persisted ID if present in fetched active list, fallback to `projects[0]` sorted `createdAt desc`), the `selectProject` write-through (AC-21: writes to localStorage under `import.meta.client`), the `handleStaleCurrent` recovery routine (AC-24: clear in-memory + remove localStorage key + refetch + auto-select), and `isLoaded` deduping per Decision 9 (lazy hydration, no fetch in `auth.global.ts`).

The i18n keys must include the four AC-25-mandated keys explicitly: `errors.projects.delete.confirmTypeName`, `errors.projects.unavailable`, `errors.projects.restore.renamedDueToConflict`, `projects.create.limitReachedTooltip` — these are asserted by a dedicated vitest spec because `check-locales.mjs` only checks parity, not completeness against AC-25.

This task does NOT wire the 404 interceptor (Task 5), does NOT render any UI (Tasks 5/6/7/8), and does NOT call from `auth.global.ts` (Decision 9 — zero-touch contract per AC-T7). It only ships the types, the store, the locale keys, and their specs.

## What to do

1. Create `frontend/types/project.ts` exporting a `Project` interface that mirrors the backend `ProjectResponse` (per tech-spec Data Models § Frontend types): fields `id`, `name`, `description: string | null`, `timezone`, `createdAt: string` (ISO instant), `updatedAt: string`, `deletedAt: string | null`.

2. Create `frontend/stores/projects.ts` — a Pinia store (`defineStore('projects', () => { ... })` setup-style, mirroring `stores/auth.ts` shape) exposing:
   - **State:** `projects` (ref<Project[]>), `currentProjectId` (ref<string | null>), `isLoaded` (ref<boolean>) — `isLoaded` flips to `true` after the first successful `fetchAll` regardless of result, used to dedupe concurrent calls and to gate the empty-state in `dashboard.vue`.
   - **Computed:** `currentProject` — returns the `Project` from `projects` whose `id === currentProjectId`, or `null`.
   - **Initialization:** on store creation, if `import.meta.client` is true, read `localStorage.getItem('bot-funnel.currentProjectId')` and seed `currentProjectId` (no validation against the list yet — `fetchAll` will auto-select per AC-20). Under SSR (`!import.meta.client`), DO NOT touch `localStorage` (must not throw `ReferenceError`). The localStorage key constant `'bot-funnel.currentProjectId'` is exported (so tests and the 404 interceptor can refer to a single source of truth).
   - **Action `fetchAll(includeDeleted = false)`:** calls `useApi()<Project[]>('/api/v1/projects', { query: includeDeleted ? { include_deleted: true } : undefined })`, assigns to `projects`, runs the AC-20 auto-select rule (if `currentProjectId` is non-null AND present in fetched active list AND `deletedAt === null` — keep it; else set to `projects[0]?.id ?? null` from active-only sorted `createdAt desc`; the backend already sorts but the store re-sorts defensively), persists the resulting `currentProjectId` via `selectProject` semantics (write-through to localStorage under `import.meta.client` gate), sets `isLoaded = true` in `finally`. Concurrent calls: if `isLoaded` is already true, still allow re-fetch (settings/restore flows need fresh data) but de-dup parallel in-flight via a module-level `inFlight` promise.
   - **Action `create(payload: { name, description, timezone })`:** `useApi()<Project>('/api/v1/projects', { method: 'POST', body: payload })`. On 201, push response to `projects`, call `selectProject(response.id)`, return the created `Project`. Errors propagate to caller (so `useApiError` in pages can map 400/409/422).
   - **Action `update(id, partial: Partial<{ name, description, timezone }>)`:** `useApi()<Project>(\`/api/v1/projects/\${id}\`, { method: 'PATCH', body: partial })`. On 200, replace the matching item in `projects` (preserve order). Errors propagate.
   - **Action `softDelete(id)`:** `useApi()(\`/api/v1/projects/\${id}\`, { method: 'DELETE' })`. On 200, remove from `projects`. If `currentProjectId === id`, fall back per AC-20 (next active sorted `createdAt desc` or `null`), persisted via `selectProject`. (Used by Settings danger zone — Task 8.)
   - **Action `restore(id)`:** `useApi()<Project>(\`/api/v1/projects/\${id}/restore\`, { method: 'POST' })`. On 200, ensure the (possibly renamed-with-suffix) project is present in `projects`. Returns the response so `/projects` page (Task 7) can compare `response.name` with the pre-request name to detect renaming and toast `errors.projects.restore.renamedDueToConflict` per AC-14b.
   - **Action `selectProject(id: string | null)`:** sets `currentProjectId = id`. Under `import.meta.client`: when `id` is non-null → `localStorage.setItem('bot-funnel.currentProjectId', id)`; when `id` is null → `localStorage.removeItem('bot-funnel.currentProjectId')`.
   - **Action `handleStaleCurrent()`:** clears `currentProjectId` (via `selectProject(null)` so the localStorage key is removed too — defensive cleanup per AC-24), then `await fetchAll()` (which runs the auto-select per AC-20 against the fresh list). Used by the 404 interceptor in Task 5 and by the `softDelete` action when current goes away.
   - **No `storage` event listener** (per user-spec Сценарій 2: cross-tab independence is intentional).

3. Add the i18n keys to `frontend/i18n/locales/uk.json` AND `frontend/i18n/locales/en.json` (atomic update; `check-locales.mjs` enforces parity). Add the following namespaces with the listed keys at minimum:
   - `projects.*`: `title` (page title for `/projects`), `activeSection`, `recentlyDeletedSection`, `emptyState.title`, `emptyState.description`, `emptyState.cta`, `create.title`, `create.submit`, `create.submitting`, `create.nameLabel`, `create.descriptionLabel`, `create.timezoneLabel`, `create.limitReachedTooltip` (AC-25), `settings.title`, `settings.general`, `settings.dangerZone`, `settings.rename`, `settings.descriptionLabel`, `settings.timezoneLabel`, `settings.save`, `settings.saving`, `settings.saved`, `settings.delete.open`, `settings.delete.modalTitle`, `settings.delete.modalIntro`, `settings.delete.typeNameLabel`, `settings.delete.confirm`, `settings.delete.cancel`, `settings.delete.deleting`, `restore.action`, `restore.success`, `daysRemaining` (with `{count}` placeholder for "Recently deleted ({count} day(s) remaining)" — match existing locale convention; if no ICU plural in repo, plain `{count}` template is fine).
   - `errors.projects.*`: `generic`, `create.400`, `create.409`, `create.422`, `update.400`, `update.409`, `update.404`, `delete.404`, `delete.confirmTypeName` (AC-25 — message in modal: "Type the project name to confirm"), `restore.404`, `restore.422`, `restore.renamedDueToConflict` (AC-25 — informational toast per AC-14b), `unavailable` (AC-25 — toast for stale-state 404 per AC-24).
   - `layout.projectSelector*`: `layout.projectSelector.placeholder` (when no project selected), `layout.projectSelector.createNew`, `layout.projectSelector.settingsLink`, `layout.projectSelector.noActive` (when 0 active projects).
   - `layout.sidebar.settings` — single key for the sidebar Settings link (Task 9).
   - `validation.projectName*`: `validation.projectNameRequired`, `validation.projectNameMin` (3 chars), `validation.projectNameMax` (50 chars).
   - `validation.timezone*`: `validation.timezoneRequired`, `validation.timezoneInvalid`.

   Translations are author-natural — UA strings in `uk.json`, EN strings in `en.json`. Keep keys identical between files (no `_locale_only` keys). Mirror existing placeholder syntax (`{name}` etc.). Preserve existing top-level namespaces; do not remove or rename existing keys.

4. Create `frontend/tests/stores/projects.spec.ts` — vitest spec covering:

**Dependencies:**
- No new packages (AC-T3). Pinia, vitest, vue, vue-router are already wired (see `stores/auth.ts` for the setup-style store pattern). For `projects` we use `ref` (not `useState`) because the data is fetched per-session and we don't need cross-component SSR state hydration the same way `auth` does.

**Edge cases:**
- Persisted ID belongs to a soft-deleted project that surfaces under `?include_deleted=true` — for default `fetchAll(false)` (active only), the auto-select treats it as missing and falls back to `projects[0]` per AC-20. The persisted ID is overwritten via `selectProject(newId)`.
- Persisted ID is malformed (e.g., user manually wrote junk into localStorage) — backend would return 404, frontend's 404 interceptor (Task 5) would call `handleStaleCurrent`. For this task: `fetchAll` itself doesn't validate the ID's shape — it just checks "present in fetched list". So junk-in-localStorage → AC-20 fallback path → write-through cleans the key. No throw.
- `localStorage` quota exceeded (very rare for a 24-char ObjectId hex) — the `setItem` call may throw `QuotaExceededError`. Wrap `selectProject`'s persistence in try/catch; on throw, log a `console.warn` and continue (in-memory state is still correct). Keeps the UX recoverable.
- Empty array from `fetchAll` — `currentProjectId` becomes `null`, localStorage key is removed (via `selectProject(null)`), `currentProject` computed returns `null`. This is the Сценарій 1 / AC-18 path — the dashboard then renders the empty-state CTA (Task 6).
- Concurrent `fetchAll` calls (e.g., `dashboard.vue` mount + `ProjectSelector.vue` mount both call it) — module-level `inFlight: Promise<void> | null` dedupes; the `isLoaded` flag is only meaningful for "has the first fetch completed".
- `softDelete` of `currentProject` — must NOT throw; must auto-select the next active or `null`. Test covers this.
- `restore` when the response name has the `" (restored)"` suffix appended by backend — store does NOT detect renaming (that's Task 7's job per AC-14b — the page compares request-context name vs response name and decides whether to toast the informational rename). The store just persists the (possibly renamed) project as-is.

**Implementation hints:**
- Match `stores/auth.ts` setup-style pattern; use `ref` (not `useState`) for `projects` and `isLoaded` because we want client-side fresh state per session, not SSR-hydrated state.
- The localStorage key constant: `export const LOCAL_STORAGE_KEY = 'bot-funnel.currentProjectId'` — Task 5's 404 interceptor and Task 8's settings danger zone may reference it.
- For the SSR guard, define a tiny inline helper inside the store: `const readPersisted = () => import.meta.client ? localStorage.getItem(LOCAL_STORAGE_KEY) : null` and `const writePersisted = (id: string | null) => { if (!import.meta.client) return; try { id ? localStorage.setItem(LOCAL_STORAGE_KEY, id) : localStorage.removeItem(LOCAL_STORAGE_KEY) } catch { /* quota or disabled — log */ } }`. This makes the SSR-branch test trivial and gives the QuotaExceeded edge case a single point of handling.
- The auto-select function is reused by `fetchAll` and `handleStaleCurrent` — extract as a private helper `runAutoSelect()` that reads `currentProjectId` and `projects`, computes the new ID per AC-20, and calls `selectProject(newId)`.
- For the i18n keys: when in doubt about key naming, mirror `profile.deleteAccount.modalTitle` / `profile.deleteAccount.modalIntro` pattern — flat-ish, scoped under feature. The `errors.projects.*` sub-tree must include status-code-keyed children for actions where the calling page uses `useApiError` (e.g., `errors.projects.create.400`) — see Task 5/6/7/8 expectations for which codes; this task adds the keys, the pages consume them.

Inspect existing files; if none, default to plain templating.
