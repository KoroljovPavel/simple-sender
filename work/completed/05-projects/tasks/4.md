## Description

Implement the daily cron that permanently removes soft-deleted projects (>7 days old) plus their associated audit events, while preserving a `project_hard_deleted` event per deleted project as a permanent audit trail. This is the back-end side of user-spec AC-16 / AC-17 / AC-17b / AC-17c and tech-spec Decision 5 (cascade scope = projects + `events` only).

The job mirrors the existing `HardDeleteJob` (users) — same cron slot `0 3 * * *` UTC, same `@Recurring` registration pattern, same JobRunr distributed-lock semantics — but with a strict cascade ordering that makes AC-17b hold:

1. sweep `events` where `metadata.projectId ∈ deletedIds` FIRST,
2. emit one `project_hard_deleted` event per deleted project SECOND (these post-date the sweep so they survive),
3. drop the project documents THIRD.

Read the tech-spec Architecture "Hard-delete cron" subsection (lines 80-86) carefully — implement that exact order. The order is what makes AC-17b hold: emitting `project_hard_deleted` BEFORE the events-collection sweep would let those events get cascade-deleted in the same run.

A structured INFO log is emitted at end-of-run on every invocation (including zero-deletion days) with `deletedCount`, `eventsRemovedCount`, `runDurationMs` so operations can see the cron is alive (AC-17c).

## What to do

- Create `backend/src/main/java/com/botfunnel/jobs/ProjectHardDeleteJob.java`:
  - `@Component` class with constructor injection of `ProjectRepository` (added in Task 1), `EventService`, and `ReactiveMongoTemplate`.
  - Method annotated `@Recurring(id = "hard-delete-projects", cron = "0 3 * * *")` and `@Job(name = "Hard delete soft-deleted projects")` — same shape as `HardDeleteJob.hardDeleteSoftDeletedUsers()`.
  - Cutoff = `Instant.now().minus(7, ChronoUnit.DAYS).plusNanos(1)` (the `+1ns` matches `HardDeleteJob` semantics — converts strict-`<` finder into inclusive-at-the-boundary).
  - Materialise candidates via `projectRepository.findByDeletedAtBefore(cutoff).collectList().blockOptional().orElseGet(List::of)` to capture id + name + ownerId for logging and event metadata before any mutation.
  - **Ordering hazard — read this before coding:** `EventService.logEvent(...)` is `void` and calls `eventRepository.save(event).subscribe(...)` internally (fire-and-forget — never throws, never blocks). Calling it between two `.block()` calls does NOT guarantee the event document is persisted to MongoDB before the next `.block()` returns. AC-17b requires the `project_hard_deleted` event to survive past step 3. The implementer MUST eliminate this race using ONE of the two options below (pick one; record the choice in `decisions.md`):
    - **Option A — recommended: add `EventService.logEventBlocking(...)` returning `Mono<Event>`.** New method (does NOT replace `logEvent`) with the same parameter list, body `return eventRepository.save(event)`. Caller chains `.block()` (or composes via `.then(...)`) so the save completes before the cascade proceeds. Existing `logEvent(...)` callers stay untouched.
    - **Option B — inline the save.** Constructor-inject `EventRepository` directly into `ProjectHardDeleteJob` and call `eventRepository.save(event).block()` for each `project_hard_deleted` row. Avoids touching `EventService` but duplicates the `Event` constructor call.
  - Implement the cascade in this exact order (the order that makes AC-17b hold) — every step must be synchronously completed before the next begins:
    1. `template.remove(Query.query(where("metadata.projectId").in(deletedIds)), "events").block()` — capture `DeleteResult.getDeletedCount()` as `eventsRemovedCount`.
    2. For each candidate project, persist the `project_hard_deleted` event SYNCHRONOUSLY using Option A or B — `eventService.logEventBlocking(ownerId, "project_hard_deleted", null, null, Map.of("projectId", id, "name", name)).block()` OR `eventRepository.save(new Event(ownerId, "project_hard_deleted", null, null, metadata, Instant.now())).block()`. Do NOT use the existing fire-and-forget `eventService.logEvent(...)` here — it does not provide the ordering guarantee AC-17b needs.
    3. `template.remove(Query.query(where("_id").in(deletedIds)), "projects").block()` — drops the project documents.
  - End-of-run INFO log on every path (including zero-deletion early-return) with the structured fields: `deletedCount=<N> eventsRemovedCount=<M> runDurationMs=<ms>`. Use a single `log.info("...")` call so log-aggregator parsers see one line per run.
  - Use typed `Criteria` only — `where("metadata.projectId").in(typedList)` and `where("_id").in(typedList)`. No string concatenation into `Criteria` (AC-T11).

IT covers: cascade ordering, cutoff semantics, empty-result-set, per-event metadata, structured log line, recurring-job registration. Cases below.
  - **Cascade + AC-17b survival:** seed two owned projects: one with `deletedAt = now - 8d` (>7d), one with `deletedAt = now - 1d` (<7d). Seed matching `events` for both projects (`project_created`, `project_soft_deleted`) — capture the seeded events' timestamps.
  - Inject the bean and call the job method directly (no scheduler trigger needed in test — JobRunr distributed-lock infra is irrelevant to ordering correctness).
  - Assert the >7d project AND its prior events are gone; <7d project + events untouched.
  - Assert the `events` collection contains exactly one `project_hard_deleted` row for the deleted project, with `metadata.projectId == deletedId`, `metadata.name == deletedName`, `userId == ownerId` — this is the AC-17b survival assertion.
  - **Ordering proof for AC-17b:** assert the surviving `project_hard_deleted` event's `timestamp` is strictly greater than the timestamps of the seeded `project_created` and `project_soft_deleted` events — proves the synchronous-save chain (Option A/B) ran AFTER the events sweep, not before it.

**Why no unit test:** the existing codebase's job-test pattern (see `HardDeleteJobTest`) is IT-only despite the `Test` suffix. There is no precedent Mockito unit test for jobs to copy. Replicating the cascade-ordering / cutoff-semantics / event-metadata / log-line / recurring-registration assertions in mocks would duplicate the IT for no incremental signal — Mockito `InOrder` proves nothing about reactive timing, which is the actual failure mode (see "Ordering hazard"). All behavior is covered at IT level.

**Dependencies:**
- Task 1 must be done first (provides `Project` entity, `ProjectRepository` with `findByDeletedAtBefore`). The frontmatter `depends_on: [1]` enforces this.
- No new packages — `jobrunr-spring-boot-3-starter`, `spring-boot-starter-data-mongodb-reactive`, and `spring-boot-test` are already on the classpath.

**Edge cases:**
- **Empty result set on a given day:** finder returns empty `Flux`; job MUST still emit the structured INFO log with `deletedCount=0 eventsRemovedCount=0`. Operations rely on this for liveness signal (AC-17c). Do NOT short-circuit before logging.
- **Cascade interleaving:** if step 1 (events sweep) succeeds but step 3 (project removal) fails, the system is left with active project rows that have no audit history. This task does NOT need transactional all-or-nothing semantics (no MongoDB cross-collection transactions configured in this codebase) — daily idempotency means the next run re-attempts cleanup. Document this trade-off as a code comment near the cascade so future readers understand it's intentional.
- **Race vs. user-driven `Restore` (Risk R4):** the cron's `findByDeletedAtBefore` may capture a project that the user is concurrently restoring. JobRunr's distributed lock prevents double-execution but does NOT serialize against HTTP traffic. Out of scope here — frontend handles the resulting 404 via the standard stale-state flow (Scenario 6 in tech-spec).
- **`metadata.projectId` field path:** `Event` stores metadata as `Map<String, Object>` so the BSON path is literally `metadata.projectId` (no nesting wrappers). The Mongo query is `where("metadata.projectId").in(stringIds)` with typed `List<String>`.
- **Cron-slot collision with `HardDeleteJob`:** both jobs are `0 3 * * *`. JobRunr serializes recurring runs internally — no extra coordination needed. Documented as Risk R5 in tech-spec.
- **`+1ns` cutoff:** matches `HardDeleteJob` (line 40). Without it, a project soft-deleted exactly 7d ago to the second survives one extra day because the repository finder is strict-`<`.
- **No HTTP exceptions from this task.** Task 4's cron path is internal — it MUST NOT throw `AppException.notFound(...)` / `AppException.unprocessableEntity(...)` / any HTTP-shaped exception. Those helpers belong to Task 1's HTTP controllers (`Restore`, `Delete`, etc.) and are scoped to user-driven flows. The cron only emits `project_hard_deleted` events into the `events` collection; it does NOT participate in the 404/422 contract. If the finder returns nothing, log and return — never throw.

**Implementation hints:**
- Pattern-match on `HardDeleteJob` as closely as possible: same constructor-injection style, same `Logger log = LoggerFactory.getLogger(...)` declaration, same `Instant cutoff = Instant.now().minus(...).plusNanos(1)` shape. Reviewers will check parity.
- Capture `runDurationMs` via `long t0 = System.currentTimeMillis()` at method entry, compute at log time. Avoid `System.nanoTime()` here — millisecond resolution is enough for daily-cron observability and matches the field name.
- For the INFO log line, prefer one structured call over multiple. Example shape (NOT pseudocode-as-spec, just structural guidance — the user-spec gives an example: `INFO ProjectHardDeleteJob - run completed: deletedCount=0 eventsRemovedCount=0 runDurationMs=12`): `log.info("ProjectHardDeleteJob - run completed: deletedCount={} eventsRemovedCount={} runDurationMs={}", ...)`.
- For `template.remove`, the return type is `Mono<DeleteResult>`. `.block()` is fine — this code runs on a JobRunr worker thread, not on a Reactor scheduler. `DeleteResult.getDeletedCount()` gives `eventsRemovedCount` for the log.
- For `EventService.logEvent`, signature is `(String userId, String eventType, String ipAddress, String userAgent, Map<String, Object> metadata)`. Cron-emitted events have no IP/UA — pass `null` for both.
- `RecurringJob` API: `org.jobrunr.jobs.RecurringJob`. Use `getId()` and `getScheduleExpression()` on each entry returned from `storageProvider.getRecurringJobs()`. Autowire `org.jobrunr.storage.StorageProvider` for this — `getRecurringJobs()` lives on `StorageProvider`, NOT on `JobScheduler` (the tech-spec wording on line 350 is wrong on that detail; use `StorageProvider`).
- For the IT `OutputCaptureExtension` import: `org.springframework.boot.test.system.OutputCaptureExtension` and `org.springframework.boot.test.system.CapturedOutput`. Method signature: `void test(CapturedOutput output) { ... assertThat(output.getOut()).contains("deletedCount=0 eventsRemovedCount=0"); }`.
