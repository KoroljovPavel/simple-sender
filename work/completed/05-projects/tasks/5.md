# Task 5: Frontend ProjectSelector component + 404 interceptor wiring in useApi

## Required Skills

Before starting the task, load:
- `/skill:code-writing` — [skills/code-writing/SKILL.md](../../../.claude/skills/code-writing/SKILL.md)

## Description

Build the topbar `ProjectSelector` dropdown over the Pinia `projects` store created in Task 2, and wire a path-scoped 404 interceptor into `composables/useApi.ts` so a stale `currentProjectId` (cron hard-deleted, foreign-tab soft-deleted, restore lost) self-heals into a clean state on the next single-resource hit.

The selector is the user's primary navigation between projects: it must list active projects sorted `createdAt desc`, expose `+ Create new project` (disabled with i18n tooltip when active count `>= 5` per AC-30), and surface a `Project settings` link only when `currentProject != null`. The 404 interceptor (Decision 11, AC-24) must match strictly `^/api/v1/projects/[^/]+$` AND extracted ID must equal `projectsStore.currentProjectId` — sub-paths like `/api/v1/projects/{id}/bots` and unrelated 404s (e.g. `/api/profile/...`) MUST pass through untouched, since future epics own their own 404 semantics.

This task does NOT inject `<ProjectSelector />` into `layouts/default.vue` (Task 9 owns layout integration) and does NOT build any list/create/settings page (Tasks 6-8). It delivers a self-contained component + the cross-cutting `useApi` change + unit tests.

## What to do

1. Create `frontend/components/ProjectSelector.vue`:
   - `<script setup lang="ts">` with `useProjectsStore()` (Pinia), `useI18n()`, `useLocalePath()`.
   - Template: a button trigger showing `currentProject?.name` (or an empty-state label when `currentProject == null`); a dropdown panel listing `projects` sorted `createdAt desc` (use a `computed` that returns a sorted shallow copy — never mutate the store array).
   - Each list item: clicking calls `projectsStore.selectProject(id)` and closes the dropdown.
   - `+ Create new project` action at the bottom: `<NuxtLinkLocale to="/projects/new">`; when `projects.length >= 5` render it as visually disabled (no navigation) with the i18n tooltip `projects.create.limitReachedTooltip` (per AC-30).
   - `Project settings` action: visible ONLY when `currentProject != null`, links via `<NuxtLinkLocale :to="...">` to `/projects/${currentProject.id}/settings`.
   - Open/close state via local `ref`; close on outside click and on item selection. ARIA: trigger button uses `aria-haspopup="menu"` and `aria-expanded` bound to the open ref; the panel uses `role="menu"` and each interactive list item uses `role="menuitem"`. There is NO existing `role=menu` dropdown in this codebase — `LangSwitcher.vue` is a flat row of buttons (no popover) and `pages/profile.vue` only uses `role="dialog"` for its delete-account modal. Build the menu pattern fresh, following the standard ARIA Authoring Practices Guide for menu buttons; consult Context7 (`/w3c/aria-practices`) if uncertain.
   - Plain Tailwind divs (no shadcn-vue scaffolding — see tech-spec Dependencies). Reuse the inline-banner / button visual language already established in `pages/dashboard.vue` and `pages/profile.vue` (rounded borders, `text-sm`, hover states).
   - `data-test="project-selector-trigger"`, `data-test="project-selector-item-${id}"`, `data-test="project-selector-create"`, `data-test="project-selector-settings"` for tests.

2. Extend `frontend/composables/useApi.ts`:
   - Add an `onResponseError` hook to the `$fetch.create({...})` config (it currently has only `onRequest`).
   - Refactor for testability: extract the body of the `onResponseError` callback into a named exported function `handleApiResponseError(ctx)` (same module). The `onResponseError` config option becomes a one-line forwarder `onResponseError: (ctx) => handleApiResponseError(ctx)`. The unit spec (file 4 below) imports `handleApiResponseError` directly and asserts its side effects without spinning up `$fetch` or mocking the config object. This is the recommended approach (it does not widen the public composable surface in any meaningful way — `useApi()` still returns the same `$fetch` instance — and the helper is a pure function over `{ request, response }`).
   - Inside `handleApiResponseError`, read `response.status` (skip if not 404) and the request path. The path comes from the `request` param — normalize: when it is a `URL` or full URL string, take `pathname`; when it is a relative string already starting with `/`, use it as-is. Strip query string before regex check.
   - Apply regex `/^\/api\/v1\/projects\/[^/]+$/` against the path. If it matches, extract the captured ID and compare against `projectsStore.currentProjectId`. If equal → call `projectsStore.handleStaleCurrent()` and set the projects store's `pendingBannerKey` to `'errors.projects.unavailable'` (see "Status surface" below). Otherwise let the error propagate unchanged.
   - Pinia store access: import via `useProjectsStore` from `~/stores/projects`. Use lazy access (call `useProjectsStore()` inside the helper) so the composable does not eagerly require the store at SSR boot.
   - Status surface (NOT a toast): the codebase has no `useToast()` composable and no toast plugin — the existing convention (`pages/profile.vue`, `pages/dashboard.vue`, `pages/auth/*.vue`) is inline-banner divs driven by component-local refs. Since the interceptor fires from a cross-cutting layer, it cannot reach into a page's local ref. Pattern: the projects store (Task 2) owns a `pendingBannerKey: Ref<string | null>` slot; the layout/host (Task 9) renders a banner div bound to it (similar shape to `data-test="pending-banner"` in `pages/dashboard.vue`) and clears the key on dismiss/route change. The interceptor only writes the i18n key into that slot. Do NOT invent a `useToast()` helper. If Task 2's store does not yet expose `pendingBannerKey`, surface this as a blocker in the working report and propose adding it to Task 2 (one ref + setter) — do not paper over the gap with an ad-hoc plugin. Document the chosen surface in decisions.md when implementing.
   - Do NOT swallow the error: the helper performs the side effect but the `onResponseError` hook must let the original 404 propagate so callers' `.catch` blocks behave consistently. (No error suppression.)

3. Create `frontend/tests/components/ProjectSelector.spec.ts`:
   - Mock `useProjectsStore` via `mockNuxtImport` (mirror `LangSwitcher.spec.ts` shape: hoist `vi.fn()` spies, declare module-level `ref`s for `projects`, `currentProjectId`, `currentProject`, plus `selectProject` and `handleStaleCurrent` spies).
   - Tests: items sorted `createdAt desc`; clicking an item calls `selectProject` with that id and closes the dropdown; `+ Create new project` is enabled when `projects.length < 5` and rendered as disabled (no navigation, tooltip key matches `projects.create.limitReachedTooltip`) when `length >= 5`; `Project settings` link is hidden when `currentProject == null` and visible with correct href when set.

4. Create `frontend/tests/composables/useApi-404-interceptor.spec.ts`:
   - Four cases (per Decision 11 / AC-24): (a) 404 from `/api/v1/projects/{currentProjectId}` → calls `handleStaleCurrent()` once AND sets `projectsStore.pendingBannerKey = 'errors.projects.unavailable'`; (b) 404 from `/api/v1/projects/{otherId}` → neither side effect fires (other ID); (c) 404 from sub-path `/api/v1/projects/{currentProjectId}/anything` → neither side effect fires (sub-path); (d) 404 from unrelated path (e.g. `/api/profile`) → neither side effect fires.
   - Drive the test by importing `handleApiResponseError` directly from `~/composables/useApi` and invoking it with a hand-rolled context object `{ request, response, options }` — no `$fetch` instance, no `mockNuxtImport` of `useApi`, no network stubs. Mock `useProjectsStore` via `mockNuxtImport` (same idiom as the component spec): module-level refs for `currentProjectId` and `pendingBannerKey`, and a `handleStaleCurrent` spy. Cover both relative-path requests (string starting with `/`) and `URL` instances in at least one case so the path-normalization branch is exercised.
   - Also assert non-suppression: the helper must not return a value that masks the rejection — calling it does not turn the 404 into a resolved promise. (Concretely: the wrapper `onResponseError: (ctx) => handleApiResponseError(ctx)` returns `void`, which is the documented "let the error propagate" signal in ofetch.)

**Dependencies:**

- No new npm packages; reuse `vee-validate` is NOT needed here (no form), `pinia`/`vue`/`@nuxt/test-utils` already present.

**Edge cases:**

- `currentProjectId` set, but the matching project is missing from `projects[]` (e.g. mid-fetch race): `currentProject` computed returns `null` → settings link hidden, trigger button shows the empty-state label. Do NOT throw.
- `projects.length === 5` exactly: button disabled. `=== 4`: enabled. Off-by-one would break AC-30 — covered by the spec test.
- 404 with no body, with text body, and with JSON body — interceptor must work in all three (it inspects `response.status` and the request path only; body is irrelevant).
- Request URL forms passed by `$fetch`: relative path string (`/api/v1/projects/abc`), absolute URL string (`http://localhost:8080/api/v1/projects/abc`), `URL` instance, with/without query string. Normalize before regex.
- SSR: `useApi` runs server-side too. The interceptor MUST be SSR-safe — `useProjectsStore()` is Pinia (SSR-OK), and writing to `pendingBannerKey` is just a ref assignment so it works on both server and client. No `import.meta.client` gate is needed (we are not touching `window`/`document` from the helper). The host that renders the banner (Task 9) is responsible for any client-only display logic.
- Race: an in-flight request to the now-stale ID can resolve AFTER the user has already manually switched projects. The interceptor STILL clears `currentProjectId` only if the response path's ID equals the CURRENT `currentProjectId` — but if the user has already switched away, the IDs do NOT match and the interceptor correctly leaves state alone. Document this in a code comment so future readers don't "fix" it.

**Implementation hints:**

- For outside-click close: a single document-level `mousedown` listener registered in `onMounted`, removed in `onBeforeUnmount`. Compare `event.target` against the panel ref via `panelRef.value?.contains(event.target as Node)`.
- For "disabled link with tooltip": render a `<span aria-disabled="true" :title="t('projects.create.limitReachedTooltip')" data-test="project-selector-create">` instead of a `<NuxtLinkLocale>` when at limit. Avoid using a real `<a>` with `pointer-events: none` — keyboard nav still reaches it.
- For the regex: anchor to start AND end (`^...$`) with `[^/]+` for the ID — exactly one path segment after `/projects/`. Do NOT use `.*` or omit anchors (false positives for sub-paths).
- For testability of the interceptor (recommended approach (a) per the test-reviewer finding): export `handleApiResponseError(ctx)` as a top-level named function from `useApi.ts`, then wire `onResponseError: (ctx) => handleApiResponseError(ctx)` in the config. Trade-off: this widens the module's named exports by exactly one symbol, but the composable's runtime surface (`useApi()` returning a `$fetch` instance) is unchanged, and consumers have no reason to import the helper. The alternative — stubbing `$fetch` and asserting through the network layer — requires non-obvious mocking because the `$fetch.create` config object is not exported and ofetch's interceptor invocation is internal; that path was rejected.
- For the status surface: there is no `useToast()` composable in this codebase — verified by reading `frontend/composables/useApiError.ts` (returns a string only) and grepping `frontend/` (zero `useToast`/toast plugin hits outside `node_modules`/types). Use the inline-banner pattern via `projectsStore.pendingBannerKey` (Task 2 store slot). If Task 2 did not add this slot, surface as a blocker rather than introducing a new helper here.
- Lazy-load `useProjectsStore()` inside `handleApiResponseError`: avoids the "Pinia not installed yet" error during early SSR boot. Same pattern as `useNuxtApp()` deferred reads.
