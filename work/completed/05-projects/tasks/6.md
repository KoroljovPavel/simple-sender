# Task 6: Frontend dashboard inline empty-state + /projects/new create form

## Required Skills

Перед выполнением задачи загрузи:
- `/skill:code-writing` — [skills/code-writing/SKILL.md](../../../.claude/skills/code-writing/SKILL.md)

## Description

Це перша «жива» точка дотику нового користувача з фічею Projects: коли в нього 0 проектів, він має побачити inline empty-state одразу на `/dashboard` (без окремої `/onboarding`-сторінки — Decision 13 у tech-spec), а CTA повинен вести на форму створення проекту `/projects/new`. Реалізує user-spec Сценарій 1 (перший проект після реєстрації / логіну з 0 проектами), AC-18, AC-19 (welcome content коли проект уже є), AC-22c частково (timezone dropdown з IANA-списку через `Intl.supportedValuesOf('timeZone')`). Споживає `projectsStore` із Wave 1 (Task 2): через `isLoaded` гейт уникаємо «спалаху» empty-state до завершення першого `fetchAll()`. Форма create — vee-validate + reactive Zod schema (live re-validation при перемиканні локалі — `patterns.md` «Reactive Zod schemas»), сабміт викликає `projectsStore.create(...)`, на успіх редірект на `localePath('/dashboard')` (тоді dashboard уже зрендерить welcome content + topbar selector з новоствореним проектом, який вибрався автоматично через `selectProject` всередині `create` action store).

**Edge cases:**
- `projectsStore.isLoaded === false` під час першого монтування `/dashboard` — НЕ показуємо ні empty-state ні welcome, щоб не блимати. Тест `dashboard_notLoaded_showsNeitherEmptyNorWelcome` фіксує цей контракт.
- Description порожній рядок vs. `null`: фронт нормалізує blank → `null` ДО виклику `create` (контракт із бекендом — Decision 13 неявно через PATCH-семантику AC-22b).
- Timezone, що повертає `Intl.DateTimeFormat().resolvedOptions().timeZone` — у деяких runtime'ах може бути offset-based (наприклад, `"UTC"`, `"GMT"`). Перевір `Intl.supportedValuesOf('timeZone').includes(default)` і якщо немає — fallback на `'UTC'` (який гарантовано в списку). Тест на дефолт перевіряє вибране значення selector'а проти `Intl.DateTimeFormat().resolvedOptions().timeZone` напряму — у тестовому oc середовищі `happy-dom`/Node це валідна IANA-зона.
- При помилці submit (`409`/`422`) користувач лишається на `/projects/new`, `submitError` показується, форма не очищається — даємо людині виправити.
- Хто куди редіректить: `localePath('/dashboard')` під дефолтною локаллю — це `/dashboard`; під `/en` — `/en/dashboard`. Тест мокає `useLocalePath` як identity, тож очікуємо `/dashboard`.
- Користувач, який вже має 5 проектів і вручну зайшов на `/projects/new` — submit поверне 422, спрацює toast/inline-error через `useApiError`. Окрема логіка (disable CTA при `length >= 5`) — задача Task 5 (selector) і Task 7 (`/projects` index), не наша.
- Cross-tab: інша вкладка з `/dashboard` НЕ дізнається про створений проект автоматично — це фіче (Constraint user-spec); навмисно НЕ слухаємо `storage` events.

**Implementation hints:**
- Дзеркаль `pages/auth/register.vue` для скелетону `/projects/new`: однакова структура імпортів, форми, submit-handler-а, рендер inline errors і submitError-блоку. Це знизить cost ревью і ризик дрейфу.
- Для тесту empty-state-CTA лінку: знайти елемент за `data-test="dashboard-empty-state-cta"` і перевірити, що його `href` дорівнює `/projects/new` (бо `useLocalePath` мокається як identity passthrough).
- Reactive Zod рятує перемикання локалі під час валідації — НЕ робити `unref()` чи `.value` над `computed`-схемою. patterns.md «Reactive Zod schemas» явно про це попереджає; практичний приклад уже є в `register.vue`.
- Description-blank → null: нормалізацію (whitespace-only → `null`) роби у submit-handler-і ДО виклику store, щоб контракт із бекендом тримався чистим (бекенд також нормалізує blank → null, але фронт-нормалізація ще й гарантує, що PATCH-семантика AC-22b не плутатиме «прибрав опис» з «не змінював»).
- `useApiError(e, 'projects.create')` — pattern `errors.projects.create.{400|409|422|generic}`. Ключі мають бути додані Wave 1; якщо чогось бракує — `check-locales.mjs` підсвітить.
- Якщо `projectsStore.create` повертає `Promise<Project>` і всередині робить `selectProject(newId)` — після `await create()` topbar selector уже знає новий currentProjectId, повторно встановлювати в `/projects/new` не потрібно.
- Для тест-сетапу `mountSuspended` + `mockNuxtImport` — pattern уже є у `tests/pages/dashboard.spec.ts` і `tests/pages/auth/*.spec.ts`. Поглянь у них перш ніж винаходити свій.
- Не ламай контракт `AC-T6`: ніяких `localStorage` у `dashboard.vue`. Усе через store, який сам гейтить `import.meta.client`.
