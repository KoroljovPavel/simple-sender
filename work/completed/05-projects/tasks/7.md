## Description

Build the user-facing `/projects` list page that consolidates active and soft-deleted projects in one place. This page is where users review what they own, jump into a project's settings, create a new one (subject to the 5-active hard cap), and — most importantly — recover projects they soft-deleted within the last 7 days before the JobRunr cron permanently removes them.

The page reads from the Pinia `projectsStore` produced in Task 2 and Task 5. Active projects come from `projectsStore.projects` (the default `GET /api/v1/projects` response, sorted `createdAt desc`). Soft-deleted rows come from a separate fetch with `?include_deleted=true` so we can show the "Recently deleted" section conditionally — only when at least one soft-deleted row exists. Days-remaining for each soft-deleted row is computed client-side from `deletedAt + 7d`, not on the backend (Decision: keep the response shape minimal; the UI does the math).

Restore is the central interaction: clicking the per-row Restore button calls `projectsStore.restore(id)`, then surfaces one of three outcomes derived from the response:
1. **Success** — row moves to Active.
2. **422 `project_limit_reached`** — user has 5 active already; message tells them to delete one first.
3. **Informational `renamedDueToConflict`** — the server appended `" (restored)"` to the name because an active project already used the original name (AC-14b). Detected client-side by comparing the response `name` with the pre-request name remembered in component state — there is no extra HTTP field for this signal.

**Deviation from tech-spec wording (toasts → inline banners):** the tech-spec describes these outcomes as "toasts", but the codebase has no toast composable, library, or shared helper today (verified — `frontend/pages/profile.vue` and other pages render inline `<p>`/banner status messages instead). To stay consistent with what already exists and the "Functionality over aesthetics on MVP" UX guideline, this task implements the three outcomes as an inline auto-dismissing banner at the top of the "Recently deleted" section, NOT as a toast popover. This deviation aligns with the same approach taken in Task 5 and must be recorded in `decisions.md` on completion so future tasks (or a real toast library) can revisit if needed.

A top-of-page "+ Create new project" button navigates to `/projects/new` (built in Task 6). When `projectsStore.projects.length >= 5`, the button is visually disabled and exposes an i18n tooltip explaining the 5-active limit and how to free a slot (AC-30).

This task is UI-only, no backend changes. It composes existing primitives (`projectsStore`, `useApiError`, `useLocalePath`, `<NuxtLinkLocale>`, vee-validate not needed here — there is no form). All visible strings go through `t('key')` and live in the `projects.*` and `errors.projects.*` namespaces already populated by Task 2.

## What to do

1. Create `frontend/pages/projects/index.vue`:
   - Set `definePageMeta({ layout: 'default' })` so the topbar/sidebar from Task 9 wraps the page.
   - On mount, ensure the store has data: call `projectsStore.fetchAll()` if `!isLoaded`, AND issue a separate fetch for soft-deleted rows via `useApi()('/api/v1/projects', { query: { include_deleted: true } })` to populate a local `softDeletedProjects` ref (the store today only tracks active; we keep deleted as page-local state to avoid bloating the store contract).
   - Render an h1 page title (`projects.list.title`).
   - Render a top-of-page "+ Create new project" button: navigates via `localePath('/projects/new')`. Visually disabled (`disabled` attribute + `aria-disabled="true"` + opacity styling) when `projectsStore.projects.length >= 5`; the disabled state shows an i18n tooltip via `title` attribute keyed to `projects.create.limitReachedTooltip`.
   - Render the **Active** section (`<section data-test="active-section">`): heading from `projects.list.activeHeading`; one row/card per project from `projectsStore.projects` (already sorted `createdAt desc` by the backend). Each row shows project name, optional description, timezone, and a `<NuxtLinkLocale>` to `/projects/${project.id}/settings`. Empty active list still renders the section with an empty-state hint (`projects.list.emptyActive`) — but this is rare; new users land here only after creating at least one project.
   - Render the **Recently deleted** section (`<section data-test="recently-deleted-section">`) **only when** `softDeletedProjects.length > 0`. Heading from `projects.list.recentlyDeletedHeading`. Each row shows project name, days remaining (computed `Math.max(0, Math.ceil((deletedAt + 7d - now) / 1day))` and rendered via `projects.list.daysRemaining` with a `{count}` interpolation), and a Restore button.
2. Wire the Restore action:
   - At the top of `<script setup>`, instantiate the resolver once: `const apiError = useApiError()`. The composable returns a resolver function — it is NOT called with the error directly; you invoke the returned function as `apiError(err, contextKey)` per row event (verified against `frontend/composables/useApiError.ts`).
   - Click handler captures `preRequestName = project.name`, calls `await projectsStore.restore(project.id)`.
   - On success: read the returned project from the store action; if `response.name !== preRequestName` (i.e. server appended `" (restored)"`), fire an informational inline banner with text resolved from i18n key `errors.projects.restore.renamedDueToConflict`. Otherwise fire a success banner (`projects.restore.success`). Then remove the row from `softDeletedProjects` (refetch or splice locally) so the row visibly moves out of the section. The store will pick up the project as active on next read.
   - On error: call `apiError(err, 'projects.restore')` — the resolver internally extracts status and walks `errors.projects.restore.{status}` → `errors.projects.restore.generic` → `errors.generic`. For the 422 `project_limit_reached` case Task 2 supplies the `errors.projects.restore.422` key so the resolver returns the limit-reached message; any other status falls through to the generic entries. Show the resolved string in the inline banner; the row stays in "Recently deleted".
3. Banner plumbing (deviation from tech-spec wording — see Description): there is no toast composable in the repo (verified — `pages/profile.vue` uses inline `<p>` status messages, not toasts). Implement the three restore outcomes as an inline auto-dismissing banner: keep a `banner` ref shape `{ kind: 'success' | 'error' | 'info', message: string } | null` rendered as a top-of-section element that auto-dismisses after 4s via `setTimeout`. This matches the "Functionality over aesthetics on MVP" UX guideline and the existing inline-status approach in `profile.vue`. The element has a `data-test="restore-toast"` attribute (kept as `restore-toast` for spec parity even though it renders as a banner).
4. Add `data-test` selectors on every interactive element so the spec can drive them deterministically: `data-test="create-project-button"`, `data-test="active-row-{id}"`, `data-test="deleted-row-{id}"`, `data-test="restore-button-{id}"`, `data-test="days-remaining-{id}"`, `data-test="restore-toast"`.
5. Create `frontend/tests/pages/projects/index.spec.ts` with the unit specs listed in TDD Anchor below. Mock `useApi` via `mockNuxtImport` following the existing pattern in `tests/pages/profile.spec.ts` (verified — that spec defines `apiMock = vi.fn()` via `vi.hoisted()` and exposes it through `mockNuxtImport('useApi', () => () => apiMock)`; `dashboard.spec.ts` does NOT mock `useApi` and is not a useful reference for this task). Mock `projectsStore` via `mockNuxtImport('useProjectsStore', ...)` exposing the actions this page calls (`fetchAll`, `restore`) plus reactive state (`projects`, `isLoaded`). Use `mountSuspended` + `settle()` from `tests/helpers/settle.ts` for async hydration.

**Edge cases:**
- All projects active and 0 deleted → "Recently deleted" section absent.
- All deleted (active list empty) → render Active section heading with `projects.list.emptyActive` empty-state text; "Recently deleted" still present.
- `softDeletedProjects.length === 0` after restore → section disappears reactively (driven by reactive ref length).
- `deletedAt + 7d - now <= 0` (boundary case where the cron is about to run) → days-remaining shows `0`; row is still rendered with Restore button — backend is the source of truth for whether restore is still possible (cron may run mid-session and produce 404, handled by the 404 interceptor + a toast).
- Concurrent restore clicks (double-click) → the Restore button must disable itself while the request is in flight (use a per-row `restoringIds: Set<string>` ref); on resolve/reject, remove from the set.
- 5-active limit reached AFTER soft-deleted rows exist (user has 5 active + 1 deleted): Restore button is still rendered (the user can try) but the 422 toast surfaces the limit message; row stays in the deleted section.
- SSR safety: the component's `<script setup>` runs on both server and client. Any direct `localStorage` access is forbidden here (AC-T6) — the store handles persistence under `import.meta.client`. Days-remaining computation can run in SSR (use `Date.now()` — both sides agree on the wall clock to second precision; minor hydration mismatch is acceptable for this human-readable countdown).

**Implementation hints (NOT pseudocode — guidance only):**
- Sort by `createdAt desc` for active is already done by the backend (`findByOwnerIdAndDeletedAtIsNullOrderByCreatedAtDesc`). For soft-deleted rows, the backend returns active + deleted mixed in `?include_deleted=true`; filter client-side via `.filter(p => p.deletedAt !== null)` and consider sorting by `deletedAt desc` so the most recently deleted appears first.
- `useApiError` returns an empty string when no key resolves — guard the toast text against empty string before showing it.
- Use `<NuxtLinkLocale>` for navigation, NOT `<a href>` or `<router-link>` (locale-aware). For programmatic navigation, wrap with `localePath()` (per `patterns.md` "Frontend i18n").
- For the disabled-button tooltip, the simplest cross-browser approach is the native `title` attribute. The shadcn-vue dependency IS installed (verified — `package.json` lists `shadcn-vue` at line 35), but the `frontend/components/ui/` scaffolding is not generated yet in this repo, so no `Tooltip` component is importable today. Render plain HTML elements with Tailwind classes and the `title` attribute; do NOT introduce shadcn-vue scaffolding as part of this task — that is a separate infra concern. This is acceptable per "Functionality over aesthetics on MVP".
- Render the page itself as plain HTML elements styled with Tailwind utility classes (the project uses Tailwind already). No shadcn-vue `Card`/`Button` imports — those would require running the shadcn-vue CLI to scaffold `components/ui/*`, which is out of scope here.
- The vitest spec must use the same `mockNuxtImport('useLocalePath', () => () => (path: string) => path)` identity-passthrough that `profile.spec.ts` uses. For `useApi`, follow `profile.spec.ts` exactly: declare `const { apiMock } = vi.hoisted(() => ({ apiMock: vi.fn() }))` at module top, then `mockNuxtImport('useApi', () => () => apiMock)`. This is the only working pattern in the repo today (per `patterns.md` "AC18 page-spec exception" — though that exception is a list of currently-authorized files; this NEW spec is allowed to follow the same pattern as part of this feature's setup).
- `vi.useFakeTimers({ now: new Date('2026-05-09T12:00:00Z').getTime() })` to make the days-remaining computation deterministic in specs.
