# Task 8: Frontend project settings page (rename, description, timezone, danger-zone delete)

## Required Skills

Перед выполнением задачи загрузи:
- `/skill:code-writing` — [skills/code-writing/SKILL.md](../../../.claude/skills/code-writing/SKILL.md)

## Description

Створюємо `pages/projects/[projectId]/settings.vue` — сторінку налаштувань поточного проекту. Це третя UI-задача Wave 3 в епіку 05-projects: вона завершує CRUD-петлю поверх Pinia-стора (`stores/projects.ts` з Task 2) і `ProjectSelector` (Task 5), даючи юзеру змогу перейменовувати проект, оновлювати опис/таймзону та безповоротно ініціювати soft-delete через danger-zone модал з type-the-name підтвердженням.

Сторінка реалізує дві секції:
1. **General** — vee-validate форма (name 3-50, description ≤200, timezone IANA dropdown). Submit викликає `projectsStore.update(id, partial)` (PATCH `/api/v1/projects/{id}`); 200 одразу віддзеркалюється в `ProjectSelector` topbar (бо стор reactive). Empty `description` відправляється як literal blank рядок (`''`) — бекенд (`@Size(min=0)` + `isBlank` перевірка) нормалізує його в `null` у Mongo (AC-22b). Empty/blank `timezone` → не відправляємо це поле зовсім (no-op semantics — AC-22c, tech-spec PATCH semantics в розділі Data Models).
2. **Danger zone** — кнопка `Delete project` відкриває модал з required type-the-name input. Кнопка `Delete` задизейблена доти, доки computed property не порівняє trim'нутий ввід з `project.name` точно (case-sensitive). Confirm → `projectsStore.softDelete(id)` (DELETE) → редірект (`/dashboard` якщо інших активних більше немає, інакше `/projects`) + toast.

Сторінка свідомо повторює UX-патерни вже існуючої `pages/profile.vue` (Delete account section): `role="dialog"`, `aria-modal`, `aria-labelledby`, disabled-state під час submit, `data-test` маркери для vitest. shadcn-vue компоненти не використовуємо — plain Tailwind (per tech-spec Dependencies / patterns.md "Functionality over aesthetics on MVP").

**PATCH-vs-POST description-blank asymmetry (intentional):** Task 6 (POST `/create`) нормалізує порожній `description` у `null` на клієнті перед відправкою; ця задача (PATCH `/update`) свідомо відправляє literal `''` і покладається на нормалізацію бекенду. Це не баг — це різні семантики: POST «створи запис без опису» vs PATCH «очисти існуючий опис» (де ми хочемо явно сигналізувати delta). Зафіксувати цю асиметрію в `decisions.md` під час post-completion (щоб ревьюер не флагав як неузгодженість) — див. Edge cases і Post-completion checklist.

## What to do

1. **Створити сторінку `frontend/pages/projects/[projectId]/settings.vue`** з `definePageMeta({ layout: 'default' })`, що:
   - Підвантажує `projectsStore.fetchAll()` якщо `!isLoaded` (lazy hydration per Decision 9), потім обчислює `project = projectsStore.projects.find(p => p.id === route.params.projectId)`. Якщо `project` не знайдений серед активних — рендерить inline fallback (помилковий стан з посиланням на `/projects`), без програмного редіректу.
   - Рендерить заголовок `t('projects.settings.title')` + дві секції.

2. **General section (vee-validate):**
   - Reactive Zod schema у `computed()` (per patterns.md "Reactive Zod schemas") — name `min(3).max(50)`, description `max(200).optional()`, timezone optional (валідація бекенду). Локалізовані повідомлення через `t()`.
   - Initial values з `project` (name, description ?? '', timezone).
   - `timezone` dropdown — `<select>` із options `Intl.supportedValuesOf('timeZone')`.
   - На submit будуємо partial-payload: `name` тільки якщо змінилось і не порожнє; `description` — якщо змінилось (порожній рядок зберігаємо як `''` → бекенд переведе в `null`); `timezone` — лише якщо обрано непорожнє значення, що відрізняється від поточного.
   - Створюємо handler один раз на верхньому рівні `<script setup>` через `const apiError = useApiError()` (фабрика, lifecycle для `useI18n()`). Викликаємо `projectsStore.update(project.id, partial)`. На 200 — inline-success повідомлення `t('projects.settings.saved')`. На 400/409/422/мережа — `apiError(err, 'projects.update')` повертає текст помилки для inline-render.

3. **Danger zone:**
   - Секція з рамкою `border-red-200`, заголовком `t('projects.settings.dangerZone.title')`, кнопкою `t('projects.settings.dangerZone.deleteOpen')`.
   - Клік відкриває модал `data-test="delete-project-modal"`. Модал має `role="dialog"`, `aria-modal="true"`, `aria-labelledby` на title.
   - Усередині модалу: підказка `t('errors.projects.delete.confirmTypeName', { name: project.name })` + `<input>` для type-the-name (autofocus, `data-test="delete-project-name-input"`).
   - Computed property порівнює trim'нутий ввід з `project.name` точно (case-sensitive); кнопка `Delete` залишається disabled, доки порівняння повертає `false`. Trailing/leading whitespace дозволений (його зрізає `.trim()`), але різниця в регістрі — НІ.
   - Кнопка `Delete` задизейблена також при `isDeleting === true`. Кнопка `Cancel` закриває модал (handler ігнорує клік, якщо `isDeleting === true`).
   - На confirm: `projectsStore.softDelete(project.id)`. Після успіху — обчислити redirect: `/dashboard` якщо у сторі більше немає активних проектів (`projects.length === 0`, де `projects` — computed-список лише активних), інакше `/projects`. Потім `await navigateTo(localePath(redirect))`.

4. **Створити vitest-spec `frontend/tests/pages/projects/settings.spec.ts`** з мокованими `useProjectsStore`, `navigateTo`, `useLocalePath`, `useRoute`. Mirror стилю `frontend/tests/pages/profile.spec.ts` (vi.hoisted, mockNuxtImport, `mountSuspended`, `settle()`-helper з `tests/helpers/settle.ts`). Покриває кейси з TDD Anchor нижче.

## Acceptance Criteria

- [ ] Сторінка існує за роутом `/projects/{projectId}/settings`, доступна тільки авторизованому юзеру (`auth.global.ts` middleware успадкований).
- [ ] **AC-22a:** Зміна name → submit → `projectsStore.update` → topbar selector показує нове ім'я без перезавантаження сторінки (Pinia reactivity).
- [ ] **AC-22b:** Опис: текстове поле (0-200), submit пустий → опис очищається у store і у відповіді бекенду (зберігається як `null` у Mongo).
- [ ] **AC-22c:** Timezone dropdown показує IANA-список (`Intl.supportedValuesOf('timeZone')`), submit → PATCH → 200; невалідне значення на бекенді (через прямий API, не через UI) → 400 з message про timezone (UI відображає через handler з `useApiError()` фабрики).
- [ ] **AC-22d:** Danger zone: модал відкривається по кліку, кнопка Delete задизейблена доти, доки computed-порівняння trim'нутого вводу з `project.name` (case-sensitive) не поверне `true`; після підтвердження — DELETE → 200 → редірект з settings (бо проект тепер soft-deleted).
- [ ] Редірект після soft-delete: `/dashboard` якщо більше немає активних проектів, інакше `/projects`.
- [ ] Помилки PATCH (400 timezone, 409 name conflict, 422 generic, network) показуються через handler з `useApiError()` фабрики, викликаний як `apiError(err, 'projects.update')`.
- [ ] Помилки DELETE (404 stale, 401 expired) показуються через той самий handler, викликаний як `apiError(err, 'projects.delete')`.
- [ ] Усі рядки UI через `t('key')` — жодних літералів англійською/українською у шаблоні. Ключі вже додані в обидва локалі в Task 2; задача НЕ редагує `uk.json` / `en.json`.
- [ ] Vitest spec зелений (`pnpm test -- tests/pages/projects/settings.spec.ts`).

**Edge cases:**
- Юзер відкриває settings проекту, якого немає в `projectsStore.projects` (stale URL, soft-deleted в іншій вкладці): показуємо inline-помилку з `t('errors.projects.unavailable')` + `<NuxtLinkLocale>` на `/projects`. **Не** робимо програмний редірект, бо 404-interceptor (Task 5) уже відловлює `/api/v1/projects/{currentProjectId}` 404 — settings page без поточного проекту просто прозоро показує stale-state.
- Submit без жодних змін у формі: partial = `{}` → НЕ робити PATCH (зекономити RTT і audit-event spam).
- Юзер двічі натискає Save: `isSubmitting` (з `useForm`) задизейблює submit-кнопку.
- Юзер закриває модал під час delete-запиту: `closeModal` ігнорує клік якщо `isDeleting === true` (як у `profile.vue` `closeDeleteModal`).
- Description trimming: `'   '` (тільки пробіли) → відправляємо raw value `'   '`; бекенд за `@Size`/`isBlank` нормалізує в `null` (per tech-spec PATCH semantics в Data Models).
- **PATCH vs POST description-blank асиметрія:** Task 6 (POST `/create`) нормалізує empty description у `null` ще на клієнті; ця задача (PATCH `/update`) свідомо відправляє literal `''` і покладається на серверну нормалізацію. Це навмисний дизайн: POST — «створи без опису», PATCH — «явна delta: очисти існуючий опис». Зафіксувати рішення в `decisions.md` (post-completion) під заголовком на кшталт «PATCH/POST description normalization split», із посиланням на цю задачу і Task 6 — щоб майбутній рев'юер не флагав це як неузгодженість контракту.
- Timezone: значення dropdown завжди валідне (з `Intl.supportedValuesOf`), тому 400 на timezone може прилетіти лише через DevTools-tampering — UI показує `errors.projects.update.400` повідомлення.
- Browser без `Intl.supportedValuesOf('timeZone')` (старий Safari): fallback — показати єдину опцію `Intl.DateTimeFormat().resolvedOptions().timeZone` + `console.warn`.

**Dependencies:**
- Task 2 (Pinia store + types + i18n keys) — store API: `update(id, partial)`, `softDelete(id)`, `projects` (computed list з активними), `currentProject`, `isLoaded`, `fetchAll`.

- Task 6 (dashboard empty-state + new) — пов'язаний UX (редірект після last-project soft-delete на `/dashboard` показує empty-state).

**Implementation hints:**
- `projectsStore.update` і `softDelete` мають бути `async` (повертають `Promise`). Якщо в Task 2 контракті інакше — задокументувати в `decisions.md` як deviation.
