# Task 9: Frontend layout integration + Project Knowledge alignment

## Required Skills

Before starting, load:
- `/skill:code-writing` — [SKILL.md](../../../.claude/skills/code-writing/SKILL.md)

## Description

Wire the `<ProjectSelector />` component (built in Task 5) into the global authenticated shell `frontend/layouts/default.vue`, and add a sidebar `Settings` link that links to the current project's settings page (`/projects/${currentProject.id}/settings`) but is only visible when a project is selected. After this task every authenticated page in the app gains the project selector in the topbar and the project-aware Settings link in the sidebar — making projects a first-class citizen of the global navigation.

In the same PR, align project-knowledge documentation with the new UX (per user-spec AC-31 / tech-spec AC-T10): `references/ux-guidelines.md` line 33 currently says zero-projects empty state is a "full-page onboarding with step-by-step 'Create your first project'", but the implementation chosen in Task 6 is an inline empty-state on `/dashboard`. Update line 33 to reflect that. Line 43 (project selector + `localStorage` persistence) stays as-is — the implementation matches it.

This is the final UI integration task before E2E (Task 10). It does not introduce new domain logic — it only composes existing pieces into the global shell and synchronises documentation.

**Files to read (no edits):**

- `frontend/stores/projects.ts` — Confirm `currentProject` is a `computed` that returns the active `Project` or `null`. Used directly in the sidebar `v-if`.

**Dependencies:**
- Task 5 (must be done before this task — provides `<ProjectSelector />` component).
- Task 2 (provides `useProjectsStore`, the i18n key `layout.sidebar.settings`, and `currentProject` computed). Already done in Wave 1.
- Task 8 (provides the destination page `/projects/[projectId]/settings.vue`). Task 9 may run in parallel with Task 8 inside Wave 3 because they touch disjoint files; the link target works as soon as both are merged.

**Edge cases:**
- `projectsStore.isLoaded === false` on first render (store fetch in flight): `currentProject` is `null` until fetch resolves, so `Settings` simply doesn't render until the store hydrates — no flicker, no broken link.
- `currentProjectId` is set in `localStorage` but the corresponding project was deleted server-side (handled by the 404 interceptor from Task 5): once `handleStaleCurrent()` runs, `currentProject` becomes `null` and the `Settings` link disappears reactively. No special handling needed in the layout.
- LangSwitcher and ProjectSelector both render dropdowns: ensure the topbar flex container does not overflow on narrow viewports. The existing `flex items-center gap-3` should accommodate one extra child; if visual clipping appears at 768px verify with the user, but do NOT introduce new responsive logic in this task (UX guidelines: "Functionality over aesthetics on MVP").
- The `Settings` link must use `NuxtLinkLocale`, not `NuxtLink`, so the `/en/...` locale prefix is preserved (per `patterns.md` Frontend i18n / locale-aware navigation rule).

**Implementation hints:**
- Use the same `t('layout.sidebar.settings')` pattern that `t('layout.dashboard')` and `t('layout.profile')` already use in this file.
- Computing the link target: build the path with `useLocalePath()` if you prefer explicit paths, but `NuxtLinkLocale` already handles locale prefixing — passing `:to="`/projects/${projectsStore.currentProject.id}/settings`"` is sufficient.
- Pinia stores in Nuxt 4 with auto-imports: `const projectsStore = useProjectsStore()` at script top; use `storeToRefs` only if you need destructured reactivity for refs — `currentProject` accessed as `projectsStore.currentProject` in the template stays reactive.
- This is intentionally a small task: no new tests, no new types, no new components. Resist scope creep — the dashboard empty-state is Task 6, the settings page is Task 8, the selector is Task 5.
