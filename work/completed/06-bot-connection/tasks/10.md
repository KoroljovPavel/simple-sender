# Task 10: Code Audit

Перед выполнением задачи загрузи:

## Description

Full-feature code quality audit for the 06-bot-connection epic. Read all source files created or modified during the feature (the union of `Files to modify` across tasks 1–9 plus anything `decisions.md` records as actually changed) and review them holistically for cross-component issues that individual per-task reviews could not see — duplicate resource initialization across newly-introduced Spring beans, shared-resource discipline against the Architecture decisions (TokenEncryptor, TelegramApiClient, WebClient, ReactiveRedisTemplate, BotRepository), architectural consistency between BotController / BotService / BotRepository, AppException usage (correct status + business code, no leaked Telegram description into user-facing messages), reactive-chain correctness (no blocking `block()`, no `.toFuture().get()`, correct `subscribeOn` boundaries for any fire-and-forget side effect), and idiomatic Spring WebFlux patterns (`Mono` chaining over imperative branches, `onErrorMap` over swallowed exceptions, `@Component` discipline, constructor injection, no field-level autowire). The output is a written audit report — no production code is changed by this task; concrete code edits, if needed, are handled in follow-up tasks after the user reads the report.

## What to do

- Enumerate every file touched by tasks 1–9 from `tech-spec.md` (the `Files to modify` sections) and from any `Deviations` entries in `decisions.md`. Build the audit's read-list from that enumeration — do not guess.
- Read each file end-to-end. For backend Java files, also re-read the AppException / GlobalErrorHandler / SecurityConfig that already exist in the project so the audit can compare new code against the established baseline.
- Review across the following dimensions, holistically:
  - Duplicate resource initialization (e.g. two WebClient builders, two `SecureRandom` instances, two retry specs) — call out any case where a single bean would have done.
  - Shared-resources compliance with `architecture.md` and `patterns.md` (TokenEncryptor is a single `@Component`; TelegramApiClient is a single `@Component`; ReactiveRedisTemplate / BotRepository are injected, not re-constructed; no module-private utility duplicates something already in `common/`).
  - Architectural consistency: controller → service → repository layering; no Mongo access from the controller; no Telegram API access outside `TelegramApiClient`; no encryption outside `TokenEncryptor`; `ProjectService.requireOwned` is the first call in every Bot-scoped service method (per `patterns.md`).
  - `AppException` usage: every error path uses the right factory (`notFound` / `conflict(code, msg)` / `unprocessableEntity(code, msg)` / `badRequest` / `internalError` / `badGateway`) with the exact HTTP status and business code mandated by user-spec AC1–AC23 + decisions D1, D5, D7, D8, D17. No Telegram raw `description` reaches user-facing JSON.
  - Reactive-chain correctness: no `block()` / `blockOptional()` / `.toFuture().get()` in production code; fire-and-forget side effects (audit event emission, brute-force counter DEL, compensating deleteWebhook) use the canonical `Mono.fromCallable(...).subscribeOn(Schedulers.boundedElastic()).subscribe(null, log::error)` shape (per `patterns.md` → Auth & Sessions); no swallowed `onErrorResume(e -> Mono.empty())` that hides real failures.
  - Idiomatic Spring WebFlux: constructor injection, `final` fields, `@Component` on stateless services, no `static` mutable state, `Mono.defer` where ordering matters, `Mono.zip` / `flatMap` chains over imperative `.block()` ladders, `Retry.backoff(...).filter(...)` configured exactly as Task 2 specifies.
  - Cross-cutting concerns: log lines never echo the raw bot token (defense beyond `BotTokenLeakTest`); brute-force counter Redis keys follow the `brute:bot-connect:{userId}` shape; audit events use the agreed `bot_connected` / `bot_disconnected` type names; no `bot_test_message_sent` event in 06 (per D7).
- For every finding, record: severity (`critical` / `high` / `medium` / `low`), file + line(s), short description of the problem, suggested fix (one sentence). Group findings by severity in the report.
- If you find zero issues in a dimension, say so explicitly in the report ("Dimension X — OK"). A short, exhaustive audit beats a long one with implicit gaps.
- Write the report to `work/06-bot-connection/logs/working/task-10/code-audit-report.md`. Use plain Markdown — section per dimension, sub-sections per severity, one bullet per finding.

**Scope boundary (intentional, Audit Wave split):**
- Task 10 (this) — code quality, architecture, reactive correctness.
- Task 11 — security (OWASP Top 10, crypto, leak vectors). Do NOT duplicate Task 11 coverage; if you spot something obviously security-flavored, mention it briefly and defer the deep analysis to Task 11.

**Dependencies:**
- Tasks 8 and 9 must be complete (all production code from waves 1–3 exists on disk).
- Wave 4 task — runs in parallel with Task 11 (Security Audit) and Task 12 (Test Audit).

**Edge cases to look for:**
- A class that should be a Spring `@Component` declared with `new` somewhere instead of injected.
- A retry / timeout / WebClient config duplicated across BotService and TelegramApiClient.
- A `Mono.fromRunnable(...)` without explicit `subscribeOn` causing the fire-and-forget to run on the calling event-loop thread.
- An `onErrorMap` that maps a generic `Throwable` and accidentally swallows `DuplicateKeyException` before the per-project / platform-wide branch can see it (D1, D5).
- An AppException factory called with the wrong arity (e.g. `conflict(msg)` instead of `conflict(code, msg)` — note `patterns.md` calls out the 2-arg asymmetry on 422; same discipline applies to 409 in this feature).
- A log statement that interpolates a request body, exception message, or Telegram description field that could carry the raw token.

**Implementation hints (NOT pseudocode — just orientation):**
- Audit is read-only. Open files in groups: crypto → Telegram client → domain → service → controller → DTOs → frontend types → frontend store → frontend page. Group reads make cross-component patterns visible.
- Keep the report's "Findings by Dimension" sections honest — explicit "OK, no findings" entries are valuable evidence that the dimension was actually checked.
- If a finding is ambiguous (could be intentional per a decision in `decisions.md`), check `decisions.md` first and quote the decision number in the suggested-fix note before recommending a change.
