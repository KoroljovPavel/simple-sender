# Task 11: Security Audit

## Required Skills

Перед выполнением задачи загрузи:
- `/skill:security-auditor` — [skills/security-auditor/SKILL.md](../../../.claude/skills/security-auditor/SKILL.md)

## Description

Full-feature security audit of the 06-bot-connection epic. Read all source files created/modified across Waves 1–3 (TokenEncryptor, TelegramApiClient, Bot domain layer, BotService, BotController + DTOs, frontend store/page, i18n, application.properties, .env.example, integration tests) and analyse them holistically against the OWASP Top 10.

The audit is the last line of defence before deploy: per-task `security-auditor` round-1/2 reviewers see one slice each, so cross-cutting and integration-level weaknesses must be caught here. The feature handles a high-value secret (bot token) with at-rest encryption, a webhook secret stored as SHA-256 hash, request DTOs accepting JSON, project-scoped routes vulnerable to IDOR, a Redis-backed rate limiter that fails open, and a compensating `deleteWebhook` code path triggered on persist failure / DuplicateKeyException — each is its own attack surface.

The output is an audit report at `work/06-bot-connection/logs/working/task-11/security-audit-report.md` listing findings by severity (Critical / High / Medium / Low / Info) with file:line anchors, OWASP category, exploit scenario, and a concrete remediation suggestion.

## What to do

1. Read every source file produced by Tasks 1–9 (backend module + frontend page/store + i18n + config) and the matching test files. Build a mental map of data flow: request → controller → service → encryptor → repository → Telegram → event log.
2. Walk OWASP Top 10 (2021) categories against the feature. For each category, decide whether the feature has surface area; if yes, inspect the relevant code paths and record findings.
3. Apply extra scrutiny to the nine focus areas listed in tech-spec Task 11 (verbatim below in Details).
4. For each finding, record: severity, OWASP category, file path + line range, what the issue is, an exploit scenario in 1–2 sentences, and a concrete fix recommendation. Tie each finding to a user-spec AC or a tech-spec Decision/Risk where one applies.
5. Cross-check findings against tech-spec Risks R1–R10 — flag any risk whose stated mitigation is not actually implemented in code.
6. Write the report to `work/06-bot-connection/logs/working/task-11/security-audit-report.md` with the sections specified in Details. If zero findings exist in a severity bucket, state that explicitly — silence is not a clean bill of health.
7. Update `decisions.md` per Post-completion: short summary + link to the report.

## Details

**Output file:** `work/06-bot-connection/logs/working/task-11/security-audit-report.md`

**Report structure (suggested):**
1. Summary — scope, files reviewed, headline verdict.
2. OWASP Top 10 walkthrough — one line per category (A01 Broken Access Control … A10 SSRF) with verdict.
3. Findings by severity — Critical → High → Medium → Low → Info. Each finding: title, OWASP category, file:line, description, exploit, fix, AC/Decision/Risk anchor.
4. Focus-area checklist — explicit pass/fail per the nine items below.
5. Risks-vs-code matrix — for R1..R10 in tech-spec Risks, state whether the stated mitigation is implemented.
6. Deploy recommendation.

**Nine focus areas (verbatim from tech-spec Task 11):**

1. **Token-at-rest encryption** — verify `TokenEncryptor` uses AES-256-GCM with a 12-byte SecureRandom IV per encryption (not a static or counter-based IV), 128-bit GCM tag, fail-fast on key length / hex-decode failure, GCM auth tag is checked on decrypt (Cipher throws on tag mismatch — not silently truncated). Verify the key is read from env (`BOT_TOKEN_ENCRYPTION_KEY`) and never logged.
2. **Webhook secret SHA-256 storage** — verify the plaintext webhook secret is generated with `SecureRandom`, sent to Telegram, hex-encoded SHA-256 hashed, the hash persisted, and the plaintext dropped (never logged, never returned in any response). Verify the hash is stored as hex (per D2).
3. **Mass-assignment in request DTOs** — verify `ConnectBotRequest` accepts only `token` and rejects unknown fields (`@JsonIgnoreProperties(ignoreUnknown = true)` either per-class or via a Jackson default mixin). Verify hostile bodies like `{"token":"...","ownerId":"someone-else"}` cannot poison entity state.
4. **IDOR through `projectId`** — verify every controller endpoint runs `ProjectService.requireOwned(ownerId, projectId, false)` as its first reactive step, that foreign-owned / soft-deleted / malformed projectIds all return 404 (never 403, per AC16), and that no body field can override the URL-derived `projectId`.
5. **Rate-limit bypass** — verify INCR happens on every Connect attempt (not just on failure) so a Connect-then-Disconnect loop cannot bypass the limiter (D14 rationale). Verify the threshold check is BEFORE any Telegram call (`getMe` not invoked when value > 10). Verify TTL is applied only when INCR returns 1 (window-stable). Verify the key shape `brute:bot-connect:{userId}` cannot be poisoned by user input. Verify fail-open on Redis error is intentional (DoS mitigation) and that a WARN log fires on every Redis failure (evidence: Logback `ListAppender` capture in the test suite). **Note:** D14's Micrometer counter expectation is deferred from epic 06 per Task 6's deviation (no Spring Boot Actuator / Micrometer dependency on the project). The audit MUST NOT fail the feature for the missing Micrometer counter; record it as Info / deferred only.
6. **Log-line and event-metadata content** — verify no log call (info, warn, error) takes the raw token, the encrypted ciphertext, the IV, the webhook secret plaintext, or the SHA-256 hash. Verify the `description` scrubber in `TelegramApiClient` actually scrubs token-shaped substrings (`\d{1,20}:[A-Za-z0-9_-]{30,50}` → `[REDACTED_TOKEN]`). Verify `EventService.logEvent` metadata maps for `bot_connected` / `bot_disconnected` contain only `projectId`, `telegramBotId`, `telegramUsername` (Connect) and `projectId`, `telegramBotId`, `webhookDeleted` (Disconnect) — never the token or any token-derived secret. Confirm `BotTokenLeakTest` exists and actually asserts what its name implies.
7. **CSRF inheritance** — verify `SecurityConfig` is NOT modified by this feature, that the existing CSRF protection covers `/api/v1/projects/{projectId}/bot/**`, and that all four endpoints (GET, connect, disconnect, test-message) live under `/api/**` (authenticated). Note: GET is exempt from CSRF by design; the three POSTs must require a CSRF token. Verify nothing accidentally registers a CSRF-exempt matcher for the bot routes.
8. **Cross-project information disclosure on 409** — verify the 409 `bot_already_connected` response body does NOT include the foreign project's name, the foreign owner's email, or the conflicting `telegramBotId`. The message must be generic enough not to confirm whether the conflict is in the requester's projects or a stranger's (R2, D1). Verify the same for the 409 `bot_already_in_project` (less sensitive — it's the requester's own project — but consistency matters).
9. **Compensating-`deleteWebhook` code path** — verify the compensation runs on BOTH (a) generic persist failure and (b) `DuplicateKeyException` from either partial unique index, that it is best-effort (`.onErrorContinue` / equivalent — never rethrows), that its failure is logged at WARN, and that the original error (500 or 409) is still propagated to the user. Verify the same plaintext token used in the `setWebhook` step is what's passed to `deleteWebhook` (no decrypt-from-DB round-trip — the token is already in scope).

**Severity rubric (suggested — calibrate to project):**
- **Critical:** Direct token / secret leak, broken auth/access control with active exploit path, missing encryption, plaintext secret in DB.
- **High:** Auth/access weakness with limited exploit window, missing CSRF on state-changing route, mass-assignment with privilege escalation potential.
- **Medium:** Information disclosure that helps an attacker, fail-open without observability, weak crypto choices, recoverable design smells.
- **Low:** Defense-in-depth gaps, missing hardening on already-hardened endpoints, log-hygiene issues with no real-world data exposure.
- **Info:** Suggestions, future-hardening notes.

**Implementation hints:**
- Use the OWASP Top 10 2021 list verbatim — do not invent categories.
- Cite file paths exactly as committed (relative to repo root) and use line ranges, not single lines, when describing multi-line constructs.
- Prefer concrete exploit scenarios over abstract warnings ("an attacker who controls X can do Y").
- A clean report (zero Critical, zero High) ends with `Deploy recommendation: GO`. Any open Critical → `NO-GO`. Mixed (no Critical, but High open) → `GO-with-fixes` listing the fixes.
- Do NOT modify any source files. This is a read-only audit.
- Do NOT spawn sub-reviewers — Audit Wave tasks have `reviewers: []`.

**Dependencies:** Tasks 8 and 9 must be complete (the full feature must be implemented before the audit runs). The audit reads but does not edit anything.

**Edge cases to look for:**
- A `toString()` override on `Bot` that includes encryptedTokenCiphertext / encryptedTokenIv.
- Pinia devtools state snapshots that retain the just-typed token between actions.
- Vue refs/reactives holding the token after a successful Connect (should clear).
- An exception message that bubbles up containing the token (e.g. `WebClientResponseException.getResponseBodyAsString()` quoted into an error message).
- Test fixtures or `application-test.properties` that hard-code a key value that could leak through CI logs.
- A logged `description` field from a Telegram error response that itself echoes the bot's token.
