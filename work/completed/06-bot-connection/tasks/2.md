# Task 2: TelegramApiClient (reactive WebClient bean)

## Required Skills

Перед виконанням задачі завантаж:
- `/skill:code-writing` — [skills/code-writing/SKILL.md](../../../.claude/skills/code-writing/SKILL.md)

## Description

Будуємо `com.botfunnel.bot.TelegramApiClient` як Spring `@Component`, що обгортає реактивний `WebClient` для виклику Telegram Bot API. Це **перший** реактивний `WebClient` bean у кодовій базі — далі його реюзатимуть `BotService` (06), webhook ingestion (06b) та sender (06c).

Клієнт інкапсулює:
- base URL з `${app.telegram.base-url}` (default `https://api.telegram.org`; property додає Task 1 у тому ж проході, щоб уникнути конфлікту правок у `application.properties` між Wave 1 задачами);
- Reactor Netty `HttpClient` з `responseTimeout(Duration.ofSeconds(10))` (D13);
- retry-політику `Retry.backoff(3, Duration.ofMillis(200)).maxBackoff(Duration.ofSeconds(2))`, відфільтровану на transient помилки: `WebClientResponseException` з 5xx, `IOException`, `java.util.concurrent.TimeoutException`, **`io.netty.handler.timeout.ReadTimeoutException`** (Reactor Netty `responseTimeout` піднімає саме його, і він не є підкласом ні `IOException`, ні `TimeoutException`, тому без явного додавання в предикат retry не спрацює; альтернатива — обгорнути ланцюг `.timeout(Duration.ofSeconds(...))`, який кидає `java.util.concurrent.TimeoutException` і вже ловиться предикатом) (D11);
- три публічні методи: `getMe(token)`, `setWebhook(token, url, secret)`, `deleteWebhook(token)`;
- маппінг Telegram 4xx відповідей у `AppException` всередині `.onStatus(...)`: 401 → 422 `invalid_bot_token`; 4xx з config-related `description` → 500 `webhook_config_error` (D8);
- token-regex scrubber: будь-який WARN/INFO log line, що echo-ить Telegram `description`, проганяється через regex `\d{1,20}:[A-Za-z0-9_-]{30,50}` із заміною на `[REDACTED_TOKEN]`, щоб Telegram-помилка, яка квотить токен назад, не витекла в operator-логи (R1).

Окрім самого клієнта створюються DTO-записи `TelegramResult<T>` (загальна оболонка `{ok, result, error_code, description}`) та `TelegramUser` (відповідь `getMe`). Build-script отримує `testImplementation 'com.squareup.okhttp3:mockwebserver:4.12.0'` (D9, D10) — Spring Boot 3.5.0 BOM цей артефакт не менеджить, тому версію піним явно. Це дозволяє юніт- та інтеграційним тестам ганяти клієнт проти локального HTTP-моку без реального Telegram. Production-конфіг не торкається — base URL дефолтиться у production endpoint, а тести конструюють клієнт напряму як pure unit (`new TelegramApiClient(WebClient.builder(), mockServer.url("/").toString())`), без Spring context.

## What to do

1. Створити `backend/src/main/java/com/botfunnel/bot/dto/TelegramResult.java` — generic Java record `TelegramResult<T>(boolean ok, T result, Integer error_code, String description)`. Поля точно з тих самих snake_case імен, що Telegram повертає, бо це вхідне DTO Jackson-десеріалізації.
2. Створити `backend/src/main/java/com/botfunnel/bot/dto/TelegramUser.java` — Java record `TelegramUser(Long id, boolean is_bot, String first_name, String username)`. Це body для `result` поля при виклику `getMe`.
3. Створити `backend/src/main/java/com/botfunnel/bot/TelegramApiClient.java` — `@Component`:
   - Конструктор приймає `WebClient.Builder builder` (Spring autoconfig із `webflux` стартера) та `@Value("${app.telegram.base-url}") String baseUrl` (property додає Task 1).
   - Усередині конструктора будує singleton `WebClient` з `baseUrl` та `ReactorClientHttpConnector`, обгортаючи `HttpClient.create().responseTimeout(Duration.ofSeconds(10))`.
   - Публічні методи:
     - `Mono<TelegramUser> getMe(String token)` — `GET /bot{token}/getMe`; розпаковує `TelegramResult<TelegramUser>` і повертає `.result`.
     - `Mono<Boolean> setWebhook(String token, String url, String secret)` — `POST /bot{token}/setWebhook` з body `{url, secret_token: secret}`; розпаковує `TelegramResult<Boolean>` і повертає `.result`.
     - `Mono<Boolean> deleteWebhook(String token)` — `POST /bot{token}/deleteWebhook`; розпаковує `TelegramResult<Boolean>` і повертає `.result`.
   - Кожен метод композує: `.retrieve().onStatus(HttpStatusCode::is4xxClientError, this::mapClientError).bodyToMono(parameterized type ref).timeout(Duration.ofSeconds(10)).retryWhen(buildRetry())`.
   - `mapClientError(ClientResponse resp)` — читає `TelegramResult` із тіла, проганяє `description` через scrubber, мапить:
     - HTTP 401 → `AppException.unprocessableEntity("invalid_bot_token", "Token is invalid or revoked")`;
     - інший 4xx із непустим `description` (config-related, як-от "HTTPS url must be provided") → `new AppException(HttpStatus.INTERNAL_SERVER_ERROR, "webhook_config_error", "Webhook configuration error")` — повне Telegram `description` логиться через `log.warn` тільки після scrubber-у; user-facing меседж тримати generic;
     - решта 4xx → fallback `AppException.badRequest(scrubbedDescription)` (на практиці майже не зустрічаємо; покрити юніт-тестом окремою гілкою).
   - Retry-фільтр (`buildRetry()`):
     - `Retry.backoff(3, Duration.ofMillis(200)).maxBackoff(Duration.ofSeconds(2))`;
     - `.filter(ex -> (ex instanceof WebClientResponseException w && w.getStatusCode().is5xxServerError()) || ex instanceof java.io.IOException || ex instanceof java.util.concurrent.TimeoutException || ex instanceof io.netty.handler.timeout.ReadTimeoutException)` — `ReadTimeoutException` критично, бо саме його кидає Reactor Netty `responseTimeout(10s)`, і він НЕ є підкласом ні `IOException`, ні `TimeoutException`; без явного додавання read-timeout-и не ретраяться, а вилітають як unhandled;
     - `.onRetryExhaustedThrow((spec, signal) -> new AppException(HttpStatus.BAD_GATEWAY, "telegram_unavailable", "Telegram is currently unavailable. Try again in a minute."))` — це лягає під 502 у `errors.bot.connect.502` для AC4.
   - Token-regex scrubber: приватний `static final Pattern TOKEN_PATTERN = Pattern.compile("\\d{1,20}:[A-Za-z0-9_-]{30,50}")` + `static String scrubTokens(String input)` що замінює всі matches на `[REDACTED_TOKEN]`. Прогоняти КОЖНУ строку, яка попадає в `log.warn(...)` / `log.error(...)` і виходить з Telegram `description` поля. Окремим unit-тестом покрити (D17, R1).
4. Оновити `backend/build.gradle` — додати в блок `dependencies`:
   ```
   testImplementation 'com.squareup.okhttp3:mockwebserver:4.12.0'
   ```
   Версію пінимо явно — Spring Boot 3.5.0 BOM `mockwebserver` не менеджить, тож без pin збірка не зарезолвить артефакт. `4.12.0` сумісна з `okhttp` 4.x, який уже непрямо тягнеться spring-стартерами.
5. Написати юніт-тести (`backend/src/test/java/com/botfunnel/bot/TelegramApiClientTest.java`) як pure unit — без `@SpringBootTest` і без Spring context. Піднімати локальний `MockWebServer` per-test (`@BeforeEach`/`@AfterEach`), конструювати клієнт напряму через `new TelegramApiClient(WebClient.builder(), mockServer.url("/").toString())` — base URL інжектиться у конструктор як другий параметр (той самий, що в production отримує `@Value("${app.telegram.base-url}")`), без оверайду Spring property. Покрити кожен сценарій із TDD Anchor / Acceptance Criteria.

## TDD Anchor

Тести, які пишемо ДО реалізації — пишемо, запускаємо, переконуємось що падають, потім код, потім зелено.

- `backend/src/test/java/com/botfunnel/bot/TelegramApiClientTest.java::getMe_happyPath_returnsPopulatedTelegramUser` — `MockWebServer` віддає `200 {"ok":true,"result":{"id":123,"is_bot":true,"first_name":"x","username":"x_bot"}}` → `getMe(token).block()` повертає `TelegramUser(123, true, "x", "x_bot")`; перевірити request path = `/bot{token}/getMe`.
- `backend/src/test/java/com/botfunnel/bot/TelegramApiClientTest.java::getMe_401_mapsToInvalidBotToken` — `MockWebServer` віддає `401 {"ok":false,"error_code":401,"description":"Unauthorized"}` → `StepVerifier` чекає `AppException` зі статусом `UNPROCESSABLE_ENTITY` і кодом `invalid_bot_token`; request count = 1 (no retries on 4xx).
- `backend/src/test/java/com/botfunnel/bot/TelegramApiClientTest.java::getMe_5xxRetryExhausted_returns502TelegramUnavailable` — `MockWebServer` enqueue 503 чотири рази → `StepVerifier` чекає `AppException` зі статусом `BAD_GATEWAY` і кодом `telegram_unavailable`; request count = 4 (1 первинний + 3 ретраї).
- `backend/src/test/java/com/botfunnel/bot/TelegramApiClientTest.java::setWebhook_4xxConfigError_mapsTo500WebhookConfigError` — `MockWebServer` віддає `400 {"ok":false,"error_code":400,"description":"HTTPS url must be provided"}` → `AppException` зі статусом `INTERNAL_SERVER_ERROR` і кодом `webhook_config_error`; через лог-аппендер (Logback `ListAppender`) перевірити, що WARN-лайн містить scrubbed `description`.
- `backend/src/test/java/com/botfunnel/bot/TelegramApiClientTest.java::scrubber_redactsTokenShapedSubstring` — pure unit на `scrubTokens(...)`: вхід `"foo 1234567890:ABCdefGHI_jklMNOpqrSTUvwxYZ0123456789 bar"` → вихід `"foo [REDACTED_TOKEN] bar"`. Edge cases: токен на початку, в кінці, мульти-токен в одному рядку, текст без токенів (unchanged), null-safe.
- `backend/src/test/java/com/botfunnel/bot/TelegramApiClientTest.java::deleteWebhook_5xxRetryExhausted_returns502TelegramUnavailable` — Симетрично до `getMe` retry exhaustion, але через `deleteWebhook`. Підтверджує, що retry-композиція спрацьовує однаково на всіх трьох методах.
- `backend/src/test/java/com/botfunnel/bot/TelegramApiClientTest.java::getMe_nettyReadTimeout_retriesThenReturns502TelegramUnavailable` — `MockWebServer` enqueue відповідь із `setBodyDelay(...)`, що перевищує сконфігурований Reactor Netty `responseTimeout` (наприклад, `responseTimeout(200ms)` у тестовій конфігурації клієнта + `setBodyDelay(500, TimeUnit.MILLISECONDS)` × 4 рази). Очікуваний результат: `StepVerifier` бачить `AppException` зі статусом `BAD_GATEWAY` і кодом `telegram_unavailable`; request count = 4 (1 первинний + 3 ретраї). Цей тест ловить регресію, коли `io.netty.handler.timeout.ReadTimeoutException` випадає з retry-фільтра (бо не успадковує ні `IOException`, ні `TimeoutException`) — без правильного предикату тест впаде з ассертом на retry count = 1.
- `backend/src/test/java/com/botfunnel/bot/TelegramApiClientTest.java::setWebhook_passesSecretTokenAndUrlInBody` — заглушка `200 {"ok":true,"result":true}` + `mockServer.takeRequest()` → перевірити, що тіло запиту містить `"url"` і `"secret_token"` (це AC10 contract).

## Details

**Files:**
- `backend/src/main/java/com/botfunnel/bot/TelegramApiClient.java` — новий `@Component`. Single private `WebClient` field, three public methods (`getMe`, `setWebhook`, `deleteWebhook`), private `mapClientError` + `buildRetry` + `scrubTokens` helpers + `TOKEN_PATTERN` constant. Один SLF4J logger.
- `backend/src/main/java/com/botfunnel/bot/dto/TelegramResult.java` — record `TelegramResult<T>(boolean ok, T result, Integer error_code, String description)`. Поля snake_case навмисно (Telegram contract). Стандартна Jackson-десеріалізація.
- `backend/src/main/java/com/botfunnel/bot/dto/TelegramUser.java` — record `TelegramUser(Long id, boolean is_bot, String first_name, String username)`. Поля — body Telegram `getMe.result`.
- `backend/build.gradle` — у блоці `dependencies` додати `testImplementation 'com.squareup.okhttp3:mockwebserver:4.12.0'` (D9). Версія пінується явно — Spring Boot 3.5.0 BOM `mockwebserver` не менеджить, тож без pin Gradle не зарезолвить артефакт. `4.12.0` сумісна з `okhttp` 4.x, який уже непрямо тягнеться spring-стартерами.
- `backend/src/test/java/com/botfunnel/bot/TelegramApiClientTest.java` — JUnit5 + Reactor `StepVerifier`. Піднімати `MockWebServer` per-test (BeforeEach/AfterEach), конструювати клієнт через `new TelegramApiClient(WebClient.builder(), mockServer.url("/").toString())`. Без `@SpringBootTest` — чистий unit, без Spring context.

**Dependencies:**
- Task 1 пише `app.telegram.base-url` у `application.properties` у тому самому Wave 1 (узгоджено в tech-spec, рядок 491). На випадок асинхронності — `@Value("${app.telegram.base-url:https://api.telegram.org}")` із default-ом дасть змогу скомпілитися/запуститися; default дублює production-значення, тож семантика не міняється.
- Існуючі бібліотеки: `spring-boot-starter-webflux` (WebClient, Reactor Netty), Jackson (через webflux). `spring-boot-starter-validation` тут не потрібен.

**Edge cases:**
- Telegram 5xx з тілом, що не парситься як `TelegramResult` — retry-фільтр спрацьовує по статусу через `WebClientResponseException`; не намагатись прочитати тіло до парсингу `onStatus`.
- 4xx із порожнім `description` — fallback гілка `AppException.badRequest(...)` (не крашити на NPE).
- Token у `description` (Telegram інколи echo-ить токен у тексті помилки) — scrubber обовʼязковий ДО `log.warn(...)`. Без scrubber токен світиться в логах.
- **Critical:** `responseTimeout` від Reactor Netty піднімає `io.netty.handler.timeout.ReadTimeoutException`, який НЕ є підкласом ні `java.io.IOException`, ні `java.util.concurrent.TimeoutException`. Без явного `|| ex instanceof io.netty.handler.timeout.ReadTimeoutException` у retry-предикаті read-timeout-и НЕ ретраяться, а пропускаються наверх як unhandled — це регресія, яку ловить тест `getMe_nettyReadTimeout_retriesThenReturns502TelegramUnavailable`. Альтернатива (якщо хочеться лишити предикат на одних JDK-типах) — обгорнути ланцюг `.timeout(Duration.ofSeconds(...))` після `.bodyToMono(...)`, що перетворить будь-який повільний response (включно з Netty read-timeout) на `java.util.concurrent.TimeoutException`, який вже у предикаті. Обидва варіанти валідні — обрати один і покрити тестом.
- `.timeout(Duration.ofSeconds(10))` на `Mono` додатково страхує від випадків, коли Netty `responseTimeout` не спрацював (наприклад, response body не приходить після headers).
- Generic-параметр `TelegramResult<T>` через `ParameterizedTypeReference` — інакше Jackson не вгадає тип. Без цього buildToMono поверне сирий `Object`.

**Implementation hints:**
- `WebClient.Builder` приходить як bean від Spring autoconfig — не створювати власний `WebClient.create()`, а використовувати `builder` із конструктора. Це той самий шаблон, що описаний у tech-spec Architecture → "Shared resources" — один `WebClient` bean на весь модуль.
- `ParameterizedTypeReference<TelegramResult<TelegramUser>>` для розпаковки generic-результату `getMe`. Для `setWebhook`/`deleteWebhook` body результату — `Boolean`, тому `ParameterizedTypeReference<TelegramResult<Boolean>>`.
- `Retry.backoff(...)` повертає `RetryBackoffSpec`; `.filter(...)` повертає `RetryBackoffSpec`; `.onRetryExhaustedThrow(BiFunction<RetryBackoffSpec, RetrySignal, Throwable>)` дає змогу замапити exhaustion у `AppException` напряму, без додаткового `.onErrorMap`.
- Для логування використовувати `private static final Logger log = LoggerFactory.getLogger(TelegramApiClient.class);` як в `EmailService`.
- Один `Pattern` constant на клас — `Pattern.compile` тяжкий, не робити його у методі.
- `TelegramResult.result` для `setWebhook`/`deleteWebhook` — `Boolean`. Якщо `ok=true` і `result=true` — повернути `true`; якщо `ok=false` — це 4xx-гілка, яка вже обробилася в `onStatus`. Захиститись від `null` у `result`.
