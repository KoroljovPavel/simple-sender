# Task 3: Bot domain layer (entity, status enum, repository, indexes)

## Description

Stand up the persistence-layer foundation for the bot module — the `bots` MongoDB collection schema, its supporting status enum, and a reactive repository. This is one of three Wave 1 foundation tasks with zero internal dependencies; `BotService` (Wave 2 / Task 6) injects this repository to run all pre-checks, persistence, and `DuplicateKeyException` handling.

Three indexes ship with the document class. The non-unique compound `(projectId, status)` index backs `findByProjectIdAndStatus` (used on every Get / Disconnect / TestMessage / pre-check). Two partial-unique indexes — both filtered to `status="CONNECTED"` — close defense-in-depth race windows: `(telegramBotId)` per D1 prevents the same Telegram identity being connected to two projects simultaneously; `(projectId)` per D5 prevents two different tokens being connected to the same project simultaneously. The filter expression `{ status: "CONNECTED" }` is critical — without it, repeated Connect-Disconnect cycles would collide on stale `DISCONNECTED` rows.

Schema fields are exactly those from tech-spec Data Models → `bots` collection: `id`, `projectId`, `telegramBotId`, `telegramUsername`, `telegramFirstName`, `status`, `encryptedTokenCiphertext` (nullable; D3), `encryptedTokenIv` (nullable; D3), `tokenSuffix` (nullable; last 3 chars of token secret segment, used by the UI mask per D17 / AC18), `webhookSecretHash` (nullable; SHA-256 hex per D2), `connectedAt`, `disconnectedAt` (nullable while CONNECTED). All four nullable secret/derived fields are cleared on Disconnect (handled by `BotService` in Task 6 — not in this task).

The repository exposes three derived queries used by `BotService`:
- `findByProjectIdAndStatus(projectId, status)` — Get / Disconnect / TestMessage path; per-project pre-check (D5).
- `findByProjectId(projectId)` — historical lookups (may be used later for disconnected-row audit views).
- `findFirstByTelegramBotIdAndStatus(telegramBotId, status)` — platform-wide pre-check (D1).

## What to do

- Create `backend/src/main/java/com/botfunnel/bot/BotStatus.java` — enum with two values: `CONNECTED`, `DISCONNECTED`. No additional methods needed.
- Create `backend/src/main/java/com/botfunnel/bot/Bot.java` — `@Document(collection = "bots")` POJO with the fields listed in tech-spec Data Models, mirroring the bean-style getters/setters pattern used by `Project.java`. Mark `projectId` with `@Indexed` (the partial-unique compound on `projectId` does not cover non-`CONNECTED` reads). Declare the three indexes via class-level `@CompoundIndexes`:
  - `projectId_status` — `def = "{'projectId': 1, 'status': 1}"`, non-unique.
  - `telegramBotId_unique_connected` — `def = "{'telegramBotId': 1}"`, `unique = true`, `partialFilter = "{ 'status': 'CONNECTED' }"`.
  - `projectId_unique_connected` — `def = "{'projectId': 1}"`, `unique = true`, `partialFilter = "{ 'status': 'CONNECTED' }"`.
- Create `backend/src/main/java/com/botfunnel/bot/BotRepository.java` — `extends ReactiveMongoRepository<Bot, String>` with three derived-query signatures: `Mono<Bot> findByProjectIdAndStatus(String projectId, BotStatus status)`, `Flux<Bot> findByProjectId(String projectId)`, `Mono<Bot> findFirstByTelegramBotIdAndStatus(Long telegramBotId, BotStatus status)`.
- Do NOT add any business logic, encryption, or service wiring here — this task is the persistence shape only. `BotService` lands in Task 6.

## Details

**Files:**

- `backend/src/main/java/com/botfunnel/bot/Bot.java` — NEW. `@Document(collection = "bots")` POJO. Class-level `@CompoundIndexes({...})` declaring the three indexes. Fields exactly as in tech-spec Data Models: `@Id String id`, `@Indexed String projectId`, `Long telegramBotId`, `String telegramUsername`, `String telegramFirstName`, `BotStatus status`, `String encryptedTokenCiphertext`, `String encryptedTokenIv`, `String tokenSuffix`, `String webhookSecretHash`, `Instant connectedAt`, `Instant disconnectedAt`. Bean-style getters/setters for every field — matches `Project.java` (no Lombok in this codebase; verified by reading `Project.java`).

- `backend/src/main/java/com/botfunnel/bot/BotStatus.java` — NEW. `public enum BotStatus { CONNECTED, DISCONNECTED }` plus two annotations that control **Jackson HTTP serialisation only**:
  - `@JsonValue public String toJson() { return name().toLowerCase(); }` — Jackson emits `"connected"` / `"disconnected"` on the wire (consumed by Tasks 7/8/9 HTTP responses, which expect lowercase per the OpenAPI contract).
  - `@JsonCreator public static BotStatus fromString(String s) { return BotStatus.valueOf(s.toUpperCase()); }` — Jackson parses lowercase request bodies back into the enum.

  Critical: Spring Data MongoDB enum mapping is **independent of Jackson** — it persists the enum as its Java `name()` (`"CONNECTED"` / `"DISCONNECTED"`). The partial-filter index expression `{ status: "CONNECTED" }` therefore continues to match correctly; the Jackson annotations only affect HTTP boundary serialisation. Do not add any Mongo-specific converter that would change the persisted form.

- `backend/src/main/java/com/botfunnel/bot/BotRepository.java` — NEW. `public interface BotRepository extends ReactiveMongoRepository<Bot, String>` with three derived-query method signatures (see TDD Anchor + What to do for exact signatures). Naming follows `ProjectRepository.java` conventions.

**Dependencies:**

- `spring-boot-starter-data-mongodb-reactive` — already on classpath; provides `ReactiveMongoRepository`, `@Document`, `@Indexed`, `@CompoundIndex`, `@CompoundIndexes`.
- No new packages added by this task. (Task 2 adds `mockwebserver`; Task 1 wires `BOT_TOKEN_ENCRYPTION_KEY` config — neither affects this task.)
- This task creates the new package `com.botfunnel.bot` — Tasks 2 (TelegramApiClient) and 6 (BotService) live in the same package and land alongside.

**Edge cases:**

- Partial filter expression must use the exact string literal `CONNECTED` matching `BotStatus.CONNECTED.name()` — the form Spring Data MongoDB persists. Lowercase `"connected"` (as appears in the Decision 1 prose: `partialFilter="{ status: \"connected\" }"`) would break against the enum's persisted form — the Data Models section of tech-spec uses the correct upper-case form and is authoritative. The `@JsonValue` lowercase annotation on `BotStatus` only affects Jackson / HTTP serialisation and does not change what Mongo stores.
- `@Indexed` on `projectId` is still useful even though the per-project partial-unique index covers connected rows: the partial index excludes `DISCONNECTED` rows, so a non-CONNECTED lookup by `projectId` alone (e.g. `findByProjectId`) needs the simple `@Indexed` to stay performant.
- All four nullable fields (`encryptedTokenCiphertext`, `encryptedTokenIv`, `tokenSuffix`, `webhookSecretHash`) must be plain mutable `String` — `BotService` (Task 6) nulls them in the Disconnect step. Do not mark them `final`.
- `disconnectedAt` is `null` while `CONNECTED`; do not initialise it.
- Do NOT make `Bot` a `record` — `@Document` POJOs in this codebase use bean-style mutable classes (see `Project.java`, `Event.java`); a record would not match the convention and would constrain `BotService`'s null-the-secrets-on-Disconnect update path.

**Implementation hints:**

- Use `@CompoundIndexes({ @CompoundIndex(...), @CompoundIndex(...), @CompoundIndex(...) })` — the plural wrapper used in `Project.java`. The `@CompoundIndex(partialFilter = ...)` attribute accepts the JSON filter as a string; either escape inner double-quotes or use single quotes inside the string (Spring Data parses both).
- Index names must match the verification-step grep targets exactly: `projectId_status`, `telegramBotId_unique_connected`, `projectId_unique_connected`.
- `findFirstByTelegramBotIdAndStatus` uses the `First` keyword because the partial unique index guarantees at most one `CONNECTED` row per `telegramBotId`, but the method signature still bounds the result to one row defensively (matches the pattern in tech-spec Architecture → "ensureTelegramBotIdNotConnectedAnywhere" pre-check).
- For repository tests, both `BotRepositoryTest` and `BotIndexTest` must extend the codebase's `AbstractIntegrationTest` base class at `backend/src/test/java/com/botfunnel/AbstractIntegrationTest.java` — it boots a real reactive Mongo via Testcontainers, which is the only test pattern used in this project for Mongo interaction (do not use `@DataMongoTest`; it is incompatible with the codebase's reactive Mongo + Testcontainers setup and is not used anywhere here). Use `StepVerifier` for reactive assertions, consistent with the platform's reactive test idiom. Note: Task 1 owns `BOT_TOKEN_ENCRYPTION_KEY` in `application-test.properties` and lands in the same wave — this task should not add or duplicate that property; trust Task 1 to provide it (boot-time wiring only matters once any `AbstractIntegrationTest` subclass runs).
- For the index-enforcement tests, `auto-index-creation=true` handles index creation; just call `botRepository.save(...)` twice with conflicting CONNECTED rows and assert `DuplicateKeyException` propagates via `StepVerifier.create(...).expectError(DuplicateKeyException.class).verify()`.
- For the `indexes_areCreatedOnCollection` assertion, inject `ReactiveMongoTemplate` and call `indexOps(Bot.class).getIndexInfo()`; assert the three names exist and that both unique-named entries carry a non-empty partial-filter expression containing `status` / `CONNECTED`.
