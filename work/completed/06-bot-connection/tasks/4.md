# Task 4: Frontend i18n keys (bot.* and errors.bot.*)

## Required Skills

Перед выполнением задачи загрузи:
- `/skill:code-writing` — [skills/code-writing/SKILL.md](../../../.claude/skills/code-writing/SKILL.md)

## Description

Add `bot.*` (page strings: titles, button labels, hints, modal copy) and the
status-keyed error subtrees to both `frontend/i18n/locales/uk.json` and
`frontend/i18n/locales/en.json`. Key inventory follows user-spec AC22
verbatim: `errors.bot.connect.{400, 422, 500, 502, 409, 429}`,
`errors.bot.testMessage.{422, 502}`, `errors.bot.disconnect.{404}` — no 401
in any subtree (backend never returns 401 from these endpoints). The two
locale files must stay in lock-step; the existing `prebuild` parity gate
(`frontend/scripts/check-locales.mjs`) enforces this on every build by
comparing flat key sets and failing the script with exit code 1 on any
asymmetric key.

The keys here are the bilingual vocabulary every later UI task in this
feature depends on: Task 5 (Settings sub-nav, `settings/bot.vue`
placeholder) and Task 9 (full Bot page) both call `t('bot.*')` and pass
`'bot.connect'` / `'bot.disconnect'` / `'bot.testMessage'` as the context
key to `useApiError()`. If a status-keyed error like `errors.bot.connect.422`
is missing, `useApiError()` (see `frontend/composables/useApiError.ts`)
falls through to `errors.bot.connect.generic`, then to `errors.generic`,
then to empty string — so AC22 demands every status from user-spec is
spelled out per-locale rather than relying on a generic fallback.

**Beyond user-spec AC22:** Task 5 (same wave) scaffolds the Settings
sub-nav and an empty `settings/bot.vue` placeholder. To keep Task 5
purely structural with no hard-coded strings, Task 4 also ships three
small UI keys that Task 5 will consume: `bot.subnav.general` (tab label
for the General tab), `bot.subnav.bot` (tab label for the Bot tab), and
`bot.placeholder` (short body text rendered on the empty Bot page until
Task 9 replaces it). These are additive to AC22 — AC22 is the
error-key contract, and the subnav/placeholder strings are co-located
here because they share the same `bot.*` namespace and parity gate.

**Key-naming convention (canonical, cross-task with Task 9):** the
entire `bot.*` UI tree is **dot-segmented** — no camelCase compound
roots. Task 9 calls `t('bot.disconnect.modal.body', { username: … })`
and the locale tree must match path-segment by path-segment, so the
keys here are `bot.disconnect.modal.{title,body,cancel,confirm}` (NOT
`bot.disconnectModal.*`) and `bot.connect.form.*` (NOT
`bot.connectForm.*`). Single-word leaves under `bot` stay as-is:
`bot.connected.*`, `bot.toasts.*`, `bot.subnav.*`, `bot.placeholder`,
`bot.page.*`. The `errors.bot.*` subtree is also dot-segmented at every
level: `errors.bot.{generic, connect.<status>, disconnect.<status>,
testMessage.<status>}` — note `testMessage` is the action context-key
that Task 9 passes to `useApiError(err, 'bot.testMessage')`, kept as a
single camelCase identifier on purpose so the composable's candidate
builder produces `errors.bot.testMessage.<status>` verbatim.

## TDD Anchor

This task only edits two JSON content files and is verified end-to-end by
the existing `frontend/scripts/check-locales.mjs` parity gate (run via
`pnpm prebuild`). No new test file is added — the parity script itself is
the test. The verification flow IS test-first in spirit: run `pnpm
prebuild` BEFORE the edit (expected: exit 0 — keys are not present so
parity holds vacuously); make the edit to one locale only and re-run
(expected: exit 1, naming the missing keys); make the symmetric edit on
the other locale and re-run (expected: exit 0). The Smoke step formalises
the failing-state check.

- `frontend/i18n/locales/uk.json` — current state: 290 lines, parity-mirror of `en.json`. Apply the identical structural edit with Ukrainian copy.

**Dependencies:** None (Wave 1, no dependencies). Tasks 5 and 9 consume the keys added here but are downstream.

**Edge cases:**
- The Connect endpoint may return 409 for either platform-wide conflict (AC6) or per-project conflict (AC7). Backend distinguishes via the `error.code` field in the response body (`bot_already_connected` vs `bot_already_in_project`). `useApiError()` keys only on HTTP status, so a single `errors.bot.connect.409` string must cover the user-visible case. Use the AC6 wording — it is strictly more general and never reveals foreign-project identity. The Bot page (Task 9) may additionally branch on the backend error code if it wants the more specific AC7 message; that decision is downstream of this task.
- The `errors.bot.testMessage.502` key is reserved for forward compatibility (per user-spec AC22). In 06 the test-message endpoint short-circuits to 422 before any Telegram call, so 502 is not reachable yet. Put a translation in anyway — when 06b lands, no further i18n change is needed.
- `errors.bot.disconnect` deliberately has NO 502 leaf — Disconnect is best-effort (AC13); even when Telegram is down the endpoint returns 200 after local state update. Adding a 502 key would imply a behaviour that does not exist.
- No `errors.bot.*.401` keys anywhere. The backend never returns 401 from bot endpoints: invalid Telegram tokens map to 422 (AC3); foreign / soft-deleted / malformed projectIds collapse to 404 via the anti-enumeration pattern (AC16); auth-layer 401 is handled globally by the existing session-expired logic, not by the bot context.

**Implementation hints:**
- **MANDATORY per-action generic fallbacks** — `errors.bot.connect.generic`,
  `errors.bot.disconnect.generic`, and `errors.bot.testMessage.generic`
  are not optional. Each must exist in BOTH `en.json` AND `uk.json`,
  separate from the top-level `errors.bot.generic`. Reason:
  `useApiError(err, 'bot.<action>')` builds the candidate chain
  `errors.bot.<action>.<status>` → `errors.bot.<action>.generic` →
  `errors.generic` — omitting the per-action `generic` collapses the
  fallback ladder by one rung and the user sees the global
  `errors.generic` for any unmapped status (which carries the wrong
  context). Top-level `errors.bot.generic` is a structural anchor for
  the action subtree, NOT a substitute for these three per-action keys.
- **Canonical dot-segmented paths** — the entire `bot.*` UI tree uses
  dot-segmented compound roots (`bot.connect.form.*`, `bot.disconnect.modal.*`),
  NOT camelCase (`bot.connectForm`, `bot.disconnectModal`). Task 9 calls
  `t('bot.disconnect.modal.body', { username })` directly. Keep the two
  task files in lock-step on this.
- Mirror the existing `errors.projects` shape: a top-level `generic`, then per-action sub-objects (`create`, `update`, `delete`, `restore`) keyed by status code as strings (`"400"`, `"409"`, `"422"`, …). The corresponding bot shape is `errors.bot.{generic, connect, disconnect, testMessage}` with status-string children plus a `generic` child inside each action object.
- Status keys are JSON strings (`"400"` not `400`) — `i18n` lookups treat them as path segments. The existing locale files already do this for `errors.login.401`, `errors.projects.create.400`, etc.
- For the modal body, `vue-i18n` named interpolation uses `{username}` (curly braces, no `$`). Example existing pattern: ad-hoc `t('errors.…', { username: bot.username })` at the call site in Task 9.
- Place the new `bot` block above `errors` for readability (matches alphabetical convention used elsewhere in the file — `auth`, `bot`, `brand`, `common`, … — though the existing file is not strictly alphabetical, putting `bot` near other feature-page blocks is consistent).
- The parity script does not enforce VALUE equality, only KEY parity. The two locales can carry any tone-appropriate translations — the only mechanical requirement is that the flat dotted-path key sets match.
- Make sure trailing JSON braces match — a missing or extra `,` is the most common mistake on hand-edit. Run a JSON formatter or `jq .` on each file after the edit if unsure: `jq . frontend/i18n/locales/en.json >/dev/null` should exit 0.
