# Task 6: BotService — full lifecycle orchestration

## Required Skills

Перед выполнением задачи загрузи:

## Description

Build `com.botfunnel.bot.BotService` — the reactive orchestrator that owns the Connect, Disconnect, Get, and TestMessage flows for the bot module. The service is the only place that composes the building blocks delivered in Wave 1 (`TokenEncryptor` from T1, `TelegramApiClient` from T2, `Bot`/`BotStatus`/`BotRepository` from T3) into the full pipeline described in tech-spec → Architecture → "How it works".

Connect must execute side effects in a strict, observable order (requireOwned → INCR brute-force counter → per-project pre-check → getMe → platform-wide pre-check → setWebhook → encrypt → persist → `bot_connected` event → DEL brute-force counter) and must compensate `setWebhook` with a best-effort `deleteWebhook` on any failure that happens after step 7 (persist exception, DuplicateKeyException variants). Disconnect must remain best-effort against Telegram (AC13) and atomically null the encrypted-token + webhook-secret-hash + tokenSuffix fields. Get is a thin read. TestMessage in 06 short-circuits to a 422 `owner_chat_id_unknown` (D7) and intentionally emits **no** `bot_test_message_sent` event — that event is introduced in 06b on the success branch.

The brute-force counter follows decision D14: a per-user key `brute:bot-connect:{userId}`, threshold 10, 15-minute TTL on first INCR, DEL on success, fail-open with `log.warn(...)` on Redis errors. Departure from `AuthService`'s INCR-on-failure-only pattern is deliberate (D14 rationale) — Connect INCRs every attempt so an attacker cannot bypass the limit via Connect-then-Disconnect cycles.

The project currently has no metrics infrastructure (no `spring-boot-starter-actuator`, no `MeterRegistry` usage anywhere in `backend/src/main`). Observability for D14's "fail-open must be operationally visible" requirement is therefore satisfied via a dedicated WARN log line on the Redis-error path (distinct, greppable message such as `"bot-connect brute-force counter Redis failure (fail-open)"`). If metrics infrastructure is added later, the WARN site is the single place to swap in a counter — do not pre-introduce actuator just for this task.

This task ships only `BotService.java` plus its unit-test class. The controller, request/response DTOs, and integration tests land in Task 8; the service must expose a contract Task 8 can wire to. Public method signatures (per tech-spec Architecture): `getByProject(ownerId, projectId)`, `connect(ownerId, projectId, token, ip, ua)`, `disconnect(ownerId, projectId, ip, ua)`, `sendTestMessage(ownerId, projectId, ip, ua)`. Every operation runs `ProjectService.requireOwned(...)` as its first reactive step.

## What to do

1. Create `backend/src/main/java/com/botfunnel/bot/BotService.java` as a Spring `@Service`. Inject `BotRepository`, `ProjectService`, `TokenEncryptor`, `TelegramApiClient`, `EventService`, and `ReactiveRedisTemplate<String, String>`. Inject `@Value("${app.url}")` for the webhook URL. Do NOT inject `MeterRegistry` — the project does not depend on `spring-boot-starter-actuator` and has no other Micrometer usage; adding the dep just for this task is out of scope. Observability for the Redis fail-open path is delivered via a dedicated WARN log message (see Description).
2. Implement `connect(ownerId, projectId, token, ip, ua): Mono<Bot>` as the reactive pipeline described in tech-spec → Architecture → "How it works", in exactly this order: `requireOwned(ownerId, projectId, false)` → `incrementBruteForceCounter` (INCR + 15-min EXPIRE on first hit, 429 on count > 10) → `ensureNoConnectedBotForProject` (D5 pre-check → 409 `bot_already_in_project`) → `telegram.getMe(token)` → `ensureTelegramBotIdNotConnectedAnywhere` (D1 pre-check → 409 `bot_already_connected`) → generate 16-byte webhook secret + SHA-256 hex hash + build webhook URL `${app.url}/webhooks/telegram/{projectId}` → `telegram.setWebhook(token, url, secret)` → `tokenEncryptor.encrypt(token)` returning an `EncryptedValue(byte[] iv, byte[] ciphertext)` (per T1 contract: raw bytes, no encoding) → **Base64-encode both `iv` and `ciphertext` with `Base64.getEncoder().encodeToString(...)` before persistence** because `Bot.encryptedTokenCiphertext` and `Bot.encryptedTokenIv` are declared as `String` (Base64) per tech-spec Data Models (lines 292-293) — `BotService` owns the encoding boundary (D15: `TokenEncryptor` is generic and knows nothing about persistence) → compute `tokenSuffix = token.substring(token.length() - 3)` → `botRepository.save(...)` with the two Base64 strings → emit `bot_connected` event → `resetBruteForceCounter` (DEL) → return saved `Bot`.
3. Wrap the `botRepository.save(...)` step in `.onErrorResume(persistErr -> telegram.deleteWebhook(token).onErrorContinue(...).then(Mono.error(persistErr)))` so the compensating `deleteWebhook` runs best-effort on any persist failure (raw save exception OR `DuplicateKeyException`). Map `DuplicateKeyException` to the matching 409: `bot_already_in_project` if the `projectId_unique_connected` index fired; `bot_already_connected` if the `telegramBotId_unique_connected` index fired — discriminate via the index name in the exception message, with a fallback that re-runs `findFirstByTelegramBotIdAndStatus` to disambiguate if the message does not carry the index name on this driver version.
4. Implement `disconnect(ownerId, projectId, ip, ua): Mono<Void>`: `requireOwned` → `findByProjectIdAndStatus(projectId, CONNECTED)` (404 if none) → **Base64-decode** the stored `encryptedTokenIv` and `encryptedTokenCiphertext` strings via `Base64.getDecoder().decode(...)` back into `byte[]`, then call `tokenEncryptor.decrypt(ivBytes, ciphertextBytes)` to recover the plaintext token in-memory (used immediately, never returned, never logged) → `telegram.deleteWebhook(token)` with `.onErrorResume(err -> { log.warn(...); return Mono.just(false); })` so persistent Telegram failure NEVER blocks the local update (AC13) → atomic update setting `status=DISCONNECTED`, nulling `encryptedTokenCiphertext`, `encryptedTokenIv`, `tokenSuffix`, `webhookSecretHash`, setting `disconnectedAt` → emit `bot_disconnected` event with `webhookDeleted: boolean` metadata reflecting whether step 4 succeeded.
5. Implement `getByProject(ownerId, projectId): Mono<Bot>`: `requireOwned` → `findByProjectIdAndStatus(projectId, CONNECTED)` → 404 if none. No decryption, no Telegram call.
6. Implement `sendTestMessage(ownerId, projectId, ip, ua): Mono<Void>`: `requireOwned` → `findByProjectIdAndStatus(projectId, CONNECTED)` (404 if none) → return `Mono.error(AppException.unprocessableEntity("owner_chat_id_unknown", "Send /start to your bot in Telegram first, then try again"))`. No subscriber lookup. No Telegram call. **No event emission** (per D7).
7. Add the brute-force helper methods: `incrementBruteForceCounter(userId)` runs `INCR` then `EXPIRE 900s` only if returned count == 1, returns 429 `AppException.tooManyRequests(...)` on count > 10, and fails open via `.onErrorResume` that logs WARN with a dedicated, greppable message (e.g. `"bot-connect brute-force counter Redis failure (fail-open)"`). `resetBruteForceCounter(userId)` runs `DEL` and silently swallows Redis errors with the same dedicated WARN message.
8. Write `backend/src/test/java/com/botfunnel/bot/BotServiceTest.java` (JUnit 5 + Mockito + reactor-test `StepVerifier`) covering every TDD-Anchor case below. Use `@ExtendWith(MockitoExtension.class)` and `@Mock` fields — do NOT spin up a Spring context.

## Acceptance Criteria

- [ ] **AC1.** Connect happy path returns the saved `Bot` document with `status=CONNECTED`, `telegramBotId`, `telegramUsername`, `telegramFirstName`, `tokenSuffix` populated, `encryptedTokenCiphertext` + `encryptedTokenIv` + `webhookSecretHash` set. The returned object carries no plaintext token field.
- [ ] **AC3.** Telegram `getMe` 401 (token invalid/revoked) surfaces as `AppException.unprocessableEntity("invalid_bot_token", ...)` (mapping owned by `TelegramApiClient` from T2; `BotService` just propagates). No `bots` document persisted.
- [ ] **AC4.** Telegram 5xx or timeout on `getMe`/`setWebhook` after retry exhaustion surfaces as `AppException` with status 502 (mapping owned by `TelegramApiClient`; service propagates). No `bots` document persisted.
- [ ] **AC5.** Telegram 4xx on `setWebhook` with a config-related description (HTTPS required, etc.) surfaces as `AppException` with status 500 and code `webhook_config_error` (mapping owned by `TelegramApiClient`; service propagates).
- [ ] **AC6.** Platform-wide pre-check returns 409 `bot_already_connected` when `findFirstByTelegramBotIdAndStatus(botId, CONNECTED)` finds an existing row. Generic message — no foreign project name/owner revealed. Same 409 produced when the platform-wide partial unique index raises `DuplicateKeyException` after `setWebhook`, AND compensating `deleteWebhook` is invoked.
- [ ] **AC7.** Per-project pre-check returns 409 `bot_already_in_project` with the message "another bot is already connected — disconnect it first" when a `status=CONNECTED` bot already exists for the project. Same 409 produced when the per-project partial unique index raises `DuplicateKeyException` after `setWebhook`, AND compensating `deleteWebhook` is invoked.
- [ ] **AC8.** A successful Connect performs side effects in the documented order — see TDD Anchor `connect_happyPath_runsSideEffectsInDocumentedOrder`. The `bots` document is persisted ONLY if all preceding steps succeed; no intermediate `pending_webhook` state exists.
- [ ] **AC9.** If `setWebhook` succeeds but Mongo persist fails, the service issues a compensating `deleteWebhook` (best-effort, error swallowed and logged) and propagates the persist error. Verified by `connect_persistFails_compensatesDeleteWebhookAndPropagatesError`.
- [ ] **AC10.** The webhook URL registered in Telegram equals `${app.url}/webhooks/telegram/{projectId}` and the secret passed to `setWebhook` is a fresh random value generated per Connect (new 16-byte `SecureRandom` draw on every invocation — never reused, never derived from a constant).
- [ ] **AC11.** Connect is rate-limited per user via Redis counter `brute:bot-connect:{userId}` (INCR every attempt, EXPIRE 900s on first hit). The 11th attempt within 15 minutes surfaces as 429 BEFORE any Telegram call. On successful Connect the counter is DELETED. Fail-open on Redis errors — both INCR and DEL silently no-op the rate-limit logic and emit the dedicated WARN log line (no metric counter, see Description).
- [ ] **AC13.** Disconnect: (a) calls `deleteWebhook` (retries on transient failure owned by `TelegramApiClient`); (b) on persistent Telegram failure logs WARN and PROCEEDS to local update; (c) atomically nulls `encryptedTokenCiphertext`, `encryptedTokenIv`, `tokenSuffix`, `webhookSecretHash`, sets `disconnectedAt`, sets `status=DISCONNECTED`; (d) returns success regardless of (a)/(b). Returns 404 if no `status=CONNECTED` bot exists for the project.
- [ ] **AC14.** `getByProject` returns the current bot with `status=CONNECTED` (or 404 if none). No decryption performed, no Telegram call.
- [ ] **AC16.** Every public method calls `ProjectService.requireOwned(...)` as its first reactive step. Foreign / soft-deleted / malformed `projectId` all collapse to 404 via existing `requireOwned` semantics.
- [ ] **AC17.** No method returns the plaintext or encrypted token to its caller. The decrypted token in `disconnect` exists only as a local in the same `flatMap` chain — never logged, never returned. No log line in this file carries the token field.
- [ ] **AC20.** The webhook secret is stored as a SHA-256 hex hash, NOT in plaintext. The plaintext secret exists only in process memory during the Connect call and is passed to Telegram `setWebhook`; nothing on our side persists it. Verified by `connect_webhookSecretIsHashedWithSha256_neverPlaintext` — the captured `Bot.webhookSecretHash` is 64 hex chars and equals `SHA-256(plaintextSecretCapturedAtSetWebhookCall)`, and no field on the saved `Bot` carries the plaintext.
- [ ] **AC23.** Audit events emitted by this service use `EventService.logEvent` with the metadata shapes documented in tech-spec and decisions.md: `bot_connected` carries `{projectId, telegramBotId, telegramUsername}`; `bot_disconnected` carries `{projectId, telegramBotId, webhookDeleted}`. **No** `bot_test_message_sent` event is emitted from this feature (the event itself is introduced in 06b on the Test-Message success branch — see D7). No string value in any metadata Map matches the Telegram-token regex `^\d{1,20}:[A-Za-z0-9_-]{30,50}$`. Verified by `connect_bot_connected_event_metadata_containsNoTokenRegex` and `sendTestMessage_returns422_noTelegramCalls_noEvents`.
- [ ] **D7 enforcement.** `sendTestMessage` returns 422 `owner_chat_id_unknown` and emits **no** event. Verified by `sendTestMessage_returns422_noTelegramCalls_noEvents`.

**Edge cases:**
- Concurrent Connects with the same Telegram bot ID slipping between the service pre-check (step 5) and the persist (step 9): the partial unique index on `(telegramBotId)` raises `DuplicateKeyException` → mapped to 409 `bot_already_connected` AND compensating `deleteWebhook` issued for the loser.
- Concurrent Connects to the same project with different tokens slipping between the per-project pre-check (step 3) and the persist (step 9): the partial unique index on `(projectId)` raises `DuplicateKeyException` → mapped to 409 `bot_already_in_project` AND compensating `deleteWebhook` issued.
- Redis unreachable on INCR: fail-open (DoS mitigation, not auth gate). Counter increment + WARN log MUST surface so a sustained outage is operationally visible.
- Redis unreachable on DEL after successful Connect: must not fail the Connect — counter expires naturally after 15 min; WARN + metric capture the failure.
- Telegram unreachable on Disconnect: `.onErrorResume` swallows; Mongo update proceeds; `bot_disconnected.metadata.webhookDeleted = false`.
- Disconnect when no `status=CONNECTED` bot exists for the project: 404 (no Telegram call attempted).
- TestMessage when no `status=CONNECTED` bot exists for the project: 404 (matches Disconnect semantics; tech-spec "How it works" → "Test Message" step 2).
- Token decryption inside Disconnect: plaintext exists only in the local `flatMap` chain. Must NOT be logged. Must NOT be returned. The `Mono` it lives in must not reach a downstream operator that serializes intermediate values.

**Implementation hints (pointers only — name the operators/classes; the implementer writes the code):**
- Brute-force counter shape: mirror `AuthService` — Reactor `ReactiveValueOperations.increment` followed by conditional `ReactiveRedisOperations.expire` keyed on the first-hit count. The fail-open `.onErrorResume` block must distinguish a 429 `AppException` (rethrow) from generic `Throwable` (swallow + WARN).
- Duplicate-key race: catch `org.springframework.dao.DuplicateKeyException` after the persist step. Discriminate via the index name in the exception message (`projectId_unique_connected` vs `telegramBotId_unique_connected`). **Driver caveat:** if `getMessage()` does NOT include the index name on this version of `mongodb-driver-sync` / Spring Data Mongo Reactive, fall back to inspecting the suppressed `MongoCommandException.getErrorMessage()`, OR treat both unique-violation paths uniformly with a recheck query (`findFirstByTelegramBotIdAndStatus(botId, CONNECTED)` — row present ⇒ platform-wide conflict, otherwise per-project). Either fallback is acceptable; pick one and cover it with a unit test.
- Webhook secret generation: use `SecureRandom` for the 16-byte plaintext, hex/Base64-encode for the Telegram header, hash via `MessageDigest` (SHA-256) and hex-encode (`HexFormat`). Plaintext lives only on the stack of the Connect call.
- Encryption-boundary encoding (cross-task with T1): `TokenEncryptor.encrypt(...)` returns `EncryptedValue(byte[] iv, byte[] ciphertext)` — raw bytes, no encoding (per T1 D15: the crypto component is generic, knows nothing about persistence). `Bot.encryptedTokenIv` and `Bot.encryptedTokenCiphertext` are declared as `String` (Base64) per tech-spec Data Models lines 292–293. `BotService` is the single place that owns the encoding boundary: Base64-encode on Connect (`Base64.getEncoder().encodeToString(bytes)`) before constructing the `Bot` for save; Base64-decode on Disconnect (`Base64.getDecoder().decode(string)`) before calling `tokenEncryptor.decrypt(ivBytes, ctBytes)`. Use `java.util.Base64` (standard encoder, not URL-safe). Cover this boundary explicitly with `connect_encryptedTokenAndIvAreBase64EncodedBeforeSave` and `disconnect_base64DecodesIvAndCiphertextBeforeDecrypt`.
- Compensating `deleteWebhook`: use `Mono.onErrorResume` around the persist step to issue a best-effort `telegram.deleteWebhook(token)`, swallow any error from the compensation itself (WARN only), then rethrow the original persist error so the caller still sees it. Never let the compensation shadow the original exception.
- Webhook URL: `@Value("${app.url}")` injected; compose as `appUrl + "/webhooks/telegram/" + projectId`.
- Audit metadata maps: `bot_connected` carries `{projectId, telegramBotId, telegramUsername}`; `bot_disconnected` carries `{projectId, telegramBotId, webhookDeleted}`. **Forbidden values in any metadata field:** plaintext token, encrypted-token bytes, IV, webhook-secret plaintext, webhook-secret hash.
