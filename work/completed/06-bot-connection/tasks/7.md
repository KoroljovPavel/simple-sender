# Task 7: Frontend bot store + types

## Required Skills

Перед выполнением задачи загрузи:
- `/skill:code-writing` — [skills/code-writing/SKILL.md](../../../.claude/skills/code-writing/SKILL.md)

## Description

Frontend layer for the Bot domain — a Pinia setup-store and TypeScript types that mirror the
backend `BotResponse` (Task 3 / Task 8 DTO) and feed Task 9's Settings → Bot page. The store
owns:

- the single "current bot for the active project" entity (or `null` when none),
- duplicate-fetch guarding via `inFlight: Promise<Bot | null> | null` (mirrors the
  pattern in `frontend/stores/projects.ts:46`),
- the four lifecycle actions matching the Task 8 endpoints (`fetch`, `connect`, `disconnect`,
  `sendTestMessage`),
- a `watch` on `useProjectsStore().currentProjectId` that re-fetches on project switch so the
  Settings → Bot page never displays stale data from a previous project.

Security boundary (D17 + AC17): the raw Telegram token entered by the user is a write-only
secret in this store. It must flow into `useApi()` as a POST body and nowhere else — no URL
parameter, no error message, no log line, no reactive ref that pinia devtools could snapshot.
The `connect(projectId, token)` action receives the token as a function argument, hands it to
`useApi()` immediately, and lets it go out of scope. Persisted state holds only the masked
`tokenSuffix` returned by the backend (D17).

Unlike `stores/projects.ts`, this store does NOT touch localStorage — there is no
"last-selected bot" concept; the bot is derived from the currently-selected project.

## What to do

1. Create `frontend/types/bot.ts`:
   - `BotStatus` union `'connected' | 'disconnected'` (lowercase — user-spec AC1 quotes
     `status:"connected"` verbatim; the backend wire format is lowercase).
   - `Bot` interface mirroring `BotResponse` from tech-spec lines 309–316:
     `telegramBotId: number` (Long → `number`; values fit in JS safe-integer range for
     Telegram bot IDs), `telegramUsername: string`, `telegramFirstName: string`,
     `tokenSuffix: string`, `status: BotStatus`, `connectedAt: string` (Instant serialized
     as ISO-8601 — matches `Project.createdAt` precedent in `frontend/types/project.ts`).

2. Create `frontend/stores/bot.ts` as a Pinia setup-store named `'bot'`:
   - State refs: `current = ref<Bot | null>(null)`. Module-scoped (NOT exposed via `return`)
     `inFlight: Promise<Bot | null> | null` variable for the fetch dedup guard — same shape
     as `stores/projects.ts:46`. The token MUST NOT live on any ref or in any closure that
     survives the `connect()` call.
   - Actions (all using `useApi()`):
     - `fetch(projectId: string): Promise<Bot | null>` — GET
       `/api/v1/projects/{projectId}/bot`. Dedup via `inFlight`. On 404 set `current = null`
       and resolve to `null` (per AC14). On 200 store the response in `current` and resolve
       to it. Other errors propagate.
     - `connect(projectId: string, token: string): Promise<Bot>` — POST
       `/api/v1/projects/{projectId}/bot/connect` with `body: { token }`. On success store
       the response in `current` and return it. The `token` parameter MUST be passed only
       inside `body`; never interpolated into the URL, never spread into an error object,
       never assigned to a ref.
     - `disconnect(projectId: string): Promise<void>` — POST
       `/api/v1/projects/{projectId}/bot/disconnect`. On success set `current = null`.
     - `sendTestMessage(projectId: string): Promise<void>` — POST
       `/api/v1/projects/{projectId}/bot/test-message`. No state mutation on
       success/failure (the bot record doesn't change; UI surfaces the outcome via
       `useApiError` in Task 9).
   - Watcher: inside the `defineStore` factory,
     `watch(() => useProjectsStore().currentProjectId, (newId) => { current.value = null;
     if (newId) fetch(newId) })`. This clears stale state synchronously on switch and
     re-fetches when the new id is non-null. SSR-safety: gate or rely on the same pattern
     used by `stores/projects.ts` — Pinia setup-stores under Nuxt don't fire watchers on
     server by default for plain refs, but verify against the existing code before adding
     `import.meta.client` guards.
   - Return: `{ current, fetch, connect, disconnect, sendTestMessage }`. Do NOT return
     `inFlight` (private dedup token).

3. No localStorage writes. No `console.log` calls that include the token argument. No
   re-export or storage of the `token` argument from `connect()` beyond the immediate
   `useApi()` call's `body`.

- `frontend/tests/stores/bot.spec.ts` (new) — vitest unit tests following the test setup in

**Wire-format contract (CRITICAL — cross-task convention):**

The `status` field is serialized as **lowercase** on the wire: `"connected"` / `"disconnected"`.
This is the source of truth for the whole feature and is anchored in user-spec AC1
(`status:"connected"`). All three layers MUST agree:

- **Task 3** (`BotStatus` enum, backend domain) — Java enum constants are uppercase
  (`CONNECTED`, `DISCONNECTED`), but Jackson serialization must emit lowercase. Achieve via
  `@JsonValue` on a `getValue()` method returning `name().toLowerCase()`, or `@JsonProperty`
  on each constant. Default Jackson behavior (uppercase `"CONNECTED"`) is INCORRECT and
  contradicts AC1 — Task 3 must override it. Symmetric deserialization (`@JsonCreator`
  accepting lowercase) is required if any inbound DTO ever carries `status`.
- **Task 8** (`BotResponse` DTO + controller tests) — the AC test assertions must check
  lowercase: e.g. `.andExpect(jsonPath("$.status").value("connected"))`. If a controller
  test asserts uppercase, that test is wrong and Task 8 must be fixed, not Task 7.
- **Task 7** (this task — frontend `BotStatus` union) — `'connected' | 'disconnected'`
  literal-type union, lowercase. Mirrors the wire format directly; no transform layer.

If during implementation the Task 3 / Task 8 backend lands with uppercase serialization,
that is a backend bug — file a follow-up against Task 3, do NOT widen the Task 7 union to
accept both cases.

**Dependencies:**
- Task 3 (Bot domain layer) — defines `BotStatus` enum + `Bot` entity. Serialization casing
  is specified above; this Task 7 union mirrors it 1:1.
- Task 8 (BotController + DTOs) supplies the runtime endpoints — not a hard build
  dependency for Task 7's unit tests (they mock `useApi`). Task 8's controller test
  assertions must use the lowercase wire format specified above.

**Edge cases:**
- Concurrent `fetch(projectId)` calls — dedup via `inFlight`, mirroring
  `stores/projects.ts:75-91`. Reset `inFlight = null` in a `finally` block.
- 404 on GET — AC14 says no bot is a valid state; resolve to `null`, do NOT reject. Catch
  the rejection from `useApi` and inspect `err.response?.status` (ofetch convention — see
  `frontend/composables/useApi.ts:50-77` for the existing 404 interceptor's reading of the
  same field). Re-throw on anything other than 404.
- Project switch mid-fetch — when the watcher fires while a previous `fetch` is pending,
  the older promise must not stomp `current` with stale data. Clear `current = null`
  synchronously in the watcher (before awaiting the new fetch). Stronger fix: capture
  `projectId` in the action and discard the result if it no longer equals the current
  selection. Pick whichever pattern matches the rest of the codebase (see
  `stores/projects.ts:124-127` `handleStaleCurrent` for precedent).
- SSR — the watcher should not eagerly fire a fetch during server render. Mirror whatever
  `stores/projects.ts` does (no explicit guard exists there for watchers because `fetchAll`
  is invoked by page-level `onMounted`, not by a watcher; for this store, gate with
  `if (import.meta.client)` if the watcher would otherwise fire on SSR hydration).
- Pinia devtools state inspection — `current` will be visible. That's fine: it carries
  `tokenSuffix` only, never the raw token. The `token` argument to `connect()` lives only
  on the call stack and in the `$fetch` request body — neither is in `$state`.

**Implementation hints:**
- Test the "no token in state after connect" invariant with
  `expect(JSON.stringify(store.$state)).not.toContain(TOKEN)`. Pick a token value clearly
  distinct from any other string in the response (e.g.
  `'1234567890:TKN_UNIQ_MARK_abcdefghijklmnopqr'`).
- Test the URL hygiene invariant by inspecting `apiMock.mock.calls[0][0]` (URL) and
  asserting it does not contain the token substring. Inspect
  `apiMock.mock.calls[0][1].body.token` to confirm it IS in the body.
- For the watcher test, do NOT mutate `useProjectsStore().currentProjectId` directly from
  the test body — drive transitions through the projects-store's public action surface
  (`selectProject(id)` for a value, `selectProject(null)` for the null transition — the
  store does not expose a separate `clearSelection()`) so the test exercises the same
  code path real consumers do. Either bootstrap Pinia with `setActivePinia(createPinia())` and
  use the real projects-store, or use `createTestingPinia({ stubActions: false })` from
  `@pinia/testing`. Await `nextTick()` after the action call so the `watch` callback
  flushes before assertions. Reference `frontend/tests/stores/projects.spec.ts` for the
  bootstrap pattern.
- For the 404 path, `apiMock` can reject with `Object.assign(new Error('Not Found'),
  { response: { status: 404 } })` to simulate the ofetch error shape.
