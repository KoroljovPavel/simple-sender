## Description

Build the HTTP layer of the bot module on top of the already-implemented `BotService` (Task 6). Introduces `com.botfunnel.bot.BotController` mapping `/api/v1/projects/{projectId}/bot` with four endpoints — `GET /`, `POST /connect`, `POST /disconnect`, `POST /test-message` — plus the two request/response DTOs `ConnectBotRequest` (carrying the AC2 bean-validation regex per D16) and `BotResponse` (carrying the `tokenSuffix` and never the raw or encrypted token per D17).

The controller is a thin orchestrator: it pulls `ownerId` from the security context, extracts IP and capped User-Agent from the `ServerWebExchange`, delegates to `BotService`, and maps the returned `Bot` to `BotResponse`. The token-format regex on `ConnectBotRequest.token` short-circuits malformed tokens at the bean validator with a 400 from `GlobalErrorHandler` so `BotService.connect` never sees them and no Telegram call ever fires for a malformed token (AC2). `@JsonIgnoreProperties(ignoreUnknown = true)` on the request DTO defends against mass-assignment per the platform pattern (matches `CreateProjectRequest`).

The companion `BotControllerIT` exercises every scenario from tech-spec Testing → Integration tests against a `MockWebServer` standing in for `api.telegram.org`. The Telegram base URL is overridden per test class via `@DynamicPropertySource` to point at the mock. `WebTestClient` is used with `.mutateWith(csrf())` and `@WithMockAppUser` for authenticated POSTs, exactly as `ProjectControllerIT` does. `BotTokenLeakTest` is a small reflective assertion verifying no production code path serialises the encrypted-token fields of the `Bot` entity through `BotResponse` (R1 / AC17 enforcement).

This is the last backend piece of the lifecycle before frontend wiring (Task 9). After this lands, the full Connect / Disconnect / Get / TestMessage HTTP contract is locked.

5. Create `BotTokenLeakTest` at `backend/src/test/java/com/botfunnel/bot/BotTokenLeakTest.java`:

   - Reflectively assert: (a) `BotResponse.class.getRecordComponents()` does NOT include `encryptedTokenCiphertext`, `encryptedTokenIv`, or `token`; (b) `Bot.class` does not declare or inherit a `toString` / serialization path that exposes the encrypted-token fields. ## Acceptance Criteria

- [ ] `POST /api/v1/projects/{projectId}/bot/connect` with a valid token returns 200 + `BotResponse{telegramBotId, telegramUsername, telegramFirstName, tokenSuffix, status:"connected", connectedAt}`; no raw/encrypted token in response (AC1, D17). **Wire-format note:** the JSON `status` value is lowercase `"connected"` / `"disconnected"` per user-spec AC1 — the Java enum `BotStatus.CONNECTED` must serialise to lowercase (Jackson `@JsonValue` on `BotStatus.name().toLowerCase()` or `spring.jackson.serialization.write-enums-using-to-string=true` + `toString` override). Tasks 3 (Mongo partial filter), 6 (service), 7 (frontend `'connected' | 'disconnected'` union), and 8 (HTTP) all agree on this convention: enum names stay uppercase inside the JVM and in Mongo; HTTP/JSON values are lowercase.
- [ ] Format-invalid token returns 400 from the bean validator; `BotService.connect` is never invoked; MockWebServer receives zero requests (AC2, D16).
- [ ] Telegram 401 on getMe → 422 with code `invalid_bot_token`; no `bots` document persisted (AC3).
- [ ] Telegram 5xx retry-exhausted on getMe or setWebhook → 502 `telegram_unavailable`; no document persisted (AC4).
- [ ] Telegram 4xx with config description on setWebhook → 500 `webhook_config_error`; operator log carries the Telegram `description` (AC5, D8).
- [ ] Platform-wide bot uniqueness violation → 409 `bot_already_connected` (AC6, D1).
- [ ] Per-project bot uniqueness violation → 409 `bot_already_in_project` (AC7, D5).
- [ ] Persist-after-setWebhook failure triggers compensating `deleteWebhook` and returns 500 (AC9, D4); MockWebServer's recorded-request log shows `setWebhook` followed by `deleteWebhook`.
- [ ] Webhook URL passed to Telegram equals `${app.url}/webhooks/telegram/{projectId}`; secret passed is a freshly generated random value per Connect (AC10).
- [ ] Brute-force counter at 11 returns 429 with no further Telegram calls; counter is DELed on a successful Connect; Redis down → Connect still succeeds with the dedicated WARN log line emitted (asserted via a Logback `ListAppender<ILoggingEvent>` attached to `BotService`'s logger — same helper pattern Task 6's unit tests use). No Micrometer assertion — Task 6 does not inject `MeterRegistry` and the project has no actuator dependency (AC11, D14).
- [ ] Two concurrent Connects with the same token: exactly one 200, the other 409 `bot_already_connected`; compensating `deleteWebhook` recorded for the loser (AC12).
- [ ] Two concurrent Connects with different tokens to the same project: exactly one 200, the other 409 `bot_already_in_project`; compensating `deleteWebhook` recorded (D5).
- [ ] `POST /disconnect` retries `deleteWebhook` on transient Telegram failures, proceeds on persistent failure with WARN, atomically updates Mongo (status DISCONNECTED, `encryptedTokenCiphertext`/`encryptedTokenIv`/`tokenSuffix`/`webhookSecretHash` all null, `disconnectedAt` set), returns 200; no connected bot → 404 (AC13).
- [ ] `GET /` returns 200 + AC1-shape `BotResponse` when connected; 404 when none (AC14).
- [ ] `POST /test-message` returns 422 with code `owner_chat_id_unknown` in 06; zero Telegram calls; zero `bot_test_message_sent` events emitted (AC15, D7).
- [ ] `ProjectService.requireOwned` is the first reactive step on every endpoint; foreign / soft-deleted / malformed `projectId` all collapse to 404; hostile body fields (`ownerId`, …) ignored by `@JsonIgnoreProperties(ignoreUnknown = true)` (AC16).
- [ ] No HTTP response body field and no event-metadata value matches the Telegram-token regex (AC17, AC23).
- [ ] Integration test asserts the emitted `bot_connected` event has metadata map = `{projectId, telegramBotId, telegramUsername}` (Task 6 contract). `ip` and `userAgent` are TOP-LEVEL fields on the `Event` document (set by `EventService.logEvent(userId, eventType, ipAddress, userAgent, metadata)`) — asserted via `evt.getIpAddress()` / `evt.getUserAgent()`, NOT via the metadata map. No value in the metadata map regex-matches `^\d{1,20}:[A-Za-z0-9_-]{30,50}$` (AC23 audit-event metadata shape + token-leak negative assertion). Same shape for `bot_disconnected`: metadata = `{projectId, telegramBotId, webhookDeleted}`; `ip`/`userAgent` asserted top-level the same way.
- [ ] `BotResponse` carries `tokenSuffix` (last 3 chars of the secret); the persisted `Bot.tokenSuffix` matches; nothing else token-derived ever leaves the backend (AC18, D17).
- [ ] `webhookSecretHash` in Mongo is hex-encoded SHA-256 of the plaintext sent to Telegram, not the plaintext itself (AC20, D2).
- [ ] `./gradlew :backend:test --tests "com.botfunnel.bot.*"` passes including the full integration suite.
- [ ] `BotTokenLeakTest` reflective assertion confirms no production path serializes the encrypted-token fields of the `Bot` entity through `BotResponse`.
