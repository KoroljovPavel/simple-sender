# Task 1: Promote `TelegramApiClient` helpers and timeout constants to public

## Required Skills

Before starting, load:
- `/skill:code-writing` — [SKILL.md](../../../.claude/skills/code-writing/SKILL.md)

## Description

Per tech-spec Decision 12, `TelegramSender` (Wave 2, Task 4) must reuse the same transient-failure classifier, the same token-shape guard, and the same connect/response timeout values that `TelegramApiClient` already encodes — instead of duplicating four module-local items across both classes. This task widens the visibility of four members on `TelegramApiClient` from `private static` to `public static` so a second consumer can call them directly:

- `requireValidTokenShape(String)` — single source of truth for the bot-token regex shape check (matches `TOKEN_SHAPE`). The sender will invoke this immediately after AES-GCM decrypt and before constructing the WebClient URI, to defend against tampered Mongo state being concatenated into the path template.
- `isTransient(Throwable)` — single source of truth for "what counts as transient" (`WebClientResponseException` 5xx, `IOException`, `TimeoutException`, `ReadTimeoutException`, walked up the cause chain). The sender's 5xx-retry loop will use it verbatim as its `Retry.filter(...)` predicate.
- `DEFAULT_RESPONSE_TIMEOUT` (10s) and `CONNECT_TIMEOUT` (5s) — the connect/read timeout pair already used by the connect-flow `WebClient`. The sender constructs its own `WebClient` instance (different retry policy, different audit semantics) but must read the same two values so AC5 ("WebClient timeouts: 5s on TCP-connect, 10s on response read. Reuse констант з `TelegramApiClient`") is satisfied without re-declaring constants.

The change is purely visibility. Signatures, bodies, and values stay byte-identical — recompile-clean, no behavior change, no call-site change inside `TelegramApiClient`. Mirrors the existing precedent at `TelegramApiClient.java:171` where `scrubTokens` was promoted earlier for the same kind of reuse, with the same explanatory comment style. The unrelated `MONO_TIMEOUT` (10s) and `CAUSE_CHAIN_MAX_HOPS` (16) constants stay private — `TelegramSender` has its own outer 30s timeout (Decision 8) and inherits cause-chain depth transitively via `isTransient` itself.

## What to do

1. Promote `requireValidTokenShape(String)` from `private static void` to `public static void`. Add a one-line comment above the method noting it is promoted for `TelegramSender` reuse — same comment style as the existing `scrubTokens` promotion comment (`TelegramApiClient.java:169-170`).
2. Promote `isTransient(Throwable)` from `private static boolean` to `public static boolean`. Add the same style of one-line promotion comment.
3. Promote `DEFAULT_RESPONSE_TIMEOUT` from `private static final Duration` to `public static final Duration`. Add a one-line comment noting it is shared with `TelegramSender`'s WebClient construction.
4. Promote `CONNECT_TIMEOUT` from `private static final Duration` to `public static final Duration`. Add a one-line comment noting it is shared with `TelegramSender`.
5. Leave `MONO_TIMEOUT`, `CAUSE_CHAIN_MAX_HOPS`, `TOKEN_PATTERN`, and `TOKEN_SHAPE` as `private`. They are not consumed by `TelegramSender` and must not be widened in this task.
6. Verify the existing `TelegramApiClientTest` suite still passes unchanged — this is a visibility-only change, so all current assertions must hold and no test rewrite is required. No new test file is added in this task; coverage for the promoted members will arrive with `TelegramSenderTest` in Task 4.
