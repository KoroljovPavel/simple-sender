## Description

Final-wave acceptance testing for feature `07-telegram-sender` (Epic 04c — TelegramSender Service) before deploy. Executes the full backend test suite, then maps every user-spec acceptance criterion (AC1–AC23) and every tech-spec acceptance criterion (11 items in `tech-spec.md` → "Acceptance Criteria") to concrete test evidence (test class + method name, code snippet, mongosh output, curl response, or grep result). Verifies the agent-perspective checks from user-spec "Як перевірити → Агент перевіряє": all `./gradlew test` green, `ListAppender` token-leak assertions present and asserted, the `curl` null-branch regression returns 422 `owner_chat_id_unknown`, the mongosh nullable-schema check confirms pre-feature documents read back with `ownerChatId == null`, and `SecurityConfig.java` has zero diff.

This task does NOT write or modify production/test code. If any check fails, the QA agent stops, produces a NO-GO report listing each failure with file/test/output references, and the gap is fixed in a follow-up task (a re-run of the appropriate implementation task or a new fix task) before re-running QA — pre-deploy QA only signs off; it does not patch code itself.

No code review on this task (Final Wave — QA is its own verification, no production deliverables produced). No Post-deploy verification task in this feature per `tech-spec.md` → "Agent Verification Plan": the happy path is unobservable in production until Epic 04b webhook ingestion populates `Bot.ownerChatId`; the 422 null-branch yields the same response as before the feature shipped (regression coverage already in tests); the staging-smoke runbook `docs/staging-smoke/07-telegram-sender.md` (produced by Task 6) documents the opt-in manual procedure for exercising the success branch with seeded Mongo state.
