# Task 2: Add nullable `ownerChatId` field to `Bot`

## Required Skills

Before starting, load:
- `/skill:code-writing` — [skills/code-writing/SKILL.md](../../../.claude/skills/code-writing/SKILL.md)

## Description

Add a nullable `Long ownerChatId` field on the `Bot` Mongo entity. This field will later be populated by Epic 04b webhook ingestion (the Telegram user's chat id resolved when the owner sends `/start` to their bot). For Epic 04c (TelegramSender), the field must exist on the entity so `BotService.sendTestMessage` can branch on it: when `null`, keep the existing 422 `owner_chat_id_unknown` stub; when present, dispatch via `TelegramSender.sendText`.

This task is foundation-only — no read/write call sites are added in this task, and no migration script is shipped. Spring Data MongoDB transparently reads missing wrapper-type fields as `null` (same pattern already used by sibling field `disconnectedAt`); however, this codebase has no prior test exercising the read side of that behavior, so a new repository-level test is added that persists a Bot without setting `ownerChatId`, reads it back via `findById`, and asserts the field is `null`. This serves as both regression net (Risk R6 in tech-spec) and explicit documentation of the legacy-document deserialization contract.

The field must NOT add a `toString` override (would regress `BotTokenLeakTest.botEntityDoesNotDeclareToStringExposingEncryptedTokenFields`) and must NOT carry an `@Indexed` annotation (no query path filters by `ownerChatId`; sender uses `findById`).

## What to do

1. Add the `ownerChatId` field on `Bot.java` between the `telegramFirstName` field and the `status` field. Use the wrapper type `Long` (not primitive `long`) so missing legacy documents read back as `null`. Provide standard JavaBean public getter and setter following the existing accessor pattern in `Bot.java`. Do not annotate with `@Indexed`. Do not add a `toString` method.

2. Update the `newBot(...)` helper in `BotRepositoryTest` if needed so existing tests stay green without referencing the new field (legacy callers should still work — confirms the field is truly optional from the entity-construction perspective).

3. Add a new test method in `BotRepositoryTest` that:
   - Builds a `Bot` via the existing `newBot(...)` helper without calling `setOwnerChatId(...)`.
   - Saves it via `botRepository.save(bot).block()`.
   - Reloads it via `botRepository.findById(saved.getId())`.
   - Asserts (via `StepVerifier`) that the reloaded bot's `getOwnerChatId()` returns `null` without any deserialization error.

4. Confirm `BotTokenLeakTest` still passes — specifically `botEntityDoesNotDeclareToStringExposingEncryptedTokenFields`, which fails if `Bot` declares any custom `toString()`.

## Details

**Files:**
- `backend/src/main/java/com/botfunnel/bot/Bot.java` — add `private Long ownerChatId;` declaration immediately after `private String telegramFirstName;` and before `private BotStatus status;`. Add public getter/setter after the `setTelegramFirstName(...)` accessor and before the `getStatus()` accessor — follow the existing one-line accessor convention (e.g. `public Long getOwnerChatId() { return ownerChatId; }`). Wrapper type `Long`, not primitive — primitive would default to 0 on legacy documents and silently mask the "field absent" case.
- `backend/src/test/java/com/botfunnel/bot/BotRepositoryTest.java` — add one new `@Test` method. Use the existing `newBot(...)` helper (do not touch its signature). Save the bot, then chain a `findById(savedId)` call via `botRepository.save(bot).flatMap(saved -> botRepository.findById(saved.getId()))` and verify with `StepVerifier.create(...).assertNext(reloaded -> assertThat(reloaded.getOwnerChatId()).isNull()).verifyComplete()`.

**Dependencies:** None (other Wave 1 tasks are independent: Task 1 promotes `TelegramApiClient` helpers, Task 3 creates new exception/DTO files).

**Edge cases:**
- Legacy documents stored before this task ran will not have an `ownerChatId` field in BSON. The new test verifies Spring Data MongoDB reads these as `null` — that is the contract, not an accident.
- The `newBot(...)` helper does not set `ownerChatId`, so all existing tests now implicitly persist documents with `ownerChatId == null` after the field exists. This is intentional and is what the new test verifies on the read side.
- Wrapper `Long` vs primitive `long`: primitive would deserialize missing fields to 0, breaking the "field absent" semantics and silently hiding the very condition `BotService.sendTestMessage` will branch on.

**Implementation hints:**
- Match the placement and style of the sibling nullable wrapper `Instant disconnectedAt` — it sits at the bottom of the field declarations and has a plain `getDisconnectedAt`/`setDisconnectedAt` pair without annotations. `ownerChatId` follows the same shape, but per tech-spec Decision 14 the placement is specifically between `telegramFirstName` and `status`.
- `BotTokenLeakTest` uses reflection to enumerate declared methods on `Bot.class`. Adding a getter/setter pair is fine — it filters by method name `"toString"` with zero parameters.
- Keep the diff to `Bot.java` minimal: one field line, two accessor lines. No JavaDoc, no annotations.
- `BotResponse` (the API DTO) deliberately does NOT expose `ownerChatId` — tech-spec Acceptance Criteria explicitly require zero diff to `BotResponse.java`.
