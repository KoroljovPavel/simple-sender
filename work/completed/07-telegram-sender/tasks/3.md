# Task 3: Create exceptions, records, and event constants

## Required Skills

Before starting, load:
- `/skill:code-writing` — [skills/code-writing/SKILL.md](../../../.claude/skills/code-writing/SKILL.md)

## Description

Create the typed exception classes and DTO records that the Wave 2 `TelegramSender` bean (Task 4) and the Wave 3 `BotService.sendTestMessage` rewrite (Task 5) consume. This is pure scaffolding — no business logic, no Spring wiring, no tests beyond compilation.

Six new files in the `bot/` and `bot/dto/` packages:

- Three exceptions implementing Decision 5 (tech-spec): two extend the platform-wide `AppException` so they round-trip through `GlobalErrorHandler` with the right HTTP status + business code; one is a package-private internal sentinel that exists only to carry `retry_after` between the 429 detection site and the `.retryWhen` filter inside `TelegramSender`.
- Three records that mirror the Telegram `sendMessage` response shape (`TelegramSendResult<T>` + nested `TelegramSendParameters`) and the typed success return value (`SentMessage`) returned to callers. The wire-shape records intentionally use Telegram's snake_case field names (`error_code`, `retry_after`) so Jackson can deserialize without `@JsonProperty` annotations — this mirrors the existing `TelegramResult<T>` precedent in the same package.

Per Decision 9, these records are deliberately separate from `TelegramResult<T>` (used by Connect-flow methods on `TelegramApiClient`). Keeping the lean four-field `TelegramResult<T>` untouched preserves the existing fallback construction at `TelegramApiClient.mapClientError` (lines 122–123) and lowers the blast radius of this feature.

## What to do

1. Create `backend/src/main/java/com/botfunnel/bot/BotTokenInvalidException.java` — `public class` extending `AppException`. Constructor `(String botId, String reason)` calls `super(HttpStatus.UNPROCESSABLE_ENTITY, "invalid_bot_token", reason)`. Stores `botId` as a `private final` field with a public getter; the field is for log context (WARN lines around decryption failures) and is NOT exposed through the HTTP response body.
2. Create `backend/src/main/java/com/botfunnel/bot/TelegramSendException.java` — `public class` extending `AppException`. Constructor `(Integer errorCode, String scrubbedDescription, int attempts)` calls `super(HttpStatus.BAD_REQUEST, "telegram_send_failed", scrubbedDescription)`. Stores `errorCode` (`Integer`, nullable — null for transient-exhausted / timeout terminal failures) and `attempts` (`int`, total HTTP attempts) as `private final` fields with public getters. The `scrubbedDescription` parameter name documents the caller's obligation: this constructor never scrubs — callers MUST pass a string that has already been run through `TelegramApiClient.scrubTokens(...)`.
3. Create `backend/src/main/java/com/botfunnel/bot/TelegramRateLimitException.java` — package-private class (no `public` modifier on the class) extending `RuntimeException`. Constructor `(int retryAfterSeconds)`; stores the value as a `private final int` with a package-private getter. No HTTP status, no business code — this exception is internal to the `.retryWhen` filter in `TelegramSender` and never reaches `GlobalErrorHandler`. Per Decision 5 / Architecture step 11, package-private visibility prevents accidental cross-package use and documents intent.
4. Create `backend/src/main/java/com/botfunnel/bot/dto/SentMessage.java` — `public record SentMessage(Long chatId, Long messageId, Instant sentAt) {}`. Returned by `TelegramSender.sendText` on success; embedded in the `telegram_message_sent` audit event metadata.
5. Create `backend/src/main/java/com/botfunnel/bot/dto/TelegramSendResult.java` — `public record TelegramSendResult<T>(boolean ok, T result, Integer error_code, String description, TelegramSendParameters parameters) {}`. Field names match Telegram's wire format verbatim — do NOT camelCase `error_code` or `retry_after` because Jackson deserializes by record-component name. Document with a brief Javadoc that explains why (mirror the existing `TelegramResult.java` style — minimal, one-line comment is sufficient).
6. Create `backend/src/main/java/com/botfunnel/bot/dto/TelegramSendParameters.java` — `public record TelegramSendParameters(Integer retry_after) {}`. Same snake_case rationale as above. `Integer` (not `int`) because Telegram may omit the field on non-429 responses, and a missing/null `retry_after` is a valid input the 429 handler must clamp to zero.
7. Verify all six files compile cleanly by running `cd backend && ./gradlew compileJava`.
8. Verify no existing tests regress: `cd backend && ./gradlew test`.

**Downstream consumers (do not implement here — they belong to Tasks 4 and 5):**

- `TelegramSender` (Task 4) constructs `BotTokenInvalidException` after decryption failures and after `requireValidTokenShape` rejects the plaintext; constructs `TelegramSendException` on 4xx (non-401), `ok=false` responses, transient-retry exhaustion, and overall timeout; throws `TelegramRateLimitException` inside `.onStatus` for 429 and filters on it inside `.retryWhen(rateLimitRetry)`. Returns `SentMessage` on success. Deserializes the response body as `TelegramSendResult<JsonNode>` via `ParameterizedTypeReference`.
- `BotService.sendTestMessage` (Task 5) does not construct any of these directly — it lets sender exceptions propagate through `GlobalErrorHandler`.

**Edge cases / decisions baked into the shapes:**

- `BotTokenInvalidException.botId` is captured for log context only. Architecture step 3 specifies WARN logging "with scrubbed context for ops review". `getBotId()` is callable from log statements; the field MUST NOT be exposed on the HTTP response (the response shape comes from `AppException` + `GlobalErrorHandler`).
- `TelegramSendException.errorCode` is `Integer` (nullable) because terminal exhaustion (`"transient_failure_exhausted"`) and overall timeout (`"timeout"`) have no upstream error code. The 4xx-mapping path always passes a non-null `errorCode`.
- `TelegramSendException.attempts` is `int` (not `Integer`) because every terminal path goes through the chain that increments `AtomicInteger attempts` — there is always a count ≥ 1.
- `TelegramSendException.scrubbedDescription` parameter name documents the caller's obligation. Per Architecture "Scrubber coverage", every call site MUST pre-scrub the string with `TelegramApiClient.scrubTokens(...)`. This task does NOT add scrubbing inside the constructor — that would split responsibility and let an unscrubbed string slip through if a future caller forgets.
- `TelegramRateLimitException` is package-private (Java default access). This prevents accidental imports from `BotService`, `BotController`, `GlobalErrorHandler`, or any test outside `bot/`. The retry filter inside `TelegramSender` lives in the same package and sees it.
- `TelegramSendResult.error_code` and `TelegramSendParameters.retry_after` use snake_case because Jackson record deserialization maps JSON keys to record component names by string equality. Renaming to camelCase would require `@JsonProperty` annotations on every component — the existing `TelegramResult<T>` (same package, same wire source) shows the project's chosen convention is snake_case-on-component.
- `TelegramSendParameters.retry_after` is `Integer` (nullable) — Telegram only includes the `parameters` object on 429 responses. On any other status the entire `parameters` value will deserialize to `null` and the field is unreachable; even if Telegram returned an empty `parameters: {}`, `retry_after` must be a wrapper to deserialize as null.
- `SentMessage` field order `(chatId, messageId, sentAt)` matches the Data Models declaration in tech-spec verbatim. Architecture step 9 destructures it positionally inside `sentMetadata(botId, sm)`; Task 4 assumes the order.

**Implementation hints:**

- Mirror the file shape of `TelegramResult.java` (already in `bot/dto/`) when writing the new records — a single-line record declaration plus a brief Javadoc is sufficient. Do NOT add accessor methods, factory methods, or `compact constructors`.
- For both `AppException` subclasses, follow Java convention: declare fields above the constructor, getters below the constructor.
- For `TelegramRateLimitException`: omit the `public` modifier on the class line entirely (`class TelegramRateLimitException extends RuntimeException { ... }`). The same omission applies to the getter (`int getRetryAfterSeconds()` not `public int getRetryAfterSeconds()`).
- Do not add `@JsonIgnoreProperties` or any Jackson annotations to the new records. The reactive WebClient uses Spring Boot's auto-configured `ObjectMapper`, which already tolerates unknown properties by default for record deserialization.
- Do not add `toString()`, `equals()`, or `hashCode()` overrides. Records get these for free; `AppException` subclasses inherit `Throwable.toString()` which is appropriate.
- Make sure the per-file package declaration matches the directory: `package com.botfunnel.bot;` for the three exceptions, `package com.botfunnel.bot.dto;` for the three records.
