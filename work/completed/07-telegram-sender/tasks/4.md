## Description

Implement the `TelegramSender` `@Component` (`backend/src/main/java/com/botfunnel/bot/TelegramSender.java`) — a reactive bean with a single public method `sendText(botId, chatId, text, parseMode?, ownerId?) → Mono<SentMessage>` that owns the entire outbound Telegram `sendMessage` policy: per-call token decryption, transient-failure retry with exponential backoff (1s/2s/4s, 3 retries after initial = 4 total attempts), 429 `parameters.retry_after` honoring as an outer loop wrapping the 5xx loop, overall 30s timeout, mapping of HTTP/payload errors to typed exceptions (`BotTokenInvalidException`, `TelegramSendException`), audit emission (`telegram_message_sent`/`telegram_send_failed`) via `EventService`, and token-scrubbed logging at every WARN/ERROR site.

Accompany with two test files: `TelegramSenderTest.java` (MockWebServer-based unit-style, no Spring context, 28 scenarios: 4 happy + 3 5xx + 6 429 + 3 4xx/payload + 5 pre-wire guards + 2 timeouts + 5 token-leak) and `TelegramSenderIT.java` (full Spring context with embedded Mongo + MockWebServer, 4 scenarios with Awaitility for fire-and-forget event assertions). Tests must cover every scenario enumerated in tech-spec → Testing Strategy verbatim; each retry/timeout scenario asserts an explicit `attempts` count to pin the `AtomicInteger attempts` semantics.

Token-decryption error handling is scoped narrowly per the updated tech-spec (Architecture step 3, Risk R7): only `IllegalArgumentException` from `Base64.getDecoder().decode(...)` is caught and mapped to `BotTokenInvalidException(botId, "decryption failed")`. `IllegalStateException` from `TokenEncryptor.decrypt` is NOT caught — `TokenEncryptor` wraps every `GeneralSecurityException` (including `AEADBadTagException` from a tampered ciphertext) into `IllegalStateException("AES-GCM decryption failed", cause)`, and a misconfigured `TokenEncryptor` bean also surfaces as `IllegalStateException`. Both failure modes are indistinguishable at the call site, so both propagate as 500 via `GlobalErrorHandler.handleThrowable` (Decision: surface to ops monitoring rather than mislead a user with a "fixable" 422).

This is the foundation for the success-branch of `BotService.sendTestMessage` (wired in Task 5) and is the primary outbound-Telegram primitive that Epic 06 (funnels) and Epic 07 (broadcasts) will reuse. No live Telegram involved — all Telegram traffic is scripted via okhttp3 MockWebServer (already in `build.gradle` as `testImplementation`).

**Note on the `bot_not_found` 404 shape:** `AppException.notFound(String)` (see `AppException.java:36-38`) is a SINGLE-ARG factory — its argument fills the `message` field and `code` is `null`. The existing precedent for the anti-enumeration branch is `BotService.requireConnectedBot` calling `AppException.notFound(BotService.MESSAGE_BOT_NOT_FOUND)` where `MESSAGE_BOT_NOT_FOUND = "Bot not found"` (`BotService.java:57`). Match that exact call shape — response body has `message: "Bot not found"`, `code: null`. The symbolic identifier `bot_not_found` used throughout the tech-spec and this task is SHORTHAND for "the anti-enumeration 404 produced by `AppException.notFound(MESSAGE_BOT_NOT_FOUND)`" — it is NOT a literal `code` value in the JSON response.

The bean uses Task 3's records (`SentMessage`, `TelegramSendResult<T>`, `TelegramSendParameters`) and exceptions (`BotTokenInvalidException`, `TelegramSendException`, `TelegramRateLimitException`). It calls Task 1's promoted helpers (`TelegramApiClient.requireValidTokenShape`, `TelegramApiClient.isTransient`, `TelegramApiClient.DEFAULT_RESPONSE_TIMEOUT`, `TelegramApiClient.CONNECT_TIMEOUT`) and the existing public `TelegramApiClient.scrubTokens`. The integration test also depends on Task 2's `Bot.ownerChatId` field.

**Edge cases:**
- **`IllegalArgumentException` has TWO distinct sources at the decrypt site — only ONE is catchable.** (1) `Base64.getDecoder().decode(...)` throws `IllegalArgumentException` on malformed Base64 — this is the data-corruption-at-storage-boundary case → catch and map to `BotTokenInvalidException(botId, "decryption failed")` → 422 `invalid_bot_token`. (2) `TokenEncryptor.decrypt(iv, ct)` ALSO throws `IllegalArgumentException` if `iv.length != 12` (see `TokenEncryptor.java:46-49`: `if (iv == null || iv.length != IV_BYTES) throw new IllegalArgumentException("AES-GCM IV must be exactly 12 bytes; got " + ...)`). This is a DIFFERENT failure mode — it signals corrupted storage or bad seed data (a previously-stored IV does not match the encryptor's expectation) and is operationally indistinguishable from the `IllegalStateException` AEAD-tag failure case → must propagate as 500 per Risk R7. **Never wrap the entire decrypt block in a single `catch (IllegalArgumentException)` — doing so would incorrectly produce 422 for a wrong-IV-length error.** The catch MUST be scoped exclusively to the Base64 decode calls; `tokenEncryptor.decrypt(iv, ct)` MUST live outside the catch.
- `parameters.retry_after` missing → treat as 0 (Reactor clamp via `Math.max(0, ...)`). Outer 30s timeout still caps the loop.
- `parameters.retry_after` negative → clamp to 0; same as missing.
- `parameters.retry_after` > 30s → clamp to 30s for a single delay; outer 30s timeout fires during the wait.
- JSON parse error in `TelegramSendResult` for a 4xx (malformed body) → fall back to empty result, treat as plain 4xx (`TelegramSendException`) per `TelegramApiClient.mapClientError` lines 122-123 precedent; do not enter 429 loop on malformed payload.
- `ok=true` with `result.message_id == null` → `TelegramSendException` (not `SentMessage`).
- `ok=true` with `result.chat == null` → fall back to the `chatId` argument from the caller when constructing `SentMessage`. Prefer `result.chat.id` when present (matches happy-path test expectation `SentMessage.chatId == 5`).
- Bot found with status `CONNECTING` or any non-CONNECTED state → 404 `bot_not_found` (anti-enumeration).
- Bot's `encryptedTokenCiphertext` / `encryptedTokenIv` is `null` (data-integrity bug — should not happen but defensive). `Base64.getDecoder().decode(null)` throws `NullPointerException` which is NOT caught — propagates as 500 (consistent with the "Base64-decode-only catch" scoping from Step 3 / Fix 1). Alternatively add a defensive null-check upstream producing `BotTokenInvalidException(botId, "decryption failed")`; either is acceptable, but the default (let NPE propagate) is correct per the narrow-catch policy.
- MockWebServer `setSocketPolicy(SocketPolicy.DISCONNECT_AT_START)` simulates a mid-response disconnect → triggers `IOException` in WebClient chain → `isTransient` catches it → retry.

*Sender flow (`sendText` method body) — 13 numbered steps per tech-spec Architecture lines 50-66:*

1. Allocate `AtomicInteger attempts = new AtomicInteger(0)` at the OUTERMOST lambda level, BEFORE any `Mono.defer` / `Mono.fromSupplier` that builds the per-attempt request. Critical: a counter declared inside the inner request supplier resets on every 429 resubscription. The outer-closure capture is what makes the `attempts == 4` semantics correct.
2. `botRepository.findById(botId)` → `.filter(bot -> bot.getStatus() == BotStatus.CONNECTED)` → `.switchIfEmpty(Mono.error(AppException.notFound(BotService.MESSAGE_BOT_NOT_FOUND)))`. Collapses both bot-not-found and bot-disconnected into a single 404 (anti-enumeration; same shape as `BotService.requireConnectedBot`). **Critical call-shape detail:** `AppException.notFound(String)` (`AppException.java:36-38`) is a single-arg factory that fills `message` (NOT `code`); the existing `BotService.MESSAGE_BOT_NOT_FOUND` constant is `"Bot not found"` (`BotService.java:57`) and that's the literal `message` in the response body. The response `code` is `null`. The token `bot_not_found` used in tech-spec / TDD anchor names / error-mapping tables is shorthand for "this 404", NOT a literal `code` value. Do NOT call `AppException.notFound("bot_not_found")` — that would put `"bot_not_found"` into `message` and break the existing pattern. If `BotService.MESSAGE_BOT_NOT_FOUND` is package-private (it is — see line 57: `private static final String`), either promote it to package-private accessibility for the sender to reuse (the sender lives in the same `com.botfunnel.bot` package, so package-private already works as long as the modifier is exactly `private static final` → change to `static final`), OR inline the literal `"Bot not found"` and add a code comment cross-referencing `BotService.java:57` to keep the two in sync. Inlining is acceptable.
3. `.flatMap(bot -> { ... decrypt ... })`. Inside, decode Base64 (`Base64.getDecoder().decode`) and call `tokenEncryptor.decrypt(iv, ct)`. Scope the catch narrowly: wrap ONLY the Base64 decode calls in try/catch on `IllegalArgumentException` and map to `Mono.error(new BotTokenInvalidException(botId, "decryption failed"))`. Do NOT wrap `tokenEncryptor.decrypt(...)` in a try/catch — let `IllegalStateException` (and any `NullPointerException`) propagate unwrapped. Per updated tech-spec Architecture step 3 / Risk R7: `TokenEncryptor.decrypt` wraps every `GeneralSecurityException` (including `AEADBadTagException` for a tampered ciphertext) into `IllegalStateException("AES-GCM decryption failed", cause)`, and a misconfigured `TokenEncryptor` bean also surfaces as `IllegalStateException`. The two failure modes are indistinguishable at this call site, so both must propagate as 500 via `GlobalErrorHandler.handleThrowable`. Do NOT inspect the cause chain to differentiate (rejected design — adds complexity for no operational benefit; ops monitoring is the correct response to either failure mode).

   **Critical scoping rule — `IllegalArgumentException` has TWO distinct sources at this site, and only Base64 is catchable:** (a) Base64 decode failure (malformed input) → catch → 422 `invalid_bot_token`. (b) `TokenEncryptor.decrypt(iv, ct)` itself throws `IllegalArgumentException` if `iv.length != 12` (`TokenEncryptor.java:46-49`); this signals corrupted storage / bad seed data and must propagate as 500 (same operational class as the `IllegalStateException` AEAD-tag failure). Wrapping the entire decrypt block in one broad `catch (IllegalArgumentException)` would incorrectly produce 422 for a wrong-length-IV error.

   **Required code shape — keep the two calls in SEPARATE try blocks:**
   ```java
   byte[] iv;
   byte[] ct;
   try {
       iv = Base64.getDecoder().decode(bot.getEncryptedTokenIv());
       ct = Base64.getDecoder().decode(bot.getEncryptedTokenCiphertext());
   } catch (IllegalArgumentException e) {
       return Mono.error(new BotTokenInvalidException(botId, "decryption failed"));
   }
   // tokenEncryptor.decrypt is OUTSIDE the catch:
   //   - IllegalArgumentException (wrong IV length) → propagate as 500
   //   - IllegalStateException (AEAD-tag failure / misconfigured bean) → propagate as 500
   //   - NullPointerException (defensive) → propagate as 500
   String plaintext = tokenEncryptor.decrypt(iv, ct);
   ```
   Anti-pattern (do NOT write): a single `try { byte[] iv = ...decode(...); byte[] ct = ...decode(...); String pt = tokenEncryptor.decrypt(iv, ct); } catch (IllegalArgumentException e) { ... }` — this swallows the wrong-IV-length signal and turns a 500-worthy storage-corruption signal into a user-facing 422 `invalid_bot_token`.
4. Immediately call `TelegramApiClient.requireValidTokenShape(plaintext)` — wrap in try/catch on `IllegalArgumentException` only, map to `Mono.error(new BotTokenInvalidException(botId, "invalid token shape after decrypt"))`. MUST happen BEFORE step 5 to prevent a tampered-Mongo token from being concatenated into the WebClient URI template.
5. Build POST body: `Map<String, Object> body = new HashMap<>(); body.put("chat_id", chatId); body.put("text", text); if (parseMode != null) body.put("parse_mode", parseMode);`. Mutable Map (not `Map.of`) because conditional `put` on an immutable map is awkward.
6. `webClient.post().uri("/bot{token}/sendMessage", token).bodyValue(body).retrieve()`. The `{token}` substitution is handled by `DefaultUriBuilderFactory` with `EncodingMode.NONE` (same shape as `TelegramApiClient`).
7. Inside the inner per-attempt Mono (returned by `.retrieve().bodyToMono(...)`), attach `.doOnSubscribe(sub -> attempts.incrementAndGet())`. First subscription = attempt 1. The counter is captured via the outer `AtomicInteger` reference.
8. `.onStatus(HttpStatusCode::is4xxClientError, this::map4xx)`. The `map4xx` helper:
   - Reads `response.statusCode().value()`.
   - Parses body to `TelegramSendResult<JsonNode>` with `.onErrorResume` fallback to empty result. Note: the precedent (`TelegramApiClient.mapClientError` lines 122-123) uses the 4-field `TelegramResult` (`new TelegramResult<>(false, null, null, null)`); `TelegramSendResult` has 5 fields (Task 3 added the `parameters` field), so the fallback shape here is `new TelegramSendResult<>(false, null, null, null, null)` — five `null`/`false` args (`ok=false, result=null, error_code=null, description=null, parameters=null`).
   - On 401 → `Mono.error(new BotTokenInvalidException(botId, "Token is invalid or revoked"))`.
   - On 429 → read `result.parameters() != null ? result.parameters().retry_after() : null`, default 0 if null. Log `log.warn("Telegram 429 retry_after={}s: {}", retryAfter, TelegramApiClient.scrubTokens(result.description()))`. Throw `Mono.error(new TelegramRateLimitException(retryAfter))`.
   - Other 4xx → log `log.warn("Telegram 4xx ({}): {}", rawStatus, TelegramApiClient.scrubTokens(result.description()))`. `Mono.error(new TelegramSendException(rawStatus, TelegramApiClient.scrubTokens(result.description()), attempts.get()))`.
9. `.bodyToMono(new ParameterizedTypeReference<TelegramSendResult<JsonNode>>() {})` then `.flatMap(result -> mapBodyToSentMessage(result, chatId))`:
   - If `result.ok() && result.result() != null && result.result().has("message_id")` → return `Mono.just(new SentMessage(extractChatId(result.result(), chatId), result.result().get("message_id").asLong(), Instant.now()))`. `extractChatId(JsonNode node, Long fallback)` guard pattern: `if (node.has("chat") && node.get("chat").has("id")) return node.get("chat").get("id").asLong(); else return fallback;`. Critical: do NOT null-check `node.get("chat")` — `JsonNode.get(String)` returns Jackson's `MissingNode` (not Java `null`) for absent fields, so `node.get("chat") != null` is always true. Use `.has("...")` for presence checks; `.get(...).asLong()` for value extraction.
   - Else → log WARN `log.warn("Telegram ok=false or missing message_id: {}", TelegramApiClient.scrubTokens(result.description()))`. `Mono.error(new TelegramSendException(null, TelegramApiClient.scrubTokens(result.description()), attempts.get()))`.
10. `.retryWhen(buildTransientRetry(attempts))` — inner 5xx loop. `Retry.backoff(3, Duration.ofSeconds(1)).maxBackoff(Duration.ofSeconds(4)).filter(TelegramApiClient::isTransient).doBeforeRetry(rs -> log.warn("Telegram transient retry #{} after error: {}", rs.totalRetries() + 1, TelegramApiClient.scrubTokens(rs.failure().getMessage()))).onRetryExhaustedThrow((spec, signal) -> new TelegramSendException(null, "transient_failure_exhausted", attempts.get()))`.
11. `.retryWhen(buildRateLimitRetry(attempts))` — outer 429 loop. Use `Retry.from(companion -> companion.flatMap(rs -> { if (!(rs.failure() instanceof TelegramRateLimitException tr)) return Mono.error(rs.failure()); long delaySeconds = Math.max(0, Math.min(tr.getRetryAfterSeconds(), 30)); long jitterMs = ThreadLocalRandom.current().nextLong(0, 200); log.warn("Telegram 429 — waiting {}s + {}ms jitter", delaySeconds, jitterMs); return Mono.delay(Duration.ofSeconds(delaySeconds).plusMillis(jitterMs)); }))`. `Retry.from` is the low-level constructor needed to compute per-attempt delay from the exception payload in one place.
12. `.timeout(Duration.ofSeconds(30))`. On `TimeoutException` from Reactor, translate via `.onErrorMap(ex -> ex instanceof TimeoutException ? new TelegramSendException(null, "timeout", attempts.get()) : ex)`. Log ERROR before mapping or via `.doOnError` filter.
13. `.doOnSuccess(sm -> eventService.logEvent(ownerId, EVENT_TELEGRAM_MESSAGE_SENT, null, null, sentMetadata(botId, sm)))` and `.doOnError(ex -> { if (isTerminalAuditable(ex)) eventService.logEvent(ownerId, EVENT_TELEGRAM_SEND_FAILED, null, null, failedMetadata(botId, chatId, ex, attempts.get())); })`. `isTerminalAuditable(ex)` returns true for `BotTokenInvalidException` and `TelegramSendException`; returns false for the `AppException(NOT_FOUND, code=null, "Bot not found")` (pre-HTTP, not a "send" failure) and for any internal `TelegramRateLimitException` that somehow escaped (defensive). Also include the terminal-failure ERROR log here: `log.error("Telegram send terminal failure attempts={}: {}", attempts.get(), TelegramApiClient.scrubTokens(ex.getMessage()))` — gated by the same `isTerminalAuditable` check so pre-HTTP failures don't pollute the error stream.

*Audit metadata shapes (tech-spec Data Models lines 256-262):*
- `sentMetadata(botId, SentMessage sm)` → `Map.of("botId", botId, "chatId", sm.chatId(), "messageId", sm.messageId())`.
- `failedMetadata(botId, chatId, Throwable ex, int attempts)` → mutable `HashMap`: always put `botId`, `chatId`, `attempts`; if `ex instanceof TelegramSendException tse` → put `errorCode` (may be null) and `errorDescription` (already scrubbed when the exception was constructed in `map4xx` / `mapBodyToSentMessage` / `onRetryExhaustedThrow`); if `ex instanceof BotTokenInvalidException` → no `errorCode`/`errorDescription` keys.

*Six scrub sites (Architecture line 70) — explicit log lines:*
1. `map4xx` 4xx branch → `log.warn("Telegram 4xx ({}): {}", rawStatus, TelegramApiClient.scrubTokens(result.description()))`.
2. `mapBodyToSentMessage` `ok=false` branch → `log.warn("Telegram ok=false or missing message_id: {}", TelegramApiClient.scrubTokens(result.description()))`.
3. Inner retry `doBeforeRetry` → `log.warn("Telegram transient retry #{} after error: {}", rs.totalRetries() + 1, TelegramApiClient.scrubTokens(rs.failure().getMessage()))`.
4. Outer 429 retry: WARN at the rate-limit error site in `map4xx` (item 1's 429 branch) AND WARN at the wait announcement inside `buildRateLimitRetry` (no token in the wait message; but if mapping a cause chain into the warn, scrub).
5. Terminal `doOnError` → `log.error("Telegram send terminal failure attempts={}: {}", attempts.get(), TelegramApiClient.scrubTokens(ex.getMessage()))`.
6. Overall timeout — emitted as part of the terminal-failure path (step 13). For a wrapped `TimeoutException` whose cause carries the URI (with token), `scrubTokens` strips it.
