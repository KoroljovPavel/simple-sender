## Description

Rewrite `BotService.sendTestMessage` so the new `TelegramSender` bean (from Wave 2 / Task 4) is actually invoked when a Bot has a known Telegram chat to send to. Today the method short-circuits with a hard 422 `owner_chat_id_unknown` for every caller — that stub was the documented behavior for Epic 06 because `Bot.ownerChatId` did not exist yet and the sender bean had not landed. With both pieces in place (`Bot.ownerChatId` from Wave 1 / Task 2 and `TelegramSender` from Task 4), `sendTestMessage` must branch on `bot.getOwnerChatId()`:

- `null` branch: preserve the existing 422 stub verbatim — same `AppException.unprocessableEntity("owner_chat_id_unknown", "Send /start to your bot in Telegram first, then try again")` factory call, same exception code, same message string. This is the production-observable path until Epic 04b webhook ingestion lands. The integration test `postTestMessage_in06_returns422_zeroTelegramCalls_zeroEvents` must continue to pass (renamed or not — the assertions must hold).
- non-null branch: call `telegramSender.sendText(bot.getId(), bot.getOwnerChatId(), TEST_MESSAGE_BODY, null, ownerId)`; on success emit one additional audit event `bot_test_message_sent` via `eventService.logEvent` with metadata `{projectId, telegramBotId, chatId, messageId}`. On failure the exception propagates up to `GlobalErrorHandler` (the sender already wrote its own `telegram_send_failed` audit; this method must NOT write `bot_test_message_failed` — Decision 3 in tech-spec).

The HTTP contract on `BotController.testMessage` (`Mono<ResponseEntity<Void>>` returning 200 OK with empty body) does not change. `messageId` is captured only in the audit event metadata, never echoed on the response.

Test updates accompany the implementation:
- `BotServiceTest`: introduce `TelegramSender` as a `@Mock` and pass it through the constructor. Split the current `sendTestMessage_returns422_noTelegramCalls_noEvents` test into two cases — one for the null-`ownerChatId` branch (preserves all current assertions, including the verbatim message string) and one for the present-`ownerChatId` happy path. Add a third case for the present-`ownerChatId` failure branch that asserts the sender error propagates and that no `bot_test_message_sent` event is written.
- `BotControllerIT`: keep the existing `postTestMessage_in06_returns422_zeroTelegramCalls_zeroEvents` test as the null-branch regression (rename if desired to drop the "in06" reference — both names are fine; assertions must not weaken). Add one new positive-path test that seeds a Bot with `ownerChatId` set **and real AES-GCM-encrypted token ciphertext** (see warning below), enqueues a Telegram 200 on the class-level `MockWebServer`, and asserts 200 OK + `bot_test_message_sent` event in the `events` collection with the full metadata shape.

> WARNING — DO NOT REUSE `seedConnectedBot` FOR THE POSITIVE PATH. The existing `seedConnectedBot(projectId, telegramBotId)` helper (lines 182–195 of `BotControllerIT`) stores **placeholder ciphertext** (`encryptedTokenCiphertext = "Zm9v"` / `encryptedTokenIv = "YmFy"` — 3-byte base64 garbage). The null-branch test (`postTestMessage_in06_returns422_zeroTelegramCalls_zeroEvents`) is fine with these placeholders because it short-circuits before any decrypt. **The new positive-path test reaches `TelegramSender.sendText`, which calls `tokenEncryptor.decrypt(iv, ct)` — the IV length check (`iv.length != IV_BYTES (12)`) will throw `IllegalArgumentException`, propagate per the narrow-catch policy from Task 4, and surface as 500.** The test will FAIL if you reuse `seedConnectedBot` as-is. You must seed real ciphertext via `tokenEncryptor.encrypt(...)` — see step 6 below and Implementation hints.
