## Description

Full-feature code quality audit of Epic 04c (TelegramSender). All implementation tasks (1–6) are complete by the time this audit runs; the audit is the team's last line of defense before pre-deploy QA. The auditor reads every source file created or modified in this feature and reviews the whole as a coherent system, not file-by-file.

**Dependency ordering note.** This task declares `depends_on: [6]` only. That is intentional and sufficient — the chain is transitive: Task 6 depends on Task 5, Task 5 depends on Task 4, Task 4 depends on Wave 1 (Tasks 1–3). By the time Task 7 starts, Tasks 1–6 are all complete by construction. The audit therefore safely treats every file listed in "Code files (in scope of audit)" as already implemented and reviews the whole as a coherent system.

The audit focuses on cross-component concerns that no single per-task reviewer can catch by reading only one file:

- **Shared resources compliance.** Per Architecture → Shared Resources, `TelegramSender` and `TelegramApiClient` each own a distinct `WebClient` instance built via the injected `WebClient.Builder`, both reusing `app.telegram.base-url` and the promoted `CONNECT_TIMEOUT` / `DEFAULT_RESPONSE_TIMEOUT` constants. No third `WebClient`. No shared mutable state between the two beans. `TokenEncryptor`, `BotRepository`, and `EventService` are singletons reused without re-creation.
- **Retry/timeout policy correctness.** Sender uses 1s/2s/4s backoff (Decision 13), 3 retries on `isTransient`, 429 outer loop wrapping the 5xx inner loop (Decision 10), 30s overall timeout (Decision 8), clamp `Math.max(0, Math.min(retryAfter, 30))` to defend against negative or missing `retry_after`. `TelegramApiClient` retains its 200ms/400ms/2s policy unchanged.
- **Audit-event metadata consistency.** `telegram_message_sent` carries `{botId, chatId, messageId}`; `telegram_send_failed` carries `{botId, chatId, errorCode?, errorDescription?, attempts}`; `bot_test_message_sent` carries `{projectId, telegramBotId, chatId, messageId}`. `attempts` is sourced from the outer-closure `AtomicInteger` (survives both retry loops) and matches the AC14 "total HTTP request count" semantics.
- **Scrubber coverage at every external-string log site.** All required sites (4xx WARN in `map4xx`, `ok=false` WARN, 5xx retry WARN inside `doBeforeRetry`, 429 wait WARN inside `rateLimitRetry`, terminal failure ERROR inside `doOnError`, overall-timeout ERROR, transport-error log) wrap external strings through `TelegramApiClient.scrubTokens(...)` before emitting. No bare `description` or `Throwable.getMessage()` reaches the appender.
- **Exception hierarchy correctness.** `BotTokenInvalidException` and `TelegramSendException` extend `AppException` (mapped uniformly by `GlobalErrorHandler` to 422 and 400); `TelegramRateLimitException` is package-private / internal, never propagates past the 429 retry loop, and never reaches `GlobalErrorHandler`.
- **Anti-enumeration uniformity.** Both `bot not found` and `bot exists but status != CONNECTED` return the same `404 bot_not_found` shape (Decision 7), mirroring the platform-wide `requireOwned` pattern from `patterns.md`. `BotService.sendTestMessage` preserves the verbatim 422 stub message for the `ownerChatId == null` branch.
- **Documentation.** The staging-smoke runbook (`docs/staging-smoke/07-telegram-sender.md`) mirrors the structure of `06-bot-connection.md`, documents the 04b dependency, and includes mongosh seeding steps and the dual-event verification (Mongo `events` collection contains both `telegram_message_sent` and `bot_test_message_sent` after a successful staging click).

The output is a single JSON report at `work/07-telegram-sender/logs/working/task-7/code-reviewer.json`. The auditor is the review (no separate reviewer agents) — findings here go straight into `decisions.md` per the post-completion checklist.

Read the user-spec for the 23 acceptance criteria the implementation must honor.
2. Read every source file in scope of the audit (see Context Files → Code files). Cross-reference each implementation against the relevant tech-spec section / decision.
3. Walk the cross-component checklist:
   - **Shared resources.** Verify `TelegramSender` constructs exactly one `WebClient` via the injected builder; verify it uses `TelegramApiClient.DEFAULT_RESPONSE_TIMEOUT` and `TelegramApiClient.CONNECT_TIMEOUT` (not re-declared local constants); verify `TelegramApiClient`'s `WebClient` is untouched.
   - **Retry/timeout policy.** Verify `Retry.backoff(3, Duration.ofSeconds(1)).maxBackoff(Duration.ofSeconds(4))` for transient inner loop; verify the 429 outer loop is chained AFTER the transient loop (so it wraps it per Decision 10); verify `.timeout(Duration.ofSeconds(30))` is the outermost operator; verify the `Math.max(0, Math.min(retryAfter, 30))` clamp is present where `retry_after` is consumed.
   - **AtomicInteger placement.** Verify `AtomicInteger attempts` is allocated in the outermost closure (BEFORE `Mono.defer` / `Mono.fromSupplier`), incremented on `.doOnSubscribe`, and read into terminal exceptions and audit metadata. A counter declared inside the request supplier would reset on every 429 resubscription — that is a regression target.
   - **Pre-wire token guards.** Verify the decrypt step's catch is **scoped to the Base64 decode call only**: catch `IllegalArgumentException` from `Base64.getDecoder().decode(...)` → map to `BotTokenInvalidException(botId, "decryption failed")`. Verify the catch does NOT catch `IllegalStateException` from `TokenEncryptor.decrypt` — `TokenEncryptor` wraps `GeneralSecurityException` (including `AEADBadTagException` from corrupted/tampered ciphertext) and misconfigured-bean failures uniformly into `IllegalStateException("AES-GCM decryption failed", cause)`, and both modes must propagate as 500 via `GlobalErrorHandler.handleThrowable` per Architecture step 3 and Risk R7 (the two modes are indistinguishable at the call site; differentiating them is explicitly deferred). Verify the catch also does NOT catch `Exception` (would mask `IllegalStateException` and misclassify a misconfigured `TokenEncryptor` bean as a user-facing 422 `invalid_bot_token`). Verify `TelegramApiClient.requireValidTokenShape(plaintext)` is called BEFORE building the URI / body. Cross-check that the unit test `sendText_decryptThrowsIllegalState_propagatesAsInternalError_notBotTokenInvalid` exists in `TelegramSenderTest.java` and asserts `IllegalStateException` is NOT wrapped in `BotTokenInvalidException`.
   - **Audit metadata shape.** Verify the three event types carry exactly the metadata fields declared in tech-spec → Data Models → Event types. No extra fields, no missing fields, no field renames. `attempts` is `int` (not `Integer`) in the failure metadata.
   - **Scrubber coverage.** Walk every `log.warn` / `log.error` call site in `TelegramSender.java` and verify the externally-sourced string is wrapped in `TelegramApiClient.scrubTokens(...)` before passing to the appender. List any site that emits a raw `description`, `getMessage()`, or URI as a finding.
   - **Exception hierarchy.** Verify `BotTokenInvalidException extends AppException` with `UNPROCESSABLE_ENTITY` / `invalid_bot_token`; `TelegramSendException extends AppException` with `BAD_REQUEST` / `telegram_send_failed`; `TelegramRateLimitException` is package-private (no `public` modifier), extends `RuntimeException`, has no HTTP mapping, and is referenced only inside the 429 retry filter.
   - **Anti-enumeration.** Verify both the `Mono.empty()` (bot not found) and `status != CONNECTED` branches resolve to the same `AppException.notFound("bot_not_found")` shape. Verify `BotService.sendTestMessage` preserves the verbatim 422 message string `"Send /start to your bot in Telegram first, then try again"` for the null-`ownerChatId` branch.
   - **Bot field.** Verify `Bot.ownerChatId` is `Long` (wrapper, nullable), has public getter/setter, is placed between `telegramFirstName` and `status`, has no `toString` override, no `@Indexed`.
   - **Helper promotion.** Verify `requireValidTokenShape`, `isTransient`, `DEFAULT_RESPONSE_TIMEOUT`, and `CONNECT_TIMEOUT` on `TelegramApiClient` are now `public static` (signatures and values unchanged) and each carries a brief comment noting the `TelegramSender` consumer — same pattern as the existing `scrubTokens` promotion comment.
   - **Runbook.** Verify `docs/staging-smoke/07-telegram-sender.md` mirrors `06-bot-connection.md` structure; documents the 04b dependency; lists mongosh seeding steps for `ownerChatId`; covers the dual-event verification (`telegram_message_sent` + `bot_test_message_sent`).
4. For every finding, classify severity (BLOCKER / MAJOR / MINOR / NIT) and propose a concrete fix. A finding without an actionable fix is unfinished — write the fix.
5. Write the JSON report to `work/07-telegram-sender/logs/working/task-7/code-reviewer.json` per the schema in `.claude/skills/code-reviewing/SKILL.md`. Include the audit dimensions (`shared_resources`, `retry_timeout`, `audit_metadata`, `scrubber_coverage`, `exception_hierarchy`, `anti_enumeration`, `runbook`) so downstream consumers can filter.

**Edge cases to look for:**
- `AtomicInteger attempts` declared inside `Mono.defer` / `Mono.fromSupplier` instead of outside (would reset on 429 resubscription — silent regression of AC14 attempts semantics).
- Retry-loop ordering reversed (5xx outer / 429 inner) — silently exhausts 5xx cap during a `retry_after` wait. Decision 10 and R3 are the spec; the test `sendText_429And5xxInterleaving_succeeds` is the runtime check but a code-level scan should also confirm the order of `.retryWhen(...)` calls.
- `retry_after` consumed without `Math.max(0, ...)` clamp — Reactor treats negative `Duration` as immediate resubscribe → spin loop.
- A scrubber site missing — e.g. retry-observer WARN emits raw `Throwable.getMessage()` which embeds the URI (token).
- Decrypt catch block too broad — the catch must be scoped to `Base64.getDecoder().decode(...)` and catch ONLY `IllegalArgumentException`. Catching `IllegalStateException` (the wrapper `TokenEncryptor.decrypt` throws for both `AEADBadTagException`-tampered ciphertext AND a misconfigured `TokenEncryptor` bean) would reclassify a 500 as a 422 `invalid_bot_token` — ops issue presented as user error. Catching `Exception` is an even broader form of the same bug. The new contract (tech-spec Architecture step 3 + Risk R7) is: `IllegalStateException` from decrypt propagates unchanged through `GlobalErrorHandler.handleThrowable` → 500. The two underlying failure modes (corrupted ciphertext, misconfigured bean) are indistinguishable at the call site and differentiating them is explicitly deferred — a single unit test stubs `TokenEncryptor` to throw `IllegalStateException` and covers both modes.
- `BotService.sendTestMessage` writing `bot_test_message_failed` on failure (double-write — sender already writes `telegram_send_failed`).
- `Bot.ownerChatId` defined as `long` (primitive) instead of `Long` (wrapper) — would break legacy-document deserialization.
- `TelegramRateLimitException` declared `public` — should be package-private; never crosses the package boundary.
- Helper promotions on `TelegramApiClient` accidentally changing a signature or value (e.g. `CONNECT_TIMEOUT` changed from `Duration.ofSeconds(5)` to a different value).
- The runbook missing the 04b dependency note or the dual-event verification (auditor should flag this — Task 6's per-task code-reviewer might have missed it).

**Implementation hints:**
- Walk the audit dimension-by-dimension, not file-by-file. The point of this audit is the cross-component view per-task reviewers cannot deliver.
- For each dimension, write the check, the file(s) consulted, and the verdict (PASS / finding). Empty `findings: []` for a dimension is acceptable when every check passes — say so explicitly per dimension rather than implicitly via omission.
- Severity rubric: BLOCKER = ships a bug or violates a Decision verbatim; MAJOR = silent regression risk under load / non-happy paths; MINOR = readability / convention drift with no behavioral impact; NIT = personal taste.
