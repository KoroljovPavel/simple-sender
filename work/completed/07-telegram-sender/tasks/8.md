Перед выполнением задачи загрузи:

## Description

Full-feature security audit of the 07-telegram-sender deliverables. The auditor is the sole reviewer for this task — no follow-up review round. Goal: detect security regressions and OWASP Top 10 issues introduced by adding `TelegramSender`, the new exceptions/DTOs, the `Bot.ownerChatId` field, and the `BotService.sendTestMessage` rewrite.

Three security-sensitive properties of this feature must hold:
1. The decrypted bot token never leaves the per-call Mono closure — never logged, never serialized, never returned in HTTP responses or exception messages.
2. The bot `ownerChatId` field and the new audit events do not change the public API surface or expose internal Telegram identifiers beyond the existing `events.metadata` precedent.
3. The 404 anti-enumeration shape (`bot_not_found` for both missing-doc and `status != CONNECTED`) is preserved end-to-end, and the existing `requireConnectedBot`/`/api/**` authentication preconditions are untouched.

The audit produces a single JSON report. Findings drive any remediation work that follows.

   - **A01 Broken Access Control** — verify the sender's 404 returns the same `bot_not_found` shape for "doc missing" and "status != CONNECTED" (Decision 7); verify `BotService.sendTestMessage` still calls `requireConnectedBot` before branching on `ownerChatId`; verify `SecurityConfig` is unchanged (`/api/**` authenticated rule still covers `/test-message`); verify no new endpoints leak bot ownership across users.
   - **A02 Cryptographic Failures** — verify per-call decrypt with no caching (Decision 2); verify the decrypted token is captured only in the Mono closure and never assigned to a field, logged, serialized, or pushed to a different scheduler; verify token-shape validation (`requireValidTokenShape`) runs immediately after decrypt and before any URI construction; verify `BotTokenLeakTest` still passes (no `toString` on `Bot`, encrypted fields not exposed); verify exception messages on `BotTokenInvalidException` and `TelegramSendException` do not embed the plaintext token. **Decrypt error contract (Architecture step 3 + Risk R7):** verify the catch around the decrypt step is **scoped to Base64 decode only** — only `IllegalArgumentException` from `Base64.getDecoder().decode(...)` maps to `BotTokenInvalidException(botId, "decryption failed")`. Verify the code does **NOT** catch `IllegalStateException` from `TokenEncryptor.decrypt` — both failure modes carried in that wrapping (corrupted/tampered ciphertext via `AEADBadTagException` wrapped as `IllegalStateException("AES-GCM decryption failed", cause)` AND a misconfigured `TokenEncryptor` bean) must propagate as a 500 via `GlobalErrorHandler.handleThrowable`, not be translated into 422 `invalid_bot_token`. Verify the corresponding unit test (`sendText_decryptThrowsIllegalState_propagatesAsInternalError_notBotTokenInvalid`) stubs `TokenEncryptor` to throw `IllegalStateException` and asserts the exception propagates as-is. Confirm Risk R7 is acknowledged as an accepted limitation (cannot distinguish corrupted ciphertext from misconfigured bean at the call site) — re-flag only if the implementation deviates from this contract (e.g., adds a blanket `catch (Exception)` around decrypt, translates `IllegalStateException` into 422, or fails to assert the IllegalStateException pass-through behavior in tests).
   - **A03 Injection** — verify `parse_mode` defaults to `null` (plain text) in `TelegramSender.sendText` and `BotService.sendTestMessage` (Decision 6 — defends against HTML/Markdown injection in Telegram-rendered output for future Epic 06/07 callers); verify the WebClient URI uses the `{token}` placeholder pattern (so `DefaultUriBuilderFactory(EncodingMode.NONE)` substitutes the token, not raw string concatenation that could allow path-traversal via tampered Mongo state); verify the request body is built via `Map.of(...)` (no string concatenation into a JSON literal); confirm no SQL or shell paths exist in this feature (Mongo + WebClient only).
   - **A05 Security Misconfiguration** — verify `SecurityConfig.java` has zero diff; verify no new `application.properties` keys; verify no `@CrossOrigin` or permitAll additions; verify `build.gradle` has no new dependencies; verify no new `@ConditionalOnProperty` toggles that could relax behavior in non-prod profiles.
   - **A07 Identification & Authentication Failures** — verify no change to the auth/session/JWT flow; verify the new endpoint reuses the existing `/api/**` authenticated chain; verify `ownerId` is passed through from the authenticated principal (not derived from a request body field where a caller could spoof it).
   - **A09 Security Logging & Monitoring Failures** — verify `telegram_message_sent` (success) and `telegram_send_failed` (terminal failure) audit events are written via `EventService.logEvent`; verify the failure event captures `attempts`, `errorCode?`, scrubbed `errorDescription?`; verify every WARN/ERROR site that echoes a Telegram `description` or transport-error message wraps the string in `TelegramApiClient.scrubTokens(...)` — the required sites per tech-spec are: `map4xx` (WARN), `ok=false` mapper (WARN), 5xx retry observer (WARN), 429 wait announcement (WARN), terminal-failure `doOnError` (ERROR), overall-timeout error log (ERROR), transport-error path (WARN/ERROR); verify the `ListAppender` unit tests cover each of those sites at the asserted log level.

**Report shape:** JSON array of finding objects. Each finding object has fields:
- `severity` — one of `critical`, `high`, `medium`, `low`, `info`.
- `category` — OWASP code (e.g., `A01`, `A02`, `A09`).
- `issue` — concrete description with file:line reference where applicable.
- `fix` — actionable remediation (or `accepted_risk` reference if the issue is a documented out-of-scope risk).

Empty array (`[]`) is an acceptable outcome when no findings exist — the audit is still considered "done" as long as the file is written and the JSON is valid.

**Dependencies:** Task 6 (Staging-smoke runbook) — Wave 4 must complete so the full feature codebase (Tasks 1-5) and its documentation exist. Audit reads but does not modify.

**Edge cases to probe:**
- Token-shaped substring in any exception message (`BotTokenInvalidException.reason`, `TelegramSendException.scrubbedDescription`) — even when the scrubber is wired at log sites, the exception payload itself reaches `GlobalErrorHandler` and is serialized to the client.
- `WebClientRequestException` transport-error path: its built-in `getMessage()` may embed the request URI (which contains the token). Verify the catch site scrubs the message before logging.
- `Bot.ownerChatId` exposure: verify `BotResponse` does not surface this field (it is internal; tech-spec AC17 + the "Unchanged" Architecture note).
- `events.metadata` shape: verify `chatId`/`messageId` are written as numeric IDs, consistent with existing `bot_connected`/`bot_disconnected` precedent, and that the failure event's `errorDescription` is scrubbed before insertion (the audit event is durable storage, not an ephemeral log line).
- `ownerId=null` system-context path: verify the sender does not derive a "system user" sentinel from any caller-controlled string (Decision 4 — `null` is the contract).
- Decrypt-step catch scope (Architecture step 3 + Risk R7): verify the catch around decrypt is narrow — `IllegalArgumentException` from Base64 decode only. A broader `catch (RuntimeException)` or `catch (IllegalStateException)` here would mask both corrupted/tampered ciphertext (AEAD auth-tag failure wrapped as `IllegalStateException`) and a misconfigured `TokenEncryptor` bean, mis-mapping a 500 to a user-facing 422 `invalid_bot_token`. The accepted limitation (cannot differentiate ops-misconfig from data-tampering) is documented in Risk R7 and is correctly handled by letting `IllegalStateException` propagate to `GlobalErrorHandler.handleThrowable`.

**Implementation hints:** This is a read-only audit. Do NOT modify any source file. Findings live entirely in the JSON report. Apply the security-auditor skill's report schema and severity rubric. When in doubt about a documented mitigation, cross-reference tech-spec Risks (R1-R12) and Decisions — if the implementation aligns with the documented mitigation, it is not a finding.
