## Description

Full-feature test quality audit for Epic 04c (TelegramSender). Goal — independently verify that the test suite created/updated across Tasks 1–6 actually proves the behavior the tech-spec promises, before pre-deploy QA runs the full suite in Task 10.

Read every test file touched by this feature: the two new files (`TelegramSenderTest.java`, `TelegramSenderIT.java`) plus updates to `BotServiceTest.java`, `BotControllerIT.java`, `BotRepositoryTest.java`. The reference `BotTokenLeakTest.java` is read to confirm the `Bot.ownerChatId` addition does not break the existing no-`toString` invariant.

Verify against the Testing Strategy section of the tech-spec (lines 286–347):
- All 28 unit scenarios in `TelegramSenderTest` are present, distinctly named, and assert observable outcomes (request count, exception types, audit metadata shape, wall-clock bounds) — not just "mock was called" or "no exception".
- All 4 integration scenarios in `TelegramSenderIT` exist and use Awaitility (`await().atMost(...)`) for any assertion on async `events` writes. Negative-presence checks (event NOT written) use a settle window via `.during(...).atMost(...)`.
- Retry-attempt counts are asserted explicitly (`attempts == 1`, `2`, or `4` per scenario) in both audit metadata and request-count assertions — never left implicit.
- `ListAppender<ILoggingEvent>` token-leak coverage is split per log site (4xx WARN, 5xx-retry WARN, 429-wait WARN, terminal-failure ERROR, transport-error WARN/ERROR) so each scrubber site is independently verified — not one umbrella test.
- `BotControllerIT` has both the existing null-branch test (`postTestMessage_in06_returns422_zeroTelegramCalls_zeroEvents`) AND the new positive-path test (`postTestMessage_in07_seededOwnerChatId_returns200_emitsEvent`) with full metadata-shape assertions.
- `BotServiceTest` split into three cases (null-branch, present-and-success, present-and-failure) with exact-argument matchers on `telegramSender.sendText` and `verify(eventService, never())` on the failure path.
- `BotRepositoryTest` has the new legacy-document case proving Spring Data MongoDB reads missing `ownerChatId` as null.

Produce a single audit report at `work/07-telegram-sender/logs/working/task-9/test-reviewer.json` listing missing scenarios, weak assertions, redundant tests, and any deviation from the tech-spec's Testing Strategy. The auditor is the review — no downstream reviewers consume this task.

## What to do

1. Read the tech-spec Testing Strategy section in full (`work/07-telegram-sender/tech-spec.md` lines 284–347) plus user-spec ACs AC19–AC23. Build the expected-scenario catalog: 28 unit-scenario names, 4 integration-scenario names, plus the three `BotServiceTest` cases, the two `BotControllerIT` cases, and the one `BotRepositoryTest` case.
2. Read every test file listed in **Context Files → Code files**. For each scenario in the catalog, find the corresponding `@Test` method in code.
3. For every scenario found, audit four dimensions:
   - **Presence.** Method exists with a name that maps to the catalog entry.
   - **Assertion strength.** Assertions are on observable outcomes (return value, thrown exception class + message, request count on MockWebServer, event metadata shape, log content). Reject "test that nothing throws" or "verify mock invoked without checking arguments".
   - **Retry-count explicitness.** Where the tech-spec calls for a specific `attempts` count, the test asserts it explicitly (audit-event metadata field AND MockWebServer `getRequestCount()`).
   - **Cross-cutting requirements.** `ListAppender` is filtered by level (WARN vs ERROR) per the scrubber-coverage table in the tech-spec; Awaitility is used on async event reads; `BotControllerIT` covers both positive and negative branches.
4. For every catalog scenario missing from code OR present but failing one of the four dimensions, record a finding.
5. Independently scan the test files for redundant tests (per `test-quality-review.md`): identical scenarios duplicated across unit and integration without added value, "tests for completeness" that protect against no specific regression. Record findings.
6. Write the audit report as JSON at `work/07-telegram-sender/logs/working/task-9/test-reviewer.json` with the schema below. The file is the deliverable — do not also write a markdown summary.
7. Do NOT modify any test or production code. The audit produces only the report; remediation is a follow-up task driven by the feature lead.

**Severity rubric:**
- `high` — missing scenario from user-spec AC, weak assertions on terminal exception type, retry count not asserted on a retry-semantics test, `ListAppender` not split per log site, Awaitility absent on async event read.
- `medium` — naming drift from catalog (test exists but name does not map), full metadata-shape not asserted (presence checked but field-level shape skipped).
- `low` — redundant test with no specific regression coverage, style/clarity issue.

**Dependencies:** Task 6 (Wave 4 — staging-smoke runbook). All preceding waves must have committed test files for the audit to make sense. The dependency on Task 6 (not directly on Task 5) is intentional — keeping the audit in Wave 5 lets it run in parallel with sibling audits (Task 7 Code Audit, Task 8 Security Audit) and after the documentation wave settles.

**Edge cases:**
- A scenario may be split across multiple `@Test` methods (e.g. the five token-leak sites). Treat the catalog entry as satisfied if all sub-tests are present; flag if any are merged into one umbrella test.
- The tech-spec lists 18 unit scenarios as the user-spec AC19 headline, but the elaboration enumerates more discrete `@Test` methods (timeout tests, pre-wire guards, per-site scrubber tests). The auditor records both the headline coverage and the elaboration coverage and only flags `needs_work` when the elaboration is missing — the headline 18 is a floor, not a ceiling.
- If `TelegramSenderTest` or `TelegramSenderIT` files do not exist (Task 4 incomplete), the audit cannot proceed — emit a `verdict: needs_work` with a single high-severity finding "prerequisite tests not implemented" and stop.

**Implementation hints:**
- Use `grep -n "@Test" backend/src/test/java/com/botfunnel/bot/TelegramSenderTest.java` to enumerate test methods quickly, then map each against the catalog.
- For `ListAppender` level filtering, search for `.list.stream().filter(e -> e.getLevel() == Level.WARN)` or equivalent in test code — absence of level filtering on a multi-site test is a `high` finding.
- For Awaitility checks, search for `Awaitility.await(` and `await(`; absence in `TelegramSenderIT` event-related assertions is a `high` finding.
- For exact-argument Mockito matchers in `BotServiceTest`, look for `eq(botId)`, `eq(ownerChatId)`, `eq(TEST_MESSAGE_BODY)`, `eq(null)`, `eq(ownerId)` on `telegramSender.sendText(...)` calls — `any()` matchers on the success-path case is a `medium` finding.
- The auditor never runs `./gradlew test` — Task 10 (Pre-deploy QA) is the suite-runner. This audit is a static read of test code only.
