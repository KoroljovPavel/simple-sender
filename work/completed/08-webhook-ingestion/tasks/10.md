## Description

The controller is the inbound HTTP surface — `POST /webhooks/telegram/{projectId}`. It runs on the Netty event loop with a target P99 < 100ms (user-spec AC1, Risk R1). Per Decision 3 every response is `Mono<ResponseEntity<Void>>` (200 / 401 / 404 — no body, no `AppException`, no `GlobalErrorHandler` path). Per Decision 1 the lookup chain is two indexed reads: bot CONNECTED for `{projectId}`, then project existence + `deletedAt == null` (covers user-spec R6 cascade gap). Per Decision 2/16 the secret verification delegates to `WebhookSecretVerifier` (constant-time). Per Decisions 4 + 11 idempotency is anchored by a unique compound index in `raw_updates` + a deterministic JobRunr UUID enqueue (self-heal on `DuplicateKeyException`).

The controller owns FOUR `Counter`s + ONE `Timer` (the FIFTH counter, `payload_too_large`, lives on the filter from T11):
- `telegram_webhook_received_total{projectId}` — Counter, success path.
- `telegram_webhook_duration_seconds` — Timer wrapping the body.
- `telegram_webhook_rejected_total{reason=invalid_secret}` — Counter, 401 path.
- `telegram_webhook_rejected_total{reason=project_not_found}` — Counter, 404 path.
- `telegram_webhook_rejected_total{reason=duplicate}` — Counter, DuplicateKey self-heal path.

Per security audit M7 every log site that touches payload-derived strings wraps through `TelegramApiClient.scrubTokens`. Enumerated controller sites: WARN on DuplicateKeyException (logs projectId + updateId — NOT payload), ERROR on enqueue failure (logs rawUpdateId — NOT payload).

The integration test (`TelegramWebhookControllerIT`) is the central acceptance vehicle for AC1, AC2, AC3, AC5, AC15, AC16, AC18 + the Decision 11 self-heal scenario. It uses `JobRunrInMemoryConfig` so the worker thread does NOT execute under IT — that path is owned by `ProcessTelegramUpdateJobTest` (T9). The IT only asserts the controller side: status code, header, body emptiness, counter values, ENQUEUED job count.

## What to do

1. Read precedent files in `## Context Files` — `BotController.java` for WebFlux controller style, `BotRepository.java` for `findByProjectIdAndStatus`, `ProjectRepository.java` for `findById`, `JobRunrMongoConfig.java` for the JobRunr setup the controller hooks into via static `BackgroundJob.enqueue`, `AbstractIntegrationTest.java` for the IT base class, `BotControllerIT.java` for IT style + spy patterns + token-leak assertion via `ListAppender`.
2. Create `backend/src/main/java/com/botfunnel/webhook/TelegramWebhookController.java` — `@RestController @RequestMapping("/webhooks/telegram")` with one `@PostMapping("/{projectId}")` method `receive(@PathVariable String projectId, @RequestHeader(value="X-Telegram-Bot-Api-Secret-Token", required=false) String headerSecret, @RequestBody org.bson.Document body)`. Return type `Mono<ResponseEntity<Void>>`. Constructor-injected collaborators:
   - `BotRepository botRepository`
   - `ProjectRepository projectRepository`
   - `RawUpdateRepository rawUpdateRepository`
   - `WebhookSecretVerifier webhookSecretVerifier`
   - `MeterRegistry meterRegistry`
3. Implement the flow per Architecture "Inbound HTTP path":
   - **Wrap entire body in a `Timer.start` / `timer.stop(meterRegistry.timer("telegram_webhook_duration_seconds"))`.**
   - **Bot lookup** — `botRepository.findByProjectIdAndStatus(projectId, CONNECTED)`. Apply `.onErrorMap(IllegalArgumentException.class, ex -> new RuntimeException(... -> NOT_FOUND))` for malformed ObjectId. If empty → increment `rejected_total{reason=project_not_found}`, return `Mono.just(ResponseEntity.notFound().build())`.
   - **Project lookup (Decision 1)** — chained `.flatMap(bot -> projectRepository.findById(projectId).map(...))`. If project missing OR `project.getDeletedAt() != null` → increment `rejected_total{reason=project_not_found}` + 404.
   - **Secret verify (Decision 2/16)** — `webhookSecretVerifier.verify(headerSecret, bot.getWebhookSecretHash())` → if false → increment `rejected_total{reason=invalid_secret}` + 401.
   - **Persist + enqueue** — `rawUpdateRepository.save(new RawUpdate(projectId, body.get("update_id", Long.class), body, RawUpdateStatus.PENDING, Instant.now()))`. Two outcomes:
     - Success → `enqueueIdempotent(rawUpdate.getId())` → increment `received_total{projectId}` + 200 OK.
     - `DuplicateKeyException` → increment `rejected_total{reason=duplicate}` + STILL call `enqueueIdempotent(rawUpdate.getId())` (Decision 4 self-heal) + 200 OK. WARN-log with scrubbed `projectId` + `updateId` (no payload).
   - **`enqueueIdempotent(String rawUpdateId)` helper** (private method):
     - `UUID jobId = UUID.nameUUIDFromBytes(rawUpdateId.getBytes(StandardCharsets.UTF_8))`.
     - `Mono.fromCallable(() -> BackgroundJob.<ProcessTelegramUpdateJob>enqueue(jobId, j -> j.handle(rawUpdateId))).subscribeOn(Schedulers.boundedElastic())`.
     - On enqueue exception (rare): ERROR log scrubbed message, propagate as 5xx (Spring's default error-handler will produce 500 — Telegram will retry). DO NOT swallow.
4. Counter registration — eagerly fetch counters in the constructor (cache `Counter` instances) to avoid repeated `Tag.of` allocation per request. Pattern:
   ```
   Counter receivedCounter = Counter.builder("telegram_webhook_received_total").register(meterRegistry); // tag projectId added per-request
   ```
   Actually — `received_total{projectId}` is high-cardinality; check if the project allows per-projectId tags. Verify against existing code (e.g. `BotController`'s metric tagging if any). If high-cardinality tagging is OK, use `Counter.builder(...).tag("projectId", id).register(meterRegistry).increment()` per request. If not — drop the tag (user-spec just says counter exists; AC16 tests assert presence + count, not per-projectId breakout). Document the choice in code comment.
5. Token-scrubber on EVERY log site that string-formats payload-derived input. Enumerated sites:
   - WARN on `DuplicateKeyException` — log includes `scrubTokens(projectId + " updateId=" + updateId)`. NOT the payload Document.
   - ERROR on enqueue failure — log includes `scrubTokens(rawUpdateId + " " + ex.getMessage())`. NOT the payload.
   - No other log site emits payload bytes.
6. Create `backend/src/test/java/com/botfunnel/webhook/TelegramWebhookControllerIT.java`. Extend `AbstractIntegrationTest`. Use `JobRunrInMemoryConfig` (already wired in `AbstractIntegrationTest` via `@Import`). Inject `WebTestClient` (use the inherited binding — `AbstractIntegrationTest.rebindWebTestClient()` already binds to `applicationContext` in `@BeforeEach`; do NOT re-bind in the IT). Inject `MeterRegistry` + `RawUpdateRepository` + `StorageProvider`. Read JobRunr's ENQUEUED-job count via `storageProvider.getJobs(StateName.ENQUEUED, new org.jobrunr.storage.navigation.OffsetBasedPageRequest("updatedAt:ASC", 0, 10))` (JobRunr 7.3.2 — `PageRequest` is abstract; `OffsetBasedPageRequest(String order, long offset, int limit)` is the concrete constructor). Cases:
   - **AC1 latency** — `Flux.range(0, 100).parallel(10).flatMap(i -> webTestClient.post().uri(...).bodyValue(...).exchange().returnResult(Void.class).getResponseTime()).collectList()` measure per-request `System.nanoTime()`; assert P99 < 100ms. Mark `@Tag("slow")` if CI-flaky; do NOT downgrade to mean-latency.
   - **AC2 invalid secret** — three sub-cases: empty header / wrong header / missing header → all 401 + body empty (`expectBody().isEmpty()`); `rejected_total{reason=invalid_secret}` ticked exactly N times.
   - **AC3 not found** — four sub-cases all → 404 empty body; `rejected_total{reason=project_not_found}` ticked for all four:
     - Project missing (no document).
     - Project soft-deleted (`deletedAt != null`).
     - Bot DISCONNECTED for the project.
     - Malformed ObjectId `projectId` (e.g. `"not-an-objectid"`).
   - **AC5 idempotency** — `Flux.range(0, 2).parallel(2).runOn(Schedulers.boundedElastic()).flatMap(i -> POST same updateId)` → status pair `{200, 200}`, `rawUpdateRepository.count().block() == 1`, ENQUEUED job count == 1. The `runOn(Schedulers.boundedElastic())` is critical — without it, the in-process `WebTestClient.bindToApplicationContext` chain serialises the requests (BotControllerIT precedent). NOTE: with deterministic UUID, even if both inserts raced through DuplicateKey self-heal, both enqueues collapse to one job — explicit comment in the test.
   - **AC6 controller side** — POST happy path → ENQUEUED job count after = 1; `ProcessTelegramUpdateJobTest` (T9) owns the `ownerChatId` populate assertion.
   - **Decision 4/11 self-heal** — spy `BackgroundJob` (or wrap via injectable enqueue helper) to throw `RuntimeException` on first invocation; second POST (Telegram retry) hits DuplicateKey path + re-enqueue → succeeds; one row, one job, no orphan.
   - **AC15 CSRF regression** — POST `/api/v1/projects` without `X-XSRF-TOKEN` returns 403 (verifies scoped CSRF disable did NOT leak past `/webhooks/telegram/{projectId}`).
   - **AC16 counter shape** — after N varied requests (1 happy + 2 invalid-secret + 1 not-found + 1 duplicate), assert exactly: `meterRegistry.find("telegram_webhook_received_total").counter().count() == 1`, `meterRegistry.find("telegram_webhook_rejected_total").tag("reason", "invalid_secret").counter().count() == 2`, etc. Use `assertThat(c).isNotNull().extracting(Counter::count).isEqualTo(N)` pattern.
   - **AC18 token-scrubber per log site** — use `ListAppender<ILoggingEvent>` filtered by `Logger.getName().equals("com.botfunnel.webhook.TelegramWebhookController")` AND `Level == WARN/ERROR`. Split per call site (no combined assertion). For each, force the condition (DuplicateKeyException via two POSTs with same updateId; enqueue failure via spy), then assert NO token regex matches in the captured log lines.

## Details

**Files:**

- `backend/src/main/java/com/botfunnel/webhook/TelegramWebhookController.java` — new. Single class.
- `backend/src/test/java/com/botfunnel/webhook/TelegramWebhookControllerIT.java` — new. Extend `AbstractIntegrationTest`. `@SpringBootTest` + `JobRunrInMemoryConfig`.

**Dependencies:**
- No new packages.
- Task dependencies: T1 (`MeterRegistry`), T2 (`WebhookSecretVerifier`), T4 (`TelegramUpdate` types — actually controller uses raw `Document`, but the deserialisation contract exists), T5 (`RawUpdate`, `RawUpdateRepository`), T9 (`ProcessTelegramUpdateJob` reference for the lambda capture in `BackgroundJob.enqueue(jobId, j -> j.handle(rawUpdateId))`).
- Wave 3 — runs after Wave 2 (T9).

**Edge cases:**
- `update_id` extraction from `Document` — `body.get("update_id")` may return `Integer` for small ints OR `Long`. Use `Long.valueOf(body.get("update_id").toString())` for safety, OR `body.getLong("update_id")` if Mongo coerces; verify with a test.
- `body == null` — Spring will reject with 400 before reaching the controller (per `@RequestBody` default `required=true`); do NOT add a null guard.
- Bot lookup may emit `IllegalArgumentException` for malformed `projectId` (24-char ObjectId requirement) BEFORE the Mongo round-trip. `.onErrorMap(IllegalArgumentException.class, ex -> ...)` collapses both "not found" outcomes (malformed and missing) into the same 404 path per Decision 1 / 3.
- Header name `X-Telegram-Bot-Api-Secret-Token` — exact case is what Telegram sends; HTTP headers are case-insensitive but the project's `@RequestHeader` annotation should use this exact string for clarity.
- Counter cardinality for `received_total{projectId}` — high-cardinality tags are a known anti-pattern with SimpleMeterRegistry (no eviction). Decision: include the projectId tag (user-spec implies per-project visibility, AC16 wording). Document risk; if Prometheus is added later the team revisits.
- `ListAppender` test setup — pattern is in `BotControllerIT`. Use `((Logger) LoggerFactory.getLogger(TelegramWebhookController.class)).addAppender(listAppender)` in `@BeforeEach`, remove in `@AfterEach`.

**Implementation hints:**
- Order matters for short-circuit performance — bot lookup first (most likely 404 path), then project, then secret verify, then save+enqueue. Each step short-circuits with a `Mono.empty()`-to-404 helper.
- Define a private helper `Mono<ResponseEntity<Void>> rejected(String reason, HttpStatus status)` that increments the counter and returns the response — cuts repeated code.
- For the AC1 latency test, the inherited `WebTestClient` from `AbstractIntegrationTest` already binds to `applicationContext` — it bypasses the HTTP transport overhead and measures the WebFlux pipeline time, which is what AC1 actually constrains. Do NOT rebind to a server explicitly.
- Cache the counters in `@PostConstruct` rather than constructing per-request. `Tag.of("reason", "invalid_secret")` is hot-path; allocate once.
- For the self-heal test, the cleanest injection point is to wrap the static `BackgroundJob.enqueue` behind a thin functional interface (e.g. `BiConsumer<UUID, String> enqueuer`) that the controller injects. A package-private setter lets the test override it. Document this seam in code.
