## Description

Two coupled concerns ship together:

**Payload-size filter (Decision 13)** — `WebhookPayloadSizeFilter implements WebFilter`, path-scoped to `/webhooks/telegram/{projectId}` (single segment, NOT `/**` — Security M4 anti-leak), rejects with 413 (empty body) if ANY of: `Transfer-Encoding: chunked` header present (Security C2 — `HttpHeaders.getContentLength()` returns -1 for chunked-encoded payloads, bypassing a naive `> 1_048_576` check), `Content-Length` header missing or unparseable, `Content-Length > 1_048_576`. `@Order(Ordered.HIGHEST_PRECEDENCE + 10)` — runs BEFORE the security filter chain. Owns the FIFTH counter `telegram_webhook_rejected_total{reason=payload_too_large}` (the filter short-circuits before the controller — counter MUST live where the rejection happens).

**SecurityConfig changes (Decisions 3, 13)** — Add `.pathMatchers("/webhooks/telegram/{projectId}").permitAll()` BEFORE `/api/**.authenticated()` (single segment, NOT `/**`, to prevent future sub-path leak per security M4). Narrow the CSRF matcher: `csrf.requireCsrfProtectionMatcher(new NegatedServerWebExchangeMatcher(new PathPatternParserServerWebExchangeMatcher("/webhooks/telegram/{projectId}")))` — keep existing `CookieServerCsrfTokenRepository.withHttpOnlyFalse()` + `ServerCsrfTokenRequestAttributeHandler` (non-Xor variant; the current SecurityConfig source code rejected the Xor variant because it breaks the cookie/header round-trip), only narrow the protection matcher. CSRF stays enforced on every other path.

Spring Security 6.5.x API cross-check via Context7 at impl time (Risks R3 / R8) — `NegatedServerWebExchangeMatcher` and `PathPatternParserServerWebExchangeMatcher` constructor / fluent-builder API has shifted historically.

   - `implements WebFilter`.
   - Constructor-injected `MeterRegistry`.
   - Build the rejection counter once in `@PostConstruct`: `Counter.builder("telegram_webhook_rejected_total").tag("reason", "payload_too_large").register(meterRegistry)`.
   - `filter(ServerWebExchange exchange, WebFilterChain chain)`:
     - Match path: `exchange.getRequest().getPath().value()` matches the literal pattern `/webhooks/telegram/{projectId}` (single segment after `/telegram/`). WARN log with scrubbed `projectId` (parsed from path) + the offending header value (Content-Length or Transfer-Encoding); wrap header value through `TelegramApiClient.scrubTokens` — header values cannot contain tokens but the scrubber is defense-in-depth and matches Risks "Token-scrubber sites" enumeration.

**Edge cases:**
- `Content-Length: 0` — Telegram never sends 0-byte bodies. Decision (resolved upfront, per validator round 1): PASS THROUGH (the filter rejects only on missing/unparseable header OR > 1 MB). The controller's empty `@RequestBody required=true` will return 400 from Spring's default, which Telegram retries against. A 413 here would be misleading.
- Multi-value `Transfer-Encoding` header (`gzip, chunked`) — `getFirst(...)` returns the comma-joined string; case-insensitive `contains "chunked"` catches it. Verify with a test if practical.
- Path matching subtlety — Spring's `PathPattern` parses `{projectId}` as a single segment by default (`/webhooks/telegram/abc` matches, `/webhooks/telegram/abc/def` does NOT). Use Spring's `PathPattern` API for the match (NOT a hand-rolled regex), so the same parsing semantics that drive `SecurityConfig` apply to the filter.
- Counter pre-registration — register in `@PostConstruct` so the first rejection does NOT race with metric initialisation.
- The `parseProjectIdFromPath(...)` helper used for log scrubbing — handle the rare case where the path didn't match but we somehow log (defensive: log "n/a" instead of crashing).

**Implementation hints:**
- Spring Security `requireCsrfProtectionMatcher` signature in 6.5.x: `csrf -> csrf.requireCsrfProtectionMatcher(matcher).csrfTokenRepository(repo).csrfTokenRequestHandler(handler)`. The matcher is what "needs CSRF"; negate the webhook path → webhook does NOT need CSRF.
- `PathPatternParserServerWebExchangeMatcher` constructor: `new PathPatternParserServerWebExchangeMatcher("/webhooks/telegram/{projectId}")` — verify via Context7 the constructor accepts a String (vs requiring a pre-built `PathPattern`).
- `WebFilter.filter` returns `Mono<Void>` — return `chain.filter(exchange)` to pass through, return `exchange.getResponse().setComplete()` (with status pre-set) to short-circuit.
- For the slice test, the `WebTestClient.bindToApplicationContext` setup auto-loads `WebhookPayloadSizeFilter` because it's `@Component`. To unit-test the filter in isolation, inject a stubbed `MeterRegistry` and call `filter(...)` directly with `MockServerWebExchange`.
