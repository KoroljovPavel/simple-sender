# Task 12: Code Audit (Audit Wave)

## Required Skills

Before starting, load:
- `/skill:code-reviewing` — [SKILL.md](../../../.claude/skills/code-reviewing/SKILL.md)

## Description

Holistic code-quality audit across ALL 04b source files after Wave 4 completes. This audit is NOT a per-task review (those happen during each task via `code-reviewer`); it is a cross-component sweep for issues that only become visible when the whole feature lands.

Specific scope:
- **Cross-component consistency** — duplicate resource initialisation, single `MeterRegistry` shared across controller + filter + worker, single `SubscriberService` / `FunnelTriggerService` injection chain (no accidental second wiring), single `Sha256Hex.hex` invocation site for SHA-256 (grep guard), single `payload_too_large` counter owner (the filter only — grep guard on controller).
- **Naming conventions** — method names, package layout (`com.botfunnel.webhook.*`, `com.botfunnel.subscriber.*`, `com.botfunnel.funnel.*`, `com.botfunnel.common.crypto.*`, `com.botfunnel.common.metrics.*`), test class naming (`*Test` vs `*IT`).
- **Error-handling shape uniformity** — controller returns `Mono<ResponseEntity<Void>>` consistently (no `AppException` path leaking through `GlobalErrorHandler`); filter returns 413 directly; worker rethrows after FAILED status flip.
- **Decisions section compliance** — for each of Decisions 1-19, confirm the implementation actually reflects the decided choice. Spot decisions that drifted (e.g. Decision 14 final-package adherence; Decision 19 no Deploy task observed in tasks list).
- **Dead code / over-engineering** — leftover scaffolding from earlier iterations, unused helper methods, premature abstractions not justified by the spec.
- **Comment hygiene** — no commented-out code, no "TODO" without an owner / issue link, javadocs accurate.

Write the audit report to `work/08-webhook-ingestion/logs/audits/code-audit.md` (Markdown). Findings format: `# Finding {N} — {short title}`, severity (Critical/Major/Minor/Info), file:line(s) reference, observation, recommendation. If no findings — say so explicitly in the report header.

## What to do

1. Read tech-spec.md (full), user-spec.md (Acceptance Criteria section), decisions.md (current state), and every 04b source + test file (the file list below).
2. For each cross-component concern in `## Description`, perform the check. Use grep liberally:
   - `grep -RIn "MeterRegistry" backend/src/main/java/com/botfunnel/webhook backend/src/main/java/com/botfunnel/common/metrics` → all consumers + the single bean producer.
   - `grep -RIn "MessageDigest.getInstance" backend/src/main/java/` → must be exactly one match in `Sha256Hex.java`.
   - `grep -RIn "payload_too_large" backend/src/main/java/` → must be exactly one match in `WebhookPayloadSizeFilter.java`.
   - `grep -RIn "BackgroundJob.enqueue\|BackgroundJob.<" backend/src/main/java/com/botfunnel/webhook/` → must be in `TelegramWebhookController.java` only (and verify deterministic UUID usage).
   - `grep -RIn "import com.botfunnel.subscriber\|import com.botfunnel.funnel" backend/src/main/java/com/botfunnel/webhook/ProcessTelegramUpdateJob.java` → must hit both (worker consumes both).
3. For each Decision 1-19, find the implementing code site and write `Decision N → file:line` mapping. Note any drift.
4. For each over-engineering risk (helpers not required by spec, premature interfaces, etc.), file a Minor finding.
5. Write the report. Sort findings by severity desc (Critical → Info). End with a "Summary" line: total counts per severity + go/no-go recommendation for merge.
6. Save report at `work/08-webhook-ingestion/logs/audits/code-audit.md`.
