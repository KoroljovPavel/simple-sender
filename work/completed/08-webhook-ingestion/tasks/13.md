## Description

Full-feature security audit after Wave 4 completes. This is a cross-cutting OWASP-Top-10-style review of the entire 04b surface; per-task `security-auditor` reviews already covered individual files during Waves 1-4 and security findings from those rounds should already be resolved. The audit-wave task confirms the COMPOSED system has no leaks that only become visible end-to-end.

Specific scope (each must produce a finding OR an explicit "verified, no issue" entry in the report):

1. **Scoped CSRF disable correctness** — the `NegatedServerWebExchangeMatcher` narrows protection-required matcher to NOT match `/webhooks/telegram/{projectId}`. Confirm:
   - CSRF still required on `/api/**` (POST without `X-XSRF-TOKEN` → 403).
   - CSRF NOT required on the webhook path.
   - Pattern is single-segment `{projectId}` (NOT `/**` — sub-path leak guard, Security M4).
   - `WebhookSecurityBlockTest` actually exercises both branches.

2. **Secret-token handling** — `X-Telegram-Bot-Api-Secret-Token` header:
   - NEVER appears in any log line (grep `WebhookSecretVerifier`, `TelegramWebhookController`, `WebhookPayloadSizeFilter` source files for any logging that takes `headerSecret` / candidate plain-text as input).
   - Stored only as SHA-256 hex (verified by reading `BotService.connect` + `Bot.webhookSecretHash` persistence shape).
   - Verified via `MessageDigest.isEqual` constant-time (NOT `String.equals`).

3. **Scrubber per log site** — every site enumerated in tech-spec Risks → "Token-scrubber sites" subsection wraps payload-derived input through `TelegramApiClient.scrubTokens(...)`. Confirm via grep against the enumeration:
   - `TelegramWebhookController`: WARN on DuplicateKeyException, ERROR on enqueue failure.
   - `WebhookPayloadSizeFilter`: WARN on 413.
   - `ProcessTelegramUpdateJob`: INFO on worker start, WARN per command branch, ERROR on terminal failure, INFO on ownerChatId populate, INFO on worker success.
   - At least one `ListAppender` integration test asserts the scrubber actually clears tokens (AC18).

4. **Chunked-encoding bypass** — `WebhookPayloadSizeFilter` rejects:
   - `Transfer-Encoding: chunked` header present.
   - `Content-Length` missing/unparseable.
   - `Content-Length > 1_048_576`.
   Confirm no path through the filter allows a chunked body to reach the controller. Confirm the filter runs BEFORE the security filter chain (`@Order(Ordered.HIGHEST_PRECEDENCE + 10)`).

5. **JobRunr deterministic-ID idempotency** — `UUID.nameUUIDFromBytes(rawUpdateId.getBytes(UTF_8))` is used at every enqueue site (controller's normal + duplicate-key paths). Confirm via grep — there must be NO `UUID.randomUUID()` invocation inside `TelegramWebhookController` or any helper it calls for the enqueue path.

6. **`processingError` PII/token leak avoidance** — worker writes `processingError = scrubTokens(ex.getMessage()).substring(0, min(len, 1024))`. Confirm:
   - The scrub call wraps the EXCEPTION MESSAGE (not just the throwable's class name).
   - Truncation happens AFTER scrubbing (truncating first might split a token in half, leaving recognisable suffix).
   - Length cap is 1024 chars (not bytes — chars suffice for SHA-256 hex / common payload patterns).

7. **Mass-assignment defense on `TelegramUpdate`** — all four records (`TelegramUpdate`, `Message`, `Chat`, `User`) carry `@JsonIgnoreProperties(ignoreUnknown=true)`. Confirm by inspecting source.

8. **Anti-enumeration** — 401 vs 404 distinction:
   - 401 returned ONLY when bot+project found AND deletedAt null AND secret invalid (i.e. the project EXISTS and you got the wrong secret).
   - 404 returned for missing-project / soft-deleted / disconnected-bot / malformed-ObjectId.
   - All four 404 sub-cases return BYTE-IDENTICAL responses (status code only, empty body, no diagnostic header). An attacker cannot distinguish "project does not exist" from "project deleted" from "bot disconnected" by response timing or content.

9. **Empty bodies on 401/404/413** — verified by integration tests + `Mono<ResponseEntity<Void>>` return type.

10. **OWASP A01 (Broken Access Control)** — webhook endpoint has NO authentication (intentional — Telegram doesn't have a session); access control is solely the secret header. Risk accepted. Confirm secret-header gate is enforced (no path to 200 without verifying the secret).

11. **OWASP A04 (Insecure Design)** — re-entry guard in worker (Decision 9) — confirm by reading `ProcessTelegramUpdateJob` that `if (status == DONE) return;` is the FIRST executable statement after load.

12. **OWASP A09 (Logging Failures)** — confirm no PII or secret leaks in logs end-to-end.

## Details

**Files:**

**Dependencies:**
- T11 must be complete.
- Wave 5 — parallel with T12 (code audit) and T14 (test audit).

**Edge cases:**
- Spring's default 401 emits a `WWW-Authenticate` header — note if this leaks "is this an authenticated path?". For anti-enumeration purity the controller should suppress that header on its 401 responses; if it does not, file as Minor or document why it is acceptable (Decision 3 implicitly accepts the trade-off — the controller bypasses the security chain for its 401 path).
- The audit must NOT execute the application or perform runtime attacks — it is a code-reading exercise. Any "attack walk-through" is a thought experiment grounded in source-code analysis.
- If a finding's resolution requires changes outside 04b (e.g. a `BotService.connect` change in 04a code) — file the finding but recommend deferring to a separate PR.

**Implementation hints:**
- Use the security-auditor agent's existing methodology — do not invent a new framework.
- Be specific about file:line refs in findings; the team needs to apply the fix quickly.
- For #8 (anti-enumeration), if any timing-side-channel concern surfaces (e.g. soft-deleted project takes an extra DB read compared to malformed-ObjectId) — file as Minor and propose a timing-equalisation mitigation (constant-time delay, or a single uniform path through `Mono.just(notFound())`).
