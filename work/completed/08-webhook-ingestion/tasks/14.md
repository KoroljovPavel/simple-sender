## Description

Full-feature test-quality audit after Wave 4 completes. The per-task `test-reviewer` rounds during Waves 1-4 covered individual test classes; this audit is a CROSS-CUTTING review that asks "does the test suite actually verify the feature contract end-to-end, or does it have AC-shaped holes?".

Specific scope (each must produce a finding OR a "verified" entry):

1. **AC1–AC19 mapping** — for each user-spec acceptance criterion AC1..AC19, identify the test(s) that would fail if the AC were removed from production code. Build a table `AC → test_class::test_method(...)`. If any AC has NO mapped test, file a Critical finding.

2. **Tech-spec Acceptance Criteria mapping** — same exercise against the tech-spec's "Acceptance Criteria" section bullets (DB indexes visible, no regressions in existing tests, etc.).

3. **Meaningful assertions** — for each test class, sample N assertions and confirm they actually exercise the AC, not just "method does not throw". Red flag: `assertThat(mono).isNotNull()` followed by no further assertion.

4. **`ListAppender` per-site filtering (AC18)** — every WARN/ERROR log site that emits payload-derived strings has its OWN `ListAppender`-filtered test (not a single combined assertion across multiple sites). Verify the filter is by `Logger.getName()` AND `Level` — not just by message-substring search (substring search is brittle when log formats evolve).

5. **`@MockitoSpyBean` usage** — used for stub call-count assertions (`SubscriberService`, `FunnelTriggerService`). Confirm not over-used (e.g. spying on `EventService` is fine; spying on `BotRepository` is fragile — if any spy lives on a Repository, file as Minor and recommend a real-DB integration test instead).

6. **Race-test correctness** — AC5 parallel size=2 + AC6 ownerChatId no-overwrite race. Confirm:
   - The AC5 test uses actual `Flux.range(...).parallel(N).flatMap(...)` (not sequential `for`).
   - The AC6 no-overwrite test runs the worker TWICE on different chat ids — second invocation must NOT alter the bot.
   - Neither test relies on `Thread.sleep` to "wait for the race" (use awaitility or deterministic `StepVerifier.thenAwait`).

7. **No flaky `Thread.sleep`** — grep `backend/src/test/java/com/botfunnel/webhook/` and surrounding directories for `Thread.sleep`. Each match must be either (a) inside an `@Disabled` manual-procedure test (e.g. TTL), or (b) documented as load-test pacing (rare). Otherwise file as Minor and propose `Awaitility.await().untilAsserted(...)`.

8. **Re-entry guard test** — `ProcessTelegramUpdateJobTest` has a test that seeds `processingStatus=DONE` and asserts NO events / NO stub calls / NO counter ticks after invocation. Confirm presence + correctness.

9. **TTL index regression test** — `RawUpdateRepositoryTest` asserts `partialFilterExpression` contains `['PENDING', 'DONE']` UPPERCASE (regression guard for completeness F5). Confirm presence + correct uppercase literals.

10. **Counter NPE protection (AC16)** — every test that asserts a counter value uses `assertThat(counter).isNotNull().extracting(Counter::count).isEqualTo(N)` pattern (NPE guard if a counter wasn't created during the test). Find any `counter.count()` call without prior null check — file as Minor.

11. **Test pyramid balance** — count unit-test methods vs integration-test methods across 04b. Roughly 70/30 unit/integration is healthy; if controller IT is dominant and unit coverage is sparse, file as Info.

12. **Existing-test regressions** — confirm `BotControllerIT`, `TelegramSenderIT`, `ProjectControllerIT`, `SecurityBlockTest` are still in the test suite and were not silently disabled or modified to accommodate the refactor (Sha256Hex extraction was the only refactor planned).

Write the audit report to `work/08-webhook-ingestion/logs/audits/test-audit.md`.

## Details

**Files:**
- `work/08-webhook-ingestion/logs/audits/test-audit.md` — new. The report.

**Dependencies:**
- T11 must be complete.
- Wave 5 — parallel with T12 (code audit) and T13 (security audit).

**Edge cases:**
- An AC that is intentionally NOT integration-tested (e.g. AC19 if it's an operator-checklist item only) — record as "AC{N} → covered by staging-smoke runbook (T8), no automated test" rather than a Critical gap.
- A test class that covers multiple ACs in one method (`@DisplayName("AC2 + AC3 + AC4 — rejection paths")`) — split-recommendation is a Minor finding; per-AC clarity matters for grep-ability when an AC fails in CI.
- The audit MUST NOT modify any test file — output is the report only. If a test is obviously broken, file a Critical finding and let the lead decide who fixes it.

**Implementation hints:**
- A grep-based starting point for AC → test mapping: `grep -RIn "AC[0-9]" backend/src/test/java/com/botfunnel/webhook/` — many test methods are named or commented with the AC number.
- For #11 test pyramid count, use `grep -RIn "@Test" backend/src/test/java/com/botfunnel/webhook/ | wc -l` to count test methods; `grep -L "AbstractIntegrationTest" backend/src/test/java/com/botfunnel/webhook/ | xargs grep -l "@Test"` to find unit-only classes.
- Severity calibration: Critical = "AC has no test"; Major = "test exists but is brittle/insufficient"; Minor = "naming, clarity, or marginal coverage"; Info = "observation, no action".
