# Task 15: Pre-deploy QA (Final Wave)

## Required Skills

Before starting, load:
- `/skill:pre-deploy-qa` — [SKILL.md](../../../.claude/skills/pre-deploy-qa/SKILL.md)

## Description

Per Decision 19, 04b ships WITHOUT a Deploy task (CI/CD platform TBD per `deployment.md`) and WITHOUT a post-deploy-qa task (no MCP tooling for Telegram bot interaction — staging-smoke runbook from T8 is the de-facto post-deploy verification). T15 is the final mechanical gate before merge: run the full test suite, verify every acceptance criterion passes, inspect the persisted indexes via `mongosh`, confirm grep invariants, and produce a go/no-go report.

This task assumes T12 (code audit), T13 (security audit), and T14 (test audit) have completed and any Critical findings from those audits have been resolved. If a Critical from any audit is still open at the time T15 starts — T15 surfaces that fact in its report and recommends "no-go" without proceeding further.

## What to do

1. **Pre-flight check.** Read `work/08-webhook-ingestion/logs/audits/code-audit.md`, `.../security-audit.md`, `.../test-audit.md`. If any has unresolved Critical findings, write the pre-deploy-qa report with "no-go" + the open critical IDs and STOP.
2. **Test suite.** Run `cd backend && ./gradlew test`. All tests must pass. Record the test count + duration.
3. **AC verification — user-spec.** For each user-spec AC (AC1..AC19 plus AC11a — 20 labeled criteria total) in `work/08-webhook-ingestion/user-spec.md`, confirm:
   - The mapped test(s) (from T14's mapping table) actually pass in the suite run.
   - Where the AC is operator-verifiable only (AC1 latency under real load, AC17 ownerChatId post-Connect, AC19 — anything from "Пользователь проверяет"), confirm the staging-smoke runbook (T8) covers it.
4. **AC verification — tech-spec.** For each bullet under tech-spec "Acceptance Criteria" section, confirm:
   - DB indexes present via `mongosh botfunnel --eval 'db.raw_updates.getIndexes()'` (you may need to run an integration test first to create the collection):
     - `_id_`.
     - `projectId_updateId_unique` (unique).
     - `projectId_1`.
     - `ttl_createdAt` with `expireAfterSeconds=7776000` AND `partialFilterExpression: { processingStatus: { $in: ['PENDING', 'DONE'] } }` (UPPERCASE).
   - No regressions in `BotControllerIT`, `TelegramSenderIT`, `ProjectControllerIT`, `SecurityBlockTest` — confirm each runs as part of `./gradlew test` and passes.
   - `SecurityConfig.pathMatchers("/webhooks/telegram/{projectId}").permitAll()` ordered BEFORE `/api/**.authenticated()` — confirm by reading the source.
   - `Sha256Hex.hex(...)` is the SOLE SHA-256 implementation: `grep -RIn "MessageDigest.getInstance(\"SHA-256\")" backend/src/main/java/` returns exactly one match.
   - Webhook handler returns `Mono<ResponseEntity<Void>>` for 200/401/404 (never via `GlobalErrorHandler`) — confirm by reading `TelegramWebhookController` source.
   - `payload_too_large` counter exclusively in filter: `grep -RIn "payload_too_large" backend/src/main/java/com/botfunnel/webhook/TelegramWebhookController.java` returns no match; `grep -RIn "payload_too_large" backend/src/main/java/com/botfunnel/webhook/WebhookPayloadSizeFilter.java` returns at least one match.
   - `MeterRegistry` bean present at context startup with no actuator on classpath: `MeterRegistryConfigTest` passes; `grep "spring-boot-starter-actuator" backend/build.gradle` returns no match.
5. **gitleaks** — confirm gitleaks pre-commit hook passed on the latest commit. The project installs its hook via `scripts/install-hooks.sh`, which runs `gitleaks detect --staged --verbose` directly (NOT the `pre-commit` framework). Re-run with: `gitleaks detect --staged --verbose --no-banner --redact` from the repo root. Exit code 0 = clean.
6. **Manual smoke commands.** Boot the app locally (or against staging — Decision 19 says the runbook covers staging) and execute:
   - `curl -i -X POST -H "Transfer-Encoding: chunked" http://localhost:8080/webhooks/telegram/507f1f77bcf86cd799439011 -d '{}'` → expect 413.
   - `curl -i -X POST http://localhost:8080/api/v1/projects` → expect 401 (authentication required — baseline).
   - `curl -i -X POST -b 'XSRF-TOKEN=...; SESSION=...' http://localhost:8080/api/v1/projects` (authenticated, NO `X-XSRF-TOKEN` header) → expect 403 (CSRF baseline still active for non-webhook paths — Spring Security returns 403 for CSRF failures, NOT 401).
   Document the actual response codes in the report.
7. **Report.** Write `work/08-webhook-ingestion/logs/qa/pre-deploy-qa-report.md` (Markdown). Structure:
   - Header — feature, branch, commit SHA, audit summary references.
   - Pre-flight result (audits clear OR open critical IDs).
   - Test suite result (count + duration + green/red).
   - user-spec AC table (AC → test → pass/fail OR runbook-covered).
   - tech-spec AC table (each bullet → check → pass/fail).
   - Manual smoke command results.
   - **Final verdict**: GO / NO-GO. If NO-GO, enumerate the blockers.

## Details

**Files:**
- `work/08-webhook-ingestion/logs/qa/pre-deploy-qa-report.md` — new. The QA report.

**Dependencies:**
- T12, T13, T14 must be complete (Audit Wave). Their outputs feed the pre-flight check.
- Wave 6 (Final Wave).

**Edge cases:**
- AC1 latency (P99 < 100ms) — the integration test enforces this in CI; if marked `@Tag("slow")` and excluded from the default Gradle run, T15 must explicitly run the slow tag (`./gradlew test -PincludeTags=slow` or equivalent) AND record the actual P99 measured.
- TTL index timing — the partial-filter assertion in `RawUpdateRepositoryTest` verifies SHAPE, not actual eviction. T15 does NOT need to wait 90 days for TTL eviction; documenting the shape match is sufficient.
- A flaky test that fails on retry but passes deterministically — file as Major in the report and recommend a follow-up fix; verdict can still be GO if the test isolation is clear, but document the trade-off.
- If `JobRunrInMemoryConfig` causes a CI failure unrelated to 04b code, log it but do NOT block on it — coordinate with the lead.
- If `mongosh` is unavailable in the QA environment — substitute `db.raw_updates.getIndexes()` invocation via the application's Mongo driver from a one-off integration test; document the substitution.

**Implementation hints:**
- Save the report under `logs/qa/` to match the audit `logs/audits/` convention. Create the directory if needed.
- The report should be roughly 1-2 pages of structured Markdown — long enough to be auditable, short enough that the lead can read it in under 5 minutes.
- The pre-flight is the cheapest gate — do it FIRST and short-circuit on unresolved Critical findings before running the test suite.
- The verdict line should be the absolute LAST line of the report — `**Verdict: GO**` or `**Verdict: NO-GO (blockers: F1, F3, AC4-failing)**`.
