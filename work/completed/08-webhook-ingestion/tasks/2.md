# Task 2: `Sha256Hex` utility + `WebhookSecretVerifier` component

## Required Skills

## Description

Per Decision 15 the private `BotService.sha256Hex(String)` method has reached the DRY threshold — the upcoming `WebhookSecretVerifier` (this task) is the second consumer of identical SHA-256 hex hashing. Inlining the duplicate would invite algorithm drift (UTF-8 vs platform encoding, lowercase vs uppercase hex), so the helper is promoted to `com.botfunnel.common.crypto.Sha256Hex.hex(String): String` (`public static`). It lives next to the existing `TokenEncryptor` in the `common/crypto/` package per architectural precedent.

Per Decision 2 the webhook handler verifies the incoming `X-Telegram-Bot-Api-Secret-Token` header by re-hashing it and comparing constant-time against `bots.webhookSecretHash` via `MessageDigest.isEqual(byte[], byte[])`. `String.equals` would be timing-vulnerable and is forbidden here. The verifier owns the policy (constant-time comparison, no plaintext logging, null/empty input handling) while `Sha256Hex` owns only the algorithm.

Per Decision 16 `WebhookSecretVerifier` is a `@Component` (not a static method on `Sha256Hex`) — this keeps the verification policy DI-injectable into `TelegramWebhookController` (T10) and `@MockitoSpyBean`-able in integration tests.

`BotService.connect` (the producer side) is refactored to call `Sha256Hex.hex(...)`; the private `sha256Hex` method is deleted. `BotControllerIT` must stay green after the refactor — it is the regression guard.

3. Refactor `BotService.connect` to call `Sha256Hex.hex(...)` instead of the private helper. Delete the private `sha256Hex` method from `BotService`. Re-run `BotControllerIT` to confirm zero behavioral change.
4. Create `backend/src/main/java/com/botfunnel/webhook/WebhookSecretVerifier.java` — `@Component` with `public boolean verify(String headerSecret, String storedHashHex)`. Behavior:
   - If `headerSecret` is `null` or empty → return `false` (do NOT throw; controller's 401 path expects a boolean).
   - If `storedHashHex` is `null` → return `false` (defensive — Bot must have a stored hash to be CONNECTED, but guard for robustness).
   - Compute `candidateHashHex = Sha256Hex.hex(headerSecret)`.
   - Decode both `candidateHashHex` and `storedHashHex` from hex to `byte[]`; if either is malformed hex → return `false` (do NOT throw — protects against corrupt persisted state).
   - Return `MessageDigest.isEqual(candidateBytes, storedBytes)`.
   - Do NOT log the header value, even truncated. Do NOT log the stored hash. A debug-level log on the comparison outcome is acceptable but must not include either operand.
5. Create `backend/src/test/java/com/botfunnel/common/crypto/Sha256HexTest.java`. Cases:
   - Known-vector parity with the producer side — for an input string, the result equals what `BotService.connect` would persist (hand-compute or capture from current behavior before refactor).
   - UTF-8 byte handling — input containing non-ASCII (e.g. `"кіт"`) hashes deterministically across runs.
   - Output is lowercase hex, length 64.
   - `null` input → throws (match existing `BotService.sha256Hex` contract; document the choice in a code comment if changing).
6. Create `backend/src/test/java/com/botfunnel/webhook/WebhookSecretVerifierTest.java`. Cases:
   - Match — header equals the plaintext that produced the stored hash → returns `true`.
   - Mismatch — different header → returns `false`.
   - Empty `headerSecret` → `false`.
   - `null` `headerSecret` → `false`.
   - `null` `storedHashHex` → `false`.
   - Malformed hex in `storedHashHex` (odd length, non-hex chars) → `false`.
   - Verifies the implementation uses `MessageDigest.isEqual` via `static MockedStatic<MessageDigest>` (Mockito 5.x, no separate `mockito-inline` artifact needed). The test stays plain JUnit 5 with NO Spring context (no `@MockitoSpyBean` — that requires Spring). Document the choice in the test javadoc. DO NOT introduce a timing-based assertion (CI-flaky).

## Details

**Files:**

- `backend/src/main/java/com/botfunnel/common/crypto/Sha256Hex.java` — new. Final class, private constructor throws `UnsupportedOperationException`, single `public static String hex(String)` method using `MessageDigest.getInstance("SHA-256")` + `StandardCharsets.UTF_8` + `HexFormat.of().formatHex(...)` (Java 17+ API) for lowercase output.
- `backend/src/main/java/com/botfunnel/bot/BotService.java` — modify. Replace the call site inside `connectAfterPreChecks(...)` (the existing call is `sha256Hex(secretHex)` where `secretHex` is the hex-encoded random secret generated upstream — NOT a user plaintext) with `Sha256Hex.hex(secretHex)`. Delete the `private static String sha256Hex(String s)` method (and any helper imports it brought in if now unused). Add `import com.botfunnel.common.crypto.Sha256Hex;`.
- `backend/src/main/java/com/botfunnel/webhook/WebhookSecretVerifier.java` — new. Spring `@Component`. Single public method. Defensive null/empty/malformed handling returns `false`. No `Logger` calls that include operand values.
- `backend/src/test/java/com/botfunnel/common/crypto/Sha256HexTest.java` — new. Plain JUnit 5; no Spring context needed.
- `backend/src/test/java/com/botfunnel/webhook/WebhookSecretVerifierTest.java` — new. Plain JUnit 5; no Spring context (the verifier has no injected collaborators yet — pure unit test).

**Dependencies:**
- No new packages. `MessageDigest`, `HexFormat`, `StandardCharsets` all in `java.base`.
- Task dependencies: none. Wave 1 leaf task. T9 (worker) and T10 (controller) depend on this for the verifier; the worker does not use the verifier directly but the controller does.

**Edge cases:**
- Length-mismatch byte arrays — `MessageDigest.isEqual` handles this internally without leaking length-information via early return. Do NOT add a length pre-check.
- Hex decoding helper: use `HexFormat.of().parseHex(...)`; on `IllegalArgumentException` return `false`.
- Producer (`BotService.connect`) currently expects `null` input to throw an NPE; preserve that contract in `Sha256Hex.hex` (test asserts it). The verifier's `null` handling is a separate concern at the verifier layer, NOT pushed down into `Sha256Hex`.
- `MessageDigest.isEqual` IS the constant-time primitive — the verifier MUST NOT short-circuit with `if (candidate.length != stored.length) return false;` before calling it.

**Implementation hints:**
- Use `java.util.HexFormat.of().formatHex(byte[])` for lowercase hex; matches Spring's own `Hex` utility output but stays in `java.base`.
- For the `verify_usesMessageDigestIsEqual` test, the cleanest mechanism is `try (MockedStatic<MessageDigest> mocked = mockStatic(MessageDigest.class, CALLS_REAL_METHODS)) { ... mocked.verify(() -> MessageDigest.isEqual(any(), any()));}`. Document the choice in the test javadoc — do NOT add a timing-based assertion (CI-flaky).
- Keep `Sha256Hex` and `WebhookSecretVerifier` test classes separate — they have orthogonal concerns and reviewer feedback historically pushes back on grab-bag test files.
