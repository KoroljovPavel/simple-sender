# Task 3: `TelegramCommandParser` pure utility

## Required Skills

Before starting, load:
- `/skill:code-writing` — [SKILL.md](../../../.claude/skills/code-writing/SKILL.md)

## Description

The worker (T9) needs to recognise `/start` and `/stop` Telegram commands in incoming messages and extract the optional payload string. Telegram clients sometimes append `@botname` to a command when the bot is in a group (e.g. `/start@MyBot ref_abc`). Per the Architecture "Worker path" step 3 in `tech-spec.md` the parser must strip that suffix before matching the command name and must return the trailing payload string as `""` (not `null`) when absent — user-spec AC7 explicitly requires `metadata.startPayload=""` for a bare `/start`.

The parser is a pure static utility (no Spring context, no I/O, no logging). It returns a small `ParsedCommand` value type with the normalised command name (without leading slash, without `@botname` suffix) and the payload string. This isolates the parsing concern from the worker dispatch logic so both sides can be unit-tested independently. T9's worker consumes the parsed value to decide which branch of its dispatch matrix to take.

## What to do

1. Create `backend/src/main/java/com/botfunnel/webhook/ParsedCommand.java` — a Java `record` `(String command, String payload)` where:
   - `command` is the lowercased command name without leading `/` and without `@botname` suffix (e.g. `"start"`, `"stop"`, `"foo"`).
   - `payload` is the substring after the command + optional `@botname`, with leading whitespace trimmed; empty string if no payload. NEVER `null`.
   - Add a static factory `ParsedCommand.notACommand()` returning the sentinel `new ParsedCommand("", "")` for inputs that are NOT a command (plain text, leading whitespace, empty string, single `/`).
2. Create `backend/src/main/java/com/botfunnel/webhook/TelegramCommandParser.java` — `public final class` with private constructor, single `public static ParsedCommand parse(String input)` method. Rules:
   - `null` input → `notACommand()`.
   - Input that does not start with `/` (after NO leading-whitespace trim — preserve user-spec AC12 "leading whitespace" non-command case) → `notACommand()`.
   - Input `"/"` alone → `notACommand()`.
   - Otherwise: strip leading `/`, split on the first whitespace OR newline character. Token before the split is the command-with-optional-bot-suffix; remainder (with one leading whitespace consumed) is the payload.
   - Strip `@botname` suffix from the command token: split the command token on `@`; first half is the command, second half is discarded. The split is case-INSENSITIVE on the `@` literal — `@` is always ASCII.
   - Case-sensitivity per user-spec test matrix: `/Start` is NOT the same as `/start`. The parser preserves the original case in the command field — the caller (T9 worker) decides whether to match case-insensitively. Test the parser preserves case; test that the worker (T9) handles only lowercase `/start` / `/stop`.
   - Multi-space payload: `"/start  ref_X"` → command `"start"`, payload `"ref_X"`. Strip exactly one whitespace character after the command; subsequent leading whitespace in the payload is preserved (or, simpler: trim leading whitespace from the payload uniformly — pick one and DOCUMENT in the parser javadoc). Recommended: trim leading whitespace from payload (matches "/start payload" UX expectation).
   - Newline payload: `"/start\nfoo"` → command `"start"`, payload `"foo"` (newline counts as the splitter). Make sure the trailing-newline normalisation does not eat the entire payload if it itself contains newlines (Telegram payloads do).
3. Create `backend/src/test/java/com/botfunnel/webhook/TelegramCommandParserTest.java`. Cover the full matrix from `tech-spec.md` Unit tests section + a handful of regression cases:
   - `/start` → `("start", "")`.
   - `/start payload` → `("start", "payload")`.
   - `/start ref_a b c` → `("start", "ref_a b c")` (everything after the first space is payload; intermediate spaces preserved).
   - `/start@SomeBot` → `("start", "")`.
   - `/start@SomeBot ref_X` → `("start", "ref_X")`.
   - `/stop` → `("stop", "")`.
   - `/stop@SomeBot` → `("stop", "")`.
   - non-command text `"hello"` → `notACommand()`.
   - `/` alone → `notACommand()`.
   - empty string `""` → `notACommand()`.
   - leading whitespace `" /start"` → `notACommand()` (parser does NOT pre-trim).
   - case-sensitivity `/Start` vs `/start` — both parse, command field preserves case (assert exact match).
   - multi-space `/start  ref_X` → `("start", "ref_X")`.
   - newline payload `"/start\nref_X"` → `("start", "ref_X")`.
   - long payload (e.g. 4 KB) round-trips intact.
   - tab between command and payload `"/start\tref_X"` → behaviour documented (recommend treating tab same as space).
4. Verify `./gradlew test --tests *TelegramCommandParserTest` green.

## Details

**Files:**

- `backend/src/main/java/com/botfunnel/webhook/ParsedCommand.java` — new. Single record with two `String` components and a static factory. Add a one-line javadoc on the record clarifying that `command` is the name WITHOUT leading slash and WITHOUT `@botname` suffix, and `payload` is `""` when absent.
- `backend/src/main/java/com/botfunnel/webhook/TelegramCommandParser.java` — new. Final class, private constructor throws `UnsupportedOperationException`, one public static method. Add a class-level javadoc summarising the rules (especially the case-sensitivity preservation and the newline/tab-as-splitter convention).
- `backend/src/test/java/com/botfunnel/webhook/TelegramCommandParserTest.java` — new. Plain JUnit 5, no Spring context.

**Dependencies:**
- No new packages.
- Task dependencies: none. Wave 1 leaf. T9 consumes the parser.

**Edge cases:**
- Empty payload after command + `@botname` — `/start@MyBot` parses to `("start", "")`, not `("start", " ")` or `null`.
- Tabs and other Unicode whitespace — `Character.isWhitespace(...)` is the canonical splitter predicate. Document the choice in the javadoc.
- Very long payloads — Telegram message text is up to 4096 chars; parser must not truncate or apply any length cap.
- `/start@` (suffix-marker but empty bot name) — recommend treating as `("start", "")` (command part before `@` is what matters); add a test pin.
- `/start@@x` (multiple `@`) — split on first `@`; subsequent `@` chars stay in the discarded suffix half. Add a test pin.

**Implementation hints:**
- Implementation can be entirely `String.indexOf`-based; no regex needed. A regex would still be acceptable but would add overhead for a hot path.
- Keep the parser allocation-light (single substring per call). The worker invokes this for every text message.
- DO NOT lowercase the command field inside the parser — the worker's case-sensitive matching is the AC. Pin this with a test that asserts `/Start` → `("Start", "")`.
