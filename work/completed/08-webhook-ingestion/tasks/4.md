# Task 4: `TelegramUpdate` + nested records (`Message`, `Chat`, `User`)

## Required Skills

Before starting, load:

## Description

The worker (T9) and controller (T10) deserialise the inbound Telegram webhook JSON into typed Java records. Per Decision 6 the project uses snake_case `record` types with `@JsonIgnoreProperties(ignoreUnknown=true)` (mass-assignment defense) instead of `Map<String, Object>`. Non-message update kinds (`callback_query`, `edited_message`, `channel_post`, `edited_channel_post`, `my_chat_member`, `chat_member`, `inline_query`, `shipping_query`, `pre_checkout_query`, `poll_answer`) are modelled as `JsonNode` slots — the worker only needs to DETECT their presence to resolve `metadata.updateKind` per user-spec AC11; their schemas belong to Epic 05/06.

The four record files (`TelegramUpdate`, `Message`, `Chat`, `User`) live in `com.botfunnel.webhook.dto`. Tests cover representative deserialization, `@JsonIgnoreProperties` swallowing unknowns, missing nested `message` → `null` (so the worker can safe-navigate), `message.from == null` (channel posts), malformed JSON propagating Jackson exceptions, empty `{}` → all-null record, and `update_id` as String → deserialization failure (type-safety regression guard).

This task does NOT introduce a `Jackson ObjectMapper` instance — the project already has one via Spring Boot's autoconfiguration; the test class can `@Autowired` it from `@JsonTest` or instantiate a default one and rely on Jackson auto-detection of records (Jackson 2.12+ supports records natively).

## What to do

1. Create `backend/src/main/java/com/botfunnel/webhook/dto/TelegramUpdate.java`. Record components in the order listed in tech-spec Data Models:
   - `Long update_id` — primary identifier (used in unique compound index per T5).
   - `Message message` — typed nested record.
   - `Message edited_message`, `Message channel_post`, `Message edited_channel_post` — same `Message` type.
   - `JsonNode callback_query`, `JsonNode my_chat_member`, `JsonNode chat_member`, `JsonNode inline_query`, `JsonNode shipping_query`, `JsonNode pre_checkout_query`, `JsonNode poll_answer` — opaque slots.
   - `@JsonIgnoreProperties(ignoreUnknown=true)` on the record.
2. Create `backend/src/main/java/com/botfunnel/webhook/dto/Message.java`. Components: `Long message_id`, `User from`, `Chat chat`, `Long date`, `String text`. `@JsonIgnoreProperties(ignoreUnknown=true)`.
3. Create `backend/src/main/java/com/botfunnel/webhook/dto/Chat.java`. Components: `Long id`, `String type` (`"private"|"group"|"supergroup"|"channel"`), `String title`, `String username`. `@JsonIgnoreProperties(ignoreUnknown=true)`.
4. Create `backend/src/main/java/com/botfunnel/webhook/dto/User.java`. Components: `Long id`, `Boolean is_bot`, `String first_name`, `String last_name`, `String username`, `String language_code`. `@JsonIgnoreProperties(ignoreUnknown=true)`. NOTE: `User` here is a Telegram-side record (the `from` field). Do NOT confuse with any platform-side user — name-collision with `com.botfunnel.user.User` (if any exists) is resolved by package boundary.
5. Create `backend/src/test/java/com/botfunnel/webhook/dto/TelegramUpdateDeserializationTest.java`. Use Jackson `ObjectMapper` directly (no Spring context). Cases:
   - Snake-case mapping — fixture JSON with `update_id`, `message.message_id`, `message.from.first_name`, `message.chat.type` populates all fields correctly.
   - `@JsonIgnoreProperties` — fixture with extra top-level `"some_future_field": "x"` and extra `"junk": 1` inside `message` deserialises WITHOUT throwing.
   - Missing nested `message` — fixture `{"update_id": 1}` → `update.message() == null`, safe to dereference via `update.message() != null` guard.
   - Channel post → `message.from == null` — fixture with `message` populated but no `from` → `message.from()` returns `null`, no NPE on the chain.
   - Malformed JSON (e.g. truncated `{"update_id": 1, "mes`) → `JsonProcessingException` or subclass thrown. Assert the exception class.
   - Empty JSON `{}` → all components null, including `update_id` (assert each is null; record itself is non-null).
   - Type-mismatch — fixture `{"update_id": "abc"}` (String where Long expected) → deserialisation fails with `MismatchedInputException`. Assert the exception class.
   - `callback_query` populated → `update.callback_query() != null` and is a `JsonNode` whose textual content matches the fixture.
   - `my_chat_member` populated, `message` null → demonstrates slot independence.
6. Verify `./gradlew test --tests *TelegramUpdateDeserializationTest` green.

## Details

**Files:**

- `backend/src/main/java/com/botfunnel/webhook/dto/TelegramUpdate.java` — new. Single record declaration with `@JsonIgnoreProperties(ignoreUnknown=true)`. Import `com.fasterxml.jackson.databind.JsonNode` for the opaque slots.
- `backend/src/main/java/com/botfunnel/webhook/dto/Message.java` — new. Record with five components.
- `backend/src/main/java/com/botfunnel/webhook/dto/Chat.java` — new. Record with four components.
- `backend/src/main/java/com/botfunnel/webhook/dto/User.java` — new. Record with six components.
- `backend/src/test/java/com/botfunnel/webhook/dto/TelegramUpdateDeserializationTest.java` — new. JUnit 5 + Jackson. Instantiate a `new ObjectMapper()` per class (no Spring) OR `@Autowired ObjectMapper` from `@JsonTest`. Pick the simpler.

**Dependencies:**
- No new packages — Jackson is already on classpath via Spring Boot starters.
- Task dependencies: none. Wave 1 leaf. Consumed by T9 worker (deserialises raw_updates.payload Document → TelegramUpdate via `ObjectMapper.convertValue` or `treeToValue`) and indirectly by T10 controller (controller forwards the raw body to Mongo; deserialisation happens at the worker boundary).

**Edge cases:**
- Snake-case binding for records — Jackson 2.12+ supports record components by name. Verify no `@JsonProperty` annotations are needed by writing the test FIRST.
- `is_bot` field on `User` — `Boolean` (not `boolean`) so `null` is distinguishable from `false` (Telegram might omit the field; do NOT default-coerce to `false`).
- `update_id` as `Long` (not `long`) — channel-post fixtures sometimes have a 60-bit value; primitive `long` boxes inefficiently in subsequent `equals`/`hashCode` paths but functionally correct. Use boxed `Long` to align with the rest of the record (all components are nullable from the JSON-shape standpoint).
- Mass-assignment — `@JsonIgnoreProperties(ignoreUnknown=true)` covers the mass-assignment defense for fields not in the record. DO NOT additionally annotate `@JsonCreator` or `@JsonAutoDetect` — defaults are correct.
- A future schema extension (e.g. new Telegram field) requires adding a record component AND a fresh test fixture; do NOT use `Object` or `Map<String, JsonNode>` as a catch-all.

**Implementation hints:**
- Implementation order: write the test class with all 9 fixtures first (they will fail with "Cannot find class TelegramUpdate"), then create the four records, then iterate until green.
- Fixture JSON strings can be inline string literals OR loaded from `src/test/resources/telegram/...`; prefer inline for short fixtures, resources for the channel-post one (largest).
- For the type-mismatch test, the message-class chain has changed across Jackson versions — assert against the parent class `JsonProcessingException` if `MismatchedInputException` is brittle, but the latter is preferred for specificity.
