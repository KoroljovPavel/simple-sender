# Task 5: `RawUpdate` entity + repository + status enum

## Required Skills

Before starting, load:
- `/skill:code-writing` — [SKILL.md](../../../.claude/skills/code-writing/SKILL.md)

## Description

The controller (T10) persists every accepted webhook body into the new MongoDB collection `raw_updates` BEFORE enqueuing the worker (T9). This task creates the persistence triad: the `RawUpdate` `@Document` entity, the `RawUpdateStatus` enum (`PENDING|DONE|FAILED`), and the reactive repository.

Two indexes are critical:
1. **Unique compound `(projectId, updateId)`** — Decision 4. The controller relies on `DuplicateKeyException` for idempotency: if Telegram retries with the same `update_id`, the second insert fails with `DuplicateKeyException` and the controller still re-enqueues via the deterministic UUID (self-heal path). Without the unique index, retries would create duplicate rows.
2. **TTL on `createdAt`, partial-filtered on UPPERCASE `processingStatus IN ['PENDING', 'DONE']`** — Decision 8. `FAILED` rows persist indefinitely as the audit trail (user-spec AC13). `expireAfter="90d"` replaces the deprecated `expireAfterSeconds`. The completeness validator's F5 finding was that lowercase `['pending','done']` would never match Spring Data MongoDB's `enum.name()` persistence and the TTL would silently apply to ALL rows including FAILED — UPPERCASE literals are mandatory.

`processingError` is nullable and only populated by the worker (T9) on FAILED. The field is scrubbed via `TelegramApiClient.scrubTokens` and truncated to ≤1024 chars BEFORE persisting (the truncation lives in the worker code path, not the entity — the entity just has the column).

## What to do

1. Create `backend/src/main/java/com/botfunnel/webhook/RawUpdateStatus.java` — enum with three constants: `PENDING`, `DONE`, `FAILED`. No additional behaviour.
2. Create `backend/src/main/java/com/botfunnel/webhook/RawUpdate.java` — `@Document(collection = "raw_updates")` class. Class-level `@CompoundIndexes({ @CompoundIndex(name="projectId_updateId_unique", def="{'projectId': 1, 'updateId': 1}", unique=true) })`. Fields:
   - `@Id String id`.
   - `@Indexed String projectId`.
   - `Long updateId` (note: NOT `@Indexed` standalone — covered by the compound index; assert this via `IndexOperations.getIndexInfo()` in the repository test).
   - `org.bson.Document payload` — raw Telegram update JSON, persisted as BSON sub-document.
   - `RawUpdateStatus processingStatus`.
   - `String processingError` — nullable; only populated on FAILED; scrubbed+truncated to 1024 chars at the worker layer.
   - `@Indexed(name="ttl_createdAt", expireAfter="90d", partialFilter="{ 'processingStatus': { $in: ['PENDING', 'DONE'] } }") Instant createdAt`.
   - Standard getters/setters or a constructor + accessor pattern matching `Bot.java` precedent. Match whichever style `Bot.java` uses (verify before writing).
3. Create `backend/src/main/java/com/botfunnel/webhook/RawUpdateRepository.java` — `public interface RawUpdateRepository extends ReactiveMongoRepository<RawUpdate, String> { }`. No custom finder methods required in this task — T9 worker uses `findById`, T10 controller uses `save`.
4. Create `backend/src/test/java/com/botfunnel/webhook/RawUpdateRepositoryTest.java`. Extend `AbstractIntegrationTest` (Testcontainers Mongo). Cases:
   - **Duplicate-key**: insert one `RawUpdate(projectId=p, updateId=42)`; insert another with the same pair → second `save(...)` emits `DuplicateKeyException` via `StepVerifier`.
   - **Index metadata**: via `reactiveMongoTemplate.indexOps(RawUpdate.class).getIndexInfo()` assert:
     - An index named `projectId_updateId_unique` exists with the right key pair AND `unique=true`.
     - An index named `ttl_createdAt` exists with `expireAfter` resolved (Mongo translates `expireAfter="90d"` to `expireAfterSeconds=7776000`) AND `partialFilterExpression` contains `{ processingStatus: { $in: [ "PENDING", "DONE" ] } }` — UPPERCASE literals. This is the regression guard for completeness F5.
     - An index named `projectId_1` exists (from the `@Indexed` on `projectId`).
   - **Partial-filter exclusion (NOTE: documented manual procedure only, NOT a test method)**: the TTL background job runs every 60s on the server side and is NOT triggerable from a unit/integration test, so there is no automated test for the "FAILED row persists past 90 days" invariant. Instead, document in this task's `Details` section a manual procedure: against a non-prod Mongo, `db.raw_updates.insertOne({projectId, updateId, processingStatus: 'FAILED', createdAt: ISODate(now-180d), ...})`, then `db.raw_updates.findOne({...})` ≥ 60s later and confirm the row still exists. This procedure is operator-side, NOT a JUnit test method — do NOT add a `@Disabled` test.
   - **Status persistence**: insert `RawUpdate` with `processingStatus=PENDING`, reload via `findById`, assert `processingStatus == PENDING` (regression guard against an `@Enumerated` configuration drift).
5. Verify `./gradlew test --tests *RawUpdateRepositoryTest` green; manually run `mongosh botfunnel --eval 'db.raw_updates.getIndexes()'` against a local Mongo to confirm the three expected indexes appear with the documented shapes.

## Details

**Files:**

- `backend/src/main/java/com/botfunnel/webhook/RawUpdate.java` — new. Class-level `@Document` + `@CompoundIndexes`. Field-level `@Id`, `@Indexed`, `@Indexed(name=..., expireAfter=..., partialFilter=...)` annotations. Match the getter/setter or constructor style used by `Bot.java`.
- `backend/src/main/java/com/botfunnel/webhook/RawUpdateStatus.java` — new. Three-constant enum, no fields, no methods.
- `backend/src/main/java/com/botfunnel/webhook/RawUpdateRepository.java` — new. Empty body — extends `ReactiveMongoRepository<RawUpdate, String>`.
- `backend/src/test/java/com/botfunnel/webhook/RawUpdateRepositoryTest.java` — new. Extend `AbstractIntegrationTest`. `@Autowired ReactiveMongoTemplate` + `@Autowired RawUpdateRepository`. Use `StepVerifier` for reactive assertions.

**Dependencies:**
- No new packages.
- Task dependencies: none. Wave 1 leaf. Consumed by T9 worker (`findById`, `save` for status flip), T10 controller (`save` for ingestion), and T11 indirectly (filter is upstream of the repo).

**Edge cases:**
- Spring Data MongoDB `expireAfter` parsing — accepts ISO-8601 durations OR shorthand like `"90d"`. Verify by inspecting `getIndexInfo()` in the test: in Spring Data MongoDB 5.x, `IndexInfo.getExpireAfter()` returns `Optional<Duration>` — assert `getExpireAfter().get().equals(Duration.ofDays(90))`. The raw `expireAfterSeconds=7776000` value is what `db.raw_updates.getIndexes()` shows on the Mongo side, but the test asserts the `Duration` form returned by Spring's API, not the raw int.
- `org.bson.Document` for `payload` (NOT `String`, NOT `Map`, NOT `JsonNode`) — Spring Data MongoDB serialises `Document` to a BSON sub-document directly, preserving Telegram's JSON shape without going through a separate Jackson conversion. The worker (T9) converts `payload` → `TelegramUpdate` via `ObjectMapper.convertValue(document, TelegramUpdate.class)` OR `objectMapper.readValue(document.toJson(), TelegramUpdate.class)` — leave the choice to T9.
- Partial-filter syntax — `def` and `partialFilter` strings must be VALID JSON literal strings (single-quoted-around-double-quoted will not parse). Use exactly `def = "{'projectId': 1, 'updateId': 1}"` and `partialFilter = "{ 'processingStatus': { $in: ['PENDING', 'DONE'] } }"` as in the tech-spec Data Models section.
- Testcontainers Mongo lifecycle — `AbstractIntegrationTest` starts/stops the container per test class; index creation happens on first `save` or eagerly via `@EventListener(ApplicationReadyEvent.class)`. Verify the test calls a no-op `save` if indexes are not yet created, OR explicitly call `reactiveMongoTemplate.indexOps(RawUpdate.class).ensureIndex(...)` for safety.

**Implementation hints:**
- Match `Bot.java`'s constructor + setters pattern. Most Spring Data MongoDB classes in this project follow that style. Don't introduce Lombok if Lombok is not currently used (check `build.gradle`).
- `processingError` is plain `String` with no length annotation; the truncation is the responsibility of T9 worker code path. Add a one-line javadoc on the field noting "scrub+truncate ≤1024 chars handled at worker layer".
- For the duplicate-key test, the second `save` returns a `Mono<RawUpdate>` that errors with `DuplicateKeyException`. Use `StepVerifier.create(repo.save(...)).expectError(DuplicateKeyException.class).verify()`.
