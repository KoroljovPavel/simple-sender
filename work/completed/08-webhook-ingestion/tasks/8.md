# Task 8: Staging-smoke runbook `docs/staging-smoke/08-webhook-ingestion.md`

Before starting, load:

## Description

Per Decision 19 the feature ships WITHOUT a `post-deploy-qa` task — there is no MCP tooling for Telegram bot interaction, and the inbound webhook path involves Telegram's real servers and the operator's actual phone client. The staging-smoke runbook IS the de-facto post-deploy verification: an operator with a throwaway BotFather bot, ngrok, and `mongosh` walks through the happy path in 10-15 minutes after the merge to confirm the deployed code accepts real inbound updates end-to-end.

The runbook must be reproducible without out-of-band knowledge — every command literal, every Telegram UI action, every Mongo query is spelled out. It mirrors the style and length of `docs/staging-smoke/07-telegram-sender.md` (the immediately prior runbook). It additionally documents the JobRunr Failed-queue inspection procedure (Decision 9 / Risk R5 mitigation) so an operator who observes a malfunction has a path to inspect the dead-letter state without escalating to engineering.

Output language is Ukrainian (per `CLAUDE.md` "User-facing docs"); commands and field names stay in English. Document the runbook for an operator who is technical but not deeply familiar with the codebase.

## What to do

1. Read `docs/staging-smoke/06-bot-connection.md` and `docs/staging-smoke/07-telegram-sender.md` to absorb the style, section ordering, command format conventions, and ngrok-setup boilerplate. Match the level of detail.
2. Read `work/08-webhook-ingestion/user-spec.md` "Пользователь проверяет" section to extract the canonical user-side checklist.
3. Create `docs/staging-smoke/08-webhook-ingestion.md`. Required sections (Ukrainian headers):
   - **Передумови** — environment (staging URL, Mongo URI, BotFather access, ngrok account, `mongosh` installed). Mirror the prereqs section of 07.
   - **Створити одноразовий бот у BotFather** — `/newbot`, copy token, mention token is throwaway.
   - **Підняти ngrok-тунель** — `ngrok http 8080`, copy public HTTPS URL.
   - **Підключити бот до проекту** — UI flow: open admin → Projects → Create or select → Connect Telegram bot → paste token → click Connect. Includes the implicit `setWebhook` call this triggers (with the ngrok URL appended).
   - **Надіслати `/start ref_smoke_001` з телефону власника бота** — from the operator's personal Telegram, find the bot by `@botname`, send `/start ref_smoke_001`.
   - **Перевірити raw_updates у Mongo** — `mongosh ...` command to list the most recent `raw_updates` row, expected shape (projectId match, `processingStatus=DONE`, `payload.update_id` non-null).
   - **Перевірити events** — `mongosh ...` command for `events.find({type: 'telegram_command_start'}).sort({createdAt:-1}).limit(1)`, expected `metadata.startPayload == "ref_smoke_001"`.
   - **Перевірити, що `bot.ownerChatId` встановлено** — `mongosh ...` find by bot `_id`, expected `ownerChatId` populated (closes user-spec AC6 happy path).
   - **Натиснути "Send test message" в адмінці** — UI verification that the 04c gap closes after `ownerChatId` is set (test message reaches the operator's Telegram chat).
   - **Надіслати `/stop`** — from same Telegram chat, expected `events.find({type: 'telegram_command_stop'})` row appears within seconds.
   - **Перевірити Failed-queue (у разі підозри на помилку)** — `mongosh ...` query `db.raw_updates.find({processingStatus:'FAILED'})` and the JobRunr equivalent if JobRunr storage uses a separate Mongo collection (verify the collection name from `JobRunrMongoConfig`). Document what `processingError` looks like (truncated, scrubbed) and the next-step escalation path.
   - **Очистити** — Disconnect bot via UI, delete the throwaway bot via BotFather `/deletebot`, kill ngrok.
   - **Чек-ліст результатів** — bullet list mirroring user-spec ACs that this runbook actually verifies (AC1, AC5 indirectly, AC6, AC7, AC8, AC17). Note explicitly which user-spec ACs are NOT covered by this runbook and are integration-test-only (AC2, AC3, AC4, AC11, AC11a, AC14, AC15, AC16, AC18, AC19).
4. Self-review: have someone (or your future self) walk the runbook end-to-end with NO additional access to source code; every step must work as written. If any step requires out-of-band knowledge (e.g. "ask backend team for the staging API URL"), add the URL/value to the Передумови section.

## Details

**Files:**

- `docs/staging-smoke/08-webhook-ingestion.md` — new. Ukrainian narrative + English command literals. Markdown.

**Dependencies:**
- No code or build dependencies.
- Task dependencies: none. Wave 1 task. Decision 19 explicitly places the runbook EARLY in the wave plan so it is ready BEFORE the feature ships (operator needs to run it on the merge commit).

**Edge cases:**
- ngrok URL freshness — note in Передумови that ngrok URLs are session-scoped; if the operator reconnects ngrok they must repeat the Connect step.
- Concurrent operators — if two operators run the runbook simultaneously on the same staging project, the second `/start` may not populate `ownerChatId` (already-populated atomic predicate fails per AC6). Add a note in the `/start` section to use a fresh BotFather bot per operator OR coordinate via Slack.
- JobRunr collection name — `JobRunrMongoConfig` only configures the `MongoClient` bean; the actual collection names live in JobRunr's `MongoDBStorageProvider` internals (defaults are `jobrunr_jobs`, `jobrunr_recurring_jobs`, `jobrunr_backgroundjobservers`, `jobrunr_metadata`). Connect to the staging Mongo and run `db.getCollectionNames()` to confirm; document the exact name observed (typically `jobrunr_jobs`) in the Failed-queue section.
- `events` collection schema — `metadata.startPayload` is the user-spec AC7 field name; do not invent alternates.

**Implementation hints:**
- Use fenced code blocks for shell commands; specify `bash` or `mongosh` as the language.
- For UI steps, format as `1. ... 2. ... 3. ...` with the element name in `**bold**`.
- Include a "Якщо щось пішло не так" section at the end of each major step, pointing to the most likely cause (e.g. "Якщо `/start` не з'являється у `events`, перевір ngrok-тунель і JobRunr Failed-queue").
- Keep total length under ~300 lines; 07's runbook is the upper bound on length.
