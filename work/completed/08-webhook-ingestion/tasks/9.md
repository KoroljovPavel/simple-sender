# Task 9: `ProcessTelegramUpdateJob` worker

## Required Skills

Before starting, load:
- `/skill:code-writing` — [SKILL.md](../../../.claude/skills/code-writing/SKILL.md)

## Description

The worker is the heart of the 04b feature. JobRunr dispatches `ProcessTelegramUpdateJob.handle(String rawUpdateId)` from the controller's deterministic-UUID enqueue (Decision 11). The worker runs on a JobRunr thread (blocking-safe per `HardDeleteJob` / `ProjectHardDeleteJob` precedent), loads the `RawUpdate` row by id, branches on the parsed Telegram update kind, populates `Bot.ownerChatId` on the first eligible private `/start` (Decision 5), calls the `SubscriberService` + `FunnelTriggerService` stubs, writes audit events via `EventService.logEventBlocking`, and flips `raw_updates.processingStatus` from PENDING to DONE.

Three correctness mechanisms must be preserved:
1. **Re-entry guard (Decision 9)** — the worker's FIRST action is "if `processingStatus == DONE` return". JobRunr can retry an already-succeeded job if the success ack didn't observe in time; without the guard, events double-fire and stubs are invoked twice.
2. **Cascade ordering (Decision 12)** — every event write is `EventService.logEventBlocking(...).block()` BEFORE `rawUpdate.save(processingStatus=DONE)`. A mid-flight worker crash must leave NO DONE row without its audit event.
3. **Failure path (Decision 9)** — on caught exception, atomically write `processingStatus=FAILED` + `processingError=scrubTokens(ex.getMessage()).substring(0, min(len, 1024))` via `findAndModify`, increment `telegram_worker_outcome_total{outcome=failure}`, then **rethrow** so JobRunr's default retry (10 attempts, exponential) kicks in.

Per Decision 5, the `ownerChatId` populate is an atomic `reactiveMongoTemplate.findAndModify(Query(_id=botId, status=CONNECTED, ownerChatId=null), Update.set("ownerChatId", chatId), Bot.class).block()`. Predicate-fail returns `Mono.empty()` (treated as no-op — another worker already populated). This eliminates the read-then-write race when two `/start` messages from different chats land on different worker threads simultaneously.

Per security audit M7 every log site that touches payload-derived strings wraps through `TelegramApiClient.scrubTokens(...)`. The enumerated sites are in tech-spec Risks → "Token-scrubber sites" subsection.

1. Read the precedent files in `## Context Files` — `ProjectHardDeleteJob.java` for cascade ordering, `HardDeleteJob.java` + `HardDeleteJobTest.java` for blocking-on-JobRunr-thread + direct-invocation test style, `EventService.java` for `logEventBlocking` signature, `Bot.java` for `ownerChatId` field, `BotRepository.java` for `findById`, `TelegramApiClient.java` for `scrubTokens`.
2. Create `backend/src/main/java/com/botfunnel/webhook/ProcessTelegramUpdateJob.java` — `@Component public class ProcessTelegramUpdateJob` with `public void handle(String rawUpdateId)`. Constructor-injected collaborators:
   - `RawUpdateRepository rawUpdateRepository`
   - `BotRepository botRepository`
   - `ReactiveMongoTemplate reactiveMongoTemplate` (for the atomic `findAndModify` on Bot)
   - `EventService eventService`
   - `SubscriberService subscriberService`
   - `FunnelTriggerService funnelTriggerService`
   - `MeterRegistry meterRegistry`
   - `ObjectMapper objectMapper` (for `payload` Document → `TelegramUpdate` conversion)
3. Implement the worker body per Architecture "Worker path" steps 1-5:
   - **Step 1 — Load + re-entry guard.** `rawUpdate = rawUpdateRepository.findById(rawUpdateId).block()`. If `null` → log WARN with scrubbed id (the row should always exist; absence means JobRunr fired before save committed, which the deterministic-UUID guarantees should not happen — but log and return). If `processingStatus == DONE` → return immediately (no event, no stub call, no counter tick). If `processingStatus == FAILED` → continue (this is a JobRunr retry of a previously-failed attempt).
   - **Step 2 — Deserialize.** `TelegramUpdate update = objectMapper.convertValue(rawUpdate.getPayload(), TelegramUpdate.class)`. Wrap any `IllegalArgumentException` / `JsonProcessingException` in the failure-path handler.
   - **Step 3 — Branch by update kind** (full matrix from Architecture):
     - `update.message() != null && message.text() != null && message.text().startsWith("/")` — parse via `TelegramCommandParser.parse(text)`:
       - `"start"` private (chat.type=="private"):
         - Look up the bot for this project: `bot = botRepository.findByProjectIdAndStatus(projectId, CONNECTED).blockOptional().orElse(null)`; the project-bot relationship is 1:1 in 04b per user-spec. Source `userId` for the event from `project.getOwnerId()` (the project's app user) — load project alongside bot if not already in scope.
         - If `bot != null && bot.getOwnerChatId() == null` → atomic `reactiveMongoTemplate.findAndModify(Query(_id=botId, status=CONNECTED, ownerChatId=null), Update.set("ownerChatId", chat.id), Bot.class).block()` per Decision 5. (Note: the in-memory `bot.getStatus() == CONNECTED` predicate would be tautological because the prior `findByProjectIdAndStatus(projectId, CONNECTED)` already guarantees it; the `status=CONNECTED` predicate in the `findAndModify` query is still essential — it makes the write itself fail safely if the bot was disconnected between the lookup and the populate.) Log INFO on populate event with scrubbed `chatId`.
         - Call `subscriberService.upsertFromTelegramUpdate(projectId, telegramBotId, chat.id, chat.type, from.id, from.first_name, from.last_name, from.username, from.language_code).block()`.
         - Call `funnelTriggerService.fire(projectId, chat.id, "on_start", parsed.payload()).block()`.
         - Event: `eventService.logEventBlocking(project.getOwnerId(), "telegram_command_start", null, null, Map.of("projectId", projectId, "startPayload", parsed.payload(), "chatId", chat.id)).block()`. The 5-param signature is `(userId, eventType, ipAddress, userAgent, metadata)` — mirror `ProjectHardDeleteJob`'s call shape. `ipAddress` and `userAgent` are `null` for worker-originated events. `startPayload` is always non-null (parser guarantees `""` if no payload).
       - `"stop"` private:
         - Call `subscriberService.markUnsubscribed(projectId, telegramBotId, chat.id).block()`.
         - Call `funnelTriggerService.cancelActiveFor(projectId, chat.id).block()`.
         - Event: `eventService.logEventBlocking(project.getOwnerId(), "telegram_command_stop", null, null, Map.of("projectId", projectId, "chatId", chat.id)).block()`.
       - `"start"` group/supergroup/channel — event `"telegram_command_start"` only, NO ownerChatId populate, NO subscriber upsert (AC9).
       - Other command (`/foo`, `/unknown`...) private — event `"telegram_message_received"`, no stubs (AC12).
       - Other command non-private — event `"telegram_message_received"`, no stubs.
     - Plain text (`message.text() != null && !text.startsWith("/")`):
       - Private chat → `subscriberService.upsertFromTelegramUpdate(...).block()` + event `"telegram_message_received"`.
       - Non-private → event `"telegram_message_received"` only.
     - Non-message update kinds (slot resolution):
       - For each modeled `JsonNode` slot (`callback_query`, `my_chat_member`, `chat_member`, `inline_query`, `shipping_query`, `pre_checkout_query`, `poll_answer`) — if non-null → event `"telegram_update_other"` with `metadata.updateKind=<jsonFieldName>`, no stubs (AC11).
       - For `edited_message`, `channel_post`, `edited_channel_post` (typed `Message`) — if non-null AND `message == null` → event `"telegram_update_other"` with the field name as `updateKind`, no stubs.
     - Fallback — `message == null` (or `message.from == null` for channel posts) AND no modeled slot populated → event `"telegram_update_other"` with `updateKind="unknown"` (AC11a). Safe-navigate; do NOT throw NPE.
   - **Step 4 — Cascade.** Event write completes via `.block()` BEFORE `rawUpdate.setProcessingStatus(DONE); rawUpdateRepository.save(rawUpdate).block();`. Increment `telegram_worker_outcome_total{outcome=success}` after the save.
   - **Step 5 — Failure handler.** Wrap the entire body of step 3+4 in `try { ... } catch (Throwable t) { ... }`. On catch: atomically write `processingStatus=FAILED` + `processingError=scrubTokens(t.getMessage()).substring(0, Math.min(scrubbed.length(), 1024))` via `reactiveMongoTemplate.findAndModify(Query(_id=rawUpdateId), Update.set("processingStatus", FAILED).set("processingError", scrubbed), RawUpdate.class).block()`. Increment `telegram_worker_outcome_total{outcome=failure}`. Log ERROR with scrubbed exception message. **Rethrow** (wrap in `RuntimeException` if checked) so JobRunr triggers retry. NOTE: The PRE-FAILURE-WRITE re-entry guard from Step 1 is the ONLY explicit FAILED-state handling — once `processingStatus=FAILED` is persisted and rethrow propagates, JobRunr's retry policy fires `handle(...)` again; that retry hits Step 1, sees FAILED, falls through (NOT a DONE short-circuit) and re-runs the dispatch matrix. Do NOT add explicit FAILED-case code at Step 1 beyond the implicit fall-through.
4. Every log site that string-formats payload-derived input wraps the value through `TelegramApiClient.scrubTokens(...)`. Sites enumerated in tech-spec Risks → "Token-scrubber sites" subsection (`ProcessTelegramUpdateJob` block).

## Details

**Files:**

- `backend/src/main/java/com/botfunnel/webhook/ProcessTelegramUpdateJob.java` — new. `@Component`. Constructor injection (no field injection per project convention).
- `backend/src/test/java/com/botfunnel/webhook/ProcessTelegramUpdateJobTest.java` — new. Extend `AbstractIntegrationTest`. Use `@SpringBootTest` so all stubs and the real repository are wired.

**Dependencies:**
- No new packages.
- Task dependencies (resolved per validator round 1): T1 (`MeterRegistry` bean for `telegram_worker_outcome_total` counter — required at context boot), T3 (`TelegramCommandParser`), T4 (`TelegramUpdate` records), T5 (`RawUpdate` + repository), T6 (`SubscriberService` stub), T7 (`FunnelTriggerService` stub). T2 is NOT a dependency — the worker neither calls `WebhookSecretVerifier` nor `Sha256Hex.hex`; secret verification is owned by the controller (T10) upstream of enqueue.
- Wave 2 — runs after Wave 1 completes.

**Edge cases:**
- `bot == null` when handling a private `/start` (bot lookup races with a concurrent disconnect) — treat as a failure, write event with kind `telegram_update_other` and `updateKind="unknown"`, do NOT populate ownerChatId on a null bot.
- `message.from == null` AND `chat.type == "channel"` (channel posts have no sender) — safe-navigate, treat as non-private, event only.
- `text == null` AND `message != null` (image-only, sticker-only, document message) — this is NOT enumerated in tech-spec AC11 (the AC enumerates non-message kinds like callback_query etc.). Resolved: classify as `telegram_update_other` with `updateKind="message"` and no stub calls. The reasoning: AC10 specifies "plain text private" triggers upsert; the upsert key is `text != null`. A media-only message has no upsertable text content, so it falls through to the "unmodeled message variant" branch. This is the same handling shape as AC11's "modeled slot present" branch. Document in code comment.
- `processingError` whose scrubbed length is < 1024 — truncation is `Math.min(scrubbed.length(), 1024)`, NOT a forced 1024-length string. Do NOT pad.
- `objectMapper.convertValue(document, TelegramUpdate.class)` may throw `IllegalArgumentException` wrapping `JsonProcessingException` — the failure handler catches `Throwable`, so this is covered.
- JobRunr retry — the rethrown exception type must propagate as a `RuntimeException` (JobRunr's API surface). Wrap checked exceptions if any are caught (none expected here).

**Implementation hints:**
- Keep the dispatch switch readable — extract per-branch private methods to keep `handle` itself small (exact helper names left to implementer judgement). Each helper returns `void` and may throw — the outer try/catch in `handle` covers all of them.
- The `updateKind` resolution for non-message updates can be a single helper `String resolveUpdateKind(TelegramUpdate update)` that returns the first non-null slot's JSON field name OR `"unknown"`.
- For the AC11 parameterised tests, use `@ParameterizedTest @MethodSource("nonMessageUpdateKinds")` returning a stream of `(jsonFieldName, fixtureJson)` pairs.
- Spy beans: `@MockitoSpyBean SubscriberService subscriberService;` — calls hit the no-op impl but Mockito records invocations. The spy survives across all `@Test` methods unless `@DirtiesContext` is used; reset via `Mockito.reset(subscriberService)` in `@BeforeEach`.
- The failure-handler `findAndModify` MUST be atomic — do NOT do a `findById` + setter mutation + `save`; that opens a race window where two retries could trample each other.
