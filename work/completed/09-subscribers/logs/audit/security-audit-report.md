# Security Audit — Epic 09 Subscribers

## Summary

Full-feature OWASP Top 10 (2021) audit of the Subscribers CRM (Tasks 1–11): 5 new controllers (20 endpoints), the `SignedDownloadToken` HMAC primitive, the async CSV export pipeline, the `TelegramSender` 403/400 subscriber hook, the `ProjectHardDeleteJob` cascade, and the 4 new frontend pages. **3 findings: 0 Critical, 0 High, 0 Medium, 3 Low.** The core security surfaces are well-built: HMAC verify is constant-time with `projectId` bound into the payload and expiry checked only after the signature is trusted; every one of the 20 endpoints opens with `requireOwned` (anti-IDOR); the cursor codec enforces all five F6 reject rules before query construction; CSV cells are formula-neutralized before RFC-4180 escaping; mass-assignment is whitelist-gated on every Request DTO; and the download endpoint writes a denied-audit event before every non-200 response. The three Low findings are a misleading-but-defended weak-key config default, a deliberately-narrowed audit surface from the Task 9 session-guard deviation, and subscriber-PII custom-field values retained 365d in `subscriber_events` (accepted-by-design in Task 3). **Overall posture: `ready`** — no finding blocks deploy; all three are defense-in-depth / detection-coverage items for the Task 15 gate to confirm-and-accept.

## Findings

### F1: Predictable all-zeros default for `SUBSCRIBER_EXPORT_TOKEN_KEY` with an incorrect fail-fast claim [Severity: Low]
**OWASP:** A02 — Cryptographic Failures (also A05 — Security Misconfiguration)
**Location:** `backend/src/main/resources/application.properties:51-52`; parse logic at `backend/src/main/java/com/botfunnel/common/crypto/SignedDownloadToken.java:118-138`
**Issue:** The property defaults to 64 hex zeros: `app.subscriber.export.token-key=${SUBSCRIBER_EXPORT_TOKEN_KEY:0000...0000}`, with an inline comment asserting "Zero-hex default trips fail-fast on real deploys." That claim is false: a 64-character all-zeros string is a *valid* 32-byte hex key, so `decodeKey()` (which only rejects blank / non-hex / wrong-length) accepts it and the application boots normally with a publicly-known HMAC key. If a production deploy omits the env var, signed download tokens are forgeable by anyone who reads this committed file. Realistic exploit: an authenticated user mints a token for another project's export. **Compensating controls hold:** the download endpoint is session-guarded (`/api/**` authenticated, Task 9 deviation) AND calls `requireOwned(currentUserId(), projectId, true)` at `SubscriberExportController.java:247` — so a forged token still 404s on a project the caller does not own. Net effect is degradation of the HMAC defense-in-depth layer (R8), not a direct PII breach. The identical pattern already exists for `app.bot.token-encryption-key` (`application.properties:47`), so this is a codebase-wide dev-ergonomics default, not an Epic-09 regression.
**Fix:** (a) Correct the misleading comment — it does NOT fail-fast. (b) Add a `@Profile("prod")`-gated startup assertion (or a `@ConfigurationProperties` validator) that rejects the known all-zeros sentinel for both `app.subscriber.export.token-key` and `app.bot.token-encryption-key`, so a missing prod secret fails closed at boot instead of silently using a public key. Task 16 already injects the real secret via GitHub Actions, so this only guards the forgot-to-set case.
**Status:** Open

### F2: Download denied-audit (Decision 16 / F4) does not fire for unauthenticated recon [Severity: Low]
**OWASP:** A09 — Security Logging & Monitoring Failures
**Location:** `backend/src/main/java/com/botfunnel/subscriber/export/SubscriberExportController.java:211-289` (download handler); root cause is the Task 9 deviation recorded in `decisions.md` Task 9
**Issue:** Decision 16 specifies that every non-200 download outcome writes a `subscribers_export_download_denied` event to support recon-attack detection (R8). The implementation does this correctly for every in-controller branch (`deny(...)` at lines 224/227/233/240/249/253/262/275/279/285 writes the audit before returning). However, Task 9 deviated by keeping the endpoint under Spring Security's `/api/**` `authenticated()` rule, so an unauthenticated request is rejected at the filter chain with 403 **before** the controller runs — meaning anonymous token-enumeration / expired-URL brute-forcing produces no `..._download_denied` audit row. This is a detection-coverage gap, not data exposure: the data stays HMAC + session + ownership protected, so the deviation is net-safer on the data axis. Surfaced per the task's "decisions.md deviation affecting security posture MUST be a finding" rule.
**Fix:** Accept-and-document (the recommended path — the deviation strengthens data protection): note in `deployment.md` that anonymous download recon is observable via the Spring Security 403 access log / `telegram_webhook`-style filter metrics rather than the `events` collection, so R8 monitoring should watch both surfaces. Alternatively, if filter-chain-level recon visibility is required, add a lightweight `permitAll` + in-controller-only auth for this single route (larger blast radius — not recommended for an MVP). Product confirmation requested per decisions.md Task 9.
**Status:** Open

### F3: Subscriber custom-field values retained 365d in `subscriber_events` audit metadata [Severity: Low]
**OWASP:** A09 — Security Logging & Monitoring Failures (GDPR data-minimization)
**Location:** `backend/src/main/java/com/botfunnel/subscriber/SubscriberServiceImpl.java:228-240` (`recordCustomFieldsSet` writes `oldValues`/`newValues`); TTL at `subscriber/SubscriberEvent.java:30-31`
**Issue:** `recordCustomFieldsSet` stores the full old and new custom-field values (`metadata.oldValues` / `metadata.newValues`) on the `subscriber_events` document, which is subscriber-identity-joined (`subscriberId`) and retained 365 days via `@Indexed(expireAfter="365d")`. Custom fields are operator-defined and may hold subscriber PII (e.g. a `phone` or `email` custom field). The event already records `changedKeys`, so retaining full before/after values for a year is more than the audit minimally needs. Decision 16 deliberately routes IP/UA *away* from `subscriber_events` for exactly this GDPR reason; the value-snapshot here is the residual PII surface. Realistic concern: a data-subject erasure or retention request must also reach `subscriber_events` value snapshots, and a year-long PII trail widens breach scope if the collection leaks. Already flagged and accepted by-design in the Task 3 security review ("PII in 365d TTL — accepted").
**Fix:** Either (a) ratify the acceptance explicitly at the Task 15 gate with the GDPR Art. 6(1)(f) basis written into `deployment.md` (consistent with Decision 16's framing); or (b) reduce to `changedKeys` + value lengths/hashes instead of plaintext values if data-minimization review prefers it. No code change is mandatory for deploy — this is a documented policy decision.
**Status:** Open

## Focused Checklist Results

1. **HMAC token verify** (`SignedDownloadToken.java`) — **PASS.** Constant-time `MessageDigest.isEqual` at :82 (NOT `Arrays`/`String.equals`); `projectId` in payload (:146) and matched against the path at `SubscriberExportController.java:231`; expiry checked at :93 only AFTER signature trust (:82) and JSON parse (:88); fail-fast key parse (length+hex) at :118-138 mirrors `TokenEncryptor`; `Mac.getInstance("HmacSHA256")` at :102. (Weak default key is F1, a config concern, not a parse-logic defect.)
2. **`requireOwned` coverage** — **PASS.** First executable line on all 20 endpoints: SubscriberController :138/170/179/200/212/224/236; SubscriberCustomFieldsController :63; TagController :44/51/62/69-70; CustomFieldsController :87/98/137/176; SubscriberExportController :160/200/315 and (download) :247 after token-verify per the documented token-gated ordering.
3. **Mass-assignment protection** — **PASS.** Every Request record carries `@JsonIgnoreProperties(ignoreUnknown=true)` (all `*Request.java` verified). Custom-field PATCH silently drops unknown keys at `SubscriberCustomFieldsController.java:83-86`; `projectId`/`ownerId`/`subscriberId` are server-derived from path+session, never read from body (DTOs lack those components). `SetCustomFieldsRequest.values` capped at 100 entries.
4. **CSV injection** (`SubscriberCsvWriter.java`) — **PASS.** `neutralizeFormula` (:100-109) triggers on `= + - @ \t \r` and runs on EVERY cell via `appendCell` (:92-93) BEFORE `escape` RFC-4180 (:113); applies to stringified numerics (negative `telegramChatId` → `-...` correctly prefixed) and the whole `custom_fields` JSON string (:82, :134).
5. **Webhook 403/400 side-effects** (`TelegramSender.java`) — **PASS.** Typed `terminalReason` enum routing (`terminalReasonFor` :327-336, dispatched at :170-191 — no substring sniffing in the service); `eventService.logEvent(...telegram_send_failed)` at :156 fires BEFORE `dispatchSubscriberHook` (markBlocked/markDeleted) at :162; hook failure is locally caught (:187) and never alters the original exception.
6. **Rate-limit fail-open exposure** — **PASS.** `bf:rate:start:` (`SubscriberServiceImpl.java:270-284`), `bf:download:export:` (`SubscriberExportController.java:348-362`), `bf:rate:personal_message:` (`SubscriberController.java:290-304`) all fail-open with greppable WARN constants (`SUBSCRIBER_START_RATE_REDIS_FAIL_OPEN`, `EXPORT_DOWNLOAD_RATE_REDIS_FAIL_OPEN`, `PERSONAL_MESSAGE_RATE_REDIS_FAIL_OPEN`); refresh-url fails CLOSED → 503 + `EXPORT_REFRESH_REDIS_FAIL_CLOSED` (`SubscriberExportController.java:364-380`), narrowly catching only `RedisConnectionFailureException`/`RedisSystemException` so the 429 is not swallowed. R12 monitoring-gap reference in `deployment.md` is **N/A here** — `deployment.md` is updated by Task 16 (Deploy), not yet run (see Recommendations).
7. **Cursor decode hardening** (`SegmentFilterBuilder.decodeCursor` :114-145) — **PASS.** All five rules before query build: (1) base64url try/catch :119-123; (2) exactly `{v,id}` :161-173; (3) recursive `$`-key reject :176-188; (4) `v` integral number :138; (5) `id` `^[a-f0-9]{24}$` :141. Any failure → 400 `invalid_cursor`, never 500/leak.
8. **Signed-URL audit events** (Decision 16 / F4, `SubscriberExportController.download`) — **PARTIAL.** In-controller every non-200 writes `subscribers_export_download_denied` with the full `reason` enum before responding (`deny` :434-451, `tokenSegmentPrefix` = first 8 chars of payload segment :455-462; IP/UA threaded via `HttpRequestUtils`). Routed to platform `events`, not `subscriber_events`. **PARTIAL** because anonymous requests are rejected pre-controller by the session guard → no audit row (finding **F2**).
9. **Personal-message rate limit** (F5, `SubscriberController.java:239-242, 290-304`) — **PASS.** Per-project bucket `bf:rate:personal_message:{projectId}`, counts before send (no Telegram call on the rejected request), no per-subscriber key (no cardinality blow-up). Breach → 429 `personal_message_rate_limited`. (Task checklist text says "429 `telegram_rate_limited`" — that conflates two distinct codes; the implementation correctly uses `personal_message_rate_limited` (429) for bucket breach and `telegram_rate_limited` (503) for Telegram retry-exhaustion, matching the tech-spec error-code table and `SubscriberPersonalMessageIT`.)
10. **Custom field `defaultValue` per-type validation** (F9) — **PASS.** `CustomFieldsController.create` (:100) and `update` (:154) both route `defaultValue` through the same `CustomFieldValueValidator.validate(type, value)` used for subscriber PATCH (`SubscriberCustomFieldsController.java:88`). Validator (`CustomFieldValueValidator.java`) enforces STRING ≤1024, NUMBER `Double.isFinite`, BOOLEAN shape, DATE ISO-8601 → 422 `custom_field_type_mismatch`; no untyped `Object` reaches Mongo unchecked.
11. **GridFS metadata integrity** (F10) — **PASS.** `ExportSubscribersJob.java:148` writes `metadata.exportId` + `metadata.projectId` (+ backfilled `metadata.rowCount` :196-199), matching tech-spec §52 exactly and supporting cascade-by-`metadata.projectId` (`ProjectHardDeleteJob.java:113-115`) and targeted cleanup-by-`fileId` (`ExportCleanupJob.java:69-72`, GridFS-first then flip). `contentType="text/csv"` at :170. Filename is server-derived from the ObjectId `exportId` (`subscribers-export-<id>.csv`), **not owner-supplied** → no path-traversal surface. *Note:* the checklist's `metadata.ownerId` is over-specification — it is not in tech-spec §52/Decision 8, and cascade/cleanup target by `projectId`/`fileId`, so its absence creates no security gap.

## Cross-cutting Checks Results

1. **Secrets / hardcoded keys** — **PASS (with F1).** No inlined keys in source; `SUBSCRIBER_EXPORT_TOKEN_KEY` loaded only via `@Value("${app.subscriber.export.token-key}")` (`SignedDownloadToken.java:43`); tests do not inline it. The only secret-shaped literal is the all-zeros property default → F1.
2. **Logging hygiene** — **PASS.** Grep of all Epic-09 `log.*` statements shows no subscriber PII (names/phone), no HMAC tokens, no full signed URLs, no raw bot tokens. Sender/job error paths route through `TelegramApiClient.scrubTokens` + 1024-truncation (`ExportSubscribersJob.java:230-265`); metadata-only logging (chatId/projectId/subscriberId) confirmed. Download audit logs only the 8-char payload prefix.
3. **Dependency vulnerabilities** — **PASS.** `git log 9acd6e9~1..HEAD -- backend/build.gradle` is empty → no new declarations; AC "No new Maven dependencies" holds. No follow-up CVE scan triggered.
4. **Frontend XSS** — **PASS.** Zero `v-html` / `innerHTML` / `insertAdjacentHTML` across `components/{subscribers,tags,customFields}` and the three pages; subscriber names / custom-field values / tag labels render via interpolation (auto-escaped). The one download link uses reactive `:href="row.downloadUrl"` (`RecentExportsDialog.vue:172`) — proper attribute binding of a server-minted https URL, not string concatenation; no attribute-context breakout, no `javascript:` scheme (scheme is server-controlled `app.url`).
5. **Error-message information disclosure** — **PASS.** `GlobalErrorHandler` returns `AppException` code+static-message only; the catch-all `Throwable` handler logs server-side and returns generic "Internal server error" with no stack/internal detail. 6. **CORS / CSRF** — **PASS.** No per-endpoint CORS override added; no `SecurityConfig` change in Epic 09 (the `/api/**` authenticated rule already covers the new routes per `patterns.md`); cookie-session CSRF posture unchanged.
7. **Telegram input handling** — **PASS.** Subscriber-supplied `firstName`/`lastName`/`username`/STRING custom fields are never concatenated into a URL (message body is JSON to Telegram, `SubscriberController.java:250`), never reach `Runtime.exec`, never compiled into a regex. CSV export defuses them via formula-neutralization. Custom-field keys are whitelisted against stored slug-validated definition names before any Mongo field-path concat.

## Residual Accepted Risks

- **R8 (Signed-URL HMAC key compromise):** Accepted with caveat. Key rotation = redeploy-invalidates-all (Decision 15); key never logged; downloads audited (Decision 16). **F1** notes the weak default degrades this layer if the prod secret is omitted — but session-guard + `requireOwned` keep data protected regardless. Acceptance stands; F1 fix recommended to restore fail-closed boot.
- **R12 (Rate-limit fail-open during Redis outage):** Accepted. Matches the `AuthService`/`BotService` codebase convention; all three subscriber buckets WARN with greppable constants for log-based alerting; refresh-url is the deliberate fail-closed exception. Acceptance stands.
- **R15 (Rate-limit fail-open monitoring gap):** Accepted-with-action. The greppable WARN constants exist in code, but the env-var registry + R12/R15 monitoring posture are not yet written to `deployment.md` (that file is owned by Task 16 Deploy). Acceptance stands provided Task 16 documents the alert + manual-purge runbook (see Recommendations).
