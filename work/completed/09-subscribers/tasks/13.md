## Description

Full-feature security audit for Epic 09 (Subscribers). Read every source file created or modified by Tasks 1–11 (backend Java + frontend Vue + email templates + i18n + Playwright E2E), then analyze the feature holistically against OWASP Top 10 (2021) with particular focus on the threat surfaces highlighted in `tech-spec.md` Decisions 5, 7, 9, 15, 16 and findings F1–F10.

This is a non-code audit task: no code is written, no tests are added, no production behavior changes. The deliverable is a single, actionable Markdown audit report at `work/09-subscribers/logs/audit/security-audit-report.md` consumed by Task 15 (Pre-deploy QA) and Task 17 (Post-deploy verification). Findings are graded Critical / High / Medium / Low per the security-auditor skill. Each finding cites file:line and concrete fix; no false positives, no recap of unaffected code.

Why now (Audit Wave, before Pre-deploy QA): security regressions caught after deploy require either rollback or out-of-band hotfix; catching them between Wave 4 (last code wave) and Wave 5 deploy is the cheapest moment. Runs in parallel with Task 12 (Code Audit) and Task 14 (Test Audit) — no shared write surface.

## What to do

1. Build the inventory: read `work/09-subscribers/tech-spec.md` "Implementation Tasks" section + `work/09-subscribers/decisions.md` agent reports to enumerate every file touched by Tasks 1–11. Group by component: data layer (T1), services (T3–T7), HTTP layer + export pipeline (T8–T9), frontend (T2, T10–T11), email templates + i18n + E2E (T2, T9, T11). If `decisions.md` is empty or stub, use tech-spec `Decisions` section (lines 67–152) as the canonical source of architectural decisions. The audit must verify code matches these decisions.

2. Re-read tech-spec Decisions 5, 7, 9, 15, 16, 17 and the Risks table (R8, R12, R15, R16) so the audit lands against the documented threat model, not against an imagined one.

3. Audit each component against OWASP Top 10 (2021). For every category, decide: applicable / not applicable / partial. Document reasoning briefly when "not applicable" (so reviewers can challenge it). Categories: A01 Broken Access Control, A02 Cryptographic Failures, A03 Injection (SQL/NoSQL/CSV/CMD/Log), A04 Insecure Design, A05 Security Misconfiguration, A06 Vulnerable Components, A07 Identification & Authentication Failures, A08 Software & Data Integrity Failures, A09 Security Logging & Monitoring Failures, A10 SSRF.

4. Apply the focused checklist from the tech-spec — every item below MUST be verified file:line in the report (PASS / FAIL / N/A with citation):

   - **HMAC token verify** (`common/crypto/SignedDownloadToken.java`): constant-time signature comparison via `MessageDigest.isEqual` (NOT `Arrays.equals`, NOT `String.equals`); `projectId` embedded in payload (cross-project token replay defense); explicit `expiresAt > now` check before returning OK; fail-fast env-var parse (length + hex shape) mirrors `TokenEncryptor`.
   - **`requireOwned` coverage** (every new controller method in `SubscriberController`, `TagController`, `CustomFieldsController`, `SubscriberCustomFieldsController`, `SubscriberExportController`): first executable line of every endpoint MUST be `projectService.requireOwned(currentUserId(), projectId, false)` — anti-IDOR + anti-enumeration per tech-spec AC.
   - **Mass-assignment protection** on PATCH custom-field values (`SubscriberCustomFieldsController` per T5) and on every Request record: `@JsonIgnoreProperties(ignoreUnknown = true)` + silent-drop of unknown keys per AC11; verify `projectId`/`ownerId`/`subscriberId` cannot be smuggled via request body (server-derived from path + session only).
   - **CSV injection** (`subscriber/export/SubscriberCsvWriter.java` per T9, Decision 7): every string cell whose first character is one of `= + - @ \t \r` MUST be prefixed with apostrophe `'` BEFORE RFC 4180 escaping; verify prefix is applied to ALL string-typed cells (firstName, lastName, username, languageCode, status, joined tags, JSON-serialized customFields, AND number-cells stringified per Decision 7 because `Double.isFinite("=1+1")` upstream is irrelevant — stringification happens at the writer).
   - **Webhook 403/400 side-effects** (`bot/TelegramSender.java` per T6, Decision 4): mapping `403 → markBlockedByChatId`, `400 + "chat not found" → markDeletedByChatId` is gated on `TelegramSendException.terminalReason` enum, NOT on substring sniffing inside `SubscriberService`; verify ordering — `eventService.logEvent(EVENT_TELEGRAM_SEND_FAILED)` fires BEFORE the markBlocked/markDeleted call so audit semantics survive a `SubscriberService` exception.
   - **Rate-limit fail-open exposure** (Decision 9 / R12): the three buckets (`bf:rate:start:`, `bf:download:export:`, `bf:rate:personal_message:`) fail-open on Redis exception, and WARN log uses the documented greppable constant (`SUBSCRIBER_START_RATE_REDIS_FAIL_OPEN`, `EXPORT_DOWNLOAD_RATE_REDIS_FAIL_OPEN`, `PERSONAL_MESSAGE_RATE_REDIS_FAIL_OPEN`); confirm the EXCEPTION: `SubscriberExportController` refresh-URL endpoint fails-CLOSED per Decision 15 (`EXPORT_REFRESH_REDIS_FAIL_CLOSED`); verify R12 monitoring-gap is referenced in `deployment.md`.
   - **Cursor decode hardening** (Decision 5 / F6 — `subscriber/SegmentFilterBuilder.java` or cursor codec per T8): all five reject rules enforced before query construction — (1) valid base64url, (2) JSON object with exactly keys `{v, id}`, (3) no `$`-prefixed sub-key at any depth (NoSQL operator injection guard), (4) `v` is a primitive (long/string, never object/array), (5) `id` is 24-char lowercase hex; any failure → HTTP 400 `invalid_cursor`, NEVER a 500 stack-trace leak.
   - **Signed-URL audit events** (Decision 16 / F4 — `SubscriberExportController.download`): every non-200 outcome writes `subscribers_export_download_denied` to platform `events` (NOT `subscriber_events`) with `reason` enum (`invalid_token`, `expired`, `rate_limited`, `project_unavailable`, `purged`, `failed`, `foreign_owner`) BEFORE returning the HTTP response; `tokenSegmentPrefix` is first 8 chars of PAYLOAD segment (not signature); IP + UA threaded through `EventService.logEvent`.
   - **Personal-message rate limit** (F5 — `SubscriberController.sendPersonalMessage` per T8 + `SubscriberServiceImpl` rate-limit per T3): per-project bucket `bf:rate:personal_message:{projectId}` at 60/min (env `SUBSCRIBER_PERSONAL_MESSAGE_RATE_LIMIT_PER_MIN`); every call counts (no bypass); on threshold breach → 429 `telegram_rate_limited`; verify no per-subscriber key-cardinality blow-up.
   - **Custom field `defaultValue` per-type validation** (F9 — `project/CustomFieldsController` + `subscriber/CustomFieldValueValidator` per T5): `defaultValue` on `CreateCustomFieldRequest` is validated by the SAME `CustomFieldValueValidator` that gates subscriber writes (string length, number `Double.isFinite`, boolean shape, date ISO-8601, enum-list membership); reject 422 `custom_field_type_mismatch` on shape violation; verify no untyped `Object` slips through to Mongo unchecked.
   - **GridFS metadata integrity** (F10 — `subscriber/export/ExportSubscribersJob` + `subscriber/jobs/ExportCleanupJob`): every GridFS file write carries `metadata.projectId` AND `metadata.exportId` AND `metadata.ownerId` so cascade-delete (Decision 8) and `ExportCleanupJob` can target by indexed projectId without scanning; verify cleanup query uses `metadata.projectId` filter, not a collection scan; verify `metadata.contentType="text/csv"` and `metadata.filename` is owner-supplied content sanitized (no path traversal: no `/` `\` `..`).

5. Cross-cutting checks (perform once across the whole feature, not per-component):
   - **Secrets / hardcoded keys**: scan all new files for hardcoded API keys, HMAC keys, passwords, connection strings; verify `SUBSCRIBER_EXPORT_TOKEN_KEY` only loaded via `@Value`/`application.properties`, never inlined in tests.
   - **Logging hygiene**: verify HMAC tokens, full signed URLs, raw Telegram bot tokens, and subscriber PII (full names, phone) are NEVER logged at INFO/WARN/ERROR; metadata-only logging (chatId, projectId, subscriberId) is acceptable.
   - **Dependency vulnerabilities**: confirm AC "No new Maven dependencies in `backend/build.gradle`" (tech-spec AC) holds — if violated, scan added deps for CVEs (no `npm audit`/`./gradlew dependencyCheckAnalyze` execution required by this audit, but flag any new declarations for follow-up).
   - **Frontend XSS** (T10–T11 Vue components): verify no `v-html` use on user-controlled content (subscriber names, custom-field values, tag labels); confirm `useApi` / fetch responses are rendered via interpolation/`v-text`, not raw HTML; confirm signed download URLs are NEVER rendered inside `href` attributes built by string concatenation that could break out of attribute context.
   - **Error-message information disclosure**: verify `GlobalErrorHandler` mappings for the 15 new error codes (`tag_name_taken`, `custom_field_*`, `export_*`, `invalid_token`, `telegram_rate_limited`) do NOT echo internal exception messages or stack traces in the response body — code + safe message only.
   - **CORS / CSRF**: confirm no per-endpoint CORS overrides added; CSRF posture (cookie-session vs token) unchanged from project precedent (`patterns.md`).
   - **Telegram input handling**: subscriber-supplied `firstName`, `lastName`, `username`, custom-field STRING values are unbounded by app validation (Telegram-platform-supplied); confirm they are never used in URL construction, never reach `Runtime.exec`, never used in regex compilation without `Pattern.quote`.
   - **GDPR / retention**: verify `subscriber_events` 365d TTL is wired via `@Indexed(expireAfter = "365d")`; verify denied-download audit events route to platform `events` (no TTL) per Decision 16 GDPR rationale (not `subscriber_events`); flag any place where IP/UA is persisted on a subscriber-identity-joined collection (per Decision 16 R2-2 rationale).

6. Write the audit report at `work/09-subscribers/logs/audit/security-audit-report.md`. Create the directory first if missing. Structure (mandatory headings, in this order):

   - `# Security Audit — Epic 09 Subscribers`
   - `## Summary` — 3–5 sentences: scope, total findings by severity, overall posture (ready / needs-fix / blocker), key residual risks.
   - `## Scope` — bullet list of components audited (group by T1 / T3 / T8 / T9 / T10–T11 etc.) and the corresponding file count.
   - `## Findings` — one subsection per finding with format:
     - `### F1: <short title> [Severity: Critical/High/Medium/Low]`
     - `**OWASP:** A0X — <category>`
     - `**Location:** path/to/file.java:LINE` (or range)
     - `**Issue:** <what is wrong, attack vector, realistic exploit scenario>`
     - `**Fix:** <concrete, implementable remediation; reference Decision N if applicable>`
     - `**Status:** Open` (always Open at audit-write time — Task 15+ closes them)
   - `## OWASP Top 10 Coverage Matrix` — 10-row table: category | applicable? | findings (IDs) | notes.
   - `## Focused Checklist Results` — the 11 focused items from step 4 above, each marked PASS / FAIL / PARTIAL with file:line citation and finding-ID if FAIL/PARTIAL.
   - `## Cross-cutting Checks Results` — the 7 cross-cutting items from step 5, same shape.
   - `## Residual Accepted Risks` — list R8, R12, R15 with one-line statement of acceptance status post-audit.
   - `## Recommendations Beyond Findings` — optional bullet list of defense-in-depth suggestions that are NOT blockers (Phase 2 fodder).

7. The report MUST be self-contained — a reader who has not seen the codebase should understand each finding from the issue + fix paragraphs. NO findings whose only evidence is "trust me"; every finding cites file:line.

**Implementation hints:**
- Read order: tech-spec Decisions first → decisions.md (per-task deviations) → source files component-by-component (data → service → controller → frontend). Reading code without the Decision context invites false positives.
- For HMAC and crypto code: read the JDK `MessageDigest.isEqual` Javadoc to confirm it is the constant-time comparator (it is, since Java 6 — but cite it). Confirm `Mac.getInstance("HmacSHA256")` (not weaker), key derivation length matches the env-var format documented in Decision 1's fail-fast template.
- For `requireOwned` coverage: grep for `@GetMapping`/`@PostMapping`/`@PatchMapping`/`@DeleteMapping` in each new controller; assert the FIRST executable line inside each handler is `projectService.requireOwned(...)`. If a handler delegates to a private method that calls requireOwned, document that pattern as PASS but flag the indirection as a minor maintainability concern (NOT a security finding).
- For cursor decode: trace the path from `@RequestParam String cursor` into the codec; assert all five reject rules are enforced BEFORE the cursor's `v` or `id` reach `Criteria.where(...)`.
- For CSV injection: open `SubscriberCsvWriter.java`, find the cell-write code path, confirm the apostrophe prefix is applied to EVERY string cell (not just user-controlled ones — Decision 7 mandates universal application). The number-to-string-then-prefix rule is the easy miss.
- For frontend XSS: ripgrep `v-html` across `frontend/components/subscribers/`, `frontend/components/tags/`, `frontend/components/customFields/`, `frontend/pages/projects/[projectId]/(subscribers|tags|custom-fields)`. Any hit is presumptive HIGH until proven otherwise (content origin confirmed sanitized).
- Severity calibration: CRITICAL only for active-exploit data-breach / RCE / auth bypass paths; HIGH for IDOR / mass-assignment / injection requiring an authenticated session; MEDIUM for missing defense-in-depth on existing controls; LOW for best-practice gaps. When in doubt, downgrade by one level — security-auditor skill explicitly penalizes false positives.
