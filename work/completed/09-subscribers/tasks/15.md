# Task 15: Pre-deploy QA

## Required Skills

Перед выполнением задачи загрузи:
- `/skill:pre-deploy-qa` — [skills/pre-deploy-qa/SKILL.md](../../../.claude/skills/pre-deploy-qa/SKILL.md)

## Description

Финальный приёмочный прогон фичи 09-subscribers перед деплоем — без живого окружения. Цель: убедиться, что весь код, написанный в Wave 1–4 (Tasks 1–11) и просмотренный в Audit Wave (Tasks 12–14), действительно реализует все 24 пользовательских критерия из `user-spec.md` (AC1–AC24) и все 16 технических AC из `tech-spec.md` "Acceptance Criteria" section, что вся тестовая пирамида (backend unit + IT, frontend Vitest, Playwright E2E, slow-tag latency/heap probes) зелёная, и что parity-gate локалей не сломан.

QA-агент:
1. Прогоняет ровно 5 тест-команд (см. What to do).
2. Маппит каждый AC1–AC24 на конкретный автотест из tech-spec "Testing Strategy".
3. Маппит каждый из 16 технических AC на конкретный автотест.
4. Помечает критерии как `passed`, `failed` или `not_verifiable` (последнее — для тех, что требуют живой среды, MCP-тулов или ручного UI-смока — они уйдут в `deferredToPostDeploy` для Task 17).
5. Пишет полный отчёт в `work/09-subscribers/logs/qa/pre-deploy-qa-report.md` (см. формат в What to do).

Результат — gate-решение: pass → Task 16 (Deploy) запускается; fail (≥1 critical) → блокер, фикс через создание ad-hoc задачи и повторный прогон.

## What to do

1. Прочитать `user-spec.md` (AC1–AC24 в секции "Критерии приёмки"), `tech-spec.md` (секции "Acceptance Criteria" — 16 технических пунктов — и "Testing Strategy"), `decisions.md` (фактические отклонения от спека по ходу Wave 1–4, если таковые есть).
2. Прогнать backend default-tag тесты: `cd backend && ./gradlew test`. Gradle wrapper лежит в `backend/`, на корне репозитория его НЕТ — всегда `cd backend` перед `./gradlew`. Записать total/passed/failed/skipped.
3. Прогнать backend slow-tag latency/heap probes: `cd backend && ./gradlew test -PrunSlow=true`. Этот прогон обязателен для AC13 (P95 <300ms на 1000 subscribers), AC18 (count-estimation <200ms на 100k) и Decision 7 heap probe (<64 MB на 50k). Записать тот же набор счётчиков.
4. Прогнать frontend Vitest: `cd frontend && pnpm install && pnpm test`. Покрывает компонент-спеки (AddTagDialog, AddCustomFieldDialog, SendPersonalMessageDialog, SubscribersFilterBar).
5. Прогнать Playwright E2E: `cd frontend && pnpm test:e2e` (или `pnpm playwright test subscribers.spec.ts --reporter=line`). Покрывает золотой путь UI (AC1, AC8, AC9, AC10–AC12, AC14, AC16, AC19, AC4 manual unsubscribe).
6. Прогнать locale parity gate: `cd frontend && pnpm prebuild`. Покрывает технический AC #10 (`subscribers.* / tags.* / customFields.* / exports.*` parity между `uk.json` и `en.json`).
7. Составить покрытие-матрицу AC1–AC24 → testName → status (passed | failed | not_verifiable). Маппинг тестов берётся из `tech-spec.md` "Testing Strategy" (см. подсказку ниже в Details).
8. Составить покрытие-матрицу 16 технических AC → evidence (testName или grep-команда или файловая проверка) → status.
9. Записать отчёт в `work/09-subscribers/logs/qa/pre-deploy-qa-report.md` по структуре ниже:
   - **Summary:** счётчики по 4 тест-сьютам + locale gate; общий статус (passed/failed).
   - **Test Suite Results:** для каждой из 5 команд — команда, total/passed/failed/skipped, длительность.
   - **AC1–AC24 Coverage Matrix:** таблица AC ID | формулировка (короткая) | тест(ы) | status | evidence.
   - **Technical AC Coverage Matrix:** таблица # | формулировка | тест/команда | status | evidence (для каждого из 16 пунктов tech-spec "Acceptance Criteria").
   - **Blockers (если есть):** для каждого finding — severity (critical/major/minor), AC ID, expected, actual, reproduction.
   - **Deferred to Post-deploy:** список критериев, которые помечены `not_verifiable` (например AC1 sub-bullet "UI observability <2s", AC8 sync cascade на dataset >10k subscribers если нет heap-теста, ручные UI-смоки из runbook `docs/staging-smoke/09-subscribers.md`). Для каждого — criterion text, reason, verificationCondition, verificationSteps (контракт-handoff для Task 17).
10. Записать краткую запись в `decisions.md` со ссылкой на полный отчёт.

**Implementation hints:**
- Рабочие директории строго: Gradle — из `backend/` (`cd backend && ./gradlew ...`), pnpm — из `frontend/` (`cd frontend && pnpm ...`). На корне репозитория `gradlew` НЕТ — попытка `./gradlew test` из корня вернёт `command not found` и завалит весь прогон. Grep-команды по `backend/src/...` запускать из корня репо.
- `cd backend && ./gradlew test -PrunSlow=true` может занять >5 минут — heap-test нагружает JVM. Если CI flaky на heap-delta — это документировано в tech-spec Testing Strategy как "MVP accepted trade-off"; пометить как `minor` finding, не блокер.
- При `failed > 0` в любой команде — это `critical`. Не маскировать.
- Если тест-команда падает с инфраструктурной ошибкой (Mongo/Redis Testcontainers не стартует) — это блокер до запуска QA, не результат QA. Эскалировать.
- Для маппинга AC → test — НЕ полагаться на маппинг-подсказку выше слепо. Открыть фактический тест-файл и убедиться, что тест действительно покрывает поведение из AC (per skill SKILL.md "Coverage Verification": тест должен exercise relevant code path, не import-check / mock-only).
- Технический AC #5 (no new Maven deps) — проверить `git diff main -- backend/build.gradle` в dependencies block; разрешены только новые `testImplementation` (если такие добавлены Task 1 / Task 9), но `implementation` block должен быть нетронут.
- Финальный verdict в отчёте: `passed` если zero criticals; `failed` если ≥1 critical. `major`/`minor` не блокируют деплой, но фиксируются для бэклога.
