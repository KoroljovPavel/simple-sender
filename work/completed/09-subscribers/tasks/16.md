## Description

Ship feature `09-subscribers` to production via the project's GitHub Actions deploy pipeline. This is the deploy gate after Task 15 (Pre-deploy QA) returns a GO verdict.

The feature introduces six new env vars (one secret + five tunables) and four new MongoDB collections (`subscribers`, `tags`, `subscriber_events`, `subscriber_exports`) plus a GridFS file collection for export blobs. Deploy responsibilities:

1. Register all six new env vars in the GitHub Actions repository secrets/variables (the secret `SUBSCRIBER_EXPORT_TOKEN_KEY` is generated fresh via `openssl rand -hex 32` and must never be pasted into chat or committed).
2. Cross-check that `.env.example` and `application.properties` already carry the six vars (Tasks 3 and 9 own those edits) — this task only verifies presence, it does NOT re-add them.
3. Author the project's first GitHub Actions deploy workflow (or update an existing one if Task 15 / a prior feature already added it) so the new secret is wired into the runtime env.
4. Author/refresh `deployment.md` (canonical file at `.claude/skills/project-knowledge/references/deployment.md`) so the new env-var table is documented for ops.
5. Push the branch, open a PR to `main`, wait for CI green, ASK THE USER before squash-merge (CLAUDE.md rule: ALWAYS ask before deploy/push to main/production).
6. Watch the deploy workflow logs after merge and verify the new collections + GridFS file collection auto-create their indexes on first boot, and the `SUBSCRIBER_EXPORT_TOKEN_KEY` fail-fast guard does NOT trip.

Per CLAUDE.md "ALL deployments via GitHub CI/CD only. Direct server access (SSH, container restarts) only for emergency debugging of broken production" — this task does NOT SSH into any server, does NOT restart any container by hand, and does NOT bypass the CI pipeline. Per `deployment.md` (project-knowledge) the deploy platform is currently TBD; if the workflow does not yet exist, this task is responsible for authoring it (consult `deploy-pipeline` SKILL.md "CI/CD Convention" section) and MUST surface the platform-choice decision to the user before pushing.

## Verification Steps

### Automated

CI on the PR is the automated gate. Required checks:
- `cd backend && ./gradlew test` → green
- `cd frontend && pnpm test` → green
- `cd frontend && pnpm prebuild` → exit 0 (locale parity)
- lint job → green
- gitleaks job → green (no secrets in diff — the empty `SUBSCRIBER_EXPORT_TOKEN_KEY=` line in `.env.example` is fine; a populated one is a FAIL and must be reverted before re-running CI)

Watched via `gh pr checks --watch <pr-number>`.

### Smoke

These are post-merge / post-deploy log inspection checks the agent runs from the GitHub Actions UI (no SSH, no direct server access — per CLAUDE.md):

- `gh run watch <deploy-run-id>` → final status `success`.
- `gh run view <deploy-run-id> --log | grep -E "(subscribers|tags|subscriber_events|subscriber_exports).*[Cc]reated index"` (or the platform's equivalent log retrieval command per `deployment.md` step 6) → at least one "Created index" line per collection. Mongo auto-index-creation logs the index name on first encounter.
- `gh run view <deploy-run-id> --log | grep -iE "SUBSCRIBER_EXPORT_TOKEN_KEY|SignedDownloadToken.*Illegal|key.*too short|key.*not hex"` → MUST return NO matches. Any match = fail-fast tripped → STOP and re-run secret-registration step.
- `gh run view <deploy-run-id> --log | grep -iE "NoSuchBeanDefinitionException.*GridFsOperations"` → MUST return no exception lines (positive bean-wiring lines are fine).
- `curl -i https://<deployed-app-url>/health` (URL from `deployment.md` once step 6 fills it) → `HTTP/1.1 200` body `{"status":"ok"}`.

If the platform stores deploy logs outside GitHub Actions (e.g. Fly.io, Railway), use the platform's CLI per `deployment.md` — same greps, same expected outcomes. Do NOT SSH to the server to tail logs; emergency-debug-only per CLAUDE.md.
