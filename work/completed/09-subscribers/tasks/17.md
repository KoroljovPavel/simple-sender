## Description

Final gate for Epic 09 (subscribers). After Task 16 deploys the feature to staging, execute the manual `docs/staging-smoke/09-subscribers.md` runbook (authored by Task 11) end-to-end on the live staging environment and confirm that every behaviour that could not be covered by pre-deploy automated tests works in production.

The runbook exists precisely because three pieces of this epic cannot be exercised in CI:

- **Real Telegram → ngrok → backend.** Telegram's `setWebhook` rejects HTTP and demands a publicly-reachable HTTPS URL; CI tests stub the inbound webhook via fake payloads. AC1 (auto-registration <2s observed in UI) and AC6 (rate-limit) only become observable here.
- **Signed-URL CSV download via email.** Pre-deploy QA verifies `SubscriberCsvWriter` output, `SignedDownloadToken` mint/verify, and the controller endpoint, but nobody clicks a real link from a real mailbox to confirm the GridFS-streamed file opens in a spreadsheet with the UTF-8 BOM intact and Cyrillic city values rendered. AC16 / AC19 are closed here.
- **One-in-flight export per project.** AC17's partial-unique index is asserted by `SubscriberExportConcurrencyIT`, but the operator-facing UX (banner / 409) is only verifiable against the deployed frontend.

In addition to the runbook, this task picks up any acceptance criteria that the pre-deploy QA report (`work/09-subscribers/logs/qa/pre-deploy-qa-report.md`) flagged as `deferredToPostDeploy` and writes a single verification report at `work/09-subscribers/logs/qa/post-deploy-verification-report.md`. The report is the artefact that the user uses to sign off the epic for production.

The task is verification-only — no code changes, no deploy actions, no schema mutations. If a failure is found on staging, file a bug pointing at the failing AC + runbook step + observed vs expected; do NOT attempt to hotfix from inside this task.

## Verification Steps

### Smoke

Verification-only task — "smoke" here means actually executing the runbook on staging (this IS the smoke). All commands below run against the live staging environment, not localhost.

- `curl -fsS ${STAGING_URL}/health` → `{"status":"ok"}` before starting (precondition check).
- Telegram MCP: send `/start` to the throwaway bot → record HTTP status + observe `/subscribers` UI within 2s. If Telegram MCP unavailable, fall back to a real Telegram client per the runbook.
- Telegram MCP: send `/stop` → observe status badge flip to Unsubscribed in `/subscribers` within 2s.
- `curl -fsSi -b cookies "${STAGING_URL}/api/v1/projects/{projectId}/subscribers/{subscriberId}/messages" -H 'Content-Type: application/json' -d '{"text":"hello"}'` → 200, then verify message arrives in Telegram (AC15). Cookies file = staging session jar created by logging in via UI first.
- During an in-flight export: `curl -fsSi -b cookies -X POST "${STAGING_URL}/api/v1/projects/{projectId}/subscribers/export" -H 'Content-Type: application/json' -d '{"filter":{}}'` → 409 `export_in_flight` (AC17).
- Click the signed URL from the export-ready email → 200, `Content-Type: text/csv`, `Content-Disposition: attachment` (AC19).
- (Optional) `mongosh "$STAGING_MONGODB_URI" --eval 'db.subscribers.getIndexes()'` (+ tags / subscriber_events / subscriber_exports analogues) — confirms indexes per Decision 2. Skip if Task 16 deploy logs already showed successful index creation.

**Edge cases:**
- **Telegram MCP unavailable.** Fall back to a real Telegram client per the runbook. Record the fallback in the report under the affected step. Do NOT mark as `passed` based on stubbed behaviour.
- **Staging email provider misconfigured.** If the export-ready email never arrives, do NOT mark AC19 as passed by trusting the controller's 200 response — file as a `failed` finding (critical: AC19 demands the operator received the link).
- **Concurrent runbook execution by two operators on the same project.** First operator wins the bot-connect race; second operator's connect fails with 409 (bot platform-wide unique). Coordinate via team chat OR use separate test projects + separate throwaway bots.
- **ngrok URL is session-scoped.** If ngrok reconnects mid-runbook, the webhook URL stored on staging now points at a dead tunnel. Re-run the connect step to refresh `setWebhook`.
- **Rate-limit fail-open (AC6) is not observably verifiable on staging** without a controlled Redis outage. AC6 is closed by `SubscriberRateLimitIT`; the report should note "covered by pre-deploy IT, not observable on staging without Redis-down injection".
- **Cyrillic spreadsheet rendering depends on the user's spreadsheet tool.** Excel without explicit UTF-8 import has historically mangled BOM-less CSVs; this is exactly what AC16 / Decision 7 BOM emission guards against. Report MUST name the spreadsheet tool used.
- **Pre-deploy QA report missing or empty `deferredToPostDeploy`.** If absent, note "no deferred items" in the report — do NOT silently skip.
- **CustomFieldDefinition delete cascade (AC12) on live data.** Optional but recommended: after AC10 + AC11 are verified, delete the `city` definition through `/custom-fields`; confirm the value disappears from your subscriber profile (AC12). Skip if it would interfere with another concurrent test.

**Implementation hints:**
- Drive the runbook in the order it documents. Do not reorder steps — earlier steps populate state used by later ones (e.g. tag must be added before `/stop` so reactivation can verify tag preservation).
- Capture evidence as you go, not retroactively. For each `passed` step keep at minimum: HTTP status, mongosh excerpt (scrubbed of connection string), or UI screenshot filename.
- **Never paste into the report or chat:** the bot token (~45-char `digits:base64`), the staging Mongo URI, the signed-URL token query parameter (HMAC), real numeric chat ids of operators, JSESSIONID cookies. Scrub mongosh output with `mongosh ... --eval '... {projection: 1}'` and copy only the projected fields.
- **Obtaining `STAGING_MONGODB_URI` (used in step 6 mongosh probes).** The connection string lives in GitHub Actions secrets as `STAGING_MONGODB_URI`. Use `gh secret list` (read-only — shows names, never values) to confirm presence; ask the deployer / human operator for the value out-of-band (1Password, Vault, encrypted message). Export it in your shell once (`export STAGING_MONGODB_URI=…`) and reference `$STAGING_MONGODB_URI` everywhere. Do NOT write the URI value to chat, into the report, into commits, or into screenshots. If you cannot obtain the URI, mark the optional index spot-check `blocked` and rely on the Task 16 deploy logs that already evidence index creation.
- The `post-deploy-qa` skill's output is JSON; this task's report is markdown for human review. Structure the markdown to mirror the JSON fields (status, summary, agentVerification, acceptanceCriteria, findings) so a follow-up tool can later convert if needed.
- If you find a regression in a previously-passing AC (e.g. AC22 soft-delete cascade), file it as `critical` even if it is outside the runbook's explicit scope — the report covers the whole feature on staging, not just the runbook surface.
- Sign-off requires zero `failed`-critical items. A `blocked` item with a credible manual verification plan does not block sign-off, but the user must decide whether to wait for the manual check before promoting.
