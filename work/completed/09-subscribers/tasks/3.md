## Description

Replace the placeholder `NoOpSubscriberService` with the real `SubscriberServiceImpl @Service` that owns the Subscriber CRM lifecycle. This is the central Wave 2 service that downstream Wave 2/3 work depends on: TelegramSender hook (Task 6) calls `markBlockedByChatId` / `markDeletedByChatId`; HTTP controllers (Task 8) call `unsubscribeManual` + tag assign/unassign (`addTag` / `removeTag`); CustomFields PATCH (Task 5) calls `recordCustomFieldsSet`. Per Decision 10, `SubscriberServiceImpl` is the SOLE writer for all CRM lifecycle events including `subscriber_custom_field_set`, `subscriber_tag_added`, `subscriber_tag_removed` — controllers MUST route audit events through these interface methods, not write to `subscriber_events` directly.

Scope of this task:
1. Extend the existing `SubscriberService` interface with **six** new methods (`markBlockedByChatId`, `markDeletedByChatId`, `unsubscribeManual`, `recordCustomFieldsSet`, `addTag`, `removeTag`). The two existing methods (`upsertFromTelegramUpdate`, `markUnsubscribed`) keep their byte-identical signatures so `ProcessTelegramUpdateJob` and its tests keep compiling unchanged. The three writer methods (`recordCustomFieldsSet`, `addTag`, `removeTag`) are required by Decision 10 — `SubscriberServiceImpl` is the SOLE writer for `subscriber_custom_field_set`, `subscriber_tag_added`, `subscriber_tag_removed` events. Task 5 (CustomFields PATCH) and Task 8 (Subscriber tag assign/unassign endpoints) call these landed-here methods.
2. Implement `SubscriberServiceImpl @Service` covering: idempotent upsert from Telegram update (lookup-then-rate-limit-then-insert pattern from tech-spec Architecture §Auto-registration data flow), full status state machine (`active ↔ unsubscribed`, `* → blocked`, `* → deleted`, reactivation `(unsubscribed|blocked|deleted) → active on /start` preserving `subscribedAt` + `tags` + `customFields`), DuplicateKeyException race recovery (re-read existing subscriber, apply update), Redis start-rate-limit fail-open shape mirroring `BotService.incrementBruteForceCounter` (uses `StringRedisTemplate`), SubscriberEvent writes for every lifecycle transition, and dedicated event-writing methods for custom-fields / tag changes per Decision 10.
3. Delete `NoOpSubscriberService` and its test atomically with the new `@Service` registration — Spring DI fails with two `@Service` beans implementing the same interface (R7, Decision 1). Slice tests that previously relied on the no-op now use `@MockitoBean SubscriberService` (touch only what's needed; do not refactor unrelated tests).
4. Add new env var + property: `SUBSCRIBER_RATE_LIMIT_START_PER_MIN=100` in `.env.example` and `app.subscriber.rate-limit.start-per-min=${SUBSCRIBER_RATE_LIMIT_START_PER_MIN:100}` in `application.properties`.
5. Register a `Clock` bean (if not already present) at `backend/src/main/java/com/botfunnel/common/ClockConfig.java` — no `@Bean Clock` exists in the codebase today; this is a new bean added in Task 3 (single-file addition, no broader refactor).

Detail sources — DO NOT duplicate here, READ from the spec:

- Rate-limit shape (key format, TTL, threshold, INCR+EXPIRE order, fail-open with greppable WARN constant, existing-subscriber bypass) — Decision 9.

- Single `@Service` bean invariant — Decision 1.

## What to do

1. **Extend the `SubscriberService` interface** with six new methods. Signatures must let the caller pass the lookup tuple it already has — Telegram 403/400 callers (`TelegramSender`, Task 6) have `(projectId, telegramBotId, chatId)`; manual unsubscribe (`SubscriberController`, Task 8) operates by `subscriberId`; CustomFields PATCH (Task 5) and tag assign/unassign endpoints (Task 8) operate by `(projectId, subscriberId)`:
   - `void markBlockedByChatId(String projectId, Long telegramBotId, Long chatId)` — flips ACTIVE → BLOCKED, sets `blockedAt=now`, writes `subscriber_blocked` event. Idempotent: BLOCKED row → no-op (no event, no field updates).
   - `void markDeletedByChatId(String projectId, Long telegramBotId, Long chatId)` — flips → DELETED, sets `deletedAt=now`, writes `subscriber_deleted` event. Idempotent: DELETED row → no-op.
   - `void unsubscribeManual(String subscriberId)` — flips → UNSUBSCRIBED, sets `unsubscribedAt=now`, writes `subscriber_unsubscribed{reason:"manual"}`. Throws `AppException.conflict("already_unsubscribed", "Already unsubscribed")` (two-arg form — one-arg form sets `code=null` and the 409 mapping in `GlobalErrorHandler` keys off the code) if status is already UNSUBSCRIBED. For BLOCKED/DELETED → also `already_unsubscribed` 409 (CRM cannot manually unsubscribe a terminal state).
   - `void recordCustomFieldsSet(String projectId, String subscriberId, Map<String, Object> oldValues, Map<String, Object> newValues)` — Decision 10 SOLE-writer entry point for `subscriber_custom_field_set`. Writes ONE event row to `subscriber_events` with metadata `{oldValues, newValues, changedKeys}` (where `changedKeys` is the symmetric-diff of the two maps' keysets — keys whose values differ or whose presence differs). Does NOT mutate the subscriber document — Task 5's `PATCH .../custom-fields` performs the document update; this method records the audit event. Idempotent: if `changedKeys.isEmpty()` → no event written, return silently.
   - `void addTag(String projectId, String subscriberId, String slug)` — Decision 10 SOLE writer for `subscriber_tag_added`. Atomic: (1) `mongoTemplate.update(Subscriber, $addToSet tags=slug)` — if `modifiedCount == 0` (tag already present), no event, return. (2) `mongoTemplate.update(Tag, $inc subscriberCount=+1)` — atomic counter bump. (3) Write `subscriber_tag_added{slug}` event to `subscriber_events`. Idempotent on already-present tag.
   - `void removeTag(String projectId, String subscriberId, String slug)` — Decision 10 SOLE writer for `subscriber_tag_removed`. Atomic mirror of `addTag`: (1) `$pull tags=slug` — if `modifiedCount == 0` (not present), no event, return. (2) `$inc subscriberCount=-1`. (3) Write `subscriber_tag_removed{slug}` event. Idempotent on already-absent tag.

   Keep existing methods unchanged: `upsertFromTelegramUpdate(...)` (9 params) and `markUnsubscribed(projectId, botId, chatId)` (used by `/stop` worker — set reason `"command_stop"`).

2. **Implement `SubscriberServiceImpl @Service`** in `backend/src/main/java/com/botfunnel/subscriber/SubscriberServiceImpl.java`. Constructor-inject: `SubscriberRepository`, `SubscriberEventRepository`, `TagRepository`, `MongoTemplate`, `StringRedisTemplate` (NOT `RedisTemplate<String, String>` — `BotService.incrementBruteForceCounter` uses `StringRedisTemplate` and this task must mirror that precedent verbatim), `EventService` (for the no-subscriber-yet `rate_limit_exceeded` platform event), `Clock` (chosen here for testability of state-machine timestamp assertions). No `@Bean Clock` exists in the codebase today — register a new `Clock` bean in a NEW config class at `backend/src/main/java/com/botfunnel/common/ClockConfig.java`: `@Configuration class ClockConfig { @Bean Clock systemClock() { return Clock.systemUTC(); } }`. Single-file addition, no broader refactor. Methods:

   - `upsertFromTelegramUpdate(...)`:
     - Lookup `subscriberRepository.findByProjectIdAndTelegramUserId(projectId, telegramUserId)`.
     - If found AND status == ACTIVE → refresh `lastSeenAt`, refresh identity fields (firstName/lastName/username/languageCode/telegramChatId/telegramBotId) via atomic `findAndModify` Update, return — NO rate-limit check, NO event.
     - If found AND status != ACTIVE → reactivate (flip to ACTIVE, preserve `subscribedAt`, clear `unsubscribedAt`/`blockedAt`/`deletedAt`, refresh `lastSeenAt` + identity, write `subscriber_reactivated{previousStatus: <enum.name()>}` event).
     - If NOT found → run Redis rate-limit (key `"bf:rate:start:" + projectId`, threshold from config, TTL 60s, INCR + EXPIRE-on-first per Decision 9). On threshold-exceeded: write platform-level event `rate_limit_exceeded` via `EventService` (NOT subscriber_events — no subscriber exists yet) and `return` silently (no exception — Telegram update is a one-shot, dropping is the user-spec choice). On Redis transport exception: WARN log with greppable constant `SUBSCRIBER_START_RATE_REDIS_FAIL_OPEN` and proceed (fail-open per Decision 9). Then `INSERT` new `Subscriber{status=ACTIVE, subscribedAt=now, lastSeenAt=now, tags=[], customFields={}}` and write `subscriber_registered` event.
     - Race against unique `(projectId, telegramUserId)` index: catch `DuplicateKeyException` on insert → re-read existing subscriber → fall through to the "found" branch (refresh-or-reactivate). This is the idempotent upsert pattern called out in tech-spec Architecture §Auto-registration; distinct from `BotService.connect` which maps DuplicateKey to a hard 409.

   - `markUnsubscribed(projectId, telegramBotId, chatId)`:
     - Lookup `findByProjectIdAndTelegramBotIdAndTelegramChatId(...)` — if missing → silent return (worker invoked from `/stop` on never-registered chat is benign).
     - If status == UNSUBSCRIBED → no-op (idempotent — covered by `SubscriberStatusMachineTest`).
     - Else flip to UNSUBSCRIBED + `unsubscribedAt=now` (atomic `findAndModify`) + write `subscriber_unsubscribed{reason:"command_stop"}`.

   - `markBlockedByChatId(projectId, telegramBotId, chatId)` / `markDeletedByChatId(...)`:
     - Same lookup-and-flip-or-noop shape. Both write their dedicated event (`subscriber_blocked` / `subscriber_deleted`). Both are idempotent on already-in-target-state.

   - `unsubscribeManual(subscriberId)`:
     - Lookup by id; not-found → `AppException.notFound(...)` matching the existing `GlobalErrorHandler` 404 convention (check `BotService` for the precedent factory name).
     - Status != ACTIVE → `AppException.conflict("already_unsubscribed", "Already unsubscribed")` (TWO-arg form — one-arg form sets `code=null`).
     - Else flip + write `subscriber_unsubscribed{reason:"manual"}`.

   - `recordCustomFieldsSet(projectId, subscriberId, oldValues, newValues)`:
     - Compute `changedKeys = symmetricDiff(oldValues, newValues)` — union of keys whose values differ between maps + keys present in one but absent in the other (use `Objects.equals` per-key for value comparison so `null` is handled).
     - If `changedKeys.isEmpty()` → return silently (no event).
     - Else write a single `subscriber_custom_field_set` event row with metadata `{oldValues, newValues, changedKeys}` via the `writeSubscriberEvent` helper.

   - `addTag(projectId, subscriberId, slug)` / `removeTag(projectId, subscriberId, slug)`:
     - Atomic `mongoTemplate.update(Query.query(Criteria.where("_id").is(subscriberId).and("projectId").is(projectId)), new Update().addToSet("tags", slug), Subscriber.class)` (or `.pull("tags", slug)` for remove).
     - If `updateResult.getModifiedCount() == 0` → idempotent no-op (tag already present / already absent): return without counter `$inc` and without event.
     - Else **delegate to `tagService.incrementCounter(projectId, slug, +1 or -1)`** (Task 4 owns the atomic `$inc` API per cross-task review iteration 2 — keeps `Tag` entity mutations encapsulated in `TagService`; do NOT inject `MongoTemplate` here for direct `$inc` on `Tag`).
     - Then write the corresponding `subscriber_tag_added` / `subscriber_tag_removed` event with metadata `{slug}`.
