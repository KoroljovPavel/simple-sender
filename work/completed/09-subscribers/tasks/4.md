# Task 4: TagService + TagController + denormalized counter

## Required Skills

Перед выполнением задачи загрузи:
- `/skill:code-writing` — [skills/code-writing/SKILL.md](../../../.claude/skills/code-writing/SKILL.md)

## Description

Доставить серверный модуль `com.botfunnel.tag` для управления тегами подписчиков в рамках Epic 05 (subscribers CRM). Сущность `Tag` и репозиторий уже созданы в Task 1 — здесь добавляем сервисный слой и HTTP-контроллер для standalone-CRUD тегов на уровне проекта.

`TagService` инкапсулирует find-or-create логику (используется Task 8 при назначении тега подписчику) и атомарный `$inc` денормализованного счётчика `subscriberCount` через `MongoTemplate.findAndModify`. `TagController` выставляет четыре эндпоинта под `/api/v1/projects/{projectId}/tags`: create, list, label-only PATCH, sync delete с cascade на коллекцию `subscribers`.

Эндпоинты ассоциации подписчик↔тег (POST/DELETE `/subscribers/{id}/tags/...`) разворачиваются в Task 8 в `SubscriberController` — здесь они НЕ реализуются. Эта задача поставляет только сервис + standalone tag CRUD.

Ключевые решения, фиксированные в tech-spec:
- **Decision 11** — `Tag.slug` immutable, валидируется через `@Pattern(regexp = "^[a-z0-9_-]{1,32}$")` на DTO. Попытка изменить slug через PATCH → 422 `tag_slug_immutable`.
- **Decision 17** — DELETE cascade выполняется синхронно в рамках запроса: один `mongoTemplate.update(..., new Update().pull("tags", slug), Subscriber.class)` (bulk modify) → `tagRepository.delete(tag)` → событие `tag_deleted` в платформенной коллекции `events` (НЕ в `subscriber_events` — это project-scoped административное событие без `subscriberId`, по таксономии Decision 10). Никаких JobRunr async-задач.
- **Mass-assignment guard** — все request-DTO несут `@JsonIgnoreProperties(ignoreUnknown = true)`; проверяется тестом `TagControllerIT.create_hostileBodyWithOwnerId_ignoresMassAssignment` (см. tech-spec Acceptance Criteria).
- **DuplicateKeyException → 409** маппится через идиому `BotService.mapPersistError` (lines 189-208): ловим `DuplicateKeyException`, выбрасываем `AppException.conflict("tag_name_taken", ...)`.
- **requireOwned first** — каждый endpoint начинается с `Project project = projectService.requireOwned(currentUserId(), projectId, false);` для anti-IDOR/anti-enumeration (uniform 404 при foreign owner / soft-deleted / malformed projectId).

## What to do

1. Создать `TagService` (`@Service`) с публичным API:
   - `Tag findOrCreate(String projectId, String slug)` — атомарный upsert: попытка `tagRepository.findByProjectIdAndSlug`; при отсутствии — insert; на гонке (`DuplicateKeyException`) — re-read и вернуть существующий. Используется Task 8 при `POST /subscribers/{id}/tags`.
   - `void incrementCounter(String projectId, String slug, long delta)` — атомарный `$inc` через `mongoTemplate.findAndModify(Query.query(Criteria.where("projectId").is(projectId).and("slug").is(slug)), new Update().inc("subscriberCount", delta), Tag.class)`. **Sole atomic Tag.subscriberCount mutation API** — `SubscriberServiceImpl.addTag/removeTag` (Task 3) MUST delegate to this method (`+1`/`-1`); НЕ инжектить `MongoTemplate` в `SubscriberServiceImpl` для прямого $inc по Tag. Это держит мутации `Tag` сущности инкапсулированными в `TagService` (cross-task review iteration 2). Decision 10 сохраняется: `SubscriberServiceImpl` остаётся sole writer событий `subscriber_tag_added`/`subscriber_tag_removed`; здесь делегируется только counter-mutation.
   - `Tag create(String projectId, String slug, String label)` — insert с `subscriberCount=0`, `createdAt=Instant.now()`. На `DuplicateKeyException` → `AppException.conflict("tag_name_taken", ...)`. Никаких событий `tag_created` / `tag_updated` Task 4 НЕ пишет (tech-spec Decision 10 их не требует; единственное административное событие из этой задачи — `tag_deleted`).
   - `List<Tag> list(String projectId)` — отдать все теги проекта, сорт по `createdAt desc` или `slug asc` (зафиксировать; tech-spec не диктует — выбрать `slug asc` как стабильный для UI).
   - `Tag updateLabel(String projectId, String slug, String label)` — `mongoTemplate.update` с `Update().set("label", label)` только. На `Tag` нет поля `updatedAt` (data model: `id, projectId, slug, label, subscriberCount, createdAt` — см. tech-spec §Data Models). Slug в body запрещён DTO-схемой (`UpdateTagRequest` его не содержит).
   - `void deleteWithCascade(String projectId, String slug)` — последовательность Decision 17:
     1. `mongoTemplate.update(Query.query(Criteria.where("projectId").is(projectId).and("tags").is(slug)), new Update().pull("tags", slug), Subscriber.class)` — bulk pull.
     2. `tagRepository.deleteByProjectIdAndSlug(projectId, slug)` (или load + delete).
     3. Записать событие `tag_deleted` в платформенную коллекцию `events` через `EventService.logEvent(currentUserId, "tag_deleted", null, null, Map.of("tagSlug", slug, "projectId", projectId, "subscriberCountAtDelete", count))`. Это project-scoped административное событие без `subscriberId` — по таксономии Decision 10 оно НЕ относится к `subscriber_events` (там только CRM-события привязанные к конкретному subscriberId: `subscriber_registered`, `subscriber_unsubscribed` и т.д.). Subscriber↔tag association events (`subscriber_tag_added`, `subscriber_tag_removed`) — это уже Task 3 / Task 8 (пишутся `SubscriberServiceImpl.addTag/removeTag`), в Task 4 их НЕ трогаем. Соответственно `TagService` инжектирует `EventService`, а НЕ `SubscriberEventRepository`. `currentUserId` пробрасывается из контроллера в сервис (новый параметр в сигнатуру `deleteWithCascade` — добавить `String currentUserId`).

2. Создать DTO под `backend/src/main/java/com/botfunnel/tag/dto/`:
   - `CreateTagRequest` (record) — `@Pattern(regexp = "^[a-z0-9_-]{1,32}$") String slug`, `@Size(max=64) String label`. `@JsonIgnoreProperties(ignoreUnknown = true)`.
   - `UpdateTagRequest` (record) — `@Size(max=64) String label`. `@JsonIgnoreProperties(ignoreUnknown = true)`. Никакого поля `slug` (иммутабельность через схему).
   - `TagResponse` (record) — `String slug, String label, long subscriberCount, Instant createdAt`. Никакого `id` / `projectId` в ответе (внутренние детали).

3. Создать `TagController` (`@RestController @RequestMapping("/api/v1/projects/{projectId}/tags")`):
   - `POST /` — `@Valid @RequestBody CreateTagRequest req` → `requireOwned` → `tagService.create(project.getId(), req.slug(), req.label())` → `201 Created` + `TagResponse`.
   - `GET /` → `requireOwned` → `tagService.list(project.getId())` → `200 OK` + `List<TagResponse>`.
   - `PATCH /{slug}` — `@PathVariable String slug, @Valid @RequestBody UpdateTagRequest req` → `requireOwned` → `tagService.updateLabel(...)` → `200 OK` + `TagResponse`. Если тег не найден → `AppException.notFound`. Note: если кто-то пошлёт `{"slug": "newslug", "label": "..."}` — DTO имеет `@JsonIgnoreProperties(ignoreUnknown = true)`, поэтому slug молча отбрасывается; явного 422 `tag_slug_immutable` не нужно (DTO-схема enforce'ит иммутабельность). Если будущий код добавит поле `slug` в `UpdateTagRequest` — тест `update_slugInBody_returns422OrSilentDrop` ловит регрессию.
   - `DELETE /{slug}` → `requireOwned` → `tagService.deleteWithCascade(...)` → `204 No Content`. Идемпотентно: если тега нет — всё равно 204 (нет ошибки), либо 404 — выбрать 204 для idempotency (типичный REST-pattern для DELETE; тест зафиксирует).

4. Маппинг ошибок: использовать `AppException.conflict("tag_name_taken", "...")` и `AppException.notFound("tag_not_found")`. `GlobalErrorHandler` уже маппит `AppException` → `ErrorResponse{message, code}` с правильным HTTP статусом — менять его НЕ надо.

5. `currentUserId()` helper — повторить идиому из `ProjectController.currentUserId()` (lines 125-131): извлечение `AppUserDetails.id()` из `SecurityContextHolder`. Скопировать паттерн (или вынести в `HttpRequestUtils` если уже там есть — проверить перед дублированием).

6. Тесты (см. TDD Anchor + Testing).

**Edge cases:**
- DELETE на несуществующий tag — выбираем 204 idempotent (REST-pattern). Зафиксировать в тесте `delete_nonexistentTag_returns204Idempotent`.
- PATCH `{slug: "newslug"}` — slug-поле в DTO отсутствует, `@JsonIgnoreProperties(ignoreUnknown=true)` молча отбросит; явный 422 `tag_slug_immutable` НЕ требуется на этом уровне (schema-enforced immutability).
- DuplicateKey на `create`: маппинг через перехват `DuplicateKeyException` — НЕ зависим от текста сообщения (в отличие от `BotService.mapPersistError`, где два разных индекса); здесь один уникальный индекс `(projectId, slug)`, простой catch достаточен.
- Race на `findOrCreate` (Task 8 параллельно зовёт его из нескольких потоков): findOrCreate должен поймать `DuplicateKeyException` от `save` и сделать повторный `findByProjectIdAndSlug` — типичный idempotent-upsert (паттерн tech-spec Architecture §1 "Auto-registration data flow").
- `incrementCounter` с `delta=-1` на счётчике 0 — приведёт к -1; tech-spec считает это "ОК" (теоретически невозможно при правильных вызовах из Task 8, но не блокировать через guard, чтобы не вносить ложный 4xx).
- Cascade DELETE при отсутствии subscribers с тегом — `mongoTemplate.update().pull()` сработает с `modifiedCount=0`, без ошибок; tag всё равно удаляется, событие `tag_deleted` пишется в `events` с `subscriberCountAtDelete=0` (либо текущее значение денормализованного `tag.subscriberCount` до удаления — на выбор; рекомендуется второе как более информативное для аудита).
- Soft-deleted project — `requireOwned(..., false)` бросит `notFound` (anti-enumeration), эндпоинт вернёт 404 без раскрытия существования.
