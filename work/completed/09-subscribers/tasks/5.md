# Task 5: CustomField schema CRUD + per-type value validation

## Required Skills

Перед виконанням задачі завантаж:
- `/skill:code-writing` — [skills/code-writing/SKILL.md](../../../.claude/skills/code-writing/SKILL.md)

## Description

Ship the CustomFieldDefinition management surface for projects (Epic 05 — Subscribers CRM). Three pieces land together so they can be reviewed as one atomic story:

1. **`CustomFieldsController`** — schema CRUD on `Project.customFieldDefinitions[]` (embedded list seeded by Task 1). Mounts under `/api/v1/projects/{projectId}/custom-fields`, every endpoint funnels through `ProjectService.requireOwned(currentUserId(), projectId, false)`. Create uses the atomic conditional push from Decision 3 (`customFieldDefinitions.20` exists-false guard) so the 20-cap race is closed at the Mongo layer. Update edits `label` + `defaultValue` only — `name` (slug) and `type` are immutable per Decision 11 (any mutation attempt → 422 `custom_field_immutable`). Delete removes the definition AND cascades values out of every project subscriber's `Subscriber.customFields[name]` (per user-spec AC12, threshold ≥10 seeded subscribers in IT).
2. **`CustomFieldValueValidator`** — per-type validation primitive (AC11): `STRING` trims + caps at 1024 chars; `NUMBER` requires `Double.isFinite` (rejects `NaN`/`Infinity`); `BOOLEAN` accepts `true|false|yes|no` case-insensitive; `DATE` accepts ISO-8601 (`OffsetDateTime.parse`-able). Validator is reused by `CustomFieldsController` for `defaultValue`-vs-`type` validation at create + update (closes security F9 — error code `custom_field_type_mismatch`, 422).
3. **`SubscriberCustomFieldsController` `PATCH` endpoint** — `PATCH /api/v1/projects/{projectId}/subscribers/{subscriberId}/custom-fields` body `{values: Map<String, Object>}`. **Mass-assignment defense:** unknown keys (not present in `Project.customFieldDefinitions`) are silently dropped — no error, no persist (user-spec AC11 + explicit IT). Known keys are run through `CustomFieldValueValidator`; type-mismatch → 422 `custom_field_type_mismatch`. After successful validation + persistence of new values to `Subscriber.customFields`, call `subscriberService.recordCustomFieldsSet(projectId, subscriberId, oldValues, newValues)` to emit the `subscriber_custom_field_set` event into `subscriber_events` (sole writer per Decision 10). No fallback / no direct event write from the controller.

This task does NOT touch the `Project` entity, the `CustomFieldDefinition` record, or the `CustomFieldType` enum — those land in Task 1 (Wave 1 foundation). This task does NOT implement the `/custom-fields` UI page — that lands in Task 11. Wire only the backend endpoints + validator + cascade behavior.

**Cross-task dependency on Task 3 (Wave 2):** the PATCH endpoint relies on `SubscriberService.recordCustomFieldsSet(...)` which is added to the interface in Task 3. Even though both tasks live in Wave 2, Task 5 effectively serializes after Task 3 (explicit `depends_on: [1, 3]`) — that's compatible with the parallel-friendly wave model so long as the dependency is declared.

## What to do

2. **`CustomFieldValueValidator` (`backend/src/main/java/com/botfunnel/subscriber/CustomFieldValueValidator.java`)** — `@Component`, single public method `Object validate(CustomFieldType type, Object rawValue)` returning the normalized/coerced value (trimmed string, parsed `Double`, parsed `OffsetDateTime`). Throws `AppException.unprocessableEntity("custom_field_type_mismatch", "...")` on any rule violation. Null inputs are allowed (definitions can have `defaultValue=null`; subscriber values can be cleared by passing `null`). Per-type rules per tech-spec §"Unit tests" line 375.

3. **`CustomFieldsController` (`backend/src/main/java/com/botfunnel/project/CustomFieldsController.java`)** — `@RestController @RequestMapping("/api/v1/projects/{projectId}/custom-fields")`. Inject `ProjectService`, `MongoTemplate`, `CustomFieldValueValidator`, `EventService`. Implement:
   - `GET ` — list current `customFieldDefinitions` (200 + `List<CustomFieldResponse>`). First line: `projectService.requireOwned(currentUserId(), projectId, false)`.
   - `POST ` (`@Valid CreateCustomFieldRequest`) — validate `defaultValue` against `type` via `CustomFieldValueValidator` (422 `custom_field_type_mismatch`). Then perform Decision 3 atomic conditional push: `mongoTemplate.update(Query.query(Criteria.where("_id").is(projectId).and("customFieldDefinitions.20").exists(false)), new Update().push("customFieldDefinitions", def), Project.class)`. If `modifiedCount == 0` → re-load project → if `definitions.size() >= 20` throw `unprocessableEntity("custom_field_limit_reached")`; else (name clash detected after re-load) throw `conflict("custom_field_name_taken")`. Pre-check existing names BEFORE the push to short-circuit the common case with 409. Emit `custom_field_definition_created`. Returns 201 + `CustomFieldResponse`.
   - `PATCH /{name}` (`@Valid UpdateCustomFieldRequest`) — re-load project, locate definition by name (404 if not found). `UpdateCustomFieldRequest` has no `name`/`type` fields; combined with `@JsonIgnoreProperties(ignoreUnknown = true)` Jackson silently drops any stray body keys (this is the chosen path for Decision 11 immutability in Task 5 — the 422 `custom_field_immutable` code remains reserved for future endpoints that explicitly parse and reject those fields). Re-validate `defaultValue` vs existing `type` via the validator. Update in-place via positional array operator + arrayFilters (e.g. `"customFieldDefinitions.$[def].label"` with `arrayFilters({"def.name": name})`). Emit `custom_field_definition_updated`. Returns 200 + `CustomFieldResponse`.
   - `DELETE /{name}` — `mongoTemplate.update(Query.query(_id=projectId), new Update().pull("customFieldDefinitions", Query.query(Criteria.where("name").is(name))), Project.class)` (404 if not present). Then cascade-remove the value out of every subscriber: `mongoTemplate.updateMulti(Query.query(Criteria.where("projectId").is(projectId).and("customFields." + name).exists(true)), new Update().unset("customFields." + name), Subscriber.class)`. Emit `custom_field_definition_deleted` with `removedValueCount=...`. Returns 204.
   - Reuse the `currentUserId()` helper pattern from `ProjectController.java:125-131` (copy into this controller — two call sites is below abstraction threshold).

4. **`SubscriberCustomFieldsController` PATCH endpoint** — IMPORTANT: tech-spec Task 8 owns the broader `SubscriberController` (list + profile + tags + messages). For Task 5 we ship the custom-fields PATCH endpoint in its own file `backend/src/main/java/com/botfunnel/subscriber/SubscriberCustomFieldsController.java` (`@RestController @RequestMapping("/api/v1/projects/{projectId}/subscribers/{subscriberId}/custom-fields")`). Inject `ProjectService`, `SubscriberRepository` (from Task 1), `CustomFieldValueValidator`, `SubscriberService` (from Task 3 — sole writer for `subscriber_custom_field_set` per Decision 10), `MongoTemplate`. Do NOT inject `EventService` here — event writes go through `SubscriberService.recordCustomFieldsSet(...)`.
   - `PATCH ` body `SetCustomFieldsRequest(Map<String, Object> values)`. Flow:
     1. `Project project = projectService.requireOwned(currentUserId(), projectId, false);`
     2. Load subscriber by `(projectId, subscriberId)` — 404 if not found OR `subscriber.projectId != projectId` (cross-project isolation). Capture `Map<String, Object> oldValues = subscriber.getCustomFields()` (defensive copy of the keys we are about to touch) BEFORE applying the update so the event metadata can reflect old→new transitions.
     3. Allowed names: `Set<String> allowed = project.getCustomFieldDefinitions().stream().map(CustomFieldDefinition::name).collect(toSet());`.
     4. Iterate `request.values()` entries. For each: if `!allowed.contains(key)` → **silently skip** (no error, debug-level log only). Otherwise look up `CustomFieldType` from the matching definition, invoke `validator.validate(type, value)`, accumulate into `Map<String, Object> newValues` (normalized value).
     5. If `newValues` non-empty: build an `Update` with one `.set("customFields." + key, value)` per entry (atomic positional set; preserves untouched keys); a `null` validated value translates to `.unset("customFields." + key)` so PATCH-with-null clears the field. Apply via `mongoTemplate.update(...)`. Then call `subscriberService.recordCustomFieldsSet(projectId, subscriberId, oldValues, newValues)` — that method is the SOLE writer of `subscriber_custom_field_set` (Decision 10) and is added to the `SubscriberService` interface by Task 3. If `newValues` is empty (all keys were unknown / silently dropped) → skip both the persist and the event emit.
     6. Return 200 + the updated `customFields` map (re-load the subscriber to get the post-write state).

- **Delete cascade on a definition with no values populated** — `updateMulti` returns `modifiedCount=0`; that's OK, return 204 anyway.
- **PATCH on a subscriber with empty `customFields` map** — initialize as `{}` if `null`; first `$set` populates it.

**Implementation hints:**
