# Task 6: TelegramSender hook — terminalReason + markBlocked/markDeleted

## Required Skills

Перед выполнением задачи загрузи:
- `/skill:code-writing` — [skills/code-writing/SKILL.md](../../../.claude/skills/code-writing/SKILL.md)

## Description

Wire `TelegramSender` so that terminal Telegram errors `403 Forbidden` (bot blocked by user) and `400 Bad Request` with description containing `chat not found` (chat removed / account deleted) automatically flip the corresponding subscriber to status `BLOCKED` / `DELETED` via `SubscriberService.markBlockedByChatId` / `markDeletedByChatId`. This closes user-spec AC5 (status state-machine writers driven by sender outcomes) and implements Decision 4 verbatim.

The implementation is constrained by three preconditions captured in the Decision and verified in code-research §16.1:
1. The existing audit emission of `telegram_send_failed` MUST stay intact and MUST fire BEFORE the new mark-* hook (preserve audit semantics — the audit event is the durable record, the CRM flip is the secondary side-effect).
2. `Bot` is already loaded inside `sendText` at line 122; the hook MUST resolve `projectId` from that same instance (no extra `findById` round-trip).
3. The hook routing decision must travel on the exception itself (typed `TerminalReason` enum on `TelegramSendException`), not via substring sniffing in the catch block or downstream in `SubscriberService` — keeps mapping logic colocated with the rest of `toThrowable` and survives future refactors.

This task does NOT introduce `ApplicationEventPublisher` (zero precedent in codebase, R6), does NOT add new sentinel exception types (would force every future caller of `sendText` to catch/rethrow), and does NOT change the `sendText` signature (would ripple into BotService and every future broadcast/funnel call site).

**Wave positioning:** Task 6 runs in **Wave 3** (depends on Task 1 from Wave 1 + Task 3 from Wave 2). Same-wave tasks cannot depend on each other, so Task 6 cannot share Wave 2 with Task 3. Task 6 sits in Wave 3 alongside Tasks 8 and 9 (the HTTP layer and export pipeline tasks, which also depend on Task 3).

## What to do

1. **Extend `TelegramSendException`** with a public nested enum `TerminalReason { BLOCKED_BY_USER, CHAT_NOT_FOUND, OTHER }`, a private final `TerminalReason terminalReason` field, a new constructor overload that accepts the reason as the last parameter, and a `getTerminalReason()` getter. The existing 3-arg constructor MUST continue to compile (default reason → `OTHER`) so callers that don't carry mapping info (`empty response body`, `ok=false`, `transient_failure_exhausted`, `timeout`, `interrupted`) keep working unchanged.

2. **Update `TelegramSender.toThrowable`** to compute `TerminalReason` for the 4xx-non-429 branch:
   - HTTP 403 → `BLOCKED_BY_USER`
   - HTTP 400 AND `result.description()` (post-scrub) contains the case-insensitive substring `chat not found` → `CHAT_NOT_FOUND`
   - all other 4xx-non-429-non-401 → `OTHER`
   - HTTP 401 stays mapped to `BotTokenInvalidException` (unchanged).
   - HTTP 429 stays mapped to `TelegramRateLimitException` (unchanged).
   Pass the computed reason to the new `TelegramSendException` constructor.

3. **Promote the `Bot bot` local** at `TelegramSender.java:122` to method scope so it is reachable from the `catch (RuntimeException ex)` block at lines 131-139. Declare `Bot bot = null;` before the `try`, assign inside; the catch block reads `bot.getProjectId()` only on the new `TelegramSendException` branch (where `bot` is guaranteed non-null because the exception originated post-load).

4. **Extend the existing `catch (RuntimeException ex)` block**: AFTER the existing `eventService.logEvent(... EVENT_TELEGRAM_SEND_FAILED ...)` call (audit MUST fire first), check whether `ex instanceof TelegramSendException tse` AND `tse.getTerminalReason() == BLOCKED_BY_USER | CHAT_NOT_FOUND`, then dispatch to the right `SubscriberService` method. Wrap the mark-* call in its own try/catch so a downstream failure (Mongo down, subscriber already deleted) does NOT swallow or change the original exception — log a WARN with a greppable constant (suggested: `TELEGRAM_SENDER_SUBSCRIBER_HOOK_FAILED`) and continue to `throw ex`.

5. **Append `SubscriberService subscriberService`** as the LAST parameter of the FULL package-private constructor at `TelegramSender.java:88-110` (the one that does the actual wiring — assigns `this.botRepository`, `this.tokenEncryptor`, `this.eventService`, etc.). Assign `this.subscriberService = subscriberService;` alongside the other field assignments. Then update the `@Autowired` prod ctor at lines 74-82 — which is the THIN WRAPPER that already delegates to the full ctor via `this(builder, baseUrl, DEFAULT_RESPONSE_TIMEOUT, DEFAULT_OVERALL_TIMEOUT, botRepository, tokenEncryptor, eventService)` — by (a) adding `SubscriberService subscriberService` as its last parameter and (b) extending its existing `this(...)` argument list to pass `subscriberService` through to the full ctor. The delegation direction is prod → full (wrapper → wired); do NOT reverse it. No new field declarations beyond the single `private final SubscriberService subscriberService;` added at the top of the class.

6. **Update `TelegramSenderTest.newSender(...)`** (and the two inline `new TelegramSender(...)` invocations at lines 587 and 763) to pass a mocked `SubscriberService` as the last argument. Existing tests MUST still pass — the mock is unused in those paths (no terminal-reason-mapped exception thrown).

7. **Write `TelegramSendExceptionTerminalReasonTest`** (new, unit) — pure constructor / getter coverage for the enum and the new ctor:
   - default 3-arg ctor → `getTerminalReason() == OTHER`
   - 4-arg ctor with each enum value → getter returns that value
   - enum order asserted (`TerminalReason.values().length == 3` + `name()` check) — defensive against silent enum renames that would mis-route the hook.

8. **Write `TelegramSenderSubscriberHookIT`** (new, integration / mock-server) following the same MockWebServer pattern as `TelegramSenderTest`:
   - 403 with description "Forbidden: bot was blocked by the user" → `SubscriberService.markBlockedByChatId(projectId, botId, chatId)` is called exactly once with the right args; `telegram_send_failed` audit is also recorded (verify call ordering: audit BEFORE mark-*).
   - 400 with description "Bad Request: chat not found" → `markDeletedByChatId(...)` invoked.
   - 400 with any other description → NEITHER mark-* invoked (still audited as `OTHER`).
   - 401 → `BotTokenInvalidException` path unchanged, NEITHER mark-* invoked.
   - Subscriber-hook downstream failure (mock `SubscriberService` throws RuntimeException) → original `TelegramSendException` still propagates to caller, WARN logged with the greppable constant.

**Dependencies:**

**Edge cases:**
- HTTP 400 with description "chat not found" — must match case-insensitively (Telegram has been observed sending both `"chat not found"` and `"Bad Request: chat not found"`). Use `String.toLowerCase().contains("chat not found")` on the post-scrub description.
- HTTP 400 with empty / null description → `OTHER` (no NPE).
- `result.description() == null` path — `toThrowable` already handles via `TelegramApiClient.scrubTokens(null)`; verify the new mapping logic null-safes the substring check.
- Race: subscriber already in `BLOCKED` / `DELETED` state when the hook fires — `SubscriberService.mark*ByChatId` (Task 3) is documented as idempotent; the hook does NOT pre-check status.
- Subscriber lookup miss inside `mark*ByChatId` (e.g. webhook never registered them — manual `/sendMessage` to a stranger): the impl logs and returns silently per Task 3 contract; the hook does not need to special-case this.
- Mongo down / `mark*` throws → catch locally, WARN with greppable constant `TELEGRAM_SENDER_SUBSCRIBER_HOOK_FAILED`, do NOT alter `ex` — covered by acceptance criterion + dedicated IT case.
- `BotTokenInvalidException` (HTTP 401) — separate exception type, NOT `TelegramSendException` — `instanceof TelegramSendException tse` check naturally excludes it; no extra guard needed.
- Test ctor signature change — ANY downstream test that constructs a `TelegramSender` directly (grep first; currently only `TelegramSenderTest`) must be updated in the same PR to avoid breaking the build.

**Implementation hints:**
- Do the test class additions in TDD order: write `TelegramSendExceptionTerminalReasonTest` first (pure unit, no infra), confirm RED, then add the enum + ctor, confirm GREEN. Then write `TelegramSenderSubscriberHookIT` (RED — `toThrowable` doesn't set reason, catch block doesn't dispatch), then implement the sender changes (GREEN).
- The audit-before-mark ordering is load-bearing — verify with Mockito `InOrder(eventService, subscriberService)` rather than just two independent verifications.
- Keep the new `catch`-internal logic minimal: a single `if (ex instanceof TelegramSendException tse) { switch (tse.getTerminalReason()) { ... } }` block immediately after the existing `eventService.logEvent(...)` line; no helper-method extraction unless reviewers ask for it (the colocation IS the design per Decision 4 rationale).
- `bot` scope: declare `Bot bot = null;` BEFORE the `try`, assign inside. The `catch` block null-checks defensively — though in practice the only way to reach the catch with `bot == null` is if `botRepository.findById(...)` threw, in which case the exception type is `AppException` (404) not `TelegramSendException`, so the new dispatch branch is naturally skipped.
- Greppable WARN constants are a codebase convention (see Decision 9 in tech-spec for precedent strings like `SUBSCRIBER_START_RATE_REDIS_FAIL_OPEN`).
