# Task 7: ProjectHardDeleteJob cascade extension

## Required Skills

Перед выполнением задачи загрузи:

## Description

Today `ProjectHardDeleteJob` only sweeps `events` and drops the `projects` documents. With Epic 09 introducing four new subscriber-domain collections (`subscribers`, `tags`, `subscriber_events`, `subscriber_exports`) plus GridFS-stored CSV export files keyed by `metadata.projectId`, leaving the cascade unchanged would orphan PII and binary blobs every time an operator hard-deletes a project after the 7-day grace window.

This task extends the existing daily 03:00 UTC cron in place per Decision 8 (single job, single observable log line, no sibling `SubscriberCascadeJob`). Cascade order matters: GridFS files are removed BEFORE `subscriber_exports` so a partial-cascade crash never leaves orphan binary files unreachable through their pointer rows. The job stays idempotent — JobRunr default retry on next daily run picks up survivors of any partial cascade.

A companion `ProjectSoftDeleteCascadeIT` (new) asserts the soft-delete side of the user-spec AC22 invariant: while a project is soft-deleted (but not yet hard-deleted), all subscriber CRM list endpoints return 404 via `ProjectService.requireOwned`. Soft-delete behavior itself is already implemented; this IT is the regression guard.

Scope note: the 410 `export_project_unavailable` case for the signed-download endpoint specifically is OUT OF SCOPE for this task — that behavior lives in the download endpoint built by Task 9, and is asserted by `SubscriberExportSignedUrlIT` (Task 9's IT). `ProjectService.requireOwned` itself maps a soft-deleted/missing project to HTTP 404 (not 410), so any 410 assertion here would contradict the actual contract. Task 7's IT stays focused on the CRM list-endpoint 404 surface; cross-reference Task 9 for the download 410 case.

## What to do

1. Extend `ProjectHardDeleteJob.hardDeleteSoftDeletedProjects()` cascade per Decision 8 in this exact order:
   1. `events` (existing — keep as step 1)
   2. GridFS files matching `{metadata.projectId: {$in: deletedIds}}` — remove both the chunks and the file-metadata entries (use `GridFsOperations.delete(query)`)
   3. `subscriber_exports` collection
   4. `subscriber_events` collection
   5. `subscribers` collection
   6. `tags` collection
   7. Emit one `project_hard_deleted` event per project (existing — keep)
   8. Drop project documents (existing — keep)

2. Each new step uses `mongoTemplate.remove(Query.query(Criteria.where(<field>).in(deletedIds)), <collection>)` — capture `DeleteResult.getDeletedCount()` per step. The `projectId` field name is the one stored on each entity (typically `projectId` — verify against the entity classes added by parallel Wave-1 task).

3. Replace the single end-of-run structured INFO log line with the extended shape:
   `ProjectHardDeleteJob - run completed: deletedCount={N} eventsRemovedCount={N} gridFsFilesRemoved={N} exportsRemoved={N} subscriberEventsRemoved={N} subscribersRemoved={N} tagsRemoved={N} runDurationMs={N}`
   The zero-deletion-day branch must keep emitting the same shape with all counts at 0 (liveness signal — operations grep for `ProjectHardDeleteJob - run completed`).

4. Wire `GridFsOperations` into the existing constructor (Spring Boot auto-config supplies it singleton — see architecture.md).

5. Extend `ProjectHardDeleteJobIT`:

**Edge cases:**
- Project with zero subscribers / zero tags / zero exports — cascade steps return `deletedCount=0`, log line still emits all fields, no exception.

- Mid-cascade exception (e.g. Mongo socket drop between step 3 and step 5) → JobRunr default retry policy re-fires the job on next daily run; next run sees: project doc still present (step 8 didn't reach), survivor collections re-processed, eventually drained. The idempotency test guards this.
- Concurrent runs would only happen via manual scheduler trigger — JobRunr deduplicates recurring jobs by id `hard-delete-projects`; not a real risk, but the cascade itself is naturally idempotent (`remove` on empty result is a no-op).
- Empty `deletedIds` list (zero-deletion-day) — short-circuit BEFORE the cascade loop (existing logic at line 57-63); keep this short-circuit but update its INFO line to the new shape.

**Implementation hints:**
- `GridFsOperations.delete(Query query)` removes both the `fs.files` and `fs.chunks` documents per-file. Reference: `org.springframework.data.mongodb.gridfs.GridFsOperations`.
- Capture `DeleteResult` from each `mongoTemplate.remove` and check for null defensively (same pattern as line 80: `eventsDelete == null ? 0L : eventsDelete.getDeletedCount()`).
- For GridFS count, `GridFsOperations.delete` does not return a count. Cheaper alternative: `mongoTemplate.count(query, "fs.files")` BEFORE the delete call — then call delete. Acceptable two-step pattern because the cron is daily and not on the hot path.
- Field name to filter on the subscriber-domain collections — verify by reading the entity classes produced by Task 1. The tech-spec data models (lines 154-234) declare `String projectId` on `Subscriber`, `Tag`, `SubscriberEvent` — use `Criteria.where("projectId").in(deletedIds)` on each. `SubscriberExport` follows the same convention.
- Constructor surgery: append `GridFsOperations gridFs` as the last parameter; assign to a `private final` field. No `@MockitoBean` needed in IT — Spring Boot auto-config supplies it.
- The existing `events` sweep at line 77-80 uses `Criteria.where("metadata.projectId").in(deletedIds)` (nested-field criterion, because `events` stores `projectId` inside the metadata map). The new subscriber-domain sweeps use top-level `Criteria.where("projectId").in(deletedIds)` because those entities store `projectId` at the document root. Do not confuse the two.
- Soft-delete contract distinction (important to keep IT scope correct): `ProjectService.requireOwned(currentUserId(), projectId, false)` maps a soft-deleted or missing project to HTTP **404** (standard not-found mapping) — this is what every CRM list endpoint (`GET /subscribers`, `GET /tags`, `GET /custom-fields`) inherits and what Task 7's `ProjectSoftDeleteCascadeIT` asserts. The HTTP **410** `export_project_unavailable` response is a SEPARATE, narrower mapping that lives ONLY in the signed-download endpoint pipeline built by Task 9 (`SubscriberExportController.download` performs an additional `project.deletedAt != null` check AFTER token verification and returns 410 with body `code: "export_project_unavailable"`). Do NOT try to fold the 410 case into Task 7's IT — `requireOwned` does not return 410, and the download endpoint doesn't exist at Wave 2 / parallel-Wave-2 execution time. Task 9's `SubscriberExportSignedUrlIT` is the canonical owner of the 410 assertion.
- Define new collection-name constants on `ProjectHardDeleteJob` (e.g. `SUBSCRIBER_EXPORTS_COLLECTION = "subscriber_exports"`) for consistency with the existing `EVENTS_COLLECTION` / `PROJECTS_COLLECTION` pattern at lines 31-32.
