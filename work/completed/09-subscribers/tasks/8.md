# Task 8: SubscriberController + TagController endpoints wiring

## Required Skills

Перед выполнением задачи загрузи:

## Description

Wave 4 HTTP layer for the Subscribers CRM. Wires the full `SubscriberController` surface (list, profile, history feed, manual unsubscribe, tag attach/detach, send personal message) plus the segment-filter translator (`SegmentFilter` immutable record + `SegmentFilterBuilder` that builds the Mongo `Query` from DTO criteria). Closes the loop between Wave 2/3 services (Task 3 `SubscriberServiceImpl`, Task 4 `TagService`, Task 5 `CustomFieldValueValidator`, Task 6 `TelegramSender.TerminalReason`) and the frontend that will consume these endpoints in Wave 5/6.

**Out of scope (owned by sibling tasks):** `PATCH /api/v1/projects/{projectId}/subscribers/{id}/custom-fields` lives on `SubscriberCustomFieldsController` (Task 5, by Decision 10 + the file-structure split documented there) — Task 8 does NOT mount the custom-fields PATCH endpoint. If a Wave-4 mistake places it here, the two controllers will conflict on the URL — cross-reference Task 5's controller file before merging.

This is the security-critical HTTP entry point for the CRM module:
- Every endpoint is the first place a hostile request can reach the CRM data; the very first statement of every handler must be `projectService.requireOwned(currentUserId(), projectId, false)` (anti-IDOR, anti-enumeration — closes user-spec AC21).
- Cursor decoding is the most attacked surface — Decision 5 spells out the strict per-key validation (closes security F6: NoSQL operator injection via cursor body).
- Personal-message endpoint introduces a NEW Redis rate-limit bucket per Decision 9 (`bf:rate:personal_message:{projectId}`, 60/min, fail-open) — closes security F5 (compromised-session flood).
- Personal-message endpoint is the SOLE writer of `personal_message_sent` / `personal_message_failed` events per Decision 10 — the controller writes them in the success path and in the OTHER-terminal-reason catch path; `markBlocked`/`markDeleted` write their own events from the service layer (no double-write).

## What to do

1. Create the segment filter primitives:
   - `subscriber/SegmentFilter.java` — immutable Java record carrying the query criteria (search, status, tagsInclude, tagsExclude, subscribedFrom, subscribedTo, sort, cursor, limit). One source of truth that both `SubscriberListQuery` DTO and the export pipeline (Task 9) will consume.
   - `subscriber/SegmentFilterBuilder.java` — translates a `SegmentFilter` into a Spring Data `Query`. Supports: text-search via `TextCriteria.forDefaultLanguage().matchingAny(input.split("\\s+"))` with min-2-chars guard (returns query without text criterion if shorter), `status` (single enum match), `tags: {$all: [...], $nin: [...]}` via `Criteria.where("tags").all(includes)` + `.nin(excludes)`, `subscribedAt` between range, sort `created_desc` or `last_seen_desc`. Cursor handling: decode + apply tie-break criterion `(sortField < v) OR (sortField == v AND _id < lastId)`.

2. Create all DTO records under `subscriber/dto/` per tech-spec Data Models §REST contracts:
   - `SubscriberResponse`, `PageResponse<T>`, `SubscriberListQuery` (controller binds via `@ModelAttribute`), `SendMessageRequest`, `SendMessageResponse`, `TagAssignRequest`, `SubscriberEventResponse`. All carry `@JsonIgnoreProperties(ignoreUnknown = true)` per `patterns.md` mass-assignment rule.

3. Create `subscriber/SubscriberController.java` with `@RequestMapping("/api/v1/projects/{projectId}/subscribers")`. Endpoints:
   - `GET /` — list with cursor pagination. Binds `SubscriberListQuery` via `@Valid @ModelAttribute`. Decodes cursor under strict Decision 5 rules. Builds query via `SegmentFilterBuilder`. Returns `PageResponse<SubscriberResponse>` with `nextCursor`.
   - `GET /{id}` — profile. Loads single subscriber scoped to `projectId`. Returns `SubscriberResponse`.
   - `GET /{id}/events?limit=50` — history feed. Reads from `subscriber_events` (compound index `subscriber_recent`), sort `createdAt desc`, default limit 50, max 200.
   - `POST /{id}/unsubscribe` — manual unsubscribe. Delegates to `SubscriberService.unsubscribeManual(projectId, subscriberId)`. Idempotent: if already unsubscribed → 409 `already_unsubscribed`.
   - `POST /{id}/tags` (body `TagAssignRequest{slug}`) — calls `TagService.findOrCreate(projectId, slug)` then service-level `subscriberService.addTag(...)` which performs the atomic `$inc` of `Tag.subscriberCount` only if `$addToSet` of the slug into `Subscriber.tags` modified the document (prevents double-count on idempotent re-attach).
   - `DELETE /{id}/tags/{slug}` — removes the slug from `Subscriber.tags` via `$pull`; only `$inc` the counter by `-1` if the pull actually modified the document.
   - `POST /{id}/messages` (body `SendMessageRequest{text}`) — Telegram text validation 1..4096 (via `@NotBlank @Size(min=1, max=4096)` on the DTO), Redis rate-limit (`bf:rate:personal_message:{projectId}`, 60/min, fail-open per Decision 9), call `TelegramSender.sendText(...)`, map per AC5:
     - 2xx → write `personal_message_sent` event (Decision 10 — controller owns this); return 200 + `SendMessageResponse{status:"sent", message:"..."}`.
     - `TelegramSendException.terminalReason == BLOCKED_BY_USER` (403) → markBlocked side-effect already written by sender (Task 6); controller does NOT write `personal_message_failed`; respond 200 + `{status:"blocked", message:"Subscriber has blocked the bot"}` (response carries the terminal state visibly to caller).
     - `terminalReason == CHAT_NOT_FOUND` (400) → markDeleted already written; controller does NOT write `personal_message_failed`; respond 200 + `{status:"deleted", message:"Chat not found"}`.
     - `terminalReason == OTHER` (e.g. 400 "text too long") → write `personal_message_failed{terminalReason:"OTHER", error:"..."}`; respond 422 / 502 per existing `GlobalErrorHandler` mapping for `TelegramSendException`.
     - 429 after retry exhaustion → 503 `telegram_rate_limited` per existing error code map.
     - Personal-message rate-limit trip → 429 `personal_message_rate_limited`.

4. Add the personal-message bucket plumbing:
   - `application.properties` → `app.subscriber.rate-limit.personal-message-per-min=${SUBSCRIBER_PERSONAL_MESSAGE_RATE_LIMIT_PER_MIN:60}` (Task 9 owns adding the env var to `.env.example`; this task only needs the property wired so the controller can read it via `@Value`).
   - Use the same INCR-then-EXPIRE-on-first-bucket pattern as `BotService.incrementBruteForceCounter` (referenced by Decision 9). WARN-on-Redis-exception with greppable constant `PERSONAL_MESSAGE_RATE_REDIS_FAIL_OPEN`.

5. Currently `BotController`/`ProjectController` duplicate a private `currentUserId()` helper that re-derives `AppUserDetails` from `SecurityContextHolder`. Reuse the same pattern in `SubscriberController` (do NOT refactor existing helpers — out of scope; matches `patterns.md` controller idiom).

6. Write all tests under `backend/src/test/java/com/botfunnel/subscriber/` extending `AbstractIntegrationTest` (real Mongo + Redis + Mailpit per patterns.md) — see TDD Anchor for the test list.

7. After tests + impl, run smoke (`./gradlew bootRun` + `curl`) and confirm the list endpoint shape.

**Edge cases:**
- Cursor decode: malformed base64 → 400 `invalid_cursor` (do NOT 500); JSON not an object → 400; extra keys beyond `{v,id}` → 400; any sub-key starting with `$` at any depth → 400 (walk the JsonNode tree); `v` is array or object → 400; `id` regex mismatch `^[a-f0-9]{24}$` → 400. All five paths covered by separate IT test methods.
- Search input exactly 2 chars: ACCEPT (boundary). Exactly 1 char: 400. Per `SubscriberListQuery` `@Size(min=2, max=120)` — relies on Bean Validation.
- Text search combined with tags: builder must `addCriteria` BOTH (Mongo allows text + criteria in same query) — covered in unit test.
- Personal-message text 4096 chars: ACCEPT (Telegram max). 4097: reject 400.
- `POST /{id}/tags` race: 10 concurrent attaches of same slug to same subscriber → counter must be `1` (not 10) — covered by `TagControllerIT.addSameTag_concurrentlyFrom10Subscribers_counterEqualsExactly10` in Task 4, but Task 8's `POST /{id}/tags` is the actual entry point under load. Solution: `$addToSet` returns modifiedCount; only call `$inc` when modifiedCount > 0.
- Manual unsubscribe of already-DELETED subscriber: tech-spec scopes idempotency narrowly to "already_unsubscribed"; for BLOCKED/DELETED subscribers, follow the same pattern — return 409 `already_unsubscribed` (the state machine in Task 3 treats all non-ACTIVE as "no-op write"). Confirm with the service contract from Task 3.
- Personal-message: if subscriber `status != ACTIVE` (already BLOCKED/UNSUBSCRIBED/DELETED), still attempt send (Telegram is source of truth) — DO NOT pre-block at controller. Subsequent 403/400 reactions will refresh state via Task 6 hook.

**Implementation hints:**
- For cursor JSON walk, use Jackson `ObjectMapper.readTree(decoded)` → `JsonNode` → recursive helper `assertNoDollarKeys(node)` that throws `AppException.badRequest("invalid_cursor")` on any field name starting with `$`.
- Idempotent `$addToSet` + conditional `$inc`: prefer two operations in a `BulkOperations` against `subscribers` collection + tag counter via `findAndModify` — atomic at the operation level, not transactional, which matches existing codebase convention (no Mongo sessions).
- For the personal-message rate-limit, inject `RedisTemplate<String, String>` and `@Value("${app.subscriber.rate-limit.personal-message-per-min}")`; lift the BotService helper signature if needed (do NOT modify `BotService.incrementBruteForceCounter` — copy the pattern locally; tech-spec Decision 9 calls for "identical shape", not shared code).
- Test fixture for `SubscriberPersonalMessageIT`: reuse `MockWebServer` fixture pattern from existing `TelegramSenderTest` to avoid creating a new harness.
- Cursor encoding for tests: helper static method `String encodeCursor(long v, String id)` lives inside the IT class — keep it co-located so the validation rules are visible in the test source.
- The `requireOwned` call returns a `Project` instance — bind it to a local `Project project = ...;` even if you don't read its fields immediately; future-proofs against analytics events that need `project.getId()`.
