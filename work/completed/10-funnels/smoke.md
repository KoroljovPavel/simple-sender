# 10-funnels — Ручний smoke-чек-лист по всьому епіку

Перевірка вручну **всього** епіку `10-funnels` (Фаза 1, лінійні воронки). Це людський
відповідник автоматичного набору (QA таски 14) і вужчого real-Telegram runbook
`docs/staging-smoke/10-funnels.md` (який покриває лише базовий ланцюг create→trigger→delay→complete).

**Навіщо окремий, ширший чек-лист:** автотести покривають бекенд-рушій, конкурентність,
ідемпотентність і HIGH-сценарії проти реального Mongo/HTTP, але дещо можна підтвердити лише очима
людини на екрані чи в чаті Telegram:

- **UX редактора воронок** (picker, форми, reorder, валідація, copy-link, inline 422) — E2E
  `funnels.spec.ts` скіпиться без живого bootstrap із CONNECTED-ботом (test-audit M2);
- **реальні повідомлення, що приходять у Telegram** — не автоматизується (немає реального бота в CI);
- **підстановка змінних + екранування parse_mode** у живому клієнті, візуально;
- **мультимовність** (uk/en) — підписи й тексти помилок (test-audit M1: підписи редактора закріплені
  лише слабко).

Джерело правди для очікуваної поведінки: `user-spec.md` (Сценарії 1–5, «Критерії приёмки») і
`tech-spec.md` («Acceptance Criteria»). Кожен пункт нижче посилається на критерій, який він доводить.

> **Легенда:** `[AUTO]` — також покрито автотестами (smoke перепідтверджує на живому стеку);
> `[MANUAL-ONLY]` — недосяжно для автоматизації, smoke є єдиною перевіркою.

## Передумови

- Бекенд доступний, `GET /health` → `HTTP 200`.
- Фронтенд-деплой вказує на той самий бекенд.
- Тестовий **акаунт власника**. **Спершу верифікуй email акаунта** — свіжий/неверифікований власник
  гейтиться банером «Verify your email» на дашборді й не може дістатися до проєктних/воронкових фіч
  (це умова F2 зі звіту QA таски 14; вона блокує весь потік).
- Проєкт того акаунта, у якому **щонайменше один бот у `status: "CONNECTED"`**, чий webhook
  зареєстровано на бекенд через HTTPS (`getWebhookInfo` показує URL, без `last_error_message`).
  Переюзай бота зі smoke `08-webhook-ingestion` або підключи одноразового `@BotFather`-бота.
- Твій **особистий акаунт Telegram** на пристрої поруч. **Не** роби `/start` боту заздалегідь для
  кейсів холодного старту.
- Доступ `mongosh` до БД (рядок підключення — зі сховища секретів; ніколи не вставляй у чат, коміти
  чи скріншоти).
- Доступ до логів бекенду, щоб читати іменовані лог-константи переходів.
- На проєкті існують визначення кастом-полів (створи через UI підписників одне STRING, одне NUMBER,
  одне DATE), щоб можна було перевірити Set-Custom-Field і `{custom.<key>}`-темплейтинг.

## Частина A — UX редактора воронок (лише браузер, без Telegram) · Сценарії 1–3

> Заведення: лог-ін → відкрити проєкт → вкладка **Funnels** (`/projects/{projectId}/funnels`).

- [ ] **A1 — Список + empty state + створення.** `[AUTO]` Без воронок показано empty-state CTA. Тиснеш
      **Create funnel**, вводиш назву (+ опц. опис), сабмітиш → створено воронку у статусі `draft`, і
      застосунок переходить у редактор (`funnels/{funnelId}`). Фільтр списку `?status=` перемикає між
      draft/active/paused. *(AC: CRUD)*

- [ ] **A2 — Додавання кожного типу кроку.** `[MANUAL-ONLY]` Тиснеш **+ Add step** → picker пропонує всі
      шість: **Send Message, Send Image, Delay, Add Tag, Remove Tag, Set Custom Field**. Для кожного
      форма рендерить правильні поля:
      - Send Message: текстове поле + picker `parse_mode` (None / HTML / MarkdownV2, дефолт None).
      - Send Image: URL зображення + caption.
      - Delay: число + одиниця (MIN / HOUR / DAY).
      - Add/Remove Tag: tag slug.
      - Set Custom Field: селектор поля + значення.
      Кожен доданий крок дописується в кінець. *(AC: усі типи кроків)*

- [ ] **A3 — Клієнтська валідація блокує погані дані.** `[MANUAL-ONLY]` Порожній текст Send-Message → не
      сабмітиться; значення Delay `< 1` → заблоковано; поганий tag slug (пробіли/великі літери) →
      заблоковано; URL зображення не http/https → заблоковано. Помилки показані inline.
      *(AC: Send Message empty→422 дзеркально; Delay <1хв)*

- [ ] **A4 — Reorder / редагування / видалення.** `[MANUAL-ONLY]` Переміщення кроку ↑/↓ (↑ верхнього й
      ↓ нижнього кроку задизейблені/обмежені), редагування кроку зі збереженням, видалення через inline
      confirm. Порядок зберігається після перезавантаження сторінки (PATCH повного масиву кроків).
      *(AC: CRUD редагування кроків)*

- [ ] **A5 — Ліміт кроків.** `[AUTO]` Додаєш кроки до `FUNNEL_MAX_STEPS` (50). 51-ше додавання
      відхилено з повідомленням `funnel_max_steps_exceeded` / `funnel_step_limit_reached` (422 inline).
      *(AC: Ліміт кроків)*

- [ ] **A6 — Тригер + deep link + Copy.** `[MANUAL-ONLY]` Відкриваєш налаштування тригера: `/start` із
      `trigger_value` (напр. `ref_promo`). UI показує готове посилання `t.me/<bot>?start=ref_promo` із
      кнопкою **Copy** (клік → скопійовано + візуальний фідбек). Очищаєш значення → відображуване
      посилання втрачає payload (голий `/start`). Без CONNECTED-бота замість посилання показано підказку.
      *(AC: Тригер + deep link; Сценарій 2)*

- [ ] **A7 — Валідація активації.** `[AUTO]` Спроба активувати порожню воронку → блок із
      `funnel_no_steps`. Додай крок без обовʼязкового поля → `funnel_step_invalid`. Обидва спливають як
      **локалізована inline-помилка**, не загальний банер 500. *(AC: Сценарій 3 валідація)*

- [ ] **A8 — Конфлікт тригера.** `[AUTO]` Активуй воронку #1 з `(/start, ref_promo)`. Створи воронку #2
      з **тим самим** `(/start, ref_promo)` і активуй → inline `funnel_trigger_conflict` (422). Потім
      зміни `trigger_value` воронки #2 на інше (або голий `/start`) → активується нормально (різні
      значення співіснують). *(AC: Конфлікт тригера)*

- [ ] **A9 — Pause / resume + видалення.** `[MANUAL-ONLY]` Постав active-воронку на паузу → статус
      `paused`. Resume/повторна активація працює. Видали воронку → діалог підтвердження → воронка зникає
      зі списку. *(AC: Pause, Delete; Сценарій 5)*

- [ ] **A10 — i18n (uk ⇄ en).** `[MANUAL-ONLY]` Перемкни мову. Усі підписи редактора (кроки, тригер,
      кнопки), empty state і повідомлення помилок активації
      (`funnel_no_steps`, `funnel_step_invalid`, `funnel_step_limit_reached`, `funnel_trigger_conflict`,
      `funnel_invalid_trigger_value`, `funnel_invalid_state`) відрендерені перекладено — без сирих
      i18n-ключів і без відсутніх рядків у будь-якій локалі. *(test-audit M1)*

## Частина B — Тригер → виконання end-to-end (реальний Telegram) · Сценарій 4

> Детальний покроковий сценарій базового delay-ланцюга (build → activate → `/start` → Step1 → delay →
> Step3 → completed, із `mongosh`-перевірками) живе в `docs/staging-smoke/10-funnels.md` кроки 1–9.
> **Спершу пройди той runbook**, потім пунктами нижче покрий те, чого там немає.

- [ ] **B1 — Точний збіг payload deep-link.** `[AUTO]` Активуй воронку з `trigger_value=ref_x`. Відкрий
      `t.me/<bot>?start=ref_x` і `/start` → ця воронка стартує (`mongosh`: рядок `funnel_execution` із
      правильним `funnelId`). Надішли **голий** `/start` → воронка `ref_x` стартувати **не** має (стартує
      лише воронка під голий `/start`). Payload без жодної відповідної воронки → **нічого** не
      стартує. *(AC: Тригер + deep link)*

- [ ] **B2 — Рендер Send Message і темплейтинг.** `[MANUAL-ONLY]` У кроці-повідомленні використай
      `Привіт, {user.first_name}! Твій план: {custom.<key>}` і `{missing_key}`. Тригерни й прочитай
      доставлене повідомлення: відомі змінні підставлені з даних твого підписника; **невідоме/порожнє →
      порожній рядок** (без літерального `{missing_key}`); літеральні `{{`/`}}` → `{`/`}`. NUMBER
      рендериться без `.0` для цілих, DATE в ISO, BOOLEAN по-людськи. *(AC: Templating)*

- [ ] **B3 — Екранування parse_mode (візуально).** `[MANUAL-ONLY]` Встанови `first_name` свого
      підписника на значення зі спецсимволами (напр. `A*_[x]` або `<b>x</b>`). Надішли те саме
      повідомлення `{user.first_name}` по одному разу на кожен режим:
      - **None** → текст приходить літерально, без форматування, повідомлення не зламане.
      - **HTML** → авторська HTML-розмітка в шаблоні рендериться як форматування, але **підставлене
        імʼя** екрановане (`&lt; &gt; &amp; &quot;`) — імʼя не може інʼєктувати теги.
      - **MarkdownV2** → підставлені спецсимволи backslash-екрановані; повідомлення **не** відхилене
        Telegram і показує імʼя літерально. *(AC: Templating escaping; security A03)*

- [ ] **B4 — Send Image.** `[MANUAL-ONLY]` Додай крок Send-Image з валідним публічним URL зображення й
      caption із `{user.first_name}`. Тригерни → фото приходить із шаблонізованим caption.
      *(AC: Send Image)*

- [ ] **B5 — Збій Send Image (поганий URL).** `[MANUAL-ONLY]` Використай URL зображення, який Telegram
      не може завантажити (напр. сторінку 404). Тригерни → фото немає; виконання → `status: "failed"`
      (`mongosh`); логи показують термінальний send-fail-маркер (scrubbed). Воронка **не** зависає тихо.
      *(AC: Send Image поганий URL→failed)*

- [ ] **B6 — Обрізання довгого тексту.** `[MANUAL-ONLY]` Зроби повідомлення, яке після підстановки
      перевищує 4096 символів. Тригерни → повідомлення **обрізане до 4096** і все одно доставлене (крок
      не падає); логи містять WARN лише з `originalLength`/`trimmedTo` (без вмісту).
      *(AC: Send Message ≤4096 truncate+WARN)*

- [ ] **B7 — Кроки Tag і Custom-Field застосовуються до підписника.** `[AUTO]` Збудуй воронку з кроками
      Add Tag, Remove Tag (тег, що вже є в підписника) і Set Custom Field. Тригерни, тоді перевір
      підписника в UI / `mongosh`: тег додано, тег прибрано, кастом-поле виставлене у валідоване
      значення. Невалідне значення кастом-поля → виконання `failed` з `custom_field_type_mismatch`;
      кастом-поле, чиє **визначення видалено** з проєкту → крок **тихо пропущено**, виконання триває.
      *(AC: Add/Remove Tag, Set Custom Field)*

- [ ] **B8 — Послідовні НЕ-Delay кроки за один тік.** `[AUTO]` Воронка з кількох НЕ-Delay кроків поспіль
      (message, tag, custom field, message) завершується за **один** sweep-тік — усі ефекти настають
      разом, а не «крок за тік». *(AC: Послідовність без Delay)*

- [ ] **B9 — Завершення.** `[AUTO]` Після останнього кроку рядок виконання — `status: "completed"`;
      більше повідомлень не приходить. *(AC: Завершення)*

## Частина C — Lifecycle і конкурентність на живому стеку · Сценарій 5

- [ ] **C1 — `/stop` скасовує.** `[AUTO]` Поки воронка (з pending Delay) виконується для твого
      підписника, надішли `/stop`. Усі `running`/`waiting` виконання підписника → `cancelled`
      (`mongosh`); більше повідомлень кроків не приходить. *(AC: /stop)*

- [ ] **C2 — Pause: нові не стартують, in-flight дограє.** `[MANUAL-ONLY]` (test-audit L2) Запусти
      виконання (pending delay), тоді **постав воронку на паузу**. (а) Свіжий `/start` від *другого*
      тестового підписника **не** створює нового виконання, поки пауза. (б) Уже запущене виконання все
      одно **завершується** після свого delay. *(AC: Pause)*

- [ ] **C3 — Delete скасовує активні.** `[MANUAL-ONLY]` Запусти виконання (pending delay), тоді
      **видали** воронку. Активне виконання → `cancelled` і лишається cancelled (**не** воскресає до
      `completed` — це фікс F2 таски 15); документ воронки зник; відкладене повідомлення кроку так і не
      приходить. *(AC: Delete; Task 15 F2)*

- [ ] **C4 — Re-enter.** `[AUTO]` З `allow_re_enter=false`: надсилаєш `/start` знову, поки виконання
      активне → **ігнор**, без другого виконання (`FUNNEL_FIRE_REENTER_IGNORED`). З `allow_re_enter=true`:
      старе виконання → `cancelled`, і стартує свіже з кроку 0 (`FUNNEL_FIRE_REENTER_RESTARTED`).
      *(AC: Re-enter)*

- [ ] **C5 — Status gating.** `[AUTO]` Зроби підписника неактивним (напр. `/stop` → unsubscribed, або
      заблокуй бота), поки pending Delay. На наступному sweep, перед надсиланням, виконання `cancelled`,
      а не надсилання в неактивний чат. *(AC: Status gating)*

- [ ] **C6 — Bot pinning.** `[MANUAL-ONLY]` Запусти виконання, тоді зміни підключення бота проєкту
      (disconnect/reconnect так, щоб id CONNECTED-бота змінився) до наступного send. In-flight виконання
      має піти у `failed` (запінений `telegramBotId` більше не CONNECTED) — воно **не** має тихо
      надсилати з іншого бота. *(AC: Bot pinning)*

- [ ] **C7 — Snapshot-розвʼязка.** `[AUTO]` Запусти виконання (pending delay), тоді **відредагуй кроки
      воронки**. In-flight виконання дограє за своїм **snapshot** (старі кроки); лише **нові** `/start`
      використовують відредаговану версію. *(AC: Snapshot)*

- [ ] **C8 — Flip на збої надсилання (заблокований бот).** `[MANUAL-ONLY]` Заблокуй бота в Telegram,
      тоді тригерни. 403 → підписник авто-flip у blocked/deleted, а виконання → `cancelled` (не
      `failed`). *(AC: Send-failure semantics)*

## Частина D — Observability та цілісність даних (логи + mongosh)

- [ ] **D1 — Логи переходів, без PII/payload.** `[AUTO]` Для повного прогону логи бекенду показують
      іменовані лог-константи переходів (`FUNNEL_FIRE_EXECUTION_STARTED`, по-крокові
      `in_progress`/`done`, термінальні `completed`/`cancelled`/`failed`), що несуть **лише**
      ідентифікатори/коди/довжини. У логах **не** має бути жодного відрендереного тексту повідомлення,
      caption, значення кастом-поля чи поля профілю підписника (Decision 16). *(AC: Observability)*

- [ ] **D2 — Аудит-івенти записані.** `[AUTO]` Після кроків Tag/Custom-Field у `subscriber_events` є
      рядки `subscriber_tag_added` / `subscriber_tag_removed` **і** `subscriber_custom_field_set` (з
      нормалізованими old/new) — аудит воронкового кастом-поля присутній (фікс F1 таски 15).
      `mongosh`: `db.subscriber_events.find({subscriberId:"<id>"}).sort({createdAt:-1})`. *(Task 15 F1)*

- [ ] **D3 — Токен бота ніколи в логах.** `[AUTO]` Спровокуй збій надсилання (B5/C8) і grep по логах:
      декрипт-токен бота / URL `/bot{token}/sendPhoto` має бути **відредагований** (scrubbed) усюди.
      *(AC: token not leaked; Decision 13)*

- [ ] **D4 — Каскад на hard-delete.** `[AUTO]` (Використай одноразовий проєкт.) Soft-delete проєкту,
      тоді дай/тригерни `ProjectHardDeleteJob`. Після цього `db.funnels.countDocuments({projectId:"<pid>"})`
      і `db.funnel_executions.countDocuments({projectId:"<pid>"})` обидва `0`; лог-рядок джоба містить
      `funnelsRemoved=… funnelExecutionsRemoved=…`. *(AC: Каскад)*

## Частина E — Безпекові spot-перевірки (вручну)

- [ ] **E1 — IDOR / cross-project.** `[AUTO]` Як власник A візьми `funnelId` із проєкту власника B і
      виклич `GET/PATCH/DELETE /api/v1/projects/{A_projectId}/funnels/{B_funnelId}` → uniform **404**
      (та сама форма, що й для відсутнього id; без 403-vs-404 leak). Малформений `funnelId` → той самий
      404. *(AC: CRUD requireOwned)*

- [ ] **E2 — SSRF (URL зображення).** `[MANUAL-ONLY]` Встанови URL Send-Image на внутрішню адресу
      (`http://169.254.169.254/...` або `http://localhost/...`) і тригерни. Бекенд **ніколи не фетчить**
      її (немає вихідного запиту з нашої мережі на той хост у логах/метриках) — лише інфраструктура
      Telegram могла б, поза нашою межею. Виконання падає термінально, якщо Telegram не може завантажити.
      *(security A10)*

- [ ] **E3 — Template injection.** `[MANUAL-ONLY]` Встанови поле профілю / кастом-поле підписника на
      `{custom.secret}` або `{user.username}`. Тригерни повідомлення, що підставляє це поле → інʼєктоване
      `{...}` **не** переparsиться як новий плейсхолдер (рендериться літерально). *(security A03)*

- [ ] **E4 — Фронтенд XSS.** `[MANUAL-ONLY]` Назви воронку `<img src=x onerror=alert(1)>` і встанови
      deep-link-ish значення; відкрий редактор/список → рендериться як **екранований текст**, скрипт не
      виконується, deep-link показано всередині `<code>` як текст (ніколи як `:href`). *(security XSS)*
