# Task 1: Граф-модель даних + статус-фундамент

## Description

Фундамент Фази 2: переводимо модель даних воронки з «плаского списку + числовий індекс» на **граф-модель** і додаємо новий статус-стан, на якому стоятиме весь інтерактив наступних хвиль. Це чисто модельна/енумова задача (Wave 1, без рушія-логіки) — рушій-навігація, валідація графа, callback-шлях і фронтенд-редактор живуть у Tasks 3-7 і залежать від цього фундаменту.

Конкретно:
- `FunnelStep` отримує граф-поля: стабільний `id`, ціль за замовчуванням `next`, список кнопок `List<Button>`, опційні timeout-поля. Новий immutable record `Button`. `copyOf` отримує **явну глибоку копію списку кнопок** — без цього мутабельний список зламає snapshot-ізоляцію Фази 1 (Decision 5).
- `FunnelExecution` отримує `currentStepId` (граф-курсор, поряд з наявним `currentStepIndex` для дренажу лінійних runs) і `lastButtonClicked` (аналітика).
- `ExecutionStatus` отримує константу `waiting_for_reply` (lowercase, як решта статусів — Decision 14). Її треба додати **в усі літерал-сайти `$in`**, де перелічені `running/waiting` (інакше припарковані executions випадуть зі sweep/claim/cancel/re-enter-індексу), і розширити статичну drift-assertion у `FunnelExecution`.
- `StepType` отримує константу `MENU`.
- Новий `FunnelStepIdBackfill implements ApplicationRunner` (за зразком `SuperAdminSeeder`: ідемпотентно, логує-не-кидає) проставляє `id` усім крокам у наявних воронках **та** in-flight `funnel_executions.stepsSnapshot`, і виставляє `currentStepId` з `currentStepIndex` для in-flight (Decision 7).
- Дзеркалимо нові типи у `frontend/types/funnel.ts` (`MENU` у `StepType`, `Button` interface, граф-поля у `FunnelStep`).

Результат: модель і статус готові, наявні воронки/in-flight runs отримують `id` без ручних дій, тести drift/index/copyOf зелені.

## Details

**Додавання `waiting_for_reply` — ДВА РІЗНІ ВИДИ правок (не плутати):**

**Вид A — query/partialFilter `$in` array sites (6 шт.):** усюди, де статус перелічений у Mongo-`$in` масиві, додати `waiting_for_reply`. Інакше припарковані executions випадуть зі sweep/claim/cancel/re-enter-індексу. Суто адитивні one-liner-и в масив — НЕ чіпати іншу логіку.
1. `FunnelExecution.java` re-enter index `partialFilter` (рядок ~27) — `{ 'status': { $in: ['running', 'waiting'] } }` → додати `'waiting_for_reply'`.
2. `FunnelExecutionEngine.java:~91` — sweep `$in`: `.in(ExecutionStatus.running.name(), ExecutionStatus.waiting.name())` → додати `ExecutionStatus.waiting_for_reply.name()`.
3. `FunnelExecutionEngine.java:~201` — claim CAS `$in`: те саме додавання.
4. `FunnelTriggerServiceImpl.java:~156` — `cancelActiveFor` `$in`: те саме.
5. `FunnelTriggerServiceImpl.java:~177` — `cancelExistingForPair` `$in`: те саме.
6. `FunnelService.java:~150` — `delete` `$in`: те саме.

**Вид B — статичний drift-assertion блок (1 шт., ОКРЕМО від `$in`):** `FunnelExecution.java` `static {}` (рядки ~34-41) — це startup-assertion, що кидає `IllegalStateException` при class-load, а НЕ query `$in` масив. Зараз він перевіряє `"running".equals(ExecutionStatus.running.name())` і `"waiting".equals(...)`. Додати окремий disjunct для нового статусу: `|| !"waiting_for_reply".equals(ExecutionStatus.waiting_for_reply.name())`. Це гарантує, що literal у partialFilter (Вид A.1) байт-у-байт збігається з `name()` enum-константи. Тобто A.1 і B стосуються одного файлу, але це дві незалежні правки: A.1 розширює масив `$in`, B розширює assertion-умову.

   Плюс тест-сайт: `FunnelIndexesIT.java:~105` `containsExactly("running","waiting")` → `containsExactly("running","waiting","waiting_for_reply")` (порядок = порядок літералів у partialFilter A.1).

   Files-to-modify у tech-spec для Task 1 не перелічив engine/trigger/service явно, але drift-assertion (Вид B) + `FunnelIndexesIT` зроблять білд червоним без правок Виду A, а самі зміни Виду A — суто адитивні one-liner-и в `$in`. НЕ чіпати жодну іншу логіку цих файлів (рушій-навігація / cancel-логіка — Tasks 3/5). Tasks 3/5 у наступних хвилях успадкують уже-оновлений `$in`.

**`FunnelStep.copyOf` (Decision 5):** зараз reference-копіює всі поля (Javadoc стверджує «field-wise copy = deep copy, бо всі поля immutable scalar» — це більше не так). `List<Button> buttons` — мутабельний контейнер, тож потрібна явна копія: `copy.buttons = source.buttons == null ? null : new ArrayList<>(source.buttons)`. Елементи (`Button`) — immutable record, тож shallow-copy списку достатньо (самі record-и копіювати не треба). Оновити Javadoc: `buttons` копіюється захисно, решта — immutable scalar.

**`Button` record:** компонентний порядок `(type, label, targetStepId, url)` за Data Models. Без бін-валідації (Task 4). Spring Data персистить record у вкладений документ.

**`FunnelStepIdBackfill`:**
- `@Component implements ApplicationRunner`; `run(ApplicationArguments)` → try/catch(Exception) з `log.error`, ніколи не кидає (взірець `SuperAdminSeeder`).
- Інжектити `MongoTemplate`. **Update-стратегія:** використати `MongoTemplate` з `$set` partial-update, а НЕ full-document save через репозиторій. Full-save серіалізує весь документ за поточною mapping-схемою і ризикує загубити поля legacy-документів, яких немає в актуальній моделі; `$set` чіпає лише цільові поля. **УВАГА — кожен крок має отримати ОКРЕМИЙ унікальний `id`.** НЕ використовувати positional-all `steps.$[].id` в одному `$set` — він проставить ОДИН і той самий `id` усім елементам масиву. Замість цього: проітерувати масив `steps`, згенерувати окремий `id` для кожного кроку без `id`, і персистити так, щоб кожен елемент отримав свій рядок. Робочі варіанти: (а) прочитати документ, у пам'яті призначити distinct `id` кожному кроку (де `id == null`), потім `$set` усього масиву `steps` цілком (`Update().set("steps", patchedSteps)`); або (б) точковий `$set` по індексу для кожного кроку (`Update().set("steps." + i + ".id", mintedId)`) у циклі; або (в) один update з `arrayFilters` per-element, де кожен фільтр прив'язаний до свого elem і свого distinct значення. У всіх випадках значення `id` мають бути різними між кроками.
- Мінт `id`: `new ObjectId().toHexString()` або `UUID.randomUUID().toString()` — узгодити з тим, як `id` мінтитимуться у `toSteps` (Task 4); для backfill головне — стабільний унікальний рядок. Зафіксувати вибір у decisions.
- Ідемпотентність: проставляти `id` лише крокам де `id == null`; не перезатирати наявні. `currentStepId` лише коли `currentStepId == null` (брати крок за `currentStepIndex` зі снапшоту).
- Охоплення: і `funnels` (визначення), і `funnel_executions.stepsSnapshot` (in-flight) — Decision 7.

**Dependencies:** немає task-залежностей (Wave 1, `depends_on: []`). Tasks 3-7 залежать від цього фундаменту. Нових пакетів немає.

**Edge cases:**
- `copyOf` з `buttons == null` → копія теж `null` (не порожній список), без NPE.
- Backfill: воронка з нуль кроків; execution з порожнім/null снапшотом; крок, що вже має `id` (re-run); `currentStepIndex` поза межами снапшоту (страховка — не падати).
- Снапшот in-flight execution може містити кроки старого лінійного формату без `next`/`buttons` — це нормально (поля nullable); backfill чіпає лише `id`/`currentStepId`.

**Implementation hints:**
- НЕ міняти `currentStepIndex` — він лишається для дренажу лінійних runs (Decision 7); `currentStepId` додається поряд.
- Дотримати lowercase-конвенцію (Decision 14): `waiting_for_reply`, не `WAITING_FOR_REPLY`. `StepType.MENU` — UPPERCASE (discriminator-конвенція).
- Frontend: `Button.targetStepId` / `url` опційні (`?`), бо взаємовиключні за типом.
- Тести backfill — Testcontainers Mongo за зразком наявних Ф1 IT (`FunnelIndexesIT` як взірець підняття контейнера).
