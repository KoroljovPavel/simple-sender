# Task 11: Pre-deploy QA

## Required Skills

Перед выполнением задачи загрузи:
- `/skill:pre-deploy-qa` — [skills/pre-deploy-qa/SKILL.md](.claude/skills/pre-deploy-qa/SKILL.md)

## Description

Приёмочное тестирование фичи `11-funnels-interactive` (Интерактив + клавиатуры, Фаза 2) перед передачей пользователю. Деплоя нет — проверка **локальная**. Цель: прогнать весь набор тестов (backend unit + integration, frontend vitest + playwright), проверить каждый критерий приёмки из user-spec («Критерии приёмки») и tech-spec («Acceptance Criteria»), и поверх автотестов выполнить агентскую верификацию из tech-spec Agent Verification Plan: `curl`-проверки бизнес-кодов валидации (422 `funnel_broken_edge`, 422 «MENU без callback»), симуляция `callback_query` на webhook (валидный / устаревший / несуществующий / malformed / oversized `callback_data`) с проверкой состояния Mongo.

Это **финальная волна** после трёх аудит-задач (8 — code audit, 9 — security audit, 10 — test audit). QA не пишет код и не правит фичу — только проверяет и фиксирует находки. Живой проход в Telegram (реальное поведение inline-клавиатур) остаётся **ручной проверкой пользователя** и в scope автоматизированного QA не входит — такие критерии помечаются `not_verifiable` и выносятся в `deferredToPostDeploy`.

## What to do

1. Прочитать спеки и контекст: `user-spec.md` (секция «Критерии приёмки»), `tech-spec.md` (секция «Acceptance Criteria» + «Agent Verification Plan»), `decisions.md` (отчёты задач 1–10, обоснованные отклонения). Учесть, что деклараций задач-аудитов 8/9/10 в decisions.md уже зафиксированы — их находки не дублировать, но проверить, что критичные закрыты.

2. **Test Suite — backend.** Прогнать backend-тесты, в первую очередь модулей `funnel`, `webhook`, `bot` (новые callback / loop / timeout / idempotency / IDOR ITs + drift/index/copyOf unit). Зафиксировать: всего тестов, passed, failed, skipped. Любой упавший тест → `critical`.

3. **Test Suite — frontend.** Прогнать vitest (форма `MENU`, пикер цели, инлайн `funnel_broken_edge`-валидация) и playwright happy-path (редактор `MENU` + 2 callback-кнопки + цель через `SearchableSelect` + save + activate). Зафиксировать результат.

4. **Agent Verification Plan (curl + симуляция webhook + Mongo).** Выполнить шаги из tech-spec «Agent Verification Plan» / user-spec «Как проверить» → «Агент проверяет»:
   - `curl` activate воронки с целью на удалённый шаг → ожидать **422 `funnel_broken_edge`**.
   - `curl` activate `MENU` без callback-кнопки → ожидать **422**.
   - Симуляция `callback_query` на `POST /webhooks/telegram/{projectId}` с устаревшим / несуществующим / malformed / oversized `callback_data` → проверить через Mongo, что execution **не сдвинулся** (тихий no-op).
   - Симуляция валидного callback → проверить в коллекции `events` запись `funnel_button_clicked` (`funnelId`/`executionId`/шаг/кнопка) и обновлённый `lastButtonClicked` на execution.
   - Если поднять локальное окружение (Mongo / Redis / backend) для curl/webhook-симуляции невозможно в среде агента — пометить эти шаги `not_verifiable` со ссылкой на покрывающие их integration-тесты как косвенное подтверждение, и вынести в `deferredToPostDeploy`.

5. **Acceptance Criteria.** Пройти по каждому критерию из user-spec и tech-spec (список ниже). Для каждого: `passed` (с доказательством — имя теста / путь кода / вывод curl), `failed` (фича есть, но критерий не выполнен → `critical`), или `not_verifiable` (нужен живой Telegram / окружение — scope post-deploy).

6. **Coverage Verification.** Для каждого файла из tech-spec «Files to modify» (по задачам 1–7) убедиться, что есть соответствующий тест. Код фичи без теста → `critical`. Проверить, что тесты под `passed`-критерии реально упражняют поведение, а не импорт/мок. Edge-кейсы из user-spec (двойной клик, устаревшая кнопка, URL-кнопка, петля-лимит, paused-drain, IDOR, snapshot-изоляция) — убедиться, что покрыты тестами; отсутствие для L-фичи → `major`.

7. **Output.** Записать полный JSON-отчёт в `work/11-funnels-interactive/logs/working/qa-report.json` (по схеме скилла, с секцией `deferredToPostDeploy` для всех `not_verifiable`). Записать краткую запись в `decisions.md` со ссылкой на JSON. `status: passed` если ноль critical, иначе `failed`.

## Acceptance Criteria

Проверить **все** критерии приёмки фичи (источники: user-spec «Критерии приёмки», tech-spec «Acceptance Criteria»):

**Из user-spec:**
- [ ] Автор добавляет шаг `MENU` с текстом и кнопками; callback-кнопка ведёт на шаг или «End», URL-кнопка — на `http(s)`-ссылку.
- [ ] Кнопка может вести назад на предыдущее меню (петля) и несколько кнопок — на один шаг (fan-in); оба сохраняются и выполняются.
- [ ] `/start` → подписчик получает `MENU` с inline-клавиатурой; `{user.first_name}` подставлен в текст.
- [ ] Нажатие callback-кнопки → «часы» исчезают (`answerCallbackQuery`) и подписчик попадает в правильную ветку.
- [ ] Ветка с возвратом на меню повторно шлёт меню; повторные нажатия работают (петля без зависания).
- [ ] Нажатие URL-кнопки открывает ссылку и не продвигает воронку.
- [ ] Нажатие старой/устаревшей кнопки (execution ушёл дальше / `completed` / `cancelled`) → `answerCallbackQuery` + тихо игнорируется.
- [ ] Двойной клик → ветка выполняется один раз (атомный claim).
- [ ] `/stop` во время ожидания → executions в `waiting_for_reply` становятся `cancelled`.
- [ ] Подписчик заблокировал бота во время ожидания → первая попытка send в ветке → execution `cancelled`.
- [ ] Воронку отредактировали пока execution ждёт → дограет по старому графу (snapshot-изоляция).
- [ ] Воронка `paused` → новые executions не стартуют; активный `waiting_for_reply` после нажатия кнопки продвигается до `completed`.
- [ ] Таймаут (если задан) → ведёт по цели таймаута; не задан → ждём неограниченно.
- [ ] Петля без wait/delay → лимит шагов за тик рвёт цикл → `failed` с греппабельным лог-маркером.
- [ ] Активация воронки с кнопкой на удалённый шаг → 422 `funnel_broken_edge`; `MENU` без callback-кнопки → 422.
- [ ] Нажатие кнопки записывает `funnel_button_clicked` + `lastButtonClicked` на execution.
- [ ] Наявные воронки Фазы 1 и их in-flight executions не ломаются (`id` проставлены, линейные runs дограют).

**Из tech-spec (технические, дополняют):**
- [ ] `waiting_for_reply` присутствует в re-enter partialFilter, sweep/claim `$in`, всех cancel-путях; drift-assertion + `FunnelStatusEnumTest` + `FunnelIndexesIT` зелёные.
- [ ] `FunnelStep.copyOf` глубоко копирует список кнопок (unit доказывает изоляцию).
- [ ] Backfill `ApplicationRunner` идемпотентен; повторный старт не дублирует `id`.
- [ ] `callback_data` ≤ 64 байт; malformed/oversized/чужой → `answerCallbackQuery` + no-op.
- [ ] Callback с чужим `executionId` (IDOR) отклонён; `answerCallbackQuery` вызван на всех no-op-путях.
- [ ] Все тесты зелёные (unit + integration + 1 e2e); нет регрессий в тестах Фазы 1.
- [ ] Нет новых секретов; URL-кнопки только `http(s)` (строгий `URI`-парс схемы + host).

## Verification Steps

### Automated

Backend (из `backend/`, есть `./gradlew`):
- `./gradlew test` → all pass (или таргетно по модулям funnel/webhook/bot, если поддерживается фильтр)
- Зафиксировать счётчик: total / passed / failed / skipped

Frontend (из `frontend/`, pnpm):
- `pnpm test` (vitest) → all pass
- `pnpm test:e2e` (playwright, happy-path редактора `MENU`) → pass

### Smoke

Проверки агента поверх автотестов (из tech-spec Agent Verification Plan). Выполнять, если локальное окружение поднимается; иначе — `not_verifiable` + `deferredToPostDeploy`:
- `curl -X POST .../funnels/{id}/activate` с целью на удалённый шаг → **422 `funnel_broken_edge`**
- `curl -X POST .../funnels/{id}/activate` для `MENU` без callback-кнопки → **422**
- `bash`-симуляция `callback_query` на `POST /webhooks/telegram/{projectId}` со stale / несуществующим / malformed / oversized `callback_data` → Mongo: execution не сдвинулся, `answerCallbackQuery` вызван
- `bash`-симуляция валидного callback → Mongo (`events`): записан `funnel_button_clicked`; на execution обновлён `lastButtonClicked`

### User

Живой проход в Telegram — **ручная проверка пользователя**, вне scope автоматизированного QA. Эти критерии помечаются `not_verifiable` и выносятся в `deferredToPostDeploy`:
- На тестовом боте `/start` → меню с кнопками → нажать callback → часы исчезли, пришла правильная ветка
- Нажать кнопку-петлю → меню появилось снова
- Нажать URL-кнопку → открылась ссылка, воронка не сдвинулась

Реальное поведение inline-клавиатур симуляция webhook не покрывает — поэтому это пользовательский шаг.

## Details

**Природа задачи:** QA, кода не пишем. Источник истины — спеки (user-spec, tech-spec, decisions.md), не файлы задач (`tasks/*.md` уже проверены ревьюерами и вне scope QA).

**Где что лежит:**
- Backend: `backend/` (Gradle, `./gradlew test`). Модули фичи — `funnel`, `webhook`, `bot`. Ключевые ITs: `FunnelExecutionEngineIT`, `FunnelControllerIT`, `FunnelIndexesIT`, `ProcessTelegramUpdateJobTest`, `TelegramSenderIT`; unit: `FunnelStatusEnumTest`, `FunnelStepTest`, `FunnelStepExecutorTest`.
- Frontend: `frontend/` (pnpm). vitest — `frontend/tests/pages/funnel-editor.spec.ts`; playwright — `frontend/e2e/funnels.spec.ts`.
- Файлы фичи для coverage-проверки — из tech-spec «Files to modify» задач 1–7 (FunnelStep, Button, FunnelExecution, ExecutionStatus, StepType, FunnelStepIdBackfill, FunnelExecutionEngine, StepExecutor, FunnelTriggerService(+Impl), FunnelService, FunnelStepDto, ButtonDto, TelegramSender, ProcessTelegramUpdateJob, TelegramUpdate, CallbackQuery DTO, + frontend компоненты/типы/i18n).

**Dependencies:** задачи 8 (code audit), 9 (security audit), 10 (test audit) завершены. QA читает их отчёты в decisions.md, чтобы не дублировать находки и убедиться, что критичные закрыты.

**Edge cases для coverage-проверки (из user-spec «Риски»/AC):** двойной клик (идемпотентность), устаревшая/malformed/oversized callback_data, URL-кнопка не двигает воронку, петля без wait → лимит шагов за тик → failed+маркер, paused-drain, IDOR (чужой executionId), snapshot-изоляция при waiting, blocked-bot во время waiting, миграция/backfill идемпотентность, таймаут (задан/null).

**Implementation hints:**
- Если backend-окружение (Testcontainers Mongo) недоступно для запуска ITs в среде агента — это критично для статуса: пометить test suite и зависящие AC соответственно, не выдавать ложный `passed`.
- curl/webhook-симуляция требует поднятого backend + Mongo + Redis. Если поднять нельзя — `not_verifiable`, опереться на покрывающие integration-тесты как косвенное доказательство, вынести в `deferredToPostDeploy` с конкретными шагами для post-deploy.
- `status: passed` только при ноль `critical`. Один и более critical → `failed`.
- Каждая находка — с конкретной репродукцией: шаги, expected vs actual.
