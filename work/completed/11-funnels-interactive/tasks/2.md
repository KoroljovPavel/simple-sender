# Task 2: TelegramSender — reply_markup + answerCallbackQuery

## Required Skills

Перед выполнением задачи загрузи:
- `/skill:code-writing` — [skills/code-writing/SKILL.md](../../../.claude/skills/code-writing/SKILL.md)

## Description

Фаза 2 додає інтерактивні меню (`MENU`-крок): бот має слати inline-клавіатуру разом із текстовим
повідомленням і вміти прибирати «спіннер» на кнопці після callback. Ця задача розширює існуючий
`TelegramSender` (Wave 1, незалежна — інші Wave-2/3 задачі споживають її результат):

1. `sendText` отримує опційний `reply_markup` — об'єкт `{"inline_keyboard":[[{text, callback_data}]
   або [{text, url}]]}`, який додається в **тіло** запиту (мапу `contentFields`, не в сигнатуру
   методу як останній параметр) `/sendMessage` **лише коли він non-null**. Ідіом only-if-non-null —
   той самий, що в `contentFields` для `parse_mode`/`caption`. **Сумісність:** поточна сигнатура
   `sendText(botId, chatId, text, parseMode, ownerId)` має 3 production call-site
   (`BotService.java:127`, `SubscriberController.java:250`, `StepExecutor.java:108`) + багато
   тест-викликів — тому **обери перевантаження**: додай новий 6-арг
   `sendText(botId, chatId, text, parseMode, ownerId, replyMarkup)`, лишивши 5-арг сигнатуру цілою
   (деталі — у Details).
2. Новий метод `answerCallbackQuery(botId, callbackQueryId, text?)` шле POST на
   `/bot{token}/answerCallbackQuery`, повторно використовуючи всі наявні патерни класу: AES-GCM
   decrypt токена per-call, CONNECTED-фільтр бота, 5xx/429 retry-backoff loop, token-scrub у логах,
   30s overall timeout. Метод **best-effort** (Decision 8): провал ack (Telegram 5xx) не повинен
   блокувати просування воронки — окремої аудит-події немає, лише WARN-лог.

Результат: бот шле клавіатуру і вміє прибирати спіннер; обидві можливості покриті IT через
`mockwebserver`.

## What to do

1. **`reply_markup` у `sendText` (через перевантаження).** Додай нове перевантаження
   `sendText(String botId, Long chatId, String text, String parseMode, String ownerId, Object replyMarkup)`
   (тип `replyMarkup` — мапа/об'єкт, що серіалізується у `{"inline_keyboard":[...]}`). У ньому збудуй
   `contentFields` як у поточному `sendText` (`text` + опц. `parse_mode`) і **додатково** поклади
   `reply_markup` у мапу **лише коли non-null** — рівно як `parse_mode` додається в `contentFields`
   (це поле **тіла**, а не останній параметр методу; останній параметр — `ownerId`). Існуючий 5-арг
   `sendText` залиш як є і задешевий делегуй у новий 6-арг з `replyMarkup=null` (або навпаки), щоб
   не дублювати логіку. **Жодних змін у спільному `send(...)`** не потрібно: `reply_markup` —
   ще одне поле тіла, що проходить наявним retry/audit/hook-конвеєром. Перевантаження лишає всі 3
   production call-site та тест-виклики незмінними (нуль file-contention з іншими хвилями).
2. **Метод `answerCallbackQuery(botId, callbackQueryId, text?)`.** Реалізувати окремий публічний
   метод, що:
   - резолвить `Bot` через `botRepository.findById(botId)` з тим самим CONNECTED-фільтром і
     `MESSAGE_BOT_NOT_FOUND` контрактом, що в `send(...)`;
   - per-call AES-GCM decrypt токена (`tokenEncryptor.decrypt`) + `requireValidTokenShape` — як у
     `sendOnce`; плейн-токен не зберігати у полях, не логувати;
   - POST `/bot{token}/answerCallbackQuery` з тілом `{"callback_query_id": ..., "text": ...}` (text
     додається лише коли non-null);
   - проходить наявний 5xx/429 retry-backoff + 30s deadline механізм (переюз існуючих
     `sendWithRateLimitRetry`/`sendWith5xxRetry` seam або їх еквівалент — НЕ дублюй loop руками,
     якщо можна переюзати);
   - **best-effort:** будь-який збій (5xx exhausted, timeout, token issue тощо) ловиться, scrub-иться
     і WARN-логиться — метод **не кидає** наверх (Decision 8). Не емітить аудит-подію.
3. **Token-scrub** усіх лог-рядків нового методу через `TelegramApiClient.scrubTokens(...)` (як решта
   класу).
4. **IT у `TelegramSenderIT`** (див. TDD Anchor) — `reply_markup` присутній у body `/sendMessage`;
   `answerCallbackQuery` шле POST на `/answerCallbackQuery`; best-effort при 5xx не кидає.

## TDD Anchor

Тести пишемо ДО реалізації, переконуємось що падають, потім пишемо код.

`TelegramSenderIT` використовує class-level `MockWebServer` (okhttp3) з `app.telegram.base-url`,
перевизначеним через `@DynamicPropertySource`. Сценарії потребують прямого виклику `TelegramSender`
(а не через `BotService`, який ще не дороблений Task 7) — інжектни `TelegramSender` як `@Autowired`
бін у тесті, засідни CONNECTED-бота, заскриптуй відповіді `mockTelegram.enqueue(...)`, дренуй і
перевір `RecordedRequest` (path + JSON-тіло).

- `backend/.../bot/TelegramSenderIT.java::sendText_withReplyMarkup_includesInlineKeyboardInBody` —
  `sendText` з non-null `reply_markup` → `RecordedRequest` на `/bot.../sendMessage` має у тілі
  `reply_markup.inline_keyboard` з очікуваними кнопками (callback_data та/або url).
- `...::sendText_nullReplyMarkup_omitsKeyField` — `sendText` без клавіатури → тіло НЕ містить ключа
  `reply_markup` (регресія only-if-non-null ідіому; як для `parse_mode`).
- `...::answerCallbackQuery_postsToAnswerCallbackQueryEndpoint` — виклик з `text` → POST на
  `/bot.../answerCallbackQuery`, тіло містить `callback_query_id` і `text`.
- `...::answerCallbackQuery_nullText_omitsTextField` — виклик без `text` → тіло без ключа `text`.
- `...::answerCallbackQuery_telegram5xx_bestEffortDoesNotThrow` — `mockTelegram` віддає 5xx на всіх
  спробах → метод не кидає виняток (best-effort, Decision 8); звір WARN-лог за бажанням.
- `...::answerCallbackQuery_disconnectedBot_noTelegramCall` (опц.) — бот не CONNECTED → жодного
  HTTP-трафіку (CONNECTED-фільтр), метод не кидає.

## Details

**Files:**
- `backend/src/main/java/com/botfunnel/bot/TelegramSender.java` — наявний `@Component`, RestClient-бін
  (singleton). Поточний стан: `sendText(botId, chatId, text, parseMode, ownerId)` будує
  `contentFields` (`text` + опц. `parse_mode`) і делегує у спільний `send(...)`, що містить
  CONNECTED-фільтр, `sendWithRateLimitRetry` → `sendWith5xxRetry` → `sendOnce` (де per-call
  decrypt + `requireValidTokenShape` + `restClient.post().uri(endpoint, token).body(body)`), audit-
  події `EVENT_TELEGRAM_MESSAGE_SENT`/`EVENT_TELEGRAM_SEND_FAILED`, Decision-4 subscriber hook.
  Що зробити: (1) додати **6-арг перевантаження** `sendText(..., Object replyMarkup)`, що кладе
  `reply_markup` у `contentFields` за ідіомом `parse_mode` (only-if-non-null), і делегує у `send(...)`;
  поточний 5-арг `sendText` лишити цілим (делегувати у 6-арг з `replyMarkup=null`). **НЕ** додавай
  6-й nullable параметр у єдиний метод і **не** чіпай останній параметр (`ownerId`) — перевантаження
  чистіше і не торкається call-sites. Якби обрав 6-й param у єдиному методі — довелось би додати
  `null` у всі 3 production call-site (`BotService.java:127`, `SubscriberController.java:250`,
  `StepExecutor.java:108`) + тести; перевантаження цього уникає.
  (2) додати метод `answerCallbackQuery` — він НЕ content-send, тож не має йти
  гілкою audit/subscriber-hook; найчистіше — окремий приватний send-helper, що переюзає
  `sendWithRateLimitRetry`/`sendWith5xxRetry`/`sendOnce` (вони параметризовані `endpoint` +
  `contentFields`), але обгорнутий у власний try/catch, який ковтає виняток і WARN-логить
  (best-effort). **Увага до visibility:** `sendWithRateLimitRetry`/`sendWith5xxRetry`/`sendOnce`
  зараз `private` і всі повертають `SentMessage` (мапінг `message_id`). Щоб переюзати retry/deadline
  seam для ack, ймовірно знадобиться або змінити їх visibility (package-private), або винести спільний
  internal helper — обери підхід сам; не дублюй retry-loop руками. `sendOnce` наразі мапить відповідь
  у `SentMessage` (потрібен `message_id`) —
  для `answerCallbackQuery` відповідь Telegram — `{"ok":true,"result":true}`, тож або зроби окремий
  мінімальний post-шлях для ack, або переконайся, що відсутність `message_id` не валить best-effort
  гілку (вона ковтається). Обери підхід, який мінімально дублює retry-loop і не ламає content-send.
- `backend/src/test/java/com/botfunnel/bot/TelegramSenderIT.java` — наявний IT із class-level
  `MockWebServer`, `seedConnectedBot`, `drainRequests`, `@DynamicPropertySource` base-url. Деякі
  сценарії `@Disabled` (чекають Task 7 wire-up через BotService). Що зробити: додати нові `@Test`-и
  (TDD Anchor), що інжектять `TelegramSender` напряму (`@Autowired`) і б'ють `sendText` /
  `answerCallbackQuery` прямо, минаючи `BotService`. Це обходить `@Disabled`-залежність від Task 7.
  Засідни CONNECTED-бота через `seedConnectedBot`, заскриптуй `mockTelegram.enqueue(...)`, дренуй
  `drainRequests()`, перевір path + парс JSON-тіла (`RecordedRequest.getBody().readUtf8()` →
  ObjectMapper) на `inline_keyboard` / `callback_query_id`.

**Dependencies:** немає залежностей від інших задач (Wave 1). Споживачі цієї задачі: Task 3
(StepExecutor шле `MENU` з `reply_markup`), Task 5 (`advanceOnCallback` зве `answerCallbackQuery`).
Пакети — без нових (переюз наявного `mockwebserver` testImplementation, RestClient).

**Edge cases:**
- `reply_markup == null` → ключ відсутній у тілі (як `parse_mode`).
- `text == null` у `answerCallbackQuery` → ключ `text` відсутній (ack без тексту валідний).
- Бот не CONNECTED → CONNECTED-фільтр; для ack це best-effort → ковтається, без HTTP.
- Telegram 5xx exhausted / 429 / timeout у `answerCallbackQuery` → best-effort: не кидати, WARN-лог.
- Decrypt/token-shape провал у ack → best-effort ковтається (не зривати воронку).

**Implementation hints (НЕ псевдокод):**
- `reply_markup` — поле **тіла** в `contentFields`, не параметр методу. Тримай only-if-non-null ідіом
  у `contentFields` так само, як `parse_mode`/`caption` у `sendText`/`sendPhoto` (`if (x != null)
  contentFields.put(...)`). Серіалізується у `{"inline_keyboard":[[{text, callback_data|url}]]}`.
- Не змінюй 5-арг сигнатуру і її останній параметр `ownerId` — додай 6-арг перевантаження
  `sendText(botId, chatId, text, parseMode, ownerId, replyMarkup)` поруч.
- Для best-effort обгортки лови `RuntimeException` навколо всього ack-шляху, scrub через
  `TelegramApiClient.scrubTokens`, WARN-логуй. Розглянь греппабельний лог-маркер у стилі наявних
  констант (`TELEGRAM_SENDER_SUBSCRIBER_HOOK_FAILED`) — напр. `TELEGRAM_ANSWER_CALLBACK_FAILED`.
- Не дублюй retry/deadline loop — переюзай наявний (`endpoint` + `contentFields` + `attempts` +
  `deadline`). Зверни увагу: `sendWithRateLimitRetry`/`sendWith5xxRetry`/`sendOnce` зараз `private` —
  може знадобитись package-private visibility або спільний internal helper, щоб ack-шлях їх переюзав.
- Перед стартом звір call-sites `grep -rn 'sendText(' backend/src` (3 production + тести) — підтвердь,
  що перевантаження лишає їх незмінними.
