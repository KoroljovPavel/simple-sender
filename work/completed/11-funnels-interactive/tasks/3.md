# Task 3: Рушій — граф-навігація, MENU-park, resumeOnCallback, таймаут

## Required Skills

Перед выполнением задачи загрузи:
- `/skill:code-writing` — [SKILL.md](../../../.claude/skills/code-writing/SKILL.md)

## Description

Переводимо `FunnelExecutionEngine` з лінійної index-навігації Фази 1 на **граф-навігацію** по `currentStepId`, додаємо park-on-reply вихід для нового кроку `MENU`, окрему точку входу `resumeOnCallback` (callback-пробудження повз sweep) і таймаут-resume-гілку. Це ядро Фази 2: рушій тепер ходить графом (петлі, fan-in), паркується на меню в статусі `waiting_for_reply` і резюмиться двома незалежними шляхами — натиском кнопки (callback, лише власник execution) і таймаутом (через наявний sweep).

Зберігаємо незмінною механіку at-most-once Фази 1: атомний claim-CAS (`pending→in_progress`), claim-conditional записи через `stillClaimed` (по `_id`+`stepRunStatus`, **не** по індексу), lowercase `ExecutionStatus.name()` у літералах. Цикл-guard `size+1` (який припускав монотонно зростаючий індекс) замінюємо на **ліміт кроків за тік** (`app.funnel.max-steps-per-tick`, дефолт 100 — Decision 4), бо ребра графа не монотонні (кнопка може вести назад на меню).

Передумова: Task 1 уже додав у `FunnelStep` поля `id`/`next`/`buttons`/`timeout*`, у `FunnelExecution` — `currentStepId`/`lastButtonClicked`, статус `ExecutionStatus.waiting_for_reply`, `StepType.MENU` та backfill `id`. Task 2 уже додав **новий 6-арг overload** `TelegramSender.sendText(botId, chatId, text, parseMode, ownerId, replyMarkup)` (reply_markup тіло only-if-non-null) і `answerCallbackQuery`. Існуючий 5-арг overload (`..., ownerId`) лишається без змін. Ця таска **використовує** ці примітиви; `advanceOnCallback` (резолв бота/підписника/кнопки + аудит-подія) — це Task 5, який делегує в наш `resumeOnCallback`.

## What to do

1. **Граф-навігація в `FunnelExecutionEngine.runExecution`:**
   - Резолв поточного кроку по `currentStepId` через новий helper `stepById(snapshot, id)` замість `snapshot.get(currentStepIndex)`.
   - **Fallback на `currentStepIndex`** коли `currentStepId == null` (дренаж лінійних Ф1-runs, у яких backfill не встиг проставити курсор) — Decision 7.
   - Просування не-`MENU` кроку: `currentStepId = step.next`, а якщо `next == null` — наступний крок у списку снапшоту (default-`next`). Кінець графа (немає наступного) → `complete`.
   - `currentStepIndex` лишаємо як вторинне поле (тримати приблизно синхронним для логів/дренажу), джерело істини — `currentStepId`.
2. **Ліміт кроків за тік:** замінити `int guard = size + 1` на `@Value("${app.funnel.max-steps-per-tick:100}")` поле. При вичерпанні ліміту, коли `status==running` і курсор **не** в кінці графа → `terminate(failed)` з новим греппабельним лог-маркером `LOG_STEP_BUDGET_EXCEEDED = "FUNNEL_STEP_BUDGET_EXCEEDED"`.
3. **`MENU`-вихід (park-on-reply):** новий `StepExecutor` outcome для `StepType.MENU` — надіслати текст меню через **НОВИЙ 6-арг overload** `sender.sendText(botId, chatId, text, parseMode, ownerId, replyMarkup)`, який додає Task 2 (рендер `reply_markup` з кнопок кроку, `VariableTemplateRenderer` для тексту під `parse_mode`, як у `SEND_MESSAGE`), потім повернути результат, який рушій застосовує як park: `status=waiting_for_reply`, `currentStepId` лишається на `MENU`-кроці, `stepRunStatus=pending` (щоб callback/sweep могли re-claim), `nextRunAt` = дедлайн таймауту (`now + timeoutValue/timeoutUnit`) або `null` (чекати необмежено). Додати новий `StepExecutor.Outcome.WAIT_FOR_REPLY` + `StepResult` фабрику з опційним `Instant nextRunAt`.
   - **`callback_data` — ДРОТЯНИЙ КОНТРАКТ із Task 5 (Decision 6):** при рендері `reply_markup` КОЖНА callback-кнопка отримує `callback_data = execution.getId() + ":" + buttonIndex`, де `buttonIndex` — 0-based позиція кнопки у `step.getButtons()` (`{executionId}:0`, `{executionId}:1`, …). Це ObjectId-hex execution id + рівно ОДИН роздільник `:` + індекс кнопки. URL-кнопки несуть поле `url` (НЕ `callback_data`). Цей формат мусить точно збігтися зі строгим парсером Task 5 (`advanceOnCallback`), який очікує РІВНО `"{executionId}:{buttonIndex}"` (рівно один `:`, ObjectId-hex shape, bounded index) — будь-яке відхилення тут робить кожен реальний натиск кнопки тихо відхиленим. Cross-ref Decision 6 у [decisions.md](../decisions.md).
   - **УВАГА (реальний код):** поточний 5-арг `sendText(botId, chatId, text, parseMode, ownerId)` має 5-й параметр = **`ownerId`**, а НЕ `reply_markup` (підтверджено в `TelegramSender.java:128`). Існуючий не-`MENU` send-шлях (`SEND_MESSAGE`/`SEND_IMAGE`) лишається на 5-арг формі (passing `null` ownerId, як зараз у `StepExecutor.sendMessage`). `reply_markup` додається ВИКЛЮЧНО через новий 6-арг overload з Task 2.
4. **Seed `currentStepId`** першого кроку в `FunnelTriggerServiceImpl.insertExecution`: після `setStepsSnapshot(...)` виставити `execution.setCurrentStepId(<id першого кроку снапшоту>)` (null-safe для порожнього снапшоту).
5. **`resumeOnCallback(executionId, subscriberId, targetStepId)`** — нова публічна точка входу в `FunnelExecutionEngine`:
   - claim-CAS **scoped по `subscriberId`** (Decision 6, anti-IDOR): предикат `_id == executionId AND subscriberId == subscriberId AND status==waiting_for_reply AND stepRunStatus==pending`, flip → `status=running`, `currentStepId=targetStepId` (або маркер «End»→ завершення), `stepRunStatus=in_progress`.
   - якщо CAS no-op (null) → тихий no-op (подвійний клік / стейл / чужий execution / уже не паркований) — повертаємо ознаку «не зрушило» для виклику `answerCallbackQuery` у Task 5.
   - після успішного claim — той самий step-loop, що й `runExecution` (виділити спільний приватний метод, напр. `drive(exec, now)`), щоб гілка обраної кнопки виконалась лінійно далі. **Без paused-gate** (Decision 11) — in-flight `waiting_for_reply` дограє навіть на paused-воронці.
   - pre-step гейти (subscriber ACTIVE + bot CONNECTED) застосовуються так само, як у `runExecution`.
6. **Таймаут-resume-гілка** у delay-resume seam: коли sweep claim-ить `waiting_for_reply` (а не `waiting`), просування веде по `timeoutTargetStepId` кроку-меню; `timeoutTargetStepId == null` → `complete`. Реюз наявного sweep: меню без таймауту з `nextRunAt=null` природно не матчить предикат `nextRunAt <= now`.
   - **$in-сайти — НЕ ця таска (Task 1, wave 1):** додавання літерала `waiting_for_reply` у `$in`-масиви sweep/claim (та решту cancel/re-enter-сайтів) ВЖЕ зробив Task 1 у wave 1. Task 3 **НЕ** ре-вставляє цей статус-літерал у `$in` рушія. Task 3 лише **верифікує grep-ом**, що `waiting_for_reply` присутній у sweep/claim `$in`-масивах `FunnelExecutionEngine` (передумова для timeout-resume), і фокусується на граф-навігації / MENU-park / resume-логіці. Якщо grep показує, що літерал відсутній — це баг Task 1, ескалювати, а НЕ латати тут.
   - **Порядок seam (реальний код):** наявний delay-resume у `runExecution` робить `currentStepIndex+1` + `status=running` для `waiting` (рядки 128-131) **ПЕРЕД** subscriber-ACTIVE і bot-CONNECTED гейтами (рядки 133-146). Таймаут-resume-гілка для `waiting_for_reply` МУСИТЬ дотримати ТОЙ САМИЙ pre-gate порядок, що й delay-resume seam (ті самі at-most-once-наслідки: курсор просунутий до гейтів, тож inactive-subscriber/disconnected-bot termin-ить уже на новій позиції). Відмінність лише в навігації: delay-seam робить index-`+1`, а timeout-seam ставить `currentStepId = timeoutTargetStepId` (або `complete` коли `null`) — БЕЗ авто-index-`+1`.
   - **`resumeOnCallback` (callback-resume) НЕ переюзає delay-resume авто-`+1` логіку** — це окрема точка входу зі своїм claim-CAS (scoped по `subscriberId`), яка ставить `currentStepId = targetStepId` напряму. Зробити це явним у `drive(exec, now)`: спільний step-loop НЕ містить delay/timeout-seam auto-advance — той auto-advance лишається у callers (`runExecution` робить delay-`+1` / timeout-`targetStepId` ПЕРЕД викликом `drive`; `resumeOnCallback` ставить `targetStepId` ПЕРЕД викликом `drive`).
7. **`app.funnel.max-steps-per-tick`** у `application.properties` з дефолтом 100 і env-override (за зразком наявних `app.funnel.*`).
8. **Тести** (див. TDD Anchor) у `FunnelExecutionEngineIT` (Testcontainers + MutableClock + MockWebServer) і `FunnelStepExecutorTest`.

## Acceptance Criteria

- [ ] `runExecution` резолвить крок по `currentStepId` через `stepById`; fallback на `currentStepIndex` коли `currentStepId==null` (лінійний Ф1-run дограє).
- [ ] Не-`MENU` крок просувається по `step.next` (дефолт — наступний у списку); кінець графа → `completed`.
- [ ] `MENU`-крок надсилає меню з `reply_markup` і паркується: `status=waiting_for_reply`, `currentStepId` на меню, `stepRunStatus=pending`, `nextRunAt`=дедлайн|null.
- [ ] Кожна callback-кнопка меню несе `callback_data = "{executionId}:{buttonIndex}"` (0-based, ObjectId-hex + рівно один `:`); URL-кнопка несе `url` без `callback_data` — дротяний контракт із парсером Task 5 (Decision 6), покрито `menu_callbackButtons_encodeCorrectCallbackData`.
- [ ] `FunnelTriggerServiceImpl.insertExecution` seed-ить `currentStepId` першого кроку снапшоту.
- [ ] `resumeOnCallback` робить claim-CAS scoped по `subscriberId` (anti-IDOR): чужий `subscriberId` → no-op; подвійний клік → один раз; стейл/уже-не-waiting → no-op.
- [ ] `resumeOnCallback` НЕ містить paused-gate (Decision 11) — in-flight дограє на paused-воронці.
- [ ] Ліміт `app.funnel.max-steps-per-tick` (дефолт 100): петля без park → `terminate(failed)` + лог-маркер `FUNNEL_STEP_BUDGET_EXCEEDED`.
- [ ] Таймаут-resume веде по `timeoutTargetStepId`; `null` → `completed`. Меню без таймауту (`nextRunAt=null`) sweep ніколи не рухає.
- [ ] at-most-once-інваріант збережений: claim-CAS і `stillClaimed`-записи по `_id`+`stepRunStatus`, lowercase `.name()` літерали; немає регресій у ITs Ф1.
- [ ] Усі нові unit + ITs зелені; тести Ф1 не зламані.

Додавання компонента (`Instant nextRunAt`) міняє канонічний конструктор і **ламає всі `new StepResult(...)` виклики** — наразі 4 внутрішні фабрики (`cont`/`delay`/`cancel`/`fail`, рядки 238/242/246/250). Перед зміною: `grep -n "new StepResult(" backend/src` і оновити кожен call-site (додати `null` для `nextRunAt`), АБО лишити канонічний `new StepResult(...)` приватним і завести статичні фабрики, що заповнюють дефолти. Назви `Instant nextRunAt`/`Outcome.WAIT_FOR_REPLY`/`StepResult.waitForReply(...)` — рекомендовані, не обов'язкові.
  - **`timeoutUnit` — конфлікт форматів (реальний код vs tech-spec):** tech-spec Data Models декларує `timeoutUnit ∈ {"minutes","hours","days"}`, але існуючий `delayUnit` у `delayDuration()` (рядки 218-226) використовує `{"MIN","HOUR","DAY"}`. **НЕ можна скопіювати `delayDuration` дослівно** — рядки одиниць різні. Імплементатор МУСИТЬ розв'язати конфлікт явно: (a) РЕКОМЕНДОВАНО — переюзати наявну конвенцію `{"MIN","HOUR","DAY"}` і для `timeoutUnit` (консистентність із `delayUnit`, спільний switch), АБО (b) додати явний маппінг `minutes→MIN` тощо. Обраний варіант ЗАПИСАТИ в `decisions.md`. НЕ припускати мовчки рядки tech-spec.
- `FunnelTriggerServiceImpl.java` — у `insertExecution`: після `setStepsSnapshot(snapshot)` виставити `setCurrentStepId(snapshot.isEmpty() ? null : snapshot.get(0).getId())`. Лишити `setCurrentStepIndex(0)` для дренаж-сумісності.
- `application.properties` — додати під `# Funnel engine`: `app.funnel.max-steps-per-tick=${FUNNEL_MAX_STEPS_PER_TICK:100}` з коментарем (дефолт 100 > максимум 50 кроків воронки, тож легітимна лінійка не тригерить — Decision 4).
- `FunnelExecutionEngineIT.java` / `FunnelStepExecutorTest.java` — нові тести з TDD Anchor.

**Dependencies:**
- Task 1 (граф-поля, статус `waiting_for_reply`, `StepType.MENU`, backfill) і Task 2 (`sendText` reply_markup, `answerCallbackQuery`) — мають бути змерджені перед стартом.
- `advanceOnCallback` (резолв бота/підписника/кнопки, аудит-подія `funnel_button_clicked`, виклик `answerCallbackQuery`) — НЕ тут, це Task 5; він викличе наш `resumeOnCallback`.

**Edge cases:**
- `currentStepId` вказує на крок, якого немає в снапшоті (битий курсор після backfill-аномалії) → `terminate(failed)` з маркером (не NPE).
- Порожній снапшот → `complete` одразу.
- `next` вказує на неіснуючий `id` → null-резолв курсора → `failed`+маркер (граф валідовано на activate у Task 4, але рушій має fail-safe).
- Resume на execution, що вже `completed`/`cancelled` → claim-CAS no-op (статус не `waiting_for_reply`).
- Таймаут спрацював одночасно з callback → claim-CAS (перший виграє); другий шлях бачить уже не `waiting_for_reply` → no-op.
- `MENU` без таймауту: `nextRunAt=null` — sweep-предикат `nextRunAt <= now` ніколи не матчить (без окремого виключення зі sweep).

**Implementation hints:**
- НЕ додавати paused-gate у `resumeOnCallback`/step-loop (Decision 11) — pause блокує лише старт нових executions на trigger, in-flight дограють.
- НЕ переюзати delay-resume авто-`+1` для callback-resume — це окрема точка входу зі своїм claim-CAS (Decision 3/6). callback ставить `currentStepId=targetStepId` напряму; delay робить index-`+1`; timeout ставить `timeoutTargetStepId`. Спільний `drive(exec, now)` step-loop НЕ містить жодного resume-auto-advance — кожен caller робить своє просування ПЕРЕД викликом `drive`.
- **Pre-gate ордерінг seam (реальний код, рядки 128-146):** delay-resume у `runExecution` просуває курсор ПЕРЕД subscriber/bot гейтами. Timeout-resume гілка (`waiting_for_reply` через sweep) МУСИТЬ дотримати той самий порядок (просування → потім гейти), щоб at-most-once-семантика збіглася з delay-seam. Не переставляти гейти перед просуванням лише для timeout-гілки.
- **`StepResult` record extension (реальний код):** додавання `Instant nextRunAt` міняє канонічний конструктор record-а й ламає всі 4 наявні `new StepResult(...)` фабрики. `grep -n "new StepResult(" backend/src` і оновити кожен (додати `null`) АБО лишити канонічний конструктор приватним зі статичними фабриками-дефолтами.
- Зберегти спостережуваність Decision 16: логи несуть лише ids/коди, без рендереного тексту/`callback_data`-payload/PII.
- `stepById` — лінійний пошук по снапшоту (списки кроків малі, ≤50); кешувати не треба.
- `MENU`-park пише стан через `stillClaimed`-CAS (як `scheduleDelay`): `status=waiting_for_reply`, `stepRunStatus=pending`, `currentStepId` без зміни, `nextRunAt`=дедлайн|null. Якщо CAS no-op (concurrent cancel) — тихий лог-no-op, як решта seam-ів.
- Детермінованість ITs: рухати час через `MutableClock` (за зразком наявних delay/timeout ITs Ф1), не реальний sleep; sweep викликається прямо (`engine.sweep()`).
