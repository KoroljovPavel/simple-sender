# Task 5: FunnelTriggerService.advanceOnCallback + аналітика-хук

## Required Skills

Перед виконанням задачі завантаж:

## Description

Це остання серверна ланка callback-шляху Фази 2: точка входу, яку викликає webhook-воркер (Task 7), коли підписник тисне inline-кнопку. Рушій (Task 3) уже вміє паркувати execution на `MENU` у статус `waiting_for_reply` і резюмити його через `resumeOnCallback(executionId, subscriberId, targetStepId)` під claim-CAS, scoped по `subscriberId`. TelegramSender (Task 2) уже має `answerCallbackQuery(...)`. Цей таск зшиває їх у новий публічний метод `advanceOnCallback(projectId, chatId, callbackData, callbackQueryId)` на `FunnelTriggerService` (інтерфейс + impl).

Метод: резолвить CONNECTED-бота проєкту → підписника по `(projectId, telegramBotId, chatId)` → завантажує припарковане execution за `executionId` із `callbackData`; строго парсить `callback_data` формату `"{executionId}:{buttonIndex}"`; проводить авторизацію власника (anti-IDOR, Decision 6): `exec.subscriberId` та `exec.projectId` мусять збігатися з резолвленим підписником/проєктом, інакше — тихий no-op; вимагає `status==waiting_for_reply` на поточному `MENU` (резолв по `currentStepId`); матчить callback-кнопку за індексом → її `targetStepId` (або `null`=End) → делегує в `resumeOnCallback`. `answerCallbackQuery` викликається **ЗАВЖДИ** (включно з усіма no-op-шляхами: null-lookup / стейл / malformed / oversized / чужий execution) в окремому try/catch, best-effort (Decision 8) — щоб спіннер у підписника гарантовано зник, навіть коли просування не відбувається. На успішне просування записується подія `funnel_button_clicked` через наявний `EventService` + поле `lastButtonClicked` на execution (лише ids/коди, без PII — Decision 9).

Уся реалізація — у `try/catch(Throwable)` swallow, як і `fire()` / `cancelActiveFor()` (метод НІКОЛИ не кидає назовні: callback-фолт не повинен отруїти webhook-dispatch). Результат: натиск кнопки атомарно просуває правильну гілку **лише власника**, подія записана, спіннер прибрано на всіх шляхах.

## What to do

1. Додати метод `advanceOnCallback(String projectId, Long chatId, String callbackData, String callbackQueryId)` у інтерфейс `FunnelTriggerService` з Javadoc-контрактом (best-effort, error-isolated, anti-IDOR, answerCallbackQuery-always).
2. Реалізувати його у `FunnelTriggerServiceImpl`. Уся бізнес-логіка — всередині зовнішнього `try/catch(Throwable)`, що логує greppable-маркер і ковтає (метод не throws назовні).
3. Резолв CONNECTED-бота проєкту (як у `fire()`); якщо немає — best-effort `answerCallbackQuery` неможливий (нема `botId`), тихий no-op + лог. Якщо бот є — резолвити підписника через `subscriberService.findByChat(projectId, telegramBotId, chatId)`.
4. Строгий парс `callback_data` у окремому helper: рівно один `:`-роздільник; ліва частина — 24-символьний ObjectId-hex (перевірка форми ДО будь-якого DB-lookup); права — невідʼємне ціле в межах (`0..7` / `< buttons.size()`). Malformed/oversized/зайві сегменти → reject (no advance), але `answerCallbackQuery` все одно викликається.
5. Завантажити execution за `executionId`; вимагати `status==waiting_for_reply`. null / інший статус → no-op.
6. **Авторизація власника (anti-IDOR, Decision 6):** `exec.getSubscriberId().equals(resolvedSubscriber.id)` AND `exec.getProjectId().equals(projectId)`. Mismatch → тихий no-op (виконання чужого підписника не зрушити). Покластися також на scope-по-`subscriberId` у `resumeOnCallback` як CAS-рівень захисту.
7. Резолв поточного `MENU` по `exec.getCurrentStepId()` у `stepsSnapshot` (helper із Task 3 / lookup); перевірити, що крок існує і це `MENU`. Витягти кнопку за `buttonIndex`; перевірити, що це callback-тип (URL-кнопка → no-op, воронка не рушить — Decision 10).
8. Делегувати `resumeOnCallback(executionId, subscriberId, targetStepId)` (де `targetStepId` = `button.targetStepId()`, `null`=End). **ДО кодування підтвердь фактичну сигнатуру/тип повернення `resumeOnCallback(executionId, subscriberId, targetStepId)` із звіту Task 3 у decisions.md або реального коду рушія (`FunnelExecutionEngine`) — не припускай.** Лише при успіху claim — записати подію `funnel_button_clicked` через `EventService.logEvent(...)` (metadata: `funnelId`, `executionId`, `currentStepId`/крок, `buttonIndex` — лише ids/коди, БЕЗ `from.first_name`/`username`/тексту) і виставити `lastButtonClicked` на execution.
9. `answerCallbackQuery(botId, callbackQueryId, null)` — викликати **ЗАВЖДИ** в окремому внутрішньому try/catch (best-effort, WARN-лог при збої, без аудит-події — Decision 8), на ВСІХ шляхах виходу (успіх, стейл, malformed, чужий, URL-кнопка, null-lookup), коли `botId` відомий.
10. Написати engine-IT-кейси у `FunnelExecutionEngineIT` (Testcontainers Mongo + MockWebServer + MutableClock, за наявним зразком): успішний клік (просування + подія + lastButtonClicked), IDOR (чужий executionId → no-op), стейл/`completed`/`cancelled` → no-op, подвійний клік (claim-CAS, другий програє), out-of-range / URL-кнопка / malformed / oversized callback_data → no-op + answerCallbackQuery викликано, `currentStepId`-mismatch → no-op, answerCallbackQuery 5xx → просування не блокується, paused-drain.

Слідувати наявному стилю: lowercase `ExecutionStatus.name()` у Mongo-критеріях, логування лише ids/кодів (Decision 16 Ф1 / Decision 9 Ф2).

**Edge cases:**
- CONNECTED-бот не резолвиться → нема `botId` → тихий no-op (навіть answerCallbackQuery неможливий); лог.
- Підписник не знайдений → no-op, але `answerCallbackQuery` викликається (botId є).
- `callback_data`: відсутній `:`, кілька `:`, non-hex / не-24-символьний executionId, негативний/нечисловий/out-of-range index, oversized (>64 байти) → reject до DB, no-op + answerCallbackQuery.
- execution null / `running` / `waiting` / `completed` / `cancelled` (не `waiting_for_reply`) → no-op.
- IDOR: `exec.subscriberId != resolvedSubscriber.id` або `exec.projectId != projectId` → no-op, чуже виконання не чіпається.
- `currentStepId` вказує не на `MENU` або execution уже пройшов цей крок → no-op.
- Кнопка за індексом — URL-типу → no-op (Decision 10: URL не рушить воронку).
- Подвійний клік: `resumeOnCallback` claim-CAS — перший виграє, другий програє → одне просування, одна подія.
- `answerCallbackQuery` 5xx → best-effort, просування не блокується (WARN, без аудит-події — Decision 8).
- Paused-воронка: НЕ додавати paused-gate у resume-шлях (Decision 11) — in-flight `waiting_for_reply` дограє.

**Implementation hints:**
- Дзеркаль структуру `fire()`: зовнішній `try/catch(Throwable)` + ранні `return` на кожному no-op-шляху, greppable LOG_*-константи.
- Виокреми парс `callback_data` у статичний private helper, що повертає тип-результат (executionId + buttonIndex) або сигнал reject; перевіряй ObjectId-hex форму регуляркою/`ObjectId.isValid` ДО DB.
- Винеси `answerCallbackQuery`-виклик у приватний best-effort helper із власним try/catch(WARN), щоб гарантовано викликати на всіх гілках (наприклад через єдину точку перед return або finally-семантику — обери варіант, що не пропускає жодного шляху).
- Подію `funnel_button_clicked` пиши лише ПІСЛЯ успішного claim у `resumeOnCallback` (щоб подвійний клік не дублював подію); metadata — Map лише з ids/кодів.
- Для IT-MockWebServer: dispatcher має відповідати на `/answerCallbackQuery` (200/5xx за кейсом) і на перший send у гілці після resume.
