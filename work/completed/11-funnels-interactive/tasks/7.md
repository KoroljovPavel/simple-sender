# Task 7: Webhook — інжест callback_query

## Required Skills

Перед виконанням задачі завантаж:
- `/skill:code-writing` — [skills/code-writing/SKILL.md](.claude/skills/code-writing/SKILL.md)

## Description

Замикаючий бекенд-вузол Фази 2: довести `callback_query` від Telegram-webhook до рушія воронок.
Сьогодні `ProcessTelegramUpdateJob.dispatch(...)` обробляє лише `message`-апдейти, а `callback_query`
лежить опаковим `JsonNode`-слотом у `TelegramUpdate` і класифікується як `telegram_update_other`
(див. `resolveUpdateKind`). Коли підписник тисне inline-кнопку меню (`MENU`-крок, Фаза 2), Telegram
POSTить `callback_query` — його треба розпарсити в типізований DTO, резолвити CONNECTED-бота проєкту,
витягти `chatId` + `callback_data` і викликати `funnelTriggerService.advanceOnCallback(projectId,
chatId, callbackData, callbackQueryId)` (доданий у Task 5), щоб рушій просунув припарковане виконання
у гілку обраної кнопки.

Критично зберегти три інваріанти Фази 1, на яких тримається коректність воркера (див. шапку
`ProcessTelegramUpdateJob`): (1) re-entry guard (`processingStatus == DONE` → return до будь-якого
side-effect); (2) event-before-flip — подія `telegram_callback_query` мусить дописатися в `events` ДО
того, як `processingStatus` стає `DONE`; (3) error-isolation — виклик з воркера має лишатися в межах
наявного `try/catch(Throwable)` → `handleFailure` (FAILED + scrubbed/truncated + rethrow для
JobRunr-retry). Сам `advanceOnCallback` у Task 5 — best-effort swallow-all, тож best-effort провал
просування не валить воркер.

Подія `telegram_callback_query` несе **лише ids/коди** (`projectId`, `chatId`, опційно усічений маркер
`data`) — БЕЗ PII (`from.first_name`/`username`), за Decision 9.

## What to do

1. Створити типізований DTO `webhook/dto/CallbackQuery.java` — record `(String id, User from,
   Message message, String data)` з `@JsonIgnoreProperties(ignoreUnknown = true)` (mass-assignment
   defense, як решта DTO модуля). `message` потрібен, щоб дістати `chat().id()`; `id` =
   callbackQueryId; `data` = `callback_data` кнопки.
2. У `webhook/dto/TelegramUpdate.java` замінити опаковий слот `JsonNode callback_query` на типізований
   `CallbackQuery callback_query`. Звірити, що це не ламає `resolveUpdateKind` у
   `ProcessTelegramUpdateJob` (там слот читається як `JsonNode` через `!n.isNull()`) — перевести цю
   гілку на null-перевірку типізованого record.
3. У `ProcessTelegramUpdateJob.dispatch(...)` додати гілку `if (update.callback_query() != null)`
   **перед** message-fallback (`if (message == null) {...}`): резолвити CONNECTED-бота проєкту (як у
   `handleStart`/`handleStop`); якщо бот == null → деградувати у `telegram_update_other` (узгодити
   updateKind з наявним bot-missing патерном); інакше екстракт `chatId` (з
   `callback_query.message().chat().id()`) + `callback_data`; виклик
   `funnelTriggerService.advanceOnCallback(projectId, chatId, data, callbackQueryId)`; потім подія
   `telegram_callback_query` (ДО return — тобто ДО status-flip у `handle`).
4. Додати константу `EVT_CALLBACK_QUERY = "telegram_callback_query"` і метод-логер
   `logEventCallbackQuery(projectId, userId, chatId, dataMarker)` — метадані лише `projectId`, `chatId`,
   і опційно усічений/санітизований `data`-маркер (без PII).
5. Зберегти error-isolation: гілка callback виконується в межах наявного `try` у `handle(...)`; не
   додавати окремий локальний swallow, що ховав би справжній воркер-failure-шлях.
6. Написати/розширити `ProcessTelegramUpdateJobTest`: інжест `callback_query` → `advanceOnCallback`
   викликано з правильними аргументами; подія `telegram_callback_query` записана; event-before-flip
   інваріант (sentinel-підхід, як у наявному `eventWriteBeforeStatusFlip_orderingInvariant`); re-entry
   guard (DONE → no-op) для callback-апдейту; bot-missing деградація; подія без PII.
7. **Прибрати регресію в наявному параметризованому тесті.** Метод `jsonNodeSlots()` (рядок ~349-350,
   `@MethodSource` для `nonMessageJsonNodeSlot_writesUpdateOther_noStubs`) включає `"callback_query"`.
   Після того як `TelegramUpdate.callback_query` стає типізованим `CallbackQuery` (а не `JsonNode`),
   `slotPayload("callback_query")` дасть non-null typed record → `dispatch()` піде в нову callback-гілку
   (а оскільки `cleanAndSeed()` сідить CONNECTED-бота, викличеться `advanceOnCallback`), і assert на
   `telegram_update_other` зламається. **Видалити `"callback_query"` зі стріму `jsonNodeSlots()`** —
   callback_query тепер типізована dispatch-гілка, а не "other"-слот. Решта слотів стріму
   (`my_chat_member`, `chat_member`, …) лишаються.

## Acceptance Criteria

- [ ] `CallbackQuery` DTO створено (`@JsonIgnoreProperties(ignoreUnknown=true)`, record, типізований).
- [ ] `TelegramUpdate.callback_query` — типізований `CallbackQuery` (не `JsonNode`); `resolveUpdateKind`

- [ ] `dispatch(...)` має гілку `callback_query` ПЕРЕД message-fallback; резолвить CONNECTED-бота,

- [ ] Подія несе лише ids/коди — без PII (`from.first_name`/`username`).
- [ ] Re-entry guard / idempotency Фази 1 збережені для callback-апдейту (DONE → no-op).
- [ ] `advanceOnCallback` викликається в error-isolated шляху (наявний `try/catch(Throwable)`); воркер
      не ламається через best-effort провал просування.

      `nonMessageJsonNodeSlot_writesUpdateOther_noStubs`) — набір `telegram_update_other` non-message
      тестів більше не включає callback_query (тепер це типізована dispatch-гілка).
- [ ] Усі тести `ProcessTelegramUpdateJobTest` зелені; немає регресій у наявних message-тестах
      (зокрема параметризований `nonMessageJsonNodeSlot_writesUpdateOther_noStubs` зелений після
      видалення `callback_query` зі стріму).

## Details

**Files:**
- `webhook/dto/CallbackQuery.java` (new) — `record CallbackQuery(String id, User from, Message message,
  String data)` + `@JsonIgnoreProperties(ignoreUnknown=true)`. `id` = Telegram callbackQueryId
  (рядок), потрібен для `answerCallbackQuery` усередині `advanceOnCallback`. `data` = `callback_data`
  кнопки (`"{executionId}:{buttonIndex}"`, Decision 6). Javadoc у стилі решти DTO модуля.
- `webhook/dto/TelegramUpdate.java` — наразі `JsonNode callback_query` (рядок 23). Замінити на
  `CallbackQuery callback_query`. Решта `JsonNode`-слотів (my_chat_member, chat_member, …) лишаються
  опаковими — їх Фаза 2 не чіпає.
- `webhook/ProcessTelegramUpdateJob.java`:
  - `resolveUpdateKind` (рядок 297) читає `update.callback_query()` як `JsonNode` через `!n.isNull()`.
    Перевести на null-перевірку типізованого record: `if (update.callback_query() != null) return
    "callback_query";`.
  - `dispatch(...)` (рядок 146) — додати callback-гілку ПЕРЕД `Message message = update.message();
    if (message == null)`. Резолв CONNECTED-бота через
    `botRepository.findByProjectIdAndStatus(projectId, BotStatus.CONNECTED)` (як `handleStart` рядок
    208). chatId = `cq.message() != null && cq.message().chat() != null ? cq.message().chat().id() :
    null`. callbackQueryId = `cq.id()`. data = `cq.data()`. Виклик
    `funnelTriggerService.advanceOnCallback(projectId, chatId, data, callbackQueryId)` потім
    `logEventCallbackQuery(...)`.
  - Нова константа `EVT_CALLBACK_QUERY = "telegram_callback_query"` поряд з рештою EVT_* (рядки 41-44).
  - `logEventCallbackQuery(projectId, userId, chatId, dataMarker)` — `LinkedHashMap` (дозволяє null),
    `projectId`+`chatId`(+опц. усічений `data`); `eventService.logEvent(userId, EVT_CALLBACK_QUERY,
    null, null, metadata)`. Без `from.*`.
- `ProcessTelegramUpdateJobTest.java` — додати `callbackQueryPayload(chatId, fromId, data,
  callbackQueryId)`-хелпер у стилі наявних `messagePayload`/`slotPayload` (Document із
  `callback_query.{id, from, message:{chat:{id,type}}, data}`). Звернути увагу: `funnelTriggerService`
  тут `@MockitoSpyBean` no-op — `advanceOnCallback` теж стане no-op-стабом у Task 5; assert через
  `verify(funnelTriggerService, times(1)).advanceOnCallback(...)`.
  **Регресія:** прибрати `"callback_query"` зі стріму `jsonNodeSlots()` (рядок ~349-350). Після зміни
  `TelegramUpdate.callback_query` на типізований record `slotPayload("callback_query")` віддасть
  non-null → `dispatch()` піде в callback-гілку (CONNECTED-бот сіднутий у `cleanAndSeed()` → виклик
  `advanceOnCallback`), і assert `telegram_update_other` зламається. callback_query тепер окрема
  типізована гілка, а не "other"-слот.

**Dependencies:** Task 5 (`FunnelTriggerService.advanceOnCallback(projectId, chatId, callbackData,
callbackQueryId)` — інтерфейс + no-op-стаб для тестів). Підтвердити точну сигнатуру з
`FunnelTriggerService.java` після Task 5 (зчитати перед написанням). Якщо порядок/типи аргументів інші
— узгодити виклик і тест-verify.

**Edge cases:**
- `callback_query.message` == null (рідкісно: inline-message без chat) → chatId null; `advanceOnCallback`
  отримує null chatId і no-op-ить (Task 5 swallow-all) — подія все одно пишеться з chatId=null.
- bot == null (race з disconnect) → деградувати у `telegram_update_other`, НЕ викликати
  `advanceOnCallback` (узгодити з bot-missing патерном `handleStart`).
- DONE re-entry → return до будь-якого виклику (наявний guard, рядок 88).
- `data` null/порожній → передати як є; парс/валідація — відповідальність `advanceOnCallback` (Task 5),
  не воркера.

**Implementation hints:**
- Гілка callback іде ПЕРЕД `if (message == null)`, бо `callback_query` апдейт має `message==null` на
  верхньому рівні `update` — інакше потрапить у `logEventOther` як раніше.
- Event-before-flip тримається автоматично, якщо логувати подію всередині `dispatch` (який
  викликається у `handle` ДО `setProcessingStatus(DONE)` рядок 104). Не виносити логування після flip.
- НЕ класти `from.first_name`/`username` у метадані події (Decision 9 — без PII).
- `advanceOnCallback` у Task 5 — swallow-all best-effort; не загортати його у додатковий локальний
  try/catch, що ховав би справжні воркер-failures (порушило б error-isolation-контракт).
