# Task 8: Code Audit

## Required Skills

Перед виконанням задачі завантаж:
- `/skill:code-reviewing` — [SKILL.md](../../../.claude/skills/code-reviewing/SKILL.md)

## Description

Холістичний аудит якості коду всієї фічі `11-funnels-interactive` (Фаза 2 воронок:
інтерактив + inline-клавіатури). Задачі 1–7 реалізували граф-модель воронки (`currentStepId`
+ `next` + цілі кнопок), новий композитний крок `MENU` з park-on-reply, callback-пробудження
(`advanceOnCallback` / `resumeOnCallback`), таймаут-resume через sweep, валідацію графа,
backfill `id`, фронтенд-редактор `MENU` і webhook-інжест `callback_query`.

Це задача-аудит: не пишемо й не правимо код — читаємо ВСІ файли, створені/змінені в цій фічі,
і оцінюємо їх **разом**, шукаючи саме кросс-компонентні проблеми, які не видно при перегляді
однієї задачі/одного PR: дубльована ініціалізація ресурсів, порушення контракту shared
resources із розділу Architecture, архітектурна неузгодженість інваріантів (граф-навігація,
claim-CAS at-most-once, snapshot-ізоляція). Аудитор САМ є рев'ю — окремих рев'юерів немає.
Результат — звіт аудиту (JSON-файндинги), який споживає батьківський агент.

## What to do

1. Зібрати повний перелік джерельних файлів фічі: усі `Files to modify` з Implementation Tasks
   1–7 у [tech-spec.md](../tech-spec.md) плюс файли, згадані як `(new)`, плюс будь-які файли,
   зафіксовані у [decisions.md](../decisions.md) як фактично змінені/додані (включно з
   відхиленнями від спека). Розбіжність «спек vs decisions» сама по собі є файндингом.
2. Прочитати кожен файл і скласти ментальну карту фічі: де живе граф-навігація, де claim-CAS,
   де snapshot-ізоляція, де ініціалізуються/споживаються shared resources.
3. Провести аудит за дименсіями скіла `code-reviewing`, з фокусом на кросс-компонентне:
   - **Дубльована ініціалізація ресурсів:** `TelegramSender`, `Clock`, `EventService`, JobRunr
     `@Recurring` sweep — переюз існуючих синглтонів, без повторного `new`/нового біна (звірити
     з таблицею Shared resources у tech-spec Architecture).
   - **Compliance shared resources:** споживачі (`StepExecutor`, `FunnelTriggerServiceImpl`,
     engine, webhook) використовують ресурси через оголошених власників, а не обходять їх.
   - **Граф-навігація:** єдина модель курсора `currentStepId` (+ fallback на `currentStepIndex`
     лише для дренажу); `stepById`-резолв консистентний у engine, trigger, validation; немає
     зайвих залишків index-навігації, що конфліктують з графом.
   - **Claim-CAS / at-most-once інваріант:** CAS лишається по `_id` + `stepRunStatus` (не по
     індексу); `resumeOnCallback` scoped по `subscriberId` (anti-IDOR, Decision 6);
     `waiting_for_reply` доданий в УСІ потрібні `$in`-сайти (sweep, claim, cancel-шляхи,
     re-enter index) — жодного пропущеного літерал-сайту; ліміт кроків за тік замість старого
     `guard=size+1`.
   - **Snapshot-ізоляція:** `FunnelStep.copyOf` робить явну глибоку копію `buttons`; `Button` —
     immutable record; редагування воронки під час `waiting_for_reply` не може просочитися в
     in-flight снапшот.
   - **Консистентність контрактів через шари:** `callback_data` білдиться і парситься однаково
     (фронт/`reply_markup` ↔ webhook ↔ trigger); DTO round-trip кнопок/цілей/timeout-полів
     узгоджений між `FunnelStepDto`/`ButtonDto` і доменом; `answerCallbackQuery` викликається на
     ВСІХ no-op-шляхах (включно з null/стейл/malformed/чужий).
   - Загальні дименсії: іменування, обробка помилок/error-isolation, дублювання логіки між
     задачами, мертвий код, dead-параметри, узгодженість логування (греппабельні маркери
     `FUNNEL_STEP_BUDGET_EXCEEDED` тощо).
4. Звірити фактичну реалізацію з Decisions 1–11 tech-spec: будь-яке мовчазне відхилення без
   запису в decisions.md — файндинг.
5. Класифікувати кожен файндинг за severity (blocker / major / minor / nit), з файлом+рядком,
   суттю проблеми і запропонованим фіксом.
6. Записати звіт аудиту у JSON (див. Verification Steps → Audit deliverable).

## Details

**Files:** читання-онлі. Жоден джерельний файл у цій задачі не редагується. Єдиний файл, що
створюється — звіт аудиту `logs/working/task-8/code-audit-1.json`.

**Dependencies:** depends_on [1,2,3,4,5,6,7] — усі реалізаційні задачі мають бути завершені;
їхні звіти й відхилення читай у decisions.md. Це Wave 5 (Audit Wave), паралельно з Task 9
(Security Audit) і Task 10 (Test Audit) — не дублюй їхній скоуп: безпека (OWASP, injection,
mass-assignment, PII, token-scrub) — у Task 9; якість тестів/покриття — у Task 10. Ця задача —
**якість і архітектурна узгодженість продакшн-коду**.

**Edge cases / на що звернути особливу увагу:**
- Пропущений літерал-сайт `waiting_for_reply` у будь-якому `$in` (sweep/claim/cancel/re-enter index) — at-most-once або таймаут зламаються тихо.
- Залишковий старий guard `size+1` або index-навігація, що співіснує з граф-курсором і дає неузгоджену поведінку на петлях/fan-in.
- `copyOf`, що копіює список кнопок поверхнево (shared reference) — діра в snapshot-ізоляції.
- CAS, що скопився по індексу/без `subscriberId`-scope — at-most-once або IDOR-ризик (перетин з Task 9, але архітектурну форму CAS фіксуй тут).
- Дубльована логіка парсу/білду `callback_data` між фронтом, `reply_markup` і webhook/trigger — джерело дрейфу.
- `answerCallbackQuery`, що не викликається на якомусь no-op-шляху — спіннер зависне (контрактна неузгодженість).
- Реалізація, що мовчки розійшлася з Decisions 1–11 без запису в decisions.md.

**Implementation hints:**
- Спирайся на дименсії рев'ю зі скіла `code-reviewing`; звіт структуруй за severity.
- Звіряй фактичний код із таблицею Shared resources і Decisions tech-spec построково — це швидко ловить мовчазні відхилення.
- Не повторюй файндинги, що належать Task 9/10; якщо проблема має і безпековий, і архітектурний бік — згадай коротко й познач, що деталь у Task 9.
