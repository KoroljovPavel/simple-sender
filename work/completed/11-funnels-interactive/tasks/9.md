# Task 9: Security Audit

## Required Skills

Перед выполнением задачи загрузи:

## Description

Це **аудит-задача Audit Wave**: жодного нового коду, жодних ревʼюерів — **сам аудитор і є ревʼю**. Деліверабл — **звіт security-аудиту по всій фічі** `11-funnels-interactive` (Фаза 2 воронок: інтерактив + inline-клавіатури).

Фаза 2 додає нову зовнішню attack-surface: підписник тепер шле `callback_query` на webhook, бот відправляє inline-клавіатури з URL-кнопками, автор задає URL у DTO, рушій просуває припарковані executions по callback. Це торкається парсингу недовіреного `callback_data`, авторизації власника execution (IDOR), валідації URL-схеми (scheme-injection/SSRF), mass-assignment на нових DTO, token-scrub у новому `answerCallbackQuery` та PII у нових подіях. Усе це треба пройти проти **OWASP Top 10** холістично, через усі компоненти фічі (backend funnel/bot/webhook + frontend редактор).

Аудитор читає **всі** source-файли, створені/змінені у Wave 1-4 (Tasks 1-7), реконструює реальний стан з коду (не з опису задач), і перевіряє, що безпекові рішення техспеку (Decisions 6, 9, 10 + Risks) реально реалізовані в коді, а не лише задекларовані. Знайдені проблеми класифікуються за severity (Critical/High/Medium/Low) з конкретним файлом+рядком та запропонованим фіксом.

Особлива увага (з техспеку):
- **IDOR на `callback_data`** (Decision 6): `advanceOnCallback` мусить звіряти `exec.subscriberId == resolvedSubscriber.id && exec.projectId == projectId`; CAS у `resumeOnCallback` мусить бути **scoped по `subscriberId`**. Інакше будь-який легітимний підписник проєкту підробляє `callback_data` з чужим `executionId` і просуває чуже виконання (ObjectId частково передбачуваний — не секрет).
- **URL-scheme injection** (Decision 10): URL-кнопки парсяться строго через `URI`, схема **рівно** `http`|`https` (НЕ `startsWith`), host непорожній; `javascript:`/`data:`/`tg://`/whitespace-обфусковані/empty-host → 422 (SSRF/scheme-injection defense). Перевірити і на бекенді (`FunnelService.validateSteps`), і що фронт не обходить.
- **Mass-assignment на DTO**: `@JsonIgnoreProperties(ignoreUnknown=true)` на `FunnelStepDto`, новому `ButtonDto`, `CallbackQuery` та всіх нових nested webhook-record-ах; жодне owner-bound поле не читається з body.
- **No PII in events** (Decision 9): події `funnel_button_clicked` і `telegram_callback_query` несуть лише ids/коди — **жодних** `from.first_name`/`username`/тексту. Звірити з Decision 16 Ф1.
- **Token-scrub у `answerCallbackQuery`** та усіх нових log-сайтах (Task 2/5/7): кожен WARN/ERROR з payload/upstream-рядком проходить `TelegramApiClient.scrubTokens(...)`; новий `answerCallbackQuery` не leak-ає токен у лог/exception.

## Verification Steps

### Automated
Аудит — статичний аналіз коду; «автоматизація» тут — допоміжні grep-перевірки, що підтверджують/спростовують наявність захисту (не тести):
- `grep -rn "JsonIgnoreProperties" backend/src/main/java/com/botfunnel/funnel/dto/ backend/src/main/java/com/botfunnel/webhook/dto/` → підтвердити whitelist на нових DTO (`ButtonDto`, `FunnelStepDto`, `CallbackQuery`).
- `grep -rn "scrubTokens" backend/src/main/java/com/botfunnel/bot/ backend/src/main/java/com/botfunnel/funnel/ backend/src/main/java/com/botfunnel/webhook/` → перелічити нові log-сайти; звірити, що `answerCallbackQuery`-шлях покритий.
- `grep -rni "first_name\|firstName\|username\|from\.\|\.text" backend/src/main/java/com/botfunnel/funnel/FunnelTriggerServiceImpl.java backend/src/main/java/com/botfunnel/webhook/ProcessTelegramUpdateJob.java` → переконатись, що PII-поля не потрапляють у `logEvent`-metadata подій.
- `grep -rn "subscriberId\|projectId" backend/src/main/java/com/botfunnel/funnel/FunnelTriggerServiceImpl.java backend/src/main/java/com/botfunnel/funnel/FunnelExecutionEngine.java` → підтвердити owner-перевірку в `advanceOnCallback` і scoped-CAS у `resumeOnCallback`.
- `grep -rn "startsWith\|getScheme\|equalsIgnoreCase\|URI" backend/src/main/java/com/botfunnel/funnel/FunnelService.java` → переконатись, що схема перевіряється точним порівнянням, не `startsWith`.
- `grep -rn "v-html" frontend/components/funnels/` → переконатись, що лейбли/текст рендеряться інтерполяцією, не `v-html` (XSS).
- (Опційно) `cd backend && ./gradlew compileJava` для впевненості, що читаний код — у консистентному стані.

**OWASP Top 10 чеклист (адаптовано до фічі):**
- **A01 Broken Access Control / IDOR:** owner-перевірка в `advanceOnCallback` (subscriberId+projectId), scoped-CAS у `resumeOnCallback`, серверна перевірка `currentStepId` (callback на пройдений крок → no-op). Це **головний** ризик фічі (Decision 6, Risks).
- **A03 Injection:** URL-scheme injection (Decision 10 — `javascript:`/`data:`/`tg://`); `callback_data` parse (ObjectId-hex shape до lookup, рівно один `:`, bounded index); відсутність Mongo-query-injection через нерозібраний ввід; frontend XSS (`v-html` vs інтерполяція; `parse_mode`-екранування через `VariableTemplateRenderer`, як Send).
- **A04 Insecure Design:** меню без callback → застрягання (≥1 callback enforced); ліміт кроків за тік (runaway-петля → failed, не нескінченний цикл); best-effort `answerCallbackQuery` не блокує і не leak-ає.
- **A05 Security Misconfiguration:** новий `app.funnel.max-steps-per-tick` дефолт; webhook CSRF-disable scope не розширено; немає нових permissive-роутів.
- **A08 Data Integrity:** mass-assignment defense (`@JsonIgnoreProperties`), snapshot-ізоляція (deep-copy кнопок у `copyOf` — цілісність in-flight execution під час edit).
- **A09 Logging/Monitoring failures:** token-scrub на нових log-сайтах; PII у подіях (Decision 9); греппабельний `FUNNEL_STEP_BUDGET_EXCEEDED` маркер.
- **A07 Auth failures / A02 Crypto:** новий код не обходить AES-GCM decrypt / CONNECTED-фільтр у bot-шляху; `answerCallbackQuery` йде тим самим захищеним патерном, що sendText.

**Dependencies:** залежить від завершення Tasks 1-7 (увесь код фічі має бути написаний). Жодних ревʼюерів — аудит сам є ревʼю; жодного TDD (нічого не пишемо).

**Edge cases для перевірки в коді:**
- `callback_data` рівно 64 байти / 65 байт; зайвий `:`-сегмент; ObjectId-hex з не-hex символом; від'ємний/out-of-range buttonIndex.
- Підписник у двох воронках з меню одночасно — `executionId` має розрізняти; чужий `executionId` того ж проєкту → reject (IDOR).
- URL `" http://..."` (leading whitespace), `HTTP://`, `hTtP://`, `http:///nohost`, `http://`+порожній host.
- Подвійний клік / callback на `completed`/`cancelled` → no-op, але `answerCallbackQuery` все одно викликано (спіннер зник), без leak.
- `answerCallbackQuery` 5xx → WARN-лог scrubbed, гілка не блокується.

**Implementation hints (для аудиту):**
- Читай **реальний** код Tasks 1-7, не опис задач — реалізатори могли відхилитись (дивись Deviations у `decisions.md`).
- Звіряй кожне безпекове твердження техспеку (Decisions 6/9/10 + таблиця Risks) з рядком коду; задеклароване ≠ реалізоване.
- Для PII: дивись не лише поля event-payload, а й що передається у `log.info/warn` навколо callback-шляху.
- Для token-scrub звір повний перелік сайтів у [patterns.md](../../../.claude/skills/project-knowledge/references/patterns.md) (секція send-path/webhook scrubber sites) — новий `answerCallbackQuery` має дотримуватись того ж інваріанту.
- Кросс-шар: фронт-валідація URL — UX, **не** безпека; реальний гейт — бекенд `validateSteps`. Підтвердь, що бекенд не довіряє фронту.
