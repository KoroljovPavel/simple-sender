# Task 1: Funnel domain — new trigger types, keywords, EMIT_EVENT, depth field

## Required Skills

## Description

Phase 3 extends the funnel engine from a single `on_start` trigger to six entry paths
(`on_start`, `keyword`, `tag_added`, `custom_field_set`, `event`) plus an in-funnel `EMIT_EVENT`
step. This task is the **data-layer foundation** every other task in the feature builds on — it adds
the new persisted fields and the validation/normalization for the new trigger types, but wires no
behavior yet (the dispatcher, webhook hook, subscriber hooks and API land in later waves).

Concretely, this task:
- adds `Funnel.keywords: List<String>` — a lowercase, contains-match keyword list used **only** by
  the `keyword` trigger (Decision 3: the exact-match `triggerValue` index cannot express
  "contains, multiple keywords");
- relaxes the `funnels` partial-unique trigger index **annotation** so uniqueness applies to
  `on_start` only (Decision 1: fan-out = N funnels sharing a trigger value). Note: the annotation
  change alone does not relax the live index — the actual drop/recreate is a separate startup
  migration (Task 2); this task only changes the `@CompoundIndex` shape so auto-index-creation
  recreates the right shape. **The runtime proof of the new index shape (old index gone, two `event`
  funnels coexist, two `on_start` collide) is verified by Task 2's `FunnelIndexesIT`, not here** —
  Task 1 owns the annotation, Task 2 owns the migration and its IT;
- adds `FunnelStep.eventName: String` (for `EMIT_EVENT`) and extends `FunnelStep.copyOf` so the
  execution snapshot preserves it (Decision 4: EMIT_EVENT and the external api-event share one
  `event` namespace keyed by `event_name`);
- adds `StepType.EMIT_EVENT`;
- adds `FunnelExecution.enrollDepth: int` (default 0) — the Redis-independent depth backstop carried
  on each execution (Decision 6);
- extends `FunnelService` to validate/normalize the four new trigger types, the `keywords` list, and
  the `EMIT_EVENT` step's `eventName` slug;
- adds the LIST repository queries `FunnelEventService` (Task 4) will need.

WHY this is Wave-1, standalone: the dispatcher (Task 4), the webhook keyword path (Task 6), the
subscriber tag/field hooks (Task 5), and the public API (Task 7) all read these fields and query
these repository methods — they cannot compile until this exists.

## What to do

1. **`StepType`** — add the `EMIT_EVENT` enum constant.

2. **`FunnelStep`** — add a nullable `eventName: String` field with getter/setter, and extend
   `copyOf(...)` so the snapshot carries `eventName` (it is an immutable `String` → reference copy,
   same as the other scalars). Update the copy-contract Javadoc to mention the new field.

3. **`FunnelExecution`** — add an `int enrollDepth` field (default 0) with getter/setter. It is a
   plain persisted scalar on the execution snapshot; no index change.

4. **`Funnel`** — add `keywords: List<String>` with getter/setter (only meaningful for
   `triggerType=keyword`; null/empty for the rest). Relax the partial-unique trigger index: change
   the `@CompoundIndex` `partialFilter` from `{ 'status': 'active' }` to
   `{ 'status': 'active', 'triggerType': 'on_start' }`. Update the index Javadoc to state that
   uniqueness now applies to `on_start` only and that the live-index drop is owned by the Task-2
   startup migration (auto-index-creation never drops/alters).

5. **`FunnelRepository`** — **this task OWNS every `FunnelRepository` change for the feature.** Task 4
   (`FunnelEventService`) consumes these queries but must NOT add or alter any repository method —
   add all of them here so there is a single owner and no merge conflict. Add LIST query variants for
   the new triggers:
   - a keyword-funnel query: active keyword funnels for a project
     (`findByProjectIdAndTriggerTypeAndStatus(projectId, "keyword", active)`) — the contains-match
     itself runs in code (Decision 3);
   - a LIST variant of the trigger lookup for `event`/`tag_added`/`custom_field_set` (the existing
     `findByProjectIdAndTriggerTypeAndTriggerValueAndStatus` returns a single `Optional` — add a
     `List`-returning sibling so fan-out can enumerate all matches).
   - **Optional-retention policy (do NOT drop):** KEEP the existing single-result
     `Optional`-returning `findByProjectIdAndTriggerTypeAndTriggerValueAndStatus` exactly as is. It is
     still used by the `on_start` conflict pre-check in `FunnelService` (one active `on_start` funnel
     per trigger payload). The `List`-returning sibling is *added alongside* it, not a replacement.
     Earlier drafts of Task 4 proposed removing this `Optional` method — that is overruled: it stays.

6. **`FunnelService`** — extend validation/normalization:
   - introduce the five valid `triggerType` constants (`on_start`, `keyword`, `tag_added`,
     `custom_field_set`, `event`) and reject any other value with a 422 business code;
   - `keyword` does **not** use `triggerValue`; `tag_added`/`custom_field_set`/`event` reuse
     `triggerValue` as the match key (validate per type: tag slug shape, field-key non-blank, event
     slug `^[A-Za-z0-9_-]{1,64}$`); keep `on_start`'s existing `triggerValue` rules;
   - normalize + validate `keywords`: lowercase each entry, trim, drop blanks/dupes; required
     non-empty **iff** `triggerType=keyword` (and rejected/ignored for other types — pick one and be
     consistent; reject-with-422 if `keywords` is sent for a non-keyword trigger is preferred to keep
     the contract tight). Enforce a sane per-keyword length and list-size cap;
   - validate the `EMIT_EVENT` step's `eventName` in `validateSteps` (slug
     `^[A-Za-z0-9_-]{1,64}$`, required) and carry it through `toSteps` (`step.setEventName(...)`) and
     `toStepDto`;
   - thread `keywords` through the create/update request DTOs, `toResponse`/`toSummary`, and the
     `FunnelStepDto` (`eventName`) as needed so the new fields round-trip over HTTP. **These DTOs are
     Java `record`s** (`FunnelStepDto`, `FunnelResponse`, `FunnelSummaryResponse`,
     `UpdateFunnelRequest`, `CreateFunnelRequest`) — adding a component to a record changes its
     canonical constructor, so EVERY call-site (mappers in `FunnelService` plus test fixtures in
     `FunnelControllerIT` and `FunnelStepExecutorTest`) must be updated in the same change or the
     module will not compile. Treat the record-field add + all call-site updates as one atomic edit.

7. Keep the chatId-keyed `on_start` `fire(...)` path and `insertExecution` **unchanged** — no
   behavior wiring in this task (Decision 2 — the new subscriber-keyed fan-out lives in Task 4's
   `FunnelEventService`).

**Edge cases:**
- `copyOf(null)` must still return null; `eventName == null` stays null in the snapshot.
- `keywords` with mixed case / surrounding spaces / duplicates → normalized lowercase, trimmed,
  unique. Empty list for a `keyword` funnel → 422.
- Sending `keywords` on a non-keyword trigger, or `triggerValue` on a `keyword` trigger → reject
  (keep the contract tight); document whichever choice you make in decisions.md.
- The partial-filter literal `'on_start'` must byte-match the persisted `triggerType` value
  (`"on_start"`). A two-active-`on_start`-same-payload pair must still collide; two active `event`
  funnels with the same `triggerValue` must coexist.
- Do not break `on_start`: `normalizeTriggerType(null/blank)` must still yield `on_start`.
- **Record call-sites compile atomically:** `FunnelStepDto`, `FunnelResponse`,
  `FunnelSummaryResponse`, `UpdateFunnelRequest` (and `CreateFunnelRequest` if `keywords` is
  creatable) are Java `record`s. Adding `keywords`/`eventName` components alters each record's
  canonical constructor, breaking every `new FunnelStepDto(...)` / `new FunnelResponse(...)` etc. The
  in-prod call-sites are the `FunnelService` mappers; the test call-sites include assertions/fixtures
  in `FunnelControllerIT` and `FunnelStepExecutorTest`. Update the record definition AND all
  constructor call-sites in one pass — a partial edit leaves `:backend:compileJava` /
  `:backend:compileTestJava` red. Grep for each record's constructor before declaring done.

**Implementation hints (not pseudocode):**
- Spring Data derives queries from method names — the `List<Funnel>` vs `Optional<Funnel>` return
  type alone changes single-vs-many; name the new method distinctly to avoid a duplicate-method clash.
- `auto-index-creation=true` (dev) creates the new annotation shape on a fresh DB but never drops the
  old one — the live drop is Task 2's startup runner, and the `listIndexes()` / coexistence proof
  lives in Task 2's `FunnelIndexesIT`. This task only changes the annotation; do not write that IT.
- Persisted enum/status literals are LOWERCASE `name()` (Decision 14); `triggerType` is a plain
  String (`"on_start"`, `"event"`, …), not an enum.
- Mirror the existing per-type `requireXxx(...)` validator style in `FunnelService` for the new
  checks (each throws `AppException.unprocessableEntity(CODE_*, msg)`).
- Keep `FunnelTriggerServiceImpl.fire` / `insertExecution` untouched — `enrollDepth` is set by the
  Task-4 dispatcher, not here (a new execution defaults to 0, which is the correct human/on_start
  root depth).
