## Description

Полнофичевый аудит качества кода для Phase 3 (`12-funnels-triggers`). Это НЕ задача написания кода —
это холистическое ревью всего кода, созданного и изменённого в волнах 1–6 (Задачи 1–10), с фокусом на
**кросс-компонентные** проблемы, которые не видны при ревью отдельной задачи.

Фича вводит шесть путей входа в воронку (`on_start`, `keyword`, `tag_added`, `custom_field_set` + общий
namespace `event`, питаемый внешним `POST /api/integrations/v1/events` и внутренним шагом `EMIT_EVENT`),
единый внутренний диспетчер `FunnelEventService` с тремя независимыми анти-цикл backstop'ами, новую
цепочку безопасности публичного API (`@Order(1)` на `/api/integrations/**`) и hash-only API-ключи.
Все эти куски писались разными агентами в разных волнах — задача аудита убедиться, что они складываются в
консистентную, не дублирующую себя архитектуру.

Аудитор сам является ревью (reviewers пустой) — результатом задачи является **отчётный JSON-файл аудита**,
а не правки кода. Найденные проблемы не правятся в рамках этой задачи; они фиксируются в отчёте с severity
и предложением фикса для последующей обработки.

     `@Service`/`@Bean`; rate-limit счётчики инициализируются один раз, ключи Redis не коллизируют

## Details

<!-- All details for task execution. -->

**Files:** аудит-задача файлы кода не правит. Единственный артефакт записи — JSON-отчёт аудита
(`work/12-funnels-triggers/logs/working/task-11/code-audit-1.json`) + краткая запись в `decisions.md`.

**Cross-component focus (главное, ради чего эта задача существует):**

1. **Shared-resource compliance (tech-spec → "Shared resources" таблица).**
   - `FunnelEventService` ДОЛЖЕН быть ровно одним `@Service` singleton. Найди все `@Service`/`@Bean`/`new`
     создания диспетчера — их быть не должно более одного.
   - Четыре консьюмера (`ProcessTelegramUpdateJob`, `SubscriberServiceImpl`, `StepExecutor`,
     `EventsController`) инжектят ОДИН и тот же бин и вызывают `dispatchForSubscriber`, а не имеют
     локальных копий fan-out-логики.
   - `StringRedisTemplate` rate-limit: ключи `bf:rate:auto-enroll:{subscriberId}` и `bf:rate:events`
     различны; идиома INCR/EXPIRE не продублирована руками с расхождениями (TTL, единицы, fail-open
     поведение должны совпадать с `SubscriberServiceImpl.startRateLimitExceeded`).

2. **Security-chain ordering (Decision 7).** В `SecurityConfig`: key-chain имеет `@Order(1)`,
   `securityMatcher("/api/integrations/**")`, STATELESS, CSRF off; session-chain `@Order(2)`. Убедись, что
   нет пересечения matcher'ов, через которое публичный эндпоинт уходит в session-чейн (теряя key-auth) или
   кабинетный эндпоинт уходит в key-чейн. Проверь, что `OncePerRequestFilter` даёт **uniform 401** на любую
   проблему ключа (анти-enumeration) и резолвит проект ИЗ ключа (анти-IDOR, нет `{projectId}` в пути).

3. **Explicit-depth threading (Decision 6, критическая ось).** Пройди цепочку:
   `EventsController`(0) / webhook keyword(0) / manual controllers(0) / `StepExecutor`
   (`execution.enrollDepth + 1`) → `dispatchForSubscriber(..., originDepth)` →
   `insertExecution(enrollDepth=originDepth)`; и `addTag`/`recordCustomFieldsSet` принимают origin depth
   явным параметром. Убедись: НЕТ ThreadLocal-протаскивания; каждый из ~5 call-site'ов передаёт корректный
   depth; root vs auto разграничение единообразно (auto = depth>0). Это самая частая точка рассинхрона между
   независимо написанными волнами.

4. **Error-isolation консистентность (Decision 12).** Все новые dispatch-пути обёрнуты в
   `try/catch(Throwable)` с greppable WARN; keyword-fault → webhook 200 (job не падает); engine-fault в
   `/events` → 202. Стиль логирования и swallow-поведение единообразны, повторяют
   `FunnelTriggerServiceImpl`.

5. **Три backstop'а — целостность (Decision 6a/6b/6c).** Volume (Redis fail-open, считает только depth>0),
   depth-cap (Redis-independent, ≤10), fan-out ceiling (Redis-independent, `max-fanout-per-event` default
   50). Проверь, что они реализованы как **три независимых** механизма (не один, выдающий себя за три), и что
   Redis-independent два действительно не зависят от Redis. Проверь конфиг-ключи в `application.properties`.

6. **Архитектурная консистентность.** Соответствие `patterns.md` (виртуальные потоки, структура сервис/
   репозиторий/доменка по пакетам, конвенции именования), отсутствие протечки внутренних id в UI, единый
   стиль валидации (`event_name` slug `^[A-Za-z0-9_-]{1,64}$` одинаков в DTO и `FunnelService`).

**Method:** загрузи скилл `code-reviewing` и примени его 11 измерений ПОВЕРХ перечисленных кросс-компонентных
осей. Severity по конвенции скилла. Аудит холистический — приоритет проблемам "на стыке" задач, которые
отдельные per-task ревью пропустили.

**Dependencies:** Задачи 1–10 завершены (wave 7 — после всех волн реализации). Аудит читает их результат.

**Edge cases для проверки:** дублирующая регистрация диспетчера/бина; ручная копия rate-limit с другим TTL;
matcher-пересечение `/api/**` vs `/api/integrations/**`; ThreadLocal вместо явного depth; пропущенный
`try/catch(Throwable)` на одном из четырёх путей; backstop, опирающийся на Redis там, где должен быть
Redis-independent; `eventName` не сохранён в `copyOf` снапшота.

**Implementation hints:** начни с `FunnelEventService` (центр графа вызовов), затем разверни наружу к четырём
консьюмерам — это быстрее всего выявляет дублирование и рассинхрон depth. Используй `git diff` фичи как карту
поверхности. НЕ правь код — только фиксируй findings в отчёте.
