## Description

Full-feature security audit of the **12-funnels-triggers (Phase 3)** delivery — the entry-trigger
expansion (`keyword` / `tag_added` / `custom_field_set` / `event` + `EMIT_EVENT`) and, critically, the
**first public-API surface**: a per-project hash-only API key and a key-authenticated
`/api/integrations/**` filter chain feeding `POST /api/integrations/v1/events`.

This is an **Audit Wave** task (Wave 7). It runs **after** all implementation tasks (1–10) are complete
and their code/test audits exist. It is NOT a code-writing task — you write no production code. You read
every source file created/modified across the feature and analyze it holistically against the **OWASP
Top 10**, with emphasis on the threat surfaces this feature introduces:

1. **API-key storage & comparison** — keys hashed (`Sha256Hex.hex`), not encrypted/plaintext; ≥256-bit
   `SecureRandom` entropy; plaintext shown once, never persisted; lookup is **by hash** (no plaintext
   compare, no low-entropy brute-force preimage); `keyPrefix` mask never leaks the full key.
2. **401 uniformity / anti-enumeration** — every key failure mode (missing / malformed / unknown key)
   returns an **identical** 401 with no distinguishing body, header, or timing tell.
3. **Chain isolation (both directions)** — the `@Order(1)` STATELESS key chain on
   `securityMatcher("/api/integrations/**")` and the `@Order(2)` session chain are **mutually
   exclusive**: an API key cannot reach `/api/v1/projects/**` (cabinet), a session cannot reach
   `/api/integrations/**`. Verify matcher precedence/shadowing, CSRF posture, and that the public chain
   is STATELESS (no session minted, cookieless).
4. **Rate-limit + fan-out-ceiling bypass** — the fail-open Redis `/events` limiter and the per-subscriber
   auto-enroll limiter cannot be trivially bypassed; the **Redis-independent** depth cap (10) and
   per-dispatch fan-out ceiling (50) actually bound chain depth and request width **even when Redis is
   down** (the documented fail-open hole-closer — Decision 6c/10). Confirm no unbounded amplification.
5. **IDOR on subscriber resolution** — subscriber resolution in `EventsController` and
   `FunnelEventService` is **always pinned to the project resolved from the key**, never to a
   caller-supplied project; `telegram_user_id` / `subscriber_id` from the body cannot cross project
   boundaries (mirrors the established `(projectId, …)`-scoped anti-IDOR convention).
6. **Input validation** — `event_name` slug (`^[A-Za-z0-9_-]{1,64}$`, `@NotBlank`), `telegram_user_id`
   well-formed, `subscriber_id` well-formed; at least one identifier required (else 400); malformed body
   → 400; mass-assignment defense (`@JsonIgnoreProperties(ignoreUnknown=true)`, no owner/project fields
   read from the body); same validation rigor on `Funnel.keywords` / `FunnelStep.eventName` /
   `triggerType` in `FunnelService`.
7. **No PII / secrets in logs** — the new dispatch/keyword/event/api-key paths never log raw API-key
   plaintext, bot tokens, subscriber PII, or session ids; greppable WARN/ERROR lines emit ids/codes
   only (project convention: token-scrubber + "ids/codes only, no PII").

Cross-check every finding against the **project security conventions in patterns.md** (anti-IDOR layers,
SHA-256-not-encryption-for-preimage, fail-open-with-WARN rate-limit shape, uniform-401 anti-enumeration,
no-PII-in-logs, mass-assignment DTO whitelist, scoped-CSRF-disable matcher shape) — a deviation from an
established convention is itself a finding. Produce a structured audit report.

## What to do

1. **Enumerate the feature's source surface.** Build the file list from the tech-spec "Files to modify"
   across Tasks 1–10 **and** `decisions.md` (each completed task records what it actually touched —
   prefer the actual paths recorded there, as implementations may have added/renamed files). Cover all
   five backend modules (`funnel`, `webhook`, `subscriber`, `api`, `security`) plus the frontend
   secret-handling surfaces (API-key card, plaintext-once modal).

2. **Read every created/modified source file** and reconstruct the trust boundaries: where untrusted
   input enters (the `/events` body, the `X-API-Key` header, Telegram free-text for keyword), where the
   project/subscriber identity is established, and where privileged actions (execution creation, key
   storage) happen.

3. **Run the OWASP Top 10 pass**, prioritizing the seven surfaces in the Description. For each, judge:
   does the code enforce the control, is it bypassable, does it match the ratified decision and the
   project convention? Pay special attention to:
   - **A01 Broken Access Control / IDOR:** project-scoping of subscriber resolution from the key;
     session-chain access guards unchanged; chain ordering can't be shadowed.
   - **A02 Cryptographic Failures:** key entropy, hash-only at rest, no plaintext persistence, prefix
     mask doesn't leak the key, `SecureRandom` (not `Random`).
   - **A03 Injection / Input validation:** DTO + `FunnelService` validation, mass-assignment whitelist,
     Mongo query construction (no operator injection via unvalidated `event_name`/identifiers).
   - **A04 Insecure Design:** the three loop backstops actually bound depth+width with Redis down;
     fail-open rate-limit paired with the Redis-independent ceiling; error-isolation (fault → 202/200,
     never 5xx, no internal-state leak in the response).
   - **A05 Security Misconfiguration:** CSRF posture on the new chain, STATELESS enforcement, no session
     minted on the public chain, `application.properties` additions don't weaken global posture.
   - **A07 Auth Failures:** uniform 401 across all three key causes; no timing/enumeration tell.
   - **A09 Logging Failures:** no PII/secret in the new log sites; WARN/ERROR are greppable + scrubbed.

4. **Verify the chain-isolation claim concretely** by reading `SecurityConfig` ordering, `securityMatcher`
   scopes, and the api-key `OncePerRequestFilter`: confirm the key filter never authenticates a session
   request and the session chain's `/api/**` matcher does not shadow `/api/integrations/**`.

5. **Write the audit report** as your final assistant message (do NOT create a `.md` file). For each
   finding: severity (Critical / High / Medium / Low / Info), the OWASP category, the exact file +
   construct, why it's exploitable (or why a checked control is sound), and a concrete fix. Conclude with
   a verdict: PASS (no Critical/High) or BLOCK (Critical/High present), and a per-surface checklist
   (the seven surfaces in the Description) marked covered/clean or flagged.

## Details

**Nature:** Read-only holistic security audit across the whole feature. No code changes, no new tests.
The deliverable is a structured findings report returned as the final assistant message.

**File-list source of truth:** `decisions.md` records what each task actually modified — start there, then
reconcile against the tech-spec "Files to modify" lists for Tasks 1–10. If a file in the tech-spec list
was renamed/split during implementation, follow the decisions.md record.

**Threat-model focus (highest blast radius first):**
- The public `/api/integrations/v1/events` endpoint is the only externally-reachable, key-authed surface
  in the whole platform so far — treat it as the primary attack target.
- The API key is a long-lived, non-rotating credential (rotation deferred to Epic 08) — storage/compare
  correctness is load-bearing.
- Loop backstops are a denial-of-service / amplification control — a bypass is an A04 issue, not cosmetic.

**Edge cases to probe:**
- Key chain shadowing: does `securityMatcher("/api/integrations/**")` at `@Order(1)` actually win over
  the session chain's broader `/api/**`? A wrong order silently routes public requests through the
  session chain (or vice-versa).
- Uniform 401: missing header vs malformed key vs unknown-hash must be byte-identical responses; check no
  exception message, stack frame, or `WWW-Authenticate` variance leaks the cause; check no timing tell
  (e.g. a DB lookup only on well-formed keys).
- IDOR: `subscriber_id` / `telegram_user_id` in the body resolved without the key-pinned `projectId`
  would let a key for project A address subscribers of project B.
- Redis-down: with the fail-open limiter open, does the depth cap (10) AND the fan-out ceiling (50) still
  bound chain length and request width? A ceiling that reads its limit from Redis would re-open the hole.
- Mass assignment: can the events DTO or any new `*Request` carry an `ownerId`/`projectId`/`status` field
  that the code reads? (Convention: never read owner/project from the body.)
- Log leakage: grep the new WARN/ERROR sites for raw key, token, subscriber name/username, chatId-as-PII;
  confirm the token-scrubber / ids-only convention holds on every new site.
- EMIT_EVENT recursion: an attacker-authored funnel emitting its own trigger event — bounded by depth cap
  + fan-out ceiling + re-enter guard?

**Severity rubric:** Critical = remote unauth/cross-tenant compromise or credential exposure; High =
authenticated cross-tenant access, auth bypass, or unbounded amplification; Medium = enumeration tell,
weak-but-not-broken control, or convention deviation with exploit path; Low/Info = defense-in-depth gaps.

**Implementation hints:** Lean on patterns.md as the project's ratified security baseline — many of the
controls under audit (anti-IDOR project-scoping, SHA-256 preimage, fail-open-with-WARN, uniform-401,
no-PII logs, mass-assignment whitelist, scoped-CSRF matcher) already have a documented "correct shape"
there; the audit is largely "does the new code match the established shape, and where it deviates, is the
deviation ratified in a Decision or is it a finding." Tech-spec Decisions 6/7/8/10/12 state the intended
security posture — verify the code realizes it.
