# Task 13: Test Audit

## Required Skills

Перед выполнением задачи загрузи:
- `/skill:test-master` — [SKILL.md](../../../.claude/skills/test-master/SKILL.md). Особенно [references/test-quality-review.md](../../../.claude/skills/test-master/references/test-quality-review.md) — категории плохих тестов, severity, litmus-тест.

## Description

Full-feature **test quality audit** for the 12-funnels-triggers feature (Phase 3: additional triggers + internal event bus + public API). This is the **Audit Wave** — the auditor IS the review, so there are no downstream reviewers. The task is read-only: it does NOT write or fix tests, it produces an audit report.

The goal is to confirm that the test suite the implementing tasks (Waves 1–6) produced actually proves the feature works and protects against regressions — not just that tests exist and pass. Phase 3 introduces high-risk behaviors (subscriber-keyed fan-out, three independent loop backstops, a key-authenticated security chain, error-isolation on every new dispatch path, an index-relax migration). Each of these has a precise expected-behavior contract in the tech-spec Testing Strategy and Acceptance Criteria; the audit verifies that the tests assert those contracts with meaningful assertions, that nothing in the matrix is missing, and that the test-pyramid balance is right (unit for logic, integration for endpoints/DB/security-chain, Vitest for the editor UI, no superfluous E2E).

WHY: a green suite that silently skips the Redis-down depth-cap path, the uniform-401 anti-enumeration assertion, or the "no-op write does not fire" case gives false confidence on exactly the parts of this feature that were called out as the riskiest. The audit is the last quality gate before pre-deploy QA (Task 14).

## What to do

1. **Inventory the test files.** From decisions.md (per-task "Reviews"/"Verification" entries and any deviations) and the tech-spec "Files to modify" lists, enumerate every test file created or modified by Tasks 1–10. Cover all four backend modules (`funnel`, `webhook`, `subscriber`, `api`/`security`) and the frontend Vitest specs. Re-glob the test dirs at audit time — the `backend/src/test/.../api/`+`.../security/` tree and the Phase-3 Vitest specs are **net-new** (created by Tasks 3/7/8/9/10), so they exist only after Waves 1–6; do not assume any path is present. Read each file that exists in full. If a required coverage area from step 2 has **no test file at all**, record it as a **critical gap** in the report — never silently skip an absent area.

2. **Map tests to the required coverage matrix** (from tech-spec Testing Strategy + Acceptance Criteria). For each required behavior below, find the test(s) that prove it and judge whether the assertions are meaningful (litmus test: would the test fail if the implementation were broken/deleted?). Flag any required behavior with no test, a weak/mock-only test, or a test that asserts the wrong thing:
   - **Each trigger type** starts the correct funnel for the correct subscriber: `on_start` (unchanged, no regression), `keyword`, `tag_added`, `custom_field_set`, `event` (external api-event + EMIT_EVENT step).
   - **Keyword matching** unit coverage: contains / case-insensitive / any-of-many / no-match; lowercase normalization on save.
   - **Keyword precedence** vs `waiting_for_reply`: assert BOTH no new execution created AND the waiting execution untouched.
   - **Fan-out**: one event/word/tag/field firing → N executions (N separate funnels sharing the trigger value).
   - **Three loop backstops, each as an independent test**:
     - *Volume* — per-subscriber auto-enroll rate-limit (≤20/min, Redis fail-open path); depth-0 human/external enrolls are exempt (asserted).
     - *Depth* — `enrollDepth` cap at >10 truncates the chain, asserted **with Redis unavailable** (the cap is Redis-independent — the fail-open rate-limit must not be what stops it).
     - *Fan-out width* — per-dispatch ceiling (`max-fanout-per-event`, default 50): one firing with >N listener funnels inserts at most N executions, asserted **with Redis unavailable**.
     - re-enter guard still catches a direct duplicate into the same funnel.
   - **`POST /api/integrations/v1/events` response-code matrix**, each code with a distinct assertion: 202 start / 202 no-op (subscriber exists, no listener) / 404 unknown subscriber / 400 malformed body / 401 / 429; never 5xx; never auto-creates a subscriber. Plus: the **uniform 401** asserted identical across all three key causes (missing / malformed / unknown); the two **400 sub-paths** (malformed `event_name` slug vs missing-both-identifiers) each distinct; the `subscriber_id`-wins precedence asserted; 404-vs-202-no-op distinction asserted.
   - **Both error-isolation paths**: keyword dispatch throws → webhook worker returns 200, JobRunr job NOT failed, WARN logged; engine throws inside `/events` → 202, no 5xx, WARN logged.
   - **Chain isolation, both directions**: key ✗ `/api/v1/projects/**` (session zone); session ✗ `/api/integrations/**` (key zone).
   - **Index-relax migration** — explicit checkpoint: confirm `FunnelIndexesIT` was **UPDATED for Phase 3**, not left asserting the old contract. Before this feature the IT asserts the OLD partial filter (`status:'active'` only); after the migration the filter must gain `triggerType:'on_start'`. The audit must verify all three required assertions are now present and that the old-filter assertion is gone:
     1. the OLD index (partial filter on `status:'active'` alone) is **gone** — a test still asserting it is a finding (stale test that would pass against the un-migrated schema);
     2. **two active `event` funnels coexist** (same project/payload, both `status:'active'`, `triggerType:'event'`) without a duplicate-key violation — proves the relaxed filter lets non-`on_start` triggers share the slot;
     3. **two `on_start` funnels with the same payload still collide** (duplicate-key) — proves the `on_start` uniqueness is preserved by the narrowed filter.
     If any of these three is absent, flag it (the index-relax migration is a named Phase-3 risk). Plus migration-runner unit: idempotent (no-op on second boot) and log-but-never-throw.
   - **Persistence round-trips**: `Funnel.keywords`, `FunnelStep.eventName` (incl. survives `copyOf` execution snapshot), `FunnelExecution.enrollDepth`; `api_keys` stores hash + prefix only (full plaintext never persisted), `keyHash` unique index enforced.
   - **API-key unit**: ≥256-bit length; plaintext ≠ stored hash; `Sha256Hex` verify round-trip; prefix mask shape.
   - **Frontend Vitest**: trigger-type selector renders the correct value editor per type; keyword multi-word list add/remove; `EMIT_EVENT` in the step picker with its event-name field; API-key card states (generate → plaintext-once → masked + regenerate).

3. **Check test-pyramid balance and quality** per test-master methodology:
   - Pyramid shape correct: unit for logic (matching/normalization/backstop arithmetic/validation), integration for endpoints + DB + security-chain + migration, Vitest for editor UI, and **E2E = none** (confirm the tech-spec's "no new critical flow" judgment holds — no missing critical journey).
   - Detect bad-test categories: empty/meaningless, mock-only / mock-return anti-pattern, excessive mocking (3+ mocks → wrong test type), redundant duplicate coverage, tests asserting implementation not behavior.
   - Confirm integration tests use **real embedded MongoDB** (no DB mocking — project rule), the `@Tag("slow")` index-migration IT is present and tagged, and Redis-down paths are exercised by an actual disabled/failing Redis stand-in (not just a mocked boolean return) where the spec demands "with Redis unavailable".
   - Confirm no-op writes do NOT fire (idempotent `addTag`/`recordCustomFieldsSet` → no execution) is asserted, not just the happy path.

4. **Write the audit report** as the final assistant message (do NOT create a .md file). Structure it as:
   - **Verdict**: pass / pass-with-findings / fail (a missing backstop test or a missing error-isolation assertion is a blocking finding).
   - **Coverage matrix**: for each required behavior in step 2 — covered / weak / missing, with the test name(s).
   - **Findings**: each with severity (critical / major / minor), the file/test, the problem, and the concrete fix (which assertion/test to add or strengthen).
   - **Pyramid assessment**: one paragraph on balance + any redundant or wrong-type tests.

## Details

**Nature:** Read-only audit. Produce a report; do NOT edit, add, or fix tests, and do NOT write any .md report file — the report is the final assistant message.

**Files:** No source files modified. Reads: all feature test files (see Context Files), tech-spec Testing Strategy + Acceptance Criteria, decisions.md.

**Dependencies:** Hard-depends on Tasks 1–10 being done (all test files must exist). Runs in the Audit Wave (wave 7) alongside Task 11 (code audit) and Task 12 (security audit) — independent of them; no file overlap.

**Edge cases the audit must specifically hunt for** (these are the spec's named risks — a test that skips one is a finding):
- Depth cap and fan-out ceiling asserted **with Redis genuinely unavailable**, not via the fail-open rate-limit (Decision 6b/6c). If the only "Redis down" simulation is a mocked boolean, that is a weak test.
- Volume rate-limit **exempts depth-0** (human/external) enrolls — assert a depth-0 burst is NOT throttled, and a depth>0 burst IS (Decision 6, the reconciled "auto = depth>0" definition).
- Uniform 401 **byte-identical** across missing / malformed / unknown key (anti-enumeration, Decision 7) — three separate assertions comparing the same body/status.
- `subscriber_id` **wins** over `telegram_user_id` when both present; missing-both → 400 (distinct from malformed-slug → 400).
- 202 **no-op** (subscriber exists, no listener funnel) distinguished from 404 (unknown subscriber) — two separate tests, not conflated.
- Idempotent `addTag` / `recordCustomFieldsSet` **no-op does NOT fire** a trigger (Decision 5).
- `eventName` **survives `copyOf`** into the execution snapshot (Decision 4 / data model).
- Migration IT (`FunnelIndexesIT`) is `@Tag("slow")`, was **updated away from the old `status:'active'`-only filter assertion**, and proves all three index facts (old gone, two `event` coexist, two `on_start` collide); the runner unit proves idempotent-no-op + never-throw (Decision 9). A `FunnelIndexesIT` still asserting only the old partial filter is a finding even if the suite is green — it would also pass against the un-migrated schema.

**Implementation hints:**
- Apply the litmus test from `test-quality-review.md` to each high-risk test: "if I delete the implementation, does this test fail?" Mock-return and mock-only tests pass the deletion and are findings.
- Per `patterns.md`, log-assertion tests must be **per-log-site `ListAppender` filtered by logger + level** — a single combined log assertion masks which site leaked; flag combined assertions on the error-isolation WARN paths.
- Per `patterns.md`, integration tests must use real embedded Mongo (no DB mock) — any `@MockitoBean` on `MongoClient` outside the Epic-01 skeleton exception is a finding.
- Treat a missing loop-backstop independent test, a missing error-isolation assertion, or a conflated 202-no-op/404 as **critical** (blocks the verdict); weak-but-present assertions as **major**; redundant / wrong-type tests as **minor**.
