## Description

Финальная волна фичи 12-funnels-triggers (Фаза 3 епіку «Воронки»). Приёмочное тестирование **перед деплоем**, без живого окружения: прогнать весь набор тестов (backend unit + integration, включая `@Tag("slow")` index-migration IT; frontend Vitest) и проверить **каждый** acceptance criterion из user-spec и tech-spec.

Это финальная проверка после трёх audit-задач (11 — code audit, 12 — security audit, 13 — test audit). К этому моменту вся реализация (Wave 1–6) и аудиты завершены; задача подтверждает, что всё зелёное и все критерии приёмки выполнены, либо явно документирует, что не выполнено / отложено на пост-деплой верификацию (Task 15, живой прогон).

Не код-задача — никакого нового кода. Если QA вскрывает падение или невыполненный критерий — зафиксировать как finding в QA-отчёте (не чинить здесь; это вход для отдельной fix-задачи или возврата к соответствующей волне).

## What to do

1. Прочитать вход: user-spec.md, tech-spec.md, decisions.md (зафиксированные отклонения и отчёты по выполненным задачам), а также Project Knowledge (architecture.md, patterns.md — секции Testing & Git Workflow).

3. **Прогон frontend-тестов:** запустить Vitest (`pnpm test`, неинтерактивно — см. hints) в `frontend/`. Зафиксировать результат по тригер-селектору + EMIT_EVENT-форме + API-key card.
4. **Проверка каждого критерия приёмки** из user-spec («Критерии приёмки») и tech-spec («Acceptance Criteria»). Для каждого: статус (passed / deferred / failed) + доказательство (имя теста, ссылка на отчёт, или причина «требует живого окружения → Task 15»).
5. 6. Свести итог: общий вердикт (готово к деплою / есть блокеры), список findings, список deferred-критериев для Task 15.
7. Записать QA-отчёт в `work/12-funnels-triggers/logs/working/task-14/qa-report.md` и краткое резюме — в decisions.md (Post-completion).

## Details

**Природа задачи:** не код-задача. Секция TDD Anchor удалена. Скилл — `pre-deploy-qa`, ревьюеров нет. Ничего не чиним и не пишем код; QA только запускает и сверяет.

**Команды (актуальные для этого репо):**
- `gradlew` живёт в `backend/`, не в корне — запускать из `backend/`.
- Default `./gradlew test` **исключает** `@Tag("slow")` (см. `backend/build.gradle:46-56`). Index-migration IT и P99-пробы под тегом `slow` запускаются **только** с `-PrunSlow=true` — обязательно сделать оба прогона.
- Frontend: `pnpm test` запускает `vitest` (watch-режим). Для неинтерактивного прогона использовать `pnpm test -- --run` (или `pnpm vitest run`), иначе процесс зависнет в watch.

**Источник критериев:**
- user-spec «Критерии приёмки» — пользовательские (16 пунктов: селектор тригера, keyword + precedence, tag_added/custom_field_set idempotent, api-event матрица, EMIT_EVENT, fan-out, on_start 1:1, анти-цикл обсяг/глубина, API-ключ, миграция, error-isolation вебхук/API).
- tech-spec «Acceptance Criteria» — технические (8 пунктов: матрица `/events`, error-isolation, три бекстопа incl. Redis-down, идемпотентность index-runner, round-trip полей + `copyOf` snapshot, hash-only `api_keys` + unique index, изоляция chains, отсутствие регрессий, slow IT).

**Что объективно deferred → Task 15 (post-deploy verification, живой локальный прогон):** keyword + menu precedence «вживую» по Telegram (UX-ощущение), реальный HTTP `POST /api/integrations/v1/events` курлом по всей матрице кодов, EMIT_EVENT fan-out по Telegram, startup-лог миграции + `listIndexes` на живом инстансе, UI-генерация API-ключа в браузере (plaintext-once модалка). Большинство этих поведений уже покрыто IT/Vitest — здесь подтверждается тестами; «вживую» — Task 15. Не помечать как failed только потому, что нет живого окружения.

**Edge cases / на что смотреть:**
- Отличить `failed` (тест красный / критерий объективно нарушен) от `deferred` (требует живого окружения, но покрыт автотестом). Только `failed` — блокер деплоя.
- Сверить decisions.md и tech-spec «User-Spec Deviations»: одобренные отклонения (auto-enroll = depth>0; добавленный fan-out ceiling; путь `/api/integrations/v1/events` вместо роадмаповского `/api/v1/events`) — это НЕ findings, они утверждены 2026-06-07. Не репортить их как расхождение.
- `@Tag("slow")` index-migration IT — критический пункт tech-spec AC; убедиться, что прогон `-PrunSlow=true` реально его включил (а не проскипал).
- Если backend/frontend тесты не компилируются или падают на старте окружения (embedded Mongo / Redis) — это блокер, зафиксировать как finding с логом.

**Dependencies:** Task 11 (Code Audit), Task 12 (Security Audit), Task 13 (Test Audit) должны быть завершены — их отчёты дают контекст известных нюансов. Вся реализация Wave 1–6 (Tasks 1–10) завершена.

**Implementation hints (НЕ псевдокод):**
- Прогоны могут быть долгими (embedded Mongo + Redis + slow IT) — заложить таймаут, не прерывать преждевременно.
- Для воспроизводимости фиксировать точные команды и хвост вывода (числа passed/failed) в QA-отчёт.
- Сверять критерии по именам тест-классов из tech-spec «Testing Strategy» (`FunnelTriggerServiceIT`, `FunnelIndexesIT`, `ProcessTelegramUpdateJobTest`, `SecurityConfigTest` и их сиблинги) — так доказательство для каждого AC становится ссылкой на конкретный тест.
