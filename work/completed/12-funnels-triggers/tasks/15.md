# Task 15: Post-deploy verification (live, local run)

Перед выполнением задачи загрузи:

## Description

Финальная задача фичи 12-funnels-triggers. После того как Task 14 (pre-deploy QA) подтвердил
зелёные тесты и acceptance-критерии без живого окружения, эта задача выполняет **живую верификацию**
поведений, которые тяжело покрыть unit/IT: реальный keyword-тригер с precedence над меню,
tag/field-тригеры, внешний event-эндпоинт со всей матрицей кодов, EMIT_EVENT fan-out, стартовая
миграция индекса и генерация/изоляция API-ключа.

**Важно про окружение:** автодеплоя для этого проекта ещё нет (pre-prod). «Live» здесь означает
**локально запущенный автором стек**: инфраструктура (MongoDB + Redis + Mailpit) через Docker
Compose, backend через `./gradlew bootRun` на `:8080`, frontend на `:3000`. Все проверки идут против
этого локального инстанса — реальный Telegram-бот (throwaway, не продакшен), `curl` на localhost,
`mongosh`/лог старта для индекса, браузер на localhost для кабинета.

Это исполнение AVP (Agent Verification Plan) из tech-spec, источник — user-spec секция «Как проверить».
Задача читающая/проверяющая: код не пишем. Если в ходе живой верификации находится баг — фиксируем
finding в отчёте (decisions.md) и сигналим, не правя код в рамках этой задачи.

## What to do

Запустить локальный стек (инфра в Docker Compose, backend `bootRun`, frontend) и подтвердить каждое
поведение из AVP вживую:

1. **keyword + precedence (Telegram MCP).** Через реального throwaway-бота: написать боту вольный
   текст со словом-триггером (в разном регистре, как подстрока) → стартует правильная keyword-воронка.
   Затем войти в меню (`waiting_for_reply` из Фазы 2) и написать то же слово → меню остаётся, keyword
   **не** срабатывает.
2. **tag_added / custom_field_set (Telegram MCP + curl/кабинет).** Добавить подписчику тег (через
   кабинет на localhost или `curl`) → стартует соответствующая `tag_added`-воронка (приходит
   сообщение в Telegram). Повторно добавить тот же тег (idempotent no-op) → воронка **не** стартует.
   Установить custom-поле → стартует `custom_field_set`-воронка; no-op set не стартует.
3. **POST /api/integrations/v1/events — матрица кодов (curl).** Сгенерировать API-ключ, затем проверить
   все коды: валидный ключ + известный `telegram_user_id` + воронка-слушатель → **202** (воронка
   стартует); подписчик есть, слушателя нет → **202 no-op**; невалидное тело (битый `event_name` slug
   / нет ни одного идентификатора) → **400**; нет/битый/неизвестный ключ → **уніфікована 401**;
   неизвестный идентификатор подписчика → **404**; превышение rate-limit → **429**. Подтвердить, что
   эндпоинт **не** создаёт подписчика и **никогда** не отдаёт 5xx.
4. **EMIT_EVENT fan-out (Telegram MCP).** Настроить воронку с шагом `EMIT_EVENT` и **две**
   активные воронки-слушателя того же `event_name`. Прогнать родительскую воронку для подписчика →
   обе воронки-слушателя стартуют (два `FunnelExecution`), родительская продолжается.
5. **Миграция индекса (bash: лог старта + listIndexes).** В логе старта backend найти маркер
   reconciliation-runner'а; через `mongosh listIndexes` на коллекции `funnels` подтвердить, что старый
   `projectId_triggerType_triggerValue_unique_active` отсутствует, а новая on_start-only-unique форма
   есть. Перезапустить backend → маркер показывает no-op (идемпотентность), ошибок нет.
6. **API-ключ: один раз, hash-only, изоляция цепочек (браузер/localhost + curl).** В настройках
   проекта на localhost нажать «Згенерувати» → plaintext показан **один раз**; перезагрузить → маска
   `prefix•••` + «Перегенерувати». Через `mongosh` подтвердить, что в `api_keys` лежит только хеш +
   префикс (полного plaintext нет). Проверить взаимную изоляцию: ключ авторизует
   `/api/integrations/**`, но **не** сессионные `/api/v1/projects/**`; сессионная cookie авторизует
   кабинет, но **не** `/api/integrations/**`.

Свести результаты в отчёт post-deploy verification (по шаблону скилла), отметить любые findings и
deferred-критерии, переданные из Task 14.

## Verification Steps

<!-- Эта задача САМА является верификацией. Ниже — конкретные живые проверки (не unit/IT). -->

### Setup (локальный стек)
- `docker compose -f infra/docker-compose.yml up -d` → MongoDB :27017, Redis :6379, Mailpit запущены.
- `cd backend && ./gradlew bootRun` → Tomcat на :8080; дождаться готовности (`GET http://localhost:8080/health`).
- Frontend на :3000 (для проверки API-ключа в кабинете).
- Throwaway Telegram-бот подключён через ngrok-туннель (как в `docs/staging-smoke/08-webhook-ingestion.md`),
  **не** продакшен-маркетинг-бот.

### Live checks
- **keyword + precedence** (Telegram MCP): отправить боту текст со словом-триггером (разный регистр) →
  стартует keyword-воронка; затем в меню (`waiting_for_reply`) то же слово → меню остаётся, keyword не стартует.
- **tag_added / custom_field_set** (curl/кабинет → Telegram MCP): добавить тег/поле подписчику →
  приходит сообщение соответствующей воронки; повторное idempotent добавление тега / no-op set → воронка не стартует.
- **POST /api/integrations/v1/events матрица** (curl):
  - `curl -X POST http://localhost:8080/api/integrations/v1/events -H 'X-API-Key: <key>' -H 'Content-Type: application/json' -d '{"event_name":"<listened>","telegram_user_id":<known>}'` → **202**, воронка стартует.
  - известный подписчик, событие без слушателя → **202 no-op**.
  - тело `{"event_name":"bad slug!!","telegram_user_id":<known>}` или без `telegram_user_id`/`subscriber_id` → **400**.
  - без заголовка ключа / битый ключ / неизвестный ключ → **401** (байт-в-байт одинаковый ответ для всех трёх).
  - валидный ключ, но неизвестный `telegram_user_id` → **404**.
  - залить запросами выше глобального лимита (~300/мин) → **429**.
  - подтвердить через `mongosh`, что новый подписчик не создан; ни один ответ не 5xx.
- **EMIT_EVENT fan-out** (Telegram MCP): прогнать воронку с шагом `EMIT_EVENT` при двух активных
  слушателях того же `event_name` → стартуют обе (два `FunnelExecution`), родительская продолжается.
- **Миграция индекса** (bash): в логе `bootRun` найти маркер reconciliation-runner'а;
  `mongosh botfunnel --eval 'db.funnels.getIndexes()'` (или `db.runCommand({listIndexes:"funnels"})`)
  → старый `projectId_triggerType_triggerValue_unique_active` отсутствует, есть on_start-only-unique
  форма (partial filter `{status:'active', triggerType:'on_start'}`). Перезапустить backend → маркер no-op, без ошибок.
- **API-ключ** (браузер localhost + curl + mongosh): настройки проекта → «Згенерувати» → plaintext
  показан один раз; reload → маска `prefix•••` + «Перегенерувати»; `mongosh` `db.api_keys.find()` →
  только `keyHash` + `keyPrefix`, полного plaintext нет. Изоляция: тем же ключом дёрнуть
  `/api/v1/projects/**` → отказ; сессионной cookie дёрнуть `/api/integrations/v1/events` → отказ.

### User
- Автор на своём Telegram «вживую» проходит keyword-сценарий и tag-сценарий — оценивает UX precedence
  (меню vs keyword) руками, поскольку это поведение лучше всего оценивается вручную (user-spec

## Details

<!-- All details for task execution — technical, organizational, any other. -->

**Тип задачи:** живая верификация (не code-writing). TDD Anchor отсутствует, автоматических unit/IT
прогонов здесь нет — это задача Task 14 (pre-deploy QA). Здесь — только live-поведение.

**Окружение:** автодеплоя нет (pre-prod). «Live» = локальный стек автора: Compose-инфра (Mongo :27017,
Redis :6379, Mailpit :1025/:8025) + backend `./gradlew bootRun` на :8080 + frontend на :3000. Health —
`/health`. Все Compose-порты привязаны к `127.0.0.1`. Telegram → ngrok → backend нельзя
автоматизировать в CI (Telegram требует HTTPS + setWebhook с реального домена) — отсюда live-прогон
вручную/через MCP, как в `docs/staging-smoke/08-webhook-ingestion.md`.

**Предусловия:**
- Throwaway-бот (например `SmokeTest_XYZ_bot`), **никогда** продакшен-маркетинг-бот.
- Подготовить тестовые воронки: keyword-воронка (со словом-триггером в `keywords`); `tag_added`- и
  `custom_field_set`-воронки; пара `event`-воронок-слушателей одного `event_name` для fan-out; воронка
  с шагом `EMIT_EVENT`, эмитящим тот же `event_name`.
- API-ключ генерируется в этой же задаче (сценарий 6 user-spec) — он же используется в curl-проверках `/events`.

**Tools:** Telegram MCP (keyword / EMIT_EVENT / tag-флоу), curl (`/events` коды, изоляция цепочек),
bash + `mongosh`/лог старта (миграция индекса, проверка `api_keys` hash-only, отсутствие авто-создания
подписчика).

**Edge cases / на что смотреть:**
- 401 должна быть **уніфікована** — байт-в-байт одинаковый ответ для missing / malformed / unknown ключа (анти-enumeration).
- Разграничить **404** (неизвестный подписчик) и **202 no-op** (подписчик есть, слушателя нет) — это разные ответы.
- Два под-кейса **400**: битый slug `event_name` и отсутствие обоих идентификаторов; при наличии обоих — `subscriber_id` побеждает.
- **fail-open rate-limit:** если Redis недоступен, 429 не сработает (это by design) — проверять 429 при поднятом Redis.
- **idempotent no-op не тригерит** — ключевая проверка для tag/field (Decision 5).
- **depth-cap / fan-out ceiling** — анти-цикл бекстопы покрыты IT (Task 14); здесь живьём не нагружаем,
  но если в логах при fan-out видны WARN-маркеры дропа — зафиксировать.
- Подписчик **не** создаётся `/events` (авто-регистрация только на `/start`).

**Findings:** код не правим. Любое расхождение с ожидаемым поведением — finding в отчёт
post-deploy verification + краткая запись в decisions.md; решение о фиксе — за пределами этой задачи.
