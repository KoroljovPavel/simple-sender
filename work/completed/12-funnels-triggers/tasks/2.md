# Task 2: Trigger-index reconciliation startup migration

## Required Skills

Перед выполнением задачи загрузи:
- `/skill:code-writing` — [skills/code-writing/SKILL.md](.claude/skills/code-writing/SKILL.md)

## Description

Phase 3 relaxes the funnel trigger-conflict guard so that **only `on_start` funnels stay unique** per
`(projectId, triggerType, triggerValue)`. Two active `event` / `keyword` / `tag_added` /
`custom_field_set` funnels sharing the same trigger value must coexist (this is the fan-out enabler —
Decision 1). The relaxation is expressed as a change to the partial-unique index's partial filter:
`{ status: 'active' }` → `{ status: 'active', triggerType: 'on_start' }`.

The problem (Decision 9): `spring.data.mongodb.auto-index-creation=true` **only creates** indexes — it
never drops or alters an index whose definition changed. So flipping the `@CompoundIndex` annotation on
`Funnel` (done in Task 1) is **not enough**: the old `projectId_triggerType_triggerValue_unique_active`
index (with the broad `{status:'active'}` filter) keeps existing on already-migrated databases and would
still block the second `event`/`keyword`/`tag`/`field` funnel.

This task adds an **idempotent startup `ApplicationRunner`** — `FunnelTriggerIndexReconciliation` —
that **drops the old index** at boot, guarded by `listIndexes()`. After the drop, Spring Data's
auto-index-creation recreates the index from the new annotation shape on the same startup. The runner
follows the established `FunnelStepIdBackfill` / `SuperAdminSeeder` pattern: `@Component implements
ApplicationRunner`, runs once per boot, **logs-but-never-throws** (the app must boot even if Mongo is
transiently unavailable), and is fully idempotent — a second boot finds nothing to drop and emits a
greppable no-op marker.

This is the de-risk spine of the whole feature: fan-out is silently broken if this migration is
forgotten, so the runner ships with its own slow IT alongside the existing `FunnelIndexesIT`.

## What to do

- Create `FunnelTriggerIndexReconciliation` in `com.botfunnel.funnel` — a `@Component` implementing
  `ApplicationRunner`, constructor-injecting `MongoTemplate`, patterned on `FunnelStepIdBackfill`.
- In `run(...)`: inspect the `funnels` collection indexes via `listIndexes()`. Find the index named
  `projectId_triggerType_triggerValue_unique_active`. If its `partialFilterExpression` is the **old**
  broad shape (`{status:'active'}` — i.e. it lacks the `triggerType:'on_start'` clause), **drop it**.
  Auto-index-creation will recreate the correct (`on_start`-only) shape from the Task 1 annotation.
- Make the decision idempotent by inspecting the actual `partialFilterExpression`, not by blindly
  dropping: if the index is absent (fresh DB — auto-index will create the new shape directly) or
  already carries the new `triggerType:'on_start'` filter, do **nothing** and log a greppable no-op
  marker. A blind unconditional drop is NOT idempotent-friendly (it would drop+recreate the correct
  index on every boot, churning the index and racing auto-index-creation).
- Wrap the whole body in `try/catch(Exception)`; log-and-swallow (mirror `FunnelStepIdBackfill.run`) so
  a transient Mongo fault never blocks app boot.
- Emit **distinct, greppable log markers**: one when the old index was dropped (migration applied), one
  when nothing needed doing (no-op). These markers are what the Verify-smoke step greps for.
- Write the tests below (TDD).

## Details

**Files:**
- `backend/src/main/java/com/botfunnel/funnel/FunnelTriggerIndexReconciliation.java` — NEW. The runner.
- `backend/src/test/java/com/botfunnel/funnel/FunnelIndexesIT.java` — UPDATE (this task owns it).
  Currently `funnelsCollectionHasExpectedIndexes` (lines ~62-77) asserts only the OLD partial filter
  (`pfe.getString("status") == "active"`, no `triggerType` clause) — that assertion must now also require
  `pfe.getString("triggerType") == "on_start"` (the new shape). Add two `@Tag("slow")` ITs: an
  `event`-coexist test and an `on_start`-collide test, modelling on the existing
  `activeFunnelTriggerUniquenessHoldsForEmptyTriggerValue` (lines ~114-139) and reusing the
  `activeFunnel(projectId, triggerValue)` helper — extend it (or add a sibling) to set `triggerType`
  so it can emit `event` funnels (the existing helper hardcodes `triggerType="on_start"` at line 146).
  These ITs are `@Tag("slow")` and depend on the migration runner having dropped the old broad-filter
  index during the same Testcontainers context startup — so the new partial-filter shape is real before
  the assertions run.
- (read-only) `Funnel.java` already carries the **new** annotation after Task 1; this runner only
  removes the **old** physical index so auto-index-creation can lay down the new one.

**Dependencies:** `depends_on: [1]`, Wave 2. The runner *code* itself is independent — it does not
import Task 1 code; it inspects/drops a named index by string, and Task 1 touches only `Funnel.java`
(no file overlap). **But this task OWNS the updated `FunnelIndexesIT`**, whose Phase-3 assertions verify
the new `{status:'active', triggerType:'on_start'}` partial-filter shape. That shape only materializes at
Testcontainers context startup from Task 1's `@CompoundIndex` annotation change (auto-index-creation
recreates the index after this runner drops the old broad-filter one). So the owned IT has a
consumer-verifies-producer dependency on Task 1: running/verifying Task 2 before Task 1 lands makes the
ITs fail. Hence `depends_on: [1]` and Wave 2 (must run after Task 1's Wave 1). Wave 2 also holds Task 4 —
no file overlap with this task, so parallel execution is fine. No new packages.

**Edge cases:**
- Fresh DB / index absent → no-op (auto-index-creation creates the new shape; nothing to drop).
- Index already in the new `triggerType:'on_start'` shape → no-op (idempotent re-boot).
- Index present in the old `{status:'active'}` shape → drop; auto-index recreates new shape same boot.
- Mongo transiently down → swallow, log, boot anyway (never throw).
- The old index name and the new index name are the **same**
  (`projectId_triggerType_triggerValue_unique_active`) — distinguish old vs new by the
  `partialFilterExpression` contents, NOT by name.

**Implementation hints (NOT pseudocode):**
- Use `mongoTemplate.getCollection("funnels").listIndexes()` and collect into a `List<Document>` by
  inlining the `listIndexes().into(new ArrayList<>())` call directly. Note: `FunnelIndexesIT.indexes(...)`
  does the same thing but is a **private** helper inside the IT class and cannot be called from the
  runner — inline the `listIndexes().into(result)` collection here rather than trying to reuse it.
- Find the target index by its `name` field; read its `partialFilterExpression` (a `Document`). The old
  shape has only a `status` key; the new shape additionally has `triggerType`.
- Drop with `mongoTemplate.getCollection("funnels").dropIndex(indexName)`.
- Keep the run-body inside `try/catch(Exception)`; on catch, `log.error(...)` and return — mirror
  `FunnelStepIdBackfill.run`.
- Log markers should be stable strings (e.g. an explicit phrase the smoke grep can match), one for the
  applied path (`log.info`) and one for the no-op path (`log.info`/`log.debug`). Do not log PII.
- The `Funnel` static-initializer already pins `FunnelStatus.active.name() == "active"`; rely on the
  literal `"active"` / `"on_start"` strings to match the persisted filter values.
