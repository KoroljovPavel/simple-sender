# Task 4: FunnelEventService — subscriber-keyed fan-out dispatcher + loop backstops

## Required Skills

Перед выполнением задачи загрузи:
- `/skill:code-writing` — [skills/code-writing/SKILL.md](.claude/skills/code-writing/SKILL.md)

## Description

This task builds the **single internal dispatcher** that all four Phase-3 trigger sources
(`keyword` via webhook, `tag_added` / `custom_field_set` via the subscriber writers, `event` via the
public API and the `EMIT_EVENT` step) will call to start funnels. It is the spine of Wave 2 — every
Wave-3/4 task depends on it, so it must exist and be correct before its callers wire in.

Today funnel firing happens only through `FunnelTriggerServiceImpl.fire(projectId, chatId,
"on_start", payload)`: chatId-keyed, single-result, one execution per firing. Phase 3 needs a
**sibling subscriber-keyed entrypoint** that **fans out** — one firing can match N active funnels and
start N executions (Decision 1: "one event → N funnels" achieved by N funnels sharing a trigger
value, enabled by the index relax that Task 1 ships). The new entrypoint is keyed by `subscriberId`
(not chatId) because tag/field/event triggers originate from a subscriber, not a Telegram chat.

The new `FunnelEventService` (`@Service`) owns this fan-out plus **three independent loop backstops**
that bound runaway cascades (tag→funnel→tag, `EMIT_EVENT` fan-out, A→B→A chains). It is
**error-isolated** (`try/catch(Throwable)`, greppable WARN) exactly like the existing
`FunnelTriggerServiceImpl.fire` — a dispatch fault must never escalate to a 5xx, a failed webhook job,
or a JobRunr retry-storm.

It deliberately **reuses** the existing `insertExecution` / `cancelExistingForPair` execution-creation
logic (Decision 2) rather than forking a second writer — and it reaches it through a **required**
extracted package-private collaborator bean (`FunnelExecutionFactory`). `FunnelEventService` must have
**zero dependency** on `FunnelTriggerServiceImpl`: both services inject the factory instead. This is not
a stylistic preference — it **structurally guarantees** that no Spring bean cycle can form when Task 5
wires the dispatcher into `StepExecutor`. A direct `FunnelEventService → FunnelTriggerServiceImpl` edge
would close the fatal cycle `FunnelEventService → FunnelTriggerServiceImpl → FunnelExecutionEngine →
StepExecutor → FunnelEventService` at that point (see the CRITICAL Edge case). It also reuses the
`SubscriberServiceImpl.startRateLimitExceeded` Redis fail-open INCR/EXPIRE idiom (Decision 10) for the
auto-enroll rate-limit. The `on_start` `fire(...)` path stays **untouched** (its single-result
contract must not regress).

Naming is deliberate (Decision 4): `FunnelEventService` is distinct from the `events` audit collection
and the `subscriber_events` CRM feed — it is the in-process dispatcher, not a bus that anything reads
back.

## What to do

1. **Expose the reusable execution-creation path WITHOUT closing a Spring cycle.** The fan-out loop must
   create executions through the existing `insertExecution` / `cancelExistingForPair` logic
   (Decision 2 — do not fork a second writer). `insertExecution` and `cancelExistingForPair` are
   currently `private` on `FunnelTriggerServiceImpl` (see lines 408 and 426) — same-package classes
   **cannot** call private methods, so the wording "package-visible" means literally **dropping the
   `private` modifier** (making them package-private), not just "same package".

   **REQUIRED approach — extract the `FunnelExecutionFactory` collaborator bean.** Do NOT inject
   `FunnelTriggerServiceImpl` into `FunnelEventService`, and do NOT reach for `@Lazy` to paper over a
   cycle. Instead, extract a small package-private `@Component` (`FunnelExecutionFactory`) that owns the
   depth-aware `insertExecution(..., int enrollDepth)` + `cancelExistingForPair(...)` logic, and have
   **both** `FunnelTriggerServiceImpl` and `FunnelEventService` inject *that* factory. `FunnelEventService`
   must end up with **zero dependency** on `FunnelTriggerServiceImpl`.

   This is mandatory because of cross-task integration, not aesthetics: the factory has **no edge back
   into** `FunnelExecutionEngine`/`StepExecutor`, so the cycle `FunnelEventService → FunnelTriggerServiceImpl
   → FunnelExecutionEngine → StepExecutor → FunnelEventService` can **never form** — including in Task 5,
   when `StepExecutor` injects `FunnelEventService` to dispatch `EMIT_EVENT`. If instead Task 4 left a
   direct `FunnelEventService → FunnelTriggerServiceImpl` edge, the context would still start cleanly at
   Task 4 completion (the cycle is not yet closed) — and then **Task 5 would break startup** with
   `BeanCurrentlyInCreationException`. The factory extraction closes that trap structurally at this task,
   so the "context starts cleanly" check cannot falsely pass.

   The depth-aware insert accepts an explicit `enrollDepth` to stamp on the new `FunnelExecution`;
   `fire(...)` calls the factory with depth 0 and stays behaviourally identical.

2. **Consume the LIST + keyword repository queries from `FunnelRepository`** (do NOT add them here —
   **Task 1 owns all `FunnelRepository` changes**: it ships the **list** variant returning all active
   funnels matching `(projectId, triggerType, triggerValue)` for `event` / `tag_added` /
   `custom_field_set`, the active-`keyword`-funnels-for-a-project query, AND it retains the
   single-result `Optional` lookup that `on_start` still uses). Task 4 only **calls** these queries
   from the fan-out loop; the contains-match over each funnel's `keywords` list is done here in code,
   not in the query (Decision 3). Task 4 `depends_on [1]`, so these queries are available — do not
   touch `FunnelRepository.java`.

3. **Create `FunnelEventService` (`@Service`, singleton)** with the single public entrypoint:
   `dispatchForSubscriber(String projectId, String subscriberId, String triggerType, String matchKey,
   int originDepth)`. Behaviour:
   - Resolve the subscriber by id via the service boundary. `SubscriberService` today exposes ONLY
     `findByChat` — there is **no** lookup-by-id at the service boundary. **Task 4 is the SOLE OWNER /
     CREATOR of this method**: ADD the canonical project-scoped
     `Optional<Subscriber> findById(String projectId, String subscriberId)` to `SubscriberService` /
     `SubscriberServiceImpl` here (see Edge cases — `SubscriberRepository.findById` exists but must be
     **project-scoped** at the service layer, filtering the repo result by `projectId` and returning
     empty on mismatch, to prevent IDOR; never reach into `SubscriberRepository` from the `funnel`
     package). Task 7 (which `depends_on [3,4]` and runs after) will **read / reuse** this exact method —
     it does NOT add its own; pin the canonical signature so Task 7 wires straight onto it. Record the
     ownership in `decisions.md`. Load the `Subscriber` to confirm project scope / get its telegram
     identity; a missing subscriber → greppable WARN no-op.
   - Resolve the project's CONNECTED bot to pin `telegramBotId` on the created executions (mirror
     `fire()`'s bot resolution); no connected bot → greppable WARN no-op.
   - Query the LIST of active matching funnels: for `keyword`, scan active keyword funnels and
     contains-match `matchKey` (lowercased) against each funnel's `keywords` list (case-insensitive,
     any-of-many); for `tag_added` / `custom_field_set` / `event`, list-match on `triggerValue ==
     matchKey`.
   - Loop the matched funnels and create one execution per match via the reused insert path, stamping
     `enrollDepth = originDepth` on each — fan-out, subject to the backstops below.
   - The whole method body is `try/catch(Throwable)` — a fault is logged (greppable WARN) and
     swallowed; the method NEVER throws outward.

4. **Enforce the three independent loop backstops** (Decision 6), each greppable-WARN on drop:
   - **(a) Volume — per-subscriber auto-enroll rate-limit.** ≤ 20 auto-starts/min, Redis fail-open,
     key `bf:rate:auto-enroll:{subscriberId}` (INCR + EXPIRE-on-first-set, fail-open on Redis error
     with WARN — reuse the `SubscriberServiceImpl.startRateLimitExceeded` idiom). **Only auto enrolls
     (`originDepth > 0`) count** against this limit; human/external roots (`originDepth == 0`:
     manual-UI tag, `/start`, keyword, external api-event) are exempt — do not even touch Redis for
     them. Over limit → drop the whole dispatch + WARN.
   - **(b) Depth — `enrollDepth` cap.** Redis-independent hard cap of **10**. When `originDepth`
     exceeds the cap, drop + WARN, **even when Redis is down**. This closes the fail-open hole the
     volume limit leaves during a Redis outage. (Confirm the `> 10` vs `>= 10` boundary — see Edge
     cases.)
   - **(c) Fan-out width — per-dispatch ceiling.** Redis-independent. A single firing inserts at most
     `app.funnel.max-fanout-per-event` (default 50) executions; excess matched funnels are dropped +
     WARN. Bounds request width even with Redis down.

5. **Add the config property.** `app.funnel.max-fanout-per-event=${FUNNEL_MAX_FANOUT_PER_EVENT:50}` in
   `application.properties` (alongside the existing `app.funnel.*` block), injected into
   `FunnelEventService` via `@Value`. The auto-enroll limit (20/min) and depth cap (10) may be
   constants or env-tunable — match the surrounding convention; if env-tunable, add the property here
   too.

6. **Write the unit + integration tests** listed in TDD Anchor — backstops in isolation, fan-out,
   error-isolation, keyword matching, and the depth/auto-enroll semantics.

## Acceptance Criteria

- [ ] `FunnelEventService` is a single `@Service` (singleton) with
      `dispatchForSubscriber(projectId, subscriberId, triggerType, matchKey, originDepth)`.
- [ ] Fan-out works: one firing matching N active funnels starts N executions for the one subscriber;
      each execution carries `enrollDepth == originDepth`.
- [ ] Keyword matching is contains / case-insensitive / any-of-many over each funnel's `keywords`
      list (code-side scan, not a query).
- [ ] All three backstops are enforced and independently testable: volume rate-limit (Redis
      fail-open, counts `originDepth > 0` only, key `bf:rate:auto-enroll:{subscriberId}`), depth cap
      of 10 (Redis-independent), fan-out ceiling `app.funnel.max-fanout-per-event` default 50
      (Redis-independent). Both Redis-independent caps are proven with Redis unavailable.
- [ ] `originDepth == 0` (human/external root) is exempt from the volume limit and never consults
      Redis.
- [ ] The method is error-isolated (`try/catch(Throwable)`): a dispatch fault is swallowed + WARN, the
      method never throws outward.
- [ ] Execution creation reuses the existing `insertExecution` / `cancelExistingForPair` logic (no
      forked second writer) — via the **required** extracted package-private collaborator bean
      `FunnelExecutionFactory`; the `on_start` `fire(...)` path is unchanged (its tests stay green).

- [ ] Subscriber-by-id resolution goes through a **project-scoped** `SubscriberService.findById`
      boundary method that **Task 4 creates and owns** (Task 7 reuses it, adds none of its own); the
      `funnel` package never touches `SubscriberRepository` directly.
- [ ] Task 4 does **not** modify `FunnelRepository.java` (Task 1 owns those queries) — it only consumes
      the list/keyword/single-result queries Task 1 ships.
- [ ] `app.funnel.max-fanout-per-event` exists in `application.properties` (default 50, env-tunable).
- [ ] All new unit + integration tests pass; existing funnel tests stay green (no regressions).

**Edge cases:**
- **CRITICAL — Circular Spring bean dependency.** `FunnelTriggerServiceImpl` injects
  `FunnelExecutionEngine`, which injects `StepExecutor`. In **Task 5**, `StepExecutor` will inject
  `FunnelEventService` (to dispatch `EMIT_EVENT`). If `FunnelEventService` injects
  `FunnelTriggerServiceImpl` directly, the bean graph becomes a cycle —
  `FunnelEventService → FunnelTriggerServiceImpl → FunnelExecutionEngine → StepExecutor →
  FunnelEventService` — and Spring throws **`BeanCurrentlyInCreationException`** at startup (constructor
  injection cannot resolve a cycle). The implementer MUST break the cycle **structurally** by extracting
  the `insertExecution`/`cancelExistingForPair` logic into a small package-private collaborator bean
  (`FunnelExecutionFactory`) that BOTH `FunnelTriggerServiceImpl` and `FunnelEventService` inject — the
  factory has no edge back into the engine, so no cycle can form. `FunnelEventService` must have **zero
  dependency** on `FunnelTriggerServiceImpl`. Do **NOT** use `@Lazy` to mask the edge — it pushes the
  burden onto Task 5 and leaves the landmine in place. **Why this matters at THIS task even though Task 5
  is what closes the cycle:** at Task 4 completion the `StepExecutor → FunnelEventService` edge does not
  exist yet, so a direct `FunnelEventService → FunnelTriggerServiceImpl` edge would let the context start
  cleanly now — a "context starts cleanly" check would **falsely pass** — and then Task 5 would break
  startup. The factory removes that trap before it can be sprung. Verify the structural guarantee (see
  Verification › Automated bean-graph check) BEFORE considering the task done — this is a startup-fatal,
  not a runtime, failure.
- **Subscriber-by-id boundary lookup (must be added).** The dispatcher receives a `subscriberId` (not a

  `findByChat` — there is **no** `findById` / lookup-by-id at the service boundary. `SubscriberRepository`
  has `findById(subscriberId)`, but the `funnel` package must NOT call the repository directly (keeps
  the module boundary — see `fire()`'s rule). So **ADD** a minimal project-scoped
  `Optional<Subscriber> findById(String projectId, String subscriberId)` to `SubscriberService` /
  `SubscriberServiceImpl`. It MUST be **project-scoped** (filter the repository result by `projectId`,
  return empty on mismatch) to prevent IDOR — even though the in-process caller is trusted, the
  `subscriberId` arriving via the public `event` API / `EMIT_EVENT` is attacker-influencable.
  **Task 4 is the SOLE OWNER/CREATOR of this method** — add the boundary method here, with the canonical
  signature `Optional<Subscriber> findById(String projectId, String subscriberId)`. Task 7
  (`depends_on [3,4]`, runs after) READS and REUSES it for the API's lookup-by-id; Task 7 adds none of
  its own. Record the ownership in `decisions.md`.
- **Depth cap boundary.** Confirm whether the drop is at `originDepth > 10` or `>= 10`. The tech-spec
