# Task 5: Funnel-step trigger integration (tag/field hooks + EMIT_EVENT + depth threading)

## Required Skills

Перед выполнением задачи загрузи:

## Description

Phase 3 wave-3 task that turns funnel-execution side-effects into active triggers. Three coupled
changes, all in the funnel/subscriber boundary (this task is the **single owner** of `StepExecutor.java`
in this feature; Task 6 owns the webhook keyword path, no file overlap):

1. **Tag / field hooks (Decision 5).** Fire `tag_added` inside `SubscriberServiceImpl.addTag` and
   `custom_field_set` inside `recordCustomFieldsSet`, **after** the existing idempotency guard
   (`getModifiedCount() == 0` / empty `changedKeys`) and **after** the existing `writeSubscriberEvent`
   audit write. These two methods are the verified sole writers — hooking here makes a tag/field
   change a trigger from every call site (manual controllers + funnel `ADD_TAG`/`SET_CUSTOM_FIELD`
   steps) without double-firing and without firing on a no-op write.

2. **EMIT_EVENT step (Decision 4).** Add the `EMIT_EVENT` case to `StepExecutor.execute(...)`: it
   synchronously dispatches the step's event (the `event` namespace, keyed by `eventName`) for the
   current subscriber via `FunnelEventService`, then returns `StepResult.cont()` (CONTINUE) so the
   parent funnel proceeds. Same `event` namespace as the external API event (Task 7).

3. **Explicit depth threading (Decision 6).** Origin depth is propagated as an **explicit method
   parameter** — never a ThreadLocal (the funnel sweep runs on arbitrary JobRunr / virtual threads).
   Manual controllers and the public API pass depth **0** (human/external root); funnel-step callers
   (`StepExecutor`) pass `execution.getEnrollDepth() + 1` so an auto child is correctly counted toward
   the volume rate-limit (depth > 0) and the depth cap. The depth value is threaded into the
   `addTag` / `recordCustomFieldsSet` writers and into the `FunnelEventService.dispatchForSubscriber`
   call from the EMIT_EVENT case.

WHY: makes tags / fields / emit active triggers with the correct enroll depth, without firing on no-op
writes — the trigger surface every other Wave-3+ source builds on.

This task **depends on Task 4** (`FunnelEventService` + `dispatchForSubscriber(projectId,
subscriberId, triggerType, matchKey, originDepth)`) and **Task 1** (`StepType.EMIT_EVENT`,
`FunnelStep.eventName`, `FunnelExecution.enrollDepth`). If those symbols are not yet present when this
task starts, coordinate with the wave order — do not re-create them here.

**Read the FINAL Task-4 signatures — do not guess or re-declare them.** Before writing any code, open
the **completed** `FunnelEventService` (Task 4) and read the exact `dispatchForSubscriber(...)` signature
and the project-scoped subscriber-by-id lookup method Task 4 added to `SubscriberService` (e.g.
`Optional<Subscriber> findById(String projectId, String subscriberId)`). Call those methods verbatim —
do NOT re-declare, overload, or invent a parallel lookup/dispatch signature. If Task 4's final
parameter order or names differ from what this task file sketches, Task 4 is the source of truth.

**Closing edge of the Spring bean cycle (critical).** This task introduces the edge `StepExecutor →
FunnelEventService` that *closes* the potential bean cycle
(`FunnelEventService → FunnelTriggerServiceImpl → FunnelExecutionEngine → StepExecutor →
FunnelEventService`). Task 4 *structurally prevents* the cycle by routing `FunnelEventService` through the
extracted `FunnelExecutionFactory` (not `FunnelTriggerServiceImpl`). But Task 5 is the task that actually
closes the loop, so Task 5 must **prove** the application context still starts cleanly after the injection
— a `@SpringBootTest` context-load assertion is sufficient (see Acceptance Criteria + Verification).

## What to do

1. **Thread the depth parameter through the `SubscriberService` contract.** Add an explicit
   `int originDepth` parameter to the two trigger-firing writers: `addTag(projectId, subscriberId,
   slug, originDepth)` and `recordCustomFieldsSet(projectId, subscriberId, oldValues, newValues,
   originDepth)`. Update the interface Javadoc to document the depth semantics (0 = human/external
   root; `execution.enrollDepth + 1` = funnel-step-originated child). Decide the cleanest contract
   shape (overload vs. single signature) — but every caller must pass an explicit depth; no implicit
   default that hides the funnel-vs-manual distinction.

2. **Fire the triggers in `SubscriberServiceImpl`** — strictly after the existing guard + audit write:
   - In `addTag`: after `tagService.incrementCounter(...)` + `writeSubscriberEvent(... EVT_TAG_ADDED
     ...)`, dispatch `tag_added` for `subscriberId` with `matchKey = slug` and the supplied
     `originDepth` via `FunnelEventService.dispatchForSubscriber`.
   - In `recordCustomFieldsSet`: after `writeSubscriberEvent(... EVT_CUSTOM_FIELD_SET ...)`, dispatch
     `custom_field_set` for `subscriberId`. The match key is the changed field **key** — if a single
     PATCH changed several keys, dispatch per changed key (the `changedKeys` list already exists),
     so each `custom_field_set` listener funnel fires on its own key. Pass the supplied `originDepth`.
   - The early-return no-op branches (tag already present / empty `changedKeys`) must **not** dispatch.

3. **Update the manual callers to pass depth 0:**
   - `SubscriberController.addTag(...)` → `subscriberService.addTag(project.getId(), id, request.slug(), 0)`.
   - `SubscriberController.removeTag` does **not** fire a trigger (only `tag_added` is a trigger; tag
     removal stays unchanged) — verify no signature change leaks there unless you choose to keep
     `removeTag` symmetric without a trigger dispatch.
   - `SubscriberCustomFieldsController.setCustomFields(...)` → the `recordCustomFieldsSet(...)` call
     passes `0`.

4. **Update the funnel-step callers in `StepExecutor` to pass `enrollDepth + 1`:**
   - `ADD_TAG` case → `subscriberService.addTag(execution.getProjectId(), execution.getSubscriberId(),
     step.getTagSlug(), execution.getEnrollDepth() + 1)`.
   - `SET_CUSTOM_FIELD` (`setCustomField`) → the `recordCustomFieldsSet(...)` call passes
     `execution.getEnrollDepth() + 1`.
   - `REMOVE_TAG` stays unchanged (no trigger).

5. **Add the `EMIT_EVENT` case to `StepExecutor.execute(...)`:** a new `switch` arm that calls
   `funnelEventService.dispatchForSubscriber(execution.getProjectId(), execution.getSubscriberId(),
   <event triggerType>, step.getEventName(), execution.getEnrollDepth() + 1)` — using the **exact**
   `dispatchForSubscriber(...)` signature from the completed Task 4 (read it; do not guess the parameter
   order) — and yields `StepResult.cont()`. Inject `FunnelEventService` via the constructor. The dispatch
   is synchronous; `FunnelEventService` already owns error-isolation + the three backstops (Task 4) —
   `StepExecutor` must **not** add a second try/catch that swallows a genuine engine fault differently.
   Keep the no-PII logging convention (ids/codes only — never the event payload).

   **Guard — do NOT add backstop / rate-limit logic in this task.** The three loop backstops (volume
   rate-limit, depth cap, fan-out ceiling) live **solely** in `FunnelEventService` (Task 4).
   `SubscriberServiceImpl` and `StepExecutor` must **not** add any rate-limit / depth-cap / fan-out
   guard, nor touch Redis for enrollment limiting. `SubscriberServiceImpl` only fires `tag_added` /
   `custom_field_set` via the dispatcher **after** its existing idempotency guard; `StepExecutor` only
   dispatches `event`. All loop-protection is delegated to `FunnelEventService`.

6. Confirm the engine call site (`FunnelExecutionEngine` line ~256, `stepExecutor.execute(step, exec,
   ctx.subscriber(), ctx.bot())`) needs **no** change — `exec` already carries `enrollDepth`, so depth
   reads off `execution` inside `StepExecutor`, not a new engine parameter.

**Dependencies:**

  originDepth)` — the single dispatcher; owns the three loop backstops + error-isolation.

**Edge cases:**
- Idempotent no-op write (tag already present; empty `changedKeys`) → MUST NOT dispatch.
- Multi-key custom-field PATCH → one `custom_field_set` dispatch per changed key (use `changedKeys`).
- `EMIT_EVENT` with a null/blank `eventName` should never have passed `FunnelService` validation
  (Task 1) — but the dispatcher is error-isolated, so a stray blank key degrades to a no-op fan-out,
  not a thrown step. Do not add a redundant guard that changes the `CONTINUE` contract.
- Depth read happens off `execution` inside `StepExecutor` — the engine call site does not gain a new
  parameter (the `enrollDepth` already rides on the execution snapshot).
- A non-funnel manual write must be depth `0` so it is exempt from the per-subscriber 20/min
  auto-enroll volume limit (Decision 6: auto = depth > 0).
- **Context fails to start with `BeanCurrentlyInCreationException` after wiring `FunnelEventService` into
  `StepExecutor`** → the Task-4 `FunnelExecutionFactory` cycle-break was NOT applied correctly.
  `FunnelEventService` must reach execution-creation through the extracted package-private
  `FunnelExecutionFactory`, NOT by injecting `FunnelTriggerServiceImpl` directly (the direct edge closes
  `FunnelEventService → FunnelTriggerServiceImpl → FunnelExecutionEngine → StepExecutor →
  FunnelEventService`). This is a Task-4 defect surfaced by Task-5's closing edge — flag it back to
  Task 4; do NOT paper over it with `@Lazy` or a workaround inside `StepExecutor`.

**Implementation hints:**
- **Read Task 4's FINAL signatures before coding — do not guess.** Open the completed `FunnelEventService`
  and use its actual `dispatchForSubscriber(...)` parameter order/names verbatim, and reuse the
  project-scoped subscriber-by-id lookup method Task 4 added to `SubscriberService` (e.g.
  `findById(projectId, subscriberId)`) — do NOT re-declare, overload, or invent a parallel lookup. If this
  task file's sketched signatures differ from Task 4's reality, Task 4 wins.
- **Do NOT add backstop logic here.** The three loop backstops (volume rate-limit, depth cap, fan-out
  ceiling) live solely in `FunnelEventService` (Task 4). `SubscriberServiceImpl` and `StepExecutor` add
  NO rate-limit / depth-cap / fan-out guard and do NOT touch Redis for enrollment limiting.
  `SubscriberServiceImpl` only fires `tag_added` / `custom_field_set` via the dispatcher after its
  idempotency guard; depth is passed through as a plain `int originDepth` argument, nothing more.
- Follow the established sole-writer pattern (patterns.md "Reuse the sole writers for subscriber
  mutations") — do NOT fork a second audit or trigger writer; both side effects live inside the
