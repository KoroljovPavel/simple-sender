# Task 6: Keyword webhook path + waiting_for_reply precedence

## Required Skills

Перед выполнением задачи загрузи:
- `/skill:code-writing` — [skills/code-writing/SKILL.md](.claude/skills/code-writing/SKILL.md)

## Description

Сделать так, чтобы бот реагировал на свободный текст по ключевым словам (`keyword`-триггер),
**не перехватывая** меню. Сейчас в `ProcessTelegramUpdateJob.dispatch(...)` ветка обычного текста
(не команда, private-чат) только апсертит подписчика и пишет `telegram_message_received` —
никакого keyword-матчинга нет. Этот таск добавляет в эту ветку, **после** апсерта подписчика:

1. Резолв подписчика по `(projectId, telegramBotId, chatId)`.
2. Проверку precedence: если у подписчика есть **in-flight** execution в статусе
   `waiting_for_reply` (подписчик стоит в меню и ждёт нажатия кнопки) — keyword **пропускается**
   (меню имеет приоритет, Decision 3 user-spec); execution меню не трогается, новый funnel не
   стартует.
3. Иначе — диспатч keyword-матчинга через `FunnelEventService.dispatchForSubscriber(...)`
   (contains-match, fan-out — Task 4), который сам сканирует активные keyword-funnel'ы и стартует
   все совпавшие.

Весь keyword-диспатч обёрнут в `try/catch(Throwable)`: любая ошибка глотается (greppable WARN),
воркер всё равно возвращается успешно и помечает rawUpdate `DONE` → HTTP 200, JobRunr-джоб не
падает (error-isolation, Decision 12). Это зеркалит существующую конвенцию `FunnelTriggerServiceImpl`
(`fire` / `cancelActiveFor` / `advanceOnCallback` все swallow-all).

Команды (`/start`, `/stop`) остаются в своей ветке — keyword их не касается. Этот таск **не**
создаёт `FunnelEventService` (он приходит из Task 4, зависимость) — только подключает его как
вызывающую сторону в webhook.

## What to do

- В `ProcessTelegramUpdateJob` внедрить зависимость на `FunnelEventService` (из Task 4) через
  конструктор; для precedence-проверки понадобится также `MongoTemplate` (уже есть в классе) для
  запроса `funnel_executions` по `(projectId, subscriberId, status=waiting_for_reply)`.
- В ветке обычного текста (`dispatch(...)`, блок `isPrivate && chatId != null`, **после**
  `subscriberService.upsertFromTelegramUpdate(...)`):
  - Резолвить подписчика через `subscriberService.findByChat(projectId, bot.getTelegramBotId(),
    chatId)` (already exists). Если подписчик не нашёлся — keyword пропустить (только лог-событие
    как сейчас).
  - Проверить наличие in-flight `waiting_for_reply` execution для этого подписчика
    (`projectId` + `subscriberId` + `status == waiting_for_reply.name()`, lowercase-литерал —
    Decision 14). Если есть → keyword **suppressed** (menu precedence), funnel не стартует, лог
    (debug/info) о пропуске.
  - Иначе → вызвать `funnelEventService.dispatchForSubscriber(projectId, subscriber.getId(),
    "keyword", text, /*originDepth*/ 0)` (точное имя/сигнатуру метода взять из готового Task 4 —
    keyword это human-root, depth 0).
  - Весь этот keyword-блок обернуть в `try/catch(Throwable)` со swallow + greppable WARN; падение
    keyword'а НЕ должно мешать дальнейшему `logEventMessageReceived(...)` и успешному завершению
    воркера.
- `logEventMessageReceived(...)` по-прежнему вызывается в конце ветки (поведение Phase-1
  сохраняется — keyword добавочный, не заменяющий).
- Поведение остальных веток (`/start`, `/stop`, callback_query, media, non-private) — без изменений.

## Acceptance Criteria

- [ ] Обычный текст в private-чате (подписчик не в меню) запускает все совпавшие по contains-match
      keyword-funnel'ы через `FunnelEventService` (fan-out — Task 4).
- [ ] Если у подписчика есть in-flight `waiting_for_reply` execution — keyword **подавляется**:
      новый funnel не стартует И execution меню остаётся нетронутым (menu precedence).
- [ ] Ошибка keyword-диспатча проглатывается (greppable WARN), воркер возвращает успех (rawUpdate
      `DONE` → HTTP 200), JobRunr-джоб не помечается failed (error-isolation, Decision 12).
- [ ] Команды (`/start`, `/stop`) и не-текстовые/не-private апдейты keyword не запускают.
- [ ] `telegram_message_received` событие по-прежнему пишется (поведение Phase-1 не регрессирует).
- [ ] Все существующие webhook/funnel тесты остаются зелёными (нет регрессий).

## Details

**Files:**
- `backend/src/main/java/com/botfunnel/webhook/ProcessTelegramUpdateJob.java` — добавить
  конструкторную зависимость `FunnelEventService funnelEventService`; в `dispatch(...)`, в блоке
  обычного текста (`isPrivate && chatId != null`, после `upsertFromTelegramUpdate`), вставить
  keyword-блок: resolve subscriber → precedence-check (`waiting_for_reply`) → dispatch, всё в
  `try/catch(Throwable)` со swallow + WARN. `logEventMessageReceived(...)` остаётся последним
  вызовом ветки.

**Dependencies:**
- Task 4 (`FunnelEventService.dispatchForSubscriber(...)`) — **должен быть готов** до этого таска
  (depends_on: [4]). Без него keyword-вызов не скомпилируется.
- Файловых пересечений с Task 5 (тот же Wave 3) нет: Task 5 трогает subscriber/StepExecutor, Task 6
  — только `ProcessTelegramUpdateJob`.
- Пакеты: новых нет (всё через существующие Spring/Mongo зависимости).

**Edge cases:**
- Подписчик не найден `findByChat(...)` (теоретически возможно, хотя апсерт только что прошёл) →
  keyword пропустить, обычный event-лог отработать.
- Bot не CONNECTED (уже отсекается в начале ветки — `logEventOther(..., "unknown")`); keyword туда
  не добавлять.
- Несколько keyword-funnel'ов совпали → fan-out обрабатывает Task 4 (с fan-out-ceiling); здесь
  только один вызов `dispatchForSubscriber`.
- `text` пустой/служебный — диспатч-сторона (Task 4) сама решает no-match; webhook не фильтрует
  заранее (кроме уже существующего `text == null` → media-ветка).
- `waiting_for_reply`-проверка должна использовать lowercase-литерал
  `ExecutionStatus.waiting_for_reply.name()` (Decision 14) — UPPERCASE даст zero-match и сломает
  precedence.

**Implementation hints (НЕ псевдокод):**
- Subscriber-резолв и форму waiting_for_reply-критерия можно подсмотреть в `FunnelTriggerServiceImpl`
  (строки ~175-205): `subscriberService.findByChat(...)` + `Criteria.where("projectId").is(...)
  .and("subscriberId").is(...).and("status").is(waiting_for_reply.name())`. **ВАЖНО:** метод
  `cancelActiveFor` использует `updateMulti` — он **деструктивный** (отменяет executions), его НЕЛЬЗЯ
  вызывать для precedence-проверки. Precedence-проверка строго **read-only**: построй тот же
  `Query`/`Criteria` по `(projectId, subscriberId, status == waiting_for_reply.name())` и используй
  `mongoTemplate.exists(query, FunnelExecution.class)` (только наличие, без какого-либо update).
- Error-isolation: НЕ добавлять локальный swallow, который скроет реальный сбой воркера — оборачивать
  только keyword-блок; остальной воркерный `try/catch(Throwable)` в `handle(...)` оставить как есть.
  Точно как комментарий у `advanceOnCallback` в `dispatch`-е: «best-effort swallow-all … must NOT
  poison the worker».
- WARN должен быть greppable (стабильный префикс-маркер, как `LOG_CANCEL_ERROR` в импле), без PII —
  логировать `projectId` + `t.getClass().getSimpleName()`, не текст сообщения подписчика.
- Точную сигнатуру/имя `dispatchForSubscriber` и тип `triggerType` ("keyword") сверить с готовым
  Task 4 — не угадывать.
