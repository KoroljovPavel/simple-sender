# Task 7: API-key security chain + EventsController

## Required Skills

Перед выполнением задачи загрузи:
- `/skill:code-writing` — [skills/code-writing/SKILL.md](../../../.claude/skills/code-writing/SKILL.md)

## Description

Lay the first rails of the public API: a dedicated key-authenticated security chain on
`/api/integrations/**` plus the external event-ingress endpoint
`POST /api/integrations/v1/events`. External systems (e.g. a broadcast platform, a CRM webhook)
call this endpoint with a per-project API key to drive funnels — the `event` trigger namespace
shared with the in-funnel `EMIT_EVENT` step (Decision 4).

Two things are built:

1. **Key-authenticated `SecurityFilterChain` (`@Order(1)`, Decision 7).** A higher-priority
   STATELESS chain with `securityMatcher("/api/integrations/**")`, CSRF disabled (cookieless,
   header-key auth), and a custom `OncePerRequestFilter` that resolves the project **from the
   presented key** (no `{projectId}` in the path → anti-IDOR). Any key problem — missing,
   malformed, or unknown — yields a **uniform 401** (anti-enumeration). On a valid key the filter
   stamps `lastUsedAt` and pins the resolved project for the controller. The existing session chain
   (`appSecurityFilterChain`) is demoted to `@Order(2)` so its broad `/api/**` matcher no longer
   shadows the public namespace.

2. **`EventsController` — `POST /api/integrations/v1/events` (Decisions 7, 10, 12).** Validates the
   request DTO, applies a global fixed Redis rate-limit (fail-open, 429 over limit), resolves the
   subscriber **project-scoped** (using the project pinned by the key filter), and dispatches via
   `FunnelEventService.dispatchForSubscriber(..., originDepth = 0)` (external = root). The full
   response-code matrix is **202 / 400 / 404 / 401 / 429**, and the endpoint **never** returns a 5xx
   and **never** auto-creates a subscriber: an engine fault is swallowed → 202 (event accepted,
   error-isolation, Decision 12).

This is Wave 4 — it depends on Task 3 (`ApiKeyService`, the credential it authenticates against) and
Task 4 (`FunnelEventService`, the dispatcher it calls). Both must exist before this task runs.

## What to do

1. **Add the key-authenticated chain to `SecurityConfig`.**
   - Add a new `SecurityFilterChain` bean annotated `@Order(1)` that uses
     `http.securityMatcher("/api/integrations/**")`, sets the session policy to STATELESS, disables
     CSRF, disables `httpBasic`/`formLogin`, requires all matched requests to be authenticated, and
     installs the new api-key filter (e.g. `addFilterBefore(...)` before the auth-entry point).
   - Annotate the existing `appSecurityFilterChain` bean `@Order(2)` so the integrations chain is
     evaluated first and the session chain's `/api/**` matcher no longer shadows the public endpoint.
   - The integrations chain's authentication-entry-point / failure handling must return a **bare
     401** with no body that distinguishes the key cause (uniform across missing/malformed/unknown).

2. **Create the api-key `OncePerRequestFilter` (in `com.botfunnel.api`).**
   - Read the API key from a request header (`X-API-Key`, per the smoke command).
   - Resolve the project via `ApiKeyService` lookup-by-hash (the service hashes the presented
     plaintext and looks up `api_keys` by `keyHash` — never a plaintext compare). On any problem
     (header absent/empty, malformed, no matching key) → **uniform 401** and stop the chain.
   - On success: stamp `lastUsedAt` (via `ApiKeyService`), set an `Authentication` in the
     `SecurityContext` and expose the resolved `projectId` to the controller (request attribute or a
     small authentication principal). Never log the key value or the hash.

3. **Create the request DTO** (in `com.botfunnel.api`) for `POST /api/integrations/v1/events`:
   `event_name` (`@NotBlank`, pattern `^[A-Za-z0-9_-]{1,64}$`), `telegram_user_id` (optional
   `Long`), `subscriber_id` (optional `String`). Use the snake_case JSON names. At least one of
   `telegram_user_id` / `subscriber_id` must be present (bean-level / cross-field validation → 400).

4. **Create `EventsController` (in `com.botfunnel.api`)** with `POST /api/integrations/v1/events`:
   - Read the project pinned by the key filter (request attribute / principal).
   - Validate the DTO (`@Valid`) — malformed `event_name` slug **or** missing-both-identifiers → 400.
   - Apply a global fixed Redis rate-limit (key `bf:rate:events`, fail-open INCR/EXPIRE idiom mirrored
     from `SubscriberServiceImpl.startRateLimitExceeded`); over limit → 429.
   - Resolve the subscriber project-scoped: `subscriber_id` wins when both present (lookup by
     `(projectId, subscriberId)`), else by `(projectId, telegram_user_id)`. Unknown subscriber → 404.
     Never auto-create a subscriber.
   - Dispatch via `FunnelEventService.dispatchForSubscriber(projectId, subscriberId, event,
     event_name, originDepth = 0)`. Success / no-op (subscriber exists, no listener) → **202**.
   - Wrap the dispatch in `try/catch(Throwable)`: an engine fault is logged (greppable WARN) and
     **swallowed → 202** (never a 5xx).

5. **Resolve the subscriber via the project-scoped `SubscriberService` lookup added by Task 4 — do NOT
   add a new lookup method (anti-IDOR — both lookups are project-pinned).**
   - **By `subscriberId`** — call the project-scoped boundary method that **Task 4 creates and solely
     owns**: `Optional<Subscriber> findById(String projectId, String subscriberId)` on
     `SubscriberService` / `SubscriberServiceImpl` (implemented as
     `repo.findById(subscriberId).filter(sub -> projectId.equals(sub.getProjectId()))` — the same
     project-pinning shape `unsubscribeManual` uses). Task 7 `depends_on [3, 4]` and runs in a later
     wave than Task 4, so this method already exists — **READ and REUSE it; do NOT add it here**
     (adding it again would create a duplicate-method / merge-conflict). Pass the project pinned by the
     key filter as `projectId`.
   - **By `telegramUserId`** — `SubscriberRepository` already exposes
     `findByProjectIdAndTelegramUserId(projectId, telegramUserId)`; reach it through the same service
     boundary (do not call the repository directly from the `api` package).
   - **Precedence:** `subscriber_id` takes precedence over `telegram_user_id` when both are present;
     both lookups are project-pinned to the key's project.
   - A raw `findById(subscriberId)` with no project filter is **forbidden** — a subscriber in a
     different project MUST collapse to the same 404 as a missing one (anti-IDOR). Do NOT list
     `SubscriberService.java` / `SubscriberServiceImpl.java` under "Code — modify"; they are read-only
     context here.

6. **Allow `X-API-Key` through CORS preflight.** `SecurityConfig.corsConfigurationSource()` currently
   sets `allowedHeaders = ["Content-Type", "X-Requested-With", "X-XSRF-TOKEN"]` — a browser cross-origin
   caller sending `X-API-Key` is blocked at the OPTIONS preflight. Add `X-API-Key` to the
   `allowedHeaders` list so cross-origin integrations callers can present the key. (The CORS source is
   shared across both chains, so one edit covers `/api/integrations/**`.)

7. **Add config keys to `application.properties`**: the `/events` global rate-limit threshold
   (~300/min, e.g. `app.api.events.rate-limit-per-min`). Reuse the existing `StringRedisTemplate`.

## Acceptance Criteria

- [ ] `@Order(1)` STATELESS `SecurityFilterChain` with `securityMatcher("/api/integrations/**")`, CSRF
      off; existing session chain demoted to `@Order(2)`.
- [ ] Api-key `OncePerRequestFilter` resolves the project from the presented key (hash lookup, no
      plaintext compare), stamps `lastUsedAt`, and returns a **uniform 401** for missing / malformed /
      unknown keys (anti-enumeration). Key value/hash never logged.
- [ ] `POST /api/integrations/v1/events` returns the exact matrix: 202 (start), 202 (no-op), 404
      (unknown subscriber), 400 (malformed body / missing identifier), 401 (any key problem, uniform),
      429 (rate-limit). Never 5xx; never auto-creates a subscriber.
- [ ] `subscriber_id` wins over `telegram_user_id` when both present; subscriber resolution is
      project-scoped (anti-IDOR): subscriber-by-id is pinned to the key's project (no raw
      `findById(subscriberId)`), and a cross-project subscriber collapses to 404.
- [ ] `X-API-Key` is in the CORS `allowedHeaders` (cross-origin preflight on the key header passes).
- [ ] Engine fault inside `/events` is swallowed → 202 with a greppable WARN (error-isolation).
- [ ] Key chain and session chain are mutually exclusive (key ✗ cabinet, session ✗ `/integrations`).
- [ ] `/events` rate-limit is fail-open (Redis outage does not 5xx the endpoint); over-limit → 429.
- [ ] All existing security/funnel/subscriber tests stay green (no regressions).

## Details

**Files:**
- `security/SecurityConfig.java` — add `@Order(1)` integrations chain; annotate existing
  `appSecurityFilterChain` `@Order(2)`. The existing chain already has `EnableWebSecurity` and a custom
  `OncePerRequestFilter` (CsrfCookieMaterializer) — same servlet-stack DSL applies. STATELESS:
  `sessionManagement(s -> s.sessionCreationPolicy(STATELESS))`; CSRF: `csrf(AbstractHttpConfigurer::disable)`.
  Also extend `corsConfigurationSource().setAllowedHeaders(...)` to include `X-API-Key` (currently
  `Content-Type` / `X-Requested-With` / `X-XSRF-TOKEN` only — without this, cross-origin preflight on
  the key header fails). The CORS source is registered on `/**`, so the one edit applies to both chains.
- `subscriber/SubscriberService.java` + `SubscriberServiceImpl.java` — **READ-ONLY here.** Task 7 does
  NOT modify these. The project-scoped `Optional<Subscriber> findById(projectId, subscriberId)` boundary
  method is **created and solely owned by Task 4** (Task 7 runs after Task 4 — `depends_on [3, 4]`); Task 7
  REUSES it. `unsubscribeManual` (`:211-223`) is the project-pinning precedent Task 4's method mirrors.
  Mirror `startRateLimitExceeded` only for the rate-limit idiom — do not add any method.
- `api/` (new) — `EventsController.java`, the api-key `OncePerRequestFilter` (e.g. `ApiKeyAuthFilter`),
  the request DTO (e.g. `EventIngressRequest`). Package `com.botfunnel.api` is greenfield from Task 3.
- `application.properties` — add `app.api.events.rate-limit-per-min` (~300). The
  `M backend/.../application.properties` already in the working tree is unrelated; append, don't rewrite.

**Dependencies:**
- Task 3 — `ApiKeyService` (generate/lookup-by-hash/stamp-lastUsedAt) + `ApiKey` domain. Do not
  re-implement hashing here; call the service. `Sha256Hex` lives in `common.crypto`.
- Task 4 — `FunnelEventService.dispatchForSubscriber(projectId, subscriberId, triggerType, matchKey,
  originDepth)`. Call with `triggerType = event`, `matchKey = event_name`, `originDepth = 0`.

**Edge cases:**
- Empty / whitespace `X-API-Key` → 401 (same as malformed). Never 200.
- `event_name` present but identifiers absent → 400 (not 404 — the body is malformed before resolution).
- Both identifiers present but mismatched subscribers — `subscriber_id` wins; resolve by it only.
- Subscriber exists in a DIFFERENT project than the key's project → 404 (project-scoped lookup, anti-IDOR).
- Redis down → rate-limit fails open (request proceeds), not a 5xx.
- Dispatcher throws → 202, WARN; the partial-unique re-enter guard inside the dispatcher is its own concern.

**Implementation hints:**
- Mirror `WebhookSecretVerifier`'s discipline: hash-only comparison, uniform false→401, never log the
  secret. The lookup-by-hash is effectively constant-time w.r.t. the secret (no plaintext compare).
- Uniform 401: do not branch the response body/status on the key cause — one code path for all faults.
- Rate-limit: copy the `startRateLimitExceeded` shape verbatim (INCR, EXPIRE only when count==1,
  fail-open with a greppable WARN constant). Use a distinct key prefix `bf:rate:events`.
- Order matters: `@Order(1)` integrations chain MUST precede the session chain or `/api/**` shadows it
  (Decision 7). Assert mutual isolation in both directions in `ChainIsolationIT`.
- Watch the VT pinning note (patterns.md): the api-key filter is per-request and lightweight; avoid
  synchronized blocks on the hot path.
- Subscriber-by-id project pinning lives in the `SubscriberService.findById(projectId, subscriberId)`
  method **Task 4 owns** (same shape as `unsubscribeManual`, `SubscriberServiceImpl:214-215`:
  `findById(id).filter(s -> projectId.equals(s.getProjectId()))`). REUSE that method — never call
  `repo.findById(subscriberId)` directly from the `api` package without the project filter; that is the
  IDOR hole.
- CORS: `X-API-Key` must be added to `allowedHeaders`, otherwise the browser preflight (OPTIONS) for a
  cross-origin caller rejects the request before it ever reaches the key filter. Curl smoke tests do
  not send preflight, so this gap is invisible to the smoke checks — assert it via a CORS/preflight
  test or verify the config directly.
