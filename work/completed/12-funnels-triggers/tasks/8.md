# Task 8: Project-settings API-key generate/regenerate endpoint

## Required Skills

Перед выполнением задачи загрузи:
- `/skill:code-writing` — [skills/code-writing/SKILL.md](.claude/skills/code-writing/SKILL.md)

## Description

Дать автору проекта эндпоинт для получения/перевыпуска публичного API-ключа **по запросу** (on-demand). Это session-authed витрина над `ApiKeyService` (создан в Task 3), которая живёт в кабинете под `/api/v1/projects/{projectId}/api-key` и защищена тем же session-chain, что и остальной кабинет.

Ключевые свойства (Decision 8):
- **Plaintext показывается ровно один раз** — в ответе на generate/regenerate. На GET возвращается только маска `prefix•••` (или признак «нет ключа»). Полный ключ нигде не персистится — в БД только `keyHash` + `keyPrefix` (это уже обеспечено `ApiKeyService` из Task 3).
- **Генерация только по требованию** — этот эндпоинт НЕ вызывается из `ProjectService.create`, нет авто-генерации при создании проекта, нет бэкфилла. Это единственная точка, где ключ создаётся.
- **Ownership-guard** — каждый вызов проходит через `ProjectService.requireOwned(ownerId, projectId, false)`, который collapses foreign / missing / soft-deleted / malformed-id в единый 404 (anti-enumeration). Чужой проект не должен раскрывать ни наличие, ни маску ключа.
- **Regenerate = overwrite** — повторный POST перевыпускает ключ (старый хэш затирается), возвращает новый plaintext один раз. Старый ключ становится невалидным.

WHY: пользователю нужен способ получить ключ для публичного API (`/api/integrations/**`, Task 7) из настроек проекта.

## What to do

1. Создать `ApiKeyController` в пакете `com.botfunnel.api` с `@RequestMapping("/api/v1/projects/{projectId}/api-key")`.
2. **GET** `/api/v1/projects/{projectId}/api-key` — резолв `ownerId` из `SecurityContextHolder` (как в `ProjectController.currentUserId()`), `requireOwned(ownerId, projectId, false)`, затем вернуть маску текущего ключа через `ApiKeyService` (lookup by projectId): если ключ есть — `{ present: true, mask: "prefix•••" }`; если нет — `{ present: false, mask: null }`. **Без plaintext.**
3. **POST** `/api/v1/projects/{projectId}/api-key` — резолв `ownerId`, `requireOwned`, затем generate-or-regenerate через `ApiKeyService` (overwrite, если ключ уже есть). Вернуть response-DTO с **plaintext-ключом один раз** + маской + признаком, был ли это первичный выпуск или перевыпуск (если удобно). Plaintext в этом ответе — единственное место, где он виден.
4. Создать response-DTO(ы): маска для GET и plaintext-once для POST. Java records в `com.botfunnel.api` (или `api/dto`, согласовать с раскладкой пакета из Task 3).
5. Маппинг маски (`prefix•••`) выполнять из `keyPrefix`, который хранит `ApiKey`. Не реконструировать из полного ключа (его нет в БД).
6. Убедиться, что эндпоинт подхватывается session-chain (`@Order(2)` после Task 7; до Task 7 — единственный chain), а НЕ key-chain `/api/integrations/**`. Путь `/api/v1/projects/**` уже покрыт session-matcher — отдельной конфигурации не нужно, но проверить, что новый контроллер не ломает существующую цепочку.

## TDD Anchor

Тесты пишем ДО реализации (slice/IT в `backend/src/test/java/com/botfunnel/api/`). Паттерн: `@SpringBootTest(webEnvironment=RANDOM_PORT)` + `@AutoConfigureMockMvc` + `@WithMockAppUser`, реальный embedded Mongo, CSRF post-processor для POST (см. `ProjectControllerIT`).

- `api/ApiKeyControllerIT::generate_returnsPlaintextOnce` — POST с session → 200/201, тело содержит непустой plaintext-ключ; в БД (`api_keys`) для проекта лежит только `keyHash` + `keyPrefix`, полный plaintext не персистится.
- `api/ApiKeyControllerIT::getAfterGenerate_returnsMaskedNoPlaintext` — после POST, GET → `present:true`, `mask` имеет форму `prefix•••`, тело НЕ содержит полного plaintext-ключа.
- `api/ApiKeyControllerIT::getWhenNoKey_returnsAbsent` — GET без ранее выпущенного ключа → `present:false`, `mask:null`.
- `api/ApiKeyControllerIT::regenerate_overwritesAndInvalidatesOld` — два POST подряд → второй plaintext отличается от первого; хэш старого ключа в БД больше не присутствует (regenerate = overwrite).
- `api/ApiKeyControllerIT::foreignProject_returns404Uniform` — POST и GET на проект другого владельца → 404 (идентично missing-проекту, anti-enumeration); ключ не создаётся.
- `api/ApiKeyControllerIT::unauthenticated_returns401` — без session-cookie → 401 (не проходит session-chain).

## Acceptance Criteria

- [ ] `POST /api/v1/projects/{projectId}/api-key` (session-authed, ownership-guarded) возвращает plaintext-ключ **ровно один раз**.
- [ ] `GET /api/v1/projects/{projectId}/api-key` возвращает маску `prefix•••` (или признак отсутствия), **никогда** полный plaintext.
- [ ] Regenerate перевыпускает ключ (overwrite): новый plaintext ≠ старый, старый хэш инвалидируется.
- [ ] Ownership-guard через `requireOwned`: чужой/несуществующий/soft-deleted/malformed projectId → единый 404, ключ не создаётся и не раскрывается.
- [ ] Неаутентифицированный запрос → 401 (session-chain).
- [ ] В БД (`api_keys`) хранится только `keyHash` + `keyPrefix`; полный plaintext не персистится.
- [ ] Генерация НЕ вызывается из `ProjectService.create` — этот эндпоинт единственная точка создания.
- [ ] Существующие тесты проекта/безопасности остаются зелёными.

**Files:**

Резолв `ownerId` повторяет `ProjectController.currentUserId()` (либо переиспользовать общий хелпер, если это согласуется с раскладкой проекта — но не усложнять).
- `backend/src/main/java/com/botfunnel/api/...` — response-DTO record(ы): GET-маска (`present`, `mask`) и POST-plaintext-once (`apiKey` plaintext, `mask`/`keyPrefix`). Раскладку пакета (`api` vs `api/dto`) согласовать с тем, что выбрал Task 3.

**Dependencies:**
- depends_on Task 3 — `ApiKeyService` + `ApiKey` домен + `api_keys` репозиторий должны существовать. **Сначала прочитать `ApiKeyService.java` и сверить реальные сигнатуры** (имена методов generate/regenerate/lookup могут отличаться от предполагаемых здесь) перед написанием контроллера.
- `ProjectService.requireOwned` — ownership-guard, переиспользуется как есть.
- Никаких новых пакетов.

**Edge cases:**
- GET на проект без ключа → `present:false`, `mask:null` (не 404 — проект существует и принадлежит юзеру).
- POST когда ключ уже есть → regenerate (overwrite), не ошибка, не дубль. Уникальный индекс `projectId` в `api_keys` (Task 3) гарантирует один ключ на проект — убедиться, что regenerate обновляет существующий документ, а не падает на duplicate-key.
- Чужой/несуществующий/soft-deleted/malformed projectId → единый 404 через `requireOwned` (anti-enumeration). Маска чужого ключа НЕ раскрывается.
- Неаутентифицированный запрос отсекается session-chain (401) до контроллера.
- POST требует CSRF-токен (session-chain, не stateless) — учесть в IT (CSRF post-processor) и в smoke (`X-XSRF-TOKEN`).

**Implementation hints:**
- НЕ хукать генерацию в `ProjectService.create` — это явный запрет (Decision 8, on-demand only).
- Маску строить из `keyPrefix` (хранится в `ApiKey`), а не из полного ключа.
- Не логировать plaintext-ключ и не класть его в audit/event-лог. Plaintext живёт только в HTTP-ответе на POST.
- Путь `/api/v1/projects/**` уже матчится session-chain; этот контроллер НЕ должен попадать под key-chain `/api/integrations/**` (Task 7). Проверить после мерджа Task 7, что порядок цепочек (`@Order(2)` session) не уводит запрос в key-filter.
- Стиль ответа (status 200 vs 201 на POST, имена полей DTO) согласовать с существующими контроллерами кабинета (`ProjectController`, `BotController`).
