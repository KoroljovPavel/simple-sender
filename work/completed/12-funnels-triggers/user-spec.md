# User Spec: 12-funnels-triggers — Додаткові тригери + подієва шина (Фаза 3)

## Что делаем

Третя фаза епіку «Воронки» (`docs/roadmap/funnels.md`). Зараз воронку можна запустити **лише** тригером `on_start` (підписник написав `/start [payload]`). Ця фаза додає ще **п'ять способів запуску** і **внутрішню подієву шину**:

1. **keyword** — підписник пише боту вільний текст, що **містить** одне з ключових слів воронки (contains, case-insensitive, кілька слів на воронку, будь-який збіг).
2. **tag_added** — підписнику **додали тег** (з будь-якого джерела: вручну в кабінеті, кроком іншої воронки, через API).
3. **custom_field_set** — підписнику **встановили/змінили** кастом-поле (будь-яке значення, без умови на значення).
4. **api-event** — зовнішня система робить `POST /api/integrations/v1/events` з `event_name`, ідентифікуючи підписника по `telegram_user_id`.
5. **EMIT_EVENT** — новий **крок воронки**, що емітить іменовану подію зсередини виконання. Внутрішній emit і зовнішня API-подія ділять **один namespace** `event_name`.

Плюс **мінімальний фундамент публічного API** (рейки для майбутнього Epic 08), без якого зовнішня подія неможлива: окремий ключ-авторизований namespace `/api/integrations/v1/**`, генерація API-ключа на вимогу в налаштуваннях проєкту, перший і єдиний ендпоінт зараз — `POST /api/integrations/v1/events`.

**Ключове архітектурне рішення (де-ризик):** усі тригери **subscriber-scoped** — кожне спрацювання створює **один** `FunnelExecution` для **одного** підписника (як `on_start` сьогодні). «Одна подія → багато воронок» (fan-out) досягається тим, що **N окремих воронок** мають той самий event/keyword/tag/field-тригер. Для цього достатньо **послабити partial-unique індекс** воронок (унікальність лишаємо тільки для `on_start`), а **не** переходити на `List<Trigger>` на воронку — кілька тригерів на одній воронці (multi-entry) свідомо лишаються в Epic 8.

Свідомо **поза скоупом** (за роадмапом): `List<Trigger>`/тригер-вузли в одній воронці (Epic 8), повноцінне керування ключами — ротація, кілька ключів, `/integrations/v1/subscribers` + `/funnels` (Epic 08), per-project/super-admin-редаговані ліміти (монетизація), regex-keyword, predicate-на-значення для `custom_field_set`, мапінг payload події в змінні воронки, Mongock (наступна окрема інфра-задача — `workflow/improvements.md`).

## Зачем

Лінійні й інтерактивні воронки досі вміють стартувати лише з `/start`. Але реальні сценарії автоматизації запускаються **подіями**, а не лише першим контактом. Три рівнозначні jobs-to-be-done, які відмикає ця фаза (користувач — власник проєкту, малий бізнес/маркетолог):

1. **Re-engage по ключовому слову:** підписник пише «хочу бонус» → стартує відповідна воронка. Без цього бот глухий до вільного тексту.
2. **Ланцюги автоматизації по стану підписника:** додали тег `paid` (вручну/кроком/через оплату) або змінили поле → автоматично йде воронка подяки/онбордингу. Це робить теги й поля **активними тригерами**, а не лише фільтрами.
3. **Зовнішні системи керують воронками:** розсилки, CRM, платіжки емітять іменовану подію (ззовні через API або зсередини кроком `EMIT_EVENT`) → «тригер-воронка» реагує повідомленням. Це конкретний кейс автора: *розсилка емітить подію → воронка віддає повідомлення*.

API-ключ на проєкт — це ще й перші рейки публічного API: далі (Epic 08) на тому ж фундаменті стануть `/integrations/v1/subscribers` тощо, щоб зовнішні системи не лише штовхали події, а й читали дані.

## Как должно работать

**Сценарій 1 — автор налаштовує тригер воронки:**
1. У редакторі воронки секція тригера (`FunnelTriggerSettings`) зараз показує `on_start` статичним бейджем. Тепер це **селектор типу**: `on_start` / `keyword` / `tag_added` / `custom_field_set` / `api-event`.
2. Поле значення рендериться **по типу**:
   - `on_start` — як зараз (текст payload + прев'ю deep-link).
   - `keyword` — введення **списку** ключових слів (кілька; нормалізуються в lowercase).
   - `tag_added` — вибір тега через `SearchableSelect` (значення = slug тега).
   - `custom_field_set` — вибір кастом-поля через `SearchableSelect` (значення = ключ поля).
   - `api-event` — введення `event_name` (slug `^[A-Za-z0-9_-]{1,64}$`).
3. Автор зберігає/активує воронку. Кілька **різних** активних воронок можуть слухати **той самий** keyword/тег/поле/подію — це дозволено (fan-out). `on_start` лишається 1:1 (дубль активної воронки на той самий payload забороняється індексом, як зараз).

**Сценарій 2 — keyword-тригер у рантаймі:**
1. Підписник пише боту вільний текст (не команду `/...`).
2. Вебхук-воркер (`ProcessTelegramUpdateJob`, гілка plain-text) визначає підписника й перевіряє: чи є в нього **активне `waiting_for_reply`** (стоїть у меню Фази 2)?
   - **Так** → keyword **НЕ** спрацьовує (не висмикуємо з меню; текст ігнорується/логується, як сьогодні — Фаза 2 не споживає вільний текст).
   - **Ні** → шукаємо активні keyword-воронки проєкту, робимо contains-match (case-insensitive) по їхніх списках слів; **усі**, що збіглися, стартують (fan-out), кожна під лімітом анти-циклу.
3. Команди (`/start`, `/stop`) йдуть своєю гілкою як раніше — keyword їх не зачіпає.

**Сценарій 3 — tag_added / custom_field_set:**
1. Тег додається (`SubscriberServiceImpl.addTag`) або поле встановлюється (`recordCustomFieldsSet`) — з будь-якого джерела: кабінет, крок воронки (`ADD_TAG`/`SET_CUSTOM_FIELD`), API.
2. **Після** idempotency-guard (no-op додавання тега тригер НЕ запускає) і запису `subscriber_events` — диспетчер шукає активні воронки з тригером `tag_added`=slug / `custom_field_set`=ключ і стартує **всі** збіги (fan-out), під анти-цикл-лімітом.

**Сценарій 4 — зовнішня подія через API:**
1. Зовнішня система: `POST /api/integrations/v1/events`, заголовок з API-ключем, тіло `{ "event_name": "...", "telegram_user_id": 123456789 }`. Основний ідентифікатор — `telegram_user_id`; **опційно** замість нього приймається наш внутрішній `subscriber_id` (lookup по `(projectId, subscriber_id)`) — для систем, що вже зберегли наш id.
2. Ключ-фільтр (`/api/integrations/**`) валідує ключ (SHA-256-lookup), визначає проєкт із ключа. **Будь-яка** проблема з ключем (відсутній / некоректний формат / невідомий) дає **уніфіковану 401** (без розрізнення причин — анти-enumeration).
3. Підписник резолвиться по `(projectId, telegram_user_id)` (або `(projectId, subscriber_id)`, якщо передано його). Диспетчер стартує всі активні воронки з тригером `event`=`event_name` для цього підписника (fan-out, анти-цикл).
4. Відповіді: успіх → **202 Accepted**; невідомий ідентифікатор підписника → **404**; підписник є, але жодна воронка не слухає → **202 no-op**; нема/невалідний ключ → **401**; перевищено rate-limit → **429**. Подія **не** створює підписника (авто-реєстрація лишається тільки на `/start`).

**Сценарій 5 — крок EMIT_EVENT + fan-out:**
1. Автор додає крок `EMIT_EVENT` (поле `eventName`, slug). У рантаймі крок синхронно в tick'у викликає той самий диспетчер для **поточного підписника** виконання й одразу віддає `CONTINUE` (батьківська воронка йде далі).
2. Усі активні воронки з тригером `event`=`eventName` стартують для цього підписника (fan-out) — той самий namespace, що й API-подія.

**Сценарій 6 — API-ключ у налаштуваннях проєкту:**
1. У налаштуваннях проєкту картка «API-ключ»: якщо ключа ще нема — кнопка **«Згенерувати»**; якщо є — маска (`prefix•••`) + **«Перегенерувати»**.
2. (Пере)генерація показує **plaintext один раз** (модалка «збережіть ключ»); у БД лежить лише SHA-256-хеш. Проєкт без згенерованого ключа просто не може звертатись до `/api/integrations/**`.
3. Авто-генерації при створенні проєкту **нема**; бекфілу наявних проєктів **нема** (ключ — на вимогу).

**Сценарій 7 — захист від циклів (два незалежні бекстопи):**
1. **Обсяг:** каскад (тег→воронка→тег, EMIT_EVENT-fan-out, A→B→A) обмежується **per-subscriber лімітом авто-enroll'ів**: ≤ **20 авто-стартів за хвилину** на підписника (Redis, fail-open). Рахуються лише **авто**-старти (з кроку/тегу/поля/події), людські (manual/`/start`/keyword) — ні. Перевищення → enroll **дропається** + WARN-лог (greppable).
2. **Глибина (Redis-незалежний бекстоп):** кожне виконання несе лічильник **глибини enroll-ланцюга**. Корінь ланцюга — людський/зовнішній старт (`on_start`, keyword, manual-UI, api-event) — має `depth = 0`. Коли **авто**-тригер (крок/тег/поле/EMIT_EVENT) стартує дочірню воронку для того ж підписника, `depth = parent.depth + 1`. Понад жорсткий cap (**10**) авто-enroll **дропається + WARN**, навіть якщо Redis недоступний (тоді rate-limit fail-open пропускає, а depth-cap усе одно ріже runaway).
3. Re-enter guard (partial-unique `(funnelId, subscriberId)`) лишається й додатково ловить прямий дубль у ту саму воронку.

**Сценарій 8 — міграція індексу на старті:**
1. На старті застосунку ідемпотентний `ApplicationRunner` (патерн `FunnelStepIdBackfill`, log-but-never-throw) звіряє trigger-індекс воронок: дропає старий `projectId_triggerType_triggerValue_unique_active`, дозволяючи auto-index-creation створити нову форму (унікальність тільки для `triggerType='on_start'`). Ідемпотентно (через `listIndexes()`); якщо вже нова форма — no-op. Адмін **не** дропає індекси руками.

## Критерии приёмки

- [ ] У редакторі воронки тип тригера обирається селектором (`on_start`/`keyword`/`tag_added`/`custom_field_set`/`api-event`), поле значення відповідає типу (keyword — список слів; tag/field — `SearchableSelect`; event — slug-інпут).
- [ ] **keyword:** підписник пише текст зі словом-тригером (у будь-якому регістрі, як підрядок) → стартує правильна воронка для цього підписника.
- [ ] **keyword precedence:** якщо підписник у `waiting_for_reply` (меню) пише слово-тригер — воронка keyword **не** стартує, меню лишається.
- [ ] **tag_added:** додавання тега (вручну / кроком воронки / API) стартує воронку з цим тригером; **idempotent** додавання (тег уже є) тригер не запускає.
- [ ] **custom_field_set:** встановлення/зміна поля стартує воронку з цим тригером; no-op set не запускає.
- [ ] **api-event:** `POST /api/integrations/v1/events` з валідним ключем і `telegram_user_id` (або опційним `subscriber_id`) → 202 і воронка стартує; невідомий ідентифікатор → 404; нема воронки-слухача → 202 no-op; будь-яка проблема з ключем (відсутній/некоректний/невідомий) → уніфікована 401; rate-limit → 429.
- [ ] **EMIT_EVENT:** крок емітить подію для поточного підписника → стартують усі воронки-слухачі цього `event_name`; батьківська воронка продовжується.
- [ ] **fan-out:** дві активні воронки з тим самим keyword/тегом/полем/подією → стартують **обидві** (два `FunnelExecution`).
- [ ] **on_start лишається 1:1:** дубль активної воронки на той самий `on_start` payload відхиляється індексом.
- [ ] **анти-цикл (обсяг):** ланцюг A→B→A (через тег/подію) не вішає систему — понад 20 авто-enroll'ів/хв на підписника дропаються з WARN-логом.
- [ ] **анти-цикл (глибина):** enroll-ланцюг глибше 10 обривається з WARN навіть за недоступного Redis (depth-cap несеться на виконанні, не залежить від rate-limit).
- [ ] **API-ключ:** у налаштуваннях проєкту «Згенерувати» → plaintext показано один раз; повторно — «Перегенерувати»; у БД лише хеш; ключ авторизує `/api/integrations/**` і **не** авторизує сесійні `/api/v1/projects/**`, а сесія **не** авторизує `/api/integrations/**`.
- [ ] **міграція:** на старті старий trigger-індекс замінюється на on_start-only-unique форму ідемпотентно; руками нічого дропати не треба.
- [ ] **error-isolation (вебхук):** якщо диспатч тригера кидає виняток під час обробки апдейта — вебхук-воркер усе одно повертає 200 OK (не 5xx), JobRunr-джоба не фейлиться, помилка лягає у WARN-лог з greppable-маркером.
- [ ] **error-isolation (API):** якщо engine кидає виняток усередині, `POST /api/integrations/v1/events` усе одно повертає 202 (подію прийнято), без 5xx.

## Ограничения

- **Subscriber-scoped only:** жодних project-wide/segment-тригерів (старт воронки для сегмента — це розсилки, інший епік). Кожне спрацювання = один execution на одного підписника.
- **Зміна схеми мінімальна:** лише **релакс partial-unique індексу** воронок (унікальність тільки для `on_start`) + новий keyword-list-поле на воронці + `eventName` на кроці + нова колекція `api_keys`. **Без** `List<Trigger>` (multi-entry = Epic 8).
- **Публічний API — мінімум:** namespace `/api/integrations/v1/**` (версія всередині namespace; auth-chain матчить `/api/integrations/**` для всіх версій); проєкт визначається **з ключа** (без `{projectId}` у шляху); ключ зберігається **hash-only** (SHA-256) → plaintext знати можна лише в момент генерації; rate-limit на `/events` — **фіксований глобальний** (~300/хв) через наявні Redis-лічильники. Ротація/кілька ключів/інші ресурси/per-project-ліміти — Epic 08.
- **Нейминг:** «events» уже зайнято двічі (audit-колекція `events`, `subscriber_events`) — внутрішній диспетчер називається окремо (`FunnelEventService`), `EventService` не реюзаємо.
- **Міграції:** index-зміна — ручна ідемпотентна стартова міграція (бо `auto-index-creation=true` лише створює, не дропає). Mongock — наступна окрема задача.
- **Deploy:** наразі автодеплою нема (pre-prod, автор запускає вручну/локально); міграція йде на старті застосунку незалежно від способу запуску.

## Риски

- **Каскади/нескінченні петлі** (tag→воронка→tag, EMIT_EVENT-fan-out, A→B→A). Re-enter guard ловить лише прямий дубль у ту саму воронку, не A→B→A. **Митигація — два незалежні бекстопи:** (1) per-subscriber ліміт авто-enroll'ів 20/хв (Redis fail-open, дроп+WARN); (2) **Redis-незалежний depth-cap** enroll-ланцюга = 10 (несеться на виконанні, ріже runaway навіть під час збою Redis, коли rate-limit fail-open пропускає). Per-tick budget обмежує лише одне виконання, тому самого rate-limit недостатньо.
- **Колізія namespace з сесійним API.** `/api/integrations/**` лежить під `/api/**`, який сесійний chain authenticated-ить. **Митигація:** окремий `@Order(1)` `SecurityFilterChain` з `securityMatcher("/api/integrations/**")` перед сесійним; IT перевіряє взаємну ізоляцію (ключ не пускає в кабінет, сесія — в `/integrations`).
- **Витік index-міграції.** Якщо забути drop — auto-index-creation не змінить наявний індекс, fan-out не запрацює. **Митигація:** ідемпотентний стартовий runner + `FunnelIndexesIT`, що доводить співіснування двох `event`-воронок і колізію двох `on_start`.
- **Втрата plaintext-ключа.** Hash-only → якщо автор не зберіг показаний ключ, відновити не можна. **Митигація:** показ-один-раз з явною модалкою + «Перегенерувати»; задокументувати в UI.
- **Keyword шумить / хибні спрацювання** (надто загальне слово матчить пів-чату). **Митигація:** contains по списку слів, нормалізація; precedence не висмикує з меню; автор сам контролює слова. Regex/точніший матч — nice-to-have.
- **Перевантаження `/events`** зовнішнім трафіком. **Митигація:** фіксований глобальний rate-limit (429). **Fail-open:** якщо Redis недоступний — rate-limit-перевірка пропускається, запит проходить і подія диспатчиться у звичайному режимі (доступність важливіша за жорсткий ліміт під час збою Redis).

## Технические решения

- Ми вирішили робити тригери **subscriber-scoped і fan-out через релакс індексу**, а не `List<Trigger>` — бо «одна подія → N воронок» = N воронок з тим самим тригером; це прибирає найризиковішу зміну схеми, а multi-entry лишається Epic 8.
- Ми вирішили додати **окремий subscriber-keyed вхід** у тригер-сервіс (з fan-out — список збігів, не один результат), а не перевантажувати наявний chatId-keyed вхід `on_start`. Шлях створення execution реюзаємо без змін.
- Ми вирішили зберігати keyword як **окреме поле-список** на воронці (lowercase, contains, any-of-many), бо одиничний exact-match `triggerValue` для цього не годиться; інші типи реюзають `triggerValue` (slug тега / ключ поля / `event_name`).
- Ми вирішили чіпляти `tag_added`/`custom_field_set` у **єдиних писарів** тегів/полів підписника — після idempotency-guard і запису audit-події (тому no-op не тригерить).
- Ми вирішили обробляти keyword у **plain-text гілці вебхука**, з перевіркою активного `waiting_for_reply` перед спрацюванням (precedence — не висмикуємо з меню).
- Ми вирішили зробити `EMIT_EVENT` новим типом кроку, що **синхронно** кличе диспетчер для поточного підписника й одразу продовжує воронку; нове поле кроку має потрапити у snapshot-копію (інакше згубиться).
- Ми вирішили назвати внутрішній диспетчер **окремо** (напр. `FunnelEventService`), щоб не плутати з audit-`events`/`subscriber_events`; наявний `EventService` не реюзаємо.
- Ми вирішили винести програмний API в **окремий ключ-авторизований filter-chain** з вищим пріоритетом (`@Order(1)`), що матчить `/api/integrations/**` **перед** сесійним `/api/**` — інакше сесійний chain перехопив би запити. Namespace `integrations` (а не `public`/`external`) обрано свідомо: точніше за призначенням і не натякає на «без авторизації».
- Ми вирішили зберігати API-ключ **hash-only** (SHA-256), генерувати **на вимогу** в налаштуваннях (без авто-ген на створенні, без бекфілу); plaintext знати можна лише в момент (пере)генерації.
- Ми вирішили захистити каскади **двома незалежними бекстопами**: Redis-лічильник авто-enroll'ів (обсяг, fail-open) **і** Redis-незалежний depth-cap enroll-ланцюга на виконанні (ріже runaway навіть під час збою Redis) — бо лише fail-open rate-limit лишав би діру під час недоступного Redis.
- Ми вирішили **переюзати** наявний Redis fail-open лічильник для rate-limit і патерн ідемпотентної стартової міграції (`FunnelStepIdBackfill`) для index-relax, а **не** заводити Mongock зараз (це окрема наступна задача).
- Ми вирішили будувати **форму тригера як переносний компонент**: при майбутньому переході на canvas-редактор вона мігрує як форма-вузол, а тимчасовою є лише list-обгортка — тому UI-інвестиція майже не throwaway.

## Тестирование

**Unit-тесты:** делаются всегда, не обсуждаются. Зокрема: keyword-матчинг (contains/case/any-of-many), EMIT_EVENT-диспатч (повертає CONTINUE, кличе диспетчер з правильним eventName + copyOf), генерація/хеш ключа, ідемпотентність стартового runner'а.

**Интеграционные тесты:** делаем — фіча L, критична логіка зав'язана на Mongo/Redis/security. Покриваємо (патерни з `AbstractIntegrationTest`, `FunnelTriggerServiceIT`, `FunnelIndexesIT`, `ProcessTelegramUpdateJobTest`, `SecurityConfigTest`):
- кожен тип тригера стартує правильну воронку для правильного підписника;
- keyword через вебхук + precedence vs `waiting_for_reply`;
- fan-out (1 подія/слово/тег → N executions);
- анти-цикл: обсяг (A→B→A під лімітом 20/хв) і глибина (depth-cap 10 при недоступному Redis);
- `POST /api/integrations/v1/events` (202 / 404 / 202-no-op / 401 / 429) + взаємна ізоляція ключ↔сесія;
- index-relax міграція (старий індекс зник, дві `event`-воронки співіснують, дві `on_start` — колізія);
- генерація API-ключа в налаштуваннях (+ що проєкт без ключа не пускає в `/integrations`).

**E2E тесты:** не делаем — нового критичного user-facing flow поза конфігом тригера в наявному редакторі немає; vitest на селектор типу тригера / EMIT_EVENT-форму достатньо.

## Как проверить

### Агент проверяет

| Шаг | Інструмент | Очікуваний результат |
|-----|-----------|-------------------|
| Запустити backend-тести (unit + IT) | bash (`./gradlew test`, slow-теги для index-IT) | Усі зелені, нові тригер/API/міграція-тести проходять |
| Frontend-тести редактора | bash (`pnpm test`) | vitest на тригер-селектор + EMIT_EVENT-форму зелені |
| keyword-тригер | MCP Telegram | Написати боту текст зі словом → воронка стартує; написати в меню → не стартує |
| tag_added/custom_field_set | curl/MCP (кабінет) → MCP Telegram | Додати тег/поле підписнику → відповідна воронка стартує (повідомлення приходить) |
| api-event | curl `POST /api/integrations/v1/events` з ключем | 202 і воронка стартує; без ключа → 401; невідомий user → 404; rate-limit → 429 |
| EMIT_EVENT + fan-out | MCP Telegram | Воронка з EMIT_EVENT → 2 воронки-слухачі стартують для підписника |
| Міграція індексу | bash (лог старту + `listIndexes`) | Старий індекс відсутній, нова on_start-only-unique форма є; повторний старт — no-op |
| API-ключ | UI (localhost) + curl | «Згенерувати» показує ключ один раз; у БД лише хеш; ключ авторизує `/integrations`, не кабінет |

### Пользователь проверяет
- На своєму Telegram пройти keyword-сценарій і tag-сценарій «вживу» (відчуття UX precedence — меню vs keyword), бо це поведінка, яку найкраще оцінити руками.
