# Task 10: Pre-deploy QA

## Required Skills

Перед выполнением задачи загрузи:
- `/skill:pre-deploy-qa` — приёмочное тестирование без live-среды: прогон тест-сьютов + верификация acceptance criteria из user-spec и tech-spec.

## Description

Финальная приёмочная проверка фичи «Воронки. Фаза 4 — інструменти автора» перед мерджем в `main`. Задача завершает фичу: имплементационные задачи (1-6) и аудит-задачи (7-9) выполнены — теперь нужно прогнать все автотесты и сверить **каждый** критерий приёмки из user-spec («Критерии приёмки») и tech-spec («Acceptance Criteria»).

**Деплоя и пост-деплоя НЕТ.** CI/CD-пайплайн в проекте ещё не настроен (deployment.md: «TBD»), живой среды нет. Фича мерджится в `main` и проверяется локально. Поэтому MCP/Playwright/Telegram-шагов в этой задаче нет (tech-spec «Agent Verification Plan»: «Live-середовища немає → пост-деплою/MCP-кроків немає»).

**Один критерий принципиально не верифицируется агентом:** реальная доставка сообщения «Test for me» в Telegram владельца. Бэкенд не наблюдает живую доставку без среды — это явно делегировано пользователю (user-spec «Пользователь проверяет»). В QA-отчёте этот критерий помечается как deferred-to-user, а не как провал.

## What to do

1. Прогнать полный backend-сьют: `./gradlew test` из `backend/` — все unit + integration тесты (включая `FunnelControllerIT` и `FunnelExecutionEngineIT` с MockWebServer) зелёные, нет регрессий в существующих тестах воронок/рушія.
   - **ВАЖНО:** `backend/build.gradle` исключает тесты с `@Tag("slow")` из дефолтного `./gradlew test`. MockWebServer send-assertion IT (из Task 2) может быть помечен `@Tag("slow")` → молча пропустится, а QA отрапортует «зелено». Перед прогоном: либо подтвердить, что новые funnel test-run IT (`FunnelExecutionEngineIT` и send-assertion IT) НЕ помечены `@Tag("slow")`, либо запустить с `-PrunSlow=true`, чтобы send-assertion IT реально выполнился. Зафиксировать в отчёте, какой вариант выбран и что IT действительно отработал (не skipped).
2. Прогнать frontend-сьют: `pnpm test -- --run` (vitest в неинтерактивном режиме) из `frontend/` — все unit + component-спеки зелёные (store-дії, панель прев'ю, confirm-діалог).
3. Прогнать i18n parity-gate: `node frontend/scripts/check-locales.mjs` — exit 0 (новые ключи присутствуют в обеих локалях `uk.json`/`en.json`).
4. Пройтись по каждому пункту user-spec «Критерии приёмки» (блоки Test for me / Дублювати / Зупинити всі активні запуски / Прев'ю / Спільне) и tech-spec «Acceptance Criteria» — для каждого зафиксировать: verified (каким тестом/проверкой) / deferred-to-user / не покрыт.
5. Собрать QA-отчёт: статус каждого сьюта, таблица критериев со статусом, явный список deferred-to-user критериев (реальная доставка Test for me), любые найденные дефекты. Перед записью создать директорию: `mkdir -p work/13-funnels-tooling/logs/qa` (её ещё нет). Записать отчёт в `work/13-funnels-tooling/logs/qa/pre-deploy-qa-report.md`.
6. Дать пользователю краткое резюме и список того, что он должен проверить вручную (реальная доставка Test for me в свой Telegram).

## Verification Steps

### Automated

- `./gradlew test` (cwd `backend/`) → BUILD SUCCESSFUL, все тесты pass. Проверить, что send-assertion IT (Task 2, MockWebServer) НЕ оказался в skipped: либо подтвердить, что он не помечен `@Tag("slow")`, либо прогнать `./gradlew test -PrunSlow=true` и убедиться, что IT отработал.
- `pnpm test -- --run` (cwd `frontend/`) → все vitest-спеки pass, exit 0.
- `node frontend/scripts/check-locales.mjs` (cwd репозитория) → exit 0, без вывода о расхождениях.

### User

- «Test for me» на реальном боте: открыть воронку → нажать → проверить, что сообщение пришло в собственный Telegram владельца. Агент не может наблюдать реальную доставку без live-среды — это deferred-to-user (user-spec «Пользователь проверяет»). Для интерактивных MENU-шагов нужен туннель/локальный бот.

## Details

QA-задача — без написания продакшн-кода и без TDD. Работа = прогон сьютов + сверка критериев + отчёт. Деплоя/пост-деплоя нет — фича проверяется локально и мерджится в `main`.

**Команды (из правильного cwd):**
- Backend: `./gradlew test` из `/Users/pavlokorolov/IdeaProjects/simple-sender/backend`. Сьют поднимает Testcontainers Mongo + in-memory JobRunr + MockWebServer — нужен доступный Docker. `build.gradle` исключает `@Tag("slow")` из дефолтного прогона — для send-assertion IT (Task 2) либо убедиться, что тег не проставлен, либо `./gradlew test -PrunSlow=true`.
- Создание директории отчёта: `mkdir -p /Users/pavlokorolov/IdeaProjects/simple-sender/work/13-funnels-tooling/logs/qa` перед записью `pre-deploy-qa-report.md` (директории `logs/qa` ещё нет).
- Frontend: `pnpm test -- --run` из `/Users/pavlokorolov/IdeaProjects/simple-sender/frontend`. Базовый `pnpm test` запускает vitest в watch-режиме (висит) — обязателен флаг `--run`.
- Parity-gate: `node frontend/scripts/check-locales.mjs` из корня репозитория.

**Сверка критериев:** проработать ровно те чек-листы, что в user-spec («Критерии приёмки»: Test for me / Дублювати / Зупинити всі активні запуски / Прев'ю / Спільне) и tech-spec («Acceptance Criteria», 8 технических пунктов). Для каждого критерия указать конкретный артефакт верификации (имя теста, имя файла, вывод parity-gate). Не подтверждать критерий без основания.

**Структура QA-отчёта** (`logs/qa/pre-deploy-qa-report.md`): дата; статус каждого сьюта (backend/frontend/parity) с числом тестов; таблица «критерий → статус → артефакт» по обоим спекам; отдельный блок Deferred-to-user (реальная доставка Test for me); блок Findings (если есть провалы/непокрытые критерии); итоговый вердикт ready-to-merge / blocked.

**Edge cases:**
- Docker недоступен → backend-IT упадут; зафиксировать как блокер инфраструктуры, не как дефект фичи.
- vitest без `--run` зависнет в watch — всегда `--run`.
- Провал теста → НЕ чинить код в этой задаче; зафиксировать finding в отчёте, вернуть пользователю/команде.
- Критерий «реальная доставка Test for me» → всегда deferred-to-user, никогда не провал.
- Send-assertion IT с `@Tag("slow")` → молча выпадет из дефолтного `./gradlew test` (фильтр в `build.gradle`). Не считать «зелёный» прогон достаточным, не подтвердив, что этот IT реально выполнился (проверить отсутствие тега или прогнать `-PrunSlow=true`).
- Директория `work/13-funnels-tooling/logs/qa` отсутствует → запись отчёта упадёт без предварительного `mkdir -p`.

**Implementation hints:**
- Сначала прогнать все три сьюта, собрать сырые результаты, потом сверять критерии — так таблица критериев ссылается на реальные имена прошедших тестов.
- decisions.md содержит отчёты по задачам 1-9 и зафиксированные deviations — свериться, не разошлась ли реализация со спеком (это часть приёмки).
