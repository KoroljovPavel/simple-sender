## Description

Phase 4 ("author tooling") adds four new POST endpoints to the funnel backend: `duplicate`, `executions/stop`, `test-run`, and `steps/{stepId}/preview` (Tasks 1-2). This task wires the **frontend data layer** for those endpoints — it is the foundation Wave 4/5 UI tasks build on.

Add four new actions to `frontend/stores/funnels.ts` (`duplicate`, `stopAllExecutions`, `testRun`, `preview`) and the matching request/response types to `frontend/types/funnel.ts`. No UI in this task — buttons and the preview panel come in Tasks 5 and 6. This task delivers only the store actions + types + vitest coverage so those later tasks can call into a tested data layer.

The actions must follow the **existing store contract exactly** (see store header comment, lines 14-18): each action flips the `error` flag in its `catch` and **RE-THROWS**; the store **NEVER** calls `useApiError` (it crashes inside a Pinia action because `useApiError` → `useI18n()` needs a component setup context). Error-to-message mapping is the component's job (Task 5/6 setup via `useApiError`). `duplicate` returns a `FunnelResponse` and must call the existing `syncRow` helper so the new copy is reflected in the list. `useApi()` auto-attaches the XSRF token for non-safe methods, so the new POST calls get CSRF for free.

## What to do

1. **Add request/response types to `frontend/types/funnel.ts`:**
   - `PreviewStepRequest` — on-the-fly (possibly unsaved) step content sent in the preview request body: `{ stepType: StepType; text: string; parseMode?: string | null }`. Mirrors backend DTO (`stepType`, `text`, `parseMode`). Decision 9: preview renders this current content, not the saved step.
   - `PreviewStepResponse` — exactly `{ rendered: string; sampleData: boolean; kind: 'message' | 'non_message' }` (no ownerChatId/identity leakage).
   - `StopAllResponse` — `{ cancelled: number }` (`modifiedCount` from the bulk-cancel; backend field is a `long`).
   - Keep the existing file convention: doc-comment each type, reference the backend DTO it mirrors and the relevant Decision number.

2. **Add four actions to `frontend/stores/funnels.ts`** (after the existing `pause`/`delete_`, mirroring `activate`/`pause` shape — `error.value = false` at entry, `catch` flips `error.value = true` and re-throws):
   - `duplicate(funnelId: string): Promise<FunnelResponse>` — `POST {listUrl()}/{funnelId}/duplicate`; on success call `syncRow(created)` for contract symmetry with activate/pause, then return it. (Note: the new copy's id is not yet in the loaded list, so `syncRow` is a no-op for it — the list page handles surfacing the new row. Do NOT push a synthetic summary here.)
   - `stopAllExecutions(funnelId: string): Promise<StopAllResponse>` — `POST {listUrl()}/{funnelId}/executions/stop`; return the `{ cancelled }` payload.
   - `testRun(funnelId: string): Promise<void>` — `POST {listUrl()}/{funnelId}/test-run`; 2xx = enroll registered. On 422 (`funnel_owner_not_linked` / validation codes) the action re-throws so the component maps it inline.
   - `preview(funnelId: string, stepId: string, payload: PreviewStepRequest): Promise<PreviewStepResponse>` — `POST {listUrl()}/{funnelId}/steps/{stepId}/preview` with `body: payload`; return the rendered response.
   - Export all four from the store's returned object.

3. **Add vitest coverage** in `frontend/tests/stores/funnels.spec.ts` (extend the existing spec — it already mocks `useApi`/`useRoute`). For each new action: happy-path (correct URL/method/body + returned shape) and error-path (flips `error`, re-throws — never swallows).

**Dependencies:**
- Depends on Task 2 (backend) for the live endpoints; this task only needs the endpoint contracts (shapes are fixed in tech-spec Data Models), so it can be authored against those contracts and verified by vitest with a mocked `useApi`.
- No new npm packages.

**Edge cases:**
- `duplicate`: the returned copy's id is NOT yet in the loaded `funnels` list, so `syncRow` is a no-op for it. That is intentional — keep `syncRow` for contract symmetry and document it; the list page (Task 5) handles surfacing the new row (refetch/navigate). Do NOT fabricate a `FunnelSummaryResponse` from the detail response here.
- `preview`: backend may return `kind: 'non_message'` with a placeholder `rendered` for non-message steps and `sampleData: true` when the bot owner is not linked — the action just returns the payload verbatim; no branching in the store.
- `testRun` 422 (`funnel_owner_not_linked`, validation codes) and network errors both re-throw; the store does not distinguish them (component maps inline-vs-toast via `useApiError`).
- Reserved-word caution: `delete` is already aliased in the return object — the four new names are safe object-shorthand keys.

**Implementation hints:**
- Read the store header comment (lines 14-18) before writing — it is the binding contract for these actions.
- `useApi()` (composable) returns the `$fetch` instance; call as `useApi()<T>(url, opts)` exactly like existing actions. XSRF is auto-attached for POST in `useApi.ts` `onRequest` — do not set headers manually.
- For `preview`, pass the typed payload as `body`; `$fetch` serializes it to JSON.
- Mirror the existing vitest style: `apiMock.mockResolvedValueOnce(...)` for happy path, `apiMock.mockRejectedValueOnce({ statusCode: 422, data: { code } })` for error path, assert `toHaveBeenLastCalledWith(url, opts)` and `store.error`.
