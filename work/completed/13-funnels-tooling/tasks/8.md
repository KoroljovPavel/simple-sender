# Task 8: Security Audit

## Required Skills

Перед выполнением задачи загрузи:
- `/skill:security-auditor` — [skills/security-auditor/SKILL.md](.claude/skills/security-auditor/SKILL.md)

## Description

Полнофичевый аудит безопасности по OWASP Top 10 для фичи `13-funnels-tooling` (четыре новых инструмента автора: Duplicate, Stop-all, Test-run, Preview). Аудит **только аналитический** — код не пишем, не правим. Цель: прочитать все файлы, созданные/изменённые в волнах 1-6 этой фичи (бэкенд `funnel`-модуль + фронтенд funnel-store/страницы/компонент превью + i18n), и оценить их holistically против реальной модели угроз фичи.

Фича намеренно не вводит новой схемы БД, миграций и деплоя — это extraction + wiring существующих примитивов. Поэтому основная поверхность риска — **не новые механизмы, а корректность переиспользования существующих guard-ов** (`requireFunnel`, CSRF-цепочка, `VariableTemplateRenderer`-экранирование) на четырёх новых POST-ендпоинтах и в новой панели превью.

Конкретные векторы, которые нужно проверить (выведены из tech-spec Risks + security-relevant Decisions 5/7/9 + AC):

1. **Anti-IDOR (A01 Broken Access Control)** — каждый из 4 ендпоинтов (`/duplicate`, `/executions/stop`, `/test-run`, `/steps/{stepId}/preview`) ОБЯЗАН первым шагом проходить `FunnelService.requireFunnel(ownerId, projectId, funnelId)` (единый guard владения, унифицированный 404 для чужого/несуществующего/soft-deleted funnel/project — никогда 403, чтобы не ликать существование). `ownerId` берётся ТОЛЬКО из сессии (`currentUserId()`), никогда из path/body. Для test-run и preview: `requireFunnel`-404 должен ПРЕВАЛИРОВАТЬ над 422/`stepId`-404, иначе 404-vs-422 становится oracle существования воронки.
2. **A03 Injection / markup-XSS-дрейф в превью** — бэкенд рендерит превью через тот же `VariableTemplateRenderer.render`, что и рантайм движка: экранирование подставляемых значений байт-в-байт под `parse_mode` (`null`→None без экранирования, `HTML`→`& < >`, `MarkdownV2`→полный спецнабор). Авторский markup НЕ экранируется (намеренно). Фронт-панель `FunnelMessagePreview.vue` выводит рендеренную строку **только как текст, НИКОГДА `v-html`/`innerHTML`** — строка несёт Telegram-экранирование, не browser-safe (stored-XSS guard, конвенция проекта «never v-html», `FunnelStepForm.vue`).
3. **A01/A04 утечка чувствительных данных в ответах** — `PreviewStepResponse` и прочие DTO НЕ должны содержать `ownerChatId`, токенов бота, `telegramBotId`, webhook-секрета или иной Telegram-identity владельца. `PreviewStepResponse` строго `{ rendered, sampleData, kind }`. Стаб-`Subscriber` (sample-данные) не должен подменять реальные данные владельца так, чтобы ликовать факт привязки.
4. **CSRF (A01)** — все 4 новых ендпоинта — мутирующие POST в session-цепочке (`@Order(2)`). Они ОБЯЗАНЫ оставаться под CSRF-защитой (`CookieCsrfTokenRepository` + `X-XSRF-TOKEN`). Проверить, что никто не добавил их в scoped CSRF-disable (CSRF disable зарезервирован только для stateless webhook/public-API путей). Фронт-store должен слать токен через стандартный `useApi` round-trip.
5. **Test-run cross-tenant authz hole (A01)** — direct-enroll через `FunnelExecutionFactory.insertExecution(depth=0)` обходит матчинг триггеров; нужно убедиться, что он НЕ обходит tenant-изоляцию: подписчик резолвится строго project-scoped (`findByChat(projectId, telegramBotId, ownerChatId)`), `cancelExistingForPair`/`insertExecution` скоупятся по `projectId`+`funnelId`+`subscriberId`. Невозможность enroll-нуть чужого подписчика или в чужую воронку.
6. **Stop-all scoping (A01)** — `updateMulti` скоупится по `projectId`+`funnelId` (fail-closed tenant hardening как `cancelActiveFor`), не может задеть execution-ы другого тенанта/воронки.

По результатам — написать audit report (формат — по security-auditor SKILL.md). Каждую найденную уязвимость пометить severity (Critical/High/Medium/Low) + конкретный remediation. Если найдены реальные issue — lead спавнит fixer-задачу (вне scope этого аудита; аудит только фиксирует находки).

**Vectors checklist (выводы tech-spec):**
- **Anti-IDOR / precedence** — Testing Strategy → «Anti-IDOR + precedence»: все ендпоинты на чужом/несуществующем funnel/project → унифицированный 404; для test-run/preview `requireFunnel`-404 ПРЕВАЛИРУЕТ над 422/stepId-404 (чтобы 404-vs-422 не стал oracle существования). Подтвердить порядок проверок в `FunnelService`.
- **A03 escaping-drift** (Decision 9, Risk «Дрейф экранирования в превью») — превью рендерит на бэкенде тем же `VariableTemplateRenderer`; фронт выводит ТОЛЬКО текстом. Проверить, что в TS/Vue нет самописной подстановки/экранирования (drift-риск) и нет `v-html`.
- **Stored-XSS guard** (Decision 9, Risk «Stored-XSS у панелі прев'ю») — Telegram-экранированная строка НЕ browser-safe; `FunnelMessagePreview.vue` — text-binding (`{{ rendered }}`), никогда `v-html`/`innerHTML`. Сверить с vitest-assert «no v-html» (Task 6).
- **Identity-leak** (Decision 5/9) — `PreviewStepResponse` строго `{ rendered, sampleData, kind }`; нет `ownerChatId`/identity. Проверить все новые DTO + что `funnel_owner_not_linked` (422) не ликает в теле факт привязки сверх необходимого.
- **CSRF** (patterns.md ~120/211) — session-цепочка enforce-ит CSRF на POST; убедиться, что новые ендпоинты НЕ попали в scoped disable (зарезервирован под webhook/public-API). IT использует `.with(csrf())` — это подтверждает enforcement.
- **Test-run tenant-isolation** (Decision 1/2/3) — подписчик резолвится project-scoped через `ownerChatId`; enroll скоупится `projectId`+`funnelId`+`subscriberId`. depth=0 обходит ТОЛЬКО матчинг триггеров, не authz. Документированная race-угроза 04b (`ownerChatId` проставлен не-владельцем) — НЕ в scope этой фичи (наследуемая модель доверия 04b); зафиксировать как known/accepted, не как новую находку.
- **Stop-all tenant-isolation** (Decision 7) — `updateMulti` скоуп `projectId`+`funnelId`; cross-funnel scoping IT доказывает изоляцию.

**Dependencies:** все имплементационные задачи (1-6) должны быть `done` — аудит читает финальное состояние кода. Пакетов не требует.

**Edge cases для проверки:**
- Незалинкованный бот (`ownerChatId=null`) → 422 `funnel_owner_not_linked`, НИКОГДА 500 (предсказуемый бизнес-стан, не утечка stack-trace).
- Превью при незалинкованном боте → стаб-Subscriber с sample-данными, без NPE/500 и без раскрытия факта непривязки сверх флага `sampleData`.
- Невалидный/неизвестный `stepId` в preview → 404, но `requireFunnel`-404 (чужой funnel) должен идти РАНЬШЕ, чтобы не ликовать существование воронки до проверки владения.
- Повторный test-run (рестарт) не должен открывать гонку, ликающую чужие execution-ы.

**Implementation hints (направления для аудитора, не псевдокод):**
- Начни с grep по `requireFunnel` в `FunnelService.java` — убедись, что каждый из 4 новых сервис-методов вызывает его ПЕРВЫМ, до любого резолва `Bot`/`Subscriber`/`stepId`/валидации.
- Для CSRF — прочитай `SecurityConfig`, найди scoped CSRF-disable matcher; убедись, что `/funnels/**` POST в нём НЕ перечислены (остаются под `@Order(2)` session-цепочкой с CSRF on).
- Для v-html — `grep -rn "v-html\|innerHTML" frontend/components/funnels/` должен показать только комментарий-конвенцию в `FunnelStepForm.vue`, не реальное использование в `FunnelMessagePreview.vue`.
- Для identity-leak — прочитай определения новых record-DTO; убедись, что поля строго по Data Models tech-spec; перепроверь, нет ли случайного `toString`/логирования `ownerChatId`/токена.
- Помни token-leak invariant (patterns.md ~201): сущности с секретами не должны получать `toString` accessor; проверь, что превью/test-run не сериализуют `Bot` целиком в ответ.
