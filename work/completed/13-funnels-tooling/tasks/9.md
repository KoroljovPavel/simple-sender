# Task 9: Test Audit

## Description

Full-feature аудит **качества тестов** фичи 13-funnels-tooling (четыре инструмента автора: duplicate / stop-all / test-run / preview). Это **analysis-only** задача — никакого кода не пишем и не правим. Запускается в Audit Wave после того, как все имплементационные задачи 1-6 завершены и их тесты написаны.

Цель — холистически проверить тестовую поверхность всей фичи целиком (а не одного компонента): покрыт ли каждый инструмент, осмысленны ли assertions (не «зелёные, но ничего не проверяют»), сбалансирована ли пирамида (unit + IT + vitest, без E2E — что в этом проекте обосновано). Отдельный фокус — на инвариантах, которые легко «протестировать понарошку»: claim-CAS контракт stop-all, byte-точное экранирование preview под каждый `parse_mode`, все три ветки 422 у test-run, граница усечения имени duplicate, cross-funnel/tenant scoping, и precedence `requireFunnel`-404 над 422/stepId-404 (anti-IDOR oracle).

Результат — письменный audit-отчёт с найденными пробелами покрытия и слабыми assertions, каждый — с severity. Если найдены проблемы — lead спавнит fixer (эта задача только диагностирует).

## Details

Audit-only задача: НЕ менять тесты и код. Только читать, оценивать, писать отчёт. Любой найденный фикс — рекомендация для последующего fixer'а, не действие здесь.

**Что считать «слабым assertion» (anti-tautology фокус):**
- **Stop-all / claim-CAS:** тест, проверяющий только `status=cancelled`, но НЕ `stepRunStatus=done` — слабый (major+). По Decision 7 / Risks: bulk-cancel, флипнувший лишь `status`, проигрывает mid-tick `persistProgress` (resurrection / double-send). Оба поля обязаны быть в assertion. Также: проверка, что терминальные (`completed`/`failed`/`cancelled`) НЕ затронуты, и что счётчик именно `modifiedCount`.
- **Cross-funnel scoping:** без отдельного теста, сеющего активный execution в ДРУГОЙ воронке/проекте и проверяющего, что он уцелел, — скоуп `projectId`+`funnelId` недоказан (tenant-isolation, fail-closed). Отсутствие = major.
- **Preview-экранирование:** assertion должен сравнивать с **точной ожидаемой строкой** под каждый `parse_mode` (null / HTML / MarkdownV2), а не «содержит подстроку» / «не пустое». Дрейф экранирования = OWASP A03; именно поэтому рендер на бэкенде, а не на фронте. Проверить покрытие полного MarkdownV2-набора + backslash, и рендер-edge: `{{`/`}}`→литералы, незакрытый `{` verbatim, целочисленный `Double` без `.0`.
- **Test-run 422:** должны быть покрыты ВСЕ три ветки (`ownerChatId=null`, подписчик отсутствует, подписчик не `ACTIVE`) — все мапятся в один код `funnel_owner_not_linked`, но через разные пути; «один тест на одну ветку» недостаточно, если две другие недостижимы. Плюс HTTP-shape (тело с `code=`, статус 422 — не 500) на IT-уровне, а не только сервисный.
- **Test-run ordering:** happy-path обязан проверять ПОРЯДОК (`InOrder`: `cancelExistingForPair` перед `insertExecution(...depth=0)`) — иначе рестарт-семантика (Decision 3) и обход триггер-матчинга (Decision 2, depth=0) недоказаны.
- **Duplicate boundary:** граница имени должна быть проверена обеими сторонами (`==128` без обрезки И `>128`/`==129` → truncate, остаётся валидным, НЕ 400). Один тест «truncate работает» без верхней границы валидности — слабый.
- **Anti-IDOR precedence:** недостаточно проверить, что чужой funnel → 404. Для test-run/preview нужен тест, доказывающий, что `requireFunnel`-404 ПЕРЕВЕШИВАЕТ 422/stepId-404 — иначе разница «404 vs 422» выдаёт существование ресурса (oracle).
- **Frontend no-v-html:** обязателен assert, что панель превью НЕ использует `v-html`/`innerHTML` (рендерится только как текст). Telegram-экранированная строка не browser-safe → stored-XSS. Отсутствие такого assert = critical (прямой security-инвариант из tech-spec AC).

**Пирамида (architecture.md / patterns.md):**
- Бизнес-логика (duplicate-копирование, stop-all-фильтр статусов, test-run-ветвление, preview-режимы) — должна иметь **unit**-покрытие, не только IT.
- HTTP-контракт + persistence + cross-tenant + send-assertion — **IT** (`@SpringBootTest`+MockMvc+embedded Mongo; `MockWebServer` для outbound test-run).
- UI (действия стора, панель превью, confirm-диалог) — **vitest**.
- **E2E:** отсутствие — корректно (architecture.md: Playwright держится только на golden-path смены локали). Если в фиче внезапно появился E2E — флагнуть как немотивированный.
- Флагнуть: логику, доступную только через дорогой IT (надо опустить в unit); IT, дублирующий unit без добавления HTTP/persistence-ценности.

**Severity-шкала:** critical = нарушен security/корректностный инвариант без покрытия (например, нет no-v-html assert, нет claim-CAS `stepRunStatus=done`); major = существенный сценарий из стратегии не покрыт или assertion tautological; minor = стилистика/дубль/слабая читаемость без риска ложно-зелёного.

**Dependencies:** задачи 1-6 завершены (их тесты написаны и проходят). Wave 6 — после всех имплементационных волн.
**Edge cases аудита:** фактический набор/имена тестовых файлов могут отличаться от ожидаемого — ориентироваться на decisions.md как источник истины; если файла из ожидаемого списка нет — это сам по себе пробел покрытия (флагнуть).
**Implementation hints:** сверять каждый пункт «Testing Strategy» tech-spec с фактическим тестом 1:1; для backend использовать `grep` по `stepRunStatus`, `cancelExistingForPair`, `InOrder`, `funnel_owner_not_linked`, точным escape-строкам; для frontend — `grep` по `v-html`/`innerHTML` в спеке превью и в самом компоненте.
