# Воронки — зведений ручний smoke-чек-лист по всьому епіку

Що перевіряти руками в епіку **Воронки** (Фази 1–5, features `10`→`14`). Автотести
(unit + engine-IT + vitest) покривають рушій, конкурентність, ізоляцію тенантів і HIGH-сценарії;
цей документ — те, що підтверджується лише очима людини на екрані / у чаті Telegram.

**Джерело правди по кожній фазі** — її власний `smoke.md` (детальні покрокові кейси). Цей файл —
зведений індекс + повний чек-лист **Фази 5** (її окремого smoke не було) + **наскрізний крос-фазний
сценарій**, що проганяє весь епік разом.

> **Легенда:** `[AUTO]` — також покрито автотестами (smoke перепідтверджує на живому стеку);
> `[MANUAL-ONLY]` — недосяжно для автоматизації, smoke є єдиною перевіркою.

## Передумови (спільні для всього епіку)

- Бекенд доступний, `GET /health` → `HTTP 200`; фронт вказує на той самий бекенд.
- Тестовий **акаунт власника з верифікованим email** (інакше гейт «Verify your email» блокує воронкові фічі).
- Проєкт із **щонайменше одним ботом у `status: CONNECTED`**, webhook зареєстровано через HTTPS
  (`getWebhookInfo` показує URL, без `last_error_message`). Для крос-funnel сценаріїв із інлайн-кнопками
  потрібен **тунель** (ngrok тощо) — callback'и приходять webhook'ом.
- Особистий акаунт Telegram поруч; **не** роби `/start` боту заздалегідь для кейсів холодного старту.
- `mongosh`-доступ до БД + доступ до логів бекенду (читати іменовані лог-константи).
- Визначені кастом-поля проєкту (STRING/NUMBER/DATE) для темплейтингу й тригерів.
- Redis піднятий (rate-limit бекстопи Фаз 3 і 5 рахують саме в Redis).

> **Ніколи** не вставляй у чат/коміти/скріншоти: токени бота, рядок підключення `mongosh`, реальні
> числові chat id, plaintext API-ключ. Використовуй плейсхолдери.

# Фаза 5 — Композиція воронок (14-funnels-composition)

Новий крок `SUBSCRIBE_TO_FUNNEL` enroll-ить того самого підписника в **іншу** воронку проєкту.
Fire-and-forget: `endParentAfter=false` → батько продовжується паралельно; `endParentAfter=true` →
батько завершується одразу після enroll. Патерни (jump / повернення-на-меню) — конфігурація поверх
одного кроку. Поле кроку входу — `targetEntryStepId`.

## Ч.5A — Редактор кроку «Почати воронку» (лише браузер) · verify-user Task 4

> Заведення: відкрити воронку → **+ Add step**.

- [ ] **5A1 — Тип кроку є в пікері.** `[MANUAL-ONLY]` У списку типів кроку присутній **«Почати воронку»**
      (`SUBSCRIBE_TO_FUNNEL`). Обрати → рендериться форма кроку.
- [ ] **5A2 — Пікер цільової воронки.** `[MANUAL-ONLY]` Поле вибору цільової воронки — `SearchableSelect`,
      lazy-підвантажує `active`-воронки проєкту; пошук працює; вибір зберігається у `targetFunnelId`.
- [ ] **5A3 — Пікер кроку входу.** `[MANUAL-ONLY]` Після вибору цілі зʼявляється пікер **кроку входу**
      (lazy-fetch кроків цільової воронки) із сентинелом **«з початку»** (= `targetEntryStepId` null).
      Зміна цільової воронки **скидає** обраний крок входу.
- [ ] **5A4 — Прапорець «завершити».** `[MANUAL-ONLY]` Є чекбокс **«завершити цю воронку після старту»**
      (`endParentAfter`); стан зберігається.
- [ ] **5A5 — Підказка про не-`active` ціль.** `[MANUAL-ONLY]` Якщо обрана ціль **не** `active` (draft/paused)
      → інлайн-підказка біля пікера, що активація батька буде заблокована, поки ціль не активна
      (`data-test="step-subscribe-inactive-hint"`).
- [ ] **5A6 — Підказка про патерн повернення.** `[MANUAL-ONLY]` Видно підказку про рекомендований
      `endParentAfter=true`: інакше повернення в ще-живого батька з `allowReEnter=false` стане no-op (Ризик 2).
- [ ] **5A7 — Прев'ю кроку.** `[MANUAL-ONLY]` У панелі прев'ю крок `SUBSCRIBE_TO_FUNNEL` показує плейсхолдер
      **«Цей крок не надсилає повідомлення»** (non_message), а не зламаний рендер. *(test-audit minor-2)*
- [ ] **5A8 — i18n (uk ⇄ en).** `[MANUAL-ONLY]` Лейбли типу/полів і тексти помилок
      `funnel_subscribe_*` відрендерені перекладено в обох локалях, без сирих ключів.

## Ч.5B — Валідація збереження та активації (curl/UI) · verify-smoke Task 2

- [ ] **5B1 — Ціль не вказана.** `[AUTO]` Зберегти SUBSCRIBE без `targetFunnelId` → **422**
      `funnel_subscribe_target_required`.
- [ ] **5B2 — Ціль не існує / malformed / чужий проєкт.** `[AUTO]` Неіснуючий id, битий hex ObjectId, і
      воронка **іншого проєкту** → у всіх трьох **422** `funnel_subscribe_target_not_found` (один код, без
      existence-leak між тенантами). *(головний IDOR-guard при save)*
- [ ] **5B3 — Крок входу не в цілі.** `[AUTO]` `targetEntryStepId`, якого немає серед кроків цілі → **422**
      `funnel_subscribe_target_step_not_found`.
- [ ] **5B4 — draft-ціль зберігається.** `[AUTO]` Посилання на ще-`draft` ціль **зберігається без 422**
      (курка-яйце для двох звʼязаних воронок); `active` при save НЕ перевіряється.
- [ ] **5B5 — Активація з не-`active` ціллю.** `[AUTO]` Активувати батька, чия SUBSCRIBE-ціль `draft`/`paused`
      → **422** `funnel_subscribe_target_inactive`. Активувати ту саму ціль → активація батька проходить.
- [ ] **5B6 — SUBSCRIBE не ламає generic edge-pass.** `[AUTO]` Збереження воронки з SUBSCRIBE-кроком **не**
      піднімає хибний `funnel_broken_edge` (крок свідомо виключений з перевірки intra-funnel ребер).

## Ч.5C — Виконання enroll-шляху (реальний Telegram) · ядро фічі

> Збудуй дві воронки одного проєкту: **A** (з MENU-кроком `M`) і **B** (кілька кроків). Обидві `active`.

- [ ] **5C1 — Базовий enroll + успадкування.** `[AUTO]` Воронка з кроком SUBSCRIBE(target=B). Тригерни →
      `mongosh`: створено **нову** `funnel_execution` цілі B для того самого підписника; `currentStepId =
      targetEntryStepId`; `enrollDepth = батько+1`; **`telegramBotId` успадковано від батька** (без нового
      lookup бота). У Telegram приходить перше повідомлення B.
- [ ] **5C2 — `endParentAfter=true` → батько completed.** `[AUTO]` Крок SUBSCRIBE(end=true) → після enroll
      батьківське виконання `status: completed`, **наступні кроки батька не виконуються** (повідомлень після
      SUBSCRIBE від батька немає).
- [ ] **5C3 — `endParentAfter=false` → паралельно.** `[AUTO]` Крок SUBSCRIBE(end=false) → батько
      **продовжується** на наступний крок; обидві воронки (батько + ціль) йдуть паралельно, приходять
      повідомлення з обох.
- [ ] **5C4 — Повернення на меню.** `[MANUAL-ONLY]` `B → SUBSCRIBE(A, entry=M, end=true)` → після B підписник
      **приземляється на крок M воронки A** (її меню); інлайн-кнопки меню активні.
- [ ] **5C5 — Старт «з початку».** `[AUTO]` SUBSCRIBE із `targetEntryStepId=null` → дочірнє виконання
      стартує з **кроку 0** цілі.

## Ч.5D — Бекстопи проти розгону + стійкість (реальний Telegram / engine) · Ризик 1

- [ ] **5D1 — Depth-cap.** `[AUTO]` Цикл `A→B→A`, що перевищує `app.funnel.max-enroll-depth` (=10) →
      наступний enroll **пропущено** + greppable-WARN; батько **не** `failed`, цикл зупиняється.
- [ ] **5D2 — Rate-limit (окремий бекстоп).** `[AUTO]` Понад `app.funnel.auto-enroll-rate-per-min` (=20)
      enroll'ів за хвилину від одного підписника → наступний enroll **пропущено** + WARN; батько не `failed`.
      *(Це другий, незалежний від depth-cap бекстоп — Ризик 1.)*
- [ ] **5D3 — Неактивна / видалена / чужа ціль на рантаймі.** `[AUTO]` Ціль `draft`/`paused`/видалена або
      іншого проєкту на момент виконання → крок **тихо пропущено** + greppable-WARN (окремий id на причину,
      у логах лише id-и), **батько продовжується** (snapshot-ізоляція).
- [ ] **5D4 — Видалений крок входу.** `[AUTO]` `targetEntryStepId` вказує на видалений крок → **fallback на
      старт** цілі + WARN (без падіння).
- [ ] **5D5 — Re-enter no-op.** `[AUTO]` Ціль вже виконується для підписника + `allowReEnter=false` → повторний
      enroll **no-op** (без падіння) + окремий greppable-**WARN**. *(audit-fix: рівень саме WARN)*
- [ ] **5D6 — Re-enter restart.** `[AUTO]` Та сама ситуація з `allowReEnter=true` → старе виконання цілі
      `cancelled`, стартує свіже з кроку входу.
- [ ] **5D7 — Self-target A→A.** `[AUTO]` SUBSCRIBE цілиться у власну воронку: `allowReEnter=false` → no-op;
      `allowReEnter=true` → перезапуск з кроку входу.
- [ ] **5D8 — At-most-once.** `[AUTO]` Enroll — side-effect перед claim-conditional advance/complete
      (як EMIT_EVENT): повтор кроку при crash не дублює enroll (re-enter guard робить no-op).

# Наскрізний крос-фазний сценарій (увесь епік разом)

Один прохід, що зачіпає всі 5 фаз. Потрібен **тунель** (інлайн-кнопки).

1. **(Ф1)** Створити воронку **A**: `SEND_MESSAGE` з `{user.first_name}` → … → MENU-крок `M`. `[Ф1: A2,B2]`
2. **(Ф2)** У меню `M` додати дві inline-кнопки: одна-петля на саме `M`, друга → крок з `SUBSCRIBE_TO_FUNNEL`. `[Ф2: MENU, callback]`
3. **(Ф5)** Створити воронку **B** (кілька кроків); останній крок `SUBSCRIBE_TO_FUNNEL(target=A, entry=M, end=true)`. `[Ф5: 5C4]`
4. **(Ф5)** У кнопці кроку 2 виставити `SUBSCRIBE_TO_FUNNEL(target=B, end=true)`. `[Ф5: 5C2]`
5. **(Ф3)** Воронці **A** призначити `keyword`-тригер (напр. `старт`) замість/додатково до `/start`. `[Ф3: keyword]`
6. **(Ф1/Ф4)** Активувати обидві (A і B). Перевірити: активація **блокується**, поки якась ціль не `active`
   (`funnel_subscribe_target_inactive`). `[Ф5: 5B5]`
7. **(Ф4)** «Test for me» / або написати боту keyword `старт` → приходить повідомлення A, підставлене імʼя. `[Ф4: Test for me]`
8. **(Ф2→Ф5)** У меню `M` тапнути кнопку «почати B» → стартує **B**; батько A завершився (`end=true`). `[Ф5: 5C2]`
9. **(Ф5)** Пройти кроки B → останній крок повертає на **меню `M` воронки A**. `[Ф5: 5C4]`
10. **(Ф5)** Покрутити цикл A↔B багато разів → enroll зрештою **пропускається** (depth-cap/rate-limit) +
    WARN, жодна execution **не** `failed`, бот не зависає. `[Ф5: 5D1/5D2]`
11. **(Ф1)** `/stop` під час будь-якого очікування → активні виконання `cancelled`, кнопки більше не просувають. `[Ф1: C1]`
12. **(Ф4)** «Зупинити всі активні запуски» → діалог → підтвердити → toast із N; нові кліки не просувають. `[Ф4: stop-all]`

**Очікувано наскрізно:** імʼя підставлене (Ф1), меню з кнопками працює і петлить (Ф2), keyword стартує (Ф3),
test-run/дублювання/прев'ю доступні (Ф4), композиція A↔B із поверненням на меню працює і **не** йде в
нескінченність (Ф5), `/stop` і «зупинити всі» гасять усе.

## Нотатки

- Відрендерені тіла повідомлень і PII **ніколи не логуються** — перевіряй вміст у Telegram, не грепом логів.
- Каденція sweep (`FUNNEL_SCHEDULER_INTERVAL`, дефолт `PT30S`): закладай до одного зайвого інтервалу слаку
  при замірі Delay і при спостереженні dочірнього enroll (5C1, 5E1).
- Бекстопи Фази 5 (depth-cap + auto-enroll rate-limit) рахують у **Redis** — без піднятого Redis 5D1/5D2
  не відтворити коректно.
- Deploy / post-deploy автоматизація поки не застосовна (немає CI/CD) — уся процедура ручна, для
  розробника/staging, ніколи не на продакшен-даних.
