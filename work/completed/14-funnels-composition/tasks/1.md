## Description

Фундамент Фази 5 (композиція воронок): новий тип кроку `SUBSCRIBE_TO_FUNNEL` («Почати воронку») і його дані на вбудованій моделі кроку. Без цього фундаменту не можна писати валідацію цілі (Task 2), enroll-рушій (Task 3) і фронт-форму (Task 4) — усі вони залежать від наявності enum-константи та трьох нових полів.

Крок несе три нові поля на `FunnelStep`: `targetFunnelId` (ціль enroll), `targetEntryStepId` (опційний крок входу в цілі; null → старт цілі), `endParentAfter` (boolean; true → батько `completed` одразу після enroll). Поле кроку входу зветься **`targetEntryStepId`**, а НЕ `targetStepId` — щоб не плутати з наявним `Button.targetStepId` (intra-funnel MENU-таргет) і щоб generic edge-pass у `FunnelService.validateSteps` хибно не підняв `funnel_broken_edge` (Decision 5; code-research місцями пише `targetStepId` — ігнорувати, використовувати `targetEntryStepId`).

Обсяг саме цієї задачі — модель + дзеркало DTO + маппінг + enum-пін у тесті. **Повна логіка кроку (валідація цілі, enroll, виконання) — НЕ тут**, вона в Task 2 і Task 3. Але `StepType` бере участь у двох exhaustive switch'ах (`StepExecutor.execute` `:93`, `FunnelService.validateSteps` `:648`) без `default`-гілки — тож додавання enum-константи зламає компіляцію, поки в обидва switch'і не додано case. Цю задачу робить білд зеленим мінімальними тимчасовими гілками, які Task 2/Task 3 заповнять реальною логікою.

## What to do

1. **`StepType.java`** — додати константу `SUBSCRIBE_TO_FUNNEL` після `EMIT_EVENT`, з коротким коментарем у стилі наявних (Phase 5: enroll того самого підписника в іншу воронку проєкту; ціль — пара `(targetFunnelId, targetEntryStepId)`).

2. **`FunnelStep.java`** — додати три immutable-поля: `String targetFunnelId`, `String targetEntryStepId`, `boolean endParentAfter`. Додати геттери/сеттери у стилі наявних. У `copyOf(...)` скопіювати всі три (рядкові — by-reference як `eventName`; `boolean` — by-value). Оновити javadoc deep-copy контракту: нові скаляри — immutable value types, копіюються field-wise (snapshot-ізоляція, Decision 3 збережена).

3. **`FunnelStepDto.java`** — додати три поля в record: `String targetFunnelId`, `String targetEntryStepId`, `boolean endParentAfter`. Без bean-валідації (per-type перевірки живуть у `FunnelService` → 422, Task 2). Додати коментар-секцію в стилі `EMIT_EVENT`.

4. **`FunnelService.toSteps`** (`:575`) — змаппити три нові поля з DTO у `FunnelStep`. Рядкові — через `blankToNull(...)` (як `eventName`); `endParentAfter` — `dto.endParentAfter()` напряму (boolean primitive).

5. **`FunnelService.toStepDto`** (`:860`) — додати три аргументи у конструктор `FunnelStepDto` у тому ж порядку, що в record.

6. **`FunnelService.isMessageStep`** (`:386`) — НЕ додавати `SUBSCRIBE_TO_FUNNEL` (крок без повідомлення). Переконатись, що `previewStep` (`:377-383`) падає у `non_message` placeholder для нового типу автоматично (нічого не міняти, лише підтвердити поведінку).

7. **Exhaustive switch'і — тимчасові мінімальні гілки (щоб білд був зеленим):**
   - `StepExecutor.execute` (`:93`) — додати `case SUBSCRIBE_TO_FUNNEL`. Поки що повернути `StepResult.cont()` (no-op fire-and-forget), з TODO-коментарем, що реальний enroll додає Task 3. Не інжектити нові залежності тут.
   - `FunnelService.validateSteps` switch (`:648`) — додати `case SUBSCRIBE_TO_FUNNEL -> { }` (порожня гілка, реальну валідацію цілі додає Task 2). **Важливо:** НЕ передавати `targetEntryStepId` у generic edge-pass (`requireExistingTarget`, `:666-667`) — воно вже бере лише `getNext()`/`getTimeoutTargetStepId()`, тож targetEntryStepId автоматично виключений; просто нічого туди не додавати.

8. **`StepTypeTest.java`** — додати тест-метод, що пінить нову константу (`valueOf("SUBSCRIBE_TO_FUNNEL")` + `name()`), у стилі наявного `emitEvent_present`.
