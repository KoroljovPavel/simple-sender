# Task 2: Save + activation валідація цілі

## Required Skills

Перед выполнением задачи загрузи:
- `/skill:code-writing` — [skills/code-writing/SKILL.md](.claude/skills/code-writing/SKILL.md)

## Description

Друга хвиля фази 5 (композиція воронок). Task 1 уже додав тип кроку `SUBSCRIBE_TO_FUNNEL`, поля `targetFunnelId`/`targetEntryStepId`/`endParentAfter` на `FunnelStep` + `FunnelStepDto`, маппінг `toSteps`/`toStepDto` і enum-пін. Ця задача додає **серверну валідацію цілі** цього кроку на двох точках:

1. **Save-time валідація** (`FunnelService.validateSteps`) — нова гілка `SUBSCRIBE_TO_FUNNEL` з DB-lookup цільової воронки **fail-closed по `projectId`** батьківської воронки: ціль вказана / існує / в тому ж проєкті; крок входу (`targetEntryStepId`), якщо вказаний, існує в snapshot кроків цільової воронки. Це **перша валідація в `validateSteps`, що торкається БД** (решта — in-memory). Свідомо **НЕ** перевіряє `active`-статус цілі при збереженні (дозволяє посилатись на ще-`draft` ціль при побудові двох зв'язаних воронок — курка-яйце, Decision 6).

2. **Activation-блок** (`FunnelService.activate`) — при активації батьківської воронки кожна SUBSCRIBE-ціль має бути `active`, інакше `funnel_subscribe_target_inactive` (422). Це окрема перевірка, яка не виконується при save.

Крок свідомо **виключений з generic edge-pass** (`requireExistingTarget` для `next`/`timeoutTargetStepId`/button-targets) — його `targetEntryStepId` вказує в ІНШУ воронку, тож не повинен перевірятись проти `stepIds` поточної воронки (інакше хибно підняв би `funnel_broken_edge`). За поточної структури `validateSteps` цей крок уже не подає `targetEntryStepId` у generic-pass — головне НЕ додати його туди.

Чому fail-closed по `projectId`: `FunnelRepository.findById` НЕ project-scoped на рівні БД, тож після load обов'язкова явна перевірка `targetFunnel.getProjectId().equals(projectId)` — головний IDOR/cross-tenant guard при save (дзеркалить `requireFunnel` :439-441). Malformed `ObjectId` від `findById` кидає `IllegalArgumentException` — її треба зловити і трактувати як «ціль не знайдено» (як `requireFunnel` :434-437), а не пускати 500.

Результат: нові 422-коди `funnel_subscribe_target_required`, `funnel_subscribe_target_not_found`, `funnel_subscribe_target_step_not_found` (save), `funnel_subscribe_target_inactive` (активація), з unit/IT-покриттям кожного.

## What to do

1. Додати чотири нові константи error-кодів у `FunnelService` (поряд з наявними `CODE_*` :79-95):
   - `funnel_subscribe_target_required` — `targetFunnelId` відсутній/порожній.
   - `funnel_subscribe_target_not_found` — ціль не існує / malformed id / інший проєкт.
   - `funnel_subscribe_target_step_not_found` — `targetEntryStepId` вказаний, але немає в кроках цілі.
   - `funnel_subscribe_target_inactive` — (лише активація) ціль не `active`.

2. Розширити `validateSteps`, щоб вона мала доступ до `projectId` для DB-lookup. Поточна сигнатура `void validateSteps(List<FunnelStep> steps)` (:633) не несе projectId. Додати параметр `projectId` (новий метод/overload або зміна сигнатури) і оновити три внутрішні callsites — `update` (:176), `activate` (:281), `testRun` (:351) — у всіх трьох `projectId` уже в scope. Обрати найменш-інвазивний варіант (overload або додатковий параметр); не міняти семантику наявних перевірок.

3. Додати гілку `case SUBSCRIBE_TO_FUNNEL` у switch `validateSteps` (:647-662). Логіка валідації цілі:
   - `targetFunnelId` blank/null → `funnel_subscribe_target_required` (422).
   - lookup цілі через `funnelRepository.findById(targetFunnelId)`; malformed id (`IllegalArgumentException`) / `Optional.empty()` / `!getProjectId().equals(projectId)` → `funnel_subscribe_target_not_found` (422). Жодного existence-leak між тенантами (один код на всі три причини).
   - якщо `targetEntryStepId` НЕ null: перевірити, що серед `targetFunnel.getSteps()` є крок з таким id; інакше `funnel_subscribe_target_step_not_found` (422). `null` `targetEntryStepId` = старт цілі → валідний без перевірки.
   - `active`-статус цілі при save НЕ перевіряти.
   - Не подавати `targetEntryStepId` у generic `requireExistingTarget`-pass (це cross-funnel посилання).

4. Додати activation-перевірку. У `activate` (:273-289), після `validateSteps`, перед `setStatus(active)`: для кожного `SUBSCRIBE_TO_FUNNEL`-кроку резолвити ціль (той самий fail-closed lookup по `projectId`) і вимагати `targetFunnel.getStatus() == FunnelStatus.active`, інакше `funnel_subscribe_target_inactive` (422). Винести спільну резолв-логіку у приватний helper, щоб save і activate не дублювали lookup+fail-closed.

5. Оновити наявні `FunnelStepDto`-callsites у тесті під нову сигнатуру. Task 1 додав 3 поля до `FunnelStepDto` (17→20 аргументів конструктора), тож наявний helper `emitStep()` у `FunnelServiceEmitEventTest` (і будь-які інші місця, що викликають конструктор `FunnelStepDto` напряму) ще кличуть 17-арг конструктор і **не скомпілюються** після Task 1. Перш ніж додавати нові тести: знайди всі такі callsites (`grep "new FunnelStepDto"` у тестовому файлі) і онови їх до 20-арг сигнатури (нові 3 поля = `targetFunnelId`/`targetEntryStepId`/`endParentAfter`, для не-SUBSCRIBE кроків передавай `null`/`null`/`false`). Узгодь фактичний порядок аргументів з реальним record після Task 1, не вгадуй за tech-spec.

6. Написати тести у `FunnelServiceEmitEventTest.java` (наслідує `AbstractIntegrationTest`, реальний Mongo через Testcontainers; зберегти стиль наявних EMIT_EVENT-тестів). Покрити:
   - save → `funnel_subscribe_target_required` (null/blank target).
   - save → `funnel_subscribe_target_not_found`: (а) неіснуючий id, (б) malformed `ObjectId` hex, (в) ціль в ІНШОМУ проєкті (cross-tenant fail-closed).
   - save → `funnel_subscribe_target_step_not_found`: `targetEntryStepId` не в цілі.
   - save → успіх: валідна ціль того ж проєкту, `targetEntryStepId=null` (старт) і валідний крок входу; payload round-trip'иться через `toStepDto` (`targetFunnelId`/`targetEntryStepId`/`endParentAfter` на response і persisted step).
   - save → `active`-статус цілі НЕ блокує save: посилання на `draft`-ціль зберігається без 422.
   - activate → `funnel_subscribe_target_inactive`: активація батька з `draft`-ціллю → 422; з `active`-ціллю → успіх.
