# Task 3: Engine enroll-шлях (ядро фічі)

## Required Skills

Перед виконанням задачі завантаж:
- `/skill:code-writing` — [skills/code-writing/SKILL.md](.claude/skills/code-writing/SKILL.md)

## Description

Ядро фічі композиції воронок: рантайм-виконання кроку `SUBSCRIBE_TO_FUNNEL`. Коли рушій доходить до цього кроку у воронці-батьку, той самий підписник enroll-иться у цільову воронку проєкту (fire-and-forget, окрема execution, яку підхопить наступний sweep), після чого батько або продовжує (`endParentAfter=false` → `CONTINUE`), або завершується статусом `completed` (`endParentAfter=true` → новий `Outcome.COMPLETE`). Це покриває реальний кейс автора «виклик під-воронки + повернення на меню».

Залежить від Task 1 (модель: enum-константа `SUBSCRIBE_TO_FUNNEL` + поля `targetFunnelId`/`targetEntryStepId`/`endParentAfter` на `FunnelStep` уже існують). Ця задача додає шлях виконання, але НЕ валідацію збереження (це Task 2) і НЕ фронт (Task 4).

Чотири складові:
1. **Фабрика** — overload `FunnelExecutionFactory.insertExecutionAt(..., String startStepId)`, бо чинний `insertExecution` жорстко стартує з кроку 0 (`FunnelExecutionFactory.java:93`), а child SUBSCRIBE має стартувати з `targetEntryStepId`.
2. **Enroll-метод** — новий non-matching `FunnelEventService.enrollSpecificFunnel(...)`: пропускає матчинг тригерів (ціль задана явно), але застосовує ті самі per-subscriber бекстопи Фази 3 (depth-cap + auto-enroll rate-limit) перед фабрикою + fail-closed резолв цілі по `projectId` (головний IDOR-guard).
3. **Крок** — новий case `SUBSCRIBE_TO_FUNNEL` у `StepExecutor`: виклик `enrollSpecificFunnel` з `parent.enrollDepth + 1`, успадкування `telegramBotId` батька, потім `COMPLETE` якщо `endParentAfter` інакше `CONTINUE`.
4. **Рушій** — новий `Outcome.COMPLETE` у `StepExecutor` + гілка в `FunnelExecutionEngine.drive` → виклик наявного `complete(exec, now)`.

**Важливо:** поле зветься `targetEntryStepId` (НЕ `targetStepId`, як подекуди пише code-research — див. Decision 5: уникнення колізії з наявним `Button.targetStepId`).

## What to do

1. **`FunnelExecutionFactory` — overload `insertExecutionAt(projectId, funnel, subscriberId, telegramBotId, enrollDepth, startStepId)`.** Старт child execution з довільного `startStepId` замість жорсткого кроку 0. Якщо `startStepId == null` АБО не існує у snapshot цілі → fallback на крок 0 (як чинний `insertExecution`). Логіка ідентична `insertExecution`, відрізняється лише обчисленням `currentStepId`. Refactor: чинний `insertExecution` стає тонким делегатом до `insertExecutionAt(..., null)`, щоб не дублювати тіло (5 наявних callsites `insertExecution` — 2 у `FunnelEventService.insertOneFunnel`, 2 у `FunnelTriggerServiceImpl`, 1 у `FunnelService.testRun` — не змінюються). Зберегти `MongoTemplate.insert` (re-enter collision → `DuplicateKeyException`) і той самий greppable-лог `LOG_EXECUTION_STARTED`.

2. **`FunnelEventService.enrollSpecificFunnel(...)`** — новий public non-matching enroll. Порядок строго як у `dispatchForSubscriber`, БЕЗ матчингу тригерів і БЕЗ fan-out:
   - **a.** Depth-cap: `if (originDepth > maxEnrollDepth)` → greppable-WARN + return (no-op). Той самий `maxEnrollDepth`, повторно використати, НЕ дублювати окрему перевірку.
   - **b.** Rate-limit: `if (originDepth > 0 && autoEnrollRateLimitExceeded(subscriberId))` → greppable-WARN + return. Повторно використати наявний приватний `autoEnrollRateLimitExceeded` (той самий Redis-ключ `bf:rate:auto-enroll:{subscriberId}`, fail-open).
   - **c.** Резолв цілі: `funnelRepository.findById(targetFunnelId)` (інхеритед від `MongoRepository`, НЕ project-scoped). Потім **явна fail-closed перевірка** `targetFunnel.getProjectId().equals(projectId)`. Malformed/`null` `targetFunnelId`, відсутня ціль, інший проєкт, ціль не `active` (`draft`/`paused`) → greppable-WARN (окремий log-id на причину) + return. Лог лише id-и (без user-input, проти log-injection).
   - **d.** `telegramBotId`: НЕ резолвити CONNECTED-бота заново — успадкувати від батька. Передати `execution.getTelegramBotId()` параметром у `enrollSpecificFunnel` (Decision 9, один CONNECTED бот/проєкт; економить lookup).
   - **e.** Fallback кроку входу: `targetEntryStepId` передається як `startStepId` у фабрику; фактичний fallback на крок 0 (коли крок не резолвиться у snapshot) робить `insertExecutionAt`. Опц. WARN при fallback.
   - **f.** Re-enter: повторно використати наявний `insertOneFunnel`-патерн (`FunnelEventService.java:192`): `allowReEnter=true` → `cancelExistingForPair` + insert; `allowReEnter=false` → `insertExecutionAt` у try + swallow `DuplicateKeyException` з окремим greppable-WARN. Викликати `insertExecutionAt(projectId, targetFunnel, subscriberId, telegramBotId, originDepth, targetEntryStepId)`.
   - Весь метод error-isolated (`try/catch(Throwable)` + greppable-WARN), як `dispatchForSubscriber` — enroll-фейл НЕ валить батька.
   - Нові greppable-WARN константи (один id на причину, узгодити з наявним `LOG_*`-стилем): напр. `LOG_ENROLL_SKIP_TARGET_MISSING`, `LOG_ENROLL_SKIP_TARGET_WRONG_PROJECT`, `LOG_ENROLL_SKIP_TARGET_INACTIVE`, `LOG_ENROLL_REENTER_IGNORED`, `LOG_ENROLL_ENTRY_STEP_FALLBACK`. Причина має бути різнознавана в логах.

3. **`StepExecutor` — case `SUBSCRIBE_TO_FUNNEL`.** Додати гілку в exhaustive switch `execute(...)` (`StepExecutor.java:93`). Виклик `funnelEventService.enrollSpecificFunnel(execution.getProjectId(), execution.getSubscriberId(), step.getTargetFunnelId(), step.getTargetEntryStepId(), execution.getEnrollDepth() + 1, execution.getTelegramBotId())` (порядок параметрів за фінальною сигнатурою). Потім: `return step.isEndParentAfter() ? StepResult.complete() : StepResult.cont();`. `funnelEventService` уже інжектиться (`:71`/`:78`) — нового інжекту НЕ додавати (Decision 2, anti-bean-cycle). НЕ інжектити `FunnelExecutionFactory`/`FunnelExecutionEngine`/`FunnelService` у `StepExecutor`.

4. **`StepExecutor.Outcome` + `StepResult` — новий `COMPLETE`.** Додати `COMPLETE` у enum `Outcome` (`:329`) і статичну фабрику `StepResult.complete()` (дзеркало `cont()`, усі поля null).

5. **`FunnelExecutionEngine.drive` — гілка `COMPLETE`.** У switch `result.outcome()` (`FunnelExecutionEngine.java:257`) додати `case COMPLETE -> { complete(exec, now); return; }`. Наявний `complete(exec, now)` (`:518`) уже атомарно ставить `completed`/`done` через `stillClaimed` CAS і повертає управління — наступні кроки не виконуються. Гілка термінальна (як `CANCEL`/`FAIL`).

6. **Тести (engine-IT + unit + test-run IT).** Див. TDD Anchor нижче. Стиль `FunnelExecutionEngineIT` (MutableClock + MockWebServer + `engine.sweep()`); test-run шлях у стилі `FunnelTestRunSendIT`; unit у `FunnelStepExecutorTest` (Mockito).

Якщо у `FunnelExecutionEngineIT`/`FunnelStepExecutorTest` крок будується через позиційний конструктор `FunnelStepDto`/`FunnelStep` або через спільний тест-хелпер — онови такі callsites/хелпери до нової сигнатури (3 нові поля), інакше наявні funnel-тести перестануть компілюватись. Чинний `FunnelExecutionEngineIT` будує кроки через `new FunnelStep()` + сетери (не позиційний ctor) і безпосередньо не зачеплений; перевір це при написанні нових SUBSCRIBE-кроків і не вводь позиційний ctor там, де достатньо сетерів.

- `FunnelExecutionEngineIT::subscribeReEnterNoOpWhenTargetInflight` — ціль у процесі + `allowReEnter=false` → no-op (без падіння) + окремий greppable-WARN (assert лог).

## Details

**Files:**
- `FunnelExecutionFactory.java` — додати overload `insertExecutionAt(String projectId, Funnel funnel, String subscriberId, Long telegramBotId, int enrollDepth, String startStepId)`. Тіло = чинний `insertExecution`, але `currentStepId` обчислюється як: знайти крок з `id == startStepId` у `snapshot` → його id; якщо `startStepId == null` або не знайдено → `snapshot.isEmpty() ? null : snapshot.get(0).getId()` (поточна поведінка). Чинний `insertExecution(...)` стає `insertExecutionAt(..., null)`. Зберегти `mongoTemplate.insert` і `LOG_EXECUTION_STARTED`.
- `FunnelEventService.java` — новий public `enrollSpecificFunnel(...)`. Перевикористати приватний `autoEnrollRateLimitExceeded`, поля `maxEnrollDepth`/`funnelRepository`/`executionFactory`. Re-enter — за патерном наявного `insertOneFunnel` (`:192`), але викликати `insertExecutionAt(... targetEntryStepId)`. Нові `LOG_ENROLL_*` константи (id/код only). Метод error-isolated (`try/catch(Throwable)`).
- `StepExecutor.java` — новий case у `execute` switch; `Outcome.COMPLETE` + `StepResult.complete()`; виклик уже-інжектованого `funnelEventService`.
- `FunnelExecutionEngine.java` — `case COMPLETE -> { complete(exec, now); return; }` у `drive` switch (`:257`).
- `FunnelExecutionEngineIT.java` / `FunnelStepExecutorTest.java` — при побудові кроків через позиційний конструктор `FunnelStepDto`/`FunnelStep` або спільний тест-хелпер врахуй 3 нові поля з Task 1 (`targetFunnelId`, `targetEntryStepId`, `endParentAfter`) і онови наявні callsites/хелпери до нової арності (17→20), щоб наявні funnel-тести компілювались. У чинному `FunnelExecutionEngineIT` кроки будуються через `new FunnelStep()` + сетери — для нових SUBSCRIBE-кроків тримайся того ж стилю (сетери `setType(SUBSCRIBE_TO_FUNNEL)`, `setTargetFunnelId(...)`, `setTargetEntryStepId(...)`, `setEndParentAfter(...)`), щоб не зачіпати конструктор.

**Dependencies:** Task 1 (модель `SUBSCRIBE_TO_FUNNEL` + поля на `FunnelStep`/`FunnelStepDto`). Без нових пакетів. Реюз props `app.funnel.max-enroll-depth` (=10), `app.funnel.auto-enroll-rate-per-min` (=20).

**Edge cases:**
- `targetFunnelId == null` / malformed `ObjectId` → `findById` повертає empty / кидає → skip + WARN (error-isolated).
- Ціль іншого проєкту → fail-closed skip (IDOR-guard).
- Ціль `draft`/`paused`/видалена → skip + WARN.
- `targetEntryStepId` відсутній у snapshot цілі → fallback на крок 0 + WARN.
- Ціль уже in-flight + `allowReEnter=false` → `DuplicateKeyException` swallow → no-op + WARN.
- Self-target A→A → впирається в re-enter guard тієї ж воронки (no-op без `allowReEnter`; перезапуск з entry при `allowReEnter`) — окремої гілки коду НЕ потребує.
- Depth-cap / rate-limit перевищено → skip + WARN, батько НЕ падає.
- At-most-once: enroll це side-effect ПЕРЕД claim-conditional advance/complete (як EMIT_EVENT) — повтор кроку при crash дає повторний enroll, який re-enter guard зробить no-op; дублю send не буде.

**Implementation hints:**
- `FunnelRepository.findById(String)` інхеритед від `MongoRepository<Funnel, String>` — НЕ project-scoped, тому fail-closed `getProjectId().equals(projectId)` обов'язковий ПІСЛЯ load (дзеркало `FunnelService.requireFunnel` scoping).
- `telegramBotId`: НЕ резолвити CONNECTED-бота заново в enroll — передати `execution.getTelegramBotId()` від батька (Decision 9). Додати `Long telegramBotId` як параметр `enrollSpecificFunnel` (узгодити порядок зі StepExecutor-викликом).
- Bean-cycle: enroll іде наявним ребром `StepExecutor → FunnelEventService`; `FunnelEventService → FunnelExecutionFactory` уже існує. НЕ створювати back-edge у engine/step-executor.
- НЕ дублювати depth-cap/rate-limit логіку — перевикористати наявні поля/метод `FunnelEventService`. Зберегти інваріант «один dispatcher володіє бекстопами».
- Engine-IT: seed цілі як активної воронки в тому ж проєкті; `engine.sweep()` для батька; reload + assert нової execution цілі (запит по `funnelId`+`subscriberId`); другий sweep проганяє ціль і assert send через MockWebServer. Для rate-limit IT — або занизити prop, або зробити N enroll'ів у циклі (узгодити з наявними IT-патернами Phase 3).
- Test-run IT: дзеркалити `FunnelTestRunSendIT` — POST test-run батька з SUBSCRIBE-кроком (depth-0), assert enroll цілі з `enrollDepth=1`; child-send наступним sweep'ом.
- Логи: лише `projectId`/`funnelId`/`subscriberId`/`executionId`/коди — НІКОЛИ `matchKey`/назву/user-input (Decision 16 PII + anti-log-injection).
