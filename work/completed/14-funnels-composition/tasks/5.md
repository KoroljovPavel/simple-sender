Повний аудит якості коду фічі «Воронки. Фаза 5 — композиція воронок» (новий крок `SUBSCRIBE_TO_FUNNEL`). Це **не** код-райтинг задача — нічого не пишемо й не правимо, тільки читаємо весь код, створений/змінений у Задачах 1-4, і робимо холістичне ревью на крос-компонентні дефекти, які не видно при ревью окремих задач.

Результат — **звіт аудиту** (audit report), який повертається як текстовий вивід для батьківського агента (НЕ окремий .md файл). Звіт фіксує знахідки за серйозністю з посиланнями `file:line` і конкретною рекомендацією до кожної.

## Details

<!-- Усі деталі для виконання — технічні, організаційні. -->

**Природа задачі:** read-only аудит. Нічого не редагуємо в коді. Вивід — звіт.

**Перелік файлів:** базується на `Files to modify` Задач 1-4 (див. Context Files) + будь-які файли, додатково згадані виконавцями у `decisions.md`. На момент написання задачі `decisions.md` ще порожній (шаблон) — на момент виконання звірити з реальними записами Задач 1-4 і додати файли, якщо виконавці відхилялись від плану.

**Крос-компонентні інваріанти (головний фокус, бо ізольовані ревью їх не ловлять):**

1. **Bean-cycle (Decision 2, Risk «Bean-цикл», code-research §14.6):** enroll має йти через `FunnelEventService.enrollSpecificFunnel`, бо ребро `StepExecutor → FunnelEventService` уже існує. Перевір DI-граф: `StepExecutor` НЕ повинен інжектити `FunnelExecutionEngine`, `FunnelService` чи `FunnelExecutionFactory` напряму — це підняло б цикл бінів. Якщо виконавець Задачі 3 заінжектив фабрику в `StepExecutor` (альтернатива, яку code-research пропонував як «чистішу») — це відхилення від Decision 2 і втрата rate-limit бекстопа: фіксуй як Major.

2. **Backstop-reuse (Decision 2, AC «не дублює бекстопи», Risk 1):** `enrollSpecificFunnel` має застосувати **обидва** per-subscriber бекстопи Фази 3 у тому ж порядку, що dispatcher: спершу depth-cap (`originDepth > maxEnrollDepth`), потім auto-enroll rate-limit (Redis `bf:rate:auto-enroll:{subscriberId}`, рахує бо `originDepth > 0`). Шукай дубльовану логіку: другий лічильник, скопійований depth-check, інлайнений rate-limit замість переюзу наявного. Дублювання → Major (дрейф двох копій).

3. **Exhaustive switch (AC, Decision 3):** кожен switch/if-ланцюг по `StepType` має явно обробляти `SUBSCRIBE_TO_FUNNEL`. Точки: `StepExecutor` (case SUBSCRIBE), `FunnelService.validateSteps` (гілка + виключення з generic edge-pass `requireExistingTarget`), `FunnelService.previewStep`/`isMessageStep` (НЕ message → `non_message` placeholder). У рушії — новий `Outcome.COMPLETE` має бути оброблений (→ `complete(exec, now)`), без default-fall-through, що мовчки нічого не робить. Мовчазний fall-through → Major.

4. **Fail-closed project scoping (AC, Risk «Витік між тенантами»):** два місця. Save: `FunnelService.validateSteps` робить DB-lookup цілі в межах `projectId`. Runtime: `enrollSpecificFunnel` резолвить через `FunnelRepository.findById` (НЕ project-scoped на рівні БД), потім **обов'язково явна перевірка** `targetFunnel.getProjectId().equals(execution.getProjectId())`. Якщо перевірки немає або вона «fail-open» (продовжує при невідповідності) — Critical (IDOR/крос-тенант витік). Перевір також лог-injection: у WARN мають бути лише id-и, без user-input у повідомленні.

5. **Архітектурна узгодженість із Фазами 1-4:**
   - **At-most-once:** enroll — side-effect ПЕРЕД claim-conditional advance/complete (як EMIT_EVENT). Якщо enroll після claim або без re-enter guard як no-op при повторі — Major.
   - **Skip+WARN precedent:** дзеркалить `StepExecutor.setCustomField` → `cont()` + WARN. Кожна причина skip (draft/paused/видалена/чужа ціль, depth-cap, rate-limit, re-enter-no-op, відсутній крок входу) має окремий greppable-WARN id.
   - **Переюз, не дублювання:** `complete(exec, now)` наявний метод; `insertExecutionAt` — overload, що fallback-ить на крок 0 (не дублює `insertExecution`); `copyOf` копіює нові поля by-ref consistently з рештою.
   - **Immutability `FunnelStep`:** нові поля immutable, у `copyOf` копіюються (не губляться).
   - **Naming:** поле зветься `targetEntryStepId` (НЕ `targetStepId` — колізія з `Button.targetStepId`, Decision 5). Якщо десь прослизнув `targetStepId` для cross-funnel — Major (generic edge-pass хибно підняв би `funnel_broken_edge`).

**Серйозність знахідок:**
- **Critical:** крос-тенант витік / fail-open scoping, bean-cycle що ламає старт контексту, втрата at-most-once.
- **Major:** дубльований бекстоп, відсутній case в exhaustive switch, відхилення від Decision 2/3/5, втрачений бекстоп.
- **Minor / Nit:** стиль, дрібна неузгодженість логів, читабельність.

**Edge cases для перевірки у звіті:** self-target A→A (має впиратись у re-enter guard, без окремої гілки коду); видалений крок входу (fallback на крок 0 + WARN); `endParentAfter=true` з будь-якої позиції (не лише останній крок); malformed `ObjectId` цілі (skip+WARN, не виняток).

**Implementation hints:** Скіл `code-reviewing` дає 11 вимірів — пройди їх, але не розпорошуйся на дрібниці окремих задач (їх уже ревьюнули). Цінність цієї задачі — стики. Для DI-графа дивись `@Service`/конструктори бінів модуля. Для switch-повноти — grep по `StepType.` і `case `. Для scoping — grep по `getProjectId()` і `findById`.
