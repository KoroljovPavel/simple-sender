# Task 6: Security Audit

## Required Skills

Перед выполнением задачи загрузи:
- `/skill:security-auditor` — [.claude/skills/security-auditor/SKILL.md](.claude/skills/security-auditor/SKILL.md)

## Description

Full-feature security audit фічі `14-funnels-composition` (новий крок `SUBSCRIBE_TO_FUNNEL` — композиція воронок). Це **не** code-writing задача: нічого не реалізуємо й не правимо. Прочитати всі вихідні файли, створені/змінені в цій фічі (Wave 1–2 бекенд + frontend), і проаналізувати їх холістично проти OWASP Top 10 (2021+) як єдину поверхню атаки, а не файл за файлом.

Фіча додає cross-funnel посилання `(targetFunnelId, targetEntryStepId)`, яке на рантаймі резолвиться в чужу воронку й enroll-ить того самого підписника. Це створює три головні зони ризику, на яких має бути сфокусований аудит:

1. **Мультитенантна ізоляція (Broken Access Control / IDOR — OWASP A01).** Резолв цільової воронки `FunnelRepository.findById` НЕ є project-scoped на рівні БД — захист тримається на **явній fail-closed перевірці** `targetFunnel.getProjectId().equals(execution.getProjectId())`. Перевірити, що ця перевірка присутня й коректна **в обох точках**: при збереженні/активації (`FunnelService.validateSteps`, DB-lookup у межах `projectId`) і на рантаймі (`FunnelEventService.enrollSpecificFunnel`). Будь-який шлях, де ціль з іншого проєкту може enroll-итися, — Critical IDOR / cross-tenant data leak (Ризик 4 user-spec).

2. **Runaway / DoS-захист (OWASP A04 Insecure Design, rate limiting).** Цикли `A→B→A` дозволені навмисно. Стримування — два per-subscriber бекстопи: depth-cap (`enrollDepth`, Redis-незалежний) і auto-enroll rate-limit (Redis `bf:rate:auto-enroll:{subscriberId}`). Перевірити, що `enrollSpecificFunnel` застосовує **обидва** перед викликом фабрики, що бекстопи не дублюються й не обходяться (напр. неправильний `originDepth`, перевищення не призводить до skip, fail-open там, де має бути fail-closed), і що перевищення → тихий skip + WARN без падіння батька (а не нескінченний розгін). Ризик 1 user-spec.

3. **Cross-funnel reference як вектор (IDOR / небезпечна обробка зовнішнього посилання).** Посилання — це пара рядків, що приходить від автора через форму. Перевірити: malformed `ObjectId` не валить флоу й не витікає stack trace; застаріле/видалене посилання деградує безпечно (skip+WARN, snapshot-ізоляція), а не fail-open enroll; self-target (A→A) не дає неконтрольованого циклу повз re-enter guard.

Додатково перевірити крізь усі компоненти: input-валідацію нових полів (save-time 422-коди), **log-injection** (логи мають містити лише id-и, без user-input у тексті повідомлення — tech-spec явно вимагає це в `enrollSpecificFunnel`), відсутність нових секретів/hardcoded values, exhaustive-switch повноту (необроблений `StepType` → невизначена поведінка), at-most-once side-effect ordering (повтор кроку при crash не має дублювати enroll-сайд-ефект небезпечно), і коректність frontend-валідації як defense-in-depth (не як єдиний бар'єр — сервер має валідувати незалежно).

Deliverable: структурований audit-звіт (див. Verification Steps → Deliverable).

## What to do

1. Зібрати точний список файлів під аудит: усі `Files to modify` з tech-spec задач 1–4, плюс будь-які файли, згадані як змінені в `decisions.md` (звіти агентів Wave 1–2). Не покладатись лише на цей task-файл — звірити з фактично закоміченими змінами фічі.
2. Прочитати кожен файл під аудит у поточному стані (після реалізації Wave 1–2). Зрозуміти data flow від входу (форма → save → activate → runtime enroll) до сайд-ефекту (insert child execution).
3. Простежити три trust boundaries: автор→save (валідація цілі), активація→runtime (active-перевірка), runtime resolve→enroll (fail-closed projectId). На кожній перевірити, що неавторизований/малформований/cross-tenant вхід відсікається fail-closed.
4. Прогнати кожен компонент проти OWASP Top 10 (2021): A01 Broken Access Control / IDOR (головне), A03 Injection (включно log-injection), A04 Insecure Design (runaway/DoS, missing backstops), A05 Security Misconfiguration, A08 Software & Data Integrity, A09 Security Logging & Monitoring (greppable-WARN коректність, no user-input у логах). Інші категорії (A02 крипто, A06 vuln deps, A07 auth, A10 SSRF) — перевірити на застосовність; фіча не додає нових пакетів, секретів, auth-поверхні чи зовнішніх URL, тож імовірно N/A — зафіксувати це явно.
5. Для кожної знахідки: severity (Critical/High/Medium/Low), точний файл+рядок, attack vector + конкретний impact (реалістичний сценарій), actionable fix. Уникати false positives — враховувати вже наявний defense-in-depth (re-enter guard, snapshot-ізоляція, exhaustive switch, Фаза-3 бекстопи).
6. Якщо нових пакетів немає — зафіксувати, що dependency scan N/A для цієї фічі (бекенд: «New packages: None»; frontend: переюз наявних). Якщо frontend торкнувся `package.json` — прогнати `npm audit` й додати результат.
7. Сформувати фінальний audit-звіт як свою фінальну текстову відповідь (НЕ окремий .md файл).

## Details

**Nature:** Аудит, не реалізація. Нічого не змінюємо у вихідних файлах. Output — звіт як текстова відповідь.

**Files:** див. Context Files → «Файли під аудит». Перед аудитом звірити список з `decisions.md` (агенти Wave 1–2 могли торкнутись додаткових файлів або відхилитись від tech-spec — аудитувати фактичний стан, не план).

**Dependencies:** залежить від задач 2 (save/activation валідація), 3 (engine enroll-шлях), 4 (frontend форма). Аудит має сенс лише після того, як ці три приземлені — інакше поверхня неповна.

**Edge cases / зони підвищеної уваги:**
- Resolve цілі через `findById` (НЕ project-scoped у БД) — fail-closed `getProjectId().equals(...)` має бути ЄДИНИМ бар'єром і він має бути присутній на обох шляхах. Якщо хоч на одному відсутній/інвертований → Critical cross-tenant IDOR.
- `originDepth` обрахунок (`parent.enrollDepth + 1`) — помилка на off-by-one або 0 замість parent+1 ламає depth-cap → можливий нескінченний розгін (DoS).
- Rate-limit рахується лише бо `originDepth > 0` (як у dispatcher) — перевірити, що цей gate не обходиться при некоректному depth.
- Malformed `targetFunnelId` (не валідний ObjectId) — має бути catch + skip+WARN, не 500 зі stack trace (information disclosure).
- Логи: tech-spec вимагає «лише id-и, без user-input у повідомленні, проти log-injection» — перевірити кожен WARN на нових шляхах.
- Frontend валідація (пікери, payload) — це UX/defense-in-depth; сервер ЗАВЖДИ має валідувати незалежно. Якщо є серверний шлях, що довіряє клієнтському payload без re-валідації → High.
- Exhaustive switch у `StepExecutor`/`FunnelService.validateSteps` — необроблений новий `StepType` (default-гілка, що мовчки пропускає) може створити security-gap.
- At-most-once: enroll — side-effect перед claim-conditional advance/complete (як EMIT_EVENT). Повтор кроку при crash → повторний enroll, який re-enter guard має зробити no-op. Перевірити, що re-enter guard справді ловить це й немає вікна на дубль-enroll з security-наслідками.

**Implementation hints:**
- Почати з entry points: `FunnelStepForm.vue` payload → `FunnelService.validateSteps` → активація → `StepExecutor` case SUBSCRIBE → `enrollSpecificFunnel` → `insertExecutionAt`. Слідувати за даними.
- Порівняти `enrollSpecificFunnel` з наявним `dispatchForSubscriber` (Фаза 3) — порядок бекстопів (depth-cap → rate-limit → resolve) має дзеркалити dispatcher; розбіжність = потенційний обхід.
- Звірити re-enter guard з unique partial index `(funnelId, subscriberId)` filtered `running|waiting|waiting_for_reply` (architecture.md `funnel_executions`).
- N/A-категорії фіксувати явно з причиною (фіча: New packages None, без нових секретів, без нової auth-поверхні, без user-controlled URL → A06/A02/A07/A10 ймовірно N/A) — не пропускати мовчки.
