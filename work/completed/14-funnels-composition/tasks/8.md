# Task 8: Pre-deploy QA

## Required Skills

Перед выполнением задачи загрузи:
- `/skill:pre-deploy-qa` — [skills/pre-deploy-qa/SKILL.md](.claude/skills/pre-deploy-qa/SKILL.md)

## Description

Фінальна приймальна перевірка фічі «Воронки. Фаза 5 — композиція воронок» перед деплоєм. Це **не** задача написання коду — нічого нового не пишемо й не правимо. Мета: переконатися, що вся реалізація (Wave 1-2: data model, save/activation валідація, engine enroll-шлях, frontend-форма; Audit Wave: code/security/test аудити) зведена разом, повний набір тестів зелений, і кожен критерій приймання з user-spec та tech-spec виконано.

Фіча backend-центрична: автоматичні тести (unit + engine-IT + vitest) покривають усі AC, що відтворюються без живого Telegram. Один наскрізний сценарій — натискання inline-кнопок у реальному Telegram (`A → B → меню A`) — автоматично без тунелю не відтворюється (інлайн-кнопки приходять webhook'ом), тому його перевіряє користувач вручну локально за нашою інструкцією.

Deliverable: **QA-звіт** — пройдена матриця AC (user-spec + tech-spec), результат прогону тестів, перелік відкладених на user-check / post-deploy критеріїв, явний go / no-go вердикт. Звіт повертається як фінальне повідомлення і записується в decisions.md.

## What to do

1. Прочитати специфікації та результати аудитів:
   - user-spec.md (розділ «Критерии приёмки» — 15 пунктів) та tech-spec.md (розділ «Acceptance Criteria» — 7 технічних пунктів).
   - decisions.md — звіти по задачах 1-7, включно з code/security/test аудитами (чи всі знайдені проблеми закриті, чи є відкладені).
2. Прогнати повний набір backend-тестів модуля funnel (`./gradlew test`). Зафіксувати: зелено / червоно, кількість тестів, будь-які регресії у наявних тестах funnel-модуля.
3. Прогнати frontend-тести (`pnpm test` / `vitest run`). Зафіксувати результат форми кроку «Почати воронку».
4. Зібрати матрицю приймання: для кожного AC з user-spec і tech-spec вказати, чим він покритий (конкретний тест-кейс / IT) і статус (pass / deferred-to-user / fail). Прив'язати engine-IT та unit-кейси до відповідних AC.
5. Окремо позначити критерії, що **не** перевіряються автоматично і відкладені на user-check: наскрізний прогін `A → B → меню A` у реальному Telegram з натисканням inline-кнопок.
6. Запросити користувача виконати наскрізний ручний сценарій локально (інструкція — у секції Verification → User нижче) і зачекати на підтвердження результату.
7. Сформувати фінальний QA-звіт із go / no-go вердиктом. Записати короткий підсумок у decisions.md.

## Verification Steps

### Automated

Backend (модуль funnel):
- `cd backend && ./gradlew test` → усі тести зелені, без регресій. Особливо звернути увагу на:
  - `StepTypeTest` (enum-пін з `SUBSCRIBE_TO_FUNNEL`)
  - `FunnelStepExecutorTest` (SUBSCRIBE → `cont()` / `complete()`, виклик `enrollSpecificFunnel` з `parent.depth+1`)
  - `FunnelServiceEmitEventTest` (нові 422-коди `funnel_subscribe_*`, блок активації)
  - `FunnelExecutionEngineIT` (enroll у ціль, `enrollDepth=батько+1`, `telegramBotId` успадковано, `endParentAfter` так/ні, повернення на меню, depth-cap, rate-limit backstop, draft/paused/видалена/чужа ціль → skip+WARN, видалений крок входу → fallback, re-enter no-op, test-run шлях)

Frontend:
- `cd frontend && pnpm test` (або `pnpm vitest run`) → форма `FunnelStepForm.vue` рендерить пікер воронки + пікер кроку входу + прапорець; submit формує `{stepType, targetFunnelId, targetEntryStepId, endParentAfter}`; inline-підказка про не-`active` ціль.

Опційно (за потреби підтвердити 422-коди поза IT) — `curl` на funnel save/activate/test-run з поганою ціллю → очікувані `funnel_subscribe_*` коди.

### User

Запит до користувача — наскрізний прогін повного сценарію `A → B → меню A` у реальному Telegram (інлайн-кнопки приходять webhook'ом, headless без тунелю не відтворюються):

1. Підняти сервіс локально (backend + frontend; за потреби — тунель для Telegram webhook, див. deployment.md).
2. У редакторі побудувати головну воронку **A** з inline-меню (MENU-крок `M`); гілка однієї кнопки завершується кроком `SUBSCRIBE_TO_FUNNEL(ціль=B, завершити=так)`.
3. Побудувати воронку **B** (кілька питань + генерація пропозиції); останній крок — `SUBSCRIBE_TO_FUNNEL(ціль=A, крок входу=M, завершити=так)`.
4. **Активувати обидві** воронки (A і B мають бути `active`, інакше активація заблокується кодом `funnel_subscribe_target_inactive`).
5. Натиснути «Test for me» на воронці A.
6. У реальному Telegram пройти `A → (кнопка меню) → B → (відповіді) → меню A`.

Очікуваний результат: натискання кнопки меню в A стартує B; після проходження B підписник повертається й **знову бачить меню воронки A** (крок `M`); цикл не розганяється нескінченно; жодна execution не падає в `failed`.

Агент має дочекатися підтвердження користувача (pass/fail + спостереження) перед фінальним вердиктом.

**Acceptance matrix — джерела:**
- user-spec «Критерии приёмки»: 15 пунктів (новий тип кроку у редакторі; підвантаження воронок/кроків; inline-підказка не-`active`; 4 коди валідації save; `active` не при save але блок активації; enroll створює execution з правильними `currentStepId`/`telegramBotId`/`enrollDepth`; `завершити=ні` паралель; `завершити=так` completed; повернення на меню; depth-cap; draft/paused/видалена runtime skip+WARN; видалений крок входу fallback; re-enter no-op + greppable-WARN; «Test for me»; preview non-message placeholder).
- tech-spec «Acceptance Criteria»: 7 технічних пунктів (усі тести зелені; exhaustive switch'і компілюються; enum-пін оновлено; без міграції/нового `ExecutionStatus`; 422-коди; `enrollSpecificFunnel` не дублює бекстопи; fail-closed по `projectId`).

**Edge cases для перевірки в матриці:**
- depth-cap **і** rate-limit — це ДВА окремі per-subscriber бекстопи (Ризик 1); обидва мають бути покриті окремими IT, не злиті в один.
- fail-closed резолв цілі по `projectId` — і при save, і на рантаймі (головний IDOR-guard).
- greppable-WARN з окремим id на причину (draft/paused/видалена/чужа ціль, depth-cap, rate-limit, re-enter no-op) — батько не `failed`.
- self-target (A→A): no-op без `allowReEnter`, перезапуск з `allowReEnter`.

**Implementation hints:**
- Якщо якийсь AC не покритий жодним автотестом і не є user-check-only — це **gap**: зафіксувати у звіті як no-go-блокер або deferred з обґрунтуванням, не «пройти мовчки».
- Наскрізний Telegram-прогін — єдиний легітимний user-check (підтверджено tech-spec «E2E tests: None» + «Verification approach»). Не намагатися автоматизувати інлайн-кнопки headless.
- Якщо `./gradlew test` падає на чомусь поза funnel-модулем і не пов'язаному з фічею — зазначити окремо, не блокувати go автоматично, але повідомити.
- Звіт: матриця AC → статус, результат тестів, відкладені/gap пункти, go/no-go. Без дампів логів — лише висновки й посилання.
