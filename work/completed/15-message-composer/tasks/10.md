# Task 10: Security Audit

## Required Skills

Перед выполнением задачи загрузи:
- `/skill:security-auditor` — [skills/security-auditor/SKILL.md](../../../.claude/skills/security-auditor/SKILL.md)

## Description

Full-feature security audit фічі message-composer. Це таск Audit Wave: скіл `security-auditor` сам
є рев'ю — окремих reviewers немає. Аудитор читає **всі** вихідні файли, створені/змінені у цій фічі
(backend модель, sender, engine, validate/DTO/preview, callback-шлях, frontend types/form/preview),
і аналізує їх цілісно проти OWASP Top 10, з фокусом на чотири інваріанти, явно зафіксовані в
decisions фічі:

- **Anti-SSRF (Decision 6, OWASP A10):** бекенд **не дереференсить** медіа-URL — медіа лише
  URL/file_id, Telegram фетчить сам; URL-поля валідуються строго як `http(s)` scheme (відхиляти
  `file://`/`data:`/`javascript:`), `file_id` — непрозорий токен. Реального аплоаду/проксі немає.
- **XSS у превʼю (Decision 8, OWASP A03):** екранування за `parseMode` лишається backend-side
  (той самий `VariableTemplateRenderer`, що в рушії); фронт рендерить text-only через `{{ }}`,
  медіа через `:src`/`:href` — **ніколи** `v-html`/`innerHTML`.
- **Callback IDOR/owner-перевірки (Decision 2, OWASP A01):** `advanceOnCallback` зберігає строгий
  парсинг `{executionId}:{buttonIndex}` ДО будь-якого DB-lookup, IDOR-перевірки (cross-subscriber +
  cross-project), range-check індексу; новий позитивний guard `stepType == MESSAGE` не послаблює
  жодну з цих перевірок.
- **Token-scrubbing у нових sender-методах (Decision 5, OWASP A09):** нові
  `sendVideo`/`sendAudio`/`sendDocument` успадковують scrub зі спільного `send(...)`; окремий
  альбом-маппер `sendMediaGroup` має свій error/log-шлях — він теж зобов'язаний проганяти
  raw-відповідь через `TelegramApiClient.scrubTokens(...)`, інакше це новий token-leak site.

Результат — audit report (severity, issue, location, fix per finding) як фінальне повідомлення
агента. Звіт також ідентифікує будь-які інші OWASP-знахідки поза цими чотирма (mass-assignment у
нових DTO, injection через змінні-підстановку, надмірне логування payload тощо).

- [ ] Audit report повернуто фінальним повідомленням (не записано у файл).

## Verification Steps

### Automated

Цей таск не пише код і не запускає тести. Перевірка = повнота й якість audit report:
кожен з чотирьох інваріантів адресовано (finding або явне підтвердження), severity/location/fix
проставлені, OWASP-категорії прив'язані.

## Details

**Files:** аудит read-only — нічого не модифікуємо. Точний перелік вихідних файлів витягнути з
`decisions.md` (записи тасків 1–8) + tech-spec «Implementation Tasks». Деякі net-new класи
(`ContentBlock`, `MediaItem`, `BlockType`, нові DTO) не вказані поіменно в інпуті — знайти їх через
decisions.md або glob у `backend/src/main/java/com/botfunnel/funnel/`.

**Dependencies:** залежить від тасків 1–8 (весь backend + frontend фічі має бути реалізований).
Це останній перед-QA gate якості безпеки; код-аудит (Task 9) і тест-аудит (Task 11) — паралельні
в тій самій Audit Wave.

**Edge cases / прицільні перевірки:**
- Anti-SSRF: чи валідація `http(s)`-scheme застосована до **обох** — `mediaUrl` у `ContentBlock`
  і `MediaItem.mediaUrl` у альбомі; чи disambiguation `file_id` vs URL не створює байпасу (напр.,
  рядок, що виглядає як file_id, але є `javascript:`-payload); чи бекенд ніде не робить HTTP-запит
  по користувацькому URL.
- XSS: чи `previewStep` повертає вже екрановані рядки; чи фронт (`FunnelMessagePreview.vue`) не має
  жодного `v-html`/`innerHTML`/`domProps.innerHTML`; чи FILE/document `:href` обмежений `http(s)`
  (інакше `javascript:` у href — DOM-XSS).
- Callback IDOR: чи строгий парсинг `{executionId}:{buttonIndex}` стоїть ДО DB-lookup; чи новий
  guard `stepType == MESSAGE` доданий, а не послабив cross-subscriber/cross-project перевірки;
  range-check `buttonIndex` проти кнопок останнього блоку; чи не-callback кнопка (url) відхиляється.
- Token-scrub: чи альбом-маппер `sendMediaGroup` проганяє raw error/description через `scrubTokens`
  на ВСІХ своїх WARN/ERROR сайтах (паритет зі спільним `send(...)` — patterns.md «Scrubber sites for
  send-path logging»); чи нові обгортки нічого не логують в обхід.
- Додатково (поза чотирма): mass-assignment у нових `*Dto`/preview-request (чи `ownerId`/`projectId`
  не читаються з body — patterns.md DTO whitelist); injection через `{user.*}`/`{custom.*}`
  підстановку в caption; надмірне логування payload (token-leak із змісту блоків).

**Implementation hints:**
- OWASP-фокус саме на A01 (IDOR/access control), A03 (injection/XSS), A09 (logging/scrub), A10 (SSRF).
- Зіставляти знахідки з конкретними рядками patterns.md (Security): scrubber sites, anti-IDOR
  callback, preview backend-render/text-display, fail-closed `projectId`, mass-assignment DTO whitelist.
- Структура звіту: per-finding severity → issue → location (file:line) → OWASP cat → Decision →
  fix. Окремо — секція підтверджених інваріантів (positive findings).
