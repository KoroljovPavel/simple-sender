# Task 11: Test Audit

## Required Skills

Перед выполнением задачи загрузи:

## Description

Full-feature **test quality audit** для фічі 15-message-composer. Це Audit Wave-таск: аудитор сам
є рев'ю (reviewers порожні), артефакт — звіт про якість тестів. Аудит проводиться **після**
завершення всіх таск Wave 1–4 (backend foundation + engine + validation/DTO/preview + callback +
frontend types/UI), коли всі тести створені/переписані.

Мета — холістично перевірити **тестовий шар фічі цілком**, а не окремий файл: чи покриті всі
load-bearing інваріанти tech-spec (per-node at-most-once, snapshot-ізоляція, callback-контракт,
анти-SSRF, XSS-guard, альбом-маппер), чи асерти **змістовні** (перевіряють поведінку, а не лише
«не впало»/статус), чи збалансована піраміда (unit/integration/E2E), і чи **переписані** наявні
Phase 1–5 funnel-ITs зі старих типів (`SEND_MESSAGE`/`SEND_IMAGE`/`MENU`) на композер без втрати
покриття. Контрольний чек-лист покриття — секція **Testing Strategy** tech-spec (unit / integration /
E2E розкладка).

## What to do

1. Зібрати інвентар тестових файлів фічі: прочитати `decisions.md` (звіти Task 1–8 — які тести
   створені/змінені) + tech-spec "Files to modify"/"Files to read" по тестових шляхах. Скласти
   список усіх unit/IT/frontend-spec файлів, дотичних до композера.
2. Прочитати кожен тестовий файл зі списку. Для кожного зафіксувати: що покрито, чи асерти
   змістовні, чи є дірки відносно Testing Strategy.
3. Прогнати покриття по чек-листу Testing Strategy (нижче в Details — повний перелік). Для кожного
   пункту: **Covered / Partial / Missing** + посилання на конкретний тест (`file::testName`).
4. Оцінити **якість асертів** (анти-патерни test-master): тести без асертів, асерт лише на
   HTTP-статус без перевірки тіла/стану БД, `verify(...)` без перевірки аргументів там, де важливі
   аргументи (напр. caption лише на першому елементі альбому, клавіатура лише на останньому блоці),
   happy-path без негативів, відсутність перевірки крах-семантики (`times(K)` через два тіки).
5. Оцінити **баланс піраміди**: чи load-bearing інваріанти покриті на правильному рівні (per-node
   at-most-once і snapshot-ізоляція — реальна Mongo IT, не unit-мок; валідація — і unit, і
   controller-IT round-trip; альбом-маппер — MockWebServer unit).
6. Перевірити **регресію/повноту видалення**: жоден тест не посилається на видалені типи
   (`SEND_MESSAGE`/`SEND_IMAGE`/`MENU`) як на чинні; наявні Phase 1–5 funnel-ITs переписані на
   композер і не втратили асертів; tolerant-read для legacy-документів покритий.
7. Скласти **звіт-аудит** (повертається як фінальне повідомлення агента, НЕ окремий .md-файл):
   coverage-таблиця по Testing Strategy, список findings з severity (blocker/major/minor) +
   конкретний фікс, вердикт піраміди, явні дірки покриття. Кожен finding має вказувати
   `file::testName` або відсутній тест.

## Acceptance Criteria

- [ ] Прочитані всі тестові файли фічі (backend unit + IT, frontend vitest); інвентар у звіті.
- [ ] Coverage-таблиця проти Testing Strategy: кожен пункт unit/integration/E2E позначено
      Covered/Partial/Missing з посиланням на тест або позначкою «дірка».
- [ ] Перевірено покриття load-bearing інваріантів: per-node at-most-once (`times(K)` через два
      тіки, не лише статус), snapshot-ізоляція (зміна `blocks` після enroll → in-flight ран шле
      оригінал), callback-контракт + IDOR-негативи, анти-SSRF (не-`http(s)` URL відхиляється),
      XSS-негатив у preview, альбом масив-маппер + scrub raw-відповіді.
- [ ] Оцінено якість асертів (анти-патерни test-master): findings із severity + конкретним фіксом.
- [ ] Перевірено баланс піраміди (правильний рівень для кожного інваріанта) + повнота видалення
      старих типів у тестах + переписані Phase 1–5 ITs.
- [ ] Звіт повернуто фінальним повідомленням (без створення summary/report .md).

## Details

<!-- Audit-таск: «Files» — не код для зміни, а вхід для читання. -->

**Артефакт:** звіт-аудит **у фінальному повідомленні агента** (не .md-файл). Структура звіту:
1. Інвентар прочитаних тестових файлів.
2. Coverage-таблиця проти Testing Strategy (рядок = пункт стратегії; колонки: рівень, статус
   Covered/Partial/Missing, тест-посилання `file::testName`).
3. Findings: severity (blocker/major/minor) + опис + конкретний фікс + локація.
4. Вердикт піраміди (баланс unit/IT/E2E; load-bearing на правильному рівні).
5. Явні дірки покриття (відсутні тести).

**Чек-лист покриття (з Testing Strategy tech-spec):**

*Unit:*
- `FunnelStepExecutorTest`: порядок блоків; підстановка змінних у text + **усіх** caption
  (text/image/video/audio/file; 4096 для text, 1024 для медіа); trim+WARN над лімітами для
  **кожного** caption-типу; збірка альбому (caption лише на першому елементі); клавіатура лише на
  останньому не-альбомному блоці → `waitForReply`; без кнопок → `cont()`; **крах-семантика**: send
  блоку K кидає `TelegramSendException` → `cancel`/`fail` за `fromTerminalReason`, крок не просувається.
- `TelegramSenderTest` (MockWebServer): happy-path `sendVideo`/`sendAudio`/`sendDocument`/`sendMediaGroup`;
  успадковані retry/429; **альбом масив-маппер** (відповідь-масив → коректний результат); error/log-шлях
  альбома проганяє raw через `scrubTokens`; single-`message_id` маппер не зламаний.
- `FunnelStep.copyOf`: `blocks` — **новий інстанс списку**, не той самий reference.
- `VariableTemplateRendererTest`: екранування caption за parseMode (наявні зелені).
- Frontend vitest: редактор блоків (add/move/remove, per-type), валідація-дзеркало
  (порожній/>10/альбом 2–10/неприпустиме змішування типів/кнопки на не-останньому), мультиблок-превʼю.

*Integration:*
- `FunnelExecutionEngineIT` (реальна Mongo): per-node at-most-once **load-bearing** —
  `verify(sender, times(K))` через два тіки (не лише статус); snapshot-ізоляція **load-bearing** —
  зміна `blocks` після enroll → in-flight шле оригінал снапшоту; кнопки-на-останньому + `resumeOnCallback`,
  `lastButtonClicked` = `currentStepId:buttonIndex`, `funnel_button_clicked` рівно один раз, stale/duplicate
  webhook (не `waiting_for_reply`) ігнорується; наявні timeout-resume ITs зелені (паритет MENU).
- `FunnelTriggerServiceIT` callback-негативи: битий формат, >64 байти, не-hex executionId, out-of-range
  buttonIndex, не-callback кнопка (url), IDOR (cross-subscriber + cross-project) — кожен відхилено,
  виконання не просувається.
- `FunnelControllerIT`: save-валідація 422 (порожній композер, >10 блоків, альбом <2/>10, неприпустиме
  змішування типів, кнопки на не-останньому/альбомному, не-`http(s)` URL; over-length — позначено, не
  блокує); **DTO round-trip** save→fetch без втрати полів; preview мультиблок (масив відрендерених з
  екрануванням) + **XSS-негатив** (ворожий payload екранується, немає неекранованої розмітки).
- **Регресія:** Phase 1–5 funnel-ITs переписані на композер і зелені; legacy old-type документ
  (tolerant-read) не крешить engine на старті.

*E2E:* None — tech-spec свідомо не вимагає E2E для воронок (golden-path покривають engine ITs;
реальну доставку перевіряє користувач через «Test for me» post-deploy). Перевірити, що наявний
`frontend/e2e/funnels.spec.ts` не зламаний змінами фічі (а не вимагати нових E2E).

**Анти-патерни для відлову (test-master):**
- Асерт лише на HTTP-статус без перевірки тіла відповіді / стану БД.
- `verify(...)` без `ArgumentCaptor`/matcher там, де важливі аргументи (caption на першому елементі
  альбому; клавіатура на конкретному — останньому — send-у; `times(K)` для at-most-once).
- Happy-path без негативів (особливо валідація 422 і callback IDOR).
- Snapshot-ізоляція або at-most-once «доведені» на моках замість реальної Mongo IT.
- Тести, що мовчки посилаються на видалені типи або втратили асерти при переписуванні з MENU.

**Files (вхід для читання — НЕ для зміни):** усі тестові файли зі секції Context Files вище.
**Dependencies:** Task 1–8 (всі implementation-таски Wave 1–4) мають бути done; тести створені/переписані.
**Edge cases:** дірки покриття caption-типів (video/audio/file часто забувають); відсутність
крах-семантики IT; snapshot-ізоляція доведена слабко; пропущений XSS-негатив у preview; альбом
scrub raw-відповіді не перевірено.
**Implementation hints:** Testing Strategy tech-spec — джерело істини для чек-листа; кожен finding
прив'язувати до `file::testName` або до конкретної відсутньої перевірки; «зелений сюїт» ≠ «якісний
сюїт» — головна цінність аудиту в дірках і слабких асертах, не в підрахунку зелених.
