# Task 12: Pre-deploy QA

## Required Skills

Перед выполнением задачи загрузи:
- `/skill:pre-deploy-qa` — [skills/pre-deploy-qa/SKILL.md](../../../.claude/skills/pre-deploy-qa/SKILL.md)

## Description

Приёмочное тестирование фичи 15-message-composer **перед деплоем**. Это последняя проверка
качества до выкатки: прогнать весь автоматический тест-сюит (backend + frontend), пройтись по
**всем** критериям приёмки из user-spec и tech-spec и убедиться, что они выполнены кодом, и
подтвердить отсутствие регрессий после удаления старых типов кроков (`SEND_MESSAGE`,
`SEND_IMAGE`, `MENU`).

Фича ломает Decision 12 свідомо (плоские per-type поля → `List<ContentBlock>`), удаляет три типа
кроков и переписывает все funnel-IT (Phases 1–5) на композер. Поэтому ключевая цель этой QA —
доказать, что существующий тест-сюит остаётся зелёным как сетка безопасности и что новая
поведенческая модель (мультиблок-send, кнопки на последнем блоке, snapshot-изоляция,
per-node at-most-once) покрыта тестами и работает.

Это **pre-deploy** проверка: живое окружение не требуется. Реальная доставка в Telegram
(«Test for me» на собственном боте) выполняется **после деплоя** пользователем (Task 14) — её
сюда не тащим, а явно фиксируем как deferred live-check в отчёте.

Зависит от аудит-волны (Task 9 Code Audit, Task 10 Security Audit, Task 11 Test Audit): их отчёты
должны быть закрыты до старта QA, чтобы приёмка не накладывалась на незакрытые находки.

## What to do

1. Загрузить скилл `pre-deploy-qa` и следовать его методологии приёмочного тестирования.
2. Прочитать user-spec («Критерии приёмки», «Как проверить») и tech-spec («Acceptance Criteria»,
   «Agent Verification Plan»), собрать единый объединённый чек-лист критериев приёмки.
3. Прочитать **записи decisions.md по Task 9/10/11** (это персистентные артефакты аудит-волны —
   аудит-таски возвращают находки финальным сообщением агента, а не файлами; под `logs/working/`
   их нет). Убедиться, что критичных незакрытых находок нет; учесть их при оценке готовности.
4. Прогнать полный backend-сюит: `cd backend && ./gradlew test` — все unit/IT (executor, sender,
   engine-IT, controller-IT, callback-негативы, переписанные Phase 1–5 ITs) должны быть зелёными.
5. Прогнать frontend-сюит: `cd frontend && pnpm test` — vitest по редактору блоков, валидации-зеркалу
   и мультиблок-превью должен быть зелёным.
6. Пройтись по каждому критерию приёмки и сопоставить его с конкретным проходящим тестом/кодом
   (executor-порядок блоков, кнопки-на-последнем + branch, таймаут park-on-reply, callback-контракт
   неизменен, подстановка переменных в text+caption, save-валидация 422, удаление старых типов,
   per-node at-most-once, новые методы TelegramSender + альбом-маппер, snapshot-изоляция,
   preview-екранування / no v-html).
7. Подтвердить отсутствие регрессий: `StepType` больше не содержит старых типов, оба
   exhaustive-switch компилируются, старые funnel-IT переписаны на композер и зелёные.
8. Зафиксировать deferred live-check: реальная доставка в Telegram через «Test for me» переносится
   в post-deploy (Task 14) — Telegram MCP недоступен, проверяет пользователь.
9. Написать QA-отчёт в `logs/working/task-12/` (статус каждого AC: pass / fail / deferred, вывод
   тест-команд, список регрессионных проверок). По итогам — вердикт: готово к деплою или нет.

## Acceptance Criteria

Объединённый чек-лист из user-spec «Критерии приёмки» + tech-spec «Acceptance Criteria». QA
проверяет каждый пункт против проходящего теста/кода и помечает pass / fail / deferred.

**Автоматические сюиты:**
- [ ] `cd backend && ./gradlew test` — весь backend-сюит зелёный (executor, sender, engine-IT,
      controller-IT, callback-негативы, переписанные Phase 1–5 ITs).
- [ ] `cd frontend && pnpm test` — frontend vitest зелёный (редактор блоков, валидация-зеркало,
      мультиблок-превью).

**Поведение композера (user-spec):**
- [ ] Композер-крок с блоками text/image/video/audio/file/album рендерится как N последовательных
      сообщений Telegram в порядке автора; медиа Telegram тянет сам по URL/file_id.
- [ ] К последнему не-альбомному блоку чіпляются inline-кнопки; крок паркуется на ответ и
      разветвляется по нажатой кнопке (паритет MENU: `resumeOnCallback` + branch).
- [ ] Таймаут park-on-reply сохранён (`timeoutValue`/`timeoutUnit`/`timeoutTargetStepId`); по
      спливанню sweep ведёт на target-крок или завершает; существующие timeout-resume ITs зелёные.
- [ ] Callback-контракт неизменен: wire-формат `{executionId}:{buttonIndex}` (≤64 байт, строгий
      парсинг), `buttonIndex` 0-based мапится на кнопки последнего блока, `lastButtonClicked` хранит
      `currentStepId:buttonIndex`; IDOR/owner-проверки `advanceOnCallback` не ослаблены.
- [ ] Подстановка `{user.*}` / `{custom.*}` работает в text и **всех** caption, с екрануванням по
      `parseMode`.

**Валидация на save/activate (user-spec + tech-spec):**
- [ ] Пустой композер (0 блоков) и >10 блоков → 422 с инлайн-кодом.
- [ ] Album <2 или >10 элементов → 422; недопустимое смешивание типов в альбоме → 422.
- [ ] Кнопки на не-последнем блоке или на Album-блоке → 422; битые edge-таргеты → 422.
- [ ] text >4096 / caption >1024 — помечено на save, но **не блокирует**; в рантайме trim + WARN.
- [ ] Не-`http(s)` медиа-URL (`file://`/`data:`/`javascript:`) → 422.

**Архитектурные инварианты (tech-spec):**
- [ ] Старые типы `SEND_MESSAGE`/`SEND_IMAGE`/`MENU` удалены из backend и frontend; `StepType` их не
      содержит; оба exhaustive-switch (`StepExecutor`, `validateSteps`) компилируются без них.
- [ ] Per-node at-most-once: крах посеред отправки блоков оставляет ноду `in_progress` без повтора;
      уже отправленные блоки не пересылаются (доказано IT: `verify(sender, times(K))` через два тика).
- [ ] Новые методы `TelegramSender` (`sendVideo`/`sendAudio`/`sendDocument`/`sendMediaGroup`)
      наследуют retry/429/audit/scrub; альбом мапит массив-ответ.
- [ ] Snapshot-изоляция: `List<ContentBlock>` глубоко копируется в `FunnelStep.copyOf`; правки воронки
      после enroll не влияют на in-flight раны (доказано IT).
- [ ] Preview-эндпоинт возвращает массив отрендеренных блоков с backend-side екрануванням; фронт не
      использует v-html (XSS-негатив проходит).
- [ ] Нет регрессий: все существующие funnel-IT переписаны на композер и зелёные.

**Deferred (post-deploy, Task 14):**
- [ ] Реальная доставка в Telegram через «Test for me» — переносится в post-deploy (Telegram MCP
      недоступен; проверяет пользователь). Зафиксировать в отчёте как deferred, не как fail.

**Источник AC:** объединить user-spec «Критерии приёмки» (8 пунктов) + tech-spec «Acceptance
Criteria» (7 технических пунктов). Они частично пересекаются — дедуплицировать, но не терять ни
одного уникального инварианта (чек-лист выше — уже объединённый).

**Agent Verification Plan (откуда подход):** tech-spec «Agent Verification Plan» + user-spec «Как
проверить» → «Агент проверяет». Таблица из user-spec:
- Шаг 1: `./gradlew test` → все executor/sender/engine-IT/controller-IT зелёные.
- Шаг 2: `pnpm test` → vitest по редактору блоков и превью зелёные.
- Шаги 3–5 (curl против live funnel API: 0/11 блоков → 422; кнопки на альбоме/не-последнем → 422;
  валидный композер + кнопки на text-хвосте → 200 active) — это **live curl-проверки save-валидации**.
  В pre-deploy эти сценарии покрыты `FunnelControllerIT` (save-валидация); их повторный прогон против
  живого funnel API относится к post-deploy (Task 14, агент-curl). В pre-deploy подтверждаем их через
  зелёный `FunnelControllerIT`, а не против живого сервера.

**Dependencies:** Task 9 (Code Audit), Task 10 (Security Audit), Task 11 (Test Audit) — их находки
должны быть закрыты до старта. Источник находок аудита — **записи decisions.md по этим таскам**
(аудит-таски возвращают результат финальным сообщением агента, под `logs/working/` файлов нет).
Если в аудитах остались критичные открытые находки — QA отмечает это как блокер и не даёт зелёный
свет на деплой.

**Edge cases / на что обратить внимание:**
- Регрессии после удаления старых типов: убедиться, что переписанные на композер Phase 1–5 ITs реально
  выполняются (не `@Disabled`/не закомментированы), а покрывают старую поведенческую модель.
- **Порядок отправки блоков:** подтвердить, что `FunnelStepExecutorTest` ассертит **ORDER** отправки
  блоков (через `InOrder`/`inOrder(sender)`), а не только `times(K)` по количеству. Зелёный сюит без
  order-ассертов пройдёт QA молча, пропустив перепутанный порядок сообщений — это считать пробелом
  покрытия и отметить в отчёте, если order-ассертов нет.
- Fail-safe tolerant-read: legacy old-type документ, переживший ручной wipe, не должен крешить engine
  на старте — проверить, что соответствующий тест есть и зелёный.
- text >4096 / caption >1024 — это **warning, не блокер**: на save помечается, save проходит; в рантайме
  trim + WARN. Не считать это fail, если save возвращает 200 с предупреждением.
- Deferred ≠ fail: реальная Telegram-доставка отсутствует в pre-deploy осознанно (Telegram MCP
  недоступен) — фиксировать как deferred для Task 14, не как провал AC.

**Implementation hints:**
- Если тест падает — сначала классифицировать: реальный дефект фичи vs flaky/инфраструктура. Реальный
  дефект = блокер деплоя, описать в отчёте с указанием упавшего теста и связанного AC.
- IT используют реальную Mongo — убедиться, что окружение для тестов поднимается (см. patterns.md
  раздел Testing про инфраструктуру интеграционных тестов).
- Отчёт писать в `logs/working/task-12/` (НЕ создавать summary .md в корне фичи).
