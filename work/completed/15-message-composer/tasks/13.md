# Task 13: Deploy + ручне очищення даних

## Required Skills

Перед выполнением задачи загрузи:
- `/skill:deploy-pipeline` — [skills/deploy-pipeline/SKILL.md](.claude/skills/deploy-pipeline/SKILL.md)

## Description

Фінальний крок фічі 15-message-composer: викотити зміни через GitHub CI/CD і **вручну** очистити
колекції `funnels` + `funnel_executions` на цільовому середовищі.

Чому ручний wipe замість backfill (Decision 4): фіча видаляє старі плоскі типи кроків
(`SEND_MESSAGE`/`SEND_IMAGE`/`MENU`) і замінює їх композером `StepType.MESSAGE` з
`List<ContentBlock> blocks`. Старі документи воронок/виконань несумісні з новою моделлю.
Продакшну ще немає, тож backfill flat→composer (надто ризикований/складний) не робимо —
просто чистимо дані. Старі воронки доведеться перебудувати в новому форматі.

Деплой — **тільки через GitHub CI/CD** (правило проекту CLAUDE.md: ALL deployments via GitHub
CI/CD only; прямий доступ до сервера — лише для emergency debugging зламаного проду). Прямого
SSH / рестарту контейнерів для деплою не використовуємо. Ручне очищення колекцій — це **крок
деплою** на середовищі без продакшну, виконується через дозволений канал доступу до БД того
середовища (наприклад `mongosh` проти dev/staging Mongo), не як обхід CI/CD.

Після старту backend — перевірити логи: engine sweep (`FunnelExecutionEngine` `@Recurring`)
піднявся, немає помилок серіалізації снапшотів `ContentBlock`/`FunnelExecution`.

## Preconditions

- **Підтвердити з користувачем перед будь-яким дотиком до даних:** цільове середовище / `MONGODB_URI`
  (куди деплоїмо і де чистимо `funnels`+`funnel_executions`) та порядок «деплой vs wipe». Проду немає,
  але деструктивний wipe має виконуватися саме на правильному (dev/staging) таргеті — помилковий URI
  знищить не ті дані. Не виконувати очищення, доки таргет і ordering не узгоджені явно.

## What to do

1. Переконатися, що Task 12 (pre-deploy QA) пройшла зелено: бекенд `./gradlew test` + фронт
   `pnpm test`/`pnpm build` (locale-parity gate), усі AC user-spec/tech-spec підтверджені, регресій

2. Викотити зміни через GitHub CI/CD (merge/push у відповідну гілку деплою згідно з налаштованим
   pipeline; платформа deploy — TBD, див. deployment.md). Дочекатися успішного завершення
   build+test+deploy у GitHub Actions і health-check.
3. **Перед** тим, як нова версія почне обробляти трафік (або одразу як крок деплою на середовищі
   без проду), вручну очистити колекції `funnels` і `funnel_executions` на цільовому середовищі
   через дозволений канал доступу до БД (наприклад `mongosh`). Підтвердити, що обидві колекції
   порожні (`countDocuments` == 0).
4. Verify-логи після старту backend:
   - engine sweep піднявся — у стартовому/recurring-лозі видно тік `FunnelExecutionEngine`
     (JobRunr `@Recurring`, інтервал `FUNNEL_SCHEDULER_INTERVAL`, дефолт `PT30S`);
   - немає stack-trace серіалізації/десеріалізації снапшотів (`ContentBlock`, `FunnelStep.blocks`,
     `FunnelExecution`) — Jackson/Spring Data Mongo помилок мапінгу немає;
   - стартові міграції відпрацювали без винятків (вони log-but-never-throw): `FunnelStepIdBackfill`
     і `trigger-index reconciliation` → APPLIED/NO-OP, без ERROR;
   - `GET /health` повертає `{"status":"ok"}`.
5. Зафіксувати у звіті: який commit/тег задеплоєно, що колекції очищено (before/after counts),
   результат перевірки логів.

## Details

<!-- All details for task execution — technical, organizational, any other. -->

**Deploy channel:** тільки GitHub CI/CD. Прямий доступ до сервера (SSH, рестарт контейнерів) —
заборонений для викату; допустимий лише як emergency debugging зламаного проду (CLAUDE.md). ALWAYS
питати користувача перед push/merge у гілку деплою (CLAUDE.md: ALWAYS ask before Deploy/push to
main/production).

**Manual data wipe (Decision 4):** очищення `funnels` + `funnel_executions` — свідомий крок деплою,
а не backfill. Продакшну немає → втрата воронок прийнятна (Risk-таблиця tech-spec: «Виконати лише на
середовищі без проду; зафіксувати як крок деплою»). Доступ до БД середовища через дозволений канал
(`mongosh` проти dev/staging Mongo, `MONGODB_URI`); це не порушує «no direct server access», бо це
операція над даними середовища, не обхід деплой-pipeline. Жодних нових індексів/колекцій фіча не
вводить; `auto-index-creation=true` лишається.

**Files:** код-файлів не змінюємо — це деплой-таска (викат уже змерджених змін Tasks 1–11 + зелений QA Task 12).

**Dependencies:**
- Task 12 (pre-deploy QA) — має бути зелена (тести + AC). Блокуюча залежність.
- GitHub Actions pipeline — платформа/воркфлоу TBD (deployment.md → CI/CD «TBD»). Якщо pipeline ще не
  існує, узгодити з користувачем фактичний канал викату перед дією.

**Edge cases:**
- Legacy old-type документ пережив wipe (tolerant-read fail-safe з tech-spec): engine не повинен
  крешити на старті — підтвердити саме у логах (немає фатальної помилки десеріалізації).
- `FUNNEL_SCHEDULER_INTERVAL` має бути ISO-8601 Duration (`PT30S`), не ціле число секунд, і ≥
  JobRunr `poll-interval-in-seconds` (15) — інакше sweep не підніметься коректно.
- Якщо health-check у pipeline падає або в логах є помилки серіалізації снапшотів — НЕ вважати
  деплой успішним; зафіксувати і повідомити користувача.

**Implementation hints:**
- Стартові міграції (`FunnelStepIdBackfill`, `FunnelTriggerIndexReconciliation`) — idempotent,
  log-but-never-throw; грепнути стартовий лог на `trigger-index reconciliation` → APPLIED/NO-OP.
- Engine sweep — JobRunr `@Recurring` у `FunnelExecutionEngine`; перевіряти наявність тіку у логах,
  не рахувати оброблені виконання (їх 0 після wipe — це норма).
- `/health` — статичний liveness `{"status":"ok"}` (без DB-перевірки).
