# Task 14: Post-deploy verification

## Required Skills

Перед выполнением задачи загрузи:
- `/skill:post-deploy-qa` — [skills/post-deploy-qa/SKILL.md](.claude/skills/post-deploy-qa/SKILL.md)

## Description

Фінальна перевірка фічі `15-message-composer` на живому (задеплоєному) середовищі після Task 13
(deploy + ручне очищення `funnels`/`funnel_executions`). Це єдина перевірка **реальної доставки**
в Telegram поза автотестами — pre-deploy QA (Task 12) вже прогнала повний сюїт і AC без живого
середовища, тому тут фокус саме на end-to-end поведінці на live.

Перевірка двостороння:
- **Агент** (curl/bash): підтверджує, що save/activate валідного мультиблок-композера на live
  повертає 200 і воронка переходить у стан `active`.
- **Користувач** (in-app «Test for me», Phase 4 test-run на власному Telegram): підтверджує реальну
  послідовну доставку блоків у правильному порядку та коректне розгалуження по кнопці на останньому
  блоці.

**Важливо:** Telegram MCP недоступний — агент не може сам тригернути/спостерігати реальну доставку
в Telegram, тому ця частина повністю user-driven через in-app «Test for me». Агент готує валідну
воронку та надає користувачу чіткі кроки перевірки.

## What to do

1. Виконати Agent Verification Plan з tech-spec на live-середовищі (curl-частина):
   - Зберегти/оновити воронку з валідним мультиблок-композером
     (text → image+caption → album×3 → text-хвіст із кнопками) → очікувано 200.
   - Активувати воронку → очікувано воронка у стані `active`.
2. Підготувати воронку до user-частини: переконатися, що збережений композер містить саме той
   мультиблок-сценарій, який користувач перевірятиме через «Test for me».
3. Передати користувачу інструкцію на in-app «Test for me» (Phase 4 test-run) на власному Telegram
   та зібрати підтвердження за критеріями нижче.
4. Звести результати: відмітити acceptance criteria (user-spec + tech-spec), пов'язані з реальною
   доставкою. Якщо pre-deploy QA (Task 12) відклала якісь live-критерії — підібрати їх тут.
5. Записати підсумок верифікації у decisions.md (pass/fail по кожному кроку, будь-які відхилення).

## Verification Steps

### Agent (curl)

Цільовий live-базовий URL уточнити у користувача (у deployment.md Production URL = TBD — **не
вигадувати**, підтвердити з користувачем). Валідний `{projectId}` і воронку також отримати у
користувача в рантаймі: після Task 13 (ручне очищення) колекції `funnels`/`funnel_executions`
порожні, тому конкретні id не можна вгадати наперед.

- Save/update валідного композера (text → image+caption → album×3 → кнопки на text-хвості):
  `curl -X PUT <live>/api/v1/projects/{projectId}/funnels/{funnelId}` з валідним тілом → **200**.
- Activate воронки:
  `curl -X POST <live>/api/v1/projects/{projectId}/funnels/{funnelId}/activate` (підтверджено в
  FunnelController) → відповідь / подальший GET показує воронку у стані **`active`**.
- (Опційно) перевірити логи бекенду після активації: engine sweep піднявся, без помилок серіалізації
  снапшотів блоків.

### User (in-app «Test for me»)

Агент просить користувача виконати на власному Telegram (Telegram MCP недоступний — це єдиний шлях
перевірити реальну доставку):

- Відкрити редактор воронки → запустити **«Test for me»** (Phase 4 test-run) для збереженого
  мультиблок-композера.
- Підтвердити: блоки приходять як **N окремих повідомлень** у правильному порядку
  (text → image+caption → album×3 → text-хвіст із кнопками).
- Натиснути кнопку на останньому (text-хвіст) блоці → підтвердити, що воронка пішла у **правильну
  гілку**.
- Повідомити агенту pass/fail і будь-які розбіжності (порядок, відсутні блоки, неправильна гілка).
