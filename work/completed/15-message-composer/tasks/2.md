# Task 2: TelegramSender — нові sender-методи + альбом-маппер

## Required Skills

Перед виконанням задачі завантаж:
- `/skill:code-writing` — [skills/code-writing/SKILL.md](../../../.claude/skills/code-writing/SKILL.md)

## Description

Композер-крок (`StepType.MESSAGE`) шле підписнику N окремих повідомлень Telegram різних типів:
text/image/video/audio/file/album. `TelegramSender` сьогодні має лише `sendText` (`/sendMessage`) і
`sendPhoto` (`/sendPhoto`), обидва над спільним приватним `send(...)`, що несе CONNECTED-фільтр,
5xx-backoff (1s/2s/4s ×3), 429-loop, 30s-deadline, типізований error-mapping, audit-події
(`telegram_message_sent`/`telegram_send_failed`), Decision-4 subscriber-hook і token-scrubbed logging.

Цей таск додає чотири нові sender-методи, щоб майбутня гілка `MESSAGE` у `StepExecutor` (Task 3) могла
слати решту типів блоків:

- **`sendVideo`** → `/sendVideo` (поле `video`)
- **`sendAudio`** → `/sendAudio` (поле `audio`)
- **`sendDocument`** → `/sendDocument` (поле `document`)
- **`sendMediaGroup`** → `/sendMediaGroup` (поле `media` — JSON-масив із 2–10 елементів)

Перші три — **тонкі обгортки над наявним `send(...)`** за патерном `sendPhoto`: збирають
`contentFields` (URL/file_id + опційні `caption`/`parse_mode`) і делегують, успадковуючи весь
retry/429/audit/scrub-конвеєр безкоштовно (Decision 5, Shared resources table — нових heavy-ресурсів
не вводимо).

`sendMediaGroup` особливий: відповідь Telegram на `/sendMediaGroup` — **масив `Message`**, а не
single-`message_id`. Наявний `mapBodyToSentMessage` припускає одиничний `message_id` і впаде на
альбомній відповіді (Decision 5). Тому альбом потребує **окремого масив-маппера**, який вертає
результат із усіма message-id. Критично: error/log-шлях альбом-маппера повинен **проганяти
raw-відповідь через `TelegramApiClient.scrubTokens`** рівно як спільний шлях — паритет token-scrub,
інакше токен може просочитись у лог при битій альбомній відповіді.

## What to do

1. Додати `sendVideo(botId, chatId, videoUrl, caption, parseMode, ownerId)` — тонка обгортка: зібрати
   `contentFields` (`video`=URL/file_id; `caption`/`parse_mode` лише коли non-null, патерн `sendPhoto`)
   і викликати спільний `send(botId, chatId, "/bot{token}/sendVideo", contentFields, ownerId)`.
2. Додати `sendAudio(...)` — те саме з ендпойнтом `/bot{token}/sendAudio` і полем `audio`.
3. Додати `sendDocument(...)` — те саме з ендпойнтом `/bot{token}/sendDocument` і полем `document`.
4. Додати `sendMediaGroup(botId, chatId, items, ownerId)` (із parseMode за потреби для caption першого
   елемента): зібрати JSON-масив `media` (кожен елемент — `{type, media, caption?, parse_mode?}`;
   `caption` осмислений лише на першому елементі — Decision 5), відправити на `/bot{token}/sendMediaGroup`
   через спільний retry/429-конвеєр, але змапити відповідь **окремим масив-маппером** (не
   `mapBodyToSentMessage`). Метод має успадкувати CONNECTED-фільтр, retry/429, audit і subscriber-hook —
   використовуй наявний seam (`sendWithRateLimitRetry` + audit-обгортку), не дублюй retry-логіку.
5. Реалізувати масив-маппер альбому: розпарсити `result` (масив `Message`) у результат із усіма
   message-id; на `ok=false`/порожньому/неочікуваному форматі — кинути `TelegramSendException`,
   **попередньо прогнавши `result.description()`/raw через `TelegramApiClient.scrubTokens`** (паритет із
   `mapBodyToSentMessage`).
6. Не змінювати наявні `sendText`/`sendPhoto`/`send`/`mapBodyToSentMessage` сигнатури так, щоб ламались
   наявні тести — лише **доповнення**. Якщо для album-result потрібен новий тип/перевантаження
   `SentMessage`, обрати найменш інвазивний варіант (новий record для альбому або список `SentMessage`)
   і зафіксувати рішення в decisions.

## Details

**Files:**
- `backend/src/main/java/com/botfunnel/bot/TelegramSender.java` — наявний `@Component` singleton.
  Має приватний `send(botId, chatId, endpoint, contentFields, ownerId)` (рядки ~213–251) — спільний шлях:
  bot-lookup `botRepository.findById` + CONNECTED-фільтр, `AtomicInteger attempts`, `Instant deadline`,
  `sendWithRateLimitRetry`, `mapBodyToSentMessage`, audit `telegram_message_sent`/`telegram_send_failed`,
  `dispatchSubscriberHook`. `sendText`/`sendPhoto` делегують у нього. **Додати** чотири public-методи; для
  альбому — окремий маппер. `sendMediaGroup` не може просто викликати `send(...)`, бо `send` зашитий на
  `mapBodyToSentMessage` (single message_id) і впаде на масив-відповіді.

  **Критично (паритет seam):** `sendMediaGroup` має переюзати той самий shared retry/audit/scrub-seam, що
  й `send()` — той самий bot-lookup + CONNECTED-фільтр + retry/429-loop + 30s-deadline + audit
  (`telegram_message_sent`/`telegram_send_failed`) + Decision-4 subscriber-hook. Не винаходь паралельний
  retry/audit/hook-шлях — це порушує Shared resources інваріант. Єдина дозволена дельта проти `send()` —
  крок маппінгу: замість single-message маппера викликається альбом масив-маппер. Це гарантує, що
  `sendMediaGroup_rateLimited_retriesThenSucceeds` реально проганяє спільний retry-seam, а не hand-rolled
  retry-гілку.
- `backend/src/test/java/com/botfunnel/bot/TelegramSenderTest.java` — MockWebServer-suite. Дзеркалити
  блок `// ---------- sendPhoto (...) ----------` для нових методів. Хелпери вже є: `okSendMessage`,
  `status429`, `status5xx`, `status5xxWithToken`, `jsonResponse`, `anyMessageMatches`, `connectedBot`,
  `stubFindReturns`. Для альбому додати хелпер на масив-відповідь, напр.
  `{"ok":true,"result":[{"message_id":1,"chat":{"id":5}},{"message_id":2,"chat":{"id":5}}]}`.

**Dependencies:** немає (Wave 1, незалежна). Може йти паралельно з Task 1. Споживач — Task 3 (`StepExecutor`
гілка `MESSAGE`) залежить від цих методів, але це Wave 2.

**Edge cases:**
- Альбомна відповідь-масив порожня / `ok=false` / не масив → `TelegramSendException` після scrub.
- 429/5xx на `/sendMediaGroup` — успадкований loop (масив-маппер викликається лише на фінальній успішній
  відповіді, як `mapBodyToSentMessage`).
- `caption`/`parse_mode` null у нових обгортках → ключі відсутні в body (патерн `sendPhoto`).
- Альбом: `caption` лише на першому елементі (Decision 5); решта елементів без `caption`.
- type-mixing предикат (photo/video суміш; audio/document не змішуються) **enforce-иться на save у Task 4**,
  не тут — `sendMediaGroup` приймає вже валідні items. Можна додати дефенсивний assert, але не бізнес-логіку.

**Implementation hints:**
- Скопіюй структуру `sendPhoto` (рядки 194–207) для трьох тонких обгорток — змінюються лише ендпойнт-шлях
  і ключ контент-поля.
- Для альбому подивись `sendWithRateLimitRetry`/`sendOnce` як retry-seam і `mapBodyToSentMessage`
  (рядки 425–443) як шаблон маппера. Альбом-маппер має змапити масив-відповідь у список sent-message
  результатів, переюзавши наявну логіку екстракції полів single-message (та сама, що в
  `mapBodyToSentMessage`/`extractChatId`).
- `scrubTokens` — `TelegramApiClient.scrubTokens(...)` (static, public). Застосовуй до `result.description()`
  та будь-якого raw перед `log.warn`/exception message, точно як рядки 440–442.
- НЕ дублюй CONNECTED-фільтр/audit/hook — переюзай наявний seam.
