# Task 3: StepExecutor — гілка MESSAGE (мультиблок send + клавіатура на останньому)

## Required Skills

Перед выполнением задачи загрузи:
- `/skill:code-writing` — [skills/code-writing/SKILL.md](../../../.claude/skills/code-writing/SKILL.md)

## Description

Замінити в `StepExecutor` три плоскі гілки (`SEND_MESSAGE`, `SEND_IMAGE`, `MENU`) на одну гілку
`MESSAGE` — серце композер-кроку. Гілка ітерує `step.getBlocks()` (новий `List<ContentBlock>` з Task 1) і
шле по одному окремому Telegram-повідомленню на блок: text → `sendText`, image → `sendPhoto`,
video/audio/file → нові `sendVideo`/`sendAudio`/`sendDocument` (з Task 2), album → `sendMediaGroup`
(з Task 2). Кожен `text` і **кожен** `caption` (включно з `caption` першого елемента альбому) рендериться
через `VariableTemplateRenderer.render(..., block.parseMode(), subscriber)`, потім trim+WARN над лімітами
(4096 для text, 1024 для будь-якого media-caption) — over-length не є помилкою кроку, рівно як зараз у
`sendMessage`/`sendImage`.

До **останнього не-альбомного блоку** опційно чіпляється inline-клавіатура: якщо `step.getButtons()`
непорожній — будуємо `buildReplyMarkup(step, execution)` і передаємо його в send-виклик цього блоку, потім
повертаємо `waitForReply(deadline)` (park-on-reply, паритет MENU); якщо кнопок немає — `cont()`. Кнопки і
таймаут лишаються полями рівня кроку (`FunnelStep`), не блоку (Decision 2) — `buildReplyMarkup`,
`menuDeadline`, callback-контракт `{executionId}:{buttonIndex}` зберігаються без змін.

Усі N send-ів виконуються в межах однієї гілки під одним claim — per-node at-most-once (Decision 3): крах
посеред блоків лишає крок `in_progress` без повтору; вже надіслані блоки lost-forward. Семантика помилки
зберігається з наявних гілок: `TelegramSendException` → `fromTerminalReason` (BLOCKED_BY_USER/CHAT_NOT_FOUND
→ `cancel`, інакше `fail`), `BotTokenInvalidException` → `fail("invalid_bot_token")`,
`AppException` → `fail(codeOrStatus(ex))`. При помилці send-у блоку K крок НЕ просувається.

## What to do

- У `switch` методу `execute(...)` прибрати гілки `case SEND_MESSAGE`, `case SEND_IMAGE`, `case MENU`;
  додати `case MESSAGE -> message(step, execution, subscriber, bot)`. Switch має лишитись exhaustive над
  оновленим `StepType` (з Task 1: `MESSAGE, DELAY, ADD_TAG, REMOVE_TAG, SET_CUSTOM_FIELD, EMIT_EVENT,
  SUBSCRIBE_TO_FUNNEL`) — без `default`.
- Видалити приватні методи `sendMessage(...)`, `sendImage(...)`, `menu(...)`, які більше не викликаються.
- Реалізувати приватний метод `message(FunnelStep, FunnelExecution, Subscriber, Bot)`:
  - Визначити індекс останнього не-альбомного блоку (для чіпляння клавіатури).
  - Ітерувати `step.getBlocks()` по порядку. Для кожного блоку — диспатч за `block.type()` на відповідний
    send-метод; рендер text/caption через `VariableTemplateRenderer`; trim+WARN над лімітом для відповідного
    типу контенту.
  - Для останнього не-альбомного блоку: якщо `step.getButtons()` непорожній — передати
    `buildReplyMarkup(step, execution)` у send-виклик і після успіху повернути `waitForReply(menuDeadline(step))`;
    інакше — продовжити цикл і в кінці повернути `cont()`.
  - Альбом: зібрати `List<MediaItem>` з відрендереними caption (caption осмислений лише на першому елементі —
    рендериться лише для нього), викликати `sender.sendMediaGroup(...)`. Альбом ніколи не несе клавіатуру
    (Decision 2 — кнопки лише на останньому **не-альбомному** блоці; валідація на save в Task 4 це enforce-ить).
  - Обгорнути весь цикл send-ів у єдиний try/catch з трьома catch-arm-ами (порядок і мапінг — точно як у
    наявних `sendMessage`/`sendImage`/`menu`): `TelegramSendException` → `fromTerminalReason(ex)`,
    `BotTokenInvalidException` → `fail("invalid_bot_token")`, `AppException` → `fail(codeOrStatus(ex))`.
- Зберегти WARN-логування кодами-only (Decision 16 / PII): `LOG_TEXT_TRIMMED` для text-блоку,
  `LOG_CAPTION_TRIMMED` для будь-якого media-caption (включно з album-caption). Жодного рендереного payload
  у логах.
- Зберегти `buildReplyMarkup`, `menuDeadline`, `durationOf`, `fromTerminalReason`, `codeOrStatus` без змін
  (вони переюзаються; лише `menu(...)` як окремий entry-point видаляється).
- Переписати тести `FunnelStepExecutorTest` зі старих типів на композер (див. TDD Anchor) — не «дописати MESSAGE-кейси»,
  а **повністю переписати** всі старотипні артефакти, які перестануть компілюватись після видалення сетерів у Task 1:
  - Хелпери `sendMessageStep(String,String)` (рядки 447–453), `sendImageStep(String,String,String)` (455–462),
    `menuStep(String,List<Button>,Integer,String)` (479–487) викликають видалені сетери
    `setStepType(SEND_MESSAGE/SEND_IMAGE/MENU)`/`setText`/`setImageUrl`/`setCaption` → видалити їх і замінити на
    `messageStep(...)`-білдери, що приймають `List<ContentBlock>` (text/image/album/...) + опційні `buttons`/timeout.
  - Усі ~6 тест-методів, що викликають ці хелпери, переписати на блок-білдери: `sendMessageOver4096TrimsAndContinues`
    (95), `sendImageCaptionEscapedAndTrimmedTo1024` (112), `menu_sends_text_with_reply_markup` (247),
    `menu_with_timeout_returns_deadline` (264), `menu_callbackButtons_encodeCorrectCallbackData` (286),
    `sendMessageBlockedByUserCancels` (320), `sendMessageOtherTerminalFails` (333),
    `sendMessageInvalidBotTokenFails` — перевести на гілку `MESSAGE` (одно-/мультиблочні кроки) зі збереженням наміру
    кожного кейсу (trim, escape, menu→keyboard, callback-encoding, cancel/fail).
  - Кейси не-MESSAGE гілок (delay/tag/customField/emit/subscribe) і їхні хелпери (`delayStep`, `tagStep`,
    `setCustomFieldStep`, `emitEventStep`, `subscribeStep`) — лишити без змін.
- Переписати engine/executor-IT `FunnelExecutionEngineIT` зі старих типів на композер — **це власність цього таска**
  (поведінка двигуна навколо гілки `MESSAGE`):
  - Видалити/переписати старотипні seed-хелпери, що викликають видалені сетери: `sendMessage(String)` (1255–1260),
    `sendImage(String)` (1262–1267), граф-білдер `sendMessageStep(String id,String text,String next)` (1279–1286),
    `menu(String id,...,Button...)` (1297–1308) — замінити на композер-білдери (`messageStep(id, blocks, next)` /
    `messageStep` з кнопками). Граф-форма (`setId`/`setNext`/`setCurrentStepId`) зберігається.
  - Переписати наявні engine-ITи, посіяні через ці хелпери, на композер-кроки: per-node **at-most-once** (крах
    посеред блоків мультиблочного MESSAGE → без повторної доставки після re-claim: `verify(sender, times(K))` по
    надісланих блоках), **snapshot-isolation** (виконання працює на знятому `List<ContentBlock>`, зміни визначення
    funnel після старту не впливають), **buttons-on-last-block park + resumeOnCallback** (ITи `resumeOnCallback_*`
    на рядках 483/502/522/575/613/671/695/725 — кнопки тепер чіпляються до останнього не-альбомного блоку MESSAGE,
    park і просування по callback `{executionId}:{buttonIndex}` зберігаються).
  - **Межа власності:** callback-negative ITи (foreign-subscriber reject, double-click idempotency, протермінований
    callback тощо) у `FunnelTriggerServiceIT` — власність **Task 5**, тут їх НЕ чіпати. Якщо аналогічні negative-кейси
    дублюються в `FunnelExecutionEngineIT` як engine-рівень (напр. `resumeOnCallback_rejects_foreign_subscriber`,
    `resumeOnCallback_double_click_advances_once`) — їх ре-сід на композер лишається в цьому таску (вони перевіряють
    поведінку двигуна, не trigger-сервісу).

## TDD Anchor

Тести, які потрібно написати/переписати ДО реалізації (у `FunnelStepExecutorTest`). Пишемо → запускаємо →
переконуємось що падають → пишемо код → переконуємось що проходять. Усі колаборатори мокаються; рендерер
використовується по-справжньому (static util).

- `FunnelStepExecutorTest::message_sendsBlocksInOrder` — крок з [text, image, file] шле рівно три повідомлення
  у порядку блоків (`InOrder` verify по `sender`), результат `CONTINUE`.
- `FunnelStepExecutorTest::message_substitutesVariablesInTextAndAllCaptions` — `{user.first_name}` підставляється
  й екранується за parseMode у text-блоці І в caption кожного media-типу (image/video/audio/file) — кожен
  caption capture-иться й перевіряється.
- `FunnelStepExecutorTest::message_trimsTextOver4096AndWarns` — text-блок >4096 trim-иться до
  `MAX_MESSAGE_LENGTH`, логнуто `LOG_TEXT_TRIMMED`, крок не падає (CONTINUE); у WARN немає payload.
- `FunnelStepExecutorTest::message_trimsCaptionOver1024PerType` — caption кожного media-типу >1024 trim-иться
  до `MAX_CAPTION_LENGTH`, логнуто `LOG_CAPTION_TRIMMED`.
- `FunnelStepExecutorTest::message_albumCaptionOnlyOnFirstItem` — album-блок шлеться через `sendMediaGroup`;
  рендериться/передається caption лише першого `MediaItem`, решта без caption; caption першого підставляє змінні.
- `FunnelStepExecutorTest::message_keyboardOnlyOnLastNonAlbumBlock_waitForReply` — крок [text, album, text] з
  непорожніми `buttons`: клавіатура (`reply_markup`) чіпляється лише до send-у останнього text-блоку, не до
  album/першого text; результат `WAIT_FOR_REPLY` з deadline = now + timeout.
- `FunnelStepExecutorTest::message_noButtons_returnsContinue` — крок без `buttons` → жоден send не несе
  reply_markup, результат `CONTINUE`.
- `FunnelStepExecutorTest::message_lastBlockIsAlbum_keyboardNotAttached` — крок [text, album] з непорожніми
  `buttons`. Перевірити обидва боки:
  - негатив: album-send (`sendMediaGroup`) НЕ отримує reply_markup (альбом ніколи не несе клавіатуру);
  - **позитив**: попередній останній **не-альбомний** text-блок ОТРИМУЄ клавіатуру — capture-нутий аргумент
    reply_markup у його send-виклику дорівнює `buildReplyMarkup(step, execution)` (не null), і гілка повертає
    `WAIT_FOR_REPLY` з deadline = now + timeout (park на цьому text-блоці, а не на альбомі).
  Сам кейс «buttons + останній блок альбомний» відхиляється на save (Task 4) — тут лише фіксуємо поведінку
  виконавця: клавіатура й park прив'язані до останнього не-альбомного блоку.
- `FunnelStepExecutorTest::message_blockKThrowsTelegramSend_returnsCancelOrFail_stepNotAdvanced` — send блоку K
  кидає `TelegramSendException(BLOCKED_BY_USER)` → `CANCEL` з reasonCode; інший terminal reason → `FAIL`; блоки
  1..K-1 вже надіслані (`verify(sender, times(K-1))` на попередніх send-методах), крок не просунутий
  (результат не `CONTINUE`/`WAIT_FOR_REPLY`).
- `FunnelStepExecutorTest::message_invalidBotToken_fails` — `BotTokenInvalidException` посеред блоків → `FAIL`
  з reasonCode `invalid_bot_token`.
- `FunnelStepExecutorTest::message_appException_fails` — `AppException` (напр. 404 bot-not-found) → `FAIL` з
  `codeOrStatus`.

## Acceptance Criteria

- [ ] `execute(...)` switch містить `case MESSAGE`, не містить `SEND_MESSAGE`/`SEND_IMAGE`/`MENU`, лишається
      exhaustive без `default` і компілюється над оновленим `StepType`.
- [ ] Гілка `MESSAGE` шле блоки послідовно по одному повідомленню на блок у порядку `step.getBlocks()`.
- [ ] Усі text та всі caption (включно з caption першого елемента альбому) проходять через
      `VariableTemplateRenderer` з parseMode блоку.
- [ ] Over-length text trim-иться до 4096, будь-який media-caption — до 1024, з WARN кодами-only; over-length
      не є помилкою кроку.
- [ ] Альбом шлеться через `sendMediaGroup`; caption передається лише на першому елементі.
- [ ] Клавіатура чіпляється лише до останнього не-альбомного блоку; з кнопками → `waitForReply(deadline)`,
      без кнопок → `cont()`.
- [ ] Усі send-и під одним claim (per-node at-most-once): крах посеред блоків повертає `cancel`/`fail` за
      `fromTerminalReason`, крок НЕ просувається.
- [ ] Catch-arms збережено: `BotTokenInvalidException` → `fail("invalid_bot_token")`,
      `AppException` → `fail(codeOrStatus(ex))`, `TelegramSendException` → `fromTerminalReason`.
- [ ] `FunnelStepExecutorTest` переписано на композер (всі старотипні хелпери `sendMessageStep`/`sendImageStep`/`menuStep`
      і ~6 кейсів, що їх викликають) — усі тести зелені, немає посилань на видалені типи/поля.
- [ ] `FunnelExecutionEngineIT` переписано на композер (seed-хелпери + engine-ITи навколо MESSAGE): at-most-once
      crash/re-claim (`verify(sender, times(K))`), snapshot-isolation на `List<ContentBlock>`, buttons-on-last-block
      park + `resumeOnCallback` — усі зелені. Callback-negative ITи в `FunnelTriggerServiceIT` (Task 5) не зачеплені.

**Edge cases:**
- Останній блок — альбом: клавіатура НЕ чіпляється (Decision 2). Якщо `buttons` непорожній, а останній блок
  альбомний — це невалідний крок на save (Task 4 відхиляє 422); у виконавці просто не чіпляємо клавіатуру до
  альбому. Поведінку «кнопки + останній альбом» у виконавці не вигадувати — лишити park/cont логіку прив'язаною
  до останнього **не-альбомного** блоку.
- Крок із єдиним блоком + кнопками: цей блок одночасно перший і останній не-альбомний → клавіатура на ньому.
- Порожній/відсутній caption у media-блоці: `sendPhoto`/`sendVideo`/... приймають `null` caption (only-if-non-null
  body) — не рендерити й не trim-ити `null`.
- Album caption: рендерити лише `items.get(0).caption()`; решта елементів — caption як є (зазвичай null) без
  рендеру (валідація save гарантує, що caption лише на першому).
- Крах посеред блоків: блоки 1..K-1 вже доставлені (lost-forward, без повтору) — це свідома per-node
  at-most-once семантика (Decision 3), НЕ баг.
- `parseMode` береться з кожного блоку окремо (`block.parseMode()`), не з кроку — на відміну від старого
  `step.getParseMode()`.

**Implementation hints (НЕ псевдокод):**
- Індекс останнього не-альбомного блоку обчислити один раз перед циклом (зворотний прохід по `blocks`), щоб у
  циклі вирішувати, чи цей блок несе клавіатуру.
- Trim+WARN винести в маленький приватний хелпер на два ліміти (text 4096 / caption 1024), щоб не дублювати
  6 разів; WARN-логування лишити кодами-only з `execution.getId()`/`currentStepIndex` як зараз.
- Диспатч за `block.type()` зробити локальним switch у методі `message(...)` (per-block), exhaustive над
  `BlockType` (TEXT/IMAGE/VIDEO/AUDIO/FILE/ALBUM).
- Один зовнішній try/catch навколо всього циклу — НЕ per-block try/catch (інакше зламається at-most-once
  семантика й lost-forward поведінка). Catch-arms у тому ж порядку, що в наявних гілках.
- `waitForReply`/`cont` повертати лише ПІСЛЯ успішного завершення циклу (повернення з try); при будь-якому
  throw управління йде в catch і повертається cancel/fail.
- Anti-SSRF (Decision 6): media `mediaUrl` передається в sender як є — бекенд НЕ дереференсить URL (Telegram
  фетчить сам); НЕ додавати жодного HTTP-виклику по URL у виконавці.
