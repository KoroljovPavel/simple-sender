# Task 4: FunnelService — validateSteps композер + DTO-ланцюг + preview мультиблок

## Required Skills

Перед виконанням задачі завантаж:
- `/skill:code-writing` — [skills/code-writing/SKILL.md](../../../.claude/skills/code-writing/SKILL.md)

## Description

Це Wave-2 backend-таск, що замикає бекенд-контракт композер-кроку всередині `FunnelService.java` та
суміжних funnel-DTO. Він спирається на модель із Task 1 (`ContentBlock`/`MediaItem` records, `BlockType`
enum, `StepType.MESSAGE`, `FunnelStep.blocks` замість плоских msg-полів).

Робимо три зчеплені речі (всі живуть у `FunnelService.java`, тому об'єднані в один таск, щоб уникнути
wave-конфлікту):

1. **`validateSteps` — case `MESSAGE`:** жорстка save/activate валідація `List<ContentBlock>` з інлайн
   422-бізнес-кодами (кількість блоків 1–10; per-type обов'язкові поля; альбом 2–10 елементів +
   type-mixing предикат із Decision 5; кнопки лише на останньому не-альбомному блоці; строгий
   `http(s)`-scheme для медіа-URL з disambiguation `file_id` vs URL із Decision 6; over-length text/caption
   — як warning, не блокує save). Видалити старі cases `SEND_MESSAGE`/`SEND_IMAGE`/`MENU` та їхні
   тепер-непотрібні приватні хелпери.

2. **DTO-ланцюг:** провести `List<ContentBlock>` через `FunnelStepDto`, `toSteps`/`toStepDto`,
   `FunnelResponse`, `FunnelSummaryResponse` — без мовчазного дропу жодного поля блоку. Ймовірно потрібен
   net-new DTO `ContentBlockDto` (+ `MediaItemDto`), що дзеркалить backend `ContentBlock`/`MediaItem`.

3. **Preview мультиблок:** розширити `previewStep` + preview DTOs на масив блоків. `isMessageStep` →
   `MESSAGE`; рендер кожного text/caption через `VariableTemplateRenderer` (backend-side parseMode-екранування
   зберігається, Decision 8); БЕЗ серверного дереференсу медіа-URL (Decision 6 — anti-SSRF). Response —
   масив відрендерених блоків (`PreviewStepResponse(renderedBlocks[], sampleData, kind)`).

Інваріанти, що мають вижити: anti-IDOR uniform-404 порядок гардів (requireFunnel FIRST), anti-enumeration,
backend-side екранування (XSS-guard, OWASP A03), і «бекенд ніколи не тягне медіа-URL».

## What to do

1. **DTO-контракт під блоки:**
   - Ввести net-new `ContentBlockDto` (дзеркало `ContentBlock`: `type`, `text`, `parseMode`, `mediaUrl`,
     `caption`, `List<MediaItemDto> items`) та `MediaItemDto` (`mediaUrl`, `caption`). Обидва з
     `@JsonIgnoreProperties(ignoreUnknown = true)` (mass-assignment defense, як решта funnel-DTO).
   - У `FunnelStepDto` видалити плоскі msg-поля (`text`, `parseMode`, `imageUrl`, `caption`), додати
     `List<ContentBlockDto> blocks`. `buttons` + `timeout*` лишаються.
   - У `FunnelResponse` провести `blocks` (через `FunnelStepDto`). У `FunnelSummaryResponse` — без блоків
     (summary згорнутий), але прибрати будь-які посилання на видалені плоскі поля; оновити Javadoc.

2. **`toSteps` / `toStepDto`:**
   - `toSteps`: мапити `dto.blocks()` → `List<ContentBlock>` (+ елементи альбому → `List<MediaItem>`),
     не дропаючи полів; зняти `setText/setParseMode/setImageUrl/setCaption`.
   - `toStepDto` (~954–975): мапити `step.getBlocks()` → `List<ContentBlockDto>` (зворотний бік round-trip).
     ВАЖЛИВО: цей метод викликає конструктор record-а `FunnelStepDto` з ~20 позиційними аргументами, серед
     яких чотири плоскі поля `text`/`parseMode`/`imageUrl`/`caption` (рядки ~963–966). Record вимагає
     атомарної заміни — усі чотири плоскі аргументи мають бути прибрані й замінені на один `blocks`-аргумент
     у ТОМУ Ж едіті, інакше арність конструктора не зійдеться й код не скомпілюється. Узгодити порядок/
     арність з оновленим `FunnelStepDto`.
   - Зберегти захист від null-блоків (порожній список, не NPE).

3. **`validateSteps` — case `MESSAGE`:**
   - Видалити cases `SEND_MESSAGE`, `SEND_IMAGE`, `MENU`; видалити тепер-мертві хелпери (`requireText`,
     `requireImageUrl`, частину `validateMenu` у старому вигляді — button-логіку переюзати, див. нижче).
   - Реалізувати `validateMessage(step, stepIds)`:
     - `blocks` непорожній і розмір 1–10 → інакше 422.
     - per-type валідація блоку за `BlockType`:
       - `TEXT`: непорожній `text`; `parseMode` ∈ {null, HTML, MarkdownV2}; над-лімітний `text` (>4096)
         НЕ блокує (warning).
       - `IMAGE/VIDEO/AUDIO/FILE`: `mediaUrl` обов'язковий; валідувати строго (http(s) URL АБО непрозорий
         `file_id`-токен — disambiguation: якщо значення схоже на URL за наявністю scheme-розділювача —
         вимагати строгий http(s); інакше приймати як `file_id`); `caption` опційний, над-лімітний (>1024)
         НЕ блокує (warning); `parseMode` ∈ {null, HTML, MarkdownV2}.
       - `ALBUM`: `items` розмір 2–10; кожен `mediaUrl` валідується тим самим media-URL/file_id-правилом;
         `caption` осмислений лише на ПЕРШОМУ елементі (Decision 5); type-mixing предикат: усі photo / усі
         video / суміш photo+video; audio/document НЕ змішуються з іншими типами в одній групі → 422.
     - кнопки (`step.getButtons()`) дозволені лише на ОСТАННЬОМУ не-альбомному блоці; кнопки на альбомі
       або не на останньому блоці → 422. Переюзати наявну button-валідацію (label/limit/callback-target/
       url http(s), `requireTimeout` для park-on-reply) — вона лишається.
   - Edge-pass (`requireExistingTarget` для `next`/`timeoutTargetStepId`) лишається без змін для всіх типів.
   - Кожна жорстка помилка повертає 422 з машинно-читаним інлайн-кодом (нові `CODE_*` константи або
     переюзаний `CODE_INVALID_STEP` з конкретним message — узгоджено зі стилем файлу).

4. **Media-URL strict-scheme хелпер (ОБОВ'ЯЗКОВО витягнути generic-валідатор, не переюзати as-is):**
   - КРИТИЧНО: наявний `requireHttpUrl` (`FunnelService.java` ~815–836) і `requireTimeout` хардкодять
     user-facing рядки `"MENU url button ..."` / `"MENU timeout requires ..."` у своїх error-меседжах.
     Переюзати їх as-is для валідації медіа-URL/timeout композера дасть оманливі помилки («MENU url button»
     для блоку медіа). НЕ робити тихого переюзу.
   - Витягнути generic-валідатор схеми/URL (або параметризувати field-label у `requireHttpUrl`), щоб
     error-меседж посилався на конкретне поле блоку/медіа (напр. `"<BlockType> media url ..."`), а не на
     «MENU url button». Логіка строгого парсингу зберігається: trim-guard, `new URI(...)`, scheme EXACTLY
     http/https, non-empty host, malformed → 422 не 500.
   - Застосувати до медіа-URL з гілкою «це file_id → пропустити» (Decision 6). НЕ копіювати слабкий
     `startsWith("http://")` із `requireImageUrl`.

5. **`previewStep` + preview DTOs:**
   - `PreviewStepRequest`: `(String stepType, List<ContentBlockDto> blocks)` (замість `text`/`parseMode`).
   - `PreviewStepResponse`: `(List<RenderedBlock> renderedBlocks, boolean sampleData, String kind)` —
     `renderedBlocks` несе відрендерений text/caption + тип блоку + (нерозіменований) mediaUrl/items;
     точну форму `RenderedBlock` визначити під Data Models (фронт рендерить text-only через `{{ }}`, медіа
     через `:src`).
   - `isMessageStep` → `type == StepType.MESSAGE`.
   - `previewStep`: message-крок → рендерить кожен блок (text+caption) через `VariableTemplateRenderer`
     (backend-екранування зберігається), медіа-URL/items проводить як є БЕЗ фетчу, повертає
     `renderedBlocks` + `kind="message"`. Non-message → `renderedBlocks=[]`, `kind="non_message"`.
     Зберегти requireFunnel-FIRST та stub-subscriber fallback.

6. Переконатися, що exhaustive-switch у `validateSteps` компілюється без видалених enum-значень (Task 1
   вже зняв їх зі `StepType`).

**Поточний стан (з прочитаного коду):**

- `requireHttpUrl` (~815–836) — строгий http(s)-парсер (trim-guard + URI + scheme EXACTLY + non-empty
  host + malformed→422), АЛЕ всі його error-меседжі хардкодять `"MENU url button ..."`. `requireTimeout`
  аналогічно хардкодить `"MENU timeout requires ..."`. Витягнути generic-валідатор (або параметризувати
  field-label), щоб для медіа-URL/timeout композера помилка посилалася на блок/медіа-поле, не на «MENU url

- `requireImageUrl` (~854) використовує слабкий `startsWith("http://")` — НЕ копіювати цей патерн; для
  медіа використовувати строгий URI-підхід (Decision 6 явно вимагає строгий scheme).
- `toSteps` (~591–634) / `toStepDto` (~954–976) виставляють плоскі msg-поля — замінити на `blocks`.
- `previewStep` (~379–400) + `isMessageStep` (~402–404) прибиті до одного рядка `request.text()` — розширити
  на масив. `PreviewStepResponse` зараз `(rendered, sampleData, kind)`; `PreviewStepRequest` зараз
  `(stepType, text, parseMode)`.

**Dependencies:**
- Task 1 (Wave 1): `ContentBlock`/`MediaItem` records, `BlockType` enum, `StepType.MESSAGE`,

**Edge cases:**
- `blocks == null` / `items == null` — трактувати як порожній → відповідний 422 (не NPE).
- альбом: `caption` лише на першому елементі (Decision 5) — наступні з caption обробити консистентно (422
  або тихий дроп — звірити з формулюванням Decision 5).
- type-mixing: photo+video дозволено; будь-яке змішування audio/document з іншим типом → 422.
- медіа-джерело: відрізнити URL від `file_id`. URL зі схемою → строгий http(s); інакше — непрозорий file_id.
  `file://`/`data:`/`javascript:`/whitespace-обфускований/empty-host → 422.
- over-length (text >4096, caption >1024) — warning, НЕ 422.
- preview: backend ніколи не фетчить медіа-URL (anti-SSRF). requireFunnel FIRST зберегти.
- preview non-message step → `renderedBlocks=[]`, `kind="non_message"`.

**Implementation hints:**
- Дзеркало DTO ↔ domain: тримати `ContentBlockDto`/`MediaItemDto` плоскими, з `@JsonIgnoreProperties(ignoreUnknown=true)`
  (як `ButtonDto`/`FunnelStepDto` — mass-assignment defense).
- 422-коди: дотримуватися наявного стилю (`CODE_*` константи + `AppException.unprocessableEntity(code, msg)`).

- over-length warning: позначити (напр. поле/прапор у відповіді або лог), але НЕ кидати — підтвердити

  + лог і покрити тестом «save проходить».
