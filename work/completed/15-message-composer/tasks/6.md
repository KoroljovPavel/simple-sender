# Task 6: Frontend types — StepType + ContentBlock + preview DTOs

## Required Skills

Перед выполнением задачи загрузи:

## Description

Фронтенд-типи у `frontend/types/funnel.ts` мають дзеркалити нову бекенд-модель композера, яку
вводять таски 1 і 4: один крок `StepType.MESSAGE` тримає впорядкований список `ContentBlock`, плоскі
msg-типи (`SEND_MESSAGE`/`SEND_IMAGE`/`MENU`) видалені, а `/preview`-контракт розширено на мультиблок.

Це pure-types таск: він не пише runtime-логіку, лише оновлює TypeScript-інтерфейси/юніони. Його
споживають Wave-4 таски: Task 7 (`FunnelStepForm.vue` — саб-редактор композера) і Task 8
(`FunnelMessagePreview.vue` + `stores/funnels.ts` preview-екшен). Тому контракт типів має точно
збігатися з бекенд-DTO (`ContentBlock`/`MediaItem`/`BlockType`, `PreviewStepRequest`/
`PreviewStepResponse`) з tech-spec "Data Models" — будь-яке розходження зламає компіляцію в тасках 7/8
або тихо пропустить поле в save/preview-пейлоаді.

`depends_on: [4]`, бо Task 4 фіксує фінальну форму бекенд preview-DTO (`PreviewStepRequest(stepType,
blocks)`, `PreviewStepResponse(renderedBlocks[], sampleData, kind)`) і `FunnelStepDto.blocks`, які тут
дзеркаляться.

## What to do

1. **`StepType`** — видалити члени `'SEND_MESSAGE'`, `'SEND_IMAGE'`, `'MENU'`; додати `'MESSAGE'`.
   Решта (`DELAY`, `ADD_TAG`, `REMOVE_TAG`, `SET_CUSTOM_FIELD`, `EMIT_EVENT`, `SUBSCRIBE_TO_FUNNEL`)
   — без змін. Оновити коментар, щоб не посилався на видалені типи.

2. **`BlockType`** — net-new юніон, дзеркало бекенд-enum: `'TEXT' | 'IMAGE' | 'VIDEO' | 'AUDIO' |
   'FILE' | 'ALBUM'`.

3. **`MediaItem`** — net-new інтерфейс (дзеркало бекенд `record MediaItem(String mediaUrl, String
   caption)`): `mediaUrl: string`, `caption?: string | null` (осмислений лише на першому елементі
   альбому).

4. **`ContentBlock`** — net-new інтерфейс (дзеркало бекенд immutable record). Поля: `type: BlockType`
   (дискримінатор) + nullable per-type поля: `text` (TEXT), `parseMode` (TEXT/media caption),
   `mediaUrl` (IMAGE/VIDEO/AUDIO/FILE), `caption` (IMAGE/VIDEO/AUDIO/FILE), `items` (ALBUM,
   `MediaItem[]`). Per-type поля — optional/nullable, бо заповнюються лише для свого `type` (як у
   бекенд-record nullable per-type полях).

5. **`FunnelStep`** — видалити плоскі msg-поля `text`, `parseMode`, `imageUrl`, `caption`; додати
   `blocks?: ContentBlock[] | null` (заповнюється лише для `stepType: 'MESSAGE'`). `buttons`,
   `timeoutValue/Unit/TargetStepId`, `id`, `next`, `order`-семантика та інші step-поля — БЕЗ змін
   (Decision 2: кнопки/таймаут лишаються полями кроку, не блоку). Оновити коментар біля `buttons`,
   щоб згадував композер-крок (`MESSAGE`), а не `MENU`.

6. **`PreviewStepRequest`** — замінити `text: string` (single-block) на `blocks: ContentBlock[]`
   (мультиблок). Лишити `stepType: StepType`. `parseMode` тепер живе per-block у `ContentBlock`, тож
   прибрати top-level `parseMode` з request. Дзеркало бекенд `PreviewStepRequest(stepType, blocks)`.

7. **`PreviewStepResponse`** — замінити `rendered: string` на `renderedBlocks: string[]` (масив
   відрендерених блоків у порядку). Зберегти `sampleData: boolean`. `kind: 'message' | 'non_message'`
   — без змін. Звірити фінальну форму з бекенд `PreviewStepResponse(renderedBlocks[], sampleData,
   kind)` з tech-spec Task 4 (точні імена полів — як у бекенд-DTO; якщо Task-4 DTO відрізняється від
   tech-spec-тексту, бекенд є джерелом істини).

8. Решта типів (`FunnelStatus`, `Button`, `DelayUnit`, `CURRENT_DATE_TOKEN`, `FunnelSummaryResponse`,
   `FunnelResponse`, `Create/UpdateFunnelRequest`, `StopAllResponse`) — НЕ чіпати, окрім випадків, де
   коментар прямо посилається на видалені плоскі поля.

## TDD Anchor

Це pure-type файл — у нього немає runtime-логіки (немає функцій типу `toListQuery` із
`types/subscriber.ts`), тож прямих behavioral-тестів він не отримує. Верифікація — `npx nuxi
typecheck` (компіляція) + downstream component/store тести тасків 7/8, що споживають ці типи.

Опційно можна додати compile-only assignability fixture у `tests/types/funnel-blocks.spec.ts`, що
конструює зразкові `ContentBlock` усіх 6 `BlockType`, `MediaItem`-альбом, `PreviewStepRequest` із
`blocks` і `PreviewStepResponse` із `renderedBlocks`, та банальний `expect(...).toBeTruthy()` — щоб
TypeScript у CI ловив дрейф форми. Тіло тесту тривіальне; цінність — у тому, що файл не скомпілюється
при розходженні з DTO. Зверни увагу: `tests/types/subscriber-filters.spec.ts` — НЕ прецедент для
цього патерну; той файл тестує runtime-функції (assignability через виклики), а не чисту type-
сумісність. Тут потрібен мінімальний vitest type-assignability fixture — інший, простіший патерн
(самі присвоєння типів + тривіальний `expect`).

- `tests/types/funnel-blocks.spec.ts` — (опційно) compile-time fixture: зразки `ContentBlock` для
  кожного `BlockType`, `MediaItem`-альбом, `PreviewStepRequest{stepType:'MESSAGE', blocks:[...]}`,
  `PreviewStepResponse{renderedBlocks:[...], sampleData:false, kind:'message'}` присвоюються без
  TS-помилок.

## Details

**Files:**
- `frontend/types/funnel.ts` — єдиний файл, що модифікується. Поточний стан:
  - `StepType` (рядки ~10-20) містить `'SEND_MESSAGE'`, `'SEND_IMAGE'`, `'MENU'` — видалити; додати
    `'MESSAGE'`.
  - `FunnelStep` (рядки ~51-81) має плоскі `text`/`parseMode`/`imageUrl`/`caption` — видалити; додати
    `blocks`. `buttons`/`timeout*` уже є (коментар біля них каже "apply to MENU steps only" — оновити
    на композер `MESSAGE`).
  - `PreviewStepRequest` (рядки ~142-146) — `{ stepType, text, parseMode? }`; переробити на
    `{ stepType, blocks }`.
  - `PreviewStepResponse` (рядки ~152-156) — `{ rendered, sampleData, kind }`; `rendered` →
    `renderedBlocks: string[]`.
  - `BlockType`/`MediaItem`/`ContentBlock` — не існують, додати (логічно поряд із `FunnelStep`/перед
    ним, або у блоці msg-типів).
  - НЕ зачіпати структуру `FunnelResponse.steps: FunnelStep[]` / `UpdateFunnelRequest.steps` — вони
    транзитивно отримають `blocks` через оновлений `FunnelStep`.

**Dependencies:** Task 4 (бекенд preview-DTO + `FunnelStepDto.blocks` фінальна форма). Споживачі —
Task 7 та Task 8 (Wave 4). Нових пакетів не треба.

**Test ownership (не скоуп цього таска):** наявні тести `frontend/tests/stores/funnels.spec.ts` та
`frontend/tests/components/funnels/FunnelMessagePreview.spec.ts` побудовані на СТАРИХ формах
`PreviewStepRequest{stepType, text, parseMode}` / `PreviewStepResponse{rendered}`. Зміна цих типів
тут зробить ті тести нескомпільованими/червоними — але переписувати їх НЕ твоя відповідальність: це
скоуп **Task 8**, який міняє store-екшен (`stores/funnels.ts` preview) і компонент
(`FunnelMessagePreview.vue`) і разом із ними оновлює їхні тести. Цей таск — pure-types: він лише
змінює декларації типів; downstream-тести оновлюють таски 7/8. Не чіпай `funnels.spec.ts` /
`FunnelMessagePreview.spec.ts`; якщо `typecheck`/тести червоніють лише там — зафіксуй як known-handoff
для Task 8 (див. Edge cases) і не торкайся їх.

**Edge cases:**
- `stores/funnels.ts` `preview(funnelId, stepId, payload: PreviewStepRequest)` передає `payload`
  verbatim у тіло і повертає `PreviewStepResponse` verbatim — він не читає поля, лише прокидає. Тож
  зміна форми `PreviewStepRequest`/`PreviewStepResponse` сама по собі НЕ ламає store-екшен на рівні
  компіляції (generics-прохід). Реальні call-sites (`FunnelMessagePreview.vue`, Task 8) збирають
  новий request-shape — це скоуп Task 8, не цього таска. Якщо `npx nuxi typecheck` поскаржиться на
  існуючий call-site зі старим shape, що споживає `.rendered` — НЕ переписуй чужу логіку; зафіксуй у
  decisions як known-handoff для Task 8 і впевнись, що поломка лише у Wave-4 компонентах, а не у
  `types/funnel.ts`.
- `ContentBlock` per-type поля nullable, бо один інтерфейс покриває 6 типів (flat-record дзеркало,
  Decision 1) — не роби discriminated union із `type`-narrowing, якщо бекенд-DTO цього не вимагає;
  тримай flat-shape паритет із бекендом, щоб save round-trip не дропав полів.
- `parseMode` мігрує з top-level (FunnelStep/PreviewStepRequest) на per-block (`ContentBlock`) —
  переконайся, що ніде не лишився "осиротілий" top-level `parseMode`, що посилається на видалену
  семантику.

**Implementation hints:**
- Дзеркаль точні назви полів бекенд Data Models: `ContentBlock(type, text, parseMode, mediaUrl,
  caption, items)`, `MediaItem(mediaUrl, caption)`. Не вигадуй camelCase-варіантів, що розходяться з
  серіалізацією (бекенд `record` → JSON ключі = імена компонентів).
- Звір `PreviewStepResponse` поле `renderedBlocks` із фактичним бекенд-DTO з Task 4 (прочитай
  `backend/.../dto/PreviewStepResponse.java` після Task 4, якщо доступний) — tech-spec називає його
  `renderedBlocks[]`, але бекенд-DTO є джерелом істини при розбіжності.
- Зберігай наявний стиль файлу: розгорнуті doc-коментарі над кожним типом, що пояснюють mirror-контракт
  і причину optional-полів (як у поточному `funnel.ts`).
