## Description

Холистический аудит качества кода всей фичи 15-message-composer после завершения всех восьми
реализационных тасков (Wave 1–4). Цель — поймать кросс-компонентные проблемы, которые невидимы при
ревью отдельного таска: дублирование инициализации ресурсов, нарушение договорённостей о shared
resources из секции Architecture, архитектурную несогласованность между бекендом и фронтендом и —
самое важное для этой фичи — **полноту удаления старых типов шагов** (`SEND_MESSAGE`, `SEND_IMAGE`,
`MENU`) из всех мест кодовой базы.

Это таск Audit Wave: аудитор сам является ревью, отдельных ревьюеров нет. Никакого нового кода не
пишется — таск только читает исходники и пишет audit-report. Output — JSON/markdown отчёт в
`work/15-message-composer/logs/working/task-9/` с находками, классифицированными по severity
(critical / major / minor) согласно методологии code-reviewing (11 review dimensions).

## Details

<!-- All details for task execution — technical, organizational, any other. -->

**Природа таска:** read-only холистический аудит. Кода не пишем, тесты не запускаем (это делает
Task 12 Pre-deploy QA). Output — отчёт.

**Измерения в фокусе** (из 11 dimensions code-reviewing, приоритизированные под эту фичу):
- **Architecture (1)** — согласованность модели `ContentBlock` сквозь слои; flat-immutable-record
  подход (Decision 1, без Mongo `_class`); кнопки/таймаут на уровне `FunnelStep`, не блока (Decision 2).
- **Resource Management (11)** — новые sender-методы не вводят второй HTTP-клиент; `TelegramSender`
  singleton; альбом-маппер (Decision 5) — отдельный путь, но переюзает общий request/scrub.
- **Cross-File Consistency (10)** — backend DTO ↔ frontend `types/funnel.ts` зеркало; сигнатуры
  новых `TelegramSender.send*` совпадают с вызовами в `StepExecutor`; preview DTO ↔ store action.
- **Separation of Concerns (2)** — гилка `MESSAGE` в `StepExecutor` не раздувается; валидация
  блоков в `validateSteps` не дублирует логику рендера.
- **Error Handling (4)** — crash-семантика посреди блоков (Decision 3, per-node at-most-once):
  catch-arms `BotTokenInvalidException`/`AppException`/`TelegramSendException` сохранены в гилке MESSAGE.
- **Security (8)** — кросс-проверка (детальный security-аудит — Task 10): нет server-side
  дереференса медиа-URL (Decision 6), `http(s)`-scheme валидация, backend-side parseMode-экранирование
  и отсутствие v-html в preview (Decision 8). Грубые нарушения фиксировать, глубину оставить Task 10.

**Полнота удаления старых типов** — главный кросс-компонентный риск фичи (Decision 4, Risk
"Blast radius от удаления"). Проверить:
- `StepType` enum: только `MESSAGE, DELAY, ADD_TAG, REMOVE_TAG, SET_CUSTOM_FIELD, EMIT_EVENT,
  SUBSCRIBE_TO_FUNNEL`.
- exhaustive-switch в `StepExecutor` и `FunnelService.validateSteps` компилируются без старых cases.
- нет мёртвых плоских полей `text`/`parseMode`/`imageUrl`/`caption` на `FunnelStep`/`FunnelStepDto`/
  `FunnelResponse`/`FunnelSummaryResponse`.
- фронтенд `types/funnel.ts` и UI не ссылаются на удалённые типы/поля.

**Shared resources (Architecture → секция Shared resources):**
| Resource | Ожидаемое состояние после фичи |
|----------|-------------------------------|
| `TelegramSender` | 1 singleton `@Component`; новые методы — тонкие обёртки над `send(...)`; альбом-маппер отдельный, но scrub/retry унаследованы |
| `VariableTemplateRenderer` | stateless static; вызывается из `StepExecutor` и `FunnelService.previewStep` без дублирования |

**Где писать отчёт:** `work/15-message-composer/logs/working/task-9/code-audit.json` (или
`.md` — формат по конвенции code-reviewing: severity, file:line, issue, recommendation).

**Dependencies:** все таски 1–8 должны быть в статусе done (depends_on). Аудит читает финальное
состояние кодовой базы. Пакеты не добавляются.

**Edge cases для проверки:** альбом 2–10 и type-mixing предикат (Decision 5); кнопки только на
последнем не-альбомном блоке; over-length как warning (не блокирует save); tolerant-read для
legacy old-type документа, пережившего ручной wipe (Risk fail-safe).

**Implementation hints:** начать с grep-проверок полноты удаления (быстрый сигнал), затем читать
файлы по слоям сверху вниз (модель → engine → DTO → callback → frontend). Сверять каждую находку с
соответствующим Decision в tech-spec — отклонение от Decision при отсутствии записи в decisions.md
— это находка. НЕ дублировать глубокий security-разбор (Task 10) и test-аудит (Task 11) — фиксировать
только грубые нарушения в этих областях со ссылкой на профильный таск.
