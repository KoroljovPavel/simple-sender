# User Spec: 15-message-composer

## Что делаем

Вводимо **один крок-композер** воронки, який містить **упорядкований список контент-блоків**
(`List<ContentBlock>`) і замінює три старі типи кроків повідомлень — `SEND_MESSAGE`, `SEND_IMAGE`
і `MENU`. Старі типи **видаляємо** з коду. Один композер-крок шле підписнику **N окремих
повідомлень Telegram** по черзі. До останнього (не-альбомного) блоку можна причепити inline-кнопки —
це переюзає механіку MENU (park-on-reply + branch по кнопці), тож композер із кнопками = новий
«rich-menu».

Типи блоків у цій фазі: **Text, Image, Video, Audio, File (document), Album** (media group, 2–10
елементів — це і є «Карусель»). Локацію, контакт, інвойс/чек, delay, input, print, animation —
**відкладено**.

## Зачем

Зараз author може покласти в одну ноду лише **один текст** або **одну картинку**, а video/audio/
file/album не підтримуються взагалі. Реальні воронки потребують багатших повідомлень: відео з
підписом, альбом, файл, кілька медіа + кнопки. Конкурент моделює повідомлення як упорядкований
список блоків — це збігається з ментальною моделлю автора 1:1. Наш плоский «одне поле на крок»
змушує зчіплювати багато кроків заради того, що концептуально є одним повідомленням.

## Как должно работать

1. Author відкриває редактор воронки, додає крок типу **«Повідомлення» (композер)**.
2. Усередині кроку додає блоки через picker типу блоку: Text / Image / Video / Audio / File / Album.
3. Кожен блок редагує:
   - **Text** — текст + `parseMode` (None / HTML / MarkdownV2).
   - **Image / Video / Audio / File** — URL або Telegram `file_id` + опційний `caption` + `parseMode`.
   - **Album** — список з 2–10 медіа-елементів (URL/file_id); `caption` лише на першому елементі.
4. Блоки **переставляються** вгору/вниз і видаляються (як кроки воронки зараз).
5. До **останнього** блоку (якщо він не Album) author може причепити inline-кнопки (як у MENU зараз),
   опційно — таймаут park-on-reply з target-кроком (як таймаут MENU). Якщо останній блок має бути
   альбомом І потрібні кнопки — author додає **текстовий блок-хвіст** після альбому і чіпляє кнопки до нього.
6. Праворуч — **превʼю**, що показує блоки стосом, як вони виглядатимуть у Telegram.
7. На збереженні/активації — валідація:
   - **Жорсткі помилки (блокують save, 422 інлайн-кодом):** порожній композер, >10 блоків, Album <2/>10
     або з неприпустимим змішуванням типів, кнопки на не-останньому або альбомному блоці, биті edge-таргети.
   - **Мʼяке попередження (НЕ блокує save):** text >4096 / caption >1024 — інлайн-warning; у рантаймі
     trim + WARN, не фейл.
8. У рантаймі підписник отримує блоки **як послідовність повідомлень** у порядку автора; Telegram сам
   тягне медіа за URL/file_id. Натискання кнопки на останньому блоці **розгалужує** воронку; таймаут
   (якщо заданий) веде на свій target-крок (паритет із таймаутом MENU).

## Критерии приёмки

- [ ] Композер-крок із блоками text/image/video/audio/file/album рендериться як **N послідовних
      повідомлень Telegram** у порядку автора; кожне медіа Telegram тягне сам за URL/file_id.
- [ ] До **останнього** не-альбомного блоку чіпляються inline-кнопки; крок **паркується** на відповідь
      і **розгалужується** по натиснутій кнопці (паритет із MENU: `resumeOnCallback` + branch).
- [ ] **Таймаут park-on-reply збережено** (паритет MENU): композер із кнопками підтримує опційний таймаут
      (`timeoutValue`/`timeoutUnit`/`timeoutTargetStepId`); по спливанню sweep веде на target-крок або
      завершує. Наявні timeout-resume ITs мають лишитись зеленими.
- [ ] **Callback-контракт незмінний:** wire-формат `"{executionId}:{buttonIndex}"` (≤64 байти, строгий
      парсинг), а `buttonIndex` стабільно мапиться 0-based на кнопки **останнього блоку**; `lastButtonClicked`
      зберігає координату `currentStepId:buttonIndex`. IDOR/owner-перевірки `advanceOnCallback` не слабшають.
- [ ] Варіативна підстановка `{user.*}` / `{custom.*}` працює в **text і всіх caption**, з екрануванням
      за `parseMode`.
- [ ] Валідація на **save/activate** (інлайн 422-коди, не рантайм-падіння):
      - порожній композер (0 блоків) і >10 блоків → помилка;
      - Album <2 або >10 елементів → помилка; неприпустиме змішування типів в альбомі → помилка;
      - кнопки на не-останньому блоці або на Album-блоці → помилка;
      - text >4096 / caption >1024 → позначено на save (у рантаймі — trim + WARN, не фейл).
- [ ] Старі типи кроків `SEND_MESSAGE`, `SEND_IMAGE`, `MENU` **видалені** з бекенду і фронтенду;
      воронки будуються лише на композері.
- [ ] **At-most-once на рівні ноди**: крах посеред відправки блоків лишає ноду застряглою
      `in_progress` (без повтору), а не передоставляє вже надіслані блоки.
- [ ] Нові методи `TelegramSender` (`sendVideo`/`sendAudio`/`sendDocument`/`sendMediaGroup`) працюють і
      успадковують наявні retry/429/audit/scrub; альбом коректно мапить **масив** повідомлень-відповідей.
- [ ] Snapshot-ізоляція збережена: `List<ContentBlock>` глибоко копіюється в `FunnelStep.copyOf`; правки
      воронки не впливають на in-flight рани.

## Ограничения

- **Ламаємо Decision 12** свідомо: плоскі per-type поля `FunnelStep` замінюються на `List<ContentBlock>`
  з дискримінатором типу блоку. `ContentBlock` має бути **immutable** (контракт snapshot-ізоляції).
- **Медіа лише URL/file_id** — бекенд **не дереференсить** URL (Telegram тягне сам) → інваріант
  «без SSRF» збережено. Реального **аплоаду файлів немає** в цій фазі (можливо S3 у пізніших кроках).
- **Кнопки лише на одному повідомленні** (обмеження Telegram `reply_markup`) → тільки на останньому
  блоці; **Album не може нести кнопки** (media group — окремий API без `reply_markup`).
- **`sendMediaGroup` повертає масив** повідомлень → потребує окремого маппера (не спільний single-
  `message_id` шлях).
- **Велика область змін** (Decision-12 break): `FunnelStep`/`copyOf`, `StepType`, два exhaustive-switch
  (`StepExecutor`, `validateSteps`), DTO-ланцюг, фронтенд-форма та превʼю. Видалення старих типів **ламає
  багато наявних funnel-ITs** (Phases 1–5) — композер має **перекрити** ту поведінку.
- **Немає inter-block pacing**: N послідовних send-ів підвищують шанс 429; покладаємось на наявний
  429-loop у межах одного send.
- **Деструктивне ручне очищення даних**: безпечно лише тому, що **продакшну ще немає**.
- Редактор воронки — **desktop-first** (≥1024px).
- **Рантайм-помилки доставки** (узгоджено з поточною send-семантикою): битий/недоступний медіа-URL →
  Telegram відхиляє на fetch → `TelegramSendException` → execution `failed` (як `sendPhoto` зараз);
  підписник заблокував бота посеред ноди → `CANCEL` (BLOCKED_BY_USER, як сьогодні); відключення/
  реконект бота → pinned `telegramBotId` → `failed`.
- **Бекенд `/preview` контракт** (зараз побудований навколо одного рендер-рядка для трьох видалюваних
  типів) треба **розширити** на мультиблок (зберігаючи backend-side `parseMode`-екранування й XSS-guard),
  а не лишати прибитим до старих типів.

## Риски

- **Риск 1 (високий): blast radius від видалення старих типів.** Зміни торкаються всіх місць, що
  перелічують плоскі поля, і ламають наявні funnel-ITs. **Митигація:** композер перекриває видалену
  поведінку; роботу різати на послідовні таски; покладатись на existing-test-suite як на сітку безпеки.
- **Риск 2 (середній): частковa доставка ноди.** Крах посеред відправки блоків → підписник отримав
  частину, нода застрягла, без повтору. **Митигація:** свідомо приймаємо per-node at-most-once (узгоджено
  з поточною send-семантикою); документуємо як відоме обмеження; per-block дослання — поза скоупом.
- **Риск 3 (середній): альбом ламає спільний send-шлях.** `sendMediaGroup` повертає масив. **Митигація:**
  окремий result-маппер лише для альбому; решта senders переюзають спільний `send(...)`.
- **Риск 4 (низький): сплеск 429 від N послідовних send-ів.** Накопичення per-send 429-retry-ів між
  блоками ще й **розширює вікно** застрягання ноди при краху (Риск 2). **Митигація:** наявний per-send
  429-loop; inter-block pacing додамо, лише якщо це реально завадить.
- **Риск 5 (низький): втрата наявних воронок при ручному wipe.** **Митигація:** виконати лише на
  середовищі без проду; зафіксувати як крок деплою.

## Технические решения

- Ми вирішили **замінити** `SEND_MESSAGE`/`SEND_IMAGE`/`MENU` одним композер-кроком і **видалити** старі
  типи, бо це чистіша модель і прибирає подвійну підтримку та ризиковану міграцію.
- Ми вирішили **не робити міграцію даних**, а **вручну видалити** наявні `funnels` і `funnel_executions`
  на деплої, бо продакшну ще немає і backfill flat→composer надто ризикований/складний.
- Ми вирішили **згорнути MENU в композер**: кнопки на останньому блоці переюзають park-on-reply +
  `resumeOnCallback` + branch, бо це той самий Telegram-примітив і вся механіка Phase 2 вже є.
- Ми вирішили тримати **at-most-once на рівні ноди** (один claim як зараз), бо per-block прогрес вимагав
  би нового `currentBlockIndex`-стану на `FunnelExecution` — невиправдана складність для цієї фази.
- Ми вирішили **медіа через URL/file_id**, бо це зберігає інваріант «без SSRF» і не тягне інфраструктуру
  зберігання файлів; реальний аплоад (S3) — окремий пізніший крок.
- Ми вирішили **валідувати ліміти на save/activate** інлайн-кодами, а не ловити в рантаймі, узгоджено з
  наявним `validateSteps`.
- Ми вирішили **обмежити скоуп блоків** до text/image/video/audio/file/album, бо location/contact/invoice/
  receipt — це інша територія (зокрема Telegram Payments), а delay/input уже існують як окремі примітиви.
- Ми вирішили **кнопки лише на останньому не-альбомному блоці**, бо Telegram чіпляє `reply_markup` лише
  до одного повідомлення, а media group його не підтримує.

## Тестирование

**Unit-тесты:** делаются всегда, не обсуждаются.
- `FunnelStepExecutorTest`: порядок блоків, підстановка змінних у text+усіх caption, trim лімітів, збірка
  альбому.
- `TelegramSenderTest` (mockwebserver): кожен новий метод happy-path + успадковані retry/429; окремий тест
  на масив-маппер альбому.

**Интеграционные тесты:** **делаем** — рушій критичний.
- `FunnelExecutionEngineIT` (реальна Mongo): per-node at-most-once (крах посеред ноди → без повтору),
  snapshot-ізоляція з `List<ContentBlock>`, кнопки-на-останньому-блоці park + `resumeOnCallback` branch.
- `FunnelControllerIT`: валідація на save (порожній композер, альбом <2/>10, кнопки на не-останньому/
  альбомному блоці, over-length).
- Frontend vitest: редактор блоків (add/move/remove, per-type віджет), мультиблок-превʼю.

**E2E тесты:** **не делаем** — E2E-набору для воронок немає; golden-path рушія покривають engine ITs.

## Как проверить

### Агент проверяет

| Шаг | Инструмент | Ожидаемый результат |
|-----|-----------|-------------------|
| 1. Запустити повний бекенд-тест-сюїт | bash (`./gradlew test`) | Усі executor/sender/engine-IT/controller-IT зелені |
| 2. Запустити фронтенд-тести | bash (`pnpm test`) | vitest по редактору блоків і превʼю зелені |
| 3. Зберегти композер із 0 блоків і з 11 блоків | curl (funnel update) | 422 з інлайн-кодом валідації в обох випадках |
| 4. Зберегти композер із кнопками на альбомному/не-останньому блоці | curl | 422 з відповідним кодом |
| 5. Зберегти валідний композер (text→image+caption→album×3) + кнопки на text-хвості, активувати | curl | 200; воронка `active` |

### Пользователь проверяет
- **«Test for me»** (Phase 4 test-run) на власному Telegram: побудувати мультиблок-композер, отримати
  послідовність повідомлень у правильному порядку, натиснути кнопку на останньому блоці → переконатися,
  що воронка пішла у правильну гілку. Це єдина перевірка реальної доставки в Telegram (поза автотестами).
