# Task 1: Backend step model + validation

## Required Skills

Before starting, load:
- `/skill:code-writing` — [SKILL.md](../../../.claude/skills/code-writing/SKILL.md)

## Description

Foundation task of the 16-persistent-keyboard feature: two new funnel step types — `SET_KEYBOARD`
(sends a mandatory text message and sets a persistent Telegram bottom reply keyboard) and
`CLEAR_KEYBOARD` (sends a mandatory text message and removes the keyboard). This task delivers the
backend **data model + validation + DTO round-trip** layer only — no `StepExecutor` changes (Task 3),
no preview changes (Task 4), no frontend (Task 2).

Concretely: the two `StepType` constants, five new nullable fields on the embedded `FunnelStep`
(carried through `copyOf` with a defensive row-list copy — load-bearing for execution-snapshot
isolation and funnel duplicate, user-spec Risk 1), new flat immutable records
`KeyboardRow`/`KeyboardButton` with DTO mirrors `KeyboardRowDto`/`KeyboardButtonDto`, wiring through
**both** mappers (`toSteps` DTO→domain AND `toStepDto` domain→DTO — three wiring points per field:
DTO record component + `toSteps` + `toStepDto`, else saved keyboards silently never return to the
editor), and `validateSetKeyboard`/`validateClearKeyboard` per tech-spec Decision 6.

Result: funnel CRUD round-trips both new step types (PATCH→GET `FunnelControllerIT` case) and
rejects invalid ones with 422 `funnel_step_invalid`. No DB migration — all new fields are nullable
on the embedded flat step document (Decision 10); `StepTypeReadConverter` handles new enum
constants automatically.

## What to do

1. **`StepType`** — add two constants `SET_KEYBOARD`, `CLEAR_KEYBOARD` immediately **before
   `UNKNOWN`** (keep the tolerant-read sentinel last), with javadoc-style comments in the existing
   per-phase style. Adding them makes the exhaustive `switch` in `FunnelService.validateSteps` (and
   later `StepExecutor.execute` — Task 3's concern) fail to compile until cases exist; in THIS task
   add only the `validateSteps` cases. For `StepExecutor.execute`, add minimal compile-fix cases
   that terminal-fail (mirroring the existing `UNKNOWN` handling) so the default lane stays green —
   Task 3 replaces them with the real send logic.
2. **New records** — `funnel/KeyboardRow.java` (`record KeyboardRow(List<KeyboardButton> buttons)`)
   and `funnel/KeyboardButton.java` (`record KeyboardButton(String text)`): flat immutable records,
   no `_class`, no bean validation — pattern and javadoc style of `ContentBlock`/`Button`.
3. **`FunnelStep`** — five new nullable fields with getters/setters: `keyboardText` (String),
   `keyboardParseMode` (String), `keyboardRows` (`List<KeyboardRow>`), `isPersistent` (Boolean),
   `oneTimeKeyboard` (Boolean). Extend `copyOf`: scalars by reference, `keyboardRows` →
   `new ArrayList<>(source.keyboardRows)` with null staying null — the same one-liner as
   `buttons`/`blocks`. Update the class and `copyOf` javadoc (the deep-copy contract text).
4. **DTO mirrors** — new `funnel/dto/KeyboardRowDto.java` / `funnel/dto/KeyboardButtonDto.java`
   (`@JsonIgnoreProperties(ignoreUnknown = true)`, pattern: `ButtonDto`). Append five components to
   the positional `FunnelStepDto` record: `keyboardText`, `keyboardParseMode`,
   `keyboardRows (List<KeyboardRowDto>)`, `isPersistent (Boolean)`, `oneTimeKeyboard (Boolean)`.
5. **Mapper wiring in `FunnelService`** — `toSteps`: set all five fields (add a
   `toKeyboardRows(List<KeyboardRowDto>)` helper mirroring `toButtons`/`toBlocks`: null in → null
   out); `toStepDto`: map all five back (add `toKeyboardRowDtos` mirroring `toButtonDtos`). Update
   every positional `new FunnelStepDto(...)` call site: `toStepDto` itself plus the test helpers in
   `FunnelServiceEmitEventTest` (`emitStep`, `subscribeStep`, `messageStep`) — and **update the
   positional-order comment** in `emitStep`.
6. **Validation in `FunnelService.validateSteps`** — two new switch cases:
   - `case SET_KEYBOARD -> validateSetKeyboard(step)`: mandatory non-blank `keyboardText` with hard
     cap ≤4096 (hard 422, NOT the warn-only channel of MESSAGE blocks — Decision 6/3), valid parse
     mode via `requireParseMode`, `keyboardRows` 1..10 rows, each row 1..4 buttons, each button text
     non-blank and ≤64 chars (= `MAX_KEYWORD_LENGTH`, so a button text can always be an exact
     keyword), duplicate **trimmed** button texts within one keyboard blocked via `HashSet`
     (new logic — no precedent in `validateButtons`).
   - `case CLEAR_KEYBOARD -> validateClearKeyboard(step)`: mandatory non-blank text ≤4096 + valid
     parse mode, and **strict rejection** of `keyboardRows`, `isPersistent`, `oneTimeKeyboard`
     being present (non-null) — symmetric strict rejection, no silently-ignored fields.
   - All rejections via `invalidStep(message)` → 422 `funnel_step_invalid` (one code, varying
     plain-English message — `validateMessage` precedent).
7. **Tests** (TDD — write first, see TDD Anchor): extend `FunnelStepTest` (copyOf), new
   `FunnelServiceKeyboardStepTest` (clone the `FunnelServiceEmitEventTest` pattern), add a
   PATCH→GET round-trip + 422 case to `FunnelControllerIT`.

  - `clearKeyboard_valid_acceptedAndRoundTrips` — valid CLEAR_KEYBOARD (text + parse mode only).
  - Rejection cases, each asserting 422 + `FunnelService.CODE_INVALID_STEP`: missing/blank

- `FunnelControllerIT::invalidKeyboardStepReturns422` — invalid SET_KEYBOARD (e.g. duplicate button
  texts) → 422, body `code: funnel_step_invalid`.

**Dependencies:** none — Wave 1, independent. No new packages. Task 3 (StepExecutor) and Task 4

**Edge cases:**
- Text exactly 4096 chars → valid; 4097 → 422. NOTE: this is a HARD cap (Decision 6) — deliberately
  different from MESSAGE blocks where over-length is warn-only (`warnIfOverLength`).
- Button text exactly 64 → valid (= `MAX_KEYWORD_LENGTH`, deliberate equality).
- Duplicate detection on TRIMMED texts: `"Бонус"` vs `" Бонус "` → duplicate → 422. Case is NOT
  folded (Decision 6 specifies trimmed texts only).
- A `KeyboardRow` with null `buttons` list, or a null `KeyboardButton`/null row element inside the
  lists → must hit a 422, never an NPE (guard like `validateAlbum`'s null-item check).
- CLEAR_KEYBOARD with an EMPTY (non-null) `keyboardRows` list still counts as "present" → 422.
- SET_KEYBOARD with null `isPersistent`/`oneTimeKeyboard` is VALID (defaults are a form concern,
  Task 2; the executor handles nulls in Task 3) — only CLEAR_KEYBOARD rejects them when present.
- `keyboardParseMode` null is valid (plain text); `""`/garbage → 422 — route through `blankToNull`
  in `toSteps` (same as block parseMode at line 726) so blank normalizes to null before validation.
- Hostile payload with unknown JSON fields → ignored (`@JsonIgnoreProperties`), never 400/500.

**Implementation hints:**
- Three wiring points per field (DTO record + `toSteps` + `toStepDto`) — code-research §5 flags
  `toStepDto` as the historically-missed one; the round-trip IT exists to catch exactly that.
- `copyOf` is exercised by BOTH the execution snapshot factory and `duplicate()` — the existing
  `FunnelControllerIT.duplicateCopiesGraphVerbatim` gives a precedent if you want a duplicate-side
  assertion, but the required coverage is the `FunnelStepTest` unit cases.
- Clone `FunnelServiceEmitEventTest` wholesale for the new test class: same seed
  (`AbstractIntegrationTest`, user/project/funnel repos), same `assert422` helper asserting
  `FunnelService.CODE_INVALID_STEP`, a `keyboardStep(...)` builder instead of `emitStep`.
- In `FunnelControllerIT`, follow `updateRewritesStepOrderByIndex` for the PUT + `jsonPath` shape
  (note: the controller update verb there is PUT, not PATCH — follow the existing test idiom).
- Validation order inside `validateSetKeyboard`: text → parse mode → rows shape → per-button rules
  → duplicates. Plain-English messages, never i18n'd on the backend (frontend maps the `code`).
- PII rule: validation messages may name fields/limits but must not echo author content beyond
  what existing messages do (they don't echo values — keep it that way).
