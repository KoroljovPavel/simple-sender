## Description

Full-feature **test quality audit** for 16-persistent-keyboard. This is an Audit Wave task: the
auditor IS the review (reviewers are empty); the artifact is a test-quality audit report. It runs
after all implementation tasks (Waves 1-3) are done, when every test of the feature exists.

The goal is to audit the feature's **test layer as a whole**, not file by file: does every
user-spec acceptance criterion map to a concrete test, are assertions **meaningful** (exact
`/sendMessage` wire bodies via JsonNode, captured `reply_markup` Maps, emitted form payloads — not
just call counts or HTTP statuses), is the test pyramid balanced (unit-heavy; slow-lane
`@Tag("slow")` ITs only for the wire-format/completion invariants), is the no-v-html source guard
in the preview spec still intact, and is the "covered by existing tests (cited, not rewritten)"
claim from the tech-spec **real** — i.e. the cited re-enter-guard and keyword-dispatch/menu-precedence
tests actually exist, assert what the tech-spec says they assert, and are still green.

The coverage checklist source of truth is the tech-spec **Testing Strategy** section
(unit / integration / E2E breakdown) plus the user-spec «Критерии приёмки» (13 ACs).
A green suite is not the bar — the audit's value is in coverage gaps and weak assertions.

## What to do

1. Build the test inventory for the feature: read [decisions.md](../decisions.md) (Task 1-7 reports —
   which test files were created/modified) and cross-check against the tech-spec Testing Strategy
   list. Expected inventory (verify it is complete, flag anything missing):
   - `FunnelStepTest` — copyOf cases for the new keyboard fields
   - `FunnelServiceKeyboardStepTest` (new) — validateSetKeyboard/validateClearKeyboard
   - `FunnelStepExecutorTest` — SET_KEYBOARD/CLEAR_KEYBOARD execution cases
   - `FunnelControllerIT` — round-trip + preview + 422 cases
   - `FunnelExecutionEngineIT` — slow-lane wire-body cases
   - `FunnelStepForm.keyboard.spec.ts` (new) — form/validation-mirror/hint specs
   - `FunnelMessagePreview.spec.ts` — keyboard render branch specs
2. Read every test file in the inventory. For each, record: what it covers, whether assertions are
   meaningful, and what is missing relative to the Testing Strategy checklist (full checklist in
   Details below).
3. Map **every user-spec acceptance criterion** (13 checkboxes in «Критерии приёмки») to a concrete
   test (`file::testName`). Mark each AC Covered / Partial / Missing. ACs covered by cited existing
   tests (re-enter guard, keyword dispatch, menu precedence) map to those tests — see step 5.
4. Assess **assertion quality** (test-master anti-patterns): wire-body cases must assert the exact
   `reply_markup` JSON shape (`keyboard` rows/labels in order, `is_persistent`,
   `resize_keyboard:true`, `one_time_keyboard`, `remove_keyboard:true`) — not just "a request was
   made"; executor cases must capture the markup argument, not just `verify(sender)`; controller
   round-trip must assert every keyboard field survives GET, not just 200; form specs must assert
   the emitted step shape (incl. preserved `id`/`next`), not just rendering.
5. Verify the **cited-not-rewritten existing coverage is real**: open
   `FunnelEventServiceTest` — `reEnter_duplicateOnOneFunnel_doesNotAbortOtherMatches`
   (`allowReEnter=false` → silent no-op) and `reEnter_allowReEnterFunnel_cancelsExistingThenInserts`
   (`true` → restart) — and `ProcessTelegramUpdateJobTest` — `plainText_dispatchesKeyword` (webhook
   leg of button-tap routing) and `plainText_keywordSuppressedWhileWaitingForReply` (menu
   precedence). Confirm the tests exist under those names, assert the cited semantics, and are not
   disabled. If a citation is inaccurate — that is a finding.
6. Assess **pyramid balance**: validation and executor logic at unit level; round-trip/preview at
   controller-IT level; only the wire-format + completed-not-parked + dispatch invariants in the
   slow lane; no E2E (per user-spec — reply keyboards render only in a real Telegram client; the
   manual leg is smoke.md, Task 7). Check the no-v-html source guard in
   `FunnelMessagePreview.spec.ts` still exists and still scans the component source.
7. Write the **audit report** to
   `work/16-persistent-keyboard/logs/working/audit/test-auditor.json` — the project's established
   audit-report location (convention from 15-message-composer:
   `logs/working/audit/{auditor}.json`; the tech-spec's `logs/audit/test-audit.md` guess is
   superseded by this convention). Structure: verdict, summary, severity_counts, inventory,
   AC-coverage table, findings (severity blocker/major/minor + concrete fix + `file::testName`
   location), pyramid verdict. Also return the findings in the final agent message and write the
   short summary entry to decisions.md (Post-completion).

## Details

**Artifact:** audit report at
`work/16-persistent-keyboard/logs/working/audit/test-auditor.json` + the same findings in the
final agent message + a short decisions.md entry. Report structure (convention from
`work/completed/15-message-composer/logs/working/audit/test-auditor.json`): `task`, `feature`,
`auditor: "test-auditor"`, `date`, `verdict` (passed / passed-with-findings / failed),

concrete fix + `file::testName` location), pyramid verdict. No source files are modified — fixes
are out of scope for this task; it only audits.

**Coverage checklist (from tech-spec Testing Strategy — every item must be Covered/Partial/Missing):**

*Unit:*
- `FunnelStepTest` (copyOf): keyboard scalars survive copy; `keyboardRows` copied to a NEW list
  instance; null rows stay null; mutating the copy's rows does not affect the source.
- `FunnelServiceKeyboardStepTest`: valid SET_KEYBOARD/CLEAR_KEYBOARD accepted; rejections —
  missing/blank text, text >4096, 0 rows, >10 rows, 0 buttons in a row, >4 buttons in a row,
  blank button text, button text >64, duplicate button texts, keyboard-only fields
  (`keyboardRows`/`isPersistent`/`oneTimeKeyboard`) present on CLEAR_KEYBOARD, invalid parse
  mode — all 422 `funnel_step_invalid`.
- `FunnelStepExecutorTest`: markup captor asserts `keyboard` rows/labels, `is_persistent`,
  `resize_keyboard:true`, `one_time_keyboard` for SET_KEYBOARD; `remove_keyboard:true` for
  CLEAR_KEYBOARD; outcome CONTINUE for both; error-mapping trio (`BLOCKED_BY_USER`/`CHAT_NOT_FOUND`
  → cancel, other Telegram errors → fail, `invalid_bot_token` → fail); text rendered through
  variables/parse mode. Also the Task 3 defensive guard: null/empty `keyboardRows` on a
  SET_KEYBOARD snapshot → terminal fail.
- `FunnelStepForm.keyboard.spec.ts`: form blocks render for BOTH types; rows sub-editor
  add/remove/caps; validation mirror (duplicates, blank, >64, text >4096); no `resize_keyboard`
  control rendered; checkbox defaults (persistent on, one-time off); keyword hint shown/hidden
  against mocked store funnels; emitted step preserves `id`/`next` (incl. a CLEAR_KEYBOARD emit
  case).
- `FunnelMessagePreview.spec.ts`: keyboard render branch for SET_KEYBOARD (text + rows mock) AND
  CLEAR_KEYBOARD (text only); payload carries keyboard fields; no-v-html source guard stays green.

*Integration:*
- `FunnelExecutionEngineIT` (`@Tag("slow")`): full sweep for SET_KEYBOARD → exact `/sendMessage`
  body `reply_markup.keyboard`/`is_persistent`/`resize_keyboard`/`one_time_keyboard` (JsonNode
  idiom per Decision 9); CLEAR_KEYBOARD → `remove_keyboard:true`; execution ends `completed`,
  never `waiting_for_reply`; keyword-dispatch case — button-label text starts the matching keyword
  funnel via `FunnelEventService.dispatchForSubscriber`.
- `FunnelControllerIT`: PATCH with both new step types → GET → ALL keyboard fields survive the
  HTTP round-trip (`toSteps`/`toStepDto` wiring); preview returns `kind="keyboard"` + rendered
  text (variables substituted) + raw rows for SET_KEYBOARD and `keyboardRows=null` for
  CLEAR_KEYBOARD; 422 for an invalid keyboard step.
- Cited, not rewritten: re-enter guard (`FunnelEventServiceTest`, two cases) and menu precedence /
  keyword dispatch (`ProcessTelegramUpdateJobTest`, two cases) — verify citations are accurate.

*E2E:* None by design (user-spec: reply keyboard renders only in a real Telegram client; the
manual leg is `smoke.md`, Task 7). Do not demand E2E; flag only if frontend specs are missing.

**User-spec AC mapping hints (13 ACs → expected test homes):** editor caps/text/variables and
duplicate-block ACs → `FunnelServiceKeyboardStepTest` + `FunnelStepForm.keyboard.spec.ts`;
checkbox/resize AC → form spec; both wire-body ACs + CONTINUE/completed → `FunnelExecutionEngineIT`
(+ `FunnelStepExecutorTest` at unit level); tap-starts-keyword-funnel AC → engine IT dispatch case
+ cited `plainText_dispatchesKeyword`; repeat-tap re-enter AC → cited `FunnelEventServiceTest`
cases; hint AC → form spec; preview AC → `FunnelControllerIT` + `FunnelMessagePreview.spec.ts`;
error-mapping AC → `FunnelStepExecutorTest`; copyOf AC → `FunnelStepTest`; blank-button AC →
validation unit + form mirror; i18n parity AC → prebuild gate (note as covered by Task 11 QA's
`pnpm build`, not by a Vitest spec — Partial-by-design, do not flag as a gap).

**Anti-patterns to hunt (test-master):**
- Wire-body "assertions" that only count requests or check HTTP 200 instead of parsing the
  recorded `/sendMessage` body (JsonNode) and asserting the exact `reply_markup` shape.
- `verify(sender)` without an `ArgumentCaptor`/matcher on the markup argument where the Map
  content is the point (rows order, object-form buttons `{"text": ...}`, hardcoded
  `resize_keyboard:true`).
- Round-trip tests asserting only status/id but not each keyboard field after GET (the
  `toStepDto` wiring is exactly what such a test exists to prove).
- copyOf test that checks field equality but not list-instance identity (`assertNotSame`) or
  copy-mutation isolation.
- Happy-path-only validation (missing the >64 / duplicate / CLEAR_KEYBOARD-rejects-rows negatives).
- Form specs asserting rendering but not the emitted payload (`id`/`next` preservation is the
  regression trap).
- Disabled/skipped tests counted as coverage.

**Dependencies:** Tasks 1-7 done (all Wave 1-3 implementation + smoke.md); their decisions.md
entries are the inventory source. Runs in parallel with Tasks 8 (Code Audit) and 9 (Security
Audit) — do not duplicate their scope (code quality, OWASP); overlap is allowed only where a test
gap IS the security gap (e.g. a missing no-v-html guard is in scope here).

**Edge cases / known traps:**
- `FunnelStepDto` is a positional record extended in Task 1 — verify the positional-order comment
  and positional ctor call sites in tests were actually updated (tech-spec Risk: silent breakage).
- Engine IT had no body-assert precedent before this feature (Decision 9) — check the new cases
  use the `TelegramSenderIT` JsonNode idiom + `FunnelTestRunSendIT` `takeRequest`/`readUtf8` drain,
  and drain ALL recorded requests so assertions hit the right request in multi-step funnels.
- Preview echoes CLAMPED rows (≤10×≤4, label ≤64, Decision 7) — check whether any test covers the
  clamp; if none, that is a finding (severity per judgment), not a silent pass.
- The no-v-html guard is a source-scan test — confirm it scans `FunnelMessagePreview.vue` content
  and was not weakened/whitelisted when the keyboard branch was added.

**Implementation hints:** tech-spec Testing Strategy is the checklist source of truth; bind every
finding to `file::testName` or to a concrete missing test; "green suite" != "quality suite" —
the audit's value is in gaps and weak assertions, not in counting green tests.
