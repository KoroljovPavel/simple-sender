# Task 11: Pre-deploy QA

## Required Skills

Before starting, load:
- `/skill:pre-deploy-qa` — [SKILL.md](../../../.claude/skills/pre-deploy-qa/SKILL.md)

## Description

Final acceptance testing for the 16-persistent-keyboard feature before it goes to `main`. The
feature added two funnel step types (`SET_KEYBOARD` / `CLEAR_KEYBOARD`) across backend
(step model + validation, StepExecutor execution, preview endpoint), frontend (step form with
keyword hint, preview panel, uk/en i18n), and slow-lane engine wire-format ITs. All
implementation tasks (1-7) and all three audits (8-10) are complete.

This task executes the Agent Verification Plan from tech-spec: full default backend lane, slow
lane (Testcontainers/MockWebServer engine ITs), frontend Vitest suite, locale parity gate, and a
local API run of a SET_KEYBOARD funnel — then verifies every acceptance criterion from both
user-spec and tech-spec against the test evidence.

There is no deploy/live environment for this project: code goes to `main` and the author verifies
manually. Manual real-Telegram checks (keyboard rendering in a client, taps, bonus scenario
end-to-end) are deferred to the user via [smoke.md](../smoke.md) (authored in Task 7). Such
criteria are reported as **deferred**, not failed.

## What to do

1. Execute the Agent Verification Plan (tech-spec "Agent Verification Plan"):
   1. Default backend lane: `cd backend && ./gradlew test` — validateSteps, StepExecutor, copyOf
      tests green; no regressions across the rest of the suite.
   2. Slow lane: `cd backend && ./gradlew test -PrunSlow=true` — engine IT wire-format assertions
      green (`FunnelExecutionEngineIT`: `reply_markup` bodies for both step types, `completed`
      final status, keyword-dispatch case).
   3. Frontend: `cd frontend && pnpm test` — form + hint + preview specs green; no regressions.
   4. Local API run (AVP step 4): run the backend locally on localhost:8080, create a funnel with
      a SET_KEYBOARD step via curl, activate it, trigger a test-run → execution ends `completed`;
      the `/sendMessage` payload with `reply_markup` is visible in logs/MockWebServer. If a full
      local run is not feasible in the environment (e.g. no bot token / Mongo / Redis available),
      document exactly why and cite the engine IT evidence for the same payload as fallback.
   5. Locale parity: `cd frontend && pnpm build` — prebuild parity gate passes for uk/en.
2. Verify EVERY acceptance criterion from user-spec («Критерии приёмки») and tech-spec
   ("Acceptance Criteria") — the full list is mirrored in this task's Acceptance Criteria section.
   For each criterion record a verdict (pass / fail / deferred) with concrete evidence: test
   class/method name, command output, or curl response.
3. Mark manual real-Telegram criteria as **deferred to user via [smoke.md](../smoke.md)**:
   persistent keyboard visible in a real client and surviving execution end, live tap starting the
   keyword funnel, bonus scenario end-to-end (child keyboard, several moves, return to main menu
   in both branches), CLEAR_KEYBOARD removing the keyboard in the client. Confirm smoke.md exists
   and covers all of them.
4. Write the QA report (JSON, per pre-deploy-qa skill format) to
   `work/16-persistent-keyboard/logs/working/qa/pre-deploy-qa-report.json`: per-criterion verdicts with
   evidence, the deferred list, and the overall verdict.
5. If any criterion fails or any suite is red — report the failure with reproduction details and
   stop; do not mark the task done.

## Details

**Verification, not implementation:** this task writes no production code. If a suite is red or a
criterion fails, the outcome is a precise failure report (test name, output, reproduction) — fixes
belong to a follow-up round, not this task.

**Test lanes:** integration tests are behind `-PrunSlow=true` (`@Tag("slow")`, Testcontainers +
MockWebServer) — the default lane will NOT run `FunnelExecutionEngineIT`; both lanes are required.
Slow lane needs Docker running.

**Criteria covered by existing (pre-feature) tests:** repeat-tap re-enter semantics —
`FunnelEventServiceTest.reEnter_duplicateOnOneFunnel_doesNotAbortOtherMatches` and
`reEnter_allowReEnterFunnel_cancelsExistingThenInserts`; menu precedence —
`ProcessTelegramUpdateJobTest.plainText_keywordSuppressedWhileWaitingForReply`; webhook keyword leg —
`ProcessTelegramUpdateJobTest.plainText_dispatchesKeyword`. Verify these still pass in the default
lane and cite them as evidence — do not re-test those paths manually.

**Editor-behavior criteria (checkboxes/defaults, keyword hint, form validation mirror, preview
panel):** verified via the frontend Vitest specs (`FunnelStepForm.keyboard.spec.ts`,
`FunnelMessagePreview.spec.ts`) — cite specific spec cases as evidence; live-browser checks were
already done as Verify-user in Tasks 2 and 5.

**Local API run (AVP step 4):** backend on localhost:8080; use curl to create a funnel containing
a SET_KEYBOARD step (keyboardText, keyboardRows, isPersistent, oneTimeKeyboard), activate, use the
funnel test-run endpoint, then poll/inspect the execution status to confirm `completed`. The
expected wire body (Decision 5 / Data Models in tech-spec):
`{"keyboard":[[{"text":"…"}]],"is_persistent":true,"resize_keyboard":true,"one_time_keyboard":false}`
for SET_KEYBOARD and `{"remove_keyboard":true}` for CLEAR_KEYBOARD. If local infrastructure
(Mongo/Redis/bot token) prevents the run, document the blocker and fall back to engine IT evidence,
which asserts the identical payload through the full sweep cycle.

**Deferred ≠ failed:** real-Telegram rendering criteria can only be verified by the user in a real
client (no live environment, no MCP tools for Telegram client rendering). Report them as deferred
with a pointer to [smoke.md](../smoke.md); a post-deploy/user round picks them up.

**Dependencies:** Tasks 8, 9, 10 (audit wave) must be done; read their reports and decisions.md
entries for known issues before issuing the final verdict.
