# Task 2: Frontend step form + i18n

## Required Skills

Before starting, load:
- `/skill:code-writing` — [SKILL.md](../../../.claude/skills/code-writing/SKILL.md)

## Description

Add editor support for the two new funnel step types — `SET_KEYBOARD` and `CLEAR_KEYBOARD` — in `FunnelStepForm.vue` plus the TS type mirrors and uk/en locale strings. This is the authoring half of feature 16-persistent-keyboard: the author builds a persistent bottom reply keyboard (rows of plain-text buttons, «Постійна» / «Сховати після натискання» options) or a keyboard-removal step, both carrying a mandatory text message (text + parse mode, ≤4096, variables rendered server-side).

The form mirrors the backend validation rules from Decision 6 **byte-for-byte** (the 422 `funnel_step_invalid` is only a backstop), and shows a **non-blocking amber hint** under any button whose text contains no keyword of an active keyword funnel (Decision 8) — because a button tap routes through the existing Phase-3 keyword dispatch, the button-to-funnel link is a text convention the editor merely advises on.

Wave 1, no dependencies: the TS types are mirrored from the tech-spec Data Models section (frontend block), not read from backend code — backend Task 1 lands in parallel. Scope boundary: the preview DTO mirrors (`kind` union gaining `'keyboard'`, `PreviewStepRequest`/`PreviewStepResponse` fields) and `FunnelMessagePreview.vue` belong to Task 5 — do NOT touch them here.

## What to do

1. **`frontend/types/funnel.ts`** — extend the `StepType` union with `'SET_KEYBOARD' | 'CLEAR_KEYBOARD'`; add new reply-button types `KeyboardButton { text: string }` and `KeyboardRow { buttons: KeyboardButton[] }` (distinct from the inline `Button` — reply buttons are plain text only); add the nullable keyboard fields to `FunnelStep`: `keyboardText?`, `keyboardParseMode?`, `keyboardRows?`, `isPersistent?`, `oneTimeKeyboard?` (exact shapes in tech-spec Data Models, frontend block). Do NOT touch the preview DTOs (Task 5).
2. **`frontend/components/funnels/FunnelStepForm.vue`** — add both types to `STEP_TYPES`; add two per-type `v-if` form blocks:
   - Both types: mandatory keyboard text (textarea) + parse mode select (reuse `PARSE_MODES`), seeded from `props.initial` when editing (type-guarded like every other branch).
   - SET_KEYBOARD only: a rows sub-editor following the `menuButtons`/`blocks` local-reactive-array idiom (uid-keyed rows, add/remove row, add/remove button per row, cap-guarded mutators) with `*Touched` hand-validation mirroring Decision 6 byte-for-byte: non-blank text ≤4096 (hard block — unlike the composer's soft warn), 1..10 rows, 1..4 buttons per row, button text non-blank and ≤64, duplicate trimmed button texts within one keyboard blocked; «Постійна» (`is_persistent`) checkbox default ON and «Сховати після натискання» (`one_time_keyboard`) checkbox default OFF; NO `resize_keyboard` control anywhere.
   - SET_KEYBOARD only: a per-button non-blocking amber keyword hint — extend the existing `selectedType` watch with `if (ty === 'SET_KEYBOARD') ensureFunnelsLoaded()` and compute the mirror of backend `containsAnyKeyword`: warn when no `status === 'active' && triggerType === 'keyword'` funnel in `useFunnelsStore` has a keyword contained in the lowercased button text.
   - `onSubmit` cases for both types: mark touched, block on invalid, emit a narrow `FunnelStep` carrying ONLY the active type's fields and preserving `id`/`next` from `props.initial` (CLEAR_KEYBOARD too). CLEAR_KEYBOARD must NOT emit `keyboardRows`/`isPersistent`/`oneTimeKeyboard` — the backend strictly rejects them on that type (Decision 6).
3. **`frontend/i18n/locales/uk.json` + `en.json`** — all new strings in BOTH files (prebuild parity gate): `funnels.steps.type.SET_KEYBOARD/.CLEAR_KEYBOARD`, form labels (keyboard text, rows/buttons add-remove, both checkbox labels, hint text), validation messages for every new rule. No new error keys — 422 reuses the existing `errors.funnels.funnel_step_invalid`. Check whether the steps list renders a per-type `funnels.steps.summary.*` entry for new types and add ones if it does.
4. **New `frontend/tests/components/funnels/FunnelStepForm.keyboard.spec.ts`** — Vitest component spec cloning the `FunnelStepForm.composer.spec.ts` harness (see TDD Anchor for the case list).

**Edge cases:**
- New SET_KEYBOARD step seeds one row with one blank button (author always has a starting point — same idiom as the composer's seeded TEXT block); 0 rows / a 0-button row blocks submit (1..10 × 1..4 is mandatory, unlike the optional inline keyboard).
- CLEAR_KEYBOARD must not carry `keyboardRows`/`isPersistent`/`oneTimeKeyboard` in the emitted step — the backend strictly rejects their presence on that type (Decision 6 symmetric rejection), so a sloppy emit would 422 on save.
- Switching away from SET_KEYBOARD and submitting another type must not be blocked by stale keyboard state (validate only the active type's state — existing convention).
- Duplicate detection compares TRIMMED texts ("Go " vs "Go" is a duplicate); the emitted texts are trimmed.
- Hint is advisory: visible hint never gates `onSubmit`; it recomputes live as the author types or as store data arrives.
- `keywords` may be `null`/absent on non-keyword funnels — guard the mirror computed.
- Editing a step whose `isPersistent`/`oneTimeKeyboard` are explicitly `false`/`true` must seed those values, not the defaults (`?? true` on a stored `false` is the classic bug — use type-guarded explicit checks).

**Implementation hints:** keep the validation constants next to the MENU/composer constant blocks with the same "mirror backend FunnelService byte-for-byte" comments (rows max 10, buttons-per-row max 4, button text max 64 = `MENU_LABEL_MAX` value but a separate constant — different backend rule). The keyword-hint computed should be a function-per-button (like `menuButtonLabelError(row)`) so the template calls it per button cell.
