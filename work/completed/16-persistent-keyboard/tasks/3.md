# Task 3: StepExecutor execution of both steps

## Required Skills

Before starting, load:
- `/skill:code-writing` — [skills/code-writing/SKILL.md](../../../.claude/skills/code-writing/SKILL.md)

## Description

Make the engine actually execute the two new step types added in Task 1. `StepExecutor.execute` is an exhaustive switch over `StepType` (currently lines 108-133) — adding the `SET_KEYBOARD`/`CLEAR_KEYBOARD` enum constants in Task 1 makes this switch non-exhaustive, so this task adds the two cases.

Both steps are fire-and-forget sends (Decision 4): render the mandatory `keyboardText` through the existing variable renderer, attach the reply-keyboard markup (`ReplyKeyboardMarkup` for SET_KEYBOARD, `ReplyKeyboardRemove` for CLEAR_KEYBOARD — wire shapes per Decision 5, verified against the Telegram Bot API), send one text message via the existing 6-arg `TelegramSender.sendText`, and return `cont()` (`Outcome.CONTINUE`). The execution never parks (`waiting_for_reply` is for inline-menu MESSAGE steps only) — the keyboard survives execution completion by design; a button tap returns later as plain text through the untouched keyword-dispatch path.

No `TelegramSender` change: its 6-arg `sendText` already accepts an arbitrary `Object replyMarkup` serialized verbatim by Jackson (code-research §4). No `Outcome` enum change: CONTINUE already exists.

## What to do

1. Add `case SET_KEYBOARD` to `StepExecutor.execute`, delegating to a new private handler that:
   - Defensively guards null/empty `step.getKeyboardRows()`: return a terminal `StepResult.fail(...)` with a non-PII reason code (e.g. `empty_keyboard_rows`), mirroring the existing MAJ-2 `empty_message_blocks` guard in `message()` — validation normally prevents this; the guard only stops a malformed/legacy snapshot from NPE-looping the sweep.
   - Renders `step.getKeyboardText()` via the existing `renderTrimmed(text, parseMode, subscriber, execution, MAX_MESSAGE_LENGTH, LOG_TEXT_TRIMMED)` — variables substituted, 4096 cap, codes-only WARN.
   - Builds the `ReplyKeyboardMarkup` Map per Decision 5 (see Details) and sends via `sender.sendText(bot.getId(), subscriber.getTelegramChatId(), text, step.getKeyboardParseMode(), null, markup)`.
   - Returns `StepResult.cont()`.
2. Add `case CLEAR_KEYBOARD` analogously: render `keyboardText` the same way, send with markup `{"remove_keyboard": true}`, return `cont()`. No rows guard (CLEAR_KEYBOARD has no rows).
3. Wrap both sends in the standard error-mapping try/catch, byte-for-byte identical to the other send steps:
   - `TelegramSendException` → `fromTerminalReason(ex)` (BLOCKED_BY_USER / CHAT_NOT_FOUND → cancel; other terminal reasons → fail)
   - `BotTokenInvalidException` → `StepResult.fail("invalid_bot_token")`
   - `AppException` → `StepResult.fail(codeOrStatus(ex))`
4. Add new markup builder(s) analogous to the existing `buildReplyMarkup` (LinkedHashMap/List, static, private). Buttons in object form `{"text": ...}`, never bare strings. `resize_keyboard` hardcoded `true`.
5. Keep logging compliant with the project PII rule (patterns.md, restated in the tech-spec Task 3 block): ids/codes only — never the rendered text, never button labels. The only expected log is the existing `LOG_TEXT_TRIMMED` WARN inside `renderTrimmed`.
6. Write the unit tests first (TDD Anchor below), watch them fail, implement, watch them pass.

Check decisions.md for the exact names Task 1 landed. No new packages.

**Edge cases:**
- Null/empty `keyboardRows` on a SET_KEYBOARD snapshot → terminal FAIL before any send (defensive only; save-validation prevents it).
- `keyboardText` over 4096 after rendering → trimmed + codes-only WARN, NOT a failure (renderTrimmed handles this).
- `keyboardParseMode` null → `sendText` omits `parse_mode` (existing sender behavior); pass it through as-is.
- `isPersistent`/`oneTimeKeyboard` null on the snapshot: the form defaults them (on/off), but the snapshot field is `Boolean` — decide explicitly how the builder emits them (e.g. apply the documented defaults `is_persistent:true` / `one_time_keyboard:false` when null) and assert that choice in a test; never emit a JSON `null`.
- A row record with a null/empty buttons list is not expected past validation; the simple defensive stance is to treat it like the rows guard if encountered — do not silently emit an empty wire row.

**Implementation hints:**
- Wire shapes (Decision 5, verified via Context7 against the Telegram Bot API): SET_KEYBOARD → `{"keyboard": [[{"text": "…"}], …], "is_persistent": <bool>, "resize_keyboard": true, "one_time_keyboard": <bool>}`; CLEAR_KEYBOARD → `{"remove_keyboard": true}`. `selective` / `input_field_placeholder` deliberately unused.
- Call shape precedent (sendBlock TEXT branch, line 223): `sender.sendText(bot.getId(), chatId, text, parseMode, null, replyMarkup)` — ownerId is `null` for funnel sends.
- Error mapping: mirror the try/catch in `message()` (lines 202-209) exactly; the retry/scrub/audit/blocked-flip pipeline lives inside the sender (code-research §4) — do not duplicate it.
- The CLEAR_KEYBOARD markup is constant — a static builder (or constant map) is fine; SET_KEYBOARD builder iterates `KeyboardRow.buttons()` → `KeyboardButton.text()` into `{"text": …}` objects.
- Both handlers can share one private send-and-map helper since they differ only in markup; keep the structure readable and consistent with the existing per-type private methods.
- Test stubbing idiom: `when(sender.sendText(anyString(), any(), anyString(), any(), any(), any())).thenReturn(new SentMessage(CHAT_ID, 1L, Instant.now()))`; markup assertion: `ArgumentCaptor<Object>` + cast to `Map<String,Object>` and walk keys.
- The engine slow-lane IT wire-body assertions are Task 6, not this task — unit-level markup captors are the scope here.
