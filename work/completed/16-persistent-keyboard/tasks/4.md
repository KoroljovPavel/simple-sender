# Task 4: Backend preview extension

## Required Skills

Before starting, load:
- `/skill:code-writing` — [SKILL.md](../../../.claude/skills/code-writing/SKILL.md)

## Description

Extend the step-preview surface on the backend so the editor's preview panel can render the two new
keyboard step types (`SET_KEYBOARD` / `CLEAR_KEYBOARD`) introduced by this feature. Implements
tech-spec Decision 7.

Today `POST /api/projects/{projectId}/funnels/{funnelId}/steps/{stepId}/preview`
(`FunnelService.previewStep`, lines 396-421) gates on the SAVED step's type: `MESSAGE` → renders the
request's composer blocks via `VariableTemplateRenderer` (kind `"message"`); everything else → empty
`renderedBlocks` with kind `"non_message"`. After this task the same endpoint gains a third branch:
for a saved SET_KEYBOARD / CLEAR_KEYBOARD step it renders the request's `keyboardText` through the
same renderer (so the preview is byte-for-byte faithful to the runtime, including parse-mode
escaping of substituted variables) and returns `kind="keyboard"` plus the raw button-label rows for
the frontend keyboard mock (Task 5 consumes them).

Two contract points are deliberate (Decision 7):
- **Button labels are NOT variable-rendered** — they are echoed verbatim. The label IS the keyword
  link (a tap sends the label as plain text into keyword dispatch); rendering variables into labels
  would break that matching.
- **Echoed rows are CLAMPED to the validation caps** (≤10 rows × ≤4 buttons per row, label ≤64
  chars). Preview is non-validating by design (it must work on in-progress, possibly-invalid form
  state), so clamping ensures the response never reflects an unbounded unvalidated payload.

The frontend mirror (`types/funnel.ts` `kind` union, preview panel render branch) is Task 5, NOT
this task. This task is backend-only: two DTO records, one service branch, IT coverage.

## What to do

1. **Extend `PreviewStepRequest`** (record) with three new components: `String keyboardText`,
   `String keyboardParseMode`, `List<KeyboardRowDto> keyboardRows` (the DTO records created by
   Task 1). Keep `@JsonIgnoreProperties(ignoreUnknown = true)` (mass-assignment defense). Update the
   record's doc comment to cover the keyboard fields.
2. **Extend `PreviewStepResponse`** (record) with a new nullable component
   `List<List<String>> keyboardRows` (raw labels for the keyboard mock; non-null only for a
   SET_KEYBOARD preview). Document the `kind` union as `"message" | "non_message" | "keyboard"` and
   the new component's semantics (verbatim labels, clamped, null otherwise).
3. **Branch `previewStep` in `FunnelService`** on the saved step's type (consistent with the
   existing `isMessageStep` gate): for SET_KEYBOARD and CLEAR_KEYBOARD render
   `request.keyboardText()` with `request.keyboardParseMode()` via
   `VariableTemplateRenderer.render(...)` against the same resolved subscriber/stub, return a
   response with exactly one TEXT `RenderedBlock` in `renderedBlocks`, the existing `sampleData`
   flag, `kind="keyboard"`, and `keyboardRows` = clamped raw label rows (SET_KEYBOARD) or null
   (CLEAR_KEYBOARD).
4. **Update all existing `new PreviewStepResponse(...)` call sites** — the record constructor is
   positional, so the `"message"` and `"non_message"` returns must pass `null` for the new
   `keyboardRows` component. Existing MESSAGE / non-message preview behavior must not change.
5. **Add `FunnelControllerIT` preview cases** per the TDD Anchor — write them first, watch them
   fail, then implement.

  state for SET_KEYBOARD/CLEAR_KEYBOARD; labels never rendered). Note: `stepType` is a String and

  `RenderedBlock` / `RenderedMediaItem` records; doc comment lists `kind` values
  `"message" | "non_message"`. Append `List<List<String>> keyboardRows`; update the doc comment:
  `kind` union gains `"keyboard"`; `keyboardRows` = verbatim, clamped raw labels, non-null only for
  SET_KEYBOARD; no-identity-leak contract stays.
- `backend/src/main/java/com/botfunnel/funnel/FunnelService.java` — `previewStep` (lines 396-421):
  after the `isMessageStep` branch (which returns at line 416) add a keyboard branch before the
  `"non_message"` fallthrough; both existing constructor calls (lines 416, 420) gain a trailing
  `null` for `keyboardRows`. New private helpers (suggested): a text-render step reusing the
  `VariableTemplateRenderer.render(text, parseMode, subscriber)` call shape from `renderBlocks`
  (build one `RenderedBlock` with type `"TEXT"`, text, parseMode, null media/caption/items), and a
  clamp-and-flatten helper `List<KeyboardRowDto> → List<List<String>>` applying the caps.
- `backend/src/test/java/com/botfunnel/funnel/FunnelControllerIT.java` — extend the
  "preview (multiblock)" section. Existing helpers `previewBody`/`previewBodyBlocks` build
  `{stepType, blocks}` maps — add a `previewKeyboardBody(stepType, text, parseMode, rows)` helper
  (LinkedHashMap → `json(...)`, rows as `List<Map<String,Object>>` of
  `{"buttons":[{"text": ...}]}` matching the `KeyboardRowDto` JSON shape). Seeding a saved keyboard
  step requires a `FunnelStep` builder analogous to `textStep(...)` — set `stepType`
  SET_KEYBOARD/CLEAR_KEYBOARD plus minimal valid keyboard fields from Task 1 (seed via repository
  like the other preview tests; if `seedFunnel` persists through the service, the step must pass
  Task 1 validation).

**Dependencies:** Task 1 (wave 1) — provides `StepType.SET_KEYBOARD`/`CLEAR_KEYBOARD`,
`FunnelStep` keyboard fields, `KeyboardRowDto`/`KeyboardButtonDto`, and the validation caps
(10 rows / 4 buttons / 64-char label) whose values this task's clamp must reuse — reference the
same constants in `FunnelService` (do not duplicate literals). No new packages.

**Edge cases:**
- `keyboardText` null/blank in the request — preview is non-validating: render null-tolerantly
  (same as `renderBlocks` renders null text) and still return one TEXT block; no 422.
- `keyboardRows` null or empty on a SET_KEYBOARD preview — echo null (mirror "no data" rather than
  inventing an empty structure); never NPE.
- Null elements inside rows / null buttons / null button text (DTO unknown-field tolerance) — skip
  nulls defensively, same idiom as `renderBlocks`/`renderMediaItems`.
- Oversized payload (rows >10, buttons/row >4, label >64) — clamp silently, 200 OK.
- Saved step is SET_KEYBOARD but the author is editing — the request body is the source of
  content; the saved step supplies only identity + type (existing gate semantics). A just-changed
  unsaved type renders per the OLD saved type — existing behavior, do not "fix".
- Unknown stepId / foreign funnel — existing 404 paths must keep precedence (anti-IDOR ordering:
  `requireFunnel` first).
- `keyboardParseMode` invalid/unknown string — preview is non-validating; pass it to the renderer
  as-is (renderer treats unknown parse modes as plain/null per its existing contract — verify in
  `VariableTemplateRenderer` before relying on it).

**Implementation hints:**
- Clamp = truncate, not reject: `rows.stream().limit(10)`, per row `buttons.limit(4)`, label
  `substring(0, min(64, len))` after null-filtering. Keep row/button order.
- Labels go into `List<List<String>>` raw — the ONLY transformation allowed is the clamp.
- The `kind="keyboard"` value is shared by BOTH new step types; the discriminator between them in
  the response is `keyboardRows` null vs non-null.
- Jackson serializes a null record component as `"keyboardRows": null` (or omits per config) —
  assert with the jsonPath form that matches actual serialization; check an existing null-field
  assertion in the IT for the project's idiom.
- Frontend mirror (`types/funnel.ts`, preview panel) is Task 5 — do not touch frontend files here.

**Security focus (for the security-auditor review):** clamping as unbounded-payload defense;
verbatim labels must never reach a render/escape bypass (frontend renders via `{{ }}` in Task 5);
anti-IDOR ordering in `previewStep` unchanged; `@JsonIgnoreProperties` mass-assignment defense
retained; no identity fields in the response.
