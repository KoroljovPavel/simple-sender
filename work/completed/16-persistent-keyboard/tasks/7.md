# Task 7: Manual smoke checklist (smoke.md)

## Required Skills

Before starting, load:

## Description

Author `work/16-persistent-keyboard/smoke.md` — the user's manual verification checklist for the
persistent-keyboard feature. Reply keyboards (`ReplyKeyboardMarkup`) render only in a real Telegram
client, and the "button → keyword funnel" links are a text convention the author assembles for
their own scenarios — so the final verification cannot be automated and is explicitly deferred to
the user (user-spec «Пользователь проверяет», tech-spec Agent Verification Plan, Task 11 note).
This checklist is what the user runs by hand with a real bot connected.

There is no staging deploy environment for this feature (user-spec «Ограничения»: code goes to
`main`, the author verifies everything manually) — the checklist targets a real bot connected to
the author's running instance, not a staging gate.

The deliverable itself is a user-facing document and MUST be written in Ukrainian (project language
policy: user-facing docs in Ukrainian). This task file is in English per the same policy (tech docs
in English).

The task depends on Task 3 (StepExecutor execution of both steps) because the checklist describes
runtime behavior — wire effects of SET_KEYBOARD/CLEAR_KEYBOARD, fire-and-forget CONTINUE semantics,
keyboard surviving execution completion — which must be settled (and may surface deviations in
decisions.md) before the manual procedure is written down.

## What to do

1. Read the source material: user-spec «Как должно работать», «Пользователь проверяет»,
   «Ограничения» (accepted keyword-mechanism properties), and the Task 3 entry in decisions.md
   (any execution-behavior deviations must be reflected in the checklist).
2. Study [docs/staging-smoke/09-subscribers.md](../../../docs/staging-smoke/09-subscribers.md) as
   the format precedent: title with estimated duration, intro paragraph explaining why this is
   manual, «Передумови», numbered «Кроки» with expected outcomes, «Чек-ліст результатів» mapped to
   acceptance criteria, «Cleanup», «Troubleshooting», «Sign-off» table, «Notes». Adapt the
   structure — this is a feature smoke checklist in `work/`, not a staging runbook, so drop
   staging-specific machinery (mongosh, email, staging URLs) and keep what fits a local run with a
   real bot.
3. Write `work/16-persistent-keyboard/smoke.md` in Ukrainian covering, in order, the scenario chain
   from user-spec «Пользователь проверяет»:
   - Prerequisites: running instance (backend + frontend), real bot connected (`CONNECTED`, webhook
     registered — ngrok for local), a Telegram account to act as subscriber.
   - Setup: author builds a main-menu funnel with a SET_KEYBOARD step (button rows incl.
     «Згенерувати бонус»-style button) and matching active keyword funnels; activate.
   - Check 1: trigger the menu funnel → message arrives and the persistent bottom keyboard is
     visible in the Telegram client; execution completes (`completed`) and the keyboard SURVIVES
     execution end (still visible after the funnel finishes).
   - Check 2: tap a keyboard button → its text arrives as a plain message → the matching keyword
     funnel starts.
   - Check 3 (bonus scenario end-to-end): the child keyword funnel sets its OWN keyboard via
     SET_KEYBOARD; the subscriber makes several moves (button taps driving keyword funnels);
     BOTH branches — success AND failure — end with SET_KEYBOARD restoring the main menu keyboard.
   - Check 4: a CLEAR_KEYBOARD step sends its mandatory text and removes the keyboard from the
     client (`remove_keyboard`).
   - Editor-side spot checks worth including: «Постійна» default on / «Сховати після натискання»
     default off; non-blocking amber hint next to a button whose text matches no active keyword
     funnel; preview panel renders text + keyboard mock.
4. Include a «Чек-ліст результатів» section (checkbox list) mapping each check to the user-spec
   intent, a short «Troubleshooting» section for the known accepted gotchas (see Edge cases below),
   and a «Sign-off» table (date, operator, result, notes) per the precedent.
5. Keep it practical and runnable: every step states the action and the expected observable result;
   no code blocks beyond optional curl/ngrok one-liners actually needed to run the check.

## Details

**Files:**

  per the 09-subscribers precedent, adapted from staging runbook to local-run feature smoke.

**Dependencies:**

  decisions.md entry for deviations.
- Informational: Task 2 (editor form labels, keyword hint) and Task 5 (preview panel) define the
  UI vocabulary referenced in editor-side spot checks; their decisions.md entries are available by
  wave 3 (Task 2 is wave 1; Task 5 runs in the same wave — if its entry is absent, describe the
  preview check from the tech-spec Task 5 description).

**Edge cases (accepted behaviors the checklist must flag as NOT bugs — source: user-spec
«Ограничения»/«Риски», tech-spec Risks):**
- Contains-match: free text containing a keyword also starts the funnel (e.g. «не хочу грати»
  triggers keyword «грати»).
- Menu precedence: while the subscriber's execution is parked on an inline menu
  (`waiting_for_reply`), keyword dispatch is suppressed — bottom-keyboard taps are ignored.
- Fan-out: one tap can start several keyword funnels at once.
- Dead button: keyword funnel deactivated after the keyboard was set → tap is a silent no-op.
- Repeat tap while the keyword funnel's execution is alive: `allowReEnter=false` → silent no-op;
  `true` → restart (re-enter guard).
- No keyboard stack/auto-restore: returning to the main menu only happens if the author put
  SET_KEYBOARD at the end of BOTH branches — a missing branch is an authoring mistake the bonus
  scenario check is designed to catch.

**Implementation hints:**
- Scope discipline: unlike 09-subscribers this is not a post-deploy staging gate — no mongosh
  verification legs, no email, no staging URL matrix. Keep prerequisites to: running app, connected
  real bot (webhook via ngrok for local), Telegram account, prepared funnels.
- The funnel-building setup steps (main menu funnel + keyword funnels + bonus branches) are part of
  the checklist's «Передумови»/first steps — the author builds them for their real scenario; give a
  concrete minimal example (e.g. main menu with «Згенерувати бонус», a bonus funnel with its own
  keyboard and success/failure branches) rather than abstract instructions.
- The decisive observations to phrase explicitly: keyboard remains visible AFTER the execution
  status becomes `completed` (fire-and-forget — the whole point of the feature), and
  CLEAR_KEYBOARD's message text arrives WITH the keyboard removal.
- `resize_keyboard` is hardcoded and invisible to the user — do not mention it as something to check.
- Keep the Sign-off table and results checklist from the precedent — they are how the user reports
  the run back.
