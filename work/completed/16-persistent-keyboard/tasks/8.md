## Description

Holistic full-feature code quality audit of `16-persistent-keyboard` after all implementation
waves complete (Tasks 1–7). The goal is to catch cross-component issues that are invisible when
reviewing tasks in isolation — the per-task reviewers (Tasks 1–6) each saw only their slice, while
this feature's correctness depends on contracts that span tasks and layers:

- **Validation mirror parity (Decision 6):** every backend rule in
  `validateSetKeyboard`/`validateClearKeyboard` must be mirrored byte-for-byte client-side in
  `FunnelStepForm.vue` — backend (Task 1) and form (Task 2) were built in parallel in Wave 1, so
  drift between the two is this feature's most likely cross-task defect.
- **`copyOf` completeness (tech-spec Risk 1, load-bearing):** a missed field silently drops the
  keyboard from execution snapshots and funnel duplication.
- **Builder/wire consistency (Decision 5):** the `reply_markup` Maps built in `StepExecutor` must
  match the verified Telegram wire shapes exactly (object-form buttons, hardcoded
  `resize_keyboard:true`, `remove_keyboard:true`).
- **Architectural consistency with Phases 1–6 patterns:** flat immutable records without `_class`,
  DTO mirrors wired in BOTH `toSteps` and `toStepDto`, the `*Touched` local-reactive-array form
  idiom, the send-step error-mapping trio, no `v-html`.

This is an Audit Wave task: the auditor IS the review — no separate reviewers, no new code. The
task only reads sources and writes an audit report with findings classified by severity
(critical / major / minor) per the code-reviewing methodology (11 review dimensions).

## Details

**Task nature:** read-only holistic audit. No code is written, no test suites are run (Task 11
Pre-deploy QA does that). The deliverable is the report.

**Report location:** `work/16-persistent-keyboard/logs/working/audit/code-auditor.json` — the
established convention from the completed 15-message-composer feature
(`work/completed/15-message-composer/logs/working/audit/code-auditor.json`). Markdown is
acceptable as a fallback (`code-audit.md` in the same directory); JSON with
severity/file:line/issue/recommendation per finding is preferred. Create the directory if missing.

**Dimensions in focus** (from the 11 code-reviewing dimensions, prioritized for this feature):
- **Cross-File Consistency** — the headline axis. Decision 6 validation rules vs the
  `FunnelStepForm.vue` mirror, rule by rule; `FunnelStep` ↔ `FunnelStepDto` ↔ `types/funnel.ts`
  field/type parity (incl. nullability); preview DTOs ↔ TS mirrors ↔ panel payload; positional
  `FunnelStepDto` ctor order vs the positional-order comment in `FunnelServiceEmitEventTest.emitStep`
  and all positional call sites.
- **Architecture** — flat immutable records without `_class` (`ContentBlock`/`Button` precedent);
  one shared `keyboardText`/`keyboardParseMode` pair for both types (Decision 3); fire-and-forget
  `cont()` with no park and no per-subscriber keyboard state (Decision 4); reply-button types
  distinct from the inline `Button` in TS.
- **Error Handling** — `StepExecutor` cases keep the send-step trio
  (`TelegramSendException → fromTerminalReason`, `BotTokenInvalidException →
  fail("invalid_bot_token")`, `AppException → fail(code)`); defensive terminal-fail guard for
  null/empty `keyboardRows` on a SET_KEYBOARD snapshot is present.
- **Separation of Concerns** — validation lives in `validateSteps` only (executor does not
  re-validate beyond the defensive guard); preview clamps echoed rows to the validation caps but
  does not duplicate full validation; hint logic stays client-side (Decision 8, no new endpoint).
- **Resource Management** — `TelegramSender` untouched, no second HTTP client, no new singletons;
  `VariableTemplateRenderer`/`renderTrimmed` reused, not duplicated.
- **Security (coarse cross-check only — depth belongs to Task 9):** no `v-html`; logs carry
  ids/codes only — never rendered text or button labels (PII rule, Task 3 scope); preview echoes
  labels verbatim but clamped. Record only gross violations here and reference Task 9.

**Key cross-component checks (what "done" looks like per file):**
- `FunnelStep.java` — 5 new nullable fields; `copyOf` carries all of them; `keyboardRows` →
  `new ArrayList<>(...)`, null-safe (tech-spec Risk 1: a missed field silently drops the keyboard
  from execution snapshots and duplication).
- `FunnelService.java` — Decision 6 rules complete, all via `invalidStep(...)` → 422
  `funnel_step_invalid` (one code, varying message); duplicate check on TRIMMED texts via
  `HashSet`; CLEAR_KEYBOARD symmetric strict rejection (no silently-ignored fields); button cap
  64 = keyword cap; `previewStep` branches on the SAVED step's type (Decision 7), labels NOT
  variable-rendered, rows clamped (≤10×≤4, label ≤64), `keyboardRows=null` for CLEAR_KEYBOARD.
- `StepExecutor.java` — Decision 5 shapes byte-exact vs the Data Models JSON; text through
  `renderTrimmed`; 6-arg `sendText`; returns `cont()` for both.
- `FunnelStepForm.vue` — `*Touched` local-reactive-array idiom (`menuButtons`/`blocks`
  precedent); defaults: «Постійна» on, «Сховати після натискання» off; no `resize_keyboard`
  control; keyword hint mirrors `containsAnyKeyword` over active keyword funnels
  (`subscribeInactiveHint` amber precedent); `onSubmit` preserves `id`/`next`.
- `FunnelMessagePreview.vue` — gate/payload/watch extended; keyboard mock without `v-html`;
  `{{ }}` interpolation only.
- Locale files — every new key in BOTH uk and en (prebuild parity gate).

**Dependencies:** Tasks 1–7 must be `done` (depends_on) — the audit reads the final state of the
codebase for this feature. No packages added.

**Edge cases to probe:**
- CLEAR_KEYBOARD step carrying `keyboardRows`/`isPersistent`/`oneTimeKeyboard` → rejected by
  backend AND blocked/never-emitted by the form.
- `copyOf` on a step with `keyboardRows = null` → null stays null (no NPE, no empty-list coercion).
- Preview request with >10 rows / >4 buttons / >64-char labels → clamped, never echoed unbounded.
- Variables in button labels: NOT rendered in preview (labels are the keyword link) — but
  `keyboardText` IS rendered.
- `isPersistent`/`oneTimeKeyboard` defaults live in the form only — backend stores what it gets
  (nullable), wire builder passes the stored values.

**Implementation hints:** start with the Verification greps (fast completeness signal), then read
by layers top-down (model → validation/DTO → executor → preview → frontend). Check every potential
finding against the corresponding tech-spec Decision — a deviation from a Decision with no
decisions.md deviation entry IS a finding. Do not duplicate the deep security audit (Task 9) or
the test-quality audit (Task 10) — record only gross violations in those areas with a pointer to
the profile task.
