# User Spec: 16-persistent-keyboard

## Что делаем

Додаємо **постійну нижню reply-клавіатуру** Telegram (`ReplyKeyboardMarkup` — НЕ inline-кнопки)
через два нові типи кроків воронки:

- **`SET_KEYBOARD`** — надсилає обов'язкове текстове повідомлення і встановлює підписнику нижню
  клавіатуру (ряди кнопок, опції "постійна" / "сховати після натискання");
- **`CLEAR_KEYBOARD`** — надсилає обов'язкове текстове повідомлення і прибирає клавіатуру
  (`remove_keyboard`).

Нового механізму розгалуження **немає**: тап по кнопці reply-клавіатури приходить у webhook як
звичайне текстове повідомлення і маршрутизується через **існуючі keyword-воронки Phase 3**
(contains-match). Зв'язка "кнопка → воронка" — текстова конвенція, підкріплена неблокуючою
підказкою в редакторі.

## Зачем

**Автор воронок** отримує постійне навігаційне меню бота: inline-меню (Phase 2/6) прокручується
разом із повідомленням і зникає з очей, а нижня reply-клавіатура завжди доступна під полем вводу
і переживає завершення execution. **Підписник** у будь-який момент має під рукою кнопки
навігації без пошуку останнього повідомлення з меню.

Конкретний сценарій автора (бонусна гра): головна клавіатура має кнопку «Згенерувати бонус» →
тап запускає keyword-воронку гри, яка ставить **свою** клавіатуру; підписник робить кілька ходів;
у кінці обох гілок (успіх і неуспіх) воронка знову ставить головну клавіатуру. Так збираються і
«нескінченні» меню-воронки, і скінченні сценарії (пройти тест тощо).

## Как должно работать

1. Автор у редакторі воронки додає крок `SET_KEYBOARD`: вводить текст повідомлення, додає ряди
   кнопок (до 10 рядів × до 4 кнопок), за потреби знімає/ставить чекбокси «Постійна» (default on)
   і «Сховати після натискання» (default off).
2. Біля кнопки, текст якої не матчить жодну активну keyword-воронку, редактор показує
   **неблокуючу** підказку-попередження (рахується на клієнті зі store воронок).
3. Прев'ю-панель показує відрендерений текст кроку (через той самий `VariableTemplateRenderer`,
   що й движок) і список кнопок.
4. Підписник, дійшовши до кроку, отримує повідомлення і бачить постійну клавіатуру знизу.
   Execution **не паркується** — крок fire-and-forget, воронка йде далі (`CONTINUE`).
   Клавіатура лишається в чаті після завершення execution.
5. Тап по кнопці надсилає її текст як звичайне повідомлення → існуючий keyword-dispatch запускає
   відповідну keyword-воронку (fan-out можливий — це поведінка Phase 3).
6. Крок `CLEAR_KEYBOARD` надсилає текст (наприклад «Меню сховано») і прибирає клавіатуру.
7. «Повернення до головного меню» — авторський патерн: у кінці гілок дочірньої воронки ставиться
   `SET_KEYBOARD` з головним меню. Стеку/авто-відновлення клавіатур у движку немає.

## Критерии приёмки

- [ ] Автор може додати крок `SET_KEYBOARD` у редакторі: текст (≤4096 символів, змінні
  `{user.*}`/`{custom.<key>}`, `parse_mode`), до 10 рядів × до 4 кнопок, текст кнопки ≤64 символи.
- [ ] Дублікати текстів кнопок в одній клавіатурі блокуються валідацією (422 `funnel_step_invalid`
  + дзеркальна перевірка у формі).
- [ ] Форма має два чекбокси: «Постійна» (`is_persistent`, default on) і «Сховати після
  натискання» (`one_time_keyboard`, default off); `resize_keyboard` завжди true (не показується).
- [ ] Виконання кроку `SET_KEYBOARD` надсилає `/sendMessage` з тілом, що містить
  `reply_markup.keyboard` (ряди кнопок), `is_persistent`, `resize_keyboard: true`,
  `one_time_keyboard` (перевіряється engine IT через MockWebServer); execution після кроку
  продовжується (`CONTINUE`) і завершується `completed`, а НЕ паркується у `waiting_for_reply`.
- [ ] Виконання кроку `CLEAR_KEYBOARD` надсилає `/sendMessage` з обов'язковим текстом і
  `reply_markup.remove_keyboard: true` (engine IT); execution продовжується.
- [ ] Тап по кнопці запускає keyword-воронку, чий keyword матчить текст кнопки (інтеграційний
  тест: text-повідомлення у webhook → keyword dispatch → створено execution; існуючий шлях,
  без змін у webhook/dispatcher).
- [ ] Повторний тап по кнопці, поки execution keyword-воронки ще живий: при
  `allowReEnter=false` — тихий no-op, при `true` — рестарт (існуюча семантика re-enter guard).
- [ ] У редакторі біля кнопки без активної keyword-воронки під її текст показується неблокуюче
  попередження.
- [ ] Прев'ю (бекенд endpoint + фронтова панель) рендерить обидва нові кроки: текст через
  `VariableTemplateRenderer` + кнопки списком.
- [ ] Помилки відправки на нових кроках мапляться як в усіх send-кроків: `BLOCKED_BY_USER` /
  `CHAT_NOT_FOUND` → execution `cancelled`; інші помилки Telegram → `failed`;
  `invalid_bot_token` → `failed` (unit-тест на `StepExecutor`).
- [ ] Обидва кроки проходять через `FunnelStep.copyOf` без втрат: нові поля присутні у snapshot
  execution та в результаті duplicate (unit-тест).
- [ ] Порожній/пробільний текст кнопки відхиляється валідацією (422 + дзеркало у формі).
- [ ] Усі нові рядки UI — через i18n (`uk` + `en`, parity gate проходить).

## Ограничения

- `reply_markup` у Telegram прикріплюється лише до повідомлення → обидва кроки надсилають
  обов'язковий текст.
- Ліміти: ≤10 рядів, ≤4 кнопки в ряду, текст кнопки ≤64 (= кап keyword, щоб текст кнопки завжди
  міг бути точним keyword'ом).
- Свідомо прийняті властивості keyword-механізму (автор перевірить на реальних воронках і дасть
  фідбек):
  - **contains-match**: вільний текст підписника, що містить keyword, теж запустить воронку;
  - **menu precedence**: поки execution підписника запаркований на inline-меню
    (`waiting_for_reply`), keyword-dispatch придушений — тапи по нижній клавіатурі ігноруються;
  - **fan-out**: один тап може запустити кілька keyword-воронок.
- «Мертва кнопка» (keyword-воронку деактивували після створення клавіатури) — тихий no-op у
  рантаймі; захист лише авторською підказкою в редакторі.
- Помилки відправки обробляються існуючим маппінгом `StepExecutor` (як у всіх send-кроків):
  підписник заблокував бота (`BLOCKED_BY_USER`) або чат не знайдено (`CHAT_NOT_FOUND`) →
  execution `cancelled`; інші помилки Telegram → `failed`; невалідний токен бота
  (`invalid_bot_token`) → `failed`. Нічого специфічного для клавіатурних кроків не додається.
- Порожній відрендерений текст (повідомлення з однієї незаповненої змінної) — той самий шлях, що
  й у `MESSAGE`: помилка Telegram → той самий маппінг (окремої валідації не робимо).
- Спостережуваність — існуюча: `TelegramSender` пише audit-події `telegram_message_sent` /
  `telegram_send_failed` для кожної відправки; нових логів/метрик не додаємо.
- Стеку клавіатур / авто-відновлення попередньої немає — повернення тільки авторським патерном.
- Reply-клавіатура рендериться лише в реальному Telegram-клієнті → фінальна перевірка ручна.
- Деплой-середовища немає: код іде в `main`, автор перевіряє все вручну. Міграцій немає —
  нові поля nullable, існуючі воронки не зачіпаються.

## Риски

- **Риск 1:** `FunnelStep.copyOf` не пронесе нові поля → клавіатура мовчки зникне зі snapshot
  execution та з duplicate. **Митигация:** окремі unit-тести на `copyOf` для нових полів
  (відзначено як load-bearing у code-research).
- **Риск 2:** Хибні спрацювання contains-match на вільному тексті (підписник написав «не хочу
  грати» — запустилась воронка з keyword «грати»). **Митигация:** прийнято свідомо; автор
  тестує на реальних воронках; точніший матчинг — кандидат на наступні фази.
- **Риск 3:** Тапи по клавіатурі ігноруються, поки підписник запаркований на inline-меню
  (menu precedence). **Митигация:** прийнято і задокументовано; авторам не рекомендується
  змішувати inline-парковку з постійним меню в одному флоу.
- **Риск 4:** Підказка редактора вводить в оману, якщо автор перейменував кнопку після
  зв'язування. **Митигация:** підказка рахується наживо зі store і неблокуюча by design.
- **Риск 5:** Wire-формат `reply_markup` (ReplyKeyboardMarkup/Remove) розійдеться з актуальним
  Telegram Bot API. **Митигация:** звірити payload з документацією API на етапі tech-spec
  (Context7) + інтеграційні тести на тіло `/sendMessage`.

## Технические решения

- Ми вирішили зробити **два нові типи кроків** (`SET_KEYBOARD`/`CLEAR_KEYBOARD`), а не вішати
  reply-клавіатуру на `MESSAGE`-композер, бо inline-кнопки `MESSAGE` зчеплені з парковкою
  `waiting_for_reply` — протилежна семантика (reply-клавіатура fire-and-forget).
- Ми вирішили **не робити нового механізму розгалуження**: тапи маршрутизуються існуючими
  keyword-воронками Phase 3. «Клавіатура + keyword-воронки» достатньо.
- Ми вирішили **не робити стек/авто-відновлення клавіатур** — повернення до головного меню є
  авторським патерном (SET_KEYBOARD у кінці гілок), без стану на підписника.
- Зв'язка «кнопка → воронка» — **текстова конвенція + неблокуюча підказка** в редакторі
  (варіант B), рахується на клієнті зі store воронок; нового endpoint не потрібно.
- Кроки — **fire-and-forget** (`Outcome.CONTINUE`), ніколи не паркують execution.
- `TelegramSender` **не змінюється**: 6-аргументний `sendText` вже приймає довільний
  `Object replyMarkup`; нові Map-білдери живуть у `StepExecutor`.
- Текст кроку — **одне текстове поле** (не блоки-композер) зі змінними та `parse_mode`, ліміт
  4096 — як TEXT-блок.
- `resize_keyboard` захардкоджено `true`; авторові показуються лише `is_persistent` і
  `one_time_keyboard`.
- Капи: ≤10 рядів × ≤4 кнопки, текст кнопки ≤64, дублікати кнопок блокуються.
- Прев'ю розширюється на обидва кроки (бекенд рендер + фронтова панель), а не placeholder.
- Міграцій немає — нові nullable-поля на embedded `FunnelStep` (flat, без `_class`).
- Точна модель зберігання рядів кнопок (list-of-lists vs typed record) і можливі майбутні поля
  кнопки (`request_contact` тощо) — рішення рівня tech-spec; зараз кнопка має лише текст.

## Тестирование

**Unit-тесты:** делаются всегда, не обсуждаются. Ключові: `StepExecutor` (Map-білдери
`keyboard`/`remove_keyboard`, outcome CONTINUE, error mapping), `FunnelService.validateSteps`
(капи, дублікати, обов'язковий текст), `FunnelStep.copyOf` (нові поля + defensive copy рядів).

**Интеграционные тесты:** делаем — slow-lane (`@Tag("slow")`, `FunnelExecutionEngineIT`):
повний цикл sweep → реальне тіло `/sendMessage` через MockWebServer з assert на
`reply_markup.keyboard` / `is_persistent` / `one_time_keyboard` / `remove_keyboard`.

**E2E тесты:** не делаем — фронт покривається Vitest-спеками форми кроку та прев'ю
(за патернами `FunnelStepForm.composer.spec.ts`); reply-клавіатура все одно рендериться лише
в реальному Telegram-клієнті.

| 5. Locale parity | `pnpm build` (prebuild gate) | Parity gate проходить (uk/en) |

### Пользователь проверяет

- За чеклістом `work/16-persistent-keyboard/smoke.md` (створюється в рамках фічі — артефакт
  процесу): підключений реальний бот → активувати меню-воронку з SET_KEYBOARD → **побачити
  постійну клавіатуру в Telegram-клієнті, що лишається після завершення execution** → тап по
  кнопці запускає keyword-воронку → **бонусний сценарій end-to-end** (своя клавіатура в
  дочірній воронці, кілька ходів, повернення до головного меню в обох гілках) →
  CLEAR_KEYBOARD прибирає клавіатуру. Потрібно руками, бо reply-клавіатура рендериться лише в
  реальному клієнті, а keyword-зв'язки автор збирає під свої реальні сценарії.
