# Task 1: Domain model `List<Trigger>` + denormalized `onStartTriggerValue` + index shape

## Required Skills

Перед выполнением задачи загрузи:

## Description

Phase 8 (фіча `17-funnel-multi-entry`) переводить воронку з одного плоского тригера на **`List<Trigger>`**.
Ця задача — фундамент усієї фічі: вона змінює domain-шар і форму індексу так, щоб усі наступні задачі
(repository, DTO, сервіс-валідація, рушій, фронт) мали на що спиратися.

Зараз `Funnel` тримає плоску трійку тригера — `triggerType` / `triggerValue` / `keywords` (рядки L72-79),
а класова анотація `@CompoundIndexes` містить partial-unique індекс
`projectId_triggerType_triggerValue_unique_active` (L35-38) із static-блоковими літеральними
assertion'ами (L47-58), які захищають partial-filter літерали `'active'` та `'on_start'` від тихого
перейменування.

Треба:
1. Створити **новий embedded POJO `Trigger`** — `(triggerType, triggerValue, keywords, entryStepId)`,
   плоский, без `_class`-дискримінатора (як `FunnelStep` — Decision 12 попередніх фаз).
2. У `Funnel` **прибрати плоску трійку** і додати `List<Trigger> triggers` + денормалізований nullable
   скалар `String onStartTriggerValue` (Decision 6 / Variant A).
3. **Замінити форму індексу**: прибрати старий `projectId_triggerType_triggerValue_unique_active` і
   покласти unique partial `{projectId:1, onStartTriggerValue:1}` з фільтром
   `{ status:'active', onStartTriggerValue:{$exists:true} }`; оновити static-блокові літеральні
   assertion'и під нові partial-filter-літерали.

Результат: funnel-домен **компілюється** з мульти-тригерною моделлю і новою анотацією індексу. Жодної
логіки синку `onStartTriggerValue` тут немає (її пише Task 4 у `FunnelService`); тут лише форма даних,
геттери/сеттери і форма індексу. `FunnelExecution` НЕ чіпаємо.

   для keyword-тригерів; `triggerValue` = "" для `on_start`) і що `Trigger` snapshot-irrelevant

## Details

**Files:**
- `backend/src/main/java/com/botfunnel/funnel/Trigger.java` (NEW) — embedded POJO, плоский, no `_class`,
  no bean-validation, no Spring annotations. Дзеркалити стиль `FunnelStep` (коментар про призначення
  полів + чисті get/set).
- `backend/src/main/java/com/botfunnel/funnel/Funnel.java` (MODIFY):
  - L72-79 — прибрати `triggerType`/`triggerValue`/`keywords`; додати `List<Trigger> triggers` +
    `String onStartTriggerValue`.
  - L101-111 — прибрати `getTriggerType/setTriggerType/getTriggerValue/setTriggerValue/getKeywords/setKeywords`;
    додати get/set для `triggers` і `onStartTriggerValue`.
  - L35-38 — замінити `@CompoundIndex` на форму нижче.
  - L47-58 — оновити static-блок (лишити `active`-assertion, прибрати `on_start`-assertion).
  - L11-30, L42-46 — оновити коментарі під нову форму.

**Точна форма нового індексу (Decision 6):**
```
@CompoundIndex(name = "projectId_onStartTriggerValue_unique_active",
        def = "{'projectId': 1, 'onStartTriggerValue': 1}",
        unique = true,
        partialFilter = "{ 'status': 'active', 'onStartTriggerValue': { '$exists': true } }")
```
Звіряй точний синтаксис partialFilter з тим, як Spring Data MongoDB очікує `$exists` у JSON-літералі —
дивись наявний робочий приклад partialFilter у поточному `Funnel`/у `FunnelExecution` анотаціях і, за
потреби, перевір у Context7 (`spring-data-mongodb`, partial index `$exists`).

**Dependencies:** немає (Wave 1, `depends_on: []`). Наступні задачі (2 repository, 3 DTO, 4 service)
залежать від цього кроку.

**Edge cases:**
- `onStartTriggerValue` має бути nullable і **не входити в індекс**, коли null (тому `$exists:true` у
  partialFilter) — інакше всі воронки без on_start-значення колізіонуватимуть на `null`.
- `triggerValue` для `on_start` = `""` (порожній рядок, не null) — синк значення в `onStartTriggerValue`
  робить Task 4, але форма поля має це дозволяти.
- Static-блок: НЕ лишай `on_start`-assertion — новий partialFilter його літерала не містить, тож
  assertion був би мертвим і вводив би в оману.

**Implementation hints (НЕ псевдокод):**
- `Trigger` — плоский POJO як `FunnelStep`: no-args конструктор, поля + get/set, без `@Document`. Spring
  Data серіалізує його як вкладений документ у масиві `triggers` без `_class`, бо тип поля статично
  відомий (`List<Trigger>`).
- Не додавай тут логіку синку/валідації — лише форма даних. `applyTrigger`/`duplicate`/`checkTriggerConflict`
  у `FunnelService` (рядки ~177-178, 282-285, 337-344, 611-639) і
  `FunnelRepository.findByProjectIdAndTriggerTypeAndTriggerValueAndStatus` все ще посилаються на старі
  поля; їх перероблюють Task 2-4.
- **Межі compile-green цього кроку:** якщо `./gradlew compileJava` упаде на `FunnelService` /
  `FunnelRepository` / DTO через зниклі геттери — це **очікувано** і це зона наступних задач. Цей крок
  гарантує насамперед, що `Funnel.java` + `Trigger.java` коректні й мають форму, на яку зможуть спертися
  Task 2-4, і що тести якоря (`TriggerTest`, `FunnelIndexAssertionsTest`, `FunnelTriggersFieldTest`)
  зелені. Якщо оркестратор вимагає, щоб весь модуль компілювався після Wave 1 окремими файлами —
  узгодь це: можливий мінімальний тимчасовий заглушковий шар тільки в тому, що Task 2-4 повністю
  перепишуть, із записом у decisions.md як технічний борг кроку. За замовчуванням тримай зміну строго в
  межах двох цільових файлів.
- TDD-тести моделюй за `FunnelStepTest` (AssertJ, JUnit 5) і `FunnelStatusEnumTest` (літеральні
  assertion'и). Для reflection-перевірки індексу читай
  `Funnel.class.getAnnotation(CompoundIndexes.class).value()` і перебирай `@CompoundIndex` по `name()`.
