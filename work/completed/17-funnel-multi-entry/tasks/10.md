## Description

Full-feature **test-quality audit** for `17-funnel-multi-entry` (Epic 8 — Phase 8, multi-entry graph model). This is the third member of the Audit Wave: you ARE the review (no downstream reviewers), so the audit report is the deliverable.

The feature replaces the flat trigger trio on `Funnel` with a `List<Trigger>` (each trigger carrying its own `entryStepId`), adds a redirect-or-start dispatcher and a new engine `redirectExecution` method, reshapes the `on_start` uniqueness index into a denormalized `onStartTriggerValue` partial-unique index, and adds a frontend Triggers panel. The change class is exactly the one the project relies on integration tests to protect: the execution engine, a concurrent claim/CAS, and Mongo indexes (user-spec "Тестирование" — "саме той клас змін, де ITs ловлять регресії, а unit не дістає").

Read every test file created or modified across tasks 1-7, hold them against the tech-spec Testing Strategy and the user-spec acceptance criteria, and judge two things: **coverage** (is every required branch and risk actually exercised) and **quality** (are the assertions meaningful, is the test-pyramid balance right — unit vs slow-lane IT vs frontend component). Produce a JSON audit report at `work/17-funnel-multi-entry/logs/working/audit/test-auditor.json`.

This is an audit, not a fix task: you read and judge, you do not modify production or test code. Concrete, file-and-test-name-anchored findings with severity are the output.

2. Audit **coverage** against the tech-spec Testing Strategy and user-spec ACs. For each required behaviour below, record covered / partial / missing with the exact test name (or its absence):
   - Redirect branch: in-flight `running`/`waiting`/`waiting_for_reply` redirected, park (`waiting_for_reply`) cleared, cursor moved to `entryStepId`.
   - Start branch: fresh start at `entryStepId`; `allowReEnter` honoured on `completed`/`cancelled`/`failed` runs (false → no-op, true → cancel-then-insert).
   - "One execution" invariant (Decision 2): redirect mutates the existing row and inserts NO second `funnel_executions` document.
   - CAS-loss best-effort no-op (Decision 4): asserts the row is untouched AND the greppable WARN is emitted (not merely a boolean return).
   - Broken-cursor isolation (Decision 5): `entryStepId` absent from `stepsSnapshot` terminal-fails ONLY that execution; sweep + other executions continue.
   - Anti-IDOR: mismatched-subscriber redirect is a no-op (Decision 3).
   - Cross-funnel isolation + one-event-matches-two-funnels: each funnel decided independently within the fan-out ceiling.
   - `EMIT_EVENT`→trigger self-loop terminates at the per-tick budget / human-press gate (US Risk 4 as a regression gate).
   - Index reshape: `onStartTriggerValue` partial-unique shape present at runtime; reconciliation retires the old index without `IndexKeySpecsConflict`; idempotent re-boot NO-OP.
   - Trigger validation 422s: duplicate `event_name`, intra-funnel "at most one on_start" vs cross-funnel duplicate on_start value (distinct cases), dangling `entryStepId`, over-cap trigger array, multiple triggers → same entry step allowed; `List<TriggerDto>` round-trips PATCH/GET.
   - `onStartTriggerValue` sync + `duplicate()` resets triggers/clears the value.
   - Entry points: API event redirects/starts; `handleStart`→`fire` enrolls via the new `onStartTriggerValue` lookup.
   - Frontend panel: add/delete trigger, entry-step pick, duplicate-event-name client guard, uk/en i18n parity (no empty keys).
3. Audit **assertion quality**. Flag tests that assert only counts/statuses where the spec demands wire-body/state assertions (the project explicitly raised the engine ITs to wire-body assertions — see patterns.md Decision 9). For CAS-loss specifically, verify the test asserts BOTH untouched-state AND the WARN (`ListAppender<ILoggingEvent>` filtered by logger + level, per the project's split-per-site idiom), not a bare boolean. Flag PII in asserted log lines (WARN must carry ids/codes only, never `event_name`/`triggerValue`).
4. Audit **test-pyramid balance** (test-master). Confirm engine/concurrency/index behaviour sits in slow-lane ITs (not faked in unit), validation/DTO logic sits in unit + controller IT (not pushed needlessly into slow ITs), and the frontend panel sits in component/page specs (no E2E — matching every prior funnel phase). Flag over-reliance on slow ITs for pure logic, or unit tests that mock away the very concurrency/index behaviour under test (no DB mocking in ITs — patterns.md Testing Requirements).
5. Check the slow-lane discipline: engine ITs are `@Tag("slow")` and only run under `-PrunSlow=true`; flag any load-bearing redirect/CAS invariant that landed outside the slow lane (would silently skip in the default `./gradlew test`).
6. Write the audit report to `work/17-funnel-multi-entry/logs/working/audit/test-auditor.json` (JSON format). Structure: summary verdict (pass / pass-with-findings / fail), a coverage matrix (required behaviour → covered/partial/missing → test name), a findings list (each: severity critical/major/minor, the test file + test name or the gap, why it matters, concrete suggested fix), and a pyramid-balance assessment. Anchor every finding to a file and test name. Do not modify any test or production code.

## Details

<!-- All details for task execution — technical, organizational, any other. -->

**Output (the only file you write):** `work/17-funnel-multi-entry/logs/working/audit/test-auditor.json` (JSON format) — create the `logs/working/audit/` directory if missing.

**Scope:** READ-ONLY for all code. You read test files and the specs and write ONE JSON report. Do not edit, add, or delete any test or production file. Do not add missing tests — record them as findings for the implementing/QA waves to act on.

**What "covered" means here:** a behaviour is covered only if an existing test actually asserts it. A test that drives the path but asserts only a return boolean or a status count, where the spec demands state/wire-body (e.g. CAS-loss must assert untouched row + WARN), is "partial", not "covered".

**Project test conventions to hold the tests against (patterns.md):**
- Engine ITs are `@Tag("slow")`, excluded from the default `./gradlew test`, run with `-PrunSlow=true`. Load-bearing redirect/CAS/snapshot invariants MUST live there, not in the default lane and not faked in unit tests.
- No DB mocking in integration tests — real embedded/Testcontainers Mongo. Skeleton/security-only tests may mock connection factories (Epic 01 exception only).
- Log-assertion idiom: `ListAppender<ILoggingEvent>` split per log site, filtered by logger name AND level — a single combined assertion masks which site leaked. CAS-loss and broken-cursor WARN/marker assertions should follow this.
- WARN/marker lines must carry ids/codes only — never `event_name`/`triggerValue`/PII (anti-log-injection, Phase-5 precedent). Flag any test asserting a log line that contains PII (and, by extension, code that would emit it).
- Race-condition IT idiom: `ConcurrencyTestUtils.parallelInvoke` + `CountDownLatch` barrier for index-uniqueness races (relevant to the `onStartTriggerValue` partial-unique index and cross-funnel duplicate on_start).
- Frontend: component/page specs only, no E2E for the trigger panel; i18n parity (uk/en, no empty keys) asserted in the component spec.

**Edge cases the audit must explicitly look for (likely-missed):**
- CAS-loss asserted as a bare boolean instead of untouched-state + WARN.
- Broken-cursor IT that fails the execution but does NOT assert the sweep / sibling executions survive.
- "One execution" invariant tested by status only, not by counting `funnel_executions` documents before/after.
- Cross-funnel isolation / two-funnels-one-event scenarios entirely absent (these are easy to forget).
- Self-loop termination (US Risk 4) only checked live, never as an IT regression gate.
- Cross-funnel duplicate on_start value collapsed with the intra-funnel "at most one on_start" case instead of being a distinct test.
- Redirect/CAS invariant accidentally landed outside `@Tag("slow")` (would skip in default lane).
- Frontend i18n parity not actually asserted (no empty-key check).

**Severity guidance:** critical = a required risk/AC behaviour has no test at all, or a slow-lane invariant would silently skip; major = behaviour driven but assertion too weak to catch the regression, or wrong pyramid layer; minor = naming/duplication/readability, redundant coverage.

**Dependencies:** Tasks 1-7 complete (all production + test code for the feature exists). This task does not depend on Tasks 8 (code audit) or 9 (security audit) — the three audits run in parallel in the Audit Wave.

**Implementation hints:** Start from the tech-spec Testing Strategy bullet list and the user-spec AC checklist — each line maps to a row in your coverage matrix. Use `grep` for greppable markers/WARN strings to confirm a log-assertion test actually targets the right site. Use `grep` for `@Tag("slow")` and `-PrunSlow` to confirm slow-lane placement.
