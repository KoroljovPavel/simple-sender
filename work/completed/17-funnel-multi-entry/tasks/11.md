## Description

Приёмочное тестирование фичи `17-funnel-multi-entry` перед деплоем. Это финальный gate
после аудитов (Tasks 8/9/10): нужно прогнать все автоматические лейны и проверить, что
**каждый** критерий приёмки — пользовательский (user-spec) и технический (tech-spec) —
действительно выполняется на текущем коде.

Фича затрагивает руший выполнения (redirect/start, claim-CAS), индексы Mongo и фронтенд
панель тригеров, поэтому проверка состоит из трёх частей:
1. **Автоматические лейны** — полный backend-прогон, включая `-PrunSlow=true` engine-ITs и
   index-ITs, плюс frontend test (`pnpm test`) и i18n parity (uk/en) через `node scripts/check-locales.mjs`.
2. **Agent Verification Plan (curl/bash)** — реальный `curl` против
   `POST /api/integrations/v1/events` (new-subscriber → старт в середину воронки) и bash-сценарий
   `/start` → `waiting_for_reply` → событие тригера → проверка, что тот же `funnel_executions`-рядок
   перекинул курсор и снял парк.
3. **Сверка критериев приёмки** — пройтись по всем AC из user-spec («Критерии приёмки») и tech-spec
   («Acceptance Criteria»), отметить выполнено / не выполнено / отложено.

Результат — QA-отчёт в `logs/working/task-11/` с вердиктом PASS/FAIL по каждому критерию.
Критерии, которые требуют живого окружения (живая петля Telegram, ручной wipe + чистый старт),
**не проверяются здесь** — они отложены на Task 12 (post-deploy) и должны быть явно помечены
как deferred в отчёте.

## Acceptance Criteria to verify (sources of truth)

**Из user-spec («Критерии приёмки»):**
- Воронка хранит несколько тригеров; каждый `event`-тригер имеет свою назву события и свой entry-крок; одно-тригерная воронка работает как до фичи.
- `on_start`-вход остаётся главным (entry = первый шаг), ведёт воронку с начала.
- `event`-тригер можно привязать к любому существующему шагу; событие заводит подписника именно на этот шаг (вход в середину).
- Две одинаковые назвы события → 422 + бизнес-код; несколько тригеров на один entry-шаг — разрешено и сохраняется.
- Событие для подписника, который **уже бежит** воронку → его выполнение продолжается с гілки тригера (парк меню снят), второго выполнения не появляется.
- Событие для подписника **вне** воронки (вкл. `completed`/`cancelled`/`failed`) → новое выполнение с entry-шага, но только если разрешает `allowReEnter`.
- Redirect ведёт по **снимку** воронки; цели нет в снимке → фейлится только это выполнение, остальные + sweep работают.
- Race с sweep → best-effort no-op + greppable WARN, состояние не портится.
- Петля «кнопка → `EMIT_EVENT` → тригер → redirect» не зацикливается на сервере. *(серверный backstop через IT; живая петля — DEFERRED → Task 12)*
- Приложение стартует без `IndexKeySpecsConflict` на чистую/витерту базу; ограничение «один активный `on_start` на (проєкт, тригер)» в силе. *(чистый старт на живом окружении — DEFERRED → Task 12)*
- Редактор: панель «Тригери» позволяет add/delete `event`-тригеры и выбрать entry-крок; сохраняется с воронкой.
- Подписи панели «Тригери» — активной локаллю (uk/en), без пустых ключей.

**Из tech-spec («Acceptance Criteria»):**
- PATCH/GET round-trips `List<TriggerDto>`; невалидные payload → 422 + бизнес-код (duplicate `event_name`, dangling `entryStepId`).
- `onStartTriggerValue` unique partial index создан на чистой/витертой базе; старт без `IndexKeySpecsConflict`; reconciliation APPLIED / NO-OP.
- `redirectExecution` мутирует существующий row (без второго выполнения); CAS-loss → no-op + greppable WARN, состояние intact.
- Broken-cursor redirect фейлит только затронутое выполнение; sweep и остальные продолжают.
- Все backend slow-lane engine-ITs + index-ITs зелёные; frontend `pnpm test` + i18n (uk/en) parity (`node scripts/check-locales.mjs`) зелёные.
- Нет регрессий в существующих funnel-тестах.

## Verification Steps

### Automated

Backend (cwd `backend/`):
- `cd backend && ./gradlew test -PrunSlow=true --tests '*FunnelExecutionEngineIT'` → redirect/start/allowReEnter/broken-cursor/CAS-loss/no-second-execution зелёные
- `cd backend && ./gradlew test --tests '*FunnelTriggerIndexReconciliationIT' --tests '*FunnelIndexesIT'` → reshape без `IndexKeySpecsConflict`, reconciliation APPLIED
- `cd backend && ./gradlew test --tests '*FunnelServiceTriggerTypeTest' --tests '*FunnelControllerIT'` → валидация тригеров + DTO round-trip зелёные
- `cd backend && ./gradlew test --tests '*EventsControllerIT' --tests '*ProcessTelegramUpdateJobTest'` → entry-points (API-событие, on_start, EMIT_EVENT) зелёные
- `cd backend && ./gradlew test -PrunSlow=true` → полный прогон (включая slow-lane), без регрессий

Frontend (cwd `frontend/`):
- `cd frontend && pnpm test tests/pages/funnel-editor.spec.ts` → панель тригеров: add/delete, entry-step pick, duplicate-event-name guard
- `cd frontend && pnpm test` → полный frontend-прогон зелёный
- `cd frontend && node scripts/check-locales.mjs` → i18n (uk/en) parity без пустых ключей

### Smoke

Agent Verification Plan (tools: `curl`, `bash`) — выполняются против локально запущенного backend:

- **API-событие → старт в середину воронки.** `curl -X POST <base>/api/integrations/v1/events` с заголовком `X-API-Key` и телом `{event_name, telegram_user_id}` для подписника, которого нет в воронке. Ожидание: 202; создаётся `funnel_executions`-выполнение с `currentStepId` = entry-крок тригера (проверить через Mongo / API).
- **Событие перекидает in-flight выполнение.** Bash-сценарий: `/start` → дождаться `waiting_for_reply` на меню → послать событие тригера. Ожидание: **тот же** `funnel_executions`-рядок — `currentStepId` сменился на гілку тригера, парк (`waiting_for_reply`) снят, шаг выполнен; второго выполнения не появилось.

(Точные base-URL, `X-API-Key`, способ поднять backend локально и читать Mongo — см. deployment.md / project.md. Если поднять живой backend в QA-окружении невозможно, пометить эти два smoke-сценария DEFERRED → Task 12 и зафиксировать причину в отчёте.)
