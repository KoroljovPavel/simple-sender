## Description

Live-environment verification on the **first available environment**. Deployment via CI/CD is TBD — there is no pipeline or staging/production environment yet (`deployment.md` → Platform/CI/CD: TBD), so this task has **no standalone Deploy predecessor**. It runs on whatever environment is first reachable (typically local-staging: `docker compose -f infra/docker-compose.yml up -d` + `./gradlew bootRun` + a throwaway BotFather bot over ngrok, the same shape every prior funnel phase used for its post-deploy check).

This task closes the two things automated lanes (Task 11) deliberately could not cover:

1. **The one-time manual data wipe + clean engine startup** (tech-spec Decision 8 "wipe, not migrate"; user-spec "Как должно работать" step 6). The Phase-8 schema change replaces `Funnel`'s flat trigger trio with `List<Trigger>` + denormalized `onStartTriggerValue`, and reshapes the trigger index. Pre-Phase-8 `funnels`/`funnel_executions` documents are schema-incompatible and there is no backfill migration. The collections must be wiped manually, then the engine must boot clean — index reconciliation logs APPLIED with no `IndexKeySpecsConflict`, and the sweep comes up with no snapshot-deserialization errors.

2. **The live Telegram redirect loop**, which no agent can reproduce without a real bot (webhook ↔ engine ↔ Telegram round-trip). This is the user-spec "Пользователь проверяет → Жива петля в Telegram" check, executed here via Telegram MCP plus a `curl` API-event check.

The verification result (the post-deploy report) **is** the review — there are no separate reviewers for this task.

## What to do

**SAFETY FIRST — the wipe is a destructive, GUARDED operation.** Before issuing any drop/clear command:
- Confirm the target connection string points at the **intended non-production environment** (not a prod/shared DB). Echo back the resolved `MONGODB_URI` host/db name and the environment name, and get explicit confirmation before proceeding.
- Confirm the **"no production data" precondition** holds (tech-spec Decision 8 — this feature was authored on the premise that there is no production data; the wipe is only safe under that premise).
- If either guard cannot be satisfied, **stop and report** — do not run the wipe.

Then:

1. **Manual wipe (guarded).** On the confirmed non-prod target, drop/clear the `funnels` and `funnel_executions` collections (the Phase-6 precedent in `deployment.md` → Startup Migrations).
2. **Verify clean startup.** Start (or restart) the backend against the wiped DB. Grep the startup log: trigger-index reconciliation logs **APPLIED** (first migrating boot) and the app starts with **no `IndexKeySpecsConflict`** (error 86). Confirm the `onStartTriggerValue` partial-unique index exists at runtime and the `FunnelExecutionEngine` sweep comes up with **no snapshot-deserialization errors**. `GET /health` returns `{"status":"ok"}`.
3. **Build the live funnel.** In a real bot, author a funnel with: a `MESSAGE` step containing a menu button whose branch hits an `EMIT_EVENT` step emitting `SOME_TRIGGER`, plus an `event` trigger (`SOME_TRIGGER`) whose `entryStepId` points at a downstream message step. Activate the funnel.
4. **Live redirect loop (Telegram MCP).** Do `/start`, wait for the funnel to park at the menu (`waiting_for_reply`), press the button. Confirm the bot **drives onto the trigger branch**: the same in-flight `funnel_executions` row is redirected (`currentStepId` = the trigger's `entryStepId`, park cleared, the trigger-branch message delivered) and **no second execution** is created (one execution per funnel per subscriber).
5. **API-event mid-funnel entry (curl/bash).** With a subscriber in-flight, `POST /api/integrations/v1/events` with an `X-API-Key` header and `{event_name: "SOME_TRIGGER", telegram_user_id|subscriber_id}`. Confirm a `202` and that the subscriber is dropped **mid-funnel** onto the trigger's entry step.
6. **Verify acceptance criteria on the live env.** Walk the user-spec + tech-spec acceptance criteria that are observable live (live-loop redirect, no-second-execution, clean startup / no index conflict, mid-entry via API). Pick up any criteria the pre-deploy QA report (Task 11) deferred to live.
7. **Write the post-deploy report** to `work/17-funnel-multi-entry/logs/working/task-12/` and a Summary to `decisions.md`.

## Verification Steps

> This task IS verification on a live environment. The sections below are the live checks the agent runs, not test suites (those ran in Task 11).

### Operational (clean startup after wipe)
- Grep the startup log for `trigger-index reconciliation` → **APPLIED** (first migrating boot) / **NO-OP** (idempotent re-boot); assert **no `IndexKeySpecsConflict`** / error 86 in the log.
- Confirm the `onStartTriggerValue` partial-unique index exists at runtime (e.g. `mongosh` → `db.funnels.getIndexes()` shows `{projectId:1, onStartTriggerValue:1}` filtered `{status:'active', onStartTriggerValue:{$exists:true}}`).
- Confirm the `FunnelExecutionEngine` sweep starts with no snapshot-deserialization errors in the log.
- `curl -s <APP_URL>/health` → `{"status":"ok"}`.

### Smoke (API event — curl/bash)
- `curl -X POST <APP_URL>/api/integrations/v1/events -H 'X-API-Key: <key>' -H 'Content-Type: application/json' -d '{"event_name":"SOME_TRIGGER","telegram_user_id":<id>}'` → `202`; then inspect the subscriber's `funnel_executions` row (`mongosh`) → `currentStepId` = the trigger's entry step, no second execution row.
  - `<key>` is the test project's **per-project integration API key** (resolved by `ApiKeyAuthFilter`, not a path `projectId`). Get it from the project's integration settings / the provisioned secret for this environment — never hardcode or paste it in chat (see Implementation hints).

### User (live Telegram loop — Telegram MCP)
- In the real bot: `/start` → wait for the menu park (`waiting_for_reply`) → press the menu button → confirm the bot delivers the trigger-branch message; inspect `funnel_executions` → the same row's `currentStepId` moved to the trigger's entry step, park cleared, no second row.

**Edge cases to observe live:**
- **No second execution** on redirect — the core "one execution per funnel per subscriber" invariant (Decision 2). Assert the redirect mutates the existing row, not inserts a new one.
- **Park cleared** — the `waiting_for_reply` menu park must be removed when the redirect drives the trigger branch.
- If the live loop does not redirect (a second row appears, or the park is not cleared), capture the `funnel_executions` state + relevant log lines in the report and flag as a failure — do not "fix" anything from this task.

**Implementation hints (NOT pseudocode):**
- The wipe is the destructive step — treat the two guards as a hard gate. Echo the resolved Mongo host/db and environment name and get confirmation before running drop/clear.
- For the `X-API-Key` value: the integration API key is a **per-project secret** — `EventsController` (`POST /api/integrations/v1/events`) never takes a `{projectId}` in the path; the project is resolved from the key by the `/api/integrations/**` security chain via `ApiKeyAuthFilter` → `ApiKeyAuthentication.getProjectId()` (Decision 7). Obtain the key for the test project from its **integration settings** (the project's generated/provisioned API key) or from the environment where the key is provisioned (configured secret / env var) — do NOT hardcode it and do NOT ask the user to paste it in chat. If you cannot locate it, report where it should be stored and stop rather than improvising a value.
- Use ids/codes only in any captured log lines — never `event_name`/`triggerValue`/PII (the codebase's anti-log-injection discipline).
