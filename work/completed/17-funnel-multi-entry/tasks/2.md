## Description

Wave-2 persistence task. Task 1 has replaced `Funnel`'s flat trigger trio (`triggerType`/`triggerValue`/`keywords`) with `List<Trigger> triggers` + a denormalized nullable `String onStartTriggerValue`, and swapped the class-level partial-unique trigger index for the `{projectId:1, onStartTriggerValue:1}` shape filtered `{status:'active', onStartTriggerValue:{$exists:true}}` (Decision 6). This task makes the data-access layer match that new model:

1. **`FunnelRepository.java`** — rewrite the derived queries so they match INTO the `triggers` array (multikey nested-property derivation: `...TriggersTriggerType...`) for the `event`/`tag_added`/`custom_field_set` fan-out and the keyword scan, and replace the flat `on_start` lookup (`findByProjectIdAndTriggerTypeAndTriggerValueAndStatus` over the removed top-level fields) with a lookup on the denormalized `onStartTriggerValue` scalar.

2. **`FunnelTriggerIndexReconciliation.java`** — re-target the existing `BeanPostProcessor` (which currently retires the Phase-3 broad-filter index and lets auto-creation lay the `on_start`-only shape) so that on a wiped/existing DB it retires the OLD `projectId_triggerType_triggerValue_unique_active` trigger index BEFORE `MongoTemplate` auto-index-creation runs, so the new `onStartTriggerValue` partial-unique shape (the Task-1 annotation) lays down without throwing MongoDB `IndexKeySpecsConflict` (error 86) and crashing boot (Decision 7). Keep it idempotent (APPLIED first boot / NO-OP re-boot or fresh DB) and log-but-never-throw.

Scope boundary: this task owns ONLY `FunnelRepository.java` and `FunnelTriggerIndexReconciliation.java` (plus the two index/reconciliation IT files). The CONSUMERS of these repository methods — `FunnelService.checkTriggerConflict` (Task 4), `FunnelEventService` fan-out (Task 5), `FunnelTriggerServiceImpl.fire` on_start lookup (Task 5) — are rewired in later waves. Provide the new repository methods with names those consumers will bind to; do not edit the consumer classes here.

## What to do

1. **Rewrite `FunnelRepository` derived queries to be array-aware:**
   - Replace the flat `event`/`tag`/`field` fan-out `findAllByProjectIdAndTriggerTypeAndTriggerValueAndStatus(...)` with a multikey derived query over the `triggers` array — Spring Data nested-property derivation `findByProjectIdAndTriggersTriggerTypeAndTriggersTriggerValueAndStatus(...)` (returns `List<Funnel>`; a multikey element-match returns the funnel — the caller in Task 5 re-scans `triggers[]` to find the matched element and its `entryStepId`).
   - Replace the flat keyword-scan `findByProjectIdAndTriggerTypeAndStatus(...)` with the array form `findByProjectIdAndTriggersTriggerTypeAndStatus(...)` (still returns all active keyword funnels for in-code contains-match — the exact-match index cannot express "contains, multiple keywords").
   - Replace the flat `on_start` conflict lookup `findByProjectIdAndTriggerTypeAndTriggerValueAndStatus(...)` with `findByProjectIdAndOnStartTriggerValueAndStatus(String projectId, String onStartTriggerValue, FunnelStatus status)` returning `Optional<Funnel>` (the denormalized scalar, Decision 6 — used by Task 4's `checkTriggerConflict` pre-check).
   - Keep `findByProjectId` / `findByProjectIdAndStatus` (CRUD list endpoints) unchanged.
   - Update the interface-level Javadoc to describe the array-aware + `onStartTriggerValue` lookups and the matched-element re-scan idiom; remove stale Phase-3 flat-trio references.

2. **Re-target `FunnelTriggerIndexReconciliation` to the `onStartTriggerValue` reshape:**
   - The drop trigger is now: retire the OLD trigger index whose key is `{projectId, triggerType, triggerValue}` (name `projectId_triggerType_triggerValue_unique_active`) — it references the now-removed `triggerValue`/`triggerType` top-level fields and is dead, and on an existing DB it must be dropped before auto-creation lays the new `{projectId, onStartTriggerValue}` index (different key, different auto-derived name, e.g. `projectId_onStartTriggerValue`). Confirm the actual annotation name Task 1 produced and align the reconciliation accordingly.
   - Keep the existing `BeanPostProcessor` mechanism on `MongoDatabaseFactory` (`postProcessAfterInitialization`), the once-per-boot guard, and the `try/catch(Exception)` log-but-never-throw discipline.
   - Idempotency rule: on a fresh/wiped DB the old index is absent → NO-OP; if the old `{projectId,triggerType,triggerValue}` index is present → drop it → APPLIED; never drop the new `onStartTriggerValue` index. Drive the decision off the actual index presence/key, not a blind unconditional drop.
   - Update the greppable `MARKER_APPLIED` / `MARKER_NOOP` strings and the class Javadoc to describe the `onStartTriggerValue` reshape (the post-deploy verification task greps these — keep them stable and PII-free, index/collection names only).

3. **Rewrite the index/reconciliation ITs** (`FunnelIndexesIT`, `FunnelTriggerIndexReconciliationIT`) — they currently assert the Phase-3 `triggerType:'on_start'` partial-filter shape and build funnels via the removed `setTriggerType`/`setTriggerValue` setters. Re-author them against the new `onStartTriggerValue` partial-unique shape, building funnels via `setTriggers(List<Trigger>)` + `setOnStartTriggerValue(...)`. See TDD Anchor for the exact cases.

**Edge cases:**
- Fresh/wiped DB: old trigger index absent → reconciliation NO-OP; auto-creation lays the new shape directly (the whole point of Decision 8 wipe-not-migrate).
- An existing DB still carrying the Phase-3 `on_start`-only trigger index: its key `{projectId,triggerType,triggerValue}` still differs from the new `{projectId,onStartTriggerValue}` key → drop it (APPLIED). Even though its name differs from the new index name, dropping is correct because it indexes removed fields and would otherwise linger dead.
- Partial-filter `{$exists:true}` indexes do NOT index documents whose key is null/absent — event-only funnels (null `onStartTriggerValue`) are never bound by the unique index, so multiple may share an event value (Decision 6, the reason a multikey-over-array index was rejected).
- `triggerValue=""` (bare `/start`) on an on_start trigger: if Task 1's sync writes `onStartTriggerValue=""` (empty string, not null) for bare-start, it IS indexed and uniqueness still fires — carry an IT case (confirm against Task 1 output; the old `FunnelIndexesIT.activeFunnelTriggerUniquenessHoldsForEmptyTriggerValue` covered this for the flat field).
- Reconciliation must never throw: a transient Mongo fault during the drop is swallowed-and-logged so boot proceeds (mirrors `FunnelStepIdBackfill`).

**Implementation hints (NOT pseudocode):**
- Spring Data derives multikey element-match from nested-property method names: `...TriggersTriggerType...` traverses `triggers` (a `List<Trigger>`) then the element's `triggerType` — Mongo applies the predicate per array element, returning the funnel if any element matches. The caller (Task 5) re-scans `triggers[]` to pick which element matched and read its `entryStepId`; the repository only narrows the candidate set.
- Mirror `FunnelExecution.java`'s precedent for partial-filter literals + the static-block byte-identity assertion when reasoning about the new annotation, but the annotation itself lives in `Funnel` (Task 1) — this task aligns the reconciliation drop and the ITs, not the annotation.
- IT shape: follow the existing `FunnelTriggerIndexReconciliationIT` helpers (`installOldBroadFilterIndex`/`installNewShapeIndex`/`runReconciliation` via a fresh `new FunnelTriggerIndexReconciliation()` instance, because the Spring singleton's once-guard tripped at startup). The current `KEY` constant is `{projectId, triggerType, triggerValue}` and both helpers create indexes under the single name `INDEX_NAME` (the old name). Re-author: `installOldBroadFilterIndex` keeps the OLD key + OLD name (`projectId_triggerType_triggerValue_unique_active`) — this is the index reconciliation drops; `installNewShapeIndex` must create a DIFFERENT index with key `{projectId, onStartTriggerValue}`, filtered `{status:'active', onStartTriggerValue:{$exists:true}}`, under the new auto-derived name (so the two helpers no longer collide on one name and `triggerIndex()`-by-name detection points at the OLD index only). Build funnels via `setTriggers(List<Trigger>)`/`setOnStartTriggerValue(...)` instead of the removed `setTriggerType`/`setTriggerValue`.
- NO-OP wiring reminder for the ITs: `reconciliationIsIdempotentNoOpOnSecondBoot` and `reconciliationNoOpOnFreshDatabase` assert NO-OP by the ABSENCE of the OLD-named index, and (for the idempotent case) that the new `{projectId,onStartTriggerValue}` index is left untouched — not by inspecting a `triggerType` clause in the old index's filter (that detection is removed).
- Tests use real embedded MongoDB (Testcontainers) — never mock the DB in these ITs (patterns.md → Testing Requirements). Keep them `@Tag("slow")`.
- Keep the `MARKER_APPLIED`/`MARKER_NOOP` strings greppable and PII-free (index/collection names only) — the post-deploy verification task (Task 12) pins them.
