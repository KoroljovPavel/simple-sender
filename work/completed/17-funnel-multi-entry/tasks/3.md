# Task 3: DTO contract — `List<TriggerDto>`

## Required Skills

Перед выполнением задачи загрузи:
- `/skill:code-writing` — [SKILL.md](../../../.claude/skills/code-writing/SKILL.md)

## Description

Эта задача переводит **HTTP API-контракт воронки** с плоского три-тригерного представления
(`triggerType` / `triggerValue` / `keywords`) на массив тригеров `List<TriggerDto>`, в соответствии
с доменной моделью `List<Trigger>`, введённой в Task 1 (tech-spec Decision 1, 12).

Нужно добавить **новый DTO `TriggerDto`** (record, по образцу `FunnelStepDto.java` — плоский record,
`@JsonIgnoreProperties(ignoreUnknown=true)`, бизнес-валидация в сервисе) и заменить плоское три-поле
на `List<TriggerDto> triggers` в трёх DTO API-границы:
- `UpdateFunnelRequest` (тело PATCH/PUT — full-replace, как сейчас),
- `FunnelResponse` (полный вид воронки),
- `FunnelSummaryResponse` (облегчённый список).

PATCH остаётся **full-replace** — новый эндпоинт не добавляется. `@JsonIgnoreProperties(ignoreUnknown=true)`
сохраняется на каждом входящем DTO как mass-assignment-защита (нельзя протолкнуть `{"status":...}`).
По Decision 14 `TriggerDto` несёт `@Size`-потолок на массив тригеров и сохраняет per-trigger
keyword-капы (`MAX_KEYWORDS=50`, `MAX_KEYWORD_LENGTH=64`), чтобы массив не открыл DoS-поверхность.

Результат этой задачи — **контракт компилируется и (де)сериализуется** с массивом тригеров. Сервисная
валидация массива (дубль `event_name`, резолв `entryStepId`, синхронизация `onStartTriggerValue`) и
маппинг entity↔DTO — это Task 4; здесь меняется только форма DTO и аннотации.

## What to do

1. Создать новый record `TriggerDto` в `backend/src/main/java/com/botfunnel/funnel/dto/TriggerDto.java`
   с полями `(String triggerType, String triggerValue, List<String> keywords, String entryStepId)`,
   зеркаля стиль `FunnelStepDto.java`: плоский record, `@JsonIgnoreProperties(ignoreUnknown=true)`,
   doc-комментарий, поясняющий что per-type / cross-trigger валидация живёт в `FunnelService` (→ 422),
   а не как bean-валидация (она сработала бы независимо от `triggerType`).
2. В `UpdateFunnelRequest`: удалить плоские `triggerType`, `triggerValue`, `keywords`; добавить
   `@Valid @Size(max = N) List<TriggerDto> triggers`, где N — потолок массива (Decision 14), сохранить
   `@JsonIgnoreProperties(ignoreUnknown=true)` и существующие `@Size` на `name`/`description`. Обновить
   doc-комментарий записи (текущий описывает плоский trigger — переписать под массив).
3. В `FunnelResponse`: удалить плоские `triggerType`, `triggerValue`, `keywords`; добавить
   `List<TriggerDto> triggers`. Обновить doc-комментарий.
4. В `FunnelSummaryResponse`: удалить плоские `triggerType`, `triggerValue`, `keywords`; добавить
   `List<TriggerDto> triggers`. Обновить doc-комментарий.
5. Убедиться, что проект **компилируется**: места, которые конструируют эти три record (в `FunnelService`),
   временно сломаются по сигнатуре. Минимально привести вызовы к новой сигнатуре, **не реализуя**
   полный маппинг/валидацию массива (это Task 4) — достаточно, чтобы код компилировался (например,
   передать пустой/собранный `List<TriggerDto>`). Не дублировать логику Task 4.
6. Написать DTO-тесты по TDD Anchor: Jackson round-trip `List<TriggerDto>` и срабатывание
   `@Size`/`@Valid` через `jakarta.validation.Validator`.

## TDD Anchor

Тесты пишем ДО реализации, запускаем → убеждаемся что падают (или не компилируются) → пишем код →
зелёные. Дом для нового теста — новый файл `backend/src/test/java/com/botfunnel/funnel/dto/TriggerDtoTest.java`
(валидатор + ObjectMapper). Стиль ObjectMapper round-trip копировать из реально существующего
`backend/src/test/java/com/botfunnel/funnel/FunnelControllerIT.java` (там есть готовые примеры
сериализации/десериализации DTO воронки). Готового `Validator`-теста в проекте пока нет — собрать
`Validator` через `Validation.buildDefaultValidatorFactory().getValidator()` в новом тесте.

- `dto/TriggerDtoTest::roundTripsTriggerArray` — `ObjectMapper` сериализует `UpdateFunnelRequest` с
  `List<TriggerDto>` (on_start + два event) и десериализует обратно без потери полей (triggerType,
  triggerValue, keywords, entryStepId).
- `dto/TriggerDtoTest::deserializeIgnoresUnknownProperties` — тело с лишним полем (`{"status":"active", ...}`)
  десериализуется без ошибки и без проброса `status` (mass-assignment-защита `@JsonIgnoreProperties`).
- `dto/TriggerDtoTest::funnelResponseRoundTrip` — `FunnelResponse` / `FunnelSummaryResponse` с
  `List<TriggerDto>` сериализуются и десериализуются без потери массива.
- `dto/TriggerDtoTest::sizeCapViolationFlaggedByValidator` — `Validator.validate(UpdateFunnelRequest)` с
  массивом тригеров сверх `@Size(max=N)` возвращает constraint violation на поле `triggers`.
- `dto/TriggerDtoTest::validCascadesIntoTriggerDto` — `@Valid` каскадирует bean-валидацию в элементы
  `List<TriggerDto>` (если на `TriggerDto` есть field-level аннотации; иначе тест опустить).

- `backend/src/main/java/com/botfunnel/funnel/dto/FunnelSummaryResponse.java` — текущее (L11-25): плоские

  `UpdateFunnelRequest`). Привести вызовы к новой сигнатуре МИНИМАЛЬНО, только чтобы компилировалось.
  Полный маппинг entity↔DTO, синхронизацию `onStartTriggerValue` и валидацию массива оставить Task 4.

**Dependencies:** depends_on Task 1 (доменный `Trigger`/`Funnel` уже с `List<Trigger>`). Task 4
поверх этого контракта делает валидацию массива и маппинг — НЕ дублировать её здесь.

**Edge cases:**
- Пустой / null `triggers` в теле PATCH — bean-валидацией не падает (валидация состава — Task 4 → 422);
  здесь только форма.
- `keywords` теперь живёт per-trigger внутри `TriggerDto` (Decision 12), не на верхнем уровне DTO.
- on_start-элемент: `triggerValue=""`/null, `entryStepId=null` — форма должна это допускать.
- Неизвестные поля в JSON-теле игнорируются (`@JsonIgnoreProperties`) — не пробрасывать `status`.

**Implementation hints:**
- `@Size(max = N)` потолок массива (Decision 14): N выровнять по существующим капам того же порядка
  (`max-fanout-per-event` / `max-steps` = 50). Сервисный дубль-чек этого капа — Task 4.
- Доменный `Trigger` (Task 1) задаёт канонические имена полей — зеркаль их в `TriggerDto` 1:1, чтобы
  Task 4 маппинг был тривиальным.
- Per-trigger keyword-капы (`MAX_KEYWORDS=50`, `MAX_KEYWORD_LENGTH=64`) — сервисные константы в
  `FunnelService` (L82-83); на DTO их можно не дублировать аннотациями, но НЕ удалять сервисные.
- Слаг-регэкспы (`TRIGGER_VALUE_PATTERN` L74, `EVENT_NAME_PATTERN` L78) уже в `FunnelService` — DTO
  их не повторяет; форматные проверки остаются сервисными (→ 422), а не bean-валидацией (она дала бы 400).
- Тестовый стиль: `jakarta.validation.Validator` + `ObjectMapper`. Готовый round-trip пример
  `ObjectMapper` есть в `backend/src/test/java/com/botfunnel/funnel/FunnelControllerIT.java` — копировать
  оттуда. Отдельного `*ValidatorTest` в проекте нет; `Validator` строить через
  `Validation.buildDefaultValidatorFactory().getValidator()`.
