# Task 4: Trigger validation + `onStartTriggerValue` sync + conflict pre-check + duplicate reset

## Required Skills

Перед выполнением задачи загрузи:
- `/skill:code-writing` — [skills/code-writing/SKILL.md](../../../.claude/skills/code-writing/SKILL.md)

## Description

Переводим `FunnelService` с плоского триггер-трио (`triggerType`/`triggerValue`/`keywords`) на
`List<Trigger>` — модель нескольких входов в воронку (Decisions 1, 6, 9, 10, 14). После Task 1
домен уже несёт `List<Trigger> triggers` + денормализованный `String onStartTriggerValue`, Task 3
дал DTO `List<TriggerDto>`, Task 2 — array-aware-запросы и новый partial-unique-индекс
`{projectId, onStartTriggerValue}`. Эта задача — сервисный слой между ними.

Что меняется в `FunnelService`:

1. **`applyTrigger`** превращается из «один триплет» в **per-element-валидацию над `List<Trigger>`**
   с cross-trigger-правилами: не больше одного `on_start`; запрет дубликата `event_name` (триггерного
   `triggerValue` для типа `event`) в пределах одной воронки; каждый `entryStepId` либо `null`, либо
   указывает на реально существующий шаг воронки; тип `event` требует non-null `entryStepId`
   (Decision 10 — mid-entry только для `event`); cap на размер массива триггеров и сохранение
   per-trigger keyword-капов (Decision 14). При этом `entryStepId` НЕ участвует в generic edge-pass
   `validateSteps` (он указывает в граф этой же воронки, но валидируется здесь, не в `requireExistingTarget`).
2. **Синхронизация `onStartTriggerValue`** из элемента `on_start` на каждом сохранении (значение
   `on_start`-триггера → скаляр; `null`, если `on_start`-триггера/значения нет).
3. **`checkTriggerConflict` / `saveHandlingTriggerConflict`** работают теперь над массивом против
   `onStartTriggerValue` (Decision 6): pre-check ищет другой активный funnel с тем же
   `onStartTriggerValue`, а `DuplicateKeyException` из нового partial-unique-индекса → тот же 422
   `funnel_trigger_conflict` (никогда 500).
4. **`duplicate`** сбрасывает триггеры клона к единственному `on_start` и обнуляет `onStartTriggerValue`
   (прецедент Phase 4 «duplicate resets trigger»), чтобы клон никогда не унаследовал конфликтующее
   `on_start`-значение и draft-клон не попадал в partial-unique-индекс.
5. Точки создания/обновления (`create`, `update`, `activate`) перестают звать
   `setTriggerType`/`setTriggerValue`/`setKeywords` и переходят на `List<Trigger>`.

Результат: невалидные наборы триггеров возвращают 422 + бизнес-код; валидные (включая клоны)
сохраняются без конфликта индекса.

## What to do

- Переписать `applyTrigger(funnel, ...)` так, чтобы он принимал и валидировал `List<Trigger>` из
  запроса (источник — `UpdateFunnelRequest.triggers()` после Task 3), а не плоский триплет. Сохранить
  существующие per-type-проверки значения (`on_start` slug `^[A-Za-z0-9_-]{0,64}$`, `event` slug
  `^[A-Za-z0-9_-]{1,64}$`, tag/field slug, keyword-нормализацию и капы), переиспользуя текущие
  приватные хелперы (`normalizeOnStartValue`, `requireEventSlugValue`, `requireKeywords` и т.д.).
- Добавить cross-trigger-правила над всем массивом:
  - не более одного `on_start`-элемента;
  - запрет дубликата `triggerValue` для `event`-триггеров (одинаковое event_name в одной воронке) → 422
    с бизнес-кодом (дубликат `event_name` — критерий приёмки user-spec);
  - каждый `entryStepId`: `null` для `on_start` (и для не-`event`), либо для `event` — non-null и
    резолвится в существующий шаг воронки (по множеству step id, как строит `validateSteps`);
  - тип `event` требует non-null `entryStepId` (Decision 10);
  - cap на размер `List<Trigger>` (service-level check → 422; число выбрать в порядке величины
    существующих `app.funnel.max-steps`/`max-fanout-per-event` = 50, Decision 14) и сохранение
    per-trigger keyword-капов (`MAX_KEYWORDS=50`, `MAX_KEYWORD_LENGTH=64`).
- Убедиться, что `entryStepId` не проверяется в generic edge-pass `validateSteps`
  (`requireExistingTarget`) — он валидируется только в триггерной валидации (как `targetEntryStepId`
  у SUBSCRIBE_TO_FUNNEL умышленно вынесен из edge-pass).
- Реализовать sync `onStartTriggerValue`: на сохранении вычислить значение из `on_start`-элемента
  (его `triggerValue`; пустая строка/отсутствие → `null`, чтобы partial-фильтр
  `{onStartTriggerValue:{$exists:true}}` не связывал документ зря).
- Переписать `checkTriggerConflict(funnel)`: pre-check теперь ищет другой **active** funnel с тем же
  `onStartTriggerValue` в этом проекте (исключая себя), через repo-метод lookup по
  `onStartTriggerValue` (после Task 2). `saveHandlingTriggerConflict` оставить как defense-in-depth:
  ловить `DuplicateKeyException` нового индекса → 422 `funnel_trigger_conflict`.
- Обновить `duplicate(...)`: вместо `setTriggerType(TRIGGER_ON_START)` / `setTriggerValue("")` —
  установить `triggers` = единственный `on_start`-элемент (entryStepId=null) и обнулить
  `onStartTriggerValue`. Перенести также keywords-логику в per-trigger-модель.
- Обновить `create(...)` (стартовый funnel рождается с единственным `on_start`-триггером) и точки
  вызова `applyTrigger` в `update(...)`.
- Обновить статические константы/комментарии, ссылающиеся на плоский триггер, где это нужно для
  компиляции и корректности (не трогать несвязанную step-валидацию).

## Acceptance Criteria

- [ ] PATCH воронки с двумя одинаковыми `event_name` → 422 + бизнес-код; несколько триггеров на один entry-крок — разрешено и сохраняется.
- [ ] В массиве допустим максимум один `on_start`; второй `on_start` → 422.
- [ ] `event`-триггер требует non-null `entryStepId`, который резолвится в существующий шаг воронки; иначе 422 (dangling / missing).
- [ ] `entryStepId` не вызывает ложный `funnel_broken_edge` в generic edge-pass `validateSteps`.
- [ ] Cap размера массива триггеров и per-trigger keyword-капы (`MAX_KEYWORDS=50`, `MAX_KEYWORD_LENGTH=64`) применяются → 422 при превышении.
- [ ] `onStartTriggerValue` синхронизируется из `on_start`-элемента на каждом сохранении; `null`, когда `on_start`-значения нет.
- [ ] `checkTriggerConflict` отклоняет второй active funnel с тем же `onStartTriggerValue`; `DuplicateKeyException` нового индекса → 422 `funnel_trigger_conflict`, никогда 500.
- [ ] `duplicate()` сбрасывает триггеры клона к одному `on_start` и обнуляет `onStartTriggerValue`.
- [ ] `FunnelServiceTriggerTypeTest` и `FunnelControllerIT` зелёные; существующие funnel-тесты без регрессий.

## Details

**Files:**
- `backend/src/main/java/com/botfunnel/funnel/FunnelService.java` — главный файл задачи. Текущее
  состояние: `applyTrigger` (L611-640) работает с плоским триплетом и зовётся из `update` (L208) и
  косвенно из `create`/`duplicate` через `setTriggerType`/`setTriggerValue`. `checkTriggerConflict`
  (L337-344) и `saveHandlingTriggerConflict` (L350-357) опираются на
  `findByProjectIdAndTriggerTypeAndTriggerValueAndStatus` и поля funnel. `duplicate` (L273-293) ставит
  `setTriggerType(TRIGGER_ON_START)`/`setTriggerValue("")`. `create` (L169-184) тоже. `validateSteps`
  (L885-931) строит `stepIds` и делает generic edge-pass — переиспользуй то же множество step id для
  резолва `entryStepId`, но НЕ добавляй `entryStepId` в `requireExistingTarget` (как `targetEntryStepId`
  у SUBSCRIBE_TO_FUNNEL умышленно вне edge-pass, L906-912). Переиспользуй существующие константы кодов:
  `CODE_INVALID_TRIGGER_VALUE`, `CODE_INVALID_TRIGGER_TYPE`, `CODE_INVALID_KEYWORDS`,
  `CODE_TRIGGER_CONFLICT`, `CODE_INVALID_STEP`/`CODE_BROKEN_EDGE`. При необходимости ввести новые
  бизнес-коды для дубликата event_name / >1 on_start / dangling entryStepId / array-cap (имя в стиле
  `funnel_*`; смысл согласовать с user-spec «422 + бизнес-код»).

**Dependencies:**
- Зависит от Task 1 (домен `List<Trigger> triggers` + `onStartTriggerValue` + геттеры/сеттеры, POJO
  `Trigger`), Task 2 (repo lookup по `onStartTriggerValue` вместо `...TriggerTypeAndTriggerValue...`;
  новый partial-unique-индекс), Task 3 (`UpdateFunnelRequest.triggers()` → `List<TriggerDto>`,
  `FunnelResponse`/`FunnelSummaryResponse` несут массив; `toResponse`/`toSummary` маппинг). Сверься с
  фактическими сигнатурами после этих задач (`decisions.md` + сами файлы) — не угадывай имена методов.
- Никаких новых backend-зависимостей (user-spec «Ограничения»).

**Edge cases:**
- Пустой/отсутствующий массив триггеров на сохранении: нормализовать к единственному `on_start` (как
  делал старый дефолт `on_start`/"") — funnel всегда имеет главный вход.
- `on_start` с пустым `triggerValue` ("") → `onStartTriggerValue=null` (чтобы не связывать
  partial-индекс пустой строкой; уникальность только для реально заданного значения).
- Несколько `event`-триггеров на один `entryStepId` — разрешено (это НЕ дубликат: дубликат —
  одинаковый event_name).
- Дубликат event_name сравнивать с учётом регистра (event slug case-preserving, как
  `EVENT_NAME_PATTERN`).
- Не-`event`-типы (`keyword`/`tag_added`/`custom_field_set`) с непустым `entryStepId` — отклонить
  согласно Decision 10 (mid-entry только для `event`), строгий reject в стиле существующего
  `requireNoKeywords`.
- `duplicate` оригинала с активным on_start: клон всё равно draft + один on_start + `onStartTriggerValue=null`.

**Implementation hints (НЕ псевдокод):**
- Сохрани и переиспользуй существующие приватные хелперы значений/keyword-нормализации — меняется
  только обход (по списку, а не по одному триплету).
- Для cross-trigger-правил сделай один проход по массиву: счётчик `on_start`, множество увиденных
  event_name, множество step id (из текущих steps) для резолва entryStepId.
- `onStartTriggerValue` sync держи в одном месте, вызываемом из всех путей сохранения (`update`,
  `activate`, `duplicate`, `create`), чтобы скаляр и массив не разъехались — дисциплина «единственный writer».
- Для `checkTriggerConflict` используй фактический repo-метод поиска active funnel по
  `onStartTriggerValue` (его владелец — Task 2). Если метода нет — согласуй с владельцем репозитория,
  не дублируй query в сервисе.
- Anti-IDOR / fail-closed по `projectId` сохраняется: все публичные методы по-прежнему через
  `requireFunnel`/`requireOwned` ПЕРВЫМИ (не менять порядок).
- Бизнес-коды и сообщения 422 не должны содержать PII; коды машинно-читаемые (как остальной контракт).
