# Task 5: Redirect-or-start dispatcher + engine `redirectExecution` + on_start lookup

## Required Skills

Перед выполнением задачи загрузи:
- `/skill:code-writing` — [.claude/skills/code-writing/SKILL.md](../../../.claude/skills/code-writing/SKILL.md)

## Description

Это самая большая и высокорисковая задача фичи. Она замыкает поведение многоточечного входа: спрацьована named-подія для подписчика либо **перекидает** его уже-бегущее выполнение этой воронки на ветку триггера (`entryStepId`), либо **стартует** свежее выполнение с этой ветки — строго **одно выполнение на воронку на подписчика** (Decision 2). `/start` (on_start) продолжает энроллить с шага 0.

Состоит из трёх связанных изменений в одном слое:

1. **`FunnelExecutionEngine.redirectExecution(...)`** — новый метод-аналог `resumeOnCallback`. Claim-CAS, привязанный одновременно к `subscriberId` и `funnelId` (анти-IDOR, Decision 3), принимающий статусы `running`/`waiting`/`waiting_for_reply` (шире, чем `claimForCallback`, который ловит только `waiting_for_reply`). Ставит курсор на `entryStepId`, снимает парк (`status=running`, `stepRunStatus=in_progress`), затем `preStepGates` + `drive` сразу. Цель резолвится **против `stepsSnapshot` выполнения** (snapshot-isolation, без funnel-versioning). Проигрыш CAS → best-effort no-op + greppable WARN (только id/коды), без искусственного retry (Decision 4). Битый курсор (`entryStepId` нет в снапшоте) → terminal-fail **только этого выполнения**, sweep и остальные продолжают (Decision 5).

2. **`FunnelEventService`** — единый redirect-or-start диспетчер (Decision 11, один коллаборатор, без форкнутого писателя). Re-scan совпавшего элемента `triggers[]` чтобы достать `entryStepId` (multikey-матч возвращает воронку, а не элемент — Decision 12, идиома keyword-re-scan). Решение redirect-vs-start на каждую совпавшую воронку: есть in-flight выполнение (`status ∈ {running, waiting, waiting_for_reply}` для пары `(funnelId, subscriberId)`) → redirect; иначе → `insertExecutionAt(entryStepId)` с уважением `allowReEnter` (Decision 9). In-flight `exists`/lookup-проб **пишется заново** в этом слое (репозиторий / диспетчер) по образцу `hasWaitingForReplyExecution` из `ProcessTelegramUpdateJob` (webhook-пакет) — этот метод НЕ живёт в `FunnelEventService`, копировать его idiom, а не «расширять существующий метод». Переиспользует три бэкстопа (depth cap → auto-enroll rate-limit → fan-out ceiling) и сохраняет error-isolation (`try/catch(Throwable)` + swallow-WARN — диспетчер никогда не бросает наружу).

3. **`FunnelTriggerServiceImpl.fire`** — перевод on_start-лукапа с удалённых плоских полей (`findByProjectIdAndTriggerTypeAndTriggerValueAndStatus`) на `onStartTriggerValue` (Decision 6). Семантика энролла остаётся step-0, depth 0.

Плюс проводка: API-event путь (`EventsController` → `dispatchForSubscriber`) и `EMIT_EVENT`-шаг (`StepExecutor` → `dispatchForSubscriber`) идут через тот же диспетчер. Самопетля `EMIT_EVENT`→триггер ограничена тем же `drive`-loop, что и sweep: per-tick budget (`FUNNEL_STEP_BUDGET_EXCEEDED`) + human-press/menu-park gate; redirect мутирует существующую строку, не создаёт новую и не сбрасывает `enrollDepth`, поэтому depth-cap по-прежнему держит enroll-driven рост (Architecture → "Loop bound under redirect", US Risk 4).

## What to do

1. **Engine — `redirectExecution(String executionId, String subscriberId, String funnelId, String entryStepId)`** в `FunnelExecutionEngine`:
   - Добавить приватный `claimForRedirect(...)` по образцу `claimForCallback`, но: предикат включает `subscriberId` **и** `funnelId`, `status ∈ {running, waiting, waiting_for_reply}`, `stepRunStatus = pending`; апдейт ставит `status=running`, `currentStepId=entryStepId`, `stepRunStatus=in_progress`, `updatedAt`.
   - Если CAS вернул `null` → залогировать новой greppable WARN-константой (id/коды только: `executionId`, `funnelId`; **никогда** event_name/triggerValue), вернуть результат (выбрать сигнатуру под нужды диспетчера; задокументировать как `resumeOnCallback`).
   - Перед `drive`: цель резолвится в `exec.getStepsSnapshot()`. `drive` уже фейлит одно выполнение через broken-cursor-ветку (`currentStep==null`+`!endOfGraph` → `terminate(failed)` + `LOG_BROKEN_CURSOR`); опереться на этот путь либо добавить явную предпроверку — выбрать минимально-инвазивный вариант, согласованный с Decision 5 (фейл ТОЛЬКО этого выполнения, никогда sweep).
   - После выигранного CAS: `preStepGates` + `drive` точно как в `resumeOnCallback`.
   - Добавить greppable лог-константу для успешного redirect (по образцу `LOG_RESUME_CALLBACK`).

2. **Диспетчер в `FunnelEventService`**:
   - Добавить re-scan совпавшего элемента: по совпавшей воронке + `triggerType`/`matchKey` найти конкретный `Trigger`-элемент и вернуть его `entryStepId` (идиома идентична keyword-re-scan из Task 2 / Decision 12).
   - Написать **новый** in-flight `find`/`findOne`-проб для пары `(funnelId, subscriberId)` со `status ∈ {running, waiting, waiting_for_reply}`, fail-closed по `projectId`. Моделировать по `hasWaitingForReplyExecution` из `ProcessTelegramUpdateJob` (`backend/.../webhook/ProcessTelegramUpdateJob.java` L262: `mongoTemplate.exists(Criteria.where("projectId").is(...).and("subscriberId").is(...).and("status").is(...))`), НО: (a) этот метод живёт в другом классе/пакете — его нельзя «расширить», его idiom копируется; (b) нужен сам `executionId`, поэтому `find`/`findOne` (не `exists`); (c) статус-предикат шире (`.in("running","waiting","waiting_for_reply")`); (d) добавить `.and("funnelId").is(...)`. Положить probe туда, где ему место — в `FunnelExecutionRepository`/`MongoTemplate`-слой диспетчера, не как «существующий метод FunnelEventService». `executionId` достаётся ТОЛЬКО из этого доверенного lookup, НИКОГДА из request-input.
   - В fan-out-цикле для каждой совпавшей воронки решить: in-flight есть → `executionEngine.redirectExecution(execId, subscriberId, funnelId, entryStepId)`; нет → start с `entryStepId` через `executionFactory.insertExecutionAt(...)` с уважением `allowReEnter` (переиспользовать `insertOneFunnel`/`insertTargetExecution`-механику, но передавая `entryStepId`).
   - Сохранить три бэкстопа и `try/catch(Throwable)` error-isolation; redirect-ветка тоже error-isolated (фейл одного redirect не валит остальной fan-out и не бросает наружу).
   - Решение принимается **независимо на каждую воронку**: одно событие, совпавшее с двумя воронками — для in-flight redirect, для другой start, в пределах fan-out ceiling.

3. **`FunnelTriggerServiceImpl.fire`** — заменить `findByProjectIdAndTriggerTypeAndTriggerValueAndStatus(projectId, triggerType, triggerValue, active)` (L142-150) на лукап по `onStartTriggerValue` (метод из Task 2 на репозитории). Энролл остаётся step-0, depth 0, re-enter-логика без изменений.

4. **Проводка путей**: убедиться, что `EventsController` (API-event) и `StepExecutor` (`EMIT_EVENT`) идут через `dispatchForSubscriber` (они уже идут — встроить redirect-логику ВНУТРЬ `dispatchForSubscriber`, а не в отдельную точку). Никакого второго писателя выполнения.

5. **Анти-IDOR**: `executionId` для redirect берётся ТОЛЬКО из доверенного in-flight lookup-проба внутри диспетчера (никогда из request-input); CAS повторно проверяет `subscriberId`+`funnelId`, поэтому mismatched-subscriber redirect — гарантированный no-op.

## Acceptance Criteria

- [ ] `redirectExecution` мутирует существующую строку `funnel_executions` (курсор = `entryStepId`, парк снят); второго выполнения для пары (funnelId, subscriberId) не появляется.
- [ ] redirect принимает `running`/`waiting`/`waiting_for_reply`; CAS привязан к `subscriberId`+`funnelId`; mismatched-subscriber redirect — гарантированный no-op (анти-IDOR).
- [ ] Проигрыш CAS (строка `in_progress`) → best-effort no-op + greppable WARN (id/коды только), состояние не испорчено, искусственного retry нет.
- [ ] Битый курсор после redirect → terminal-fail только этого выполнения (greppable broken-cursor-маркер); sweep и остальные выполнения работают дальше.
- [ ] Диспетчер выбирает redirect (in-flight есть) / start с `entryStepId` (нет in-flight), уважая `allowReEnter`; решение независимо на каждую совпавшую воронку.
- [ ] Совпавший элемент `triggers[]` корректно re-scan-ится, `entryStepId` достаётся для нужного триггера.
- [ ] `FunnelTriggerServiceImpl.fire` находит on_start-воронку через `onStartTriggerValue`; `/start` по-прежнему энроллит с шага 0.
- [ ] API-event и `EMIT_EVENT` идут через единый диспетчер; второго писателя выполнения нет.
- [ ] Error-isolation сохранена: ни одна новая ветка не бросает наружу; новые WARN-логи не содержат `event_name`/`triggerValue`/PII.
- [ ] Self-loop `EMIT_EVENT`→триггер завершается per-tick budget / menu-park gate (не зацикливается).
- [ ] Bean-цикл `FunnelEventService → FunnelExecutionEngine → StepExecutor → FunnelEventService` разорван через `@Lazy` (или эквивалентный deferred-резолв): Spring-контекст стартует без `BeanCurrentlyInCreationException`.
- [ ] `cd backend && ./gradlew test -PrunSlow=true --tests '*FunnelExecutionEngineIT'` — зелёный.

Раньше цикла не было ТОЛЬКО потому, что `FunnelEventService` инжектил `FunnelExecutionFactory` (у которой нет ребра в engine — см. её class-doc L16-32); инъекция самого engine это ребро добавляет. **Сломать цикл через `@Lazy` на инжектируемом `FunnelExecutionEngine`** (deferred resolution — Spring создаёт прокси, разрывает цикл создания бинов). **Dependencies:**
- Task 1 (Trigger POJO с `entryStepId`, `Funnel.onStartTriggerValue`), Task 2 (репозиторий: array-aware queries + `onStartTriggerValue`-лукап), Task 3 (DTO) — должны быть выполнены.
- Пакеты не добавлять (US: без новых бекенд-зависимостей).

**Edge cases:**
- CAS-loss (sweep владеет строкой, `in_progress`) → no-op + WARN, без retry, состояние не тронуто.
- Битый курсор (`entryStepId` нет в `stepsSnapshot` из-за snapshot-isolation) → fail только этого выполнения.
- Mismatched-subscriber / cross-project → CAS-предикат не матчит → no-op (анти-IDOR).
- Cross-funnel: in-flight в воронке B, событие для воронки A → A стартует, B не тронута.
- Один event → две воронки → решение независимо на каждую, в пределах fan-out ceiling.
- `allowReEnter=false`: start — no-op (swallow `DuplicateKeyException`) ТОЛЬКО когда есть активное (`running|waiting|waiting_for_reply`) выполнение; terminal-статусы (`completed`/`cancelled`/`failed`) не держат re-enter unique index → fresh insert проходит. Сверить с Decision 9 и существующей `insertOneFunnel` (L328).
- Self-loop `EMIT_EVENT`→триггер: redirect мутирует строку (нет новой, `enrollDepth` без изменений) → bounded per-tick budget + menu-park.
- Не-`event` триггеры (keyword/tag/field) остаются start-from-beginning (Decision 10) — redirect только для `event`.

**Implementation hints:**
- `redirectExecution` — копия структуры `resumeOnCallback` (L181-200) с более широким claim. Курсор ставится В CAS-апдейте (как `claimForCallback`), не отдельным write.
- in-flight probe для redirect: нужен сам `executionId` → `findOne`/`find` по `Criteria.where("projectId").is(projectId).and("funnelId").is(...).and("subscriberId").is(...).and("status").in("running","waiting","waiting_for_reply")` (НЕ из request-input). Статусы — lowercase `.name()` литералы (Decision 14).
- Лог-константы: id/коды только (Decision 16). Никогда `event_name`/`triggerValue`/имя подписчика.
- В ITs: `ListAppender` (logback) для проверки WARN (паттерн `stateTransitionsEmitNamedLogConstantsWithoutPayload` в EngineIT); `ConcurrencyTestUtils` для CAS-race (паттерн `atomicClaimRaceAcrossTwoReplicasRunsStepOnce`).
- НЕ форкать второй писатель выполнения — redirect через engine, start через `executionFactory.insertExecutionAt` (Decision 2/11).
- **BEAN CYCLE — РЕАЛЬНЫЙ, не отсутствующий.** Инъекция `FunnelExecutionEngine` в `FunnelEventService` замыкает цикл `FunnelEventService → FunnelExecutionEngine → StepExecutor → FunnelEventService` (все три ребра в коде: engine L70/L256 → StepExecutor; StepExecutor L87 → FunnelEventService; новое ребро — engine в FunnelEventService). Без разрыва Spring бросит `BeanCurrentlyInCreationException` на старте. **Разорвать через `@Lazy`** на поле/параметре `FunnelExecutionEngine` в `FunnelEventService` (`@Lazy FunnelExecutionEngine engine` в конструкторе) — Spring подставит прокси и отложит резолв, разорвав цикл создания. Это согласовано с тем, как кодбейс уже изолирует engine-ветку: `FunnelExecutionFactory` (class-doc L16-32) был выделен именно чтобы НЕ замыкать аналогичный документированный цикл `… → StepExecutor → FunnelEventService`; здесь, поскольку нужен сам engine, deferred-резолв (`@Lazy`) — эквивалентный приём. Проверить: контекст Spring стартует без `BeanCurrentlyInCreationException` (любой IT, поднимающий контекст, поймает регресс).
