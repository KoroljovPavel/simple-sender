# Task 6: Frontend types, store, and Triggers panel

## Required Skills

Перед выполнением задачи загрузи:
- `/skill:code-writing` — [skills/code-writing/SKILL.md](.claude/skills/code-writing/SKILL.md)

## Description

Фронтенд-модель и UI для нескольких точек входа (mid-entry). Бэкенд (Task 1-5) уже перешёл с плоского
триггер-трио (`triggerType`/`triggerValue`/`keywords`) на `List<Trigger>`, где каждый `Trigger` несёт
свой `entryStepId`. Эта задача приводит фронтенд-контракт в соответствие и даёт автору воронки панель
«Тригери» для управления N `event`-триггерами.

Три части:

1. **`types/funnel.ts`** — новый интерфейс `FunnelTrigger`, зеркалящий бэкендовый `TriggerDto`
   (Task 3); замена плоского трио на `FunnelTrigger[]` в `FunnelResponse`, `FunnelSummaryResponse`,
   `UpdateFunnelRequest`.
2. **`stores/funnels.ts`** — тонкий pass-through: убрать ссылки на `triggerType`/`triggerValue` в
   `update()`/`syncRow()` (они проецируют поля summary-строки), оставить store «глупым» относительно
   формы триггеров (массив идёт в `update()` целиком как часть `UpdateFunnelRequest`).
3. **`FunnelTriggersPanel.vue`** (НОВЫЙ компонент) — вертикальный список, клон add/delete/select
   структуры `FunnelStepsList.vue`. Под `on_start` (главный вход, entry = первый шаг) показывает список
   добавленных `event`-триггеров; на каждый монтирует `FunnelTriggerSettings.vue` (портативная форма
   узла, Phase 3 Decision 11) + per-trigger entry-step `SearchableSelect` над шагами самой воронки
   (скопировать билдер `subscribeEntryOptions` из `FunnelStepForm.vue`; `null`/`__START__` = шаг 1).
   ВНИМАНИЕ: в `FunnelStepForm` `subscribeEntryOptions` читает шаги из async-фетченного ref'а — в панели
   строить entry-опции из ШАГОВ ИЗ PROP'а (собственные шаги воронки, переданные в панель), а НЕ из async-фетча.
   Клиентский зеркальный guard на дубль `event_name` внутри воронки (advisory — серверный 422 остаётся
   backstop, Decision 13/14).

Результат: массив триггеров смоделирован end-to-end; автор может добавлять/удалять `event`-триггеры и
выбирать entry-шаг каждому; подписи uk/en без пустых ключей. Привязку панели к странице редактора и
автосейв делает Task 7 — эта задача даёт сам компонент + типы + store.

**Dependencies:**
- depends_on Task 3 (DTO `List<TriggerDto>` контракт) — `FunnelTrigger` зеркалит реально созданный `TriggerDto`; перед началом прочитать отчёт Task 3 в `decisions.md`, чтобы взять точные имена/нуллабельность полей.
- Пакетов новых не добавлять (US «Ограничения»: без графовых библиотек, без новых зависимостей).

**Edge cases:**
- Шаг без `id` (не сохранён) — пропускать в entry-опциях (как в `subscribeEntryOptions`): нет стабильного target.
- Несколько триггеров на один и тот же entry-шаг — разрешено (US AC), guard только на дубль `event_name`.
- Удалённый/переименованный шаг, на который указывает `entryStepId` — `SearchableSelect.selectedLabel` фолбэчит на сырое значение (уже встроено).
- `event_name` нормализация для сравнения дублей — мириться с тем, как сравнивает бэкенд (case/regex `^[A-Za-z0-9_-]{1,64}$`); guard advisory, серверный 422 — истина.
- Пустой список event-триггеров — панель показывает empty-state (как `FunnelStepsList` empty-block), on_start всё равно виден.

**Implementation hints:**
- Тест-идиома: `mountSuspended` + `mockNuxtImport('useI18n', ...)` / `useRoute` как в `CreateFunnelDialog.spec.ts`; `data-test`-селекторы через `document.querySelector` + `DOMWrapper`. `FunnelTriggerSettings` лениво фетчит tags/fields по типу — в спеке мокать `useApi` или ограничить тест типом `event` (без tag/field), чтобы избежать сетевых вызовов.
- entry-label формат: `{position+1}. {t('funnels.steps.type.'+stepType)}` — точь-в-точь как `subscribeEntryOptions`.
- sentinel: использовать ту же константу-семантику `__START__` (= entry первый шаг); на emit маппить sentinel → `null` (или `__START__`, согласовать с тем, что бэкенд `entryStepId=null` трактует как старт). Бэкенд: для `event` `entryStepId` обязателен (Decision 14) — но «from start» для event может быть валидной опцией только если бэкенд это допускает; СВЕРИТЬ с Task 4 валидацией (`event` requires non-null `entryStepId`). Если бэкенд требует non-null entryStepId для event — sentinel «from start» для event-триггера НЕ предлагать (или маппить на id первого шага). Решить по фактической валидации Task 4 (decisions.md) и зафиксировать в отчёте.
- i18n: не плодить пустые ключи; добавить осмысленные uk/en строки. Переиспользовать `funnels.trigger.*` (title/eventNameLabel/eventNamePattern и т.д.) где совпадает.
- Store: НЕ вызывать `useApiError`/`useI18n` внутри Pinia-экшенов (см. CRITICAL-комментарий в `stores/funnels.ts`).
