# Task 7: Editor page wiring for the trigger array

## Required Skills

Перед выполнением задачи загрузи:
- `/skill:code-writing` — [skills/code-writing/SKILL.md](.claude/skills/code-writing/SKILL.md)

## Description

Переробити сторінку редактора воронки `frontend/pages/projects/[projectId]/funnels/[funnelId].vue` під
**масив тригерів** замість сьогоднішнього єдиного тригера.

Зараз сторінка тримає тригер як три плоских реф-и (`triggerType`, `triggerValue`, `keywords`), один на
воронку. Tech-spec (Decision 1, Data Models) замінює цю модель на `List<Trigger>`, де кожен `Trigger`
несе власні `triggerType`/`triggerValue`/`keywords` плюс `entryStepId`. Task 6 (залежність) вже додав
тип `FunnelTrigger` у `types/funnel.ts`, провів масив через store `update()` і збудував компонент
`FunnelTriggersPanel.vue` (vertical-list панель «Тригери» з add/delete/select + per-trigger entry-крок).
**Ця задача — споживач**: вона під'єднує панель до сторінки і переписує autosave-логіку під масив.

Що саме змінюється на сторінці:
1. Три плоских тригер-реф-и → один реактивний `triggers: FunnelTrigger[]`, заповнюваний з
   `FunnelResponse.triggers` у `load()`/`applyResponse()`.
2. `persist()`: тригер-блок payload-а більше не надсилає `triggerType`/`triggerValue`/`keywords` плоско —
   надсилає `triggers` (масив) у `UpdateFunnelRequest` (контракт уже оновлено Task 3 backend + Task 6
   frontend types).
3. `triggerReady()`: з єдиного тригера → **per-element** перевірка готовності (тригер «готовий» до PATCH,
   коли його обов'язкове для свого типу значення заповнене). Дебаунс-autosave планується лише коли
   **усі редаговані тригери готові** — щоб перемикання типу тригера наодинці (поки значення ще порожнє)
   **не стріляло передчасний 422**, як і сьогодні для одного тригера.
4. Дебаунсний watch (`scheduleTriggerPersist`) переходить на глибоке спостереження масиву `triggers`.
5. Замість `<FunnelTriggerSettings>` у шаблоні монтується `<FunnelTriggersPanel>`, прив'язана через
   `v-model` до `triggers`, плюс прокидання `botUsername`/`deepLink` та списку кроків воронки для
   per-trigger entry-step picker.

Результат: правки кожного тригера автозберігаються per-element, а перемикання типу одного тригера
наодинці ніколи не викликає передчасний 422; додавання event-тригера з вибором entry-кроку
зберігається та переживає reload.

## What to do

- Замінити три тригер-реф-и (`triggerType`, `triggerValue`, `keywords`) одним `triggers: Ref<FunnelTrigger[]>`.
- У `applyResponse()`/`load()` заповнювати `triggers` з `res.triggers` (з безпечним fallback на масив з
  одним `on_start`-тригером, якщо бекенд повернув порожньо — щоб панель завжди мала головний вхід).
- Переписати тригер-блок `persist()`: надсилати `triggers` у тілі `update()` замість плоского трио;
  кожен елемент надсилає лише поля, що належать його типу (keyword володіє `keywords` і чистить
  `triggerValue`; решта типів — навпаки), `entryStepId` несеться як є (null для `on_start`).
- Зробити `triggerReady()` per-element: приймає `FunnelTrigger`, повертає, чи його обов'язкове значення
  заповнене (за тими ж канонічними regex-ами `TRIGGER_VALUE_RE`/`EVENT_NAME_RE`, що й зараз). Зберегти
  семантику: `event` вимагає валідного slug; `keyword` ≥1 keyword; `tag_added`/`custom_field_set` —
  непорожнє значення; `on_start` — value за `TRIGGER_VALUE_RE` (порожнє валідне).
- `scheduleTriggerPersist()` планує дебаунсний PATCH лише коли **кожен** елемент `triggers` готовий
  (`triggers.every(triggerReady)`); інакше — no-op (як сьогодні для одного тригера). Зберегти 600ms
  дебаунс, очистку таймера в `activate()` (flush перед активацією) та в `onBeforeUnmount`.
- Перевести `watch(...)` на `triggers` з `{ deep: true }`.
- У шаблоні замінити `<FunnelTriggerSettings .../>` на `<FunnelTriggersPanel>`. **СПОЧАТКУ** прочитати
  фактичний `frontend/components/funnels/FunnelTriggersPanel.vue` (вихід Task 6) і визначити його реальний
  контракт: які пропси він приймає (`defineProps`), які події емітить (`defineEmits`) чи має `v-model`/
  `defineModel`, і який саме тип масиву / store він споживає. **ПОТІМ** під'єднати сторінку під цей
  фактичний контракт — не хардкодити презумптивний список пропсів. Орієнтовно панелі потрібні: масив
  тригерів (через `v-model`/emit — як визначив Task 6), список кроків воронки для entry-step picker та,
  за потреби, `botUsername`/`deepLink` для вкладеної форми; але точні імена/форму брати з прочитаного файлу.
- Не чіпати логіку step-ів, preview-панелі, header-екшенів (Duplicate/Stop-all/Test for me),
  404-redirect та 422-inline-mapping — вони мають продовжувати працювати без регресій.

  `triggers: FunnelTrigger[]`; переписати `persist()` тригер-блок, `triggerReady()` (per-element),
  `scheduleTriggerPersist()`/`watch`; замінити `<FunnelTriggerSettings>` на `<FunnelTriggersPanel>` у
  шаблоні. Прибрати зі сторінки прямий імпорт/монтаж `FunnelTriggerSettings` — компонент НЕ видаляється,
  а тепер монтується всередині `FunnelTriggersPanel` (Task 6); зі сторінки зникає лише page-level посилання.
- `frontend/tests/pages/funnel-editor.spec.ts` — переписати блок `trigger auto-save readiness` під масив,
  додати TDD-кейси з якоря. Оновити `draft()`-фабрику: повертати `triggers: [...]` замість плоского трио
  (узгодити з оновленим `FunnelResponse` з Task 6).

**Dependencies:**
- Task 6 (попередник): надає `FunnelTrigger` тип, масив-контракт у `UpdateFunnelRequest`/`FunnelResponse`,
  store-passthrough та компонент `FunnelTriggersPanel.vue`. **Не переробляти** ці артефакти — споживати їх.
  Якщо контракт панелі (пропси/події) відрізняється від очікуваного — узгодити під фактичний експорт
  Task-6 файлу, а не вигадувати новий.
- Жодних нових npm-залежностей (user-spec «Ограничения»).

**Edge cases:**
- Бекенд повернув порожній/відсутній `triggers` → fallback на масив з одним `on_start`-тригером
  (`{ triggerType: 'on_start', triggerValue: '', entryStepId: null }`), щоб панель завжди мала головний вхід.
- Перемикання типу тригера наодинці (значення порожнє) → no PATCH (per-element gate). Це головний
  регресійний кейс — сьогоднішні тести `does NOT PATCH when the type switches to ...` мають мати масив-аналог.
- Кілька тригерів, один готовий + один напівзаповнений → autosave чекає, доки готові **всі** (`every`).
- `activate()` має flush-ити pending тригер-таймер ПЕРЕД PATCH (як зараз), щоб сервер валідував те, що
  на екрані; неповний тригер усе одно дає 422 через `activate()→persist()` і мапиться inline.
- keyword-тригер володіє `keywords` і обнуляє `triggerValue`; решта типів — навпаки (не нести stale-значення
  з раніше вибраного типу — той самий принцип, що в поточному `persist()`).
- **Переписаний spec має монтувати РЕАЛЬНУ `FunnelTriggersPanel`, а не стаб.** Якщо застабити панель
  (`stubs: { FunnelTriggersPanel: true }` або shallow), вкладені `funnel-trigger-*` селектори зникнуть і
  assertions autosave-readiness (per-element gate, premature-422, `triggers.every(ready)`) перевірятимуть
  порожнечу — тести стануть зеленими, нічого не перевіряючи. Монтувати панель повноцінно; стабити лише
  мережеві залежності вкладеної форми (lazy tags/fields fetch), а не саму панель.

**Implementation hints:**
- Канонічні regex-и `TRIGGER_VALUE_RE = /^[A-Za-z0-9_-]{0,64}$/` і `EVENT_NAME_RE = /^[A-Za-z0-9_-]{1,64}$/`
  уже визначені на сторінці — переюзати їх у per-element `triggerReady(trigger)`.
- `watch(triggers, scheduleTriggerPersist, { deep: true })` — глибоке спостереження, бо редагуються поля
  всередині елементів масиву.
- Шаблон: блок `<FunnelTriggerSettings v-model:trigger-type=... v-model:trigger-value=... v-model:keywords=.../>`
  (рядки ~445-451) прибирається зі сторінки і замінюється на `<FunnelTriggersPanel ...>`. **Точну форму
  пропсів/подій НЕ вигадувати — взяти з фактичного `defineProps`/`defineEmits`/`defineModel` прочитаного
  Task-6 компонента** (див. крок «What to do»). Орієнтир (НЕ канон): панель приймає масив тригерів (v-model
  або emit), `steps`, опційно `botUsername`/`deepLink`.
- **`FunnelTriggerSettings.vue` НЕ виходить з ужитку — він переїжджає ВСЕРЕДИНУ панелі** (Task 6 монтує
  його per-trigger). Зі сторінки зникає лише прямий монтаж/імпорт `FunnelTriggerSettings`; самі форму та її
  поведінку (типи тригера, lazy tags/fields) тепер інкапсулює `FunnelTriggersPanel`.
- **Міграція `data-test`-селекторів:** page-level селектори тригер-форми (`funnel-trigger-type-select`,
  `funnel-trigger-keyword-input`, `funnel-trigger-keyword-add`, `funnel-trigger-event-input`,
  `funnel-trigger-value-input` тощо) сьогодні висять на page-mounted `FunnelTriggerSettings`. Після переїзду
  форми всередину панелі ці селектори стають **panel-mounted** (через `FunnelTriggersPanel` → вкладений
  `FunnelTriggerSettings`). Блок `trigger auto-save readiness` у spec (зараз ~рядки 179-300, селектори
  `funnel-trigger-*`) треба **перенацілити** на panel-mounted селектори (або на нові array-level тест-хуки
  сторінки, якщо Task 6 ввів такі). У тесті вже є fake-timers + `tick(ms)` helper + ці `data-test`-селектори
  — узгодити їх з фактичними селекторами Task-6 панелі; не лишати мертвих селекторів старого page-level монтажу.
- НЕ перевизначати поведінку валідації сервера — клієнтський gate лише запобігає передчасному PATCH;
  фінальний валідатор — бекенд (422 + бізнес-код), inline-mapping уже є на сторінці.
