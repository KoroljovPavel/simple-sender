## Description

Сквозной security-аудит всей фичи `17-funnel-multi-entry` (Epic 8 — Phase 8, multi-entry graph model) против OWASP Top 10. Это задача Audit Wave: аудитор сам является ревью (отдельных reviewers нет), результат — единый отчёт по безопасности всей фичи, а не отзыв на одну задачу.

Фича заменяет плоское трио триггеров на `Funnel` (`triggerType`/`triggerValue`/`keywords`) на `List<Trigger>`, где каждый `Trigger` несёт собственный `entryStepId` (mid-entry для `event`-триггеров). Появляется единый диспетчер redirect-or-start: сработавший event либо перенаправляет существующее in-flight выполнение воронки (новый `FunnelExecutionEngine.redirectExecution` с CAS), либо стартует новое через `insertExecutionAt`. Это вводит новую поверхность атаки: публичный `POST /api/integrations/v1/events` принимает event-имена от внешних интеграций; redirect мутирует существующую строку выполнения по subscriberId-scoped CAS (риск IDOR); массив триггеров и per-trigger keywords открывают DoS-поверхность (A04); новые WARN-маркеры на redirect/start путях не должны логировать PII (anti log-injection).

Аудит должен прочитать ВЕСЬ исходный код, созданный/изменённый в задачах 1-7 (backend + frontend), и техспек, и проанализировать целостно — кросс-компонентные уязвимости, а не отдельный файл.

## What to do

1. Собери полный набор файлов фичи: прочти `decisions.md` (отчёты по выполненным задачам со списками файлов) и секцию `Implementation Tasks → Files to modify` техспека, чтобы получить точный перечень созданного/изменённого кода в задачах 1-7. Прочти каждый из этих файлов.
2. Прочти `tech-spec.md` (особенно Decision 3 — anti-IDOR; Decision 4 — CAS-loss WARN без PII; Decision 14 — DoS-капы; таблицу Risks — DoS/A04, log-injection, error-isolation) и `user-spec.md` (Risks 1-4) как контекст ожидаемых контролей безопасности.
3. Проведи аудит против OWASP Top 10 по всем компонентам фичи. Минимально, но не ограничиваясь, проверь:
   - **A01 Broken Access Control / IDOR** — redirect CAS в `FunnelExecutionEngine.redirectExecution` обязан быть привязан И к `subscriberId`, И к `funnelId` (Decision 3); `executionId` приходит ТОЛЬКО из доверенного in-flight `exists`/lookup внутри диспетчера, НИКОГДА из request-input; mismatched-subscriber redirect — гарантированный no-op. Проверь fail-closed `projectId`-дисциплину на путях redirect и start (`enrollSpecificFunnel`/`insertExecutionAt`).
   - **A03 Injection / log-injection** — новые WARN-маркеры на redirect/start/CAS-loss путях логируют только ids/коды, НИКОГДА `event_name`/`triggerValue`/PII (Decision 4, Phase-5 precedent). Mongo derived-queries по массиву триггеров не должны давать инъекцию через `triggerValue`/`entryStepId`.
   - **A04 Insecure Design / DoS** — `@Size` cap на массиве триггеров + сохранённые per-trigger keyword-капы (`MAX_KEYWORDS=50`, `MAX_KEYWORD_LENGTH=64`) по Decision 14; публичный `/events` остаётся за rate-limit + fan-out ceiling; N×keyword-scan по перемещённым per-trigger keywords не растёт неограниченно.
   - **A08 Software & Data Integrity / Mass-assignment** — `TriggerDto` и `UpdateFunnelRequest` не допускают mass-assignment запрещённых полей; `@JsonIgnoreProperties(ignoreUnknown=true)` сохранён; `entryStepId`/`triggerValue` валидируются slug-regex.
   - **Input validation** — API-event input (`POST /api/integrations/v1/events`): event-имя валидируется до fan-out; dangling `entryStepId` отклоняется (422); duplicate `event_name` в воронке отклоняется (422).
   - **Error-isolation как контроль безопасности** — redirect/start путь сохраняет `try/catch(Throwable)` + swallow-and-WARN дисциплину `fire`/`dispatchForSubscriber`, чтобы redirect-фолт не валил webhook-job и не отдавал 5xx наружу.
4. Для каждой находки зафиксируй: severity (critical/high/medium/low/info), OWASP-категорию, файл и строку, описание уязвимости, конкретный fix.
5. Напиши отчёт в `work/17-funnel-multi-entry/logs/working/audit/security-auditor.json` (создай директорию при необходимости). Структура JSON: краткое summary (вердикт по фиче), затем находки сгруппированы по severity, затем явное подтверждение проверенных контролей (anti-IDOR CAS, fail-closed projectId, no-PII WARN, DoS-капы, mass-assignment defense) с указанием где они реализованы.

## Details

**Output:** `work/17-funnel-multi-entry/logs/working/audit/security-auditor.json` — отчёт по безопасности всей фичи.

**Главные зоны риска фичи (из техспека Risks + Decisions):**
- **Anti-IDOR (Decision 3):** `redirectExecution` CAS-predicate обязан включать `subscriberId` И `funnelId` (как `claimForCallback`). `executionId` берётся только из доверенного in-flight `exists`/lookup внутри диспетчера, не из входных данных запроса; CAS перепроверяет scope → mismatched-subscriber redirect = гарантированный no-op. Это ключевой контроль доступа — проверь его в первую очередь.
- **No-PII WARN (Decision 4, Risks → fire()/dispatch error-isolation):** новые WARN на CAS-loss/broken-cursor/redirect путях логируют только ids/коды, НИКОГДА `event_name`/`triggerValue`/PII. Phase-5 precedent против log-injection.
- **DoS / A04 (Decision 14):** `@Size` cap на `List<Trigger>` + service-level check (`funnel_step_invalid`/422); сохранённые keyword-капы `MAX_KEYWORDS=50`/`MAX_KEYWORD_LENGTH=64`; `/events` за rate-limit + fan-out ceiling. Массив переоткрывает DoS-поверхность (bloat, N×keyword scan, крупные PATCH payloads) — проверь, что капы реально стоят.
- **Fail-closed projectId:** redirect/start путь наследует fail-closed `projectId`-дисциплину `enrollSpecificFunnel`/`insertExecutionAt`. Subscriber и его выполнения строго scoped по projectId.
- **Mass-assignment / A08:** `TriggerDto`/`UpdateFunnelRequest` с `@JsonIgnoreProperties(ignoreUnknown=true)`; `entryStepId`/`triggerValue` через существующие slug-regex.

**Dependencies:** задачи 1-7 должны быть завершены (весь код фичи на месте). Зависит от того же кода, что аудитят Task 8 (code) и Task 10 (test) — три аудита независимы между собой и могут идти параллельно.

**Edge cases для проверки:**
- redirect с подменённым subscriberId (anti-IDOR) — должен быть no-op.
- event-имя из публичного `/events` с инъекционной нагрузкой в `triggerValue` — derived-query безопасна, лог чист.
- переполнение массива триггеров / keywords (DoS) — отклонено капами до fan-out.
- `entryStepId`, не разрешающийся в `stepsSnapshot` (broken cursor) — терминальный фейл только этого выполнения, без утечки данных в лог.

**Implementation hints:**
- Источник истины по точному списку файлов — `decisions.md` (отчёты задач) + секция Implementation Tasks техспека. Если отчёт задачи указывает файл, не перечисленный выше, всё равно прочти его.
- Сверяй фактический код с заявленными контролями (Decisions 3/4/14): аудит фиксирует расхождение между обещанным контролем и реализацией как находку.
- Группируй находки по severity; в конце явно подтверди проверенные контроли с указанием файла:строки, где они реализованы.
