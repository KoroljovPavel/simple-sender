## Description

Resolve the `auth → security` циклічну залежність на рівні імпортів ДО атомарного flip-коміту Wave 2 (Phase B). Зараз `AuthService` (модуль `auth`) імпортує `RememberMeWebSessionIdResolver` (модуль `security`) лише заради одного публічного String-константи `REMEMBER_ME_ATTR = "com.botfunnel.auth.rememberMe"`. Це створює `auth ↔ security` циркулярність, яка інакше форсувала б одночасну міграцію обох модулів у атомарному коміті.

Завдання: створити новий публічний клас `common/SessionAttributes.java` з константою, переключити всі імпорт-сайти на новий клас, оновити тести. Проєкт ВЕСЬ ЧАС лишається повноцінно компільованим на реактивному стеку (WebFlux / `Mono`/`Flux` не чіпаємо). Це чистий рефакторинг — нуль зміни поведінки, нуль зміни runtime-залежностей.

Контекст для агента:
- Це Wave 1 (pre-flip cleanup), parallelizable з Task 2.
- Tech-spec Decision 7 і user-spec D7 пояснюють чому саме перенесення константи (а не inline літералу) — string duplication крихка для двох модулів.
- Після цього таску `AuthService` імпортує з `common`, `RememberMeWebSessionIdResolver` імпортує з `common`, жоден файл з `auth/` і `security/` НЕ імпортує один одного.
- Назва пакету: `com.botfunnel.common`. Назва файлу: `SessionAttributes.java`. Видимість класу: `public`. Константа: `public static final String REMEMBER_ME_ATTR = "com.botfunnel.auth.rememberMe"`.

**Implementation hints:**
- Utility-class pattern для `SessionAttributes`: `public final class SessionAttributes { private SessionAttributes() {} public static final String REMEMBER_ME_ATTR = "..."; }` — final-клас + приватний конструктор унеможливлюють інстанціювання / наслідування.

У runtime жоден існуючий request на flight не зламається, бо JVM працює зі строковими-pool reference'ами, і обидва сайти (writer / reader) тепер посилаються на той самий новий клас, що містить ту саму строку.
