## Description

Full-feature code quality audit across the entire `migrate-to-virtual-threads` change set (Phase A: Tasks 1-2; Phase B atomic flip: Tasks 3-10; Phase C verification + docs: Tasks 11-13). This is the first task of the Audit Wave — it precedes Security Audit (Task 15) and Test Audit (Task 16), each of which has its own focus. Code Audit covers correctness, consistency, control-flow clarity, and cross-component design integrity that survived the WebFlux → MVC + virtual-threads migration.

The audit is non-blocking by default: it produces a written report listing findings classified by severity. Severity classification follows the standard code-reviewing skill (critical / major / minor / nit). Critical or major findings are the signal to follow-up engineering work; the audit itself does NOT fix them. The audit is its own review — there are no downstream reviewers spawned on this task.

Focus areas (from tech-spec line 474):

1. **Cross-component duplication after `HttpRequestUtils` extraction.** Verify the 4 original IP/UA extraction sites (3 controllers + `AuthService`) all delegate to `HttpRequestUtils.extractIp(...)` / `extractUserAgent(...)` and that no residual copy-paste remains.
2. **`SecurityContextHolder` (servlet) vs `ReactiveSecurityContextHolder` (no leakage).** Grep the full diff: zero remaining references to `ReactiveSecurityContextHolder`, `ServerSecurityContextRepository`, `@EnableWebFluxSecurity`, or any reactive Spring Security type in production sources. Verify that `SecurityContextHolder.getContext()` / `getAuthentication()` usages are consistent and read from the servlet thread-local correctly.
3. **`HttpSession` vs `WebSession` separation.** Verify zero `org.springframework.web.server.WebSession` imports remain in production sources. Verify `HttpSession` is consistently consumed where session-bound state is read/written (login, change-password, logout, remember-me attribute write). Verify session-fixation `request.changeSessionId()` (or `HttpSession.invalidate()` + new session) is called on successful login per D3 / D6 / SecurityConfig design.
4. **`MongoTemplate` consistency vs hidden reactive references.** Verify zero `ReactiveMongoTemplate`, `ReactiveMongoRepository`, `com.mongodb.reactivestreams.client.MongoClient` references in production sources. Verify the dual-MongoClient setup (Spring main + JobRunr) per D11 is correct: two distinct sync `MongoClient` beans, no accidental cross-wiring.
5. **`RestClient` construction consistency between `TelegramApiClient` and `TelegramSender`.** Verify both clients construct `RestClient` with the same base-URL convention, same connect/read timeout configuration, and same JSON message-converter setup. Verify the per-component singleton pattern from `patterns.md` (one `@Component`, one client) is preserved.
6. **Control-flow clarity of imperative rewrites of former Reactor chains** in `TelegramWebhookController.receive(...)` and `ProcessTelegramUpdateJob.handle(String)`. Verify the imperative if/else + try/catch shape preserves: (controller) 401-vs-404 status-distinguishing carve-out, explicit-status no-body responses, `DuplicateKeyException` → 200 idempotent path, outer 500 fallback; (job) event-write-before-status-flip ordering, CAS first-writer-wins invariant, all 17 former `.block()` sites now direct sync calls. Flag any logic divergence from the pre-migration semantics, dead branches, missed early returns, or unclear nesting.
7. **Correct error mapping in `GlobalErrorHandler`.** Verify `@ExceptionHandler(MethodArgumentNotValidException.class)` is wired and the previous `@ExceptionHandler(WebExchangeBindException.class)` is gone. Verify `BindingResult` extraction produces the same `ErrorResponse(message, null)` body (preserves `code: null` invariant per AC17). Verify other exception mappings (`IllegalArgumentException`, `DuplicateKeyException`, `IllegalStateException`, generic `Exception` fallback) are preserved or correctly migrated.

Out of scope for this audit (covered by sibling audits): security analysis (CSRF, session fixation policy, token scrubbing, rate-limit fail-open semantics) lives in Task 15; test coverage / test design / `StepVerifier` → JUnit migration correctness lives in Task 16. Code Audit may NOTICE security or test concerns but should DEFER findings to those audits with a pointer rather than redo the analysis.

**Severity rubric (from code-reviewing skill):**
- **Critical:** bug breaking documented behaviour, security regression, build/test breakage. Must be fixed before merge.
- **Major:** correctness risk, design inconsistency that will compound, missing invariant. Should be fixed before merge unless explicitly deferred.
- **Minor:** code-style or readability concern; safe to defer.
- **Nit:** cosmetic. Author discretion.

**Dependencies:** All Phase A + Phase B + Phase C tasks (Tasks 1-13) must be marked `done` before this audit runs. The audit reads the post-flip code state; running it pre-flip yields meaningless results.

**Edge cases:**
- If a file in the scope list is missing post-merge (e.g. `RememberMeWebSessionIdResolver` was deleted per D3), record it as "deleted as expected" rather than a finding.
- If a grep gate returns matches inside string literals, log messages, or test fixtures, classify as nit (cosmetic) unless the literal is a code reference (e.g. a comment claiming "Mono<>" pattern is still in use).
- Documentation in `patterns.md` / `architecture.md` / `deployment.md` is updated by Task 13 — if grep finds reactive symbols there, that is a Task 13 escape, not a production-code finding; record it under "Deferred to Task 13 follow-up".

**Implementation hints:**
- The audit is observational. Do NOT modify source files. The output is a report only.
- Use the code-reviewing skill's 11-dimension checklist as a prompt, but only score the dimensions relevant to this audit's 7 focus areas. Security and tests are sibling-audit territory — note-and-defer, do not redo.
- Reading order: start with `SecurityConfig`, then walk outward to controllers, services, repositories. The security shell sets the framing for everything else.
- Report length target: 300-800 lines of Markdown. Below 300 likely missed coverage; above 800 likely re-doing sibling audits.
