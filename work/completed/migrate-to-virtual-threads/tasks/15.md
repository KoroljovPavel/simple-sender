# Task 15: Security Audit

## Required Skills

Перед выполнением задачи загрузи:
- `/skill:security-auditor` — [.claude/skills/security-auditor/SKILL.md](../../../.claude/skills/security-auditor/SKILL.md)

## Description

Full-feature security audit of the WebFlux → MVC + virtual-threads migration. The migration rewrites the entire authentication shell (`SecurityConfig`), the session-cookie write path (`RememberMeWebSessionIdResolver` → `RememberMeCookieSerializer`), the CSRF protection wiring (`csrfCookieMaterializer WebFilter` deleted; MVC `CsrfFilter` + `XorCsrfTokenRequestAttributeHandler` introduced), the validation-error mapping (`WebExchangeBindException` → `MethodArgumentNotValidException`), the webhook payload-size filter (`OncePerRequestFilter` rewrite), the outbound Telegram HTTP clients (`WebClient` → `RestClient` with hand-rolled retry loops), and the entire service layer's blocking-shape (17 `.block()` sites dropped from `ProcessTelegramUpdateJob`; `Mono.fromCallable(boundedElastic())` ceremonies collapsed). Every surface that handles credentials, sessions, CSRF tokens, bot tokens, brute-force counters, or untrusted webhook payloads is touched.

This audit is the cross-cutting security gate for the whole feature. It runs after Wave 3 (Task 11 / Task 12 / Task 13) lands all production + test + documentation changes, and runs in parallel with Task 14 (code audit) and Task 16 (test audit) inside the Audit Wave. The audit is self-contained: it consumes the source tree and produces a written report. No reviewers — the audit IS the review for cross-cutting security.

Scope is OWASP Top 10 (2021) across every component touched by the migration, with explicit attention to the seven focus areas listed in tech-spec Task 15 plus the security-related TC10 (token-scrubber preservation) and TC11 (XSRF-TOKEN co-emission) technical acceptance criteria. The auditor must read the actual post-migration source — not infer from spec — and assert each invariant survives the imperative rewrite.

End state: an audit report file at `work/migrate-to-virtual-threads/logs/audits/security-audit.md` with severity-graded findings (Critical / High / Medium / Low), per-finding file:line references, attack vector + impact, and a remediation suggestion. A clean audit (zero Critical/High) is required before Task 17 pre-deploy QA opens.

## What to do

1. Read every source file modified or created in Wave 1 + Wave 2 + Wave 3, plus the audit-target test files that lock the security invariants. Use the file list in **Details → Files** as the authoritative scope. Do not audit files outside the feature touch-list — Task 14 covers general code quality elsewhere.
2. Perform a full OWASP Top 10 (2021) sweep across the audit scope. Categorise findings against A01–A10 plus the additional categories from the security-auditor skill (SSRF, hardcoded secrets, secure logging, dependency vulnerabilities).
3. For each of the seven focus areas below, produce an explicit pass/fail verdict with file:line evidence:
   - **(1) CSRF wiring.** Read `security/SecurityConfig`. Verify the MVC `CsrfFilter` setup uses `CookieCsrfTokenRepository.withHttpOnlyFalse()` paired with `XorCsrfTokenRequestAttributeHandler` (BREACH mitigation). Verify the CSRF disable matcher is `AndRequestMatcher(CsrfFilter.DEFAULT_CSRF_MATCHER, NegatedRequestMatcher(antMatcher("/webhooks/telegram/{projectId}")))` — i.e. AND-scoped to (a) state-changing verbs only AND (b) the webhook path only. Confirm GET/HEAD/OPTIONS on non-webhook paths still flow through CSRF protection. Confirm webhook path scoping is exact — no wildcard widening, no accidental `/webhooks/**` blanket.
   - **(2) Session fixation.** Read `auth/AuthService.login(...)` and any helpers it invokes. Verify that on successful authentication, `request.changeSessionId()` is called BEFORE `securityContextRepository.saveContext(...)`. Confirm pre-flip `WebSession.invalidate() + new session` semantics map correctly: a fresh `JSESSIONID` MUST be minted on every successful login, and any pre-login anonymous session attributes MUST NOT carry into the authenticated session. Tech-spec Architecture says `request.changeSessionId()`; tech-spec Task 15 description names `HttpSession.invalidate() + request.getSession(true)`. Both achieve fixation defence — flag the spec-internal divergence as a Low documentation finding and verify whichever the actual code uses.
   - **(3) Timing-attack guard.** Read `auth/AuthService.authenticate(...)` and the BCrypt-dummy-hash code path. Verify the dummy-hash branch is taken when the user is not found, so that login-with-nonexistent-user and login-with-wrong-password have indistinguishable wall-clock time. Confirm the dummy hash is a real BCrypt cost-12 hash (not a sentinel that short-circuits). Confirm no exception or early-return predates the dummy compare. Confirm BCrypt cost stayed at 12 across the migration.
   - **(4) Rate-limit fail-open semantics under VT.** Read `auth/AuthService` brute-force counter logic + `bot/BotService` bot-connect counter logic + `profile/ProfileService` change-password counter logic. Verify the sync Lettuce `INCR + EXPIRE + DEL` sequence preserves: (a) atomicity — no interleaving in the increment-then-set-TTL window that lets a counter live forever; (b) fail-open semantics — Redis down → request still served, log warning but don't block the user; (c) no VT-specific race where two virtual threads enter `INCR` concurrently and both see counter below threshold. Spec says these primitives are sync — confirm no `boundedElastic()` ceremonies survived. Flag any `try { redis.incr(...) } catch (...) { throw }` that converts a Redis outage into a 500 — regression vs. current fail-open.
   - **(5) Token scrubber preservation (covers TC10).** Walk every log site in the Telegram-API path. The 6 enumerated sites per tech-spec TC10: `TelegramWebhookController` DuplicateKey WARN; `TelegramWebhookController` enqueue-failure ERROR; `WebhookPayloadSizeFilter` 413 WARN; `ProcessTelegramUpdateJob` INFO/WARN/ERROR sites; `TelegramSender` 4xx/5xx/429/timeout sites. For each, confirm the `scrubTokens(...)` helper (or equivalent) is invoked on every log argument that may include a raw bot-token-shaped string. Confirm the helper itself is unchanged. Cross-reference with the `BotTokenLeakTest` (`ListAppender<ILoggingEvent>` style) — if a site lacks per-site coverage, raise a finding even if the scrubber appears to be invoked, because TC10 requires automation per site.
   - **(6) At-rest encryption — `TokenEncryptor` unchanged.** Diff `common/crypto/TokenEncryptor` (and any caller: `BotService`, `TelegramApiClient`, `TelegramSender`) against the pre-migration source. The encryption-at-rest path for bot tokens MUST NOT have changed — same algorithm, same key derivation, same IV handling, same authenticated mode. The migration is a runtime-stack swap; any incidental edit to `TokenEncryptor` is a Critical finding — key rotation / IV reuse risk.
   - **(7) `RememberMeCookieSerializer` does not leak token.** Read the new `security/RememberMeCookieSerializer`. Confirm: (a) the serializer extends `DefaultCookieSerializer` and overrides `writeCookieValue(CookieValue)` only — does NOT override the cookie name, value, or domain in a way that could embed the remember-me token in a header/attribute; (b) the `REMEMBER_ME_ATTR` request-attribute is read via `SessionAttributes.REMEMBER_ME_ATTR` (the new common constant) and only controls `setCookieMaxAge` — never written back into the cookie body, the path, the domain, the comment, or any custom attribute; (c) `HttpOnly`, `Secure`, `SameSite=Strict` flow from `ServerProperties.getServlet().getSession().getCookie()` via `PropertyMapper.alwaysApplyingWhenNonNull()` and are NOT silently dropped; (d) the Max-Age branching does not leak the remember-me bit into a separate cookie (e.g. a sibling `Set-Cookie: REMEMBER=1` that an attacker could read).
4. Additional cross-cutting checks the auditor MUST perform regardless of the seven focus areas:
   - **XSRF-TOKEN co-emission (TC11).** Verify that a logged-in user receives BOTH `SESSION=...` and `XSRF-TOKEN=...` cookies on the same response after login. The pre-migration `csrfCookieMaterializer WebFilter` is deleted; the replacement must be MVC `CsrfFilter` writing the token eagerly via `XorCsrfTokenRequestAttributeHandler.handle(request, response, deferredToken)`. Confirm via reading `SecurityConfig` + `AuthController.login(...)` + the `AuthControllerIT` post-login response assertions.
   - **Webhook authorisation invariants.** Read `TelegramWebhookController.receive(...)`. Confirm the 401-vs-404 status-distinguishing carve-out is preserved (`patterns.md` Webhook Ingestion). Confirm `WebhookPayloadSizeFilter` rejects chunked Transfer-Encoding and missing-Content-Length payloads before reaching the controller — DoS guard. Confirm the path matcher is exactly `/webhooks/telegram/{projectId}` (single segment — no path traversal via `..`).
   - **Tenancy guard.** Read `ProjectService.requireOwned(...)` after the non-reactive flip. Confirm the uniform 404 mapping is preserved across all three carve-outs (foreign-owned project / soft-deleted project / `IllegalArgumentException` on bad ObjectId hex). A divergence to 403 or 400 in any branch is an authorisation-bypass enumeration leak — anti-enumeration invariant from `patterns.md`.
   - **Concurrency-safe brute-force semantics under VT.** The migration removes implicit Reactor back-pressure. Verify that `BotService.connect(...)` still preserves the bot-connect race invariant: two parallel virtual-thread requests to claim the same bot must produce a `{200, 409}` status pair + exactly one persisted `bots` row + Telegram `setWebhook` count in `[1, 2]`. Confirm `BotConnectRaceIT` (new file under Task 7) asserts these invariants on real transport. A divergence here is an authorisation-and-integrity bug — two users could co-claim a bot under VT racing.
   - **Webhook idempotency under VT.** Verify `TelegramWebhookController.receive(...)` + `ProcessTelegramUpdateJob.handle(...)` preserve: (a) first-writer-wins CAS in `raw_updates`; (b) deterministic JobRunr UUID — so duplicate enqueue is a no-op; (c) duplicate-update DuplicateKey → 200 + scrubbed WARN. A divergence enables event duplication via webhook replay.
   - **Validation-error body shape (TC6/AC17).** Read `common/GlobalErrorHandler.handleMethodArgumentNotValidException(...)`. Confirm `code: null` invariant preserved AND `message` field uses the joined-error format `"<field>: <defaultMessage>"`. If `code` ever becomes non-null or the joiner shape changes, frontend `useApiError` breaks — flag as High (broken auth UI = user-facing security UX regression).
   - **`HttpRequestUtils` IP/UA extraction.** Read `common/HttpRequestUtils.extractIp(HttpServletRequest)`. If the helper trusts `X-Forwarded-For` / `X-Real-IP` without a known-proxy allowlist, it's a per-request IP-spoofing vector that lets attackers evade brute-force counters by sending an attacker-controlled header. Confirm the trust model matches the pre-migration behaviour — the existing reactive helper had specific trust rules; port them faithfully.
   - **Imperative rewrite control-flow.** Read the imperative rewrites of former Reactor chains: `TelegramWebhookController.receive(...)` (was `flatMap`/`switchIfEmpty`/`onErrorResume`), `TelegramSender.sendText(...)` (was stacked `.retryWhen`), `TelegramApiClient.setWebhook(...)` (was `Retry.backoff`). For each, confirm: error paths still emit audit events in the same order; deadlines (30s outer ceiling) are enforced; 429-wraps-5xx ordering invariant is intact; no exception swallowing introduced. A swallowed exception in an audit-event path is a security-logging gap (OWASP A09).
   - **Dependency vulnerabilities.** Read `build.gradle` and confirm the swap to `spring-boot-starter-web` + `spring-boot-starter-data-mongodb` + `spring-boot-starter-data-redis` (Boot 3.5.0) pulls only known-good versions. Cross-reference with CVE databases for any newly introduced transitive (Tomcat 10.x, sync Lettuce, sync MongoDB driver). The removed `reactor-test` is testImplementation-only — no production-CVE risk from removal.
5. Write the audit report to `work/migrate-to-virtual-threads/logs/audits/security-audit.md`. Required structure:
   - **Executive Summary** — overall verdict (PASS / PASS WITH CONDITIONS / FAIL), counts per severity, top-3 findings.
   - **Focus Area Verdicts** — one section per (1)–(7) above with explicit pass/fail + evidence.
   - **OWASP Top 10 Sweep** — one row per A01–A10 with verdict + brief justification.
   - **Findings** — one entry per finding, severity-graded (Critical / High / Medium / Low), with: file:line, attack vector, impact, remediation. Use OWASP category tags.
   - **Test Coverage Gaps** — security-specific gaps where automation does not lock an invariant the audit verified by reading code (cross-reference Task 16 test audit if applicable).
   - **Cleared Risks** — explicit attestation for each focus area + cross-cutting check that came out clean. This makes the audit auditable — a downstream reviewer can verify the auditor actually looked.
6. Re-run a quick consistency check: every Critical and High finding MUST have a concrete file:line and a concrete remediation. Findings without actionable fixes are not allowed (security-auditor skill rule).
7. If any Critical or High finding is raised, the feature is BLOCKED on Task 17 pre-deploy QA — note this explicitly in the Executive Summary and surface it back into `decisions.md`.

**Dependencies:**
- Wave 1 (Tasks 1, 2) — must be complete: stub flips + constant relocation are part of the audit scope.
- Wave 2 (Tasks 3–10) — must be complete: the entire atomic flip is the primary audit surface.
- Wave 3 (Tasks 11, 12, 13) — must be complete: AC16/AC17/AC18 test assertions lock invariants the audit needs to verify; the patterns.md "Virtual Threads" section documents pinning sites the audit references for fail-open / VT-race analysis.
- Runs in parallel with Task 14 (code audit) + Task 16 (test audit) within the Audit Wave (Wave 4). The three audits do not coordinate inputs — each audit produces an independent report. If Task 14 surfaces a control-flow issue that affects a security invariant, the security audit may reference Task 14's finding but is not blocked by Task 14.

**Edge cases:**
- **Pre-flip BSON fixture continuity (R5).** Task 12's AC16 test loads a hand-crafted BSON document representing the pre-flip `ReactiveMongoSessionRepository` byte-shape. The auditor must read this test and confirm the assertion actually verifies cross-repository compatibility — not just a freshly-written session. A test that writes-then-reads inside the same session repository proves nothing about migration continuity.
- **VT pinning vs. brute-force counter accuracy.** Lettuce sync API pins the VT on Netty futures (documented per Task 11 patterns.md). Confirm that the pinning does not introduce a race where a parked-but-not-yielded VT lets a second concurrent login through the gate. Lettuce sync is documented thread-safe; this is a paranoid check, not a presumed bug — but the auditor must trace the path explicitly.
- **`EmailService` try/catch swallowing SMTP errors (D15).** Per D15 the silent fire-and-forget semantics are preserved. Confirm the swallowed exception is logged — so SMTP outages are observable via logs. A silently dropped exception with no log entry is a security-logging gap (OWASP A09).
- **Removed `csrfCookieMaterializer` WebFilter.** The auditor must confirm the deletion did not orphan any consumer expecting an eagerly-resolved CSRF token. Read all controllers — if any expects `XSRF-TOKEN` to be present on the request side (rather than written to the response by `CsrfFilter`), the migration is incomplete.
- **Two `MongoClient` beans (D11).** The audit must confirm JobRunr's separate `MongoClient` does NOT accidentally bind to the wrong credentials/uri — a misbinding leaks JobRunr job payloads (potentially sensitive) to the wrong store. Read `JobRunrMongoConfig` and confirm explicit, separate property prefixes.
- **`scrubTokens` invocation on multi-line stack traces.** Several log sites pass `e.toString()` or `e.getMessage()` — confirm the scrubber runs on the full stack trace, not just the message. A bot token in a `RestClientException` cause chain that the scrubber misses is a per-request token leak.
- **Spec divergence: session fixation API.** Tech-spec Architecture says `request.changeSessionId()`. Tech-spec Task 15 description says `HttpSession.invalidate() + request.getSession(true)`. Both achieve fixation defence. Audit must report which one the actual code uses, and flag the spec-internal inconsistency as a Low documentation finding — not a security finding, but worth surfacing for spec hygiene.

**Implementation hints:**
- Skill load: `/skill:security-auditor` is the entry point. The skill enumerates OWASP categories + severity grading + report style. Follow it.
- Start with `SecurityConfig` — it's the trust-boundary root and gates focus areas (1), (2), (4), (7), plus cross-cutting checks (XSRF-TOKEN co-emission, tenancy entry-points).
- Diff `TokenEncryptor` against the pre-migration version. Use `git log` on the dev branch — the pre-flip commit is the parent of the Wave 2 atomic-flip commit. Any line change = Critical until proven cosmetic.
- For TC10 token-scrubber sites, the easiest enumeration: `grep -rn "log\.\(info\|warn\|error\)" backend/src/main/java/com/botfunnel/{bot,webhook}/` then cross-reference with the `scrubTokens(...)` call sites in the same files. A log call without a scrubber on a payload argument is a finding.
- For the imperative rewrite control-flow check, read the original reactive version in git history side-by-side with the new imperative version. Reactor chains that emit audit events via `.doOnNext` / `.doOnError` can lose ordering when rewritten as try/catch — verify the audit-event emission lines match between old and new.
- Do NOT spawn parallel agents for the audit. The skill is a single-agent linear walk through the scope — concurrency does not help and undermines cross-file consistency.
- The audit is unscored externally — no review wave on it. The discipline lever is the report's Cleared Risks section: an auditor who claims a focus area is clean MUST cite the file:line they read. A vacuous "all clear" is itself a finding against the audit quality.
