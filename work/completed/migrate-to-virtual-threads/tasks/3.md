## Description

Open the Wave 2 atomic flip by swapping the WebFlux ↔ MVC stack at the build + config layer and rewriting the security shell that auto-config keys off. This sub-task lands seven files (one delete, one new) inside the single physical Phase B commit per D5. It is the entry point of the cascade: the moment `spring-boot-starter-webflux` is replaced with `spring-boot-starter-web` in `backend/build.gradle`, every `Mono` / `Flux` / `ServerWebExchange` / `WebSession` / `ServerHttpSecurity` / `ReactiveMongoRepository` / `ReactiveRedisConnectionFactory` symbol leaves the classpath and the other Wave 2 sub-tasks (Tasks 4–10) become required for the project to compile. This sub-task is owned for: starter swaps, properties rename + VT enablement, the new servlet-stack `SecurityConfig`, the `RememberMeWebSessionIdResolver` → `RememberMeCookieSerializer` swap (per D3), and the `GlobalErrorHandler` exception-type swap (per AC17).

What ships:

- **`backend/build.gradle`** — three starter swaps (`spring-boot-starter-webflux` → `spring-boot-starter-web`; `spring-boot-starter-data-mongodb-reactive` → `spring-boot-starter-data-mongodb`; `spring-boot-starter-data-redis-reactive` → `spring-boot-starter-data-redis`) and drop `io.projectreactor:reactor-test` from `testImplementation`. `spring-boot-starter-security`, `spring-session-data-mongodb`, `spring-boot-starter-mail`, `spring-boot-starter-validation`, `org.mongodb:mongodb-driver-sync`, JobRunr starter, micrometer, mockwebserver, testcontainers, and `spring-security-test` remain untouched. Lombok is NOT added (AC4).
- **`backend/src/main/resources/application.properties`** — add `spring.threads.virtual.enabled=true` (AC5) and rename the three `server.reactive.session.cookie.*` keys to `server.servlet.session.cookie.*`. All env-var placeholders (`SESSION_COOKIE_SECURE`, `SESSION_COOKIE_SAME_SITE`) are preserved verbatim. `app.session.ttl-default-hours`, `app.session.ttl-remember-me-days`, and every non-session key are untouched.
- **`backend/src/test/resources/application-test.properties`** — audited for the same rename; the current file has no `server.reactive.session.cookie.*` keys so this is a no-op audit (verified at decomposition time) — record the audit outcome but only modify the file if a stray reactive cookie key is present.
- **`backend/src/main/java/com/botfunnel/security/SecurityConfig.java`** — full rewrite on the servlet stack. New imports: `@EnableWebSecurity`, `SecurityFilterChain`, `HttpSecurity`, `CookieCsrfTokenRepository`, `CsrfTokenRequestAttributeHandler`, `CsrfFilter`, `HttpSessionSecurityContextRepository`, `org.springframework.web.cors.UrlBasedCorsConfigurationSource`, `AndRequestMatcher`, `NegatedRequestMatcher`, `AntPathRequestMatcher` (or its `antMatcher(...)` factory). Beans exposed: `SecurityFilterChain`, `SecurityContextRepository` (servlet variant), `PasswordEncoder` (`BCryptPasswordEncoder(12)` — unchanged), and the new `CookieSerializer` bean. CSRF: `CookieCsrfTokenRepository.withHttpOnlyFalse()` paired with `CsrfTokenRequestAttributeHandler` (the non-Xor variant — matches the current reactive `ServerCsrfTokenRequestAttributeHandler` choice; the Xor variant would break the cookie round-trip because `CookieCsrfTokenRepository` writes the raw token while Xor expects an XOR-masked token from the request → 403 on every state-changing call; carry forward the explanatory comment from the current `SecurityConfig`). Webhook path exclusion expressed as `AndRequestMatcher(CsrfFilter.DEFAULT_CSRF_MATCHER, NegatedRequestMatcher(antMatcher("/webhooks/telegram/{projectId}")))` so non-excluded paths retain GET safety and the path stays single-segment (anti-leak invariant from `patterns.md` "Scoped CSRF disable"). Auth rules order: `/health` permitAll, `/api/auth/**` permitAll, `/webhooks/telegram/{projectId}` permitAll (ordered BEFORE `/api/**`), `/api/**` authenticated, `anyRequest()` authenticated. CORS allowedOrigins from `${app.url}`, methods `GET, POST, PATCH, DELETE, OPTIONS`, headers `Content-Type, X-Requested-With, X-XSRF-TOKEN`, `allowCredentials=true`. `httpBasic` and `formLogin` disabled. The reactive-only `csrfCookieMaterializer()` `WebFilter` is removed entirely — MVC `CsrfFilter` invokes the request-attribute handler eagerly so the XSRF-TOKEN cookie is written without a helper filter (closes the regression risk under TC11; AC18/Task 12 verifies cookie co-emission).
- **`backend/src/main/java/com/botfunnel/security/RememberMeWebSessionIdResolver.java`** — DELETE. Replaced by the new serializer below; no callers remain after this sub-task lands because the new `@Bean CookieSerializer` shadows Spring Session's auto-configured default.
- **`backend/src/main/java/com/botfunnel/security/RememberMeCookieSerializer.java`** — NEW, `extends DefaultCookieSerializer` (per D3). Constructor wires every cookie attribute from `ServerProperties.getServlet().getSession().getCookie()` via `PropertyMapper.alwaysApplyingWhenNonNull()`: `setCookieName`, `setUseHttpOnlyCookie`, `setUseSecureCookie`, `setSameSite`, `setCookiePath`, `setDomainName`. This mirrors the cookie-attribute pass-through pattern in the deleted reactive resolver so the `SESSION_COOKIE_*` env vars and `server.servlet.session.cookie.*` config keys flow through unchanged (closes the AC18 cookie-flag continuity guarantee). Overrides `writeCookieValue(CookieValue)` to read `SessionAttributes.REMEMBER_ME_ATTR` from `cookieValue.getRequest().getAttribute(...)`; when present and `Boolean.TRUE`, call `cookieValue.setCookieMaxAge((int)(rememberMeDays * 86400L))`. When absent or `Boolean.FALSE`, leave the default (`-1`) so the cookie is session-scoped. After branching call `super.writeCookieValue(cookieValue)`. `rememberMeDays` is injected from `${app.session.ttl-remember-me-days:30}` so `SESSION_TTL_REMEMBER_ME_DAYS` continues to drive the value. Registered as `@Bean CookieSerializer` inside `SecurityConfig` so Spring Session's `@ConditionalOnMissingBean` default is shadowed (TC5).
- **`backend/src/main/java/com/botfunnel/common/GlobalErrorHandler.java`** — swap `@ExceptionHandler(WebExchangeBindException.class)` → `@ExceptionHandler(MethodArgumentNotValidException.class)` (servlet equivalent). Pull `BindingResult` via `ex.getBindingResult()` and reuse the same `getFieldErrors()` + `getGlobalErrors()` extraction, the same `", "` joiner, and the same `new ErrorResponse(message, null)` body — preserves the `code: null` invariant (AC17) and pins the joined-message format that `useApiError` may parse. The `AppException`, `ResponseStatusException`, and `Throwable` handlers stay byte-identical. Imports: drop `org.springframework.web.bind.support.WebExchangeBindException`; add `org.springframework.web.bind.MethodArgumentNotValidException`.

The result of this sub-task in isolation is: classpath flipped to servlet starters; properties file VT-enabled and cookie-prefix-renamed; security shell rewritten for servlet stack with CSRF / remember-me / CORS wiring functional; validation 400 path wired to the servlet exception. The project still does not compile until Tasks 4–10 land in the same physical commit (D5 atomicity) — the compile-success verify-smoke gate is therefore exercised at the Wave 2 boundary, not at the end of this sub-task.

**Edge cases:**
- `REMEMBER_ME_ATTR` absent on a non-login request (lazy session creation, any flow that triggers cookie write without going through `AuthService.openSession`): `writeCookieValue` must leave the default `Max-Age=-1` (session-scoped). Skipping the cookie write or throwing is a regression.
- `REMEMBER_ME_ATTR == Boolean.FALSE` (explicit "remember-me off" login): same behaviour as "absent" — session-scoped cookie.
- A future `Cookie` field added by Boot (e.g. `partitioned`) that the manual `PropertyMapper` does not forward: documented `[TECHNICAL]` deviation, not a block.
- Two concurrent logins (different users, same JVM): the serializer is a singleton but holds no per-request mutable state — every read of `cookieValue.getRequest().getAttribute(...)` is per-call.
- Logout: Spring Session's standard servlet flow clears the cookie via `Set-Cookie: ...; Max-Age=0` independently of the serializer's per-request branching. No code in this task touches the logout path; AC18 covers this case via Task 12.
- CSRF cookie write without the deleted `csrfCookieMaterializer`: MVC's `CsrfFilter` invokes the request-attribute handler eagerly so the XSRF-TOKEN cookie is materialised on every safe-verb response — TDD Anchor `csrfCookie_writtenOnSafeVerbRequest` is the regression guard.

**Implementation hints:**
- Import `CsrfFilter.DEFAULT_CSRF_MATCHER` from `org.springframework.security.web.csrf.CsrfFilter` (servlet variant — distinct from the reactive `CsrfWebFilter.DEFAULT_CSRF_MATCHER` you are deleting).
- For `antMatcher("/webhooks/telegram/{projectId}")` use the static factory `AntPathRequestMatcher.antMatcher(...)` if Spring Security 6.x exposes it on your version; otherwise instantiate `new AntPathRequestMatcher("/webhooks/telegram/{projectId}")`. Either form participates in `AndRequestMatcher` correctly.
- `HttpSessionSecurityContextRepository` is a singleton — exposing it as a `@Bean` mirrors the current reactive pattern of letting `AuthService` autowire and call `saveContext(...)` after login.
- **CSRF handler choice (corrected from tech-spec):** use `new CsrfTokenRequestAttributeHandler()` — the servlet equivalent of the **non-Xor** `ServerCsrfTokenRequestAttributeHandler` the current reactive `SecurityConfig` already uses on purpose. The tech-spec text mentions `CsrfTokenRequestAttributeHandler`, but the existing reactive `SecurityConfig` deliberately opted out of the Xor variant (see the inline comment at the reactive `csrfTokenRequestHandler(...)` site) because the Xor handler breaks the `CookieCsrfTokenRepository` round-trip — the cookie repository writes the raw token, while the Xor handler expects an XOR-masked token from the request, producing a 403 mismatch on every state-changing call. Treat the tech-spec wording as a documentation drift; the correct servlet handler is the non-Xor `CsrfTokenRequestAttributeHandler` and the implementation note must repeat the same warning comment so a future reader does not re-introduce Xor. Record this as a Post-completion note for tech-spec correction (Architecture + Decision rationale).
- `DefaultCookieSerializer` lives in `org.springframework.session.web.http.DefaultCookieSerializer`. `CookieValue` is the static inner type `DefaultCookieSerializer.CookieValue`. Both are public in `spring-session-core` (already on classpath via `spring-session-data-mongodb`).
- Do NOT log session id, cookie value, or any `SecurityContext` content from `RememberMeCookieSerializer.writeCookieValue` — security invariant preserved from the deleted resolver (audited in Wave 4 / Task 15).
- The `RememberMeCookieSerializer` `@Bean` definition replaces Spring Session's `@ConditionalOnMissingBean` default — once registered, the auto-config does not run. TC5 + the `SecurityConfigTest` boot assertion are the regression guards.
