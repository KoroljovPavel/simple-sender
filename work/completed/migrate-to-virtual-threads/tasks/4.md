# Task 4: Repositories — `ReactiveMongoRepository` → `MongoRepository`

## Required Skills

Перед выполнением задачи загрузи:
- `/skill:code-writing` — [skills/code-writing/SKILL.md](../../../.claude/skills/code-writing/SKILL.md)

## Description

This task flips all 5 Spring Data MongoDB repository interfaces from the reactive driver to the synchronous driver as part of the Wave 2 atomic flip (see tech-spec D5/D9 — Wave 2 lands as ONE physical commit). The interfaces are leaves in the dependency graph: they have no callers inside this task, but downstream services and controllers (Tasks 5–9) consume their return types. Flipping the return types here is a hard prerequisite for the rest of Wave 2 — once `spring-boot-starter-data-mongodb-reactive` is replaced by `spring-boot-starter-data-mongodb` (Task 3), `ReactiveMongoRepository` leaves the classpath and these interfaces must already be on the sync base.

Per tech-spec Architecture line 32 and the repository description on line 391: custom finder signatures change as follows — `Mono<T>` → `Optional<T>`, `Flux<T>` → `List<T>`, `Mono<Long>` → `long`. The base interface flips from `ReactiveMongoRepository<T, String>` to `MongoRepository<T, String>`. No method bodies exist (these are pure interfaces); the change is purely at the type-signature layer. Reactor imports (`reactor.core.publisher.Mono`, `reactor.core.publisher.Flux`) are removed entirely; `java.util.Optional` and `java.util.List` are added where the new return types require them.

Reviewer note: `security-auditor` is intentionally omitted from this task's reviewer set per tech-spec line 393. Rationale: this is a pure type-signature refactor with no auth or data-handling surface; cross-cutting security concerns are picked up by the Audit Wave (Task 15) which reads every file modified across the feature.

## What to do

1. Edit `UserRepository.java`:
   - Switch base interface from `ReactiveMongoRepository<User, String>` to `MongoRepository<User, String>`.
   - Convert the three `Mono<User>` finders (`findByEmail`, `findByEmailVerificationTokenHash`, `findByPasswordResetTokenHash`) to return `Optional<User>`.
   - Convert the `Flux<User> findByStatusAndDeletedAtBefore(...)` finder to return `List<User>`.
   - Replace Reactor imports with `java.util.List` and `java.util.Optional` plus the sync `MongoRepository` import.

2. Edit `ProjectRepository.java`:
   - Switch base interface to `MongoRepository<Project, String>`.
   - Convert the three `Flux<Project>` finders (`findByOwnerIdAndDeletedAtIsNullOrderByCreatedAtDesc`, `findByOwnerIdOrderByCreatedAtDesc`, `findByDeletedAtBefore`) to `List<Project>`.
   - Convert `Mono<Long> countByOwnerIdAndDeletedAtIsNull(...)` to primitive `long` (Spring Data sync driver returns primitive `long` for count-derived queries).
   - Convert the two `Mono<Project>` finders (`findByOwnerIdAndNameAndDeletedAtIsNull`, `findByOwnerIdAndNameAndIdNotAndDeletedAtIsNull`) to `Optional<Project>`.
   - Replace Reactor imports with sync ones.

3. Edit `BotRepository.java`:
   - Switch base interface to `MongoRepository<Bot, String>`.
   - Convert `Mono<Bot> findByProjectIdAndStatus(...)` to `Optional<Bot>`.
   - Convert `Flux<Bot> findByProjectId(...)` to `List<Bot>`.
   - Convert `Mono<Bot> findFirstByTelegramBotIdAndStatus(...)` to `Optional<Bot>`.
   - Replace Reactor imports with sync ones.

4. Edit `EventRepository.java`:
   - Switch base interface to `MongoRepository<Event, String>`.
   - No custom finders to convert — the body stays empty. Only the base interface line and the import change.

5. Edit `RawUpdateRepository.java`:
   - Switch base interface to `MongoRepository<RawUpdate, String>`.
   - Convert `Mono<RawUpdate> findFirstByProjectIdAndUpdateId(...)` to `Optional<RawUpdate>`. Preserve the existing class-level comment about indexed lookup vs scan — it remains accurate post-flip.
   - Replace Reactor imports with sync ones.

6. After all five files are flipped, run `./gradlew compileJava` locally to confirm the project still compiles. Note: per tech-spec Wave 2 description (line 380), other Wave 2 sub-tasks (3, 5, 6, 7, 8, 9, 10) co-flip the consumers of these return types in the same physical commit, so an in-isolation compile attempt of just this task before the rest of Wave 2 lands is expected to fail at consumer call sites. The local compile check is therefore deferred to after the full Wave 2 commit is assembled.

Per tech-spec Testing Strategy (lines 272–290), `StepVerifier`-based unit tests in consuming services (Tasks 5–9) migrate from `thenReturn(Mono.just(x))` to `thenReturn(Optional.of(x))` / `thenReturn(List.of(...))` / `thenReturn(<long>)` in their respective tasks; those test migrations are NOT in scope for this task because they belong to the services that own them. The acceptance gate for this task is therefore compilation of the consumers after Wave 2 fully lands, not a dedicated unit test.
