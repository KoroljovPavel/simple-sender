## Description

Part of Wave 2 atomic flip (`Tasks 3-10` land as ONE physical commit per D5/D9). This sub-task flips the three project-scoped service trees — `project/`, `bot/`, `profile/` — from reactive (`Mono`/`Flux` + `ServerWebExchange` + `WebSession` + `ReactiveMongoTemplate` + `ReactiveRedisTemplate`) to synchronous servlet-stack APIs running on Spring MVC + virtual threads.

These three modules MUST flip together because they share `ProjectService.requireOwned(...)` as the cross-module tenancy guard. `BotService.connect/disconnect/getByProject/sendTestMessage` all call `projectService.requireOwned(...).then(...)` as the first step of every chain (the platform's anti-enumeration access primitive — foreign owner / soft-deleted / malformed-ObjectId all collapse to a uniform 404 with the literal message `"Project not found"`). Splitting them across commits would either break the build or force a temporary `Mono`-wrapping shim that delivers zero value.

Key surface changes:
- **`ProjectService.requireOwned(ownerId, projectId, includeSoftDeleted): Mono<Project>` → `Project`** (per signature mapping in code-research §3). Anti-enumeration 404 mapping preserved: foreign-owned → 404, soft-deleted without flag → 404, `IllegalArgumentException` from bad ObjectId hex → 404, missing → 404. All four paths collapse to `AppException.notFound("Project not found")`.
- **`ProjectController.list(boolean): Mono<ResponseEntity<Flux<ProjectResponse>>>` → `ResponseEntity<List<ProjectResponse>>`** per D6. MVP cap of 5 projects per user (`app.projects.max-per-user=5`) makes streaming JSON meaningless at this scale; UI consumes the full response.
- **`BotService` brute-force counter (`brute:bot-connect:{userId}`) INCR+EXPIRE+DEL atomicity** preserved via synchronous Lettuce primitives (`StringRedisTemplate.opsForValue().increment(...)` / `.expire(...)` / `.delete(...)`). D14 fail-open semantics preserved (sustained Redis outage → WARN log on the pinned `REDIS_FAIL_OPEN_WARN` string + chain continues; never converts to 429).
- **`ProfileService.changePassword/deleteAccount`** lose the `WebSession session` parameter — replaced with `HttpSession session` (passed in from controller). `terminateAllSessionsExcept(userId, currentSessionId)` keeps its `_id`-not-equal query against the `sessions` collection unchanged. BCrypt match/encode become direct synchronous calls (no `Mono.fromCallable + subscribeOn(boundedElastic)`).
- **All 3 controllers** drop `ServerWebExchange` in favour of `HttpServletRequest` for IP/UA extraction (delegate to the new `common/HttpRequestUtils.extractIp(...)` + `.extractUserAgent(...)` from Task 5 per D13). `currentUserId()` switches from `ReactiveSecurityContextHolder.getContext().map(...)` to `SecurityContextHolder.getContext().getAuthentication()`.
- **ITs migrate to MockMvc** in-process (`AbstractIntegrationTest` provides `@Autowired MockMvc mockMvc` from Task 10). State-changing requests use the `csrf()` request post-processor (`SecurityMockMvcRequestPostProcessors.csrf()`) — the MockMvc equivalent of `webTestClient.mutateWith(csrf())`.
- **Bot-connect race test extracts** to a new `BotConnectRaceIT` class per D14, configured with `@SpringBootTest(webEnvironment = RANDOM_PORT)` + `TestRestTemplate` over loopback Tomcat. MockMvc's in-process DispatcherServlet dispatch does NOT reliably interleave critical sections under a parked-VT release barrier — real transport is required to genuinely race two POSTs through the security filter + service layer. Uses `ConcurrencyTestUtils.parallelInvoke(...)` (D10, created by Task 10) to guarantee N VTs are parked at a `CountDownLatch` barrier before simultaneous release.

End state: `project/`, `bot/`, `profile/` are fully synchronous on the servlet stack; `requireOwned` returns `Project` directly (no `.flatMap`); race-test invariants `{200, 409}` status pair + exactly-one-CONNECTED-row + `delCount == setCount - 1` preserved on real Tomcat transport; tenancy guard semantics unchanged (caller probing for project existence still learns nothing).

**Edge cases:**
- **Anti-enumeration 4-way 404 collapse in `requireOwned`** — verify EVERY path produces the same `AppException.notFound("Project not found")` with no differentiating information leaked: foreign owner (different `ownerId`), soft-deleted without `includeSoftDeleted=true`, missing (`Optional.empty()` from `findById`), `IllegalArgumentException` from `findById` on bad ObjectId hex. The current `.onErrorMap(IllegalArgumentException.class, ...)` migrates to a `try { repository.findById(...) } catch (IllegalArgumentException e) { throw AppException.notFound(MESSAGE_NOT_FOUND); }`. Test: `requireOwned_throwsNotFound_whenIdMalformed` MUST cover the bad-hex case.
- **D14 deletedAt-FIRST guard in `restore`** — preserve the guard BEFORE quota check and name-collision check. An already-active project must NOT be mutated (no silent " (restored)" suffix appended). The guard is defense-in-depth against future regressions.
- **D14 INCR-every-attempt on `BotService.connect`** — counter increments BEFORE the Telegram call, not only on failure. This closes the Connect-then-Disconnect-then-Connect bypass that an INCR-on-failure-only counter (auth pattern) would leave open. The 11th attempt within the 15-min window throws `AppException.tooManyRequests(...)` with NO Telegram calls — verified by `BotServiceTest::connect_eleventhAttemptWithinWindow_returns429_noTelegramCalls`.
- **D4 compensating deleteWebhook on persist failure** — if `botRepository.save` throws `DuplicateKeyException`, the prior successful `setWebhook` must be rolled back via `telegramApiClient.deleteWebhook(token)`. Compensation errors are swallowed (logged via `TelegramApiClient.scrubTokens(...)`); the ORIGINAL persist error propagates to the caller. Order matters: compensation FIRST, then throw.
- **`mapPersistError` driver-fallback** — when `DuplicateKeyException.getMessage()` does NOT contain `projectId_unique_connected` or `telegramBotId_unique_connected` (driver omits the index name), re-query the platform-wide partial unique index via `botRepository.findFirstByTelegramBotIdAndStatus(...)`. If found → `bot_already_connected` 409; else → `bot_already_in_project` 409. This must NOT crash on a `null` exception message.
- **AC13b fail-open on Disconnect Telegram failure** — persistent Telegram failure on `telegramApiClient.deleteWebhook(token)` during Disconnect MUST NOT block the local update. WARN log on pinned `TELEGRAM_DISCONNECT_WARN` string + Bot doc still flipped to DISCONNECTED + 200 returned to the caller. The plaintext token is decoded → decrypted → passed to deleteWebhook → never logged.
- **Token-scrub on every Telegram log site** — every `log.warn(..., err.getMessage())` involving Telegram errors MUST wrap the message via `TelegramApiClient.scrubTokens(...)`. WebClient transport-error messages embed the request URI which carries the token; sync `RestClient`/`RestTemplate` errors are similar. Currently this is at lines 188–189 (compensation), 245 (Disconnect) in `BotService.java` — preserve both. Audit the rewritten code with `grep -n "log\.\(warn\|error\)" backend/src/main/java/com/botfunnel/bot/BotService.java` and verify every `getMessage()` is scrub-wrapped.
- **Change-password brute-force counter (`change-pwd:fail:{userId}`)** — threshold 5, TTL 15 minutes. Counter increments ONLY on BCrypt mismatch (failure path) — not on success. This differs from `BotService` D14 INCR-every-attempt because the user is already authenticated; the rate limit guards against a hijacked-session brute-force of the current password. The 6th attempt within the window trips 429 — verify in `ProfileServiceTest`.
- **Spring Session `_id` field** — Spring Session's `MongoSession.MONGO_ID = "_id"` stores the session ID literally in the `_id` field of the `sessions` collection. `terminateAllSessionsExcept` excludes the current session by `_id != currentSessionId`. After flip, `sessionRepository` (auto-configured by `spring-session-data-mongodb`, NON-reactive variant) reads the same field path. Task 12 strengthens this with a BSON-fixture assertion (AC16) — leave the field-path assertion in `ProfileControllerIT` as-is for this task.
- **CSRF in `BotConnectRaceIT`** — `TestRestTemplate` does NOT support the MockMvc `csrf()` post-processor. Preferred path: emit `XSRF-TOKEN` cookie on first GET, then echo it back as the `X-XSRF-TOKEN` header on the parallel POSTs (matches AC18 cookie scheme). Alternative: override security config for this test class to disable CSRF (drifts from production — discouraged).
- **`HttpSession.invalidate()`** — synchronous, returns `void`. Differs from `WebSession.invalidate()` which returned `Mono<Void>`. The `deleteAccount` flow calls `terminateAllSessions(userId)` FIRST (removes ALL session docs including the current one), THEN `session.invalidate()` (which becomes a near-no-op for the cookie clean-up but is still called for the Set-Cookie removal signal). Order matters.
