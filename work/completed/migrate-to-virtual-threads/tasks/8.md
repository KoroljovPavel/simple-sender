# Task 8: Telegram clients + retry — TelegramApiClient + TelegramSender + tests

## Required Skills

Before starting, load:

## Description

Rewrite both outbound Telegram clients (`TelegramApiClient` + `TelegramSender`) from Reactor `WebClient` onto Spring 6 `RestClient` (per D1) with hand-rolled retry loops (per D2). Production HTTP behaviour must remain byte-for-byte identical, including the retry ladder, the 429-wraps-5xx ordering invariant, the overall 30s deadline on `TelegramSender`, the `isTransient` cause-chain walking, the `requireValidTokenShape` precondition, audit-event emission order, token-scrubber sites on every log line, and the `attempts==4` test invariant for the `[5xx, 429, 5xx, 200]` interleaving sequence.

This is part of the Wave 2 atomic flip commit (per D5): `WebClient`/`Mono`/`Flux` symbols leave the classpath when `spring-boot-starter-webflux` is removed in Task 3, so this rewrite MUST land in the same physical commit. The hand-rolled loops shape:
- `TelegramApiClient`: single `for (attempt = 0..3)` loop, 200ms→2s exponential backoff, ~10s overall ceiling, `isTransient` filter walking the cause chain (now matching `RestClientResponseException` / `HttpServerErrorException` types instead of `WebClientResponseException`).
- `TelegramSender`: outer `while(true)` for 429 retry-after (jittered, clamped `[0..30s]`), inner `for(attempt = 0..3)` for 5xx 1s→2s→4s. 30s outer ceiling enforced via deadline-based check (`Instant deadline = Instant.now().plus(Duration.ofSeconds(30))` captured at chain start; checked before every sleep and every retry attempt — throws `TelegramSendException(null, "timeout", attempts)` when exceeded). `TelegramRateLimitException` sentinel survives untouched.

Tests (`TelegramApiClientTest`, `TelegramSenderTest`, `TelegramSenderIT`) lose `StepVerifier` and `Mono`/`Flux` imports — assertions become direct (`assertThat(client.getMe(token))...`, `assertThatThrownBy(() -> sender.sendText(...))...`). MockWebServer fixtures carry over unchanged because MockWebServer operates at the HTTP-protocol level.

Result: outbound Telegram HTTP fully synchronous on `RestClient` over JDK `HttpClient`; production behaviour identical including retry semantics, audit ordering, scrubber coverage, and the `attempts==4` interleaving invariant.

## What to do

1. Rewrite `TelegramApiClient.java`:
   - Replace `WebClient` field and constructor wiring with a `RestClient` field. Construct `RestClient` via `RestClient.builder().baseUrl(baseUrl).requestFactory(JdkClientHttpRequestFactory)` with the same 5s connect timeout + 10s response timeout currently enforced on Reactor `HttpClient`. Preserve the `DefaultUriBuilderFactory` with `EncodingMode.NONE` so `{token}` path-variable encoding stays unchanged.
   - Flip `getMe(String)`, `setWebhook(String, String, String)`, `deleteWebhook(String)` from `Mono<X>` to plain return types (`TelegramUser`, `boolean`, `boolean`). Preserve `requireValidTokenShape(token)` precondition at method entry.
   - Replace the Reactor `Retry.backoff(3, 200ms).maxBackoff(2s)` pipeline with a private `for (int attempt = 0; attempt <= 3; attempt++)` loop. Inside the loop: call the `RestClient` synchronously, catch transient exceptions matched by `isTransient`, compute backoff (`200ms * 2^attempt`, capped at `2s`), `Thread.sleep(backoff)`, continue. On `isTransient` filter mismatch — rethrow immediately. On retries-exhausted — throw `AppException(BAD_GATEWAY, "telegram_unavailable", ...)` mirroring current `onRetryExhaustedThrow`.
   - Rewrite `mapClientError(...)` to operate on `RestClientResponseException` (or `HttpClientErrorException` from `RestClient`'s `defaultStatusHandler`). Preserve the body-deserialization-with-empty-fallback shape; preserve `toAppException(...)` semantics including all token-scrubber call sites and the 401 → `invalid_bot_token` carve-out.
   - Update `isTransient(...)` cause-chain matcher: replace `WebClientResponseException w && w.getStatusCode().is5xxServerError()` with the `RestClient` analog (`RestClientResponseException` whose status is 5xx, or `HttpServerErrorException`). Keep the `IOException`/`TimeoutException` branches. Drop the `ReadTimeoutException` branch if it's a Netty-only type post-flip — replace with the JDK `HttpTimeoutException` if needed.
   - Promote-as-public constants (`DEFAULT_RESPONSE_TIMEOUT`, `CONNECT_TIMEOUT`) and the `requireValidTokenShape`, `isTransient`, `scrubTokens` helpers stay public — they are consumed by `TelegramSender` and by `BotService` log sites.

2. Rewrite `TelegramSender.java`:
   - Replace `WebClient` field and constructor wiring with `RestClient` (same shape as `TelegramApiClient`). Preserve the package-private test constructor that lets unit tests dial down `responseTimeout` and `overallTimeout`.
   - Flip `sendText(String, Long, String, String, String)` from `Mono<SentMessage>` to `SentMessage`. Replace `botRepository.findById(botId)` (`Mono<Bot>`) chain with a synchronous call (returns `Optional<Bot>` post-Task-4) and explicit `.filter(...).orElseThrow(() -> AppException.notFound(MESSAGE_BOT_NOT_FOUND))` filtering for `BotStatus.CONNECTED`.
   - Implement the nested-loop structure per Architecture section + D2:
     - Capture `Instant deadline = Instant.now().plus(overallTimeout)` ONCE at the start of `sendText(...)` — before either loop.
     - Outer 429 loop: `while (true) { try { return sendOnceWithRetryOn5xx(...); } catch (TelegramRateLimitException tr) { check deadline; sleep(clamp(retry_after,0,30)s + jitter[0..200ms]); check deadline; } }`. Deadline check before AND after the sleep — must throw `TelegramSendException(null, "timeout", attempts.get())` if exceeded.
     - Inner 5xx loop: `for (int attempt = 0; attempt <= 3; attempt++) { try { return sendOnce(...); } catch (Throwable ex) { if (!isTransient(ex)) throw ex; if (attempt == 3) throw new TelegramSendException(null, "transient_failure_exhausted", attempts.get()); check deadline; sleep(1s * 2^attempt, capped at 4s); check deadline; } }`.
   - Preserve `AtomicInteger attempts` semantics: declared once in `sendText(...)`, incremented once per `RestClient` request invocation (the same site that `.doOnSubscribe(s -> attempts.incrementAndGet())` covers today). This counter persists across BOTH retry loops — that is the invariant the `[5xx, 429, 5xx, 200] → attempts==4` test asserts.
   - Preserve audit-event emission ordering end-to-end (this is the critical invariant). Today `.doOnSuccess` and `.doOnError` fire post-chain; in the imperative rewrite:
     - On success (`SentMessage sm` returned): call `eventService.logEvent(ownerId, EVENT_TELEGRAM_MESSAGE_SENT, null, null, sentMetadata(botId, sm))` BEFORE returning `sm` to the caller.
     - On terminal failure (caught at outermost level, `isTerminalAuditable(ex)` true): emit `log.error(...)` with `scrubTokens(ex.getMessage())` FIRST, then `eventService.logEvent(ownerId, EVENT_TELEGRAM_SEND_FAILED, null, null, failedMetadata(...))`, then rethrow.
     - Pre-HTTP `AppException(404)` (bot-not-found/disconnected) and leaked `TelegramRateLimitException` must NOT emit audit events (today's `isTerminalAuditable` guard is the same).
   - Preserve every existing token-scrubber site on log lines (per TC10 in tech-spec line 354):
     - 4xx warn: `log.warn("Telegram 4xx ({}): {}", rawStatus, scrubbed)` — `scrubbed = TelegramApiClient.scrubTokens(result.description())`.
     - 429 warn: `log.warn("Telegram 429 retry_after={}s: {}", retryAfter, scrubbed)`.
     - 5xx transient retry log: `log.warn("Telegram transient retry #{} after error: {}", attempt+1, scrubTokens(ex.getMessage()))`.
     - 429 rate-limit wait log: `log.warn("Telegram 429 — waiting {}s + {}ms jitter", delaySeconds, jitterMs)`.
     - ok=false/missing message_id warn: `log.warn("Telegram ok=false or missing message_id: {}", scrubbed)`.
     - Terminal failure error: `log.error("Telegram send terminal failure attempts={}: {}", attempts.get(), scrubTokens(ex.getMessage()))`.
   - `map4xx(...)` / `toThrowable(...)` semantics unchanged: 401 → `BotTokenInvalidException`, 429 → `TelegramRateLimitException(retry_after)`, other 4xx → `TelegramSendException(rawStatus, scrubbed, attempts.get())`. Switch from reactive `ClientResponse` body-deserialization to `RestClient`'s error-handler `(request, response) -> {...}` with `objectMapper.readValue(response.getBody(), TelegramSendResult.class)` (or `RestClientResponseException.getResponseBodyAsByteArray()`).
   - Body-mapping (`mapBodyToSentMessage(...)`) becomes synchronous: returns `SentMessage` on success, throws `TelegramSendException` on `ok=false`/missing `message_id` (no more `Mono.just` / `Mono.error`).

**Edge cases (all preserved from current implementation — do NOT silently drop any):**
- Empty 4xx response body: `mapClientError` must produce `TelegramResult(false, null, null, null)` fallback (today's `.onErrorResume(ex -> Mono.just(...)).defaultIfEmpty(...)` pattern) — preserve the equivalent in synchronous form.
- 429 with missing `retry_after`: treated as `retryAfter=0` (no sleep), still classified as 429.
- 429 with negative `retry_after`: clamped to 0 (`Math.max(0, ...)`).
- 429 with `retry_after > 30`: clamped to 30 (`Math.min(retry_after, 30)`).
- `isTransient` cause-chain ends with self-reference (`cur.getCause() == cur`): the existing loop bails out via `if (next == cur) break;` — preserve.
- AES-GCM decrypt failure during `tokenEncryptor.decrypt(...)`: propagates as 500 (NOT mapped to `BotTokenInvalidException`) — per existing comment at TelegramSender.java:147-149.
- Base64-decode failure on stored IV/ciphertext: produces `BotTokenInvalidException` (422), per current TelegramSender.java:143-146.
- `ok=false` body OR missing `message_id`: throws `TelegramSendException(null, scrubbed, attempts.get())` — same warn log as today.
- JSON `chat.id` missing in response body: fallback to caller-provided `chatId` per existing `extractChatId` helper.

- For `RestClient` body deserialization: use `restClient.post().uri(...).body(map).retrieve().toEntity(TelegramSendResult.class)` for the success path; install a `defaultStatusHandler(HttpStatusCode::is4xxClientError, (req, resp) -> { ... read body, throw mapped exception ... })` for 4xx; 5xx propagates naturally as `HttpServerErrorException` which the `isTransient` cause-chain matcher will catch.
- For sleep + deadline: a helper method like `private void sleepWithDeadlineCheck(Duration d, Instant deadline, AtomicInteger attempts)` centralises both checks (before sleep + after sleep) and keeps the deadline rule in one place.
- For `Thread.sleep` `InterruptedException` handling: re-set the interrupt flag (`Thread.currentThread().interrupt()`) and throw `TelegramSendException(null, "interrupted", attempts.get())`. The current Reactor pipeline doesn't have this concern; the imperative version does.
- For `RestClient.Builder`: pass it through the constructor for testability (the same way today's `WebClient.Builder` is passed). Don't construct `RestClient.builder()` inside the constructor — that breaks the test-injectable pattern.
- 30s outer ceiling check ordering matters: check deadline BEFORE the sleep (avoid an unnecessary sleep that would overshoot) AND AFTER the sleep (in case the clock advanced during the sleep, common under VT scheduling).
- Keep all currently-public statics public — `BotService` and `TelegramSender` consume `TelegramApiClient.scrubTokens`, `TelegramApiClient.isTransient`, `TelegramApiClient.requireValidTokenShape`, `TelegramApiClient.DEFAULT_RESPONSE_TIMEOUT`, `TelegramApiClient.CONNECT_TIMEOUT`.
