## Description

Wave 2 atomic-flip task that finalises the webhook ingestion + JobRunr worker + admin-seed surfaces to the servlet/MVC + virtual-threads stack. This is the last production-code surface in the atomic flip commit (alongside Task 6 service trees, Task 7 controllers/security, Task 8 outbound Telegram), after which all `Mono`/`Flux`/`ServerWebExchange`/`WebFilter` symbols leave the production classpath.

Three concrete deliverables, scoped together because they share the JobRunr + webhook ingestion correctness invariants and must land in the same physical commit per D5 / D9:

1. **`ProcessTelegramUpdateJob.handle(String)` — drop 17 `.block()` sites.** Per code-research §5(d) the worker contains 17 `.block()` call sites against `RawUpdateRepository`, `ProjectRepository`, `BotRepository`, `ReactiveMongoTemplate` (two `findAndModify` sites), `SubscriberService` (already flipped in Task 2 — verify drop is clean), `FunnelTriggerService` (same), and `EventService.logEventBlocking(...)`. Field `private final ReactiveMongoTemplate reactiveMongoTemplate` renames to `private final MongoTemplate mongoTemplate`. Return-type adjustments: `Mono<T>` → `Optional<T>` / `T` / nullable (per repository finder shape). Preserve invariants verbatim: (a) re-entry guard short-circuit on `RawUpdateStatus.DONE`; (b) **event-write-before-status-flip** — every `eventService.logEvent(...)` returns BEFORE the rawUpdate flip to `DONE`; (c) atomic `findAndModify` CAS for `Bot.ownerChatId` first-writer-wins (null return = predicate-fail benign no-op); (d) failure path — atomic `findAndModify` FAILED-with-scrubbed-truncated-error, rethrow NEW `RuntimeException(simpleClassName + ": " + scrubbedMessage)` with `setStackTrace` and no cause chain.

2. **`WebhookPayloadSizeFilter` — rewrite as `OncePerRequestFilter`.** Replace `implements WebFilter` + `filter(ServerWebExchange, WebFilterChain): Mono<Void>` with `extends OncePerRequestFilter` + `doFilterInternal(HttpServletRequest, HttpServletResponse, FilterChain)`. Keep `@Order(Ordered.HIGHEST_PRECEDENCE + 10)` (registered as Spring bean — Spring Boot picks up filters via `FilterRegistrationBean` ordering). Preserve all current behaviour per `patterns.md` Webhook Ingestion section:

   - Reject `Content-Length > 1_048_576`.
   - On reject: scrubbed WARN log (projectId + reason + headers), increment `telegram_webhook_rejected_total{reason=payload_too_large}` counter (filter owns it — `grep "payload_too_large" backend/src/main/java/.../TelegramWebhookController.java` must return zero matches), set 413 status, write empty body via `response.setStatus(...)` + `return` without chaining. **Edge cases:**

- **`Bot.ownerChatId` CAS race:** Two workers race to populate `ownerChatId` for the same bot on a first private-chat `/start`. After flip, `mongoTemplate.findAndModify(query, update, Bot.class)` returns `null` for the loser (predicate-fail = `Mono.empty()` analog). Treat null as benign no-op — do not log ERROR, do not throw. Current test `ownerChatIdCas_firstWriterWins_secondCallNoOp` must pass unchanged.

- **JobRunr retry overlap (re-entry guard):** JobRunr can re-dispatch a job whose previous attempt ack didn't arrive in time. First action in `handle(...)` must be load + `if status == DONE return` — no event write, no stub call. Without this guard double-event-fire breaks AC-13 audit invariants.

- **DuplicateKey self-heal (controller):** `rawUpdateRepository.save(row)` throws `DuplicateKeyException` if a prior request inserted the row and the current request retries (Telegram retries on its own timeout). Re-enqueue with the same deterministic UUID (JobRunr `enqueue(UUID, lambda)` is idempotent at the UUID level — duplicate is a no-op). Return 200 so Telegram stops retrying. Without this branch a PENDING orphan rawUpdate stays forever.

- **Worker rethrow with no cause chain (token leak guard):** `throw new RuntimeException(simpleClassName + ": " + scrubbedTruncatedMessage); newEx.setStackTrace(t.getStackTrace());` — DO NOT use `throw new RuntimeException(msg, t)` because `t.getCause().getMessage()` would re-leak the raw token via JobRunr's `jobrunr_jobs` failure row and the ERROR log path. Class-name prefix is compile-time constant, safe.

- **Multi-value `Transfer-Encoding` case-fold:** `Transfer-Encoding: gzip,Chunked` is HTTP-1.1 legal and must still reject. `Collections.list(request.getHeaders(name))` → stream → `toLowerCase(Locale.ROOT).contains("chunked")`. Turkish-locale JVM dotless-i bug is the reason `Locale.ROOT` is mandatory.

- **Malformed ObjectId collapse to 404 (anti-enumeration):** Spring Data MongoDB throws `IllegalArgumentException` for bad ObjectId strings. Without the catch, the response would be 500 (and `GlobalErrorHandler` would write a JSON body). With it, the response is 404 — same as missing project — so an attacker cannot distinguish "malformed id" from "missing project" via status.

- **Missing-Content-Length on webhook path:** Telegram contract guarantees Content-Length. Missing it is anomalous and must reject with 413 + `reason=missing_content_length`. `request.getContentLengthLong() == -1` is the missing/unparseable indicator. Empty body (`Content-Length: 0`) passes the filter and the controller's `@RequestBody required=true` produces a Spring 400 downstream.

- **Test seam (`BiConsumer<UUID, String> enqueuer`):** The package-private `setEnqueuer(...)` lets the self-heal IT inject a failing enqueue (e.g. always-throw). After flip, the lambda no longer wraps in `Mono.fromRunnable` — it calls `jobScheduler.enqueue(...)` directly. Tests that swap the lambda continue to work: throw → outer catch-all → 500. The self-heal scenario (save succeeds → enqueue fails → Telegram retries → DuplicateKey self-heal → re-enqueue → 200) tests both the controller and the JobRunr idempotency-at-UUID behaviour.

- **Counter tag cardinality (`projectId`):** `RECEIVED_TOTAL` tags each success increment with `projectId` per `meterRegistry.counter(RECEIVED_TOTAL, "projectId", projectId).increment()`. SimpleMeterRegistry tolerates this at our volume; do not switch to Tag.of caching for this counter (the reject counters DO cache via @PostConstruct because their tags are static-set strings).

- **`logEventBlocking` → `logEvent` (D12):** The `Blocking`-named variant disappears in Wave 2 along with the sync collapse. Every caller in this task's scope renames. The fire-and-forget `void logEvent(...)` variant ALSO disappears (per D12). Only one signature remains: `Event logEvent(String, String, String, String, Map<String,Object>)` returning `Event`.
