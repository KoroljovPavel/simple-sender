# Ручне тестування — 04 Telegram-боти

Консолідований чек-лист усіх сценаріїв, які треба перевірити **руками** після
деплою фіч `06-bot-connection` (04a), `07-telegram-sender` (04c) і
`08-webhook-ingestion` (04b) на staging. Реальний Telegram + `@BotFather` +
ngrok неможливо автоматизувати в CI, тому це єдиний пост-деплой gate.

Джерела:
- `work/completed/06-bot-connection/user-spec.md` (AC1–AC23)
- `work/completed/07-telegram-sender/user-spec.md` (AC1–AC23)
- `work/completed/08-webhook-ingestion/user-spec.md` (AC1–AC19)
- `docs/staging-smoke/06-bot-connection.md`
- `docs/staging-smoke/07-telegram-sender.md`
- `docs/staging-smoke/08-webhook-ingestion.md`

Час виконання: ~30 хв на повний прогін (10 + 5 + 15).

## Загальні передумови

- [ ] Staging URL бекенду досяжний: `GET {APP_URL}/health` → `HTTP 200`.
- [ ] Staging frontend задеплоєний і вказує на той самий бекенд.
- [ ] Test-owner-аккаунт (`smoke_test_owner@…`) із принаймні одним проектом.
- [ ] Персональний Telegram-аккаунт під рукою (мобільний або desktop).
- [ ] `mongosh` із доступом до staging Mongo (`db: botfunnel`).
  Connection string у secret store — НЕ вставляти в чат/коміти/скріншоти.
- [ ] (для локального staging) `ngrok` встановлено:
  `brew install ngrok` + `ngrok config add-authtoken <token>` одноразово.

**Безпека:** ніколи не вставляти в чат/комміти/скріншоти:
- bot-token (`1234567890:AAH...`)
- `BOT_TOKEN_ENCRYPTION_KEY` (staging env)
- staging `mongosh` connection string
- реальні numeric chat ids
- JWT/session кукі

## Частина 1 — 04a Bot Connection (~10 хв)

### Підготовка throwaway-бота

- [ ] **1.1 Створити бот у `@BotFather`.**
  - У Telegram: `@BotFather` → `/newbot`vm
  - Display name: `SmokeTest_<initials>_<date>` (наприклад `SmokeTest_pk_20260517`)
  - Username: має закінчуватись на `_bot` (наприклад `SmokeTest_pk_20260517_bot`)
  - Скопіювати токен виду `1234567890:AAH...` (~45 символів).
  - Якщо username зайнятий → інший суфікс.

### Connect happy-path (AC1, AC10, AC21, AC22)

- [ ] **1.2 Залогінитись як `smoke_test_owner@…`** у staging-frontend.
- [ ] **1.3 Відкрити Settings → Bot** у проекті.
  Має бути видно форму Connect із password-input, hint
  `"Get one by messaging @BotFather → /newbot"`, disabled-кнопку Connect.
- [ ] **1.4 Вставити токен → Connect.** Протягом ~5 секунд:
  - форма замінюється на **Connected view**
  - видно `@SmokeTest_<…>_bot` (username, великий/жирний)
  - видно `first_name` із BotFather
  - masked-token виду `1234567890:•••...xyz` (U+2022 bullets)
  - кнопка **Send Test Message** (enabled)
  - кнопка **Disconnect** (enabled)
- [ ] **1.5 i18n parity.** Перемкнути локаль uk ↔ en — усі `bot.*` рядки
  локалізовані без `[missing]`/key-fallback.

### Connect помилки (AC2, AC3, AC4, AC5, AC11)

- [ ] **1.6 Невалідний format токена** (`abc123`, без `:` або з неправильною
  довжиною secret) → інлайн-помилка `errors.bot.connect.400`
  ("Bot token has invalid format"). Жодного network-call до Telegram
  (перевірити в DevTools Network — реквесту на `/connect` ще не було або 400
  з backend без проксі до Telegram).
- [ ] **1.7 Token revoked / 401 від Telegram** (взяти бот, ревокнути у
  BotFather через `/revoke`, спробувати connect старим токеном) →
  `errors.bot.connect.422` ("Token is invalid or revoked"). `bots` doc у
  Mongo НЕ створений.
- [ ] **1.8 Rate-limit (AC11).** Зробити 11+ спроб Connect із невалідним
  токеном протягом 15 хв (можна різні токени, що падають на 400/422) →
  11-та спроба повертає `errors.bot.connect.429`. Після успішного Connect
  counter скидається.

### Bot-uniqueness (AC6, AC7, AC12)

- [ ] **1.9 Платформо-широка унікальність (AC6).** Створити другий
  test-проект у тому ж user → Settings → Bot → вставити **той самий**
  токен → Connect → `errors.bot.connect.409` ("This bot is already
  connected to another project").
  **Перевірити:** повідомлення НЕ містить імені першого проекту, email
  власника або будь-якого ідентифікатора (R2 — anti-leak).
- [ ] **1.10 Per-project unique (AC7).** Створити ще один throwaway-бот у
  BotFather → у тому самому проекті (де вже є connected bot) вставити
  його токен → Connect → `errors.bot.connect.409`
  ("another bot is already connected — disconnect it first").

### Webhook конфігурація (AC10, AC20)

- [ ] **1.11 Перевірити webhook у BotFather.** `@BotFather → /mybots →
  SmokeTest_…_bot → Bot Settings → Webhook` → URL field має містити
  `{staging-APP_URL}/webhooks/telegram/{projectId}` точно.
- [ ] **1.12 Webhook secret як SHA-256 (AC20, R7).** У `mongosh`:
  ```
  db.bots.findOne({projectId: "<projectId>", status: "CONNECTED"}, {webhookSecretHash: 1})
  ```
  `webhookSecretHash` — hex/base64 рядок ~64 chars. Plaintext-секрету в
  колекції немає.

### Security & token leak (AC17, AC18, AC23)

- [ ] **1.13 Token masked в UI (AC18).** На Connected view токен
  показується як `1234567890:•••...xyz`. Кнопки "Show full token" НЕ
  існує.
- [ ] **1.14 Token не повертається в API (AC17).** DevTools Network →
  response на `POST /api/v1/projects/{id}/bot/connect` НЕ містить полів
  `token`/`encryptedToken`/raw-token-substring.
- [ ] **1.15 Audit event без токена (AC23).** У `mongosh`:
  ```
  db.events.find({eventType: "bot_connected", createdAt: {$gte: new Date(Date.now()-10*60*1000)}}).limit(1)
  ```
  Жодне поле `metadata.*` не містить рядка виду `\d+:[A-Za-z0-9_-]{35}`
  (Telegram token shape).

### Send Test Message stub-гілка (AC15)

- [ ] **1.16 До запуску 04b/04c success-гілки:** натиснути **Send Test
  Message** → інлайн-помилка `errors.bot.testMessage.422`
  ("Send /start to your bot in Telegram first, then try again").
  *(Це stub-поведінка фічі 04a; справжній send закриває 04b/04c —
  див. Частина 2/3.)*

### Disconnect (AC13, AC19)

- [ ] **1.17 Disconnect modal.** Клікнути **Disconnect** → модалка з
  копією:
  *"Disconnect bot @SmokeTest_…_bot? Incoming messages will stop and
  the webhook will be removed. You can reconnect anytime."*
  Кнопки Cancel / Disconnect.
- [ ] **1.18 Cancel у модалці** → модалка закривається, нічого не
  змінилось. API-call НЕ відбувся.
- [ ] **1.19 Disconnect → Confirm.** Протягом ~3 сек UI повертається на
  порожню форму Connect.
- [ ] **1.20 Webhook очищено в BotFather.** `@BotFather → /mybots →
  SmokeTest → Bot Settings → Webhook` → URL field порожній.
- [ ] **1.21 Mongo: soft-disconnect (D17).** `mongosh`:
  ```
  db.bots.find({projectId: "<projectId>"}).sort({createdAt: -1}).limit(2)
  ```
  Має бути запис із `status: "DISCONNECTED"`,
  `encryptedTokenCiphertext: null`, `webhookSecretHash: null`,
  `tokenSuffix: null`, `disconnectedAt: <timestamp>`.

### Reconnect (AC12)

- [ ] **1.22 Reconnect тим самим токеном.** Вставити токен повторно →
  Connect → Connected view знову. У Mongo має бути **два** документи
  для `projectId`: один `DISCONNECTED`, один `CONNECTED` (D17 —
  append-only, не in-place update).

### Disconnect 404 (AC13)

- [ ] **1.23 Disconnect ще раз** (через UI це не змодуливо, але `curl`):
  ```
  curl -X POST -b session=... {APP_URL}/api/v1/projects/{id}/bot/disconnect
  ```
  → `404` коли нема `CONNECTED`-боту.

### GET bot endpoint (AC14)

- [ ] **1.24 `GET /api/v1/projects/{id}/bot`** через DevTools на page-mount:
  - якщо бот connected → 200 + `{telegramBotId, telegramUsername, ...}` без токена
  - якщо нема → 404

### Webhook 401 (AC2)

- [ ] **2.17 401 без secret.** `curl`:
  ```
  curl -i -X POST -H "Content-Type: application/json" \
    {APP_URL}/webhooks/telegram/<projectId> -d '{}'
  ```

### Webhook 404 (AC3)

- [ ] **2.18 404 на неіснуючий project.** `curl`:
  ```
  curl -i -X POST -H "Content-Type: application/json" \
    -H "X-Telegram-Bot-Api-Secret-Token: random" \
    {APP_URL}/webhooks/telegram/507f1f77bcf86cd799439011 -d '{}'
  ```
  - `HTTP/1.1 404`
- [ ] **2.19 404 на soft-deleted project.** Soft-delete тест-проект через

### Payload size 1 MB (AC4)

- [ ] **2.20 413 на > 1 MB.** Згенерувати payload >1 MB:
  ```
  dd if=/dev/zero bs=1M count=2 | base64 > /tmp/big.json
  curl -i -X POST -H "Content-Type: application/json" \
    -H "X-Telegram-Bot-Api-Secret-Token: <correct>" \
    {APP_URL}/webhooks/telegram/<projectId> --data-binary @/tmp/big.json
  ```
  - `HTTP/1.1 413 Payload Too Large`
- [ ] **2.21 `/api/**` ліміт залишився 256 KB** (NOT global bump).
  Послати >256 KB на `/api/v1/projects/<id>` із валідним sessionом →
  413 (підтверджує scoped-config).

### CSRF (AC15)

- [ ] **2.22 CSRF active на /api/**.** Залогінитись, дістати session cookie,
  зробити POST на `/api/v1/projects` **без** `X-XSRF-TOKEN`:
  ```
  curl -i -X POST -b "session=..." {APP_URL}/api/v1/projects -d '{}'
  ```
  - `HTTP/1.1 403` (CSRF protection вмикається).
- [ ] **2.23 CSRF disabled на webhook**. Webhook 401-тест (крок 2.17) НЕ
  повертає 403 з CSRF reason — лише 401.

### Idempotency (AC5)

- [ ] **2.24 Той самий update_id двічі.** Це найкраще через інтеграційний
  тест — manual можна симулювати:
  - надіслати `/start ref_idempotent`,
  - подивитись `updateId` у `raw_updates` (`db.raw_updates.find().sort({createdAt:-1}).limit(1)`),
  - відправити curl із тим же payload (включаючи `update_id`) і
    правильним secret:
  ```
  curl -i -X POST -H "Content-Type: application/json" \
    -H "X-Telegram-Bot-Api-Secret-Token: <correct>" \
    {APP_URL}/webhooks/telegram/<projectId> \
    -d '{"update_id": <тот же>, "message": {...}}'
  ```
  - `HTTP/1.1 200 OK`
  - `db.raw_updates.count({updateId: <…>})` = 1 (без дубля).

### Webhook на disconnected bot (R5)

- [ ] **2.25 Disconnect bot → orphan webhook відсік.** У UI Disconnect.
  Швидко (поки Telegram може ще ретраїти) надіслати `/start` боту чи
  curl-ом симулювати update з валідним secret-ом (із cache).
  Очікувано: secret check fails → 401 (бо `webhookSecretHash` стерто).

### Failed-queue (AC14)

- [ ] **2.26 Перевірка Failed-queue** (виконати, лише якщо у кроках 2.5–2.16
  траплявся `processingStatus: "FAILED"`):
  ```
  db.raw_updates.find({processingStatus:"FAILED"}, {projectId:1, updateId:1, processingError:1, createdAt:1}).sort({createdAt:-1}).limit(5)
  db.jobrunr_jobs.find({state:"FAILED"}, {jobName:1, exceptionMessage:1, updatedAt:1}).sort({updatedAt:-1}).limit(5)
  ```
  - `processingError` scrubbed (нема bot-token substrings, ≤1024 chars).
  - Якщо токен у `processingError` — security regression M6, bug-репорт
    негайно.

### Observability counters (AC16)

- [ ] **2.27 Counters інкрементуються.** Це переважно integration-test

### Race на ownerChatId (AC6)

- [ ] **2.28 Другий `/start` від іншого користувача** не перезаписує
